# GitOps for agent configuration

## Summary
OpenGitOps (a CNCF working group) defines GitOps as four principles for a system's desired state: declarative, versioned and immutable, pulled automatically, and continuously reconciled by software agents. Its glossary leaves persistent application data out of the desired state and asks the state store (git, canonically) for access control and auditing. Claude Code's project files (`.claude/settings.json`, `CLAUDE.md`, `.mcp.json`, skills, subagents) are declarative and can live in git, and Claude Code reloads several of them into a running session. Nothing in Claude Code itself pulls them from git, though, and local and user files can drift from the committed state. Only managed settings outrank every other layer. Agent memory, transcripts and task lists are runtime data, not desired state. For agent workloads that run on Kubernetes, Azure offers two pull-based reconcilers as cluster extensions on AKS and Azure Arc-enabled Kubernetes: Flux v2 (`microsoft.flux`), whose controllers pull Git, Helm, Bucket or Azure Blob sources and apply them every interval (10 minutes by default), and Argo CD (`microsoft.argocd`, GA on AKS, preview on Arc), which polls about every 3 minutes, marks drift as OutOfSync and syncs it back only under an automated sync policy (with `selfHeal` for live edits and `prune` for deletions). Both reconcile Kubernetes objects; no official page names a git reconciler for Windows endpoints or Claude Code settings.

## Facts

### OpenGitOps principles and terms
- GitOps is defined as a set of principles for operating and managing software systems, rooted in widely adopted practice; the desired state of a GitOps-managed system must meet four principles. [DOC S-43ycwzdw]
- Principle 1, Declarative: the system's desired state is expressed declaratively; principle 2, Versioned and Immutable: it is stored so that immutability and versioning are enforced and a complete version history is kept. [DOC S-43ycwzdw]
- Principle 3, Pulled Automatically: software agents pull the desired state declarations from the source; principle 4, Continuously Reconciled: they keep observing the actual state and attempt to apply the desired state. [DOC S-43ycwzdw]
- The desired state is all configuration data sufficient to recreate the system so that instances behave indistinguishably; it generally excludes persistent application data such as database contents, though it often includes the credentials or recovery configuration for that data. [DOC S-5pzuphp4]
- A state store holds immutable versions of the desired state and should provide access control and auditing on changes to it; git is the canonical example, but any system meeting the criteria may serve. [DOC S-5pzuphp4]
- Pull is required rather than push so that agents can read the desired state at any time; unlike CI/CD's pre-set triggers, reconciliation runs whenever actual state diverges, whether by drift or by an intentional change. [DOC S-5pzuphp4]
- "Continuous" means reconciliation keeps happening, not that it is instantaneous; drift is actual state moving away from the desired state. [DOC S-5pzuphp4]
- A GitOps-managed software system includes its runtime environments, the management agents within each, and policies controlling access to and management of repositories, deployments and runtimes. [DOC S-5pzuphp4]

### Flux v2 on AKS and Azure Arc-enabled Kubernetes (microsoft.flux)
- GitOps on AKS and Azure Arc-enabled Kubernetes uses Flux, which takes Git and Helm repositories, Buckets and Azure Blob Storage as sources and YAML, Helm and Kustomize as templates. Flux runs on each cluster and is pull-based: neither the source repository nor any other cluster needs access to the cluster. [DOC S-7na2vvh5]
- GitOps is enabled as the cluster extension `Microsoft.KubernetesConfiguration/extensions/microsoft.flux`, which must be on the cluster before any `fluxConfigurations` resource. It installs itself with the first `fluxConfigurations`, or by hand through the portal, `az k8s-extension create --extensionType=microsoft.flux`, an ARM template or REST. It runs in the `flux-system` namespace at cluster scope only. [DOC S-7na2vvh5]
- By default the extension installs the Flux Source, Kustomize, Helm and Notification controllers, the FluxConfig CRD, `fluxconfig-agent` and `fluxconfig-controller`; the Flux `image-automation` and `image-reflector` controllers are optional. [DOC S-7na2vvh5]
- What each controller reconciles: Source syncs Git repositories, Helm repositories, Buckets and Azure Blob storage and serves the latest content as a tar archive; Kustomize applies Kustomize or raw YAML from the source; Helm applies `HelmRelease` objects from a Helm repository source; Notification forwards events from all controllers to webhooks. [DOC S-7na2vvh5]
- The Azure side is a second loop: `fluxconfig-agent` polls the Kubernetes Configuration data plane for new or changed `fluxConfigurations`, writes them as `FluxConfig` objects and pushes their status back to Azure, and `fluxconfig-controller` turns each `FluxConfig` into one `GitRepository` or `Bucket` and one or more `Kustomization` objects, with the RBAC and authentication secrets they need. [DOC S-7na2vvh5]
- A change to a `fluxConfigurations` resource waits while the agent cannot reach Azure; after more than 48 hours disconnected the request times out and must be reapplied in Azure, and private keys, tokens and passwords are kept under 48 hours in the service. [DOC S-7na2vvh5]
- Multi-tenancy is on by default: the extension applies configurations by impersonating the `flux-applier` service account of the configuration's namespace, so a `sourceRef` into another namespace is blocked; `--configuration-settings multiTenancy.enforce=false` opts out. [DOC S-7na2vvh5]
- The latest `microsoft.flux` version and the two before it (N-2) are supported. Azure Policy can create the same Flux configuration across every AKS and Arc-enabled cluster in a subscription or resource group. [DOC S-7na2vvh5]
- Flux deployments cost nothing on AKS, AKS Edge Essentials and AKS on Azure Local; on other Arc-connected distributions the first six vCPUs in a subscription are free and charges then follow vCPUs per cluster. [DOC S-7na2vvh5]
- `az k8s-configuration flux create` source settings: `--kind` is `git` (default), `bucket`, `azblob` or `oci`; `--sync-interval` and `--timeout` default to `10m`; `--scope` is `cluster` (default, full access) or `namespace`; `--branch` defaults to `master`; `--suspend` stops new source and kustomize reconciliations. [DOC S-htplz4gp]
- Each kustomization takes `path`, `depends_on`, `sync_interval`, `retry_interval` and `timeout` (each `10m` by default), and `prune` (default `false`): `prune=true` deletes deployed objects once they leave the repository or the configuration is deleted, which Microsoft calls important where users change clusters only through git. `force=true` re-creates a resource when a patch fails on an immutable field. [DOC S-htplz4gp]
- The Azure implementation does not support every Flux parameter; the documented workaround is to commit the Flux custom resources (`GitRepository`, `Kustomization`) to the repository the configuration deploys. [DOC S-htplz4gp]
- Upstream, a Kustomization runs a server-side apply dry-run every `.spec.interval` to detect and correct drift (60 seconds is the stated minimum); objects missing from a new revision are deleted when `.spec.prune` is on; `.spec.suspend` pauses drift detection and correction; `.spec.ignore` lists JSON Pointer paths left out of drift detection. [DOC S-6eib7udh]

### Argo CD on AKS and Azure Arc-enabled Kubernetes (microsoft.argocd)
- Azure provides Argo CD as the managed cluster extension `Microsoft.KubernetesConfiguration/extensions/microsoft.argocd` (extension type `Microsoft.ArgoCD`); it runs in the cluster and pulls manifests, Helm charts or Kustomize configurations from Git, so no inbound firewall port is opened. [DOC S-kfmk5l6f, S-4jndm2w6]
- GitOps with Argo CD is generally available for AKS and in preview for Azure Arc-enabled Kubernetes. From extension version 1.0.0-preview it uses the community Helm chart with changed configuration keys, so a 0.0.x install is uninstalled and reinstalled. [DOC S-4jndm2w6]
- The extension's components: the application controller compares live state with the target state in Git; the repository server caches repositories and generates manifests (Helm, Kustomize); the API server serves the UI, CLI and CI; Redis caches; Dex brokers sign-in; a notifications controller and an ApplicationSet controller. It supports workload identity federation and Microsoft Entra ID single sign-on. [DOC S-kfmk5l6f]
- High availability is the default and needs four nodes (`redis-ha.enabled=false` installs on one); Argo CD administrator access is in practice equivalent to cluster administrator; direct edits to Argo CD ConfigMaps are not supported, so configuration goes through the extension's settings. [DOC S-4jndm2w6]
- Argo CD's terms: the target state is the desired state in Git, the live state is what is deployed, sync status says whether they match, a sync moves the application to its target state, and a refresh compares the latest Git content with the live state. [DOC S-2k3bcw7n]
- By default Argo CD polls repositories every 3 minutes (`timeout.reconciliation` 120s plus up to 60s `timeout.reconciliation.jitter` in `argocd-cm`); on a change, auto-sync applications sync and the others are only marked OutOfSync. Setting it to 0 leaves only webhooks and manual refresh, which the FAQ does not recommend. [DOC S-2mzbvpov]
- Automated sync (`spec.syncPolicy.automated`, or `argocd app set <APPNAME> --sync-policy automated`) syncs an application when the manifests in Git differ from the live state; `automated.enabled: false` switches it off while keeping `prune`, `selfHeal` and `allowEmpty` set. [DOC S-ures7t57]
- As safety defaults, automated sync deletes nothing that left Git unless `prune` is true, refuses to prune an application down to no resources unless `allowEmpty` is true, and does not react to edits of the live cluster unless `selfHeal` is true. [DOC S-ures7t57]
- Automated sync runs only on an OutOfSync application, once per commit SHA and parameters unless `selfHeal` is set (then again after the self-heal timeout, 5 seconds by default); a failed sync can retry with exponential backoff; rollback is not possible while automated sync is on. [DOC S-ures7t57]
- Where a cluster is meant to change only through git, Flux needs `prune=true` on its kustomizations, while Argo CD needs both `prune` and `selfHeal` in its automated policy: Flux corrects live edits at every interval by default, Argo CD by default only reports them as OutOfSync. [DER S-htplz4gp, S-6eib7udh, S-ures7t57, S-2mzbvpov: Flux's Microsoft prune guidance and its per-interval drift correction against Argo CD's prune and self-heal defaults]
- Argo CD administrator rights on an agent workload's cluster are a cluster-administrator grant, so they belong in the tier that approves cluster-wide changes, not in an agent's own identity. [DER S-4jndm2w6, S-5pzuphp4: administrator access equals cluster administrator; the state store should control access to changes]

### Applied to Claude Code agent configuration
- Claude Code's shared project configuration is a set of declarative files that can be committed with the code: `.claude/settings.json`, `CLAUDE.md`, `.mcp.json` for team MCP servers, and `.claude/skills/`, `.claude/agents/` and `.claude/rules/`. A repository can therefore hold an agent's configuration under principles 1 and 2. [DER S2057, S-rfpmkpck, S-43ycwzdw: project-scope files are plain JSON/Markdown in the repository; principles 1 and 2 ask for declarative, versioned state]
- Claude Code reloads changed settings files into a running session, watches skill directories for edits, reloads a file-based `managed-settings.json` when it changes, checks MDM policy every 30 minutes and polls server-managed settings hourly. These apply a changed declaration to a running agent, but only from the files already on disk; nothing in Claude Code pulls the repository itself. [DER S2057, S2158, S2042, S-43ycwzdw: reload and poll intervals as documented; principle 3 asks agents to pull from the source]
- Project settings are not the highest layer: `.claude/settings.local.json`, `--settings` and managed settings override `.claude/settings.json`. A developer's local file is therefore drift from the committed state, and only managed settings (server-managed, MDM or `managed-settings.json`) win over every layer. [DER S2057, S-5pzuphp4: settings precedence; drift is actual state moving away from desired state]
- Policy that must not drift belongs in managed settings rather than the repository: the dev container page itself warns that anyone with write access can remove a Dockerfile step that installs `managed-settings.json`, and points to server-managed settings or MDM instead. [DER S-fzkqxhmg, S-5pzuphp4: repository writers can remove the step; the state store should control access to changes]
- Claude Code's GitLab CI/CD integration (marked beta, maintained by GitLab) runs each task in a container and sends every change through a merge request, so reviewers see the diff and approvals still apply. That is the review gate the state-store definition asks for, applied to the agent's output. [DOC S1802]
- Agent memory (auto-memory, subagent memory directories), session transcripts and team task lists are runtime data rather than desired state: the glossary keeps persistent application data out of the desired state, so these belong in backed-up storage, not in the reconciled configuration. [DER S-5pzuphp4, S2057: desired state excludes persistent application data; these files are written by sessions at run time]
- No page read from Anthropic or Microsoft describes GitOps for agent configuration as such, or a reconciler that pulls Claude Code configuration from git onto workstations. [UNK: looked in code.claude.com docs search and the OpenGitOps documents, 2026-10-14; Claude Code docs search for GitOps and reconciliation and Learn searches for GitOps on Windows, 2026-10-15]

### Windows endpoints
- Microsoft's Flux and Argo CD extensions target Kubernetes clusters only (`managedClusters`, `connectedClusters`, `provisionedClusters`) and reconcile Kubernetes objects, so neither manages the operating system of a Windows endpoint. [DER S-7na2vvh5, S-htplz4gp, S-kfmk5l6f: the extensions are cluster resources and their controllers apply Kubernetes manifests]
- The nearest official pull-and-reconcile loop for Windows OS settings is Azure Machine Configuration: its agent polls the Machine Configuration service for guest assignments every 5 minutes, rechecks them every 15, and `ApplyAndAutoCorrect` corrects drift. Its desired state comes from Azure Policy assignments, not from a git repository, so git can only sit upstream of the assignment as the reviewed state store. [DER S-4xar7ise, S-zfc5iphl, S-43ycwzdw: poll and recheck intervals and the assignment types from `windows/azure-arc-servers.md`; principles 3 and 4]
- Ansible's control node, the machine that runs Ansible, can be nearly any UNIX-like machine with Python, including Windows under WSL; Windows without WSL is not natively supported as a control node. [DOC S-hu4wtonu]
- `ansible-pull` (`prior-art/drift-detection.md`) is the one agent in the kb that pulls desired state from git onto a host: it checks a playbook repository out on the target and runs it there. That makes the target a control node, so it serves Linux hosts but not a Windows endpoint outside WSL. [DER S-wbcdphyr, S-hu4wtonu: ansible-pull runs the playbook on the target; Windows is no native control node]

## Examples
- A repository holds `.claude/settings.json`, `.mcp.json` and `.claude/skills/` and changes them only through reviewed merge requests, while the deny rules every engineer on `PL-LT-00123` must keep come from server-managed settings, which outrank the repository's files. [DER S2057, S1802: precedence puts managed settings above project settings; changes reach the repository through merge requests]
- An MCP server for agents runs on an Arc-enabled cluster at `corp.example.com`: `az k8s-configuration flux create -g <resource-group> -c <cluster> -n agents -t connectedClusters --namespace agents --scope namespace -u https://git.corp.example.com/platform/agents.git --branch main --kustomization name=mcp path=./mcp prune=true` reconciles it from git every 10 minutes and deletes what the repository drops. [DER S-htplz4gp, S-7na2vvh5: parameters and defaults as documented; the host and repository are placeholders]
