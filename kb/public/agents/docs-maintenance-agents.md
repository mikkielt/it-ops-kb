# Prior art for self-updating documentation

## Summary
No product surveyed here runs a fully unattended "docs agent that commits straight to the docs branch."
The common pattern is: read the code/repo (not a separate spec), regenerate on a trigger (deploy, PR
merge, or on-demand query), and either serve the result live (DeepWiki, Mintlify's generated `llms.txt`)
or open a change for a human to merge (Swimm's Auto-sync commit, a Mintlify agent-authored PR). None of
the vendor docs found this session state a fully-autonomous merge-with-no-review path for prose docs.

## Facts
- DeepWiki (Cognition, the company behind Devin) is the free public version of Devin Wiki and Devin Search; the DeepWiki page for a public GitHub repository is reached by replacing `github.com` with `deepwiki.com` in its URL, any public repository can be added for free, and private repositories need a Devin account. Cognition's launch post says over 50,000 top public repositories were already indexed. [DOC S1808]
- A community summary of a Cognition talk describes DeepWiki as scoring files and file connections with heuristics (directory structure, symbol graphs, git history, runtime data), clustering them into a graph, and, in v2, handing more orchestration to an "agentic core". [COMMUNITY S-rqjvl632]
- Refresh: the `CognitionAI/deepwiki` README says DeepWikis are auto-refreshed when the repository carries a DeepWiki badge [DOC S-tpvi7ohn], and Devin's docs say Devin indexes each repository's default branch, with further indexed branches added per repository [DOC S-k527bca2]. No refresh cadence is published.
- Devin's own docs describe "DeepWiki repository wikis" as a feature Devin consults/produces for a repo it works in. [DOC S1809]
- GitHub's `CognitionAI/deepwiki` repository describes itself as "Devin-generated docs for any public repo": free docs at deepwiki.com for public repositories, private-repo indexing through a Devin account, an MCP server for querying wiki content, and a README badge whose presence enables automatic refresh. [DOC S1810] At its last commit (2025-05-22) the repository holds only a README naming the MCP tools `ask_question`, `read_wiki_structure` and `read_wiki_contents` at `mcp.deepwiki.com/sse` and `/mcp`, and it has no licence file (GitHub reports no licence). [DOC S-tpvi7ohn]
- Mintlify auto-generates `/llms.txt`, `/llms-full.txt`, and a Markdown version of every page, "generated from your docs on every deploy" — i.e. the trigger is a documentation deploy, not a code-repository event, and no human review gate is described for this generation step because it is a mechanical export of already-published prose. [DOC S1811,S1812]
- Mintlify automations are a separate, opt-in pipeline from the `llms.txt` export: a task can trigger on a content update, a code change (e.g. updating API specs or docs after a PR merges), a custom schedule or an integration, and runs in one of two modes: "Update and merge changes" (no review) or "Modify and wait for review" (the agent opens a pull request for a human). [DOC S-jgplbv5j]
- Mintlify auto-merge requires the Mintlify GitHub App on the bypass list of every ruleset targeting the deploy branch; if any ruleset lacks it, the automation opens a PR but does not merge it. [DOC S-f2vfcma6]
- The `llms.txt` file format (root or subpath `llms.txt`, Markdown, one mandatory H1 + blockquote summary, optional H2 file-list sections with links) was proposed by Jeremy Howard, v1 published 2024-09-03, v2 updated 2026-08-10; the spec explicitly states "agents are best served by concise, expert-level information gathered in a single, accessible location," i.e. its trigger for use is agent navigation, not compliance. [DOC S1813]
- The `llms.txt` spec's own currency mechanism is a public GitHub repo, a community Discord, and an issue tracker — there is no vendor-run scheduled regeneration described in the spec itself; individual sites (like Mintlify above) choose their own trigger (deploy-time) for producing a conforming file. [DOC S1813]
- Swimm's Verify and Auto-sync features update docs "at any relevant pull, merge, or CI test": Swimm checks code snippets, smart tokens and smart paths in docs against the latest code; Auto-sync decides whether a change can be synced automatically, and when it judges the change impactful enough, the Verify check fails and the docs are flagged for review. Auto-synced changes are accepted through Swimm's GitHub App (an "Approve Auto-sync" button in the check, or automatic approval), which commits them to the open pull request in a dedicated commit. [DOC S1814, S1815, S-cfuusq2i]
- Swimm's drift trigger is therefore a code change reaching CI (pull, merge, or test run), not a calendar schedule; more complex/impactful changes fail Verify instead of auto-syncing, forcing human review. [DOC S1814, S1815]
- GitHub Copilot Spaces (GA 2025-09-24) let a user centralize context — repos, code, PRs, issues, free-text notes, uploaded files — that grounds Copilot's chat answers for a task; it is a curated-context store for querying, not a scheduled or merge-triggered documentation generator. [DOC S1816,S1817]
- Copilot Spaces access: any Copilot-licensed user (including Copilot Free) can create a space; organization-owned spaces can be shared at varying access levels, personal spaces can be shared publicly, with specific users, or kept private. [DOC S1816]
- DeepWiki wikis are steered by a `.devin/wiki.json` file committed to the repository root: it can list exactly which pages to generate (overriding DeepWiki's automatic clustering) and carry a `repo_notes` field that points the generator at important folders (the documented example asks for the `cui/` UI components folder to be prioritized). Committing a change to `.devin/wiki.json` and asking DeepWiki/Devin to "regenerate your wiki" is the one explicit, human-triggered refresh path documented on that page. [DOC S1809] The badge-based auto-refresh (above) is the only automatic route documented, with no published cadence. [DER S1809, S-tpvi7ohn: documented refresh routes compared]
- **Google Code Wiki** (announced 2025-11-13): generates and maintains structured repository documentation with diagrams and a Gemini chat; it "regenerates the documentation after each change" (trigger: code change, not a schedule). Public preview for open-source repositories only; a Gemini CLI extension for private repositories was announced as coming, behind a waitlist. No MR/review gate is described. [DOC S1825]
- GitHub Agentic Workflows (`gh-aw`, MIT-licensed, GitHub Next + Microsoft Research; the repository moved from `githubnext/gh-aw` to `github/gh-aw`) ships a sample "Documentation Maintenance" workflow in its gallery that is described as automatically detecting "drift between code and documentation and propos[ing] reviewable updates" — a schedule- or event-triggered, GitHub-native counterpart to DeepWiki/Swimm, and it uses the same "safe-outputs" review gate (buffered writes validated and applied by a separate scoped job) as gh-aw's other workflows, rather than direct commits. [DOC S1818,S-qso27noq] (Full runtime mechanics recorded in `agents/headless-agent-runtimes.md`, not repeated here.)
- The **AGENTS.md standard** (agents.md, stewarded by the Agentic AI Foundation under the Linux Foundation, originated by OpenAI Codex/Amp/Google Jules/Cursor/Factory) is a single predictable file read by an AI coding agent for build/test/convention instructions, distinct from a human-facing README; nested `AGENTS.md` files in subdirectories override the parent (closest wins); the standard claims 20+ supporting tools and over 60,000 adopting open-source projects as of the page fetched. It is a grounding-file convention, not a self-updating-docs mechanism in itself — nothing in the standard triggers or reviews its own regeneration. [DOC S1820]
- GitHub Copilot recognizes `.github/copilot-instructions.md` (repo-wide) and glob-scoped `.github/instructions/**/*.instructions.md` files for build/test/convention guidance, applied across Copilot Chat, code review, and cloud agent (coding agent) tasks; Copilot's own docs additionally list `**/AGENTS.md`, `/CLAUDE.md`, and `/GEMINI.md` as custom-instruction files it also reads — i.e. GitHub Copilot treats a repository's own Claude Code `CLAUDE.md` as a native input format without any conversion step, if a Copilot coding-agent task ever runs against that repository. [DOC S1821] The fetched page names no scheduled or issue-triggered documentation-update workflow specific to Copilot coding agent beyond this instruction-reading behaviour. GitHub's scheduled or event-triggered route is GitHub Agentic Workflows (public preview): Markdown workflows compiled to a hardened `.lock.yml` Actions workflow, with "keeping documentation up to date with code changes" as a listed use case, writes only through declared `safe-outputs`, and Copilot as the default engine (Claude, Codex and Gemini also supported). [DOC S-h6jpev6e]
- Deterministic guardrail tools usable in front of (or instead of) a docs-generating agent: **Vale** (MIT, errata-ai) is a markup-aware prose linter — style rules (Microsoft/Google/Red Hat style packages, or custom YAML rules) checked via a `.vale.ini` config, runnable in GitHub Actions or a pre-commit hook, enforcing terminology/voice/"state the present"-style rules mechanically rather than by asking a model. [DOC S1822] **markdownlint** (MIT, DavidAnson) is a Node.js Markdown/CommonMark style checker with 60+ built-in rules (MD001–MD060: headings, lists, whitespace, links, code blocks, tables), runnable in CI/pre-commit/ESLint pipelines, with inline HTML-comment exceptions per file. [DOC S1823] Neither tool detects doc-vs-code drift by itself; both are the kind of "strict build" check a docs-quality gate would require, applied to style/structure rather than content currency. **lychee** (Apache-2.0 or MIT, lycheeverse) is a fast async link checker written in Rust that finds broken links and mail addresses in websites, Markdown, HTML and other formats, with a GitHub Action (`lycheeverse/lychee-action`) and a pre-commit hook. [DOC S-xote3xa2]
- **Doc Detective** (AGPL-3.0; v4.38.1, 2026-08-13) is a documentation-testing framework: it parses test specs and doc files for testable actions, runs them in a browser or against APIs, and outputs PASS/FAIL results as JSON for other tooling. It checks docs against product behaviour, not against code diffs, unlike Swimm's Verify/Auto-sync. [DOC S-sit75nzz]
- A team that keeps "no session schedules its own future" as a rule: none of these products' default trigger is a self-scheduled recurrence in that sense — the Mintlify `llms.txt` export regenerates on every docs deploy, an event already outside the agent's control (DeepWiki refreshes badge-carrying repositories automatically, with no published cadence), and Swimm's Auto-sync/Verify runs inside CI a human already triggers. Only a scheduled Mintlify automation, a scheduled GitHub Agentic Workflow or a Claude Code routine (see `agents/headless-agent-runtimes.md`) introduces the kind of self-scheduled recurrence such a rule would flag. [DER S1811,S1812,S1814,S1815,S-tpvi7ohn,S-jgplbv5j,S-h6jpev6e: compares each product's stated trigger against "a session never schedules its own future"]
- **Committing machine-written data from automation.** git's built-in `union` merge driver, set per path with the `merge` attribute in `.gitattributes`, runs a 3-way merge but takes lines from both versions instead of leaving conflict markers; the added lines tend to land in random order, and the git documentation says the user should verify the result. [DOC S-vmz33l7n]
- Events caused by a GitHub Actions workflow's `GITHUB_TOKEN` do not create new workflow runs, to prevent recursive runs: a workflow that pushes with it does not trigger `push` workflows. The exceptions are `workflow_dispatch` and `repository_dispatch`, and `pull_request` opened, synchronize or reopened events, whose runs wait for approval; a GitHub App installation token or a personal access token avoids that. [DOC S-ivq5edtq]
- On GitLab, `[ci skip]` or `[skip ci]` (any capitalization) in a commit message pushes without running a pipeline, and the `ci.skip` Git push option (Git 2.10+) does the same but does not skip merge request pipelines; a skipped pipeline is still created, empty, with status `skipped`. Pipeline execution and scan execution policies can restrict or disable the directive. [DOC S-wane77q5]
- An append-only store that automation updates in a repository therefore needs three things: a union (or custom) merge driver so parallel appends do not conflict, a deduplicating pass after each merge because union keeps both sides' lines in any order, and a guard against the bot's own push re-triggering the job (GitHub's `GITHUB_TOKEN` rule, GitLab's `[skip ci]`). This kb's `kbgit.py fix` is such a pass for its union-merged ledgers. [DER S-vmz33l7n, S-ivq5edtq, S-wane77q5: combined from the three documented behaviours; `kb/_self/git.md`]
- In a documentation-update pipeline the rule-based checks (Vale, markdownlint and lychee in the table below) need no model, so they can run before any model reviews a change and reject what a rule can decide. This is the same order Anthropic's eval guidance gives for graders: deterministic ones where possible, LLM ones where necessary; the model review keeps what rules cannot express (`agents/agent-evaluation.md`, rule-based checks before a model judge). [DER S1822, S1823, S-xote3xa2, S1896: linters and link checkers are deterministic; graders ranked deterministic-first]

| Tool | Checks | Trigger | Review step it forces |

## Examples
For a repository whose docs live under a strict-build docs home, a Swimm-style trigger ("run a check when a docs-relevant directory changes in a merge request") stays closer to a "no repository holds anything but code, data, generated reference and docs" regime than a DeepWiki- or routine-style calendar job, since it rides the existing merge-request pipeline rather than adding a new scheduled trigger against example fixtures such as `corp.example.com`.
