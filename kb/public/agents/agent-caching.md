# Caching in agent systems

## Summary

Anthropic prompt caching stores the KV state for an unchanged prefix, keyed by up to 4 explicit `cache_control` breakpoints, with a 5-minute default TTL (refreshed on each hit) or an optional 1-hour TTL; cache writes cost more than base input, cache reads cost a fraction, and the cache is invalidated by anything that changes the rendered prefix ahead of a breakpoint, most importantly tool definitions, in the fixed order tools → system → messages [DOC S2130]. Claude Code surfaces this as a `Prompt cache (main)` line in `/usage` including named likely causes for a miss [DOC S2132]; its prompt-caching page lists model switches, `/compact`, and MCP server changes when tools are loaded into the prefix (not when deferred, the default) among the actions that invalidate the cache [DOC S2159]. OpenAI and Azure OpenAI apply the same shape (prefix caching on by default, a 1,024-token minimum prefix on GPT-5.6 and later, up to ~90% discount on cache reads) with provider-side differences in TTL model; from GPT-5.6 OpenAI also offers explicit breakpoints and charges 1.25x for cache writes at the default 30-minute lifetime (2.5x for the optional 12-hour one) [DOC S2133,S2134]. The MCP spec (2026-07-28) adds server-side result caching for `tools/list`/similar list operations (`ttlMs`, `cacheScope`) and recommends deterministic tool ordering specifically to raise LLM prompt-cache hit rates, extending `mcp/tools.md`'s existing note on `CacheableResult` [DOC S2135,S2136].

## Facts

### Anthropic prompt caching

- Up to 4 explicit cache breakpoints per request are supported via `cache_control` blocks [DOC S2130].
- Two TTLs: 5-minute (default/ephemeral, refreshed on each cache hit) and 1-hour (opt-in, `"ttl": "1h"`) [DOC S2130].
- Minimum cacheable prefix length is model-dependent: as low as 512 tokens for some newer/thinking-oriented models (per the fetched page: "Claude Fable 5.1, Mythos 5.1, Opus 5.5, Opus 5, Sonnet 5.5, Fable 5, Mythos 5", and Haiku 5.5), 1,024 tokens for Sonnet 5 / Sonnet 4.6 / Sonnet 4.5 / Opus 4.8, 2,048 tokens for Opus 4.7/Mythos Preview, and 4,096 tokens for Haiku 4.5 and Opus 4.6/4.5 [DOC S2130].
- Cache write pricing: 5-minute writes cost 1.25x the base input token price; 1-hour writes cost 2x [DOC S2130,S2131].
- Cache read (hit and refresh) pricing: 0.1x base input price for all models except Claude Fable 5.1 and Claude Mythos 5.1 (0.025x) and Claude Opus 5.5 and Claude Sonnet 5.5 (0.05x); the prompt-caching and pricing pages give the same multipliers [DOC S2130, S2131].
- Prompt caching prices input tokens in three classes, cache reads versus cache writes versus uncached input tokens: uncached (regular) input tokens are billed at the base input price, cache writes at 1.25x (5-minute) or 2x (1-hour) that price, and cache reads at a fraction of it (0.1x, 0.05x or 0.025x by model); a cache breakpoint adds no charge by itself [DOC S2130].
- Per-million-token prices (uncached input / 5-minute write / 1-hour write / cache read): Opus 4.5 to Opus 5 $5 / $6.25 / $10 / $0.50; Opus 5.5 $4 / $5 / $8 / $0.20; Sonnet 4.5 and 4.6 $3 / $3.75 / $6 / $0.30; Sonnet 5 $2 / $2.50 / $4 / $0.20; Sonnet 5.5 $2 / $2.50 / $4 / $0.10; Fable 5 and Mythos 5 $10 / $12.50 / $20 / $1; Fable 5.1 and Mythos 5.1 $10 / $12.50 / $20 / $0.25; Haiku 4.5 $1 / $1.25 / $2 / $0.10 [DOC S2130, S2131].
- Claude Haiku 5.5 is priced by prompt length: up to 100,000 tokens $0.10 uncached input / $0.125 5-minute write / $0.20 1-hour write / $0.01 read; over 100,000 tokens $0.50 / $0.625 / $1 / $0.05 [DOC S2130, S2131].
- Break-even: a cache hit at 0.1x pays off the 5-minute write (1.25x) after one read, and the 1-hour write (2x) after two reads [DOC S2131].
- Worked example (Claude Opus 5.5, $4 per million base input): 40,000 cache-read tokens plus 10,000 uncached input tokens cost $0.008 for the reads (40,000 x $4 x 0.05 / 1,000,000) and $0.04 for the uncached tokens (10,000 x $4 / 1,000,000) [DOC S2131].
- The caching multipliers stack with other price modifiers: the Batch API discount, and the 1.1x data-residency multiplier for US-only inference (`inference_geo`), which applies to input, output, cache writes and cache reads on Claude 4.6 and later models [DOC S2131].
- Invalidation hierarchy: caching follows the order **tools → system → messages**; a change to tool definitions invalidates everything (tools, system, messages); toggling web search or citations, or switching `speed`, invalidates system+messages but not tools; a change to `tool_choice` or adding/removing images invalidates only the messages cache; thinking parameters and `output_config.effort` always invalidate messages and, depending on the model, tools and system too [DOC S2130]. This is the concrete "invalidation hierarchy" the assignment asked for.
- Usage fields: responses report `cache_creation_input_tokens` (tokens newly written to cache) and `cache_read_input_tokens` (tokens served from cache); `input_tokens` covers only what follows the last cache breakpoint; total input = read + creation + input [DOC S2130].
- Practical rules: a cache breakpoint must sit on a block identical across requests (never on a changing timestamp or per-request value); the server looks back up to 20 blocks for a prior cache write; a hit requires the full prefix, text and images, to match exactly; a cache can be pre-warmed with a `max_tokens: 0` request that only writes the cache [DOC S2130].
- Cache scope ("Cache storage and sharing"): caches are isolated between organizations, so different organizations never share one even for identical prompts; within an organization they are also isolated per workspace on the Claude API, Claude Platform on AWS and Microsoft Foundry, while Bedrock and Google Cloud isolate by organization only. [DOC S2130]
- A cache key is a cryptographic hash of the prompt up to the cache control point, so only a request with an identical prefix can read an entry; the hashes of cached content are held in memory only, and entries live at least 5 minutes (standard) or 1 hour (extended) before they are deleted promptly, not immediately. [DOC S2130]
- For a team, the page's only isolation boundaries are the organization and (on the first-party API) the workspace; it names no per-user or per-session boundary. Two sessions or users that send an identical prefix through one workspace, or on Bedrock or Google Cloud through one organization, are therefore inside one isolation scope, and developers on separate workspaces or organizations never read each other's entries. The page does not say in a sentence that such sessions hit each other's entries. [DER S2130: the isolation scopes, the identical-prefix hit rule and the absence of a user or session boundary]
- Concurrent requests: "a cache entry only becomes available after the first response begins", so the page advises that parallel requests wanting cache hits wait for the first response before the others are sent. [DOC S2130]
- So parallel agents started at once on an identical prefix (the same system prompt, tools and files) get no cache hits from each other at the start: each sends that prefix before any of them has a response, none reads an entry the others are writing, and each pays the cache-write price (1.25x for 5 minutes) on it. This agrees with the workflows page, which says agents of one workflow can read each other's cache when they share a prefix: the read comes once an entry exists. The page adds that matching needs the same model, effort level, agent type, tools, output schema and working directory, and that Claude Code itself avoids the simultaneous start in a workflow fan-out: it holds all but the first matching agent until the first agent's response begins, then releases them together so their first requests read the shared prefix (the hold is capped by `CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS`, 5000 ms by default, `0` disables it). A workflow agent's cache lives 5 minutes by default, including on a Claude subscription; `subagentPromptCacheTtl` set to `1h` keeps it for an hour at the higher 1-hour write rate. An agent that starts after another's first response began reads the entry at the read price, so staggering starts or running agents one at a time moves the prefix cost from writes to reads, and a benchmark of concurrent against sequential agents must record `cache_creation_input_tokens` and `cache_read_input_tokens` apart to show it. [DER S2130, S-qulnsg4e: the entry-availability rule, the write and read multipliers and the workflows page's shared-prefix sentence]

### Claude Code and the cache

- Claude Code (>=2.1.251) shows a `Prompt cache (main)` line in `/usage`: request count, percent of input tokens served from cache, count of misses (with time of last miss and tokens re-cached), a count of "expected rebuilds" (Claude Code's own compaction or tool-result clearing, not counted as ordinary misses), and whether the cache is currently warm against its TTL [DOC S2132].
- A miss is counted when a request reprocessed more than 5% and at least 2,000 tokens of what could have been read from cache; from v2.1.260 the line names a likely cause, e.g. `likely cause: tool definitions changed` [DOC S2132].
- The `/usage` cache line counts Claude Code's own compaction or its clearing of old tool results from context as an *expected* rebuild, not as a miss [DOC S2132].
- Claude Code's list of actions that invalidate the cache: switching models, changing effort level (on most models; on Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1 with an API key or a Claude subscription the cache is kept, though not on Bedrock, Google Cloud's Agent Platform or a Claude apps gateway), turning on fast mode, connecting or removing an MCP server, enabling or disabling a plugin, denying an entire tool, compacting, accumulating many images, and upgrading Claude Code; with deferred tools (the default on supported models) an MCP server connecting, disconnecting or changing its tool list only appends content and keeps the cache [DOC S2159].
- Claude Code's cache lifetime by billing surface: it decides the lifetime per request, in two buckets: the main conversation (interactive turns, non-interactive `-p` runs, Agent SDK turns and the helpers run inline with them) and everything else (subagents, workflows, in-process teammates, forks, compaction, session titles). Unless a lifetime is chosen, one hour is requested only on a Claude subscription within the plan's included usage: the main conversation gets one hour there, everything else five minutes except a small set of server-controlled helper requests that get one hour; with usage credits, an API key or a cloud provider every bucket gets five minutes. The cost page shows the TTL in effect on the `/usage` cache line (e.g. `1h TTL`) and refers to the prompt-caching page, and a first message after a break longer than the lifetime misses the cache [DOC S2159, S2132].
- Either bucket is set to `5m` or `1h` with `promptCacheTtl` (main conversation) or `subagentPromptCacheTtl` (everything else), or the environment variables `CLAUDE_CODE_PROMPT_CACHE_TTL` and `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL`, all from v2.1.242; `ENABLE_PROMPT_CACHING_1H` asks for one hour on both buckets and `FORCE_PROMPT_CACHING_5M` forces five minutes on both and wins over every other control [DOC S2159].
- Claude Code's cache is effectively scoped to one machine and directory: the system prompt embeds the auto memory paths and the conversation opens with the working directory, platform, shell and OS version, so sessions in different directories build different prefixes and miss each other's cache; sessions run in parallel in one directory build matching prefixes and read each other's cache, and sequential sessions share the prefix only when the git status snapshot taken at startup matches. The page adds that the underlying API cache is broader: isolated between organizations and, on some providers, between workspaces, with any two requests of the same model and prefix reading the same cache within those boundaries [DOC S2159].
- MCP tool definitions are deferred by default in current Claude Code (only names + server instructions enter context until a tool is actually used) [DOC S2132].
- `/clear` resets the cache-stat line along with the rest of the session block; `/compact` itself is a large request because it must read the conversation it is about to summarize [DOC S2132].
- General implication: before building a bespoke cache-hit-rate dashboard, check whether Claude Code's built-in `/usage` line or OTel export already covers it — a team that treats "no new mechanism without an observed failure" as policy would need to name what a bespoke dashboard catches that the built-in ones do not [DER — general cost/complexity discipline for agent tooling].
- The prices of Opus 5.5, Sonnet 5.5 and Haiku 5.5 in the Anthropic prompt caching facts above were read again on the pricing page on 2026-10-12 and had not changed [DOC S2131].
- Claude Code's own cost figures (`/cost`, the status line, `--max-budget-usd`, the SDK's cost figures) price Sonnet 5.5 cache reads at $0.10 per million tokens from v2.1.296, where the changelog says they were $0.20 before; see `claude/ci-and-headless` for the runs that show it [DOC S1864].
- The changelog entry of v2.1.284, which added Sonnet 5.5, lists its price as "$2/$10 per Mtok with $0.20/Mtok cache reads", the cache-read rate of Sonnet 5 [DOC S1864].
- In the changelog no entry between v2.1.284 and v2.1.296 changes the Sonnet 5.5 cache-read price of $0.20 per million tokens: the entries from v2.1.285 to v2.1.295 name no Sonnet 5.5 price, and the first entry that states a changed cache-read price is v2.1.296's [DER S1864: the changelog's entries v2.1.285 to v2.1.296 read on 2026-10-13 for a price, cache or cost-figure line].
- Claude Code 2.1.295 or older counts Sonnet 5.5 cache reads at $0.20 per million tokens in `/cost`, the status line, `--max-budget-usd` and a `claude -p` result's `total_cost_usd`, double the pricing page's $0.10; the changelog states no price for a version before v2.1.284 and says nothing of what Anthropic invoiced for cache reads on any version [DER S1864, S2131: the v2.1.284 entry's $0.20 and the v2.1.296 entry's "was $0.20" read against the page's $0.10].
- The Agent SDK cost-tracking page calls `total_cost_usd` and `costUSD` client-side estimates computed locally from a price table bundled at build time, not authoritative billing data, which can drift from the bill when pricing changes, the installed SDK version does not recognise a model, or billing rules apply that the client cannot model; for authoritative billing it points to the Usage and Cost API and the Console Usage page [DOC S-isqfh6pr].
- Parallel Claude Code sessions draw on one subscription's usage allowance: the agent view page says background sessions use subscription usage like interactive ones, so ten agents in parallel use quota roughly ten times as fast as one; the error reference says the session and weekly allowances are shared across models and that a burst such as a large workflow fanout can exhaust the weekly allowance before the session window resets; a workflow's agents pause at the limit only in an interactive session signed in with a subscription, so in a `claude -p` or Agent SDK run the affected agent fails [DOC S-aishnkok, S-7caoetch, S-qulnsg4e].
- None of the pages above, the Claude Code docs search or the costs, headless, monitoring-usage and model-config pages read 2026-10-19 and 2026-10-21 gives a number of concurrent `claude -p` processes one subscription login takes before a run is limited [DER S-aishnkok, S-7caoetch, S-qulnsg4e: the absence read across the pages].

### OpenAI / Azure OpenAI (comparison)

- OpenAI: caching is on by default for supported models; minimum prefix is 1,024 visible input tokens for GPT-5.6 and later (varies by settings for earlier models); cache reuse requires the *entire* rendered prefix to match exactly (model, tools, schemas, reasoning effort, verbosity all count); caches are not shared across organizations or across regional processing boundaries [DOC S2133].
- OpenAI pricing and breakpoints by generation: GPT-5.6 and later charge 1.25x the uncached input rate for a cache write (30-minute lifetime; 2.5x for 12 hours) and 0.1x for a read, and support explicit breakpoints (`prompt_cache_options.mode: explicit`, `prompt_cache_breakpoint` on a content block, up to four cache writes per request) besides the default implicit breakpoint at the latest eligible message; earlier models are implicit-only, with a model-dependent cached-input rate and no cache-write charge [DOC S2133].
- OpenAI bills each input token at exactly one of the uncached-input, cached-input or cache-write rates, so a cache write is no extra fee on top; on GPT-5.6 and later a read costs 0.1x the uncached input rate (0.05x on GPT-6.1 Sol), and a prefix written once and fully reused once costs 1.35x its ordinary input cost at the 0.1x read rate, against 2x without caching [DOC S2133].
- TTL: GPT-5.6+ uses `prompt_cache_options.ttl` (overridable per explicit breakpoint with `prompt_cache_breakpoint.ttl`) with two values: `30m` (default, writes at 1.25x) and `12h` (Responses API, writes at 2.5x; a minimum lifetime, same read rate, entries may be kept longer); earlier models use `prompt_cache_retention` with `in_memory` (typically 5-10 minutes of inactivity, up to an hour) or `24h` (GPT-5.5 and GPT-5.5 Pro: `24h` only); where both exist the default is `24h` unless the organization has Zero Data Retention, then `in_memory` [DOC S2133].
- Azure OpenAI (Microsoft Foundry Models): same 1,024-token minimum-prefix rule (first 1,024 tokens must be identical); discount applies to Standard deployments' input pricing, with up to 100% discount on Provisioned deployment types; supported on GPT-4o and newer [DOC S2134].
- Azure OpenAI cache lifetime matches OpenAI's: on GPT-5.6 and later `prompt_cache_options.ttl` sets a minimum lifetime whose only (and default) value is `30m` (the service may keep the prefix longer); earlier models use `prompt_cache_retention` with in-memory retention (all GPT-4o+ models) or extended retention of up to 24 hours on listed models. [DOC S2134]

### MCP-side caching and `listChanged`

- The MCP spec (2026-07-28 revision) documents that `tools/list` responses support pagination and a caching utility, returning `ttlMs` and `cacheScope` (`public`/`private`) fields on the result (already noted for `mcp/tools.md`, not repeated there) [DOC S2135] — this is the same `CacheableResult` mechanism `mcp/tools.md` cites.
- Servers that declare the `tools` capability with `listChanged: true` SHOULD send `notifications/tools/list_changed` when the tool set changes; a client that has opened a `subscriptions/listen` stream with `toolsListChanged: true` receives it and is expected to re-fetch `tools/list` [DOC S2135].
- The spec explicitly ties deterministic list ordering to prompt caching: servers SHOULD return tools in a deterministic order, which lets clients cache the tool list reliably and "improves LLM prompt cache hit rates when tools are included in model context" [DOC S2135].
- The tool-set returned by `tools/list` MUST NOT vary per-connection or as a side effect of other requests, but MAY vary by the caller's authorization/granted scopes, since credentials are per-request, not connection state [DOC S2135].
- The scope-dependent tool list is relevant to an MCP server that varies its tool list by the caller's permission tier [DER S2135: general implication for tiered-access MCP servers].
- GitLab CI's `cache:key:files` makes the cache key from the content of the files named: "generate a new
  cache key when the content of the specified files change", and the key stays the same while they do
  not. [DOC S1512]
- So a cache of derived results keyed only by its data inputs serves stale results once the code or rule
  that derived them changes; keying it also by a form or version of that rule (or a hash of its source)
  makes a rule change a new key. [DER S1512: the key changes with what it names, and only with that]

## Examples

For a stdio MCP server serving example devices (`PL-LT-00123`, `corp.example.com`), the cache-friendly pattern is: a fixed, alphabetically or capability-ordered tool list with no timestamps in tool descriptions, example values (e.g. `jan.kowalski`) kept out of the system prompt (put per-call values in `messages`, not `system`), and reading `/usage`'s `Prompt cache (main)` line or the OTel cache-token metrics (see `claude/otel-monitoring.md`) rather than building a bespoke cache-hit dashboard [DER S2130,S2132,S2135].
