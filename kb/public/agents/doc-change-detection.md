# Detecting documentation source changes: version signals, redirects, archives, soft 404s

## Summary
Signals a tool can read, without a model, to tell whether a cited documentation page changed, moved or
died. A Microsoft Learn page carries a per-page `git_commit_id`, `updated_at` and a stable `document_id`
in its HTML `<head>` and in the YAML front matter of its markdown form (`?accept=text/markdown`), and it
answers conditional requests with `304`. Learn sitemaps are split per product and locale, but their
`lastmod` did not match the page's own `updated_at` in the probe below. Moved pages are recorded in each
docs repository's `.openpublishing.redirection*.json` and served as `301`, sometimes to an anchor on another
page. Old text comes from the public MicrosoftDocs repository at the page's commit, or from web archives
through Memento (RFC 7089) and the Wayback CDX API. A page that answers `200` with error content (a soft
404) is caught by fetching a random sibling URL and comparing the two. A client-rendered page gives a plain fetch only its shell, so the two
texts to compare can both be empty and a client that follows redirects calls a live page a soft 404,
while one that does not follow them sees the sibling's redirect and the pair differs (the section on
client-rendered pages below). A host that did not accept
connections is remembered by libraries and proxies for seconds, growing to minutes, not by any standard. For a source on GitHub, an
issue's or repository's `updated_at` (or `pushed_at`) and the `since` filter date the last change, a wiki is
its own Git repository (`<repo>.wiki.git`) whose history dates each page, and an unauthenticated `304` still
counts against the 60 requests an hour. Design context: `kb/_self/tools.md`,
"fact diff", and `kb/_self/reports/fact-diff.md`.

## Facts
### Microsoft Learn page version signals
- A Learn page's HTML `<head>` has `<meta>` tags `ms.date`, `document_id`, `document_version_independent_id`, `updated_at`, `git_commit_id` and `depot_name`; on the probed ConfigMgr page `ms.date` was 2025-11-11, `updated_at` 2026-08-31T17:37:00Z and `depot_name` `MSDN.memdocs`. [DOC S-7jumyiid]
- `ms.date` is not a change signal for small edits: Microsoft's contributor guidance says to update it for major content, "but not for fixes like clarification, formatting, grammar, or spelling". [DOC S-ecrpwvoh]
- The same page returned a strong `ETag` and a `Last-Modified` header with `cache-control: public, max-age=600`; the ETag was the same across repeated requests (including one with a cache-busting query that reached a new edge request id), and `If-None-Match` or `If-Modified-Since` with those values returned `304`. [DOC S-7jumyiid]
- The draft note that Learn sends no usable ETag is therefore not true for this page. Wayback captures of the same page show the ETag also changing across Learn site builds with no content change: captures of 2025-12-12 and 2025-12-28 carry the same `Last-Modified` (2025-12-11) but different `x-buildversion` values and different ETags. So a changed ETag means the rendered HTML changed, not necessarily the content; `updated_at` or `git_commit_id` is the content signal. [DER S-qvogwadn: archived response headers of captures compared]
- Adding `?accept=text/markdown` to a Learn URL, or sending `Accept: text/markdown`, returned `content-type: text/markdown` with the same ETag: a YAML front matter block (`title`, `ms.date`, `document_id`, `updated_at`, `git_commit_id`, `original_content_git_url`, `gitcommit`, ...) followed by the article body, several times smaller than the HTML page. [DOC S-7jumyiid]
- The documented ways to get a Learn page as Markdown are the Learn MCP server's fetch tool, which "fetches and converts a page into markdown" [DOC S2176], and the Learn CLI's `mslearn fetch <url>`, which returns "Markdown-friendly output" [DOC S-lylm4eqz]. No Learn page read on 2026-09-27 documents the `?accept=text/markdown` query or header form, and `learn.microsoft.com/en-us/llms.txt` returns 404, so that form is observed behaviour, not a published interface. [DER S2176, S-lylm4eqz: documented routes compared with the probed form]
- In the markdown front matter, `original_content_git_url` and `gitcommit` name the source file in a private `-pr` repository (`MicrosoftDocs/memdocs-pr`, `MicrosoftDocs/entra-docs-pr`) at branch `live` and at the commit in `git_commit_id`. [DOC S-7jumyiid, S-ybuoluc4]
- The public mirror repository holds the commit of a page: the Entra device-identity page's `git_commit_id` resolves in `MicrosoftDocs/entra-docs` and its file is readable at that commit. [DOC S-xpbhjzu7] A ConfigMgr page's commit was read as resolving in `MicrosoftDocs/memdocs` on 2026-09-27; that lookup cannot be repeated, because the repository now answers `404`. [UNK: source S-rgpijsmb gone 2026-10-12]
- So the old text of a Learn page can be fetched from the public mirror at a stored `git_commit_id`, without keeping a local copy, as long as the mirror is public and still receives commits; the `memdocs` mirror, which held ConfigMgr and Intune pages, answered `404` on 2026-10-12, so the text at a stored ConfigMgr or Intune commit can no longer be fetched from it, while Learn still names it as the public path. [DER S-xpbhjzu7, S-u2afup7q, S-xmqy75h7: the commit lookup in `entra-docs`; the `memdocs` probes and the Learn page]
- `microsoft_docs_fetch` (the Learn MCP server) returns the article as markdown without the front matter, so it carries no `updated_at` or `git_commit_id`; a change check needs a plain HTTP request for those. [DER S2177: the fetches made for this article returned bare markdown]

### Learn page to source file and its git history
- For the Entra "device identity" page on 2026-10-10, the markdown front matter's `original_content_git_url` was `https://github.com/MicrosoftDocs/entra-docs-pr/blob/live/docs/identity/devices/overview.md` and its `source_path` was `docs/identity/devices/overview.md`; the HTML head also held `original_content_git_url_template="{repo}/blob/{branch}/docs/identity/devices/overview.md"`. So the url is the private repository, the branch `live` and the page's `source_path`. [DER S-ybuoluc4: the front matter and head of one page, read 2026-10-10]
- On the same page the HTML head's `github_feedback_content_git_url` was `https://github.com/MicrosoftDocs/entra-docs/blob/main/docs/identity/devices/overview.md`: the public repository (no `-pr`), branch `main`, the same repository path. A tool takes the public file's url from that tag and need not rewrite `-pr` by hand. [DER S-ybuoluc4: the head of one page, read 2026-10-10]
- The commits endpoint of GitHub's REST API takes a `path` parameter ("Only commits containing this file path will be returned") and `since` and `until` timestamps, so the history of one source file is one request. [DOC S-o6lmrcgh]
- For that page, `GET /repos/MicrosoftDocs/entra-docs/commits?path=docs/identity/devices/overview.md&per_page=3` on 2026-10-10 returned `95d306db` first: the page's own `git_commit_id`, with committer date 2026-06-15T16:45:09Z. The page's `updated_at` was 2026-06-15T17:40:00Z, 55 minutes later, and its `ms.date` 2025-06-27. [DER S-stitrqhm, S-ybuoluc4: one page compared on 2026-10-10]
- Two of the file's three newest commits had subjects that start `[BULK UPDATE]`, one of them naming a metadata move (author, `ms.author`, `ms.service`); the commit that set `git_commit_id` and `updated_at` was one of these. So the file's commit date and the page's `updated_at` moved together on a bulk commit, and neither shows by itself whether the article text changed; a diff of the text between two stored commits does. [DER S-stitrqhm, S-ybuoluc4: commit subjects of one file read 2026-10-10; the diffs were not read]
- So the git side adds, to the head's `updated_at` and `git_commit_id` that cost no API request, the list of commits that touched the file and the text at each (at one unauthenticated request per page, against the limit in the GitHub section below); on this page it dated the change no better than `updated_at` did. A file of the `memdocs` repository cannot be asked for its commits at all while the repository answers `404` (2026-10-12). [DER S-stitrqhm, S-ybuoluc4, S-u2afup7q: the commit list of one `entra-docs` file; the `memdocs` probes]
- A ConfigMgr page read 2026-10-12 still names `MicrosoftDocs/memdocs-pr` at branch `live` as `original_content_git_url` and the public `MicrosoftDocs/memdocs/blob/main/...` path as `github_feedback_content_git_url`, with `git_commit_id` `51052ad73287`: Learn still advertises the public path that now answers `404`, so a tool that takes the public file's url from that tag gets a url with no page behind it. [DER S-f6ejsacc, S-xmqy75h7: head tags of one page against the `memdocs` probes]

### Learn site search endpoint
- `learn.microsoft.com/api/search?search=<query>&locale=en-us&$top=<n>` answered `200 application/json` without authentication; each result carries `title`, `url`, `description`, `lastUpdatedDate`, `breadcrumbs`, `category` and `products`, and the response has `count` and `nextLink`. [DOC S-7ivxsp4z]
- For the Entra page "Manage devices in Microsoft Entra ID", the search result's `lastUpdatedDate` (2026-08-25T07:33) was the page's own `updated_at` from its markdown form. [DOC S-7ivxsp4z, S-7n65j7bo]
- So one search request returns the content date of up to `$top` pages at once, a cheaper batch signal than fetching each page, and it also finds pages a moved passage may have gone to. [DER S-7ivxsp4z, S-7n65j7bo: one page compared; a larger sample would confirm]
- The documented Learn Platform API (`learn.microsoft.com/api/v1`) is an authenticated catalog of training content (modules, learning paths, certifications, exams) and states it does not output documentation, so the site search endpoint above is undocumented and may change without notice. [DOC S-ffzntayk]

### Sitemaps
- `learn.microsoft.com/robots.txt` names `https://learn.microsoft.com/_sitemaps/sitemapindex.xml`; the index listed several thousand sitemap files split by product and locale (for example `intune_en-us_1.xml`), each with a `lastmod` date. [DOC S-zb3jd525]
- A product sitemap lists each page URL with a day-precision `lastmod` and `hreflang` alternates for other locales. [DOC S-lldnrkhv]
- For the probed ConfigMgr page the sitemap `lastmod` was 2026-01-14 while the page's `updated_at` was 2026-08-31 and its `ms.date` 2025-11-11: none of the three agreed. [DOC S-lldnrkhv, S-7jumyiid]
- Sitemap `lastmod` is therefore usable to find added and removed URLs, but not as a per-page change signal on Learn; `updated_at` or `git_commit_id` from the page itself is the reliable one. [DER S-lldnrkhv, S-7jumyiid: one page compared; a larger sample would confirm]

### Redirects on Learn
- A docs repository records moved or deleted articles in `.openpublishing.redirection.json` at its root, as a `redirections` array of entries with `source_path` (repository path of the old `.md`), `redirect_url` (public URL, may end in `#section` or point to another site) and `redirect_document_id`. [DOC S-ecrpwvoh]
- `redirect_document_id: true` keeps the old page's document id (and its page views and rankings) on the target, meant for a rename; `false` (the default) is for a pointer to a different article that covers only part of the old content. [DOC S-ecrpwvoh]
- So `redirect_document_id` tells a fact-diff tool whether a redirect is a rename (the facts should be found on the target) or a partial merge (the facts may be gone or split). [DER S-ecrpwvoh]
- Some repositories split the file per product: the root listing of `memdocs` at commit `4b5429df`, read 2026-09-27, named `.openpublishing.redirection.autopilot.json`, `.configmgr.json`, `.intune.json`, `.external.json` and `.legacy.json`; the listing can no longer be read. [UNK: source S-pcy7cqea gone 2026-10-12]
- The `entra-docs` file at the pinned commit holds several hundred entries; most use `source_path_from_root` instead of `source_path`, and a few redirect to an anchor on another docset (for example a licensing page to a Microsoft 365 admin page with `#manage-group-based-licensing-errors`). [DOC S-xv7jeuvk]
- Redirects can chain (A to B, later B to C); the Learn Authoring Pack's sort command exists partly because of this "daisy chaining", so a tool must follow chains rather than read one hop. [DOC S-v3vc7a3l]
- Learn serves a redirected page as `301` to the target, keeping the anchor when there is one, and a nonexistent path under a docset as a real `404`, not a soft 404. [DER S-xv7jeuvk: two Entra paths from this file and one made-up path, requested 2026-09-27]

### Web archives: Memento and the Wayback Machine
- RFC 7089 (Informational, December 2013) defines Memento: an Original Resource (URI-R), a Memento that holds its state at a time T (URI-M), a TimeGate that negotiates on datetime (URI-G) and a TimeMap that lists a resource's Mementos (URI-T). [DOC S-2dckbgu5]
- A client asks a TimeGate for a past state with the `Accept-Datetime` request header; a Memento states its time in the `Memento-Datetime` response header. [DOC S-2dckbgu5]
- The Internet Archive states that the Wayback Machine is "fully compliant with the Memento Protocol"; a request to `web.archive.org/web/<timestamp>/<url>` answered `302` to the nearest capture, which carried `Memento-Datetime` and a `Link` header with `original` and `timemap` relations. [DOC S-km6slvii]
- The Wayback Availability JSON API (`archive.org/wayback/available?url=...&timestamp=YYYYMMDDhhmmss`) returns only the single closest snapshot, or an empty `archived_snapshots` object when the URL is "not archived or currently not accessible". [DOC S-km6slvii]
- For a Learn page with several 2025-2026 captures, the Availability API returned an empty `archived_snapshots`, while the TimeGate and the CDX API found them. [DOC S-oo5kmppv, S-znp63ln6]
- The Availability API's empty answer does not prove a page was never archived; the CDX API or the TimeGate is the check to trust. [DER S-oo5kmppv, S-znp63ln6, S-km6slvii: "not accessible" is one of the documented reasons for an empty result]
- The CDX Server API (`web.archive.org/cdx/search/cdx`) lists captures with `urlkey`, `timestamp`, `original`, `mimetype`, `statuscode`, `digest` and `length`; it takes `output=json`, `fl=` (field list), `from=`/`to=` (timestamp range), `filter=` (regex per field, `!` negates), `matchType=` (`exact`, `prefix`, `host`, `domain`) and `collapse=` (for example `collapse=digest`, which collapses only adjacent duplicates). [DOC S-s6xjctzu]
- A CDX query answered `504 Gateway Time-out` once and succeeded on retry. [DOC S-znp63ln6]
- CDX `digest` values let a tool list only the captures whose content changed (`collapse=digest`) before reading any archived text. [DER S-s6xjctzu]

### Dead pages and soft 404s
- Bar-Yossef, Broder, Kumar and Tomkins (WWW 2004) define a page as dead when its URL is malformed, its host is down or nonexistent, or it does not exist on the host, and note that servers answering "soft 404s" hide the last case. [DOC S-xc4ibwg4]
- Their soft-404 test fetches the page and a sibling URL made of the page's parent plus 25 random characters: if the random URL gets a hard error the server does not do soft 404s; if both redirect to the same place, or return identical or nearly identical content (checked by shingling), the page is declared a soft 404. [DOC S-xc4ibwg4]
- The paper notes one case the test cannot settle: a dead domain's home page bought or parked by a new owner. [DOC S-xc4ibwg4]
- Google Search treats a `2xx` response whose content "suggests an error", such as an empty page or an error message, as a soft 404 in Search Console. [DOC S-vh33l6f5]
- Google treats `301` as a strong signal that the redirect target should be processed, `308` as equivalent to `301`, and `304` as "the content is the same as last time it was crawled". [DOC S-vh33l6f5]

### Client-rendered pages: what a plain fetch gets and what a soft-404 comparison then compares
- Google describes an "app shell model" in which "the initial HTML does not contain the actual content" and a client must execute JavaScript to see what the page shows; it says "not all bots can run JavaScript". [DOC S-yrqtp5aq]
- Google's crawler "queues all pages with a 200 HTTP status code for rendering", so a client-rendered page is rendered only after a `200`; the HTTP response of the crawl step is the shell. [DOC S-yrqtp5aq]
- Google says that in client-side rendered single-page apps "using meaningful HTTP status codes can be impossible or impractical", and gives two ways to avoid soft 404s: a JavaScript redirect to a URL for which the server answers `404`, or a `noindex` robots meta tag added by JavaScript to error pages. [DOC S-yrqtp5aq]
- On 2026-10-13 (curl 8.7.1, macOS, one unauthenticated `GET`) a Tech Community blog post (the `S1217` page) answered `200` `text/html`. The text outside `script` and `style` elements was only the `<title>`: the `<div id="__next">` held a loading placeholder, and the post's text was in a `<script id="__NEXT_DATA__" type="application/json">` block (the message's `body`) and, as plain text of the post, in the `description` of an `application/ld+json` `BlogPosting`. [DER S1217: one page read with no JavaScript]
- The same post's `<meta name="description">` held only the first sentences followed by `...`, so a meta description alone is not the post's text. [DER S1217: one page read]
- Two requests for that post two minutes apart answered `200` both times with different `etag` values; a conditional request with the first `etag` in `If-None-Match` got `200`, not `304`. The article body in `__NEXT_DATA__` was identical in both and the `csrfToken` differed, so the `etag` followed per-response values in the page, not the content; the responses carried `cache-control: private, no-cache, no-store, max-age=0, must-revalidate` and no `last-modified`. [DER S1217: two responses compared; whether the `etag` ever repeats was not tested]
- A made-up sibling of that post (the same board with a random 26-letter subject and the message id `9999999`) answered `302` with an empty body to the site's single sign-on login path carrying the requested URL as `referer`, not `404` and not `200`. [DER S1217: one request, 2026-10-13]
- So the Bar-Yossef test, which fetches the page and a random sibling and calls it a soft 404 when both "return identical or nearly identical content", gets from a client-rendered page the text of its shell: a made-up sibling on a host that answers every path with the same shell has the same text, so a live page is declared a soft 404 although a browser shows its content. Where the sibling answers a redirect, as the made-up sibling of the blog post above did (`302` with an empty body), the outcome depends on the client: one that does not follow redirects, as the probe's `curl` did, compares the shell's text with an empty body, the pair differs and the test says "not a soft 404"; a redirect-following client reads the redirect's target, and the kb's own fetch, which follows redirects, got one newline for another Tech Community post and one for its made-up sibling on 2026-10-12, so the two empty texts matched and the test said "soft 404" for a live page. [DER S-xc4ibwg4, S-yrqtp5aq, S1217: the paper's test applied to Google's app-shell description, the probe and a lookup of a second post by a client that follows redirects]
- A comparison that is meant to work on such pages therefore needs text that differs per page: the `<title>`, a state block such as `__NEXT_DATA__` or the JSON-LD `description` where the host embeds one, or the rendered page from a browser, and it must not call two empty texts "identical content". [DER S-xc4ibwg4, S-yrqtp5aq: what the test compares, applied to the shell]
- Not confirmed: whether the host serves a different body to a client that identifies as a crawler (the embedded state carried an `isCrawler` flag set to `true` for the probe's own user agent), and whether the embedded state is a supported interface. [UNK: one host; looked at the page's HTML only, 2026-10-13]

### Hosts that do not accept connections: how long a client may remember it
- No standard read gives a time. RFC 8305 (Happy Eyeballs v2, December 2017) says a client with "historical RTT data gathered from other connections to the same host or prefix" can use it to set its delay between attempts, and that late DNS replies "will populate the DNS cache", but it states no period for remembering that a host refused or did not answer. [DER S-tjb5zoq2: the sections on connection attempt delay and DNS read in full]
- Microsoft's Circuit Breaker pattern describes a proxy that, after failures exceed a threshold in a period, goes **Open**, fails requests at once and "starts a time-out timer"; when the timer expires it goes **Half-Open** and lets a limited number of requests through, closing on success and re-opening with a restarted timer on any failure. [DOC S-tyedhnrz]
- The same page gives no duration but says an application can "place the circuit breaker in the Open state for a few seconds initially" and, if the failure is not resolved, "increase the time-out to a few minutes". [DOC S-tyedhnrz]
- It warns in both directions: staying Open for a long period "can raise exceptions even if the reason for the failure is resolved", and switching to Half-Open "too quickly" makes the breaker fluctuate and slow the application. [DOC S-tyedhnrz]
- It also says that in the Open state a breaker can ping the remote service periodically instead of using a timer, and that a response such as `429` or `503` "can include other information, such as the anticipated duration of the delay", which can trip the breaker for a minimum time. [DOC S-tyedhnrz]
- Polly's circuit breaker strategy (documentation; a .NET library, not a Microsoft product) defaults to `BreakDuration` 5 seconds, `FailureRatio` 0.1, `MinimumThroughput` 100 and `SamplingDuration` 30 seconds, and ignores the ratio when fewer executions than the minimum happened in the sampling window. [DOC S-xc5fkeod]
- In Polly the circuit does not move to HalfOpen in the background: it does so "when the Execute{Async} method is called and the BreakDuration elapsed", and a failed probe breaks it again; a `BreakDurationGenerator` can lengthen the duration with the failure count. [DOC S-xc5fkeod]
- Envoy's outlier detection ejects a host for `base_ejection_time` (default 30 s) multiplied by the number of times it has been ejected, capped by `max_ejection_time` (default 300 s or the base time, whichever is larger); `max_ejection_time_jitter` (default 0 s) adds a random part so that proxies do not all reconnect at once. [DOC S-if5q2jhk]
- So how long a client may remember that a host did not accept connections before it asks again is fixed by no standard and by no documentation host: the documented values are defaults of libraries and proxies, from 5 s to 30 s, growing with each repeated failure up to a cap of minutes. [DER S-tyedhnrz, S-xc5fkeod, S-if5q2jhk, S-tjb5zoq2: the three defaults and the missing period in RFC 8305, read together]
- Applied to a lookup tool that opens one connection per question: a remembered failure of a host should be short (seconds to a minute), grow with repeated failures to a cap, end on the first success and be kept where a restart does not lose it, since a tool started anew for each question forgets a time kept in its own memory alone (for example a file per host under `_cache/`, never committed, with a first window of 60 s doubled with each failure in a row up to a cap of 300 s, read by every process on the clone); a refused connection (`ConnectionRefusedError`) and a name that did not resolve (`socket.gaierror`) are told apart by type (`python/stdlib-urllib-errors.md:57`). The window is a design choice, not a vendor fact. [DER S-tyedhnrz, S-xc5fkeod, S-if5q2jhk: the breaker states and defaults applied to one process]
- An answer that names its own wait (`Retry-After` with a `503`, `arch/http-rate-limit-429-retry-after.md:31`) replaces any default window: the server states how long it expects to be unavailable. [DOC S-wct3uoax]

### GitHub repositories, issues and discussions: date fields, conditional requests, limits
- The REST API's repository objects carry `created_at`, `updated_at` and `pushed_at` (date-times, nullable on the repository and minimal-repository schemas), and the OpenAPI description gives them no description, so the API documents no rule for what moves either date. [DOC S-o6lmrcgh]
- For `MicrosoftDocs/entra-docs` on 2026-10-10: the newest commit's committer date was 2026-10-09T22:33:00Z, `pushed_at` 22:35:40Z and `updated_at` 22:35:45Z, and the response's `last-modified` header was `Fri, 09 Oct 2026 22:35:45 GMT`, the same instant as `updated_at`. ### Reference rot and content drift
- Klein et al. (PLoS ONE, 2014) name the combination of link rot and content drift "reference rot"; over a million web references in 3.5 million science, technology and medicine articles (1997-2012), one in five articles suffered from it, and seven in ten of those that cite web resources. [DOC S-shha3est]
- Jones et al. (PLoS ONE, 2016) found that for over 75% of web references with a representative archived snapshot, the live content had drifted from what it was when cited; representative snapshots existed for about 30% of references. [DOC S-wcrrjfwh]
- Jones et al. compared the text of snapshots with Simhash, Jaccard, Sørensen-Dice and cosine similarity, and used a high threshold to call two snapshots the same content; they dropped Spamsum because its input needs more than 4 KB of text, which about 70% of their comparisons lacked. [DOC S-wcrrjfwh]
- So a 200 answer on a cited URL says little: most references drift, and only text comparison (not the status code) shows it. [DER S-shha3est, S-wcrrjfwh]

### Change monitors, extraction and date rules
- urlwatch runs two filter stages per job: `filter` on the downloaded page before diffing and `diff_filter` on the diff before reporting; built-in filters include `css`, `element-by-id`, `html2text`, `format-json`, `pretty-xml`, `grep`, `grepi` and `re.sub`. [DOC S-a6bblnnl]
- urlwatch applies `filter` only to new content: the old content keeps the filter of the time it was retrieved, so a changed filter shows up in the next diff as a content change. [DOC S-a6bblnnl]
- changedetection.io (Apache-2.0) offers filters such as "Trigger on text", "Remove text by selector", "Ignore text" and "Extract text" (regular expressions too), targets elements with XPath 1 and 2, CSS selectors, JSONPath or jq, and can parse JSON embedded in an HTML page. [DOC S-gceoq2qq]
- changedetection.io's optional AI rules evaluate each detected diff against a plain-English intent and send the diff and extracted text to a third-party AI provider the user chooses. [DOC S-gceoq2qq]
- htmldate finds a page's original and updated dates in three steps: markup in the header (`link` and `meta` elements, Open Graph), structural markers in the whole document (`abbr`, `time`, attributes), then heuristics on the text, in a `fast` or an `extensive` mode; it is Apache-2.0 from v1.8.0, GPLv3+ before. [DOC S-yvdwutca]
- htmldate's README reports, on 1,000 pages with identifiable dates, precision 0.924 and recall 0.927 in `fast` mode and 0.908 and 0.993 in `extensive` mode. [DOC S-yvdwutca]
- trafilatura (Apache-2.0 from v1.8.0) extracts a page's main text with common patterns and falls back on generic algorithms such as jusText and readability, to leave out recurring headers and footers. [DOC S-niqtbnmc]

### Reading a page's text: the aside element, content sidebars and navigation
- The HTML Standard (a living standard, section 4.3 read on 2026-10-17) says `aside` represents a section of a page whose content is "tangentially related to the content around the aside element, and which could be considered separate from that content"; such sections are often sidebars in printed typography. [DOC S-zrzsmepn]
- It names pull quotes, sidebars, advertising and "groups of nav elements" as uses of `aside`, and says it is "not appropriate to use the aside element just for parentheticals", which are part of the main flow. [DOC S-zrzsmepn]
- Where an `aside` sits says what it is about: in the standard's blog example an `aside` inside an `article` is about that post, and a blogroll in an `aside` outside the articles relates to the page as a whole. [DOC S-zrzsmepn]
- `nav` represents "a section of a page that links to other pages or to parts within the page", is primarily for major navigation blocks (a footer's short link list needs no `nav`), and may be used by user agents such as screen readers to decide what to skip or provide on request. [DOC S-zrzsmepn]
- `aside` and `nav` both have the content model "flow content", are sectioning content and are allowed "where sectioning content is expected", and the entries for the two state no ban on either inside the other: the standard's own blog example puts two `nav` elements in one `aside`, and an `aside` inside a `nav` is permitted by the content models. [DER S-zrzsmepn: the `aside` and `nav` entries and the blog example read; no nesting rule found]
- ARIA in HTML (a W3C Recommendation of 2026-08-11) maps `aside` to `role=complementary` and allows only `feed`, `none`, `note`, `presentation`, `region` and `search` on it (`complementary` is allowed but not recommended), so `navigation` is not an allowed role for an `aside`. [DOC S-jj4lbdze]
- The same document maps `nav` to `role=navigation` and allows `menu`, `menubar`, `none`, `presentation` and `tablist` on it; `navigation` is allowed but not recommended. [DOC S-jj4lbdze]
- HTML Accessibility API Mappings (a W3C Working Draft of 2026-10-12) gives an `aside` scoped to the body or `main` element the complementary role, and an `aside` scoped to a sectioning content element a complementary role only if it has an accessible name, "Otherwise, generic role". [DOC S-er62secx]
- WAI-ARIA 1.2 defines the `complementary` landmark as complementary to the main content "at a similar level in the DOM hierarchy, but remaining meaningful when separated from the main content", and the `navigation` landmark as "a collection of navigational elements (usually links) for navigating the document or related documents". [DOC S-umpci7ic]
- On 2026-10-17 (curl, one unauthenticated `GET`) the SRE book chapter "Effective troubleshooting" (`S-bykh7vnm`) held six `<aside data-type="sidebar" class="highlight">` elements inside its `<main>`, no `article` or `nav` element and no `role` attribute on any `aside`; the first holds the sentence "Wild goose chases often result.", which the kb's text reduction (`provider.py read`) did not print, so a text reduction that drops every `aside` loses a content sidebar. [DER S-bykh7vnm: the raw HTML compared with the reduced text, one page]
- So a reader of a page's text can tell the two by structure, in this order: an `aside` with a `nav` ancestor, or with `role=navigation` on it or an ancestor, is navigation; an `aside` that holds `nav` elements is a navigation block, as in the standard's blogroll example; an `aside` inside the `article` or `main` that holds the prose, with none of those, is a content sidebar whose text belongs to the page, whether or not it has an accessible name (a landmark role is a navigation aid for assistive technology, not a statement of whether the text is content). [DER S-zrzsmepn, S-jj4lbdze, S-er62secx, S-umpci7ic: the content models, role tables and mappings applied to the two cases; a design rule, not a vendor fact]
- Not confirmed: how browsers and screen readers expose an `aside` inside a `nav`, and whether the `data-type="sidebar"` attribute of the SRE book's markup is defined by a published convention. [UNK: the specifications read state neither; no browser or assistive technology was run]

### Freshness at question time
- RFC 9111 calls a stored response fresh while its age, the time since the origin generated or last successfully validated it, has not exceeded its freshness lifetime: `response_is_fresh = (freshness_lifetime > current_age)`. [DOC S-ods72iyh]
- Without an explicit expiration time, a cache may assign a heuristic one; with a `Last-Modified` time, RFC 9111 encourages no more than some fraction of the interval since then, and "a typical setting of this fraction might be 10%". [DOC S-ods72iyh]
- A cache must not use a heuristic when the stored response carries an explicit expiration time, and must not serve a stale response unless it is disconnected or the client, the origin or an out-of-band contract permits it. [DOC S-ods72iyh]
- RFC 5861's `stale-while-revalidate` lets a cache serve a response for a stated number of seconds after it goes stale, while it "SHOULD attempt to revalidate it while still serving stale responses (i.e., without blocking)". [DOC S-m7xkty3c]
- A 2019 survey of change detection and notification systems reports that most change-frequency work assumes changes arrive as a Poisson process, with the rate λ estimated per page as 1/Δ for a mean time Δ between changes, and that Cho and Garcia-Molina proposed frequency estimators of different accuracy for different applications. [DOC S-7uckhkxr]
- The same survey reports that pages of sports and news sites change often while government and educational pages change less, which is why such systems schedule checks per page from its estimated change frequency. [DOC S-7uckhkxr]
- A 2008 WWW poster by two Google authors calls the simple estimator of a page's change rate, the changes observed divided by the time observed, significantly asymptotically biased when the time between checks is not small against the time between changes: several changes within one check interval show as one, so a check interval too long against the change interval makes the estimate overestimate the time between changes, however many checks are made. [DOC S-ea26tgr2]
- The same poster cites Cho and Garcia-Molina (ACM TOIT 3(3), 2003, its section 4.2) for a modified estimator that subtracts the expected bias and avoids singularities, `-1 / log((T - X + 0.5) / (T + 0.5))` with `T` the time observed and `X` the changes observed, and reports it has better bias even below 50 observations, most where the check interval is about 0.5 to 2 times the change interval; its asymptotic results do not hold when the changes are significantly non-Poisson. [DOC S-ea26tgr2]
- In the poster's sample of 29,000 quickly changing pages, checked hourly, nearly 20% followed a regular 1-hour pattern better than a Poisson process and pages with a mean change interval near 24 hours showed a spike of intervals of exactly 24 hours, so a source that is regenerated on a schedule breaks the Poisson assumption. [DOC S-ea26tgr2]
- A 2021 paper on online change-rate estimation (Avrachenkov, Patil, Thoppe) describes the naive estimator as the ratio of observed changes to total monitoring time, "clearly biased" because the crawler learns only whether a page changed since its last visit; the maximum likelihood estimator also handles irregular access times but has no closed form, must be recomputed from the whole history at each observation, and its value is infinite while a change is detected at every access. [DOC S-vrx7t6cc]
- Mapped onto the kb's sources, a change rate read from the recorded change dates of one source counts at most one change per check, so it underestimates the rate when several edits fall between two checks and overstates the freshness lifetime; the checks come at irregular times (census, refresh, lookups), not at a regular interval, which the modified estimator's formula assumes; a source that changed at every check has an infinite plain rate, where the `0.5` terms keep the modified estimate finite. [DER S-ea26tgr2, S-vrx7t6cc: the poster's bias and formula, the paper's irregular-access and instability remarks, applied to the checks the kb records]
- FreshQA (600 questions) found that all models tested, whatever their size, struggle with questions that need fast-changing knowledge, and that FreshPrompt, which puts current search-engine evidence into the prompt, raised GPT-4's accuracy substantially; the number and the order of the evidence items both changed correctness. [DOC S-rcaeqaft]
- Mapped onto a kb lookup, a fact line's "age" is the time since its anchor's `verified_utc` or its source's last check, a source's heuristic freshness lifetime can be a fraction of the time since its content date or estimated from its own change history, and a lookup can print the fact with its age and revalidate the cited sources after or beside the answer, as stale-while-revalidate does. [DER S-ods72iyh, S-m7xkty3c, S-7uckhkxr]
- The kb's calibration on two Microsoft documentation repositories found about 99% of sentences kept word for word across an edit of a page, and an eight-month replay of the `entra` domain found 82 of 94 anchored facts on changed pages word for word and 5 not found: a source-level "changed" flag alone would mostly be a false alarm, and a check at the fact's anchored passage is what separates the facts that changed (`kb/_self/reports/fact-diff.md`). [DER S-wcrrjfwh, S-ods72iyh: page-level change against passage-level change in the kb's own replay]
- An offline probe on 2026-10-11 (Python 3.13.2 on macOS, kb at origin/main 58e7bff, no model) revalidated the sources one `pack` cites with `factdiff.py detect --no-save`: three Learn and pinned sources of an Autopilot question in 1.9 s (two unchanged, one pinned), five pinned DSC files in 0.2 s with no request, and five `code.claude.com` pages in 7.3 s, all `changed` by text hash since that host gives no ETag, with 134 facts citing them verbatim, 8 modified, 5 not found and 65 unanchored; over the pool's answerable questions, 186 of the 241 DOC lines `pack` printed (77%) had a located anchor for every cited source. [DER S-ods72iyh, S-7uckhkxr: the revalidation and anchor rules above run on the kb's own lookups]
