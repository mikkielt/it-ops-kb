# Microsoft Entra Agent ID

Extends, does not repeat, `agents/agent-rbac.md` (Entra Agent ID's role in RBAC for agents, app-role vs
group-claim behavior for service principals), `agents/api-tokens-issue-and-store.md` (workload identity
federation for issuing credentials), `auth/workload-identity.md` (Entra federated identity credentials,
Azure Arc managed identity) and `agents/own-chatbot-architecture.md` (Foundry Agent Service's own Entra
agent identities, A2A support). This article is the identity-platform-first view: what an agent identity
and its blueprint are, how they authenticate, how they're governed and protected, and which Microsoft
products create them automatically.

## Summary
- Microsoft Entra Agent ID is an identity and security framework that extends Entra capabilities to AI
  agents; the platform for creating and managing agent identities and blueprints is available for all
  Microsoft Entra customers, while extending Entra security features to agents requires **Microsoft
  Agent 365**. [DOC S-fdnhk2tn]
- Microsoft Entra Agent ID is now generally available. [DOC S-ifhonpv7]
- An agent identity is a credential-less service principal; all credentials live on a reusable **agent
  identity blueprint**, which acquires tokens on the agent identity's behalf in three modes: app-only
  (autonomous), on-behalf-of a user (interactive/delegated), or as the audience of an incoming call.
  [DOC S2040]
- Governance (sponsors, access packages, lifecycle workflows) and protection (Conditional Access, ID
  Protection risky-agent detection) are built by re-using Entra ID Governance and Identity Protection
  machinery already documented for human/group identities, extended to the `agentIdentity`,
  `agentIdentityBlueprint`, and `agentUser` object types. [DOC S-midck7u4, S-735ghpq5, S-5yopk2hr]
- Microsoft Foundry (per-project and per-published-agent) and Microsoft Copilot Studio (per-agent, sharing
  one tenant-wide blueprint, since May 2026 per the Copilot Studio admin page) create agent identities
  and blueprints automatically; in Microsoft Teams a developer creates and manages blueprints in the
  Developer Portal. [DOC S-midck7u4, S-q6lirjr2]

## Facts

### What an agent identity is
- Microsoft Entra Agent ID is generally available: its What's new page opens with "Microsoft Entra Agent ID
  is now generally available." [DOC S-ifhonpv7]
- The Agent ID overview page, re-read 2026-09-27, no longer carries the PREVIEW banner that was quoted
  from it on 2026-09-26. [DOC S-fdnhk2tn]
- An agent identity is "a special service principal... that represents an identity that the agent
  identity blueprint created and is authorized to impersonate," with no credentials of its own. [DOC S2040]
- Components of an agent identity: an `id` (object ID) generated by Entra; no credentials (relies on the
  blueprint); a human-friendly, changeable **display name** shown in the Entra admin center, Azure portal,
  Teams, and Outlook; an optional **sponsor** (a human or group accountable for the agent, e.g. for
  incident contact); the **blueprint** it was created from; and an optional second **agent's user
  account** for systems that strictly require a Microsoft Entra user account for authentication (1:1 with
  the agent identity, different `id`). [DOC S2040]
- The object ID and app ID of an agent identity always have the same value and can be reliably used for
  authentication/authorization decisions. [DOC S2040]
- Agent identities are always **single-tenant** and can only be issued tokens in the tenant where they
  were created, even when created from a multitenant blueprint (which then creates one tenant-local agent
  identity per tenant it is added to). [DOC S2040]
- Base platform availability: "Microsoft Entra Agent ID is a product within Microsoft Entra... available
  for all Microsoft Entra customers" for creating and managing agent identities and blueprints. [DOC
  S-fdnhk2tn]

### Authentication modes and OBO for agents
- Three explicit token-acquisition modes: (a) autonomous agent → app token, subject = agent identity;
  (b) interactive agent called with a user token → user token acquired on-behalf-of the agent identity,
  subject = the user, actor = the agent identity; (c) agent identity as the token's audience (incoming
  calls). [DOC S2040]
- Agent identities authenticate only via **federated identity credentials (FIC)** issued by the blueprint
  — never passwords, SMS, passkeys, or authenticator apps — because credentials never reside on the agent
  identity itself, only on the blueprint (FICs, certificates/keys, or client secrets). [DOC S2040]
- Two named Conditional-Access-relevant access patterns for agents: **on-behalf-of (OBO)** — a signed-in
  user's identity and delegated permissions are used by the agent, so Conditional Access targets **users
  and groups**, not the agent identity, because the user is the subject; and **application (client
  credentials)** access — the agent uses its own identity with no signed-in user, used by autonomous
  scheduled/background agents or interactive agents not acting on a user's behalf. [DOC S-735ghpq5]

### Agent identity blueprint
- The blueprint is the reusable template ("kind") an organization adds once per agent product (e.g. a
  purchased "Sales Assistant Agent"); it records the blueprint's name, publisher, offered roles (e.g.
  "sales manager"), and the Graph permissions its agents are granted. [DOC S2040]
- Fleet-wide policy is the blueprint's stated purpose: because every agent identity of one kind shares a
  blueprint, an admin can apply one Conditional Access policy, disable all agents of that kind, or revoke
  a permission grant, in a single action across the whole fleet. [DOC S2040]
- The Graph `agentIdentityBlueprint` resource **inherits from `application`** and is an open type; it adds
  a `sponsors` relationship (required at create; "users or groups who can authorize and manage the
  lifecycle of agent identity instances") alongside the inherited `owners`, `federatedIdentityCredentials`,
  `passwordCredentials` and `requiredResourceAccess` (capped, like any application registration, at 50
  resource services / 400 total required permissions). [DOC S-nzxr4eg2]
- `inheritablePermission` on the blueprint defines scopes of a resource application that may be
  automatically granted to agent identities created from it, without additional consent. [DOC S-nzxr4eg2]
- The v1.0 `agentIdentityBlueprint` resource lists List, Create, Get, Update, Upsert and Delete methods,
  plus credential (password, key, federated identity credential), owner and sponsor methods. [DOC
  S-nzxr4eg2]
- Create: `POST /applications/microsoft.graph.agentIdentityBlueprint`, least-privileged
  `AgentIdentityBlueprint.Create` (higher: `AgentIdentityBlueprint.ReadWrite.All`), body must give
  `displayName` and `sponsors`; a non-owner in delegated calls needs **Agent ID Administrator** or **Agent
  ID Developer**. Get: `GET /applications/{id}/microsoft.graph.agentIdentityBlueprint`, least-privileged
  `AgentIdentityBlueprint.Read.All` (higher: `Application.Read.All`); a non-owner needs **Agent ID
  Administrator**. [DOC S-ee22tgci, S-rasraulp]
- Whoever creates a blueprint (or blueprint principal) is automatically its owner; owners can create and
  modify agent identities under a blueprint they own without any separate Agent ID role assignment. [DOC
  S-ee22tgci, S-rasraulp]
- Credential management is a distinct Graph permission from general read/write: adding or removing a
  blueprint's password credentials needs the least-privileged `AgentIdentityBlueprint.AddRemoveCreds.All`,
  separate from `AgentIdentityBlueprint.ReadWrite.All`. [DOC S-nzxr4eg2]
- The blueprint has a `disabledByMicrosoftStatus` property (`null`, `NotDisabled`, or
  `DisabledDueToViolationOfServicesAgreement`) inherited from `application`, i.e. Microsoft can disable a
  blueprint tenant-wide for abuse. [DOC S-nzxr4eg2]

### Governance: sponsors, owners, and access packages
- Distinct administrative relationships: owners (technical administrators, optional, for blueprints and
  agent identities), sponsors (business accountability; required at creation of agent identities and
  blueprints; also possible on blueprint principals and agents' user accounts) and managers (individual
  users, set on the agent's user account, who can request access packages but can't modify or delete the
  agent). [DOC S-ch6zrjfg]
- Access packages (Entra entitlement management) are the recommended mechanism for standardized,
  time-bound, auditable access for fleets of agents with common needs (e.g. many customer-support
  agents), instead of ad-hoc permission assignment; resource roles allowed in an agent access package are
  **security group memberships, Microsoft Entra directory roles, and OAuth application-permission
  grants** — explicitly **not** application roles, SAP roles, or SharePoint Online site roles (agent
  identities/service principals cannot be added to those via access packages). [DOC S-lekwizgd]
- Three access-package request pathways for an agent: the agent identity itself (programmatically, via
  `accessPackageAssignmentRequest`), its sponsor requesting on the agent's behalf, or an administrator's
  direct assignment. [DOC S-lekwizgd]
- Creating an access package with OAuth API permissions or directory roles as resource roles marks the
  containing catalog **privileged** and requires **Global Administrator** (vs. Identity Governance
  Administrator for a package with only group resource roles). [DOC S-lekwizgd]
- On assignment expiry, if a sponsor is set, the sponsor is notified and can request an extension
  (triggering a new approval cycle) or let the assignment expire automatically, removing the agent's
  access. [DOC S-lekwizgd]
- Licensing for governance specifically: using Entra ID Governance for agent identities requires either
  **Microsoft 365 E7** (includes Agent 365 + Entra Suite) or a **Microsoft Agent 365** licence paired with
  at least Entra ID P1 or Microsoft 365 E3. [DOC S-midck7u4]

### Conditional Access for agents
- Conditional Access enforcement applies whenever an agent identity or agent's user account requests a
  token for a resource; it does **not** apply when a blueprint itself acquires a token to create agent
  identities or agent's user accounts. [DOC S-735ghpq5]
- CA policies can scope to **All agent identities** or **All agent users (Preview)** (or selected ones)
  against **All resources**; for agent identities the only condition is **agent risk** (high/medium/low)
  and the only control is **Block access**. [DOC S-6ecweang]
- Conditional Access policies for agent identities support **Report-only** mode for evaluation before enforcement (Manage agent identities, 2026-06-17); the best-practices page also says to test agent policies in report-only mode first. [DOC S-sxxqhpa2, S-uva2ob4g]
- The Conditional Access template list has an **AI Agents** category with three templates: Block high-risk
  agent identities, Configure policy for autonomous agent access, and Configure policy for on-behalf-of agent
  access. [DOC S-3puxctla]
- For on-behalf-of (delegated) agent access, the Conditional Access for agents page says policies target
  **users and groups**, since the user is the token subject; autonomous (client-credentials) flows are
  targeted at the agent identity. [DOC S-735ghpq5]
- Best-practice guidance explicitly warns against reusing user-targeted policies (e.g. "all users must use
  MFA") for agents, because agents cannot satisfy interactive controls like MFA; dedicated agent policies
  should instead use identity filters, risk signals, custom security attributes, and named locations as
  control points. [DOC S-uva2ob4g]

### ID Protection for agents (risky agents)
- ID Protection for agents requires one of **Security Administrator**, **Security Operator**, or
  **Security Reader** to view Risky Agent reports, and **Conditional Access Administrator** to build
  policies keyed on agent risk. [DOC S-5yopk2hr]
- Licensing: ID Protection for agents "will require a Microsoft Agent 365 license" to extend protection to
  agents via Entra Agent ID (stated as a forthcoming requirement at time of retrieval, i.e. not yet fully
  enforced). [DOC S-5yopk2hr]
- **Learning Mode** automatically suppresses behavioral risk alerts for agents that lack sufficient
  activity history (new or long-idle agents), reducing false positives during onboarding, while a
  separate parallel detection still catches genuinely malicious early-life behavior. [DOC S-5yopk2hr]
- Agent risk detections (all offline at retrieval) cover autonomous agent activity; in on-behalf-of flows
  risky activity is attributed to the **user**, not the agent. Risk-based Conditional Access policies can
  block risky agents, and "Confirm compromise" sets the agent's risk to High. [DOC S-5yopk2hr]
- The migration pages still list "risk-based detection and automated remediation" from ID Protection and agent registry visibility as benefits of Agent ID, but the current Agent ID overview (re-read 2026-09-27) no longer says risk signals feed the Agent Registry with automatic remediation; that sentence survives only in the Learn search index's older copy. Treat a registry-driven automatic remediation as unconfirmed. [DER S-pbkrk3ow, S-fdnhk2tn: present on the migration page, absent from the live overview]
- Programmatic access: Microsoft Graph exposes `riskyAgents` and `agentRiskDetections` collections; the
  Risky Agents report also offers a **Disable** action that blocks all sign-ins for the agent. [DOC
  S-5yopk2hr]

### Agent Registry and lifecycle governance
- Agent registry experiences are converging under **Microsoft Agent 365**, which becomes the unified
  registry and control plane for agents, while Entra keeps providing the identity foundation through
  Agent ID. [DOC S-avju6l5n]
- Governance features for agent identity lifecycle: periodic access reviews with sponsor attestation every
  6-12 months, decommissioning on non-confirmation, and a quarterly review process to find orphaned agents
  (missing sponsors, stale metadata, no recent activity). [DOC S-uva2ob4g]
- Sponsorship continuity: if a sponsor leaves the organization, sponsorship of their agent identities is
  automatically transferred to their manager; Lifecycle Workflows include tasks that notify cosponsors and
  the sponsor's manager of sponsorship changes. [DOC S-midck7u4]
- Lifecycle Workflows has three agent-sponsor tasks, all **mover and leaver** tasks available only in
  mover or leaver templates: send email to manager about sponsorship changes, send email to cosponsors
  about sponsor changes, and transfer agent identity sponsorships to manager. [DOC S-3avzf7db]

### Which products create agent identities/blueprints automatically
- **Microsoft Foundry**: on the first agent created in a Foundry project, Foundry provisions a default
  agent identity blueprint and a default agent identity for the project (agents share the project's agent
  identity); **publishing** an agent instead creates a dedicated blueprint and agent identity, unique to
  that published agent, used for MCP and A2A tool authentication. [DOC S-midck7u4]
- **Microsoft Copilot Studio**: per the admin page, starting **May 2026** all new Copilot Studio agents
  automatically get an Entra Agent ID and the environment-level opt-out is gone (another Learn page gives
  2026-03-18, see `_conflicts.md`). All Copilot-Studio-created agent identities are children of one
  **Microsoft Copilot Studio agent identity blueprint** (Blueprint ID
  `25664c89-cea5-4ab6-b924-a54fd8a19ae0` at retrieval). [DOC S-q6lirjr2]
- The Agent 365 Copilot Studio identity page says that unlike pro-code agents, where each agent has its own blueprint, all Copilot Studio app-based agents share one blueprint. [DOC S-ketmxnue]
- Entra's planning guidance instead defaults to one blueprint per **trust boundary**: agents sharing a runtime, secrets, file system and network can share one, and blocking, audit separation or scale-out are not reasons to add blueprints (see `_conflicts.md`). [DOC S-3tt3ywvk]
- Agents created **before** the May 2026 rollout keep using legacy **app registrations**; Microsoft will
  migrate them in a future update, and meanwhile they can be migrated manually in the Power Platform admin
  center, with PowerShell scripts, or with Power Platform APIs. Governance works for both identity types
  during the transition. [DOC S-q6lirjr2]
- Deleting a Copilot Studio agent also deletes its associated Entra Agent ID. [DOC S-q6lirjr2]
- Each Copilot Studio Entra Agent ID is provisioned as a directory object at agent-**creation** time and
  counts against the tenant's Microsoft Entra directory-object quota: **50,000** objects by default, or
  **300,000** if the tenant has a verified domain (a tenant created through self-service sign-up stays at
  50,000 even after verifying a domain); agent identities plus all other Entra resources can use no more
  than **95%** of this quota. If the tenant is at quota when an agent is created, Copilot Studio can't
  provision the Agent ID and agent creation fails. [DOC S-l4557zht]
- Agent IDs are Entra service principals with an "Agent" subtype using the same OAuth-based authentication
  flow as a standard app registration; when an existing app-registration agent is migrated, its GUID is
  preserved (no breaking change) and migration is zero-downtime with no manual action required. [DOC
  S-l4557zht]
- **Microsoft Teams**: developers create and manage agent identity blueprints via the Teams Developer
  Portal. [DOC S-midck7u4]
- **Microsoft Agent 365** itself gives each AI agent its own Entra Agent ID for identity, lifecycle, and
  access management. [DOC S-midck7u4]

## Examples
- Registering a new blueprint via Graph (least-privileged app permission `AgentIdentityBlueprint.Create`):
  ```http
  POST https://graph.microsoft.com/v1.0/applications/microsoft.graph.agentIdentityBlueprint
  Content-Type: application/json

  {
    "displayName": "Sales Assistant Agent",
    "sponsors@odata.bind": [
      "https://graph.microsoft.com/v1.0/users/jan.kowalski@corp.example.com"
    ]
  }
  ```
- Reading a blueprint's properties (least-privileged `AgentIdentityBlueprint.Read.All`):
  ```http
  GET https://graph.microsoft.com/v1.0/applications/{id}/microsoft.graph.agentIdentityBlueprint
  ```
- An agent identity acting autonomously (client-credentials/app-only pattern) is not affected by a
  Conditional Access policy that targets users and groups for MFA; a separate agent-scoped policy
  (`policy-autonomous-agents` template) with an agent-risk condition is needed to cover it, per the
  best-practice guidance against reusing user-targeted policies for agents.
