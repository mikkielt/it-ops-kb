# OpenTelemetry monitoring events (MCP-relevant)

## Summary
Enable with `CLAUDE_CODE_ENABLE_TELEMETRY=1` plus OTLP exporter variables. MCP activity appears in
`claude_code.mcp_server_connection`, `claude_code.tool_result` and `claude_code.tool_decision` events. Without
`OTEL_LOG_TOOL_DETAILS=1`, user-configured MCP tools appear as `tool_name = "mcp_tool"` with no server/tool names or arguments.

## Facts
- Enable: `CLAUDE_CODE_ENABLE_TELEMETRY=1`; `OTEL_METRICS_EXPORTER` (otlp, prometheus, console, none); `OTEL_LOGS_EXPORTER` (otlp, console, none); `OTEL_EXPORTER_OTLP_PROTOCOL`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_HEADERS`. [DOC S744]
- `claude_code.tool_result`: `tool_name`, `tool_use_id` (matches hook `tool_use_id`), `success`, `duration_ms`, `error_type`, `decision_type`, `decision_source` (config/hook/user_permanent/user_temporary), `tool_input_size_bytes`, `tool_result_size_bytes`, `mcp_server_scope`; with details flag: `error`, `tool_parameters` (`mcp_server_name`, `mcp_tool_name`), `tool_input` (values >512 chars truncated, ~4K total). [DOC S744]
- `claude_code.tool_decision`: `decision` (accept/reject), `tool_source` (builtin/mcp/sdk_host_builtin_mcp), `source` (config, hook, user_permanent, user_temporary, user_abort, user_reject); `tool_parameters` with details flag. [DOC S744]
- `claude_code.mcp_server_connection`: `status` (connected/failed/disconnected), `transport_type`, `server_scope`, `duration_ms`, `error_code`, `is_plugin`; `server_name` and `error` only with `OTEL_LOG_TOOL_DETAILS=1`. [DOC S744]
- Without `OTEL_LOG_TOOL_DETAILS`, user-configured MCP tools are redacted to `tool_name = "mcp_tool"` and argument content is omitted. [DOC S744]
- `OTEL_LOG_TOOL_CONTENT=1` includes tool content in the `tool.output` span event (tracing beta). [DOC S745]
- `OTEL_LOG_USER_PROMPTS=1` includes prompt text (redacted by default). [DOC S745]
- `claude_code.user_prompt` is logged when a user submits a prompt, with `prompt_length`, `prompt` (redacted unless `OTEL_LOG_USER_PROMPTS=1`) and `message.uuid` (the transcript entry; absent for command dispatches, which can produce zero or many messages). [DOC S744]
- `prompt.id` (UUID v4) links every event produced while processing one user prompt: filtering on it returns the `user_prompt` event, its `api_request` events and its `tool_result` events. The same id reaches hooks as the `prompt_id` input field (`claude/hooks.md`). [DOC S744, S743]
- `claude_code.token.usage` (unit tokens) and `claude_code.cost.usage` (unit USD) are counters incremented after each API request; both carry all standard attributes (including `session.id`, on by default and switched off with `OTEL_METRICS_INCLUDE_SESSION_ID=false`) plus `model`, `query_source`, `speed`, `effort` and `agent.name`, `skill.name`, `plugin.name`, `marketplace.name`, `mcp_server.name`, `mcp_tool.name`; `token.usage` adds `type` with the values `input`, `output`, `cacheRead` and `cacheCreation`. [DOC S744]
- On the metrics, `query_source` is one of `main`, `subagent` or `auxiliary`, and the `subagent` category also counts requests from agent-based hooks; `agent.name` is absent when no named subagent type issued the request, and `agent.name`, `skill.name` and `plugin.name` show a redacted `custom` or `third-party` placeholder unless `OTEL_LOG_TOOL_DETAILS=1`. [DOC S744]
- The docs say to roll subagent tokens and cost up from the token and cost counters filtered to `query_source` `subagent`, because `claude_code.subagent_completed` has `total_tokens` for only the subagent's final API request (its context size at completion, not a sum), alongside `agent_type`, `total_tool_uses`, `duration_ms`, `is_async`, `model` and `agent.source`. [DOC S744]
- `claude_code.api_request` (one event per API request) carries `model`, `cost_usd`, `cost_usd_micros`, `duration_ms`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `request_id`, `client_request_id`, `speed`, `effort`, `query_source` (there `repl_main_thread`, `compact` or a subagent name, not the metric's three values) and the same `agent.name`/`skill.name`/`plugin.name` attribution; events, unlike metrics, also carry `prompt.id`, so cost per prompt comes from events and cost per session from either. [DOC S744]
- Event correlation keys that match the session transcript: `message.uuid` (the transcript entry; on `user_prompt`, `assistant_response`, `api_response_body`), `request_id` (persisted as `requestId` on the transcript's assistant entries) and `tool_use_id`; the docs call these joins version-specific because the transcript entry format is internal and changes between versions. `event.sequence` is a per-process counter, so within a resumed session it can repeat or go backwards and events sort by `event.timestamp` first. [DOC S744]
- Each streaming response counts toward the cost and token metrics once, including gateways that stream usage over several frames. (The earlier note that versions before v2.1.214 double-counted such streams is no longer on the page.) [DOC S744]
- Admin monitoring guidance: set `OTEL_LOG_TOOL_DETAILS=1` to see which MCP servers and tools users invoke. [DOC S741]
- PostToolUse `updatedToolOutput` does not affect telemetry, which captures the original output. [DOC S743]
- Claude Code has no default OTLP protocol: each `otlp` exporter needs `OTEL_EXPORTER_OTLP_PROTOCOL` or its signal's own variable (`OTEL_EXPORTER_OTLP_LOGS_PROTOCOL` for logs and events), and a per-signal endpoint or protocol variable such as `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` replaces the generic one for that signal. [DOC S744]
- Logs and events are exported every `OTEL_LOGS_EXPORT_INTERVAL` milliseconds (default 5000); metrics every `OTEL_METRIC_EXPORT_INTERVAL` milliseconds (default 60000). [DOC S744]
- For the `http/protobuf` and `http/json` protocols Claude Code sends each export request with a `Content-Length` header. (The page no longer carries the earlier note that versions from v2.1.191 used chunked transfer encoding, which length-requiring endpoints rejected with `411`.) [DOC S744]
- `OTEL_LOG_TOOL_DETAILS` (default disabled) is the switch for tool parameters and input arguments in tool events and span attributes: Bash commands, MCP server and tool names, skill names and tool input; left unset, they stay out of the events. [DOC S744]
- The OTLP exporter's protocol is one of `grpc`, `http/protobuf` or `http/json`; a per-signal endpoint such as `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` is used as-is, while `OTEL_EXPORTER_OTLP_ENDPOINT` is a base URL to which `v1/logs` is appended for logs. [DOC S-kumwk4fp]
- An OTLP/HTTP log request is a POST to `/v1/logs` whose body is an `ExportLogsServiceRequest`; the default OTLP/HTTP port is 4318, and on success the server answers `HTTP 200 OK` with an `ExportLogsServiceResponse`. [DOC S-v2wnj4qk]
- In OTLP's JSON encoding the request and response carry `Content-Type: application/json`, object keys are field names in lowerCamelCase, 64-bit integers such as `timeUnixNano` are decimal strings, and enum values are integers. [DOC S-v2wnj4qk]
- OTLP JSON payloads encode 64-bit integer fields as decimal strings and decoders accept either numbers or strings; the pinned OTLP specification text does not mention `AnyValue` or how an attribute that holds a number is typed. [DOC S-v2wnj4qk]
- In one headless `claude -p` session on 2026-10-22 with `OTEL_EXPORTER_OTLP_LOGS_PROTOCOL=http/json`, a `tool_result` event carried `success`, `duration_ms` and `tool_result_size_bytes` as `stringValue` (`"true"`, `"716"`, `"29"`) while its `api_request` event carried `duration_ms` as `intValue` and `cost_usd` as `doubleValue`; the Claude Code version was not recorded, the docs list these attributes without a type, and other versions and modes were not run. [UNK: one unversioned observation, to repeat with a recorded version]
- A logs request nests `resourceLogs`, then `scopeLogs`, then `logRecords`; each log record carries `timeUnixNano`, a `body` (`AnyValue`), `attributes` (a list of key and value pairs) and an `eventName`, which names the event's schema. [DOC S-iekncbeu]
- A standard-library local receiver for Claude Code's events needs only an HTTP server on `127.0.0.1` that accepts `POST /v1/logs` with `Content-Type: application/json`, reads each log record's `eventName` and `attributes`, and answers `200` with an empty JSON object; the session runs with `CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_LOGS_EXPORTER=otlp`, `OTEL_EXPORTER_OTLP_LOGS_PROTOCOL=http/json`, `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` set to that URL and `OTEL_LOG_TOOL_DETAILS` and `OTEL_LOG_USER_PROMPTS` unset, so no tool input or prompt text arrives. [DER S744, S-kumwk4fp, S-v2wnj4qk, S-iekncbeu: the variables, endpoint rules, path, encoding and record layout above]

### Collecting every member's telemetry centrally
- An administrator turns telemetry on for all users by putting `CLAUDE_CODE_ENABLE_TELEMETRY` and the `OTEL_*` exporter variables in the `env` block of the managed settings (the docs' example sets the OTLP exporters, a `grpc` protocol, a collector endpoint and an `Authorization` header). Claude Code ignores the OpenTelemetry exporter variables in a repository's `.claude/settings.json` and `.claude/settings.local.json`, so a repository cannot turn telemetry on, pick the destination or capture content. [DOC S744]
- A managed `OTEL_EXPORTER_OTLP_ENDPOINT` makes Claude Code remove every developer-set per-signal endpoint at startup, a managed `OTEL_EXPORTER_OTLP_PROTOCOL` removes developer-set per-signal protocols, and a managed `OTEL_EXPORTER_OTLP_HEADERS`, client key or client certificate removes the developer-set per-signal versions plus every developer-set endpoint; exporter selectors follow normal per-key precedence, so set `OTEL_METRICS_EXPORTER` and `OTEL_LOGS_EXPORTER` in managed settings too if developers must not disable a signal (v2.1.223+). [DOC S744]
- Standard attributes on every metric and event identify the user and session: `session.id` (on by default), `organization.id`, `user.account_uuid` and `user.account_id` (on by default), `user.email` (when authenticated), `user.id` (an anonymous random identifier kept in `~/.claude.json`, not derived from the account) and `terminal.type`; `app.version`, `app.entrypoint` and the repository attributes are off by default and switched on with `OTEL_METRICS_INCLUDE_VERSION`, `_ENTRYPOINT` and `_REPOSITORY`. [DOC S744]
- `OTEL_RESOURCE_ATTRIBUTES` adds custom attributes such as `department`, `team.id` or `cost_center` to all metrics and events, so cost can be filtered per team or cost centre; values must be percent-encoded for spaces and similar characters. [DOC S744]
- Per user and per session cost and tokens therefore come from the `claude_code.cost.usage` and `claude_code.token.usage` counters grouped by `user.email` (or `user.account_id`) and `session.id`; per prompt needs the events, whose `prompt.id` metrics never carry. [DER S744: the counters, the standard attributes and the events-only `prompt.id` read together]
- Through a Claude apps gateway the CLI stamps each export from the gateway-issued JWT with `user.id` (the IdP subject), `user.email`, `user.groups` and `identity.source: gateway-oidc`, which `OTEL_RESOURCE_ATTRIBUTES` cannot override; the gateway then acts as an authenticated OTLP relay that, when `telemetry.forward_to` and `listen.public_url` are set, pushes the exporter variables to connected clients and forwards their traffic to each listed destination, metrics only unless a destination also opts into logs or traces. [DOC S744, S-r7mszxqu]
- `user.email` comes from the sign-in or, in a cloud session, from the session's own credentials; `organization.id` is always included when authenticated; `user.account_id` is the account in the tagged form the Anthropic admin APIs use (`user_01...`), and `OTEL_METRICS_INCLUDE_ACCOUNT_UUID` (default `true`) controls both `user.account_uuid` and `user.account_id` on metrics. [DOC S744]
- When authenticated through OAuth, `user.email` is in the telemetry attributes, sent only to the configured OpenTelemetry endpoint and never to Anthropic; the docs leave filtering or redacting it to the telemetry backend. [DOC S744]
- In a session a developer starts, MCP tool calls, Bash commands and file edits are attributed to the developer's own Claude account (or IdP identity on a gateway session), not to a separate service account. [DOC S744]
- OpenTelemetry data from Claude Code goes only to destinations the organization configures, never to Anthropic. [DOC S-r7mszxqu]
- Cloud sessions (including Claude Tag) run on Anthropic-hosted VMs, so a device's managed file does not configure them: set the variables in server-managed settings `env` (reaches cloud sessions except Claude Tag) or in the cloud environment's variables (the only route that reaches Claude Tag); anyone who uses an environment can read its variables, so a collector token goes through server-managed settings instead, and the collector's domain must be on the environment's network allowlist. Cloud sessions add `ccr.session.id`; Claude Tag sessions act as the organization's shared identity, so `user.*` does not say who tagged Claude, and `OTEL_METRICS_INCLUDE_ENTRYPOINT=true` marks them with `app.entrypoint` `claude-in-slack`. [DOC S744]
- Beside OpenTelemetry the docs list, for usage reporting, an analytics dashboard (Teams and Enterprise at `claude.ai/analytics`, Console at `platform.claude.com/claude-code`) and per-user usage and cost over an API (Enterprise Analytics API on Enterprise, Claude Code Analytics API on Console); on Teams and Enterprise, per-user spend numbers come from the spend report, not the dashboard. [DOC S-ggeduchu]

### Distributed tracing (beta) and trace context
- Distributed tracing is a beta feature, off by default: set `CLAUDE_CODE_ENABLE_TELEMETRY=1` and `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1` (`ENABLE_ENHANCED_TELEMETRY_BETA` is also accepted), then `OTEL_TRACES_EXPORTER` (comma-separated: `console`, `otlp`, `none`) to choose where spans go; the docs title the section "Traces (beta)". [DOC S744]
- Traces reuse the common OTLP configuration, and the per-signal variables `OTEL_EXPORTER_OTLP_TRACES_PROTOCOL` (`grpc`, `http/json`, `http/protobuf`) and `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` override `OTEL_EXPORTER_OTLP_PROTOCOL` and `OTEL_EXPORTER_OTLP_ENDPOINT`; `OTEL_EXPORTER_OTLP_TRACES_HEADERS` is merged with `OTEL_EXPORTER_OTLP_HEADERS` and `OTEL_TRACES_EXPORT_INTERVAL` (default 5000 ms) sets the span batch interval. Spans redact prompt text, tool input details and tool content unless `OTEL_LOG_USER_PROMPTS=1`, `OTEL_LOG_TOOL_DETAILS=1` and `OTEL_LOG_TOOL_CONTENT=1` are set. [DOC S744]
- Span hierarchy: each user prompt starts a `claude_code.interaction` root span whose children are `claude_code.llm_request`, `claude_code.tool` and `claude_code.hook`; a tool span has two children, `claude_code.tool.blocked_on_user` (the wait for a permission decision) and `claude_code.tool.execution`, and a subagent started by the Agent tool nests its API and tool spans under the parent's `claude_code.tool` span. [DOC S744]
- Status rules: the `llm_request`, `tool.execution` and `hook` spans set OpenTelemetry status `ERROR` when they record a failure, and every other span (interaction, tool, `tool.blocked_on_user`) always ends with status `UNSET`; every span carries the standard attributes plus a `span.type` attribute matching its name. [DOC S744]
- The `claude_code.hook` span appears only under detailed beta tracing, which needs `ENABLE_BETA_TRACING_DETAILED=1` and `BETA_TRACING_ENDPOINT` (both ignored in project and local settings; the pair also changes where logs and traces go); `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA` alone does not produce it, and interactive CLI sessions also need the organization to be allowlisted while Agent SDK and `-p` sessions do not. [DOC S744]
- In Agent SDK and non-interactive sessions started with `-p`, Claude Code reads `TRACEPARENT` and `TRACESTATE` from its own environment when it starts each interaction span, so `claude_code.interaction` becomes a child of the caller's span in the caller's distributed trace; interactive sessions ignore an inbound `TRACEPARENT`, so values inherited from CI or a container environment are not picked up. [DOC S744]
- `claude_code.interaction` carries a `parent.source` attribute that says how the span got its trace parent: `env` when it parented under an inbound `TRACEPARENT`, `none` when it started its own trace; it needs Claude Code v2.1.268 or later. [DOC S744]
- Event log records carry `trace_id` and `span_id` without a traces exporter: in Agent SDK and `-p` sessions with `TRACEPARENT` set, each OTLP event log record carries the `trace_id` and `span_id` that join it to the caller's trace, even when no traces exporter is configured. The docs page names no version for this; the changelog lists the fix for records missing them in SDK or headless mode under v2.1.212. [DOC S744, S746]
- Which IDs an event record carries: a record emitted while an interaction is active carries the interaction span's `trace_id` and `span_id` (also outside the span's async context, such as in a permission prompt callback or a record buffered during startup), and a record emitted with no active interaction span carries the inbound `TRACEPARENT` IDs directly; the changelog lists the fix for log events emitted outside the turn's async context missing the interaction span's trace context under v2.1.214. [DOC S744, S746]
- Bash and PowerShell subprocesses inherit a `TRACEPARENT` environment variable, set to the W3C trace context of the active tool execution span, while tracing is active; by default this happens only when `ANTHROPIC_BASE_URL` is unset or points at the Anthropic API, and `CLAUDE_CODE_PROPAGATE_TRACEPARENT=1` turns propagation on behind a custom proxy, for the `TRACEPARENT` variable of Bash, PowerShell and hook subprocesses and for the `traceparent` header (added in v2.1.152). [DOC S744, S745]
- While tracing is active and Claude Code is connected directly to the Anthropic API, each model request carries a W3C `traceparent` header set to the `claude_code.llm_request` span's context and the API's `traceresponse` header is recorded as a span link; outbound HTTP MCP requests carry `traceparent` the same way, and it is not sent to third-party providers. [DOC S744]
- Claude Code attaches the keys of `OTEL_RESOURCE_ATTRIBUTES` as attributes on every metric datapoint and every event record, in addition to the OTLP resource block, so backends can group and filter by them; `OTEL_METRICS_INCLUDE_RESOURCE_ATTRIBUTES=false` (default `true`, in effect from v2.1.161) keeps them in the resource block only and off the datapoint labels, which matters because each custom key becomes a label on every metric series and high-cardinality values raise storage cost. Custom keys never override standard attributes such as `user.id` or `session.id`, except the `vcs.*` repository attributes. [DOC S744, S745]
- `OTEL_RESOURCE_ATTRIBUTES` is comma-separated `key=value` pairs with no spaces; values may use only US-ASCII characters outside control characters, whitespace, double quotes, commas, semicolons and backslashes, and any other character must be percent-encoded (`org.name=John%27s%20Organization`; any character may be encoded); wrapping a value in quotes does not escape spaces, because `org.name="My Company"` keeps the quotes in the value. Claude Code does not expand the value, so `host.name=$(hostname)` arrives literally, and unlike the exporter variables `OTEL_RESOURCE_ATTRIBUTES` still applies from project and local settings. [DOC S744, S745]
