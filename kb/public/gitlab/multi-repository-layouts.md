# Knowledge kept in several repositories: submodules, subtrees, sparse checkout, partial clone and forks

## Summary
Git gives one way to hold another repository inside a checkout with its own access rules: a submodule, a gitlink to a commit plus a `.gitmodules` url that each reader clones with their own credentials. A subtree copies the other project's files and history into the superproject, so whoever reads the superproject reads them; sparse checkout and partial clone only trim what is checked out or downloaded and grant no access of their own. A superproject clone succeeds when a submodule's repository is unreachable, and only the submodule step fails, which is the property a team without read access needs. Forks carry visibility rules: a GitLab fork may be more restrictive than its upstream, while a GitHub fork of a public repository stays public. A merge or pull request from a fork gives the upstream every commit of the proposed branch it lacks, so a branch of shared work is built from chosen commits with `git cherry-pick`, and a push never carries a gitlink's target but does carry the gitlink and `.gitmodules` text.

## Facts
### Submodules
- A submodule is a repository embedded in another (the superproject) with its own history; the superproject records it as a `gitlink` tree entry holding the commit it expects, plus a `.gitmodules` entry mapping the submodule's name to its path and url. [DOC S-tzjw5vut]
- The gitsubmodules page names access control as one use: restricting user access to submodules can implement read and write policies for different users, and avoiding the fetch of submodules a user does not need reduces the transfer. [DOC S-tzjw5vut]
- Cloning or pulling a superproject does not check its submodules out by default; `git clone --recurse-submodules`, `git submodule update --init` or `submodule.recurse` brings them in. [DOC S-tzjw5vut]
- A submodule is active when `submodule.<name>.active` is true, else when its path matches the `submodule.active` pathspec, else when `submodule.<name>.url` is set, in that order; an `active = false` or an excluded path wins over a url. [DOC S-tzjw5vut]
- `git submodule update` checks out the commit the superproject records, on a detached `HEAD`, by default; `--remote` instead uses the submodule's remote-tracking branch (`submodule.<name>.branch`, else the remote `HEAD`) and fetches it first unless `--no-fetch`. [DOC S-vvarw4uu]
- `submodule.<name>.update = none` leaves a submodule out of `git submodule update`; the value is not allowed on the command line. [DOC S-vvarw4uu]
- A submodule url that starts with `./` or `../` is relative to the superproject's default remote, so a repository next to `bar.git` is `../foo.git`; with no default remote the superproject is its own upstream and the working directory is used. [DOC S-vvarw4uu]
- `git submodule update --filter=<filter-spec>` applies a partial clone filter to the submodules it clones. [DOC S-vvarw4uu]
- The `file` protocol (any local path or `file://` url) has the default policy `user`: usable when `GIT_PROTOCOL_FROM_USER` is unset or 1, and not by commands that clone without user input, such as recursive submodule initialisation. [DOC S-umm7t5f4]

### Pushing a superproject that records a submodule's commit
- `git push --recurse-submodules=check` verifies that every submodule commit changed in the revisions to be pushed is "available on at least one remote of the submodule", and aborts with a non-zero status if any is missing. [DOC S-l6s4hfqp]
- `--recurse-submodules=on-demand` pushes all submodules that changed in the revisions to be pushed, and aborts non-zero if it could not push all necessary revisions; `only` pushes all submodules and leaves the superproject unpushed; `no` or `--no-recurse-submodules` overrides the `push.recurseSubmodules` configuration. With `on-demand` or `only`, a submodule that has its own `push.recurseSubmodules=(on-demand|only)` or `submodule.recurse` recurses further, `only` treated as `on-demand` there. [DOC S-l6s4hfqp]
- `push.recurseSubmodules` takes `check`, `on-demand`, `only` or `no`, with the behaviour of the command-line option; unset it is `no`, unless `submodule.recurse` is set, and then a `true` value means `on-demand`. [DOC S-ph2mlwwa]
- In `transport_push`, the `pre-push` hook runs first, then the `on-demand` and `only` submodule push, then the check, and only then are refs sent; the check is skipped in a bare repository. `check` runs even under `--dry-run`, while the check of `on-demand` and `only` is skipped there. A refusal prints "The following submodule paths contain changes that can not be found on any remote:", the paths, a hint to use `git push --recurse-submodules=on-demand`, and `fatal: Aborting.`. [CODE S-5obxyibm: transport.c#transport_push, die_with_unpushed_submodules]
- The check takes the commits being pushed that are not on the remote-tracking refs of the remote pushed to (`--remotes=<remote name>`), finds the submodules they change, and runs `git rev-list <new commits> --not --remotes -n 1` inside each, over every remote of the submodule whatever its name; a submodule that prints a commit is reported. A submodule is not reported when its repository lacks the commit (not cloned, deinitialised, or commit absent), when the commit is not reachable from any of its refs, or when it has no remote-tracking ref at all; a source comment calls skipping the missing-submodule case safe. [CODE S-mvqt325m: submodule.c#find_unpushed_submodules, submodule_needs_pushing, submodule_has_commits]
- For an unpushed submodule, `on-demand` first runs `submodule--helper push-check` in it, then `git push --recurse-submodules=only-is-on-demand <remote> <refspecs>` with the superproject's remote name and refspecs when the push target is a configured remote (a URL passes neither), printing `Pushing submodule '<path>'`; when that fails git prints `Unable to push submodule '<path>'` and dies with `failed to push all needed submodules`, so the superproject is not pushed. In a submodule, `only` becomes `on-demand` with the warning "recursing into submodule with push.recurseSubmodules=only; using on-demand instead". [CODE S-mvqt325m, S-5obxyibm, S-wt7v2674: submodule.c#push_unpushed_submodules, push_submodule; transport.c#transport_push; builtin/push.c#option_parse_recurse_submodules]
- In a probe on 2026-10-19 (git 2.50.1, macOS, local bare repositories for the superproject and the team repository, `protocol.file.allow=always`), a push with no recursion or with `--no-recurse-submodules` sent a superproject commit whose gitlink named a commit the team repository lacked (exit 0); `--recurse-submodules=check` and `push.recurseSubmodules=check` printed the refusal above and exited 128, also under `--dry-run`, with nothing sent. With `push.recurseSubmodules=on-demand` the output was `Pushing submodule 'kb/team'`, the team branch moved, then the superproject was pushed (exit 0), and `check` then passed. [DER S-l6s4hfqp, S-5obxyibm: one run of a shell script against throwaway repositories]
- In a second probe run on 2026-10-19 (git 2.50.1, same setup) with `check`, a `--dry-run` push exited 0 and would have sent the superproject when the gitlink named a commit absent from the submodule clone, and when the submodule was deinitialised and the gitlink named a commit made elsewhere; a commit pushed by hand to a submodule remote named `up` passed. With `on-demand`, a submodule whose only remote was named `up` gave `fatal: remote 'origin' not configured` and `fatal: process for submodule 'kb/team' failed`, and a submodule on a detached HEAD with no `main` gave `fatal: src refspec 'main' must name a ref` and the same last line; both exited 128 and sent nothing. [DER S-mvqt325m: one run of a shell script; real forges, Windows and other git versions not run]
- So `check` guards the writer's own checkout and a server enforces nothing: it passes whenever the submodule is not cloned (a writer who never cloned the team root gets no protection), and it counts a commit on any remote of the submodule as pushed. `on-demand` carries the submodule's push out only when the submodule has a remote of the same name as the superproject's push remote and a ref the refspec names; otherwise the submodule is pushed in its own repository first and the superproject after it. [DER S-mvqt325m, S-l6s4hfqp: the code paths above and the probes]
- What a push sends of a gitlink: `process_tree_contents` in `list-objects.c` walks a tree's directories and blobs and skips an entry whose mode is a gitlink (the source comment is `ignore gitlink`), so no object lookup is made for the commit it names; `get_object_list` in `pack-objects.c` builds the pack with that traversal (`traverse_commit_list`) unless a bitmap or the path-walk is used, and the receiving side's connectivity check runs `git rev-list --objects --stdin`. The code of `rev-list`'s own call into the traversal, the bitmap path and the path-walk were not traced. [CODE S-7otaqc5c, S-rl2loiqt, S-mhjsbdfr: list-objects.c#process_tree_contents; builtin/pack-objects.c#get_object_list; connected.c#check_connected]
- In a probe on 2026-10-19 (git 2.50.1, macOS, local bare repositories, `protocol.file.allow=always`), a superproject whose gitlink named a commit of a team repository that the receiving bare repository could not read was pushed with exit 0. The receiver's `ls-tree` showed `160000 commit <40 hex>` and its `show main:.gitmodules` the submodule's path and url verbatim; `cat-file -e` of the gitlink's commit exited 1 there, `rev-list --objects --all` listed 7 objects and none of the team's files, and `fsck --full` exited 0, also after `receive.fsckObjects=true` was set and a second push sent (exit 0). A gitlink naming an id (`1111…`) that no repository holds was also pushed with exit 0 and a clean `fsck`. A clone of that receiver exited 0 and showed the gitlink, and `submodule update --init` failed once the team repository was moved away (exit 1 after two clone attempts). [DER S-7otaqc5c, S-mhjsbdfr: one run of a shell script against throwaway repositories; a real forge's hooks, its web view and push rules were not run]
- So a remote that cannot read a submodule's repository receives, for each gitlink, the commit id and the `.gitmodules` text (the submodule's name, path and url), and none of the submodule's objects; it neither checks nor refuses the gitlink, and only the pusher's `--recurse-submodules=check` stands in the way. A public repository that holds the gitlink or `.gitmodules` of a private root therefore shows the root's url host and path and the commit it pins. [DER S-7otaqc5c, S-mhjsbdfr, S-l6s4hfqp: the traversal code and the probe above]

### Submodules in GitLab CI/CD
- GitLab warns that relative submodule urls may resolve incorrectly in forking workflows and recommends absolute urls for a project expected to have forks; a submodule on another server always takes the full url. [DOC S-7ozb4qou]
- Cloning a submodule with `CI_JOB_TOKEN` needs the Reporter, Developer, Maintainer or Owner role on the submodule's project and the job token access configured in that project. [DOC S-7ozb4qou]
- `GIT_SUBMODULE_STRATEGY` is `none` (no submodules), `normal` (top level, as `git submodule sync` and `update --init`) or `recursive`; `GIT_SUBMODULE_PATHS` names or `:(exclude)`s paths, and `GIT_SUBMODULE_UPDATE_FLAGS` passes flags such as `--jobs 4`. [DOC S-hvhro6n5]
- A submodule on another GitLab instance cannot be cloned with the current instance's `CI_JOB_TOKEN`; the job uses a personal, deploy or project access token of that instance with `read_repository`, through url rewriting or a credential helper, and on a shell executor a `git config --global` credential persists between jobs. [DOC S-7ozb4qou]

### Subtrees, sparse checkout and partial clone
- `git subtree` (in git's `contrib/`) includes a subproject in a subdirectory, optionally with its whole history, with no `.gitmodules` or gitlinks; `split` extracts a subdirectory's history as a standalone project and `--squash` imports one commit instead of the history. [DOC S-lu3mudsw]
- A subtree's files are ordinary files of the superproject, so anyone who can read the superproject reads them; a subtree cannot keep a team's content from readers of the repository that holds it. [DER S-lu3mudsw: no gitlink or separate repository]
- `git sparse-checkout` reduces the working tree to a subset of tracked files, chosen by directories in cone mode (the default; non-cone mode is deprecated); its page marks the command experimental. [DOC S-hvg7hx3q]
- Partial clone (`git clone --filter=blob:none`, or `blob:limit=<size>`) skips objects at clone time and fetches them on demand from a promisor remote, so it needs the user online with the promisor reachable; it limits blobs and trees within the commits fetched, unlike shallow or single-branch clones. [DOC S-dhea6atb, S-k2jlpd4u]
- A server serves a filtered clone only when `uploadpack.allowFilter` is set on it: "If this option is set, `upload-pack` will support partial clone and partial fetch object filtering." [DOC S-7gx5uugz]
- In a probe on 2026-10-19 (git 2.50.1, macOS, `file://` clone of a local bare repository), `git clone --filter=blob:none` against a repository without `uploadpack.allowFilter` printed `warning: filtering not recognized by server, ignoring` and exited 0, yet the clone's config held `remote.origin.promisor=true` and `remote.origin.partialclonefilter=blob:none`; with `uploadpack.allowFilter` set there was no warning and `git rev-list --all --objects --missing=print` listed one missing object (the older blob). With the repository then moved away, `git fetch` exited 128 and `git cat-file -p HEAD~1:a` exited 128 with `fatal: could not fetch <oid> from promisor remote`. [DER S-7gx5uugz, S-dhea6atb, S-k2jlpd4u: one run of a shell script against throwaway repositories; the missing-object count of the first clone was not taken]
- GitLab documents partial clone for Git 2.22.0 or later: `--filter=blob:limit=<size>` (the page's example is `1m`) leaves out larger files, which are downloaded on demand when needed (also when changing branches); `--filter=blob:none --sparse` followed by `git sparse-checkout` suits repositories with millions of files; `--filter=sparse:oid=<blob-ish>` is marked experimental, "might be slow and significantly increase" Gitaly resource utilization. [DOC S-zniasdly]
- In GitLab CI/CD a `--filter` reaches `git clone` through `GIT_CLONE_EXTRA_FLAGS` (the page's example is `--filter=blob:limit=1m`); for local development the page prefers partial clones (`--filter=blob:none`, `--filter=tree:0`) to shallow clones, which "greatly increase the time needed to push changes". [DOC S-oewizkwq]
- GitHub Enterprise Server 3.21's administrator documentation lists partial clones among its Git load reductions: "use `--filter` to request only the objects the workflow requires, for example `git clone --filter=blob:none`"; it states no support matrix for github.com. [DOC S-lwtajpn7]
- A GitHub Blog post of 2020-12-21 says that on github.com and GitHub Enterprise Server 2.22 and later two filters work, `--filter=blob:none` (blobless) and `--filter=tree:0` (treeless), and that "the server can choose to deny your filter and revert to a full clone"; the post is old and no current GitHub documentation page of the same statement was found. [COMMUNITY S-vck2yl5v]
- Sparse checkout and partial clone trim what one clone holds, not what a reader may read: every object stays reachable from the one repository, so they are no access control between teams. [DER S-hvg7hx3q, S-dhea6atb: both act on a clone of a single repository]

### A branch built from selected commits: cherry-pick, rebase --onto and git cherry
- `git cherry-pick <commit>...` "apply[ies] the change each one introduces, recording a new commit for each", and needs a working tree with no modification from `HEAD`; the named commits are applied as given, with no traversal (as if `--no-walk`), while a range such as `..master` or `maint master..next` feeds one revision walk. [DOC S-mjtf6vif]
- Cherry-pick adds no trace of the source commit by default: `-x` appends a `(cherry picked from commit ...)` line, only for a pick without conflicts, and the page says not to use it when picking from a private branch, "because the information is useless to the recipient"; `-r` is a no-op. [DOC S-mjtf6vif]
- A merge commit cannot be picked without `-m <parent-number>`, which names the mainline parent; an initially empty commit fails unless `--allow-empty` is given, and `--empty=(drop|keep|stop)` (default `stop`) decides what happens to a commit that became empty because the change is already in the history. [DOC S-mjtf6vif]
- On a pick that does not apply cleanly `HEAD` stays at the last commit made, `CHERRY_PICK_HEAD` names the difficult commit, and `--continue`, `--skip`, `--abort` or `--quit` end the sequence; `-n` / `--no-commit` applies each named commit to the working tree and index without committing, so several can be combined into one new commit. [DOC S-mjtf6vif]
- `git rebase --onto topicA~5 topicA~3 topicA` removes the commits between the two (the page's F and G: "flawed in some way, or should not be part of topicA"), and both the `--onto` and the `<upstream>` argument may be any commit-ish; by default a rebase drops merge commits from the todo list and linearises the rest, and `--rebase-merges` recreates them. [DOC S-7kl4eeso]
- A rebase detects commits that are clean cherry-picks of upstream commits (as `git log --cherry-mark` determines) and drops them as a preliminary step unless `--reapply-cherry-picks` or `--keep-base` is given; the merge backend warns for each commit dropped. [DOC S-7kl4eeso]
- `git cherry [-v] [<upstream> [<head> [<limit>]]]` prints every commit of `<limit>..<head>` prefixed `-` when `<upstream>` holds an equivalent and `+` when it does not; "the equivalence test is based on the diff, after removing whitespace and line numbers", so it finds commits copied by cherry-pick, `git am` or rebase. [DOC S-2f2bbr7f]
- In a probe on 2026-10-19 (git 2.50.1, macOS, a throwaway repository, `main` at an upstream commit `U1` and a branch `work` of `P1` (a file under `private/`), `S1`, `P2`, `S2` and `X` (files under both `shared/` and `private/`)), `git cherry-pick S1 S2 X` on a new branch at `main` exited 0 and made three commits with new ids; the author stayed and the committer became the picking identity, the full message including its body was copied unchanged with no added line, `X` arrived whole with both paths, and neither `P1` nor `S1` was an ancestor of the new branch. With `-x` the message ended `(cherry picked from commit <40 hex>)` with the original's id. [DER S-mjtf6vif: one run of a shell script; merge backends and other git versions not run]
- In the same probe (git 2.50.1) `git cherry -v contrib work` printed `-` for `S1`, `S2` and `X` and `+` for `P1` and `P2`. A second pick of `S1` onto that branch exited 1 with `The previous cherry-pick is now empty, possibly due to conflict resolution.` and a `--skip` hint (`--abort` exited 0), while `--empty=drop` exited 0, printed `dropping <id> S1: shared change A -- patch contents already upstream` and made no commit. A merge commit without `-m` gave `error: commit <id> is a merge but no -m option was given.` and `fatal: cherry-pick failed` (exit 128); a pick that conflicted exited 1 with `CHERRY_PICK_HEAD` present and `--abort` exited 0. [DER S-mjtf6vif, S-2f2bbr7f: one run of a shell script]
- In the same probe (git 2.50.1) `git rebase --onto S1 P2 work` (exit 0) left `P1`, `S1`, `S2'` and `X'` on `work`: it removed `P2` only, `S1` kept its id and the commits after the cut were rewritten; `git rebase --onto main P1 work_copy` (exit 0) replayed `S1`, `P2`, `S2` and `X` onto `main` and removed `P1` only. [DER S-7kl4eeso: one run of a shell script]
- So a branch holding only chosen commits at an upstream tip is built by creating a branch there and cherry-picking the chosen commits in order; `rebase --onto` removes a contiguous run only, and everything after the cut comes along. A pick takes a commit whole: one that changes a shared and a private path, or names a private identifier in its message body, goes upstream whole unless it is left out or picked with `-n` and trimmed, and `-x` would write the private commit's id into the message. `git cherry` against the upstream tip tells which commits are not yet there. [DER S-mjtf6vif, S-7kl4eeso, S-2f2bbr7f: the page statements and the probe above]

### Bringing an upstream main into a clone that has local commits: merge or rebase
- The git-rebase page says rebasing "a branch that others have based work on is a bad idea": anyone downstream "is forced to manually fix their history", and a later merge of the downstream topic into the rebased branch leaves the old commits "duplicated forever". Its section "RECOVERING FROM UPSTREAM REBASE" gives the downstream fix, `git rebase --onto`, and calls avoiding the upstream rebase the real fix. [DOC S-7kl4eeso]
- `git rebase` with no `<upstream>` argument uses the branch's configured upstream and assumes `--fork-point`, which uses the reflog to find the commits the branch introduced; with an `<upstream>` argument the default is `--no-fork-point`. `--fork-point` with `--keep-base` drops commits of a branch whose upstream was rewound. [DOC S-7kl4eeso]
- `pull.ff` defaults to a fast-forward whenever the fetched commit descends from the current one (`false` makes a merge commit, `only` refuses anything else); `pull.rebase` set to `true` makes `git pull` rebase the branch onto the fetched branch instead of merging, `merges` keeps the local merge commits, and the page calls rebasing pull "possibly dangerous". A rebasing pull refuses any local change, which `pull.autoStash` works around. [DOC S-xw4rpv22]
- A probe on 2026-10-23 (git 2.50.1, Apple Git-155, macOS, local bare repositories for an upstream `up` and a team remote, a clone whose fetch remote was `up` and whose pushes went to the team remote): after local commits `L1` and `L2` were pushed to the team remote and `up` fast-forwarded by one commit `U2`, `git merge upstream/main` exited 0 with a merge commit whose parents were `L2` and `U2`, `L1` and `L2` kept their ids, and `git push` to the team remote was a fast-forward (exit 0). A second upstream commit `U3` made a second merge commit on the next merge, and a clone with no local commits took `U2` and `U3` as `Fast-forward`. [DER S-xw4rpv22, S-njfmq56u: one run of a shell script; the merge backend was `ort`; other git versions and conflicting changes not run]
- In the same probe (git 2.50.1) a second clone of the same history ran `git rebase upstream/main`: it exited 0, `L1` and `L2` got new ids on top of `U2`, and pushing the result to the team remote printed `! [rejected] B -> main (non-fast-forward)` (exit 1) because the team remote held the old `L1` and `L2`. [DER S-7kl4eeso, S-l6s4hfqp: the same run; a push of the rewritten commits needs a force, which the push page's non-fast-forward refusal makes explicit]
- Also in the probe (git 2.50.1), the upstream re-created its tip commit with a new id (same tree, new message) and force-updated its `main`: `git merge upstream/main` in the merging clone exited 0 with no conflict and the clone's history then held both the old and the re-created commit, while `git rebase upstream/main` in the other clone replayed `L1` and `L2` over the re-created commit and left no copy of the old one. [DER S-7kl4eeso: the same run; the duplication is the page's "duplicated forever" case, with identical changes on both sides merging cleanly here]
- So a clone whose local commits exist nowhere else can rebase them onto each upstream fetch, while a clone whose local commits are on a shared remote merges (a rebase rewrites commits the remote already holds and needs a force push); a merge is safe against an upstream that only fast-forwards, and an upstream that re-creates commits (a projection rebuilt, a force-update) adds duplicate commits to a merging clone rather than conflicts. [DER S-7kl4eeso, S-xw4rpv22, S-l6s4hfqp: the page statements and the probe above]

### Forks and visibility
- A GitLab fork's visibility must be at least as restrictive as both the upstream project's and the namespace's; a fork does not follow when the upstream later becomes more restrictive. [DOC S-p6qwirq5]
- A GitHub fork's visibility follows its upstream: forks of public repositories are public, forks of private ones private, and a fork's visibility cannot be changed by itself. [DOC S-nhku2azk]
- So a team's private knowledge next to a public upstream is a private fork on GitLab, but on GitHub a separate private repository (not a fork) that pulls from the upstream. [DER S-p6qwirq5, S-nhku2azk]
- A GitLab merge request from a fork is created in the target (upstream) project, not in the fork, and uses the target's approval rules; when the fork is more restricted than the parent, the target branch of a new request defaults to the fork's own default branch, which the page says "prevents potential exposure of private information in your fork". [DOC S-esk5mh7z]
- A GitLab merge request "contains all the history from a repository, plus the additional commits added to the branch associated with the merge request"; its `head` ref `refs/merge-requests/:iid/head` exists for each request, a request can be checked out through it "even if the source project is a fork (even a private fork)", and the ref is deleted 14 days after the request is closed or merged. [DOC S-3o2ashyn]
- GitLab's option "Allow commits from members who can merge to the target branch" gives those upstream members write permission to the request's source branch in the fork; the page offers it for merge requests across forked projects that are publicly accessible. [DOC S-7vhtlusy]
- A GitHub pull request from a fork has a base branch in the upstream and a compare branch in the fork ("compare across forks" in the pull request form); the pull request page shows a three-dot diff, from the merge base of the two branches to the compare branch's tip, and a two-dot comparison must name commits "pushed to the same repository or its forks". [DOC S-acpw7zsh, S-askrbg64]
- GitHub stores a pull request's changes in the base repository: "Commits in a pull request are available in a repository even before the pull request is merged", the pull request is fetched as `pull/ID/head`, the `refs/pull/` namespace is read-only (`deny updating a hidden ref`), and a request whose fork was deleted can still be merged through a new one. [DOC S-7pysmrqf]
- On GitHub the repositories of a network share Git data: "Commits pushed to any repository in a network can be accessible from other repositories in that network, including the upstream repository", the page adds that this holds even after a fork is deleted, and that owners of an upstream repository can read all forks in the network. [DOC S-nhku2azk]
- In a probe on 2026-10-19 (git 2.50.1, macOS, local bare repository as the upstream), pushing a branch whose history held a private commit `P1` and a shared commit `S1` sent both: the upstream's `log work ^main` listed them and its `ls-tree -r work` showed the private file. A branch made by cherry-picking `S1` onto `main` sent one commit and no private path. After the pushed branch was deleted on the upstream, `git cat-file -t <P1>` there still answered `commit` (no `gc` ran). [DER S-nhku2azk, S-3o2ashyn: one run of a shell script against throwaway repositories; a forge's own retention of objects was not run]
- So the upstream of a fork sees every commit reachable from the proposed branch's tip that it does not hold, each with its author, message and tree, and keeps them reachable by id: on GitLab through the request's `head` ref for as long as the request lives and 14 days after, on GitHub through a pull request's stored changes and the network's shared Git data, deleted fork or not. A private ancestor of a contribution branch is thus disclosed to the upstream by the request itself, so the branch a request is opened from must hold only commits already cleared for the upstream. [DER S-3o2ashyn, S-7pysmrqf, S-nhku2azk: the three page statements and the probe above]
- Not found: whether commits pushed to other branches of a GitLab fork can be read by id through its upstream project, and whether GitHub lets a repository outside the upstream's network (a separate private repository) open a pull request into it. The pages read name only the fork's compare branch and, for GitHub, "compare across forks". [UNK: S-esk5mh7z, S-acpw7zsh, S-nhku2azk read in full on 2026-10-19; logged in `_gaps.md`]

### How it fits
- A shared public root plus private team roots maps to one repository per root: the public repository pins each team root as a submodule or names it in a pointer file; a reader without access to a team's repository still clones the public root, and only that root is missing. [DER S-tzjw5vut, S-vvarw4uu: per-submodule access and a clone that does not recurse by default; the probes above saw it for a missing local path, a stand-in HTTP 401 and 403 and a stand-in ssh refusal, on macOS only]
- A pointer that names a branch (`submodule.<name>.branch` with `update --remote`) follows the team's latest work, and a recorded gitlink pins a commit that only a superproject commit moves; offline use needs the submodule already cloned, since a partial clone fetches missing objects on demand. [DER S-vvarw4uu, S-dhea6atb]
- A fetch root cloned with `--filter=blob:none` saves transfer on GitLab and GitHub but is not a self-contained copy: its older blobs come from the promisor remote on demand, so offline use reads only the blobs already fetched, and a server without `uploadpack.allowFilter` ignores the filter with a warning and exit 0, which a caller sees only on stderr or in `remote.origin.partialclonefilter`. [DER S-7gx5uugz, S-dhea6atb, S-zniasdly: the filter rules and the probe above; GitHub's support rests on a 2020 blog post and a GHES page]
- Giving shared work back from a clone that also holds private roots is a branch rebuilt at the upstream tip from the chosen commits, pushed to a fork or to the upstream and proposed as a merge or pull request; the pages and code read describe no check in git, GitLab or GitHub that refuses a private ancestor, a private name in a message or a gitlink to a private root, so the refusal belongs to the tool that builds the branch: it picks (`git cherry-pick`, no `-x`), leaves out each commit that touches a private path or names a private identifier, and may say why for each commit it left out (`git cherry` marks the ones already upstream). [DER S-mjtf6vif, S-2f2bbr7f, S-3o2ashyn, S-7pysmrqf, S-7otaqc5c: the pick, request and gitlink facts above]
- On Windows a submodule keeps its git directory under the superproject's `.git/modules/<name>/`, so deep paths also meet Git for Windows' path-length limit described in `gitlab/git-test-repositories.md` (`core.longpaths`). [DER S-tzjw5vut]
