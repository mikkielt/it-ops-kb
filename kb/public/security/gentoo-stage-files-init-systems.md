# Gentoo stage files and the init system choice

## Summary
A Gentoo install starts from a stage 3 tarball: an almost complete system built by Release Engineering with Catalyst for one architecture and profile, without a kernel or a bootloader. The choice of stage fixes the init system (OpenRC or systemd), desktop or server flavour, multilib or not and libc, and those are coupled to the profile chosen later; switching init systems afterwards is possible but non-trivial. There are no numbered releases in the wiki pages read: stage files are dated autobuilds on the mirrors, verified with `gpg` and checksums and unpacked with `tar` preserving extended attributes. OpenRC is Gentoo's native init system and systemd is fully supported.

## Facts
- A stage file (stage tarball) is an archive of the files for a minimal Gentoo environment, normally the seed of an installation; only stage 3 is used for installation, stages 1 and 2 are for development and are not downloadable. [DOC S-qfnocjvf]
- Stage files are generated by the Release Engineering team with Catalyst from spec files, for a given architecture and for selected profiles. [DOC S-qfnocjvf]
- Unpacking a stage 3 installs an almost-complete, mostly functional system; the main missing parts are a kernel and a bootloader. [DOC S-qfnocjvf]
- A stage 3 is built from a stage 2 and contains the `@system` set of packages; the base list of the set is `profiles/base/packages` in the Gentoo repository. [DOC S-qfnocjvf]
- A stage 4 is a loosely defined term for a stage 3 with extra parts; official ones were available only in January 2016 for amd64, and Catalyst lets users build their own. [DOC S-qfnocjvf]
- Stage 3 files are on the downloads page and on `distfiles.gentoo.org/releases/<arch>/autobuilds/`, distributed through the mirror system. [DOC S-qfnocjvf]
- The basic stages are named `stage3-<architecture>-openrc` and `stage3-<architecture>-systemd` and are for command-line systems such as servers and containers. [DOC S-qfnocjvf]
- Most stages are now explicitly suffixed with the init system type (`openrc` or `systemd`), although some architectures may still be missing it. [DOC S-rq7fzez5]
- Desktop stages have `desktop` in the name and add packages such as LLVM and `rust-bin` and tuned USE flags, which can save many hours over converting another stage to a desktop. [DOC S-qfnocjvf]
- Multilib stages use 64-bit libraries where possible and fall back to 32-bit ones; a no-multilib stage excludes 32-bit libraries, which stops some software such as most Steam games, and moving back to multilib usually means reinstalling. [DOC S-qfnocjvf]
- Musl and LLVM stages are experimental and for advanced installs, and moving back to glibc or GCC is not possible without reinstalling. [DOC S-qfnocjvf]
- The stage choice is tightly coupled with the profile selected later; switching init systems, no-multilib to multilib, or ABI is difficult or impossible without reinstalling, and the wiki advises conservative choices. [DOC S-qfnocjvf]
- Verification files sit next to the stage on the mirror: `.CONTENTS.gz` (list of files), `.DIGESTS` (several hashes) and `.sha256` (a PGP-signed SHA256, not present for every stage), and the `tar.xz` has a detached signature checked with `gpg`. [DOC S-rq7fzez5]
- Official release signing keys come from `sec-keys/openpgp-keys-gentoo-release` (`/usr/share/openpgp-keys/gentoo-release.asc`), imported with `gpg --import`, and the fingerprints are on the release media signatures page; success prints "Good signature from". [DOC S-rq7fzez5]
- The checksum can be compared with `openssl dgst -r -sha512` or `-blake2b512` and `sha256sum --check` against the verified files, and a mismatch means the download should be discarded. [DOC S-rq7fzez5]
- The stage is unpacked with `tar xpvf <stage>.tar.xz --xattrs-include='*.*' --numeric-owner -C /mnt/gentoo`, keeping permissions, extended attributes and numeric owners as Release Engineering intended. [DOC S-rq7fzez5]
- After unpacking, the Handbook edits `/mnt/gentoo/etc/portage/make.conf` (`CFLAGS`, `MAKEOPTS` and other variables), which Portage reads on every run. [DOC S-rq7fzez5]
- The next steps are syncing the repository with `emerge-webrsync`, selecting a profile with `eselect profile` and optionally adding a binary package host. [DOC S-5rih6fam]
- Recent stage 3 files come with the Gentoo binhost preconfigured. [DOC S-rzs2uo4g]
- Gentoo officially supports both OpenRC and systemd, and other init systems are available. [DOC S-kdxg3wyq]
- OpenRC is a dependency-based init system that maintains compatibility with the system-provided init, is Gentoo's native and original init system and is also used by a few other distributions and BSDs. [DOC S-rq7fzez5]
- On Gentoo OpenRC is by default invoked by sysvinit, and it also has an optional `openrc-init` and an optional process supervisor `supervise-daemon`. [DOC S-kdxg3wyq]
- OpenRC's global configuration is `/etc/rc.conf`, per-service settings are in `/etc/conf.d`, runlevels are directories in `/etc/runlevels` managed with `rc-update` and `rc-status`, and it writes no log unless `rc_logger` is enabled in `rc.conf`. [DOC S-kdxg3wyq]
- With an OpenRC profile `sys-apps/openrc` comes in through `virtual/service-manager` and should not be in the world file; network connections are managed by netifrc scripts by default. [DOC S-kdxg3wyq]
- The kernel command-line parameter `softlevel=<runlevel>` boots a runlevel other than `default`. [DOC S-kdxg3wyq]
- The OpenRC wiki page carries a notice that its user-services section may need updating to current best practice. [DOC S-kdxg3wyq]
- systemd is described as a modern SysV-style init and rc replacement and is supported as an alternative init system; the wiki says an init system is normally chosen at install time by downloading a systemd or OpenRC stage 3. [DOC S-6er43wub]
- The Handbook calls systemd fully supported in Gentoo and a modern SysV-style init and rc replacement. [DOC S-rq7fzez5]
- To use systemd the Handbook says to select a profile with `systemd` in its name. [DOC S-5rih6fam]
- Moving an OpenRC system to systemd means a systemd profile (or the `systemd` USE flag globally with `elogind` disabled), then `emerge -avDN @world`, and switching the `init=` the kernel or initramfs starts (not needed when `sys-apps/systemd` has `sysv-utils`, default from 239). [DOC S-6er43wub]
- After the switch services of the old manager are not started automatically; the page runs `systemd-machine-id-setup`, `systemd-firstboot --prompt` and `systemctl preset-all`, and warns that skipping `systemd-firstboot` interrupts the next boot for SSH-only access. [DOC S-6er43wub]
- OpenRC init.d scripts are not run by systemd on Gentoo, and the page notes it is possible to boot back into OpenRC by undoing the init change if the migration fails. [DOC S-6er43wub]
- The systemd wiki page carries a stale notice that it references deprecated packages (`sys-fs/udev`, `microcode-ctl`). [DOC S-6er43wub]
- Gentoo's support page names the FAQ, the documentation, IRC channels, forums and mailing lists as support venues for a volunteer-driven distribution, and Bugzilla for bug reports. [DOC S-ak5nrgfs]
- For automation the init system is decided by the stage and profile before the first boot, so a provisioning step should pick `stage3-<arch>-openrc` or `-systemd` once and keep the matching profile, since an in-place switch is a manual migration. [DER S-qfnocjvf, S-6egnea5f, S-6er43wub: coupling of stage, profile and init system and the multi-step migration]

## Examples
- SNIPPET: unpack a verified stage file into a new root; context: Gentoo live environment, target mounted at `/mnt/gentoo`, stage name placeholders as in the Handbook; checked: no [DER S-rq7fzez5: command and options from the Handbook page]
```
gpg --verify stage3-amd64-<release>-<init>.tar.xz.asc stage3-amd64-<release>-<init>.tar.xz
tar xpvf stage3-amd64-<release>-<init>.tar.xz --xattrs-include='*.*' --numeric-owner -C /mnt/gentoo
```
