# Token usage: exact counts from session transcripts

What a kb lookup costs in tokens, read from what Claude Code already recorded and never estimated: `_tools/kbusage.py` reads a session transcript, and the query log keeps the counts of every lookup in a usage sidecar beside its run file, and the counts of the prompts spent on a backlog item in a work sidecar (`kb/_self/querylog.md`, Surfaces and Store). Standard library only, with no model and no network, so the same transcript always gives the same record.

## How tokens are measured

- **The counts are the API's own.** For every API request Claude Code writes the response's `usage` into the session transcript (`~/.claude/projects/<project>/<session>.jsonl`): `input_tokens` (uncached), `cache_creation_input_tokens` (with its one-hour part in `cache_creation.ephemeral_1h_input_tokens`), `cache_read_input_tokens` and `output_tokens`. These are the numbers billing uses (`claude/agent-sdk.md`, `agents/agent-caching.md`); the reader copies them and adds them up.
- **One count per request.** A request's response is written as one record per content block, all with the same `requestId` and `usage`; the reader counts each `requestId` once, with the most output any of its records reports. Records with the model `<synthetic>` (no API call) are left out.
- **A prompt's requests.** Every user record carries the `promptId` of the prompt it belongs to (the prompt itself and each tool result); an assistant record belongs to the prompt of the user record before it. The reader reads the main transcript from its end, in blocks, back to the last user record of another prompt, so reading one prompt of a long session reads only its end.
- **Subagents.** A subagent writes its own transcript, `<session>/subagents/agent-<id>.jsonl`, whose first record carries the `promptId` of the prompt that started it, and `agent-<id>.meta.json` names its `agentType`. Its requests count under `sub`, by agent group; the main transcript's own sidechain records are left out, so nothing counts twice. A background subagent still running when the session ends is counted as far as it got.
- **A subagent on a work branch is routed to its item.** A worker the sprint starts in a worktree has its `work/<id>` branch checked out (`kb/_self/backlog.md`, Git), and every record of its transcript names the branch it was on in `gitBranch`: first the branch its worktree was made on, then `work/<id>`. When a subagent transcript names exactly one branch of that shape (`work/` and a backlog id, nothing more; none, two different ones or any other name do not), the reader counts its requests under `routed`, by that item id and agent group in `sub`'s shape, and leaves them out of `sub`, so the prompt that started it does not count them again (`kbusage.work_item`). The branch is read in memory: the record keeps the item id alone, never the branch string or any other branch. A worker whose worktree was made by hand keeps its session's working directory, so no record of it names a work branch: then the one item whose `.claude/worktrees/<id>` directory its shell commands name is the item (`kbusage.work_item`; two items' directories or none leave it under `sub`), and only the id is kept. A usage row written before this routing keeps such a subagent under `sub`.
  - **The routing is by path, and its limits are silent.** A worker's tokens go to its item only when a record names the `work/<id>` branch in `gitBranch` or, when none does, the commands of its transcript name one `.claude/worktrees/<id>` directory. A worker whose worktree is outside .claude/worktrees, one whose commands name two different items' directories or none (also one that runs a first command with no path in it), and one killed before its first command stay in `sub` and read zero for the item, with no warning: the item's cost then reads low, and the prompt that started the worker still holds the tokens. The `kb-worker` brief therefore makes the worker's first command name its worktree path (`.claude/agents/kb-worker.md`, rule 2).
- **Per tool call.** The API reports no tokens per tool call. A step is one request whose `tool_use` blocks the next user record answered: the reader keeps each result's tool group, whether it succeeded (`is_error`) and its length in characters, and `grow`, how much the next request's whole input (uncached + cache write + cache read) exceeds this request's. `grow` is the context the step added: the tool results, plus the request's own reply and the framing Claude Code adds; it is exact as a difference, not a count of the results alone, and it is left out when the context shrank (a compaction) or no request followed.
- **`start`** is the whole input of the prompt's first request: the context the prompt began with (system prompt, tools, instructions, earlier turns).
- **Checked against the session's own totals.** A transcript's `cost-state` record holds the session's totals per model (`modelUsage`); on a Claude Code 2.1.283 session the sum of every prompt's `main` and `sub` counts equalled them for input, cache write, cache read and output.
- **The format is observed, not documented.** Claude Code documents no transcript schema (the kb has no fact on it); the reader relies on the fields above, skips a line that is not JSON, and gives no record when it finds no request of the prompt. `READER_VERSION` changes when what the reader returns changes.

## What a record holds, and what never leaves the transcript

| kept | never kept |
|---|---|
| model ids (`claude-...`, anything else as `other`) | prompts, replies, thinking, system text |
| per model: `requests`, `in`, `cw`, `cw1h`, `cr`, `out` | tool inputs (commands, urls, questions) and tool results |
| agent groups: `general-purpose`, `Explore`, `Plan`, `kb-lookup`, `kb-reviewer`, `kb-worker`, else `other` | agent names and descriptions, other agent types |
| tool groups: a kb tool's name (`kb_pack`, ...), `docs:<server>` for the three documentation servers, a built-in tool's name, `mcp:other` for any other MCP tool, else `other` | other MCP servers' and tools' names |
| per step: tool group, `ok`, `chars`, `grow` | file paths, the transcript path, `requestId`, uuids, session, user and organisation ids, `cwd`, git branch |
| `routed`: the item id of a subagent's `work/<id>` branch or of the one `.claude/worktrees/<id>` its commands name, with its counts | the branch string, any other branch, the worktree path, the commands |

- **The transcript is read where it is, never copied.** A hook gets `transcript_path` in its input; the query log reads each kb prompt's records in memory and writes one `usage` spool row of the record. The path is written to no file: the `SessionEnd` launcher passes it to the distill it starts as a command-line argument.
- **At most `STEPS_MAX` steps** per record; `cut` counts the steps left out.

## `kbusage.py`

- `python3 _tools/kbusage.py TRANSCRIPT [--prompt PROMPT_ID]` prints one JSON line per prompt of a transcript (or the one named), numbered in order instead of by its id: the record the sidecar keeps, or `"usage": null`.
- `python3 _tools/kbusage.py tree PATH [--format json] [--top N]` reads a transcript with its `subagents/*.jsonl`, or a project directory of transcripts, and prints the calls and characters of tool results by tool, Bash command head, file path and agent group; a call repeated across resumed transcripts counts once. Its check exits 1 when a group's rows do not add up to the totals or the characters exceed `TOKEN_SPAN_MAX` (16) per token of fresh input, and 2 for a missing path or no transcripts. The distill does not use it.
- `tree` also prints `by tick`, and `rot` in the JSON (Context rot, below).
- `python3 _tools/kbusage.py errors [--days N] [--path P] [--script S] [--exit CODE] [--top N]` is the usage-error report: the ops row `call.tool` keeps a shell call's class and outcome, never its message, so the message is read here, on the host that made the calls, from the transcripts of this clone's project directory and its worktrees' (`<Claude config dir>/projects/`, the directory named after the working directory, every character but a letter or digit as `-`; subagent transcripts included) of the last N days (default 7). Each failed `Bash` or `PowerShell` call whose class is `tools.<stem>` and whose result starts `Exit code N` (the only exit status a result carries, `public/claude/hooks.md`) gives its message: the first line after the exit code, or argparse's `prog: error:` line past its `usage:` block. Titles, absolute paths, emails, uuids, backlog and source ids, commits, host names, numbers and this host's user and host name become placeholders (`kbusage.NORMALISE`), so a message agents repeat with other ids is one row: count, exit codes, script, message and the subcommands it came from, most frequent first; `--exit 2` keeps the bad-argument and refusal exits, `--script backlog` one script. A call that never ran (a permission or hook refusal) is counted apart. The transcript format is internal (`public/_gaps.md`): a line or block it cannot read is passed over. It prints no command line, writes nothing to the spool or the store, and refuses a `--path` outside the config directory's `projects/` (exit 2).
- `kbusage.prompt_usage(transcript_path, prompt_id)` is what the query log's distill calls: the record, or None.

## A census before and after a change

`tree` answers where a session's tool results went, so a change meant to cut them (a command that replaces a hand-written script, a tool that returns less, a rule that stops a re-read) is judged by running the same kind of work before it and after it and comparing the two rollups. It reads transcripts only, writes nothing, and uses no model and no network, so the same transcripts always give the same rollup.

- **Two runs of the same work.** Run the task the change touches in a session before the change, and the same task in a session after it, each a transcript under `~/.claude/projects/<project>/` with its `<session>/subagents/` beside it (the `tree` of a session whose subagents are missing reads the main chain only, so keep the directory). The comparison is only as good as the likeness of the two tasks; one pair of sessions is a sample, not a measurement, so repeat the pair when the difference is small.
- **One command per run.** `python3 _tools/kbusage.py tree <transcript>.jsonl --top 0 > <before>.txt` for the text with every row, or `--format json` for rows a program reads (`rows` of `group`, `key`, `calls`, `chars`, `errors`, with `totals`, `usage` and `check`; keys sorted, so the same transcripts give the same bytes). A project directory as `PATH` rolls up every transcript directly in it, which fits when the directory holds only the runs being compared; a call that appears in two resumed transcripts counts once. Keep the output in a scratch directory, never in the repository: a row key is a command head or a file path from a tool input, which the usage record never keeps (What a record holds).
- **Read the totals first.** The header line gives the transcripts and subagent transcripts read, the tool results and their characters, the errors, `without a tool use` (a result whose call is in a transcript not read) and `tool uses without a result` (a call still running when the session ended). The characters are the length of the results, not billed tokens: `~N tokens` divides them by 4, an estimate, and the `usage` line has the billed counts per side (main chain and subagents). `results against usage` sets the estimate against the fresh input (uncached input plus cache write), the part of a session's input that is new each time; a result that stays in the context is read from the cache on later requests, so characters do not add up to cost.
- **The five groups, each splitting the same results.** `by tool` has a row per tool (a kb tool by its name, `docs:<server>`, a built-in tool, an MCP tool of no group by its own name) and `by agent` one per agent group (`main`, `general-purpose`, `Explore`, `kb-lookup`, `kb-worker`, ..., `other`): each holds every result once. `by bash` splits what Bash and PowerShell returned by command head: the first command of the line with `cd`, `export`, assignments and `sudo` left out, so a compound command counts under its first real command; Python is its script (the last two path parts), `-m module` or `-c`, with a bare subcommand word after a script; `git`, `gh`, `glab`, `docker`, `kubectl`, `npm`, `pip`, `uv`, `cargo`, `go` and `claude` by subcommand. `by class` splits the same shell results by the closed class the ops row `call.tool` records (`kbusage.command_class`: `tools.<stem>`, `python-c`, `python-m`, `python-script`, `<tool>.<subcommand>` when `kbusage.CLASS_SUBCOMMANDS` lists the subcommand and else the tool alone, a known command's name, `other`), so the census and the transcript agree on one session. `by file` splits what Read, Write, Edit, MultiEdit and NotebookEdit returned by path, relative to the session's working directory and with a worktree's directory folded into the project's, so a file read from a worktree and from the checkout is one row (`(no path)` for a call without one). Rows are sorted by characters, largest first, and `--top N` cuts each group (default 15; `... N more rows` names what it left out).
- **Compare row by row, by group and key.** A hand-written script shows as characters under `python3 -c` or a bare `python3` (a script read from standard input); a command that replaced it shows as a row under its own head (`python3 _tools/<tool>.py <subcommand>`); the change worked where the first rows shrink or go and the second hold less than they did. A row in one run and not the other is a change of behaviour, so read `by tool` and `by agent` for where the work moved (to a subagent, say, which keeps its results out of the main context). Errors per row are failed calls: a change that cuts characters and adds errors has moved its cost, not removed it. `by file` names what was read again and again; a file that appears with many calls in the before run and few after is the saving of a rule that points to a section instead of the whole file.
- **The totals check is the proof the rollup is sound.** Each group's rows must sum to what it splits: calls, characters and errors of `by tool` and `by agent` equal the totals, `by bash` and `by class` each equal the Bash and PowerShell rows of `by tool`, `by file` equals the file tools' rows, and the result characters must not exceed `TOKEN_SPAN_MAX` (16) per token of fresh input, a bound no transcript can break. `check: ok` ends the text; `check: FAILED` lists each problem and exits 1. Treat a failed check as a reader defect (a bug to file), never as a finding about the session, and compare no rollup that failed it. Exit 2 means the path is missing or holds no `*.jsonl`.
- **What it does not show.** Tokens per tool call (the API reports none; the per-step `grow` of the prompt record is the exact context a step added), the model's own text, or whether a smaller result was enough for the work. A change that cuts characters is a saving only when the task still finished: compare the outcome of the two sessions as well.

## Context rot: compactions, tokens and repeated reads per tick

`tree` answers whether a session's context fills and its work repeats, from the transcripts Claude Code already writes; nothing is recorded for it, and a tick with no compaction prints `0`.

- **Where a compaction is recorded.** A Claude Code transcript holds a `system` record with `subtype` `compact_boundary` and `compactMetadata.preTokens` (the context size when it compacted; observed, not documented, like the rest of the transcript format).
- **A tick** is one prompt of a main transcript (a `/loop` firing is one prompt): the records from its first user record to the next prompt's, numbered from 1 per transcript (`t<transcript>.<tick>`). `kbusage` reads transcripts by path and imports no backlog module.
- **Columns.** `compactions` (the boundary records of the tick), `pre_tokens` (each one's `preTokens`, `0` when none), `tokens` (uncached input + cache write + cache read + output of every request, once by request id, with the most output any record of it reports), `reads` (Read tool uses, once by tool use id) and `repeated` (reads beyond the first of a file, summed over files). In JSON, `rot.ticks` holds these as `compactions`, `pre_tokens`, `tokens`, `requests`, `reads`, `repeated_reads` and `repeated_files`.
- **Tokens by tick.** A tick's tokens are its main chain's requests plus those of the subagent transcripts whose first record names its prompt (the main transcript's own sidechain records are left out, as for a prompt's usage).
- **Repeated reads.** The same file read more than once by the main chain inside one tick: paths compare as `by file` keys them (a worktree's directory folded into the project's, relative to the session's working directory).

## OpenTelemetry events

`python3 _tools/kbotel.py serve` takes Claude Code's OpenTelemetry events locally, so a session's per-request cost, duration and token counts and its tool results' durations are kept beside the transcript without a collector (`kb/public/claude/otel-monitoring.md`: the exporter has only `otlp`, `console` or `none`, so a local file needs a receiver).
- **Run a session against it:** `CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_LOGS_EXPORTER=otlp`, `OTEL_EXPORTER_OTLP_LOGS_PROTOCOL=http/json`, `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT=http://127.0.0.1:4318/v1/logs`, and `OTEL_LOG_TOOL_DETAILS` and `OTEL_LOG_USER_PROMPTS` unset, with `kbotel.py serve` running (`--port`, `--idle` seconds without a request before it exits, default 600; `--parent PID` to exit with the session on POSIX).
- **What it keeps:** it listens on `127.0.0.1` only, answers `POST /v1/logs` with `200` and an empty JSON object, and appends one line per `tool_result` or `api_request` event to the query log's data directory (`otel/events.jsonl`: in a clone's own `_cache/querylog`, which git ignores, or in the plugin's data directory, `ql_base.places`): the event, its time in milliseconds and the attributes of `kbotel.EVENT_KEYS` in their closed shapes (ids and model names without spaces or slashes, non-negative numbers, flags). A prompt, a tool's input or output, an error message, a body and every other event (`user_prompt` among them) are dropped.
- **Join:** `python3 _tools/kbotel.py join TRANSCRIPT [--events FILE]` prints, per prompt id of a main transcript, the cost of the `api_request` events whose `request_id` the transcript holds and the count of `tool_result` events whose `tool_use_id` it holds; an event of another session counts nowhere.

## In the query log

- **After the prompt, not at its `Stop`.** When the `Stop` hook runs, the transcript does not hold the answer's own request yet: on Claude Code 2.1.283 a record read at `Stop` missed each prompt's last request, while the same transcript read after the session equalled the run's reported usage exactly. So a prompt's usage is read at the next event of its session that comes after it (`ql_capture.add_usage`: one `usage` row for each prompt of the session's spool file that used the kb, a `kb_hook` or `mcp` row or a prompt with a `kb_intent`, or lies inside a work window (below), and has none of this reader yet):
  - **the next prompt:** the async `UserPromptSubmit` capture writes the rows of the session's earlier kb prompts, never of the prompt it records;
  - **the session's end:** `SessionEnd` marks the session closed and starts `querylog.py distill --session <id> --transcript <path>`, which waits for the distill lock (`USAGE_LOCK_WAIT_S`), writes the rows of the prompts still without one (the last prompt), then distills (`kb/_self/querylog.md`, Surfaces and Distill);
  - **a later launch, when `SessionEnd` never ran:** every `querylog.py launch` (on `SessionStart` and on `SessionEnd`) starts the same `distill --session <id> --transcript <path>` for each session of the spool that has no `.end` marker and whose transcript has exited, that is, ends in Claude Code's `cost-state` record, which it writes once, last, when a session exits (`kbusage.transcript_ended`; the transcript is found by the session id under `projects/` of the Claude config directory, `kbusage.find_transcript`, which takes the most recently modified of the files of that name when several project directories hold one (`/cd` and a worktree entry or exit move a transcript and can leave a stale copy), and its path is never written; the ending session's own `SessionEnd` does not search, it reads the `transcript_path` of its hook input). That distill writes the rows and then marks the session closed (`ql_distill.close_ended`), so a session's rows are written before any distill pass consumes it. A launch closes at most `MISSED_ENDS_MAX` such sessions.
- **A work window** is the prompts of a session between a `work` row that opens an item's window, a `claim` or the `branch` row of the session's own `work/<id>` branch (`ql_capture.branch_row`, below), and the `done` or `release` row of the same item (a successful `land` or `merge` of it that the session ran is stored as a `done`; one launched in the background writes a `done-pending` row at its launch instead, and its window closes by the `done` row a later hook of the session writes once the item file reads `done`; `kb/_self/querylog.md`, Surfaces), the prompt of each of the two rows included. Every prompt in one gets a `usage` row, kb prompts or not, so what a session spent on the item is counted whatever it asked. Windows of several items may overlap; a prompt is inside while any is open. A window with no `done` or `release` yet runs to the end of the spool file, so at `SessionEnd` the last prompts of an unfinished item get rows. A `done` or `release` with no `claim` or `branch` row of the item earlier in the same session's file opens and ends nothing: the window's start is in another session. A prompt outside every window keeps the kb rule above. The rows carry no item id for the window: the `work` rows beside them name the item (`ql_capture.usage_targets`, `add_usage`); only a routed subagent (above) carries its item's id, in `routed`.
- **`SessionEnd` does not always run in `claude -p`.** On Claude Code 2.1.283 some headless runs ran their `SessionEnd` hooks and others, with the same flags and tools, ran none, not even a plain command hook that appends its input to a file. On 2.1.291 the headless workers a sprint started in the background, each with its prompt on stdin from a file and the project's hooks loaded, ended with a spool file and no `.end` marker, so no `SessionEnd` launch reached them, while ended interactive sessions did and so did short foreground `claude -p` runs with the prompt as an argument, whose `SessionEnd` hook wrote the marker and the usage row through the same command, `kbpy` and launcher: nothing in the launcher, the distill or `kbusage.prompt_usage` stops that path, and why Claude Code did not run it is not known. A session that ends without it is closed by the next launch, which finds in its transcript that it exited (the `cost-state` record, above), and its last prompt gets its usage row then; a session whose transcript never ends in that record (a crash or a kill) closes by idle time (`SESSION_IDLE_CLOSED_S`), and its last prompt gets a usage row only if a later prompt of the session (`claude -p --resume`) comes first.
- **A delegated headless session reaches `backlog.py cost` only with the project's hooks loaded.** The capture hooks (`querylog.py capture`) and the `SessionEnd` launcher are configured in the project's `.claude/settings.json`. A `claude -p` started with `--setting-sources local` loads no project settings, so none of them runs: the session leaves no spool row, no `work` row and no `usage` row, and `backlog.py cost` prints 0 runs and 0 prompts for what it worked. Start it with `--setting-sources project,local` instead (the flag the kb's own headless runs pass, `kb_ask.py` and `ql_research.py`, which also pass `kbcommon.NO_HOOKS`, `--settings '{"disableAllHooks": true}'`: they run with no hook, so the capture hooks never log them and they are no sessions whose work is measured; `kb_ask.py` writes its own query log row); a session whose hooks do not load is not measured, and nothing warns of it.
  - **The spool place is not the cause.** A session working in a linked worktree spools in the main worktree's `_cache/querylog`, where distill and `backlog.py cost` read (`kb/_self/querylog.md`, Surfaces).
  - **What loading the project settings costs.** The same file's `SessionStart` hooks run too, among them `backlog.py intake --file --hook`, which files each new finding as an uncommitted draft item under `kb/_self/backlog/` of the worker's worktree and never commits it (`kb/_self/backlog.md`, Bug intake). Such an untracked file is no part of the worker's commits, and the landing needs a worktree with only the worker's own changes, so the orchestrator moves the drafts out of the worker's worktree before it lands the branch. `--setting-sources local` was the way to keep them out.
  - **A window opens from a `claim` the session ran, or from its `work/<id>` branch.** A prompt gets a work window, and so a line of the work sidecar, only from an opening row in its own session's spool file (above, and Work sidecar below): a `claim` row, or the `branch` row the capture hook writes on a prompt whose session directory is on a `work/<id>` branch (`ql_capture.branch_row`, from the repository's HEAD file; only the item id and the action are written, no process is started). A worker session started in the worktree of the branch of an item the orchestrator claimed in its own checkout therefore opens that item's window at its first prompt and runs no `backlog.py claim` of its own; the window runs to a `done` or `release` row of the item, or to the end of the file. The `branch` row is written only when all three hold: the prompt is the session's first (no earlier `prompt` row of the session in its spool file), the item file `kb/_self/backlog/<id>.json` at the root of the checkout the session directory is in exists with `"status": "doing"`, and the session's rows hold no `claim`, `done` or `release` of the item. A checkout left on a stale `work/<id>` branch with no item file, an orchestrator whose directory followed a `cd` into a worker's worktree on a later prompt, and a session back in a worktree after the item was done therefore open no window that only a `done` or `release` row of that session could close (such a session runs no `land` of the item, and the `done` that `land` runs is a process of its own that no hook sees), and a window that `done`, `land`, `merge` or `release` closed stays closed on the session's later prompts. An orchestrator's own claims open windows in the orchestrator's session, not in the worker's, and a session on no `work/<id>` branch (the main checkout, a hand-made worktree on another branch) that runs no `claim` has no window: its prompts get a `usage` row only when they used the kb, and it reads zero for the item even with the hooks loaded. An orchestrator's own window runs to the `land` or `merge` of the item that session ran, which closes it as a `done` does (a `land` of another item closes none of its windows); a `land` or `merge` it starts in the background closes it only by the `done` row the capture hook writes at the session's first later prompt, tool call or `Stop` that finds the item file `done` (`ql_capture.settle_pending`), so a background landing that stops or is refused leaves the window open, so its prompts after a landing count on no line of that item, and a session that never claimed or branched the item gets a `done` row from a `land` that opens and closes nothing. At distill a `claim` or `branch` row opens a window only for an item that has a file in the clone's `kb/_self/backlog` (`ql_distill.item_finder`), unless a later `done` or `release` row of the session closes it (`ql_distill.kept_rows`, `kb/_self/querylog.md`, Distill): a stale `work/<id>` checkout's `branch` row, written before the capture read the item file, opens none, and neither does a `branch` row written at or after the commit that set its item `done` or `dropped` (`ql_distill.stale_branch`): a helper session in a worker worktree whose branch predates the landing reads its own copy of the item file, still `doing`, yet counts on no line of the item, while a worker's own `branch` row from before the landing keeps its window however late distill runs.
  - **When distill delivers.** The work sidecar is written from closed sessions only. A headless run that ends without its `SessionEnd` (the bullet above) is closed by the next launch once its transcript shows it exited, and its last prompt has its usage row from that distill; until a launch runs (the next session to start), its figures are not in the sidecar. A session whose transcript never shows an exit closes by idle time (`SESSION_IDLE_CLOSED_S`), and its last prompt has no usage row unless a later prompt of the session comes first; `backlog.py cost --rework` prints a session still open apart, as `open session figures` (`kb/_self/querylog.md`, Distill).
- **What gets no usage:** a prompt outside every work window that did not use the kb, a prompt the `kb:` hook answered without the model (no request), the last prompt of a session that ended with neither a `SessionEnd` nor an exit record in its transcript (a crash or a kill, which no launch closes before the idle time), and a `kb_ask.py` run (its `claude -p` runs with hooks off). The sidecar header's `missing` counts the written entries without usage.
- **Distill:** the written entries with a `usage` row of this `READER_VERSION` become the lines of `kb/_querylog/usage/<yyyy-mm>/<run-id>.jsonl`, beside the run file of the same run, committed and pushed with it (Store, Delivery). A window prompt that did not use the kb has a `usage` row but no entry, so it is in no usage sidecar: the work sidecar sums it. A rules lookup's entry (`root` `_self`, `kb/_self/querylog.md`, Distill) gets its usage line the same way, and the digest's usage figures leave it out, as every public count does.
- **Work sidecar:** the prompts of the work windows of a closed session, with their `usage` rows of this `READER_VERSION`, become the lines of `kb/_querylog/work/<yyyy-mm>/<run-id>.jsonl`, beside the run file of the same run, committed and pushed with it (`kb/_self/querylog.md`, Distill, Store and Delivery):
  - one line per item: the item id, the number of window prompts counted and their `main` and `sub` counts summed per model and agent group, the counts of the usage record without its `start`, `steps` and `cut`, and the `routed` counts of the subagents that worked on the item's `work/<id>` branch, added to `sub` without a prompt of their own (an item only a subagent worked has no prompt, so `prompts` 0 and an empty `main`); a prompt's `routed` counts go to their item whether or not the prompt lies in its window, and never also to the prompt's own lines;
  - **`rework`, an optional block of the item line, from the item's first refused done.** A `backlog.py done` that exited 1 leaves a `work` row with action `refused`, except one refused only because the item's code commits are not yet on the integration main (no row: the landing after it is not rework) (`kb/_self/querylog.md`, Surfaces). When an item has one in its window, its line gains `rework`: `prompts`, `main` and `sub` in the shapes above (with the same form for an item only subagents were counted for), the counts of the prompts from the prompt of its first refused row to the end of its window (its `done` or `release`) and of the subagents routed to it from those prompts. It is a part of the line's counts, not an addition to them: the line keeps the window's total and the work before the first refused done is the line less `rework`. The unit is the prompt, so the one that ran the refused done counts as rework. No `rework` for an item with no refused row, on a sprint's line (a prompt in several windows is never split) or on a shared line; an earlier sidecar has none, and its lines read as before. `backlog.py cost ID --rework` prints the two (`kb/_self/backlog.md`, Cost of work);
  - **`interrupts`, an optional count of the item line:** the tool calls interrupted in prompts of the item's window alone (the `work` rows of action `interrupt`, `kb/_self/querylog.md`, Store), a count with no command, path or text, absent when there were none.
  - **a prompt in several windows counts once, on the line of their sprint.** An orchestrator holding several claims is in several windows at once, and the prompt is the sprint's, not any item's: the line is `item: <sprint id>`, the sprint of the items. An item's sprint is read from the clone's backlog files when the distill runs (`ql_distill.sprint_finder`): the `sprint` of the item's own file, else that of the nearest item above it that has one, a sprint being its own; the sprint id is stored as the item id of its line, nothing else of the backlog. When the items of the windows do not all have one sprint (two sprints, an item whose files are gone because its sprint was closed, a clone without the backlog) the prompt counts once on the session's shared line instead. So the lines of a run never add to more prompts than the session spent, and a prompt in one window stays on its item as before. An item whose prompts are all on its sprint's line or the shared line has no item line, and `backlog.py cost ID` says so with its reason instead of a bare 0 (`kb/_self/backlog.md`, Cost of work);
  - one shared line per session that worked an item: the item ids whose window it opened (by a `claim` or its `work/<id>` branch), and the summed counts of its prompts outside every window that have a `usage` row, and of its prompts in windows that share no sprint (the prompts that used the kb: no other prompt outside a window gets a row, so what a session spent outside its windows on prompts that did not use the kb is not measured);
  - nothing that names the session, a prompt, the transcript or a command; a session that opened no item's window (no `claim` row and no `branch` row, or only ones of items with no file that no row closes) is not recorded, and neither is one whose `done` or `release` has no `claim` or `branch` row of the item in its own spool file;
  - a prompt is counted once: `worked.json` beside the spool lists the prompts a sidecar already holds.
- **Overhead lines: the kb's own background runs, apart from every item.** The same sidecar holds one more kind of line, `overhead: <kind>`, `calls` (the `claude -p` calls counted) and `main` (their counts per model, in the usage record's shape: `requests`, `in`, `cw`, `cw1h`, `cr`, `out`), and never an `item`, `items`, `sub`, session, prompt, cost or text: tokens a background run spent are the system's, not any item's, so a cost report never adds them to an item's totals (`backlog.py cost`):
  - **which kinds have counts.** `OVERHEAD_KINDS` (`ql_store`) names `distill`, `digest`, `eval` and `census`, and only `distill` writes a line: its Haiku calls (`ql_distill.claude_haiku`) run with `--output-format json`, and `ql_distill.haiku_result` reads the result's `modelUsage`, the whole run's counts per model (`claude/ci-and-headless.md`, DOC S-fksbud2r, S-isqfh6pr), never its text, session id or cost. The digest and `rag.py eval` start no model, and `census.py` only fetches web pages, so those kinds spend no tokens and write no line; the gate accepts their names for a run that one day does. The research runs of `apply` (`ql_research.py`), `kb_ask.py`'s reader and researcher and the benchmarks' runs are `claude -p` runs too, outside the four kinds, and write none yet: their `claude -p` calls are not read for counts;
  - **how the counts are read.** A call's `requests` is its `num_turns` when `modelUsage` names one model, else 1 for each model; `cw1h` is 0, since the result does not split the cache write by lifetime; a model id outside the `claude-` shape is `other`. A stdout that is not a result (an older CLI), a result with no counts and a failed call add nothing; a replayed or stubbed Haiku (`querylog.py distill --replay`, the tests) has no counts, so none is written;
  - **one line per kind in a file.** The distill run adds up its calls into its `distill` line, written with the run's other work lines or alone (a run file of no entry holds it); the header's `counts` gain `overhead`, the number of overhead lines, only in a file that has one, so earlier sidecars read as before. Gates: `querylog.py check` refuses an overhead line with an item, a session, prompt or text field, a kind outside `OVERHEAD_KINDS`, a `calls` or a count that is not a count (`calls` positive), counts outside the model shape, a header count that does not match, and a kind twice in a file (`kb/_self/querylog.md`, Store).
- **A sprint's cost report keeps three totals apart.** `python3 _tools/backlog.py cost SP` prints the sprint's item work (the item lines of the work sidecar and the shared figure), its research (the lines of the items whose touches are all kb content) and the system overhead (the overhead lines) as three totals that no figure adds into another: an overhead line is in no item's or sprint's counts, and a research item's is in no item-work figure. Overhead is the one total with no item to date it by, so it is placed by its run: a line belongs to the sprint when its run id's time (UTC) falls in the sprint's window, read from git history; what a window is, and what the report prints when git cannot say, are in `kb/_self/backlog.md`, Cost of work (`backlog.py`: `cost_overhead`). For any other id the report has no overhead.
- **Digest:** per week, the lookups with usage, input tokens per lookup (median and p90), output (median), the share of input read from the cache and spent in subagents, and the steps made only of kb tools with their median `grow` and result characters (Reporting). It then lists the week's top items by tokens from the work sidecar (`ql_report.work_lines`); the sidecar holds only `main` and `sub` counts, so there is no kb-tool share for them.
- **Not tokens: the ops sidecar.** `kb/_querylog/ops/<yyyy-mm>/<run-id>.jsonl` holds what the kb's own tools did and took (steps, exit codes, milliseconds, counts, item ids, test file names), read from `ops` spool rows, not from a transcript: it holds no token count, no `usage` row feeds it and no cost report adds it to an item's or the system's tokens (`kb/_self/querylog.md`, Surfaces and Store).
