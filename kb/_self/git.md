# Git: commits, sync, merging and history

## The regime by role

Two remotes matter, named by role, never by host. The **integration remote** (`git config kb.integrationRemote R`, default `origin`; `kbpublic.integration_remote`) holds the `main` every clone syncs with and the plugin installs from; it also holds the query log's store. The **publish remote** (`git config kb.publishRemote R`; `kbpublic.publish_remote`) is the public home; a clone without it has none, and nothing about publishing applies to it. Both settings live in the clone's config, never in a commit.

- **Lanes.** A commit is content (kb roots, the query log, backlog items, process docs, the two tool data files) or code (everything else); `_tools/kblane.py` is the classifier (Lanes below). Content lands on the integration `main` by `kbgit.py sync --push`. A range with a code-lane commit goes as branch `code/<id>` with merge-request push options (auto-merge, remove the source branch) and reaches `main` when that merge request merges; `main` does not move on the push. Only pushes to `main` are routed: another branch is pushed as it is, and a force push is allowed only to `code/*`, with a lease.
- **Enforcement.** The pre-push hook refuses a push of a code-lane commit to the integration `main` (no API call, sync's own push included). `kbgit.py check-lanes` asks the forge whether a merged request introduced each code-lane commit; run it by hand, no CI job does. `backlog.py done` refuses an item whose code-lane `KB-Work` commits are not on the integration `main` as last fetched (`kb/_self/backlog.md`, Definition of done). Neither host enforces paths on its free tier, so these are the enforcement points (Optional host setup below).
- **The gate is local.** `sync`'s gate and the pre-push hook are the gate. Every CI job is manual and a merge request merges without a pipeline (Workflow); a job a person starts reports afterwards.
- **Publish.** `kbgit.py publish` projects the integration `main` without `kb/_querylog/` and fast-forwards the public home; it refuses internal roots, `_private` and `_cache` paths, leak hits and a CI verdict that is not ok, and `publish --hook` runs it from the SessionStart hook of every clone with a publish remote (Public home).
- **Bridge.** A branch pushed to the public home (a pull request there) reaches the integration remote through `kbgit.py bridge <branch>`: its commits are rebased onto the integration `main` and routed by lane as sync does. A person closes the public pull request once `publish` brings the commits back (Public home).

### Optional host setup

The tools work without any of this; it makes the host cooperate. Each setting is a fact about the host's documented behaviour, so the kb cites it and a clone applies it in its own project settings.

- **Merge method: merge commit.** Choose the merge-commit method on the integration project. A merge request keeps its commits' hashes then, which `backlog.py done`'s ancestor check needs; fast-forward and semi-linear methods cancel an auto-merge whenever `main` gets a new commit meanwhile (`public/gitlab/automated-merge-requests.md:24`, DOC), and a rebase merge on GitHub gives every commit a new SHA (`public/gitlab/github-branch-rules-and-auto-merge.md:35`, DOC).
- **Skipped pipelines are considered successful.** With every job manual, a merge request's head pipeline is `skipped`; auto-merge merges it only when this project setting is on (`public/gitlab/automated-merge-requests.md:25`, `:29` and `:31`, DOC).
- **Protected branches.** Protect `main` on the integration project. A Free project can force merge requests for a whole branch (Allowed to push and merge: No one) but not for some paths; path rules need Premium (push rules, Code Owners) or an administrator's server hook, so the hook and `check-lanes` stay the per-path enforcement (`public/gitlab/protected-branches-tags.md:23` DOC, `:35` DER). Protection is per branch, never per path (`:30`, DER).
- **Public home rules.** On a GitHub public home that only the publisher writes to, a ruleset with restrict updates and a bypass for the publisher blocks every other writer, and a pull request can be required for the rest; the rules are per ref and per actor, never per path (`public/gitlab/github-branch-rules-and-auto-merge.md:19`, `:21` DOC, `:39` DER). A push ruleset by path is not available on a public repository with the Free plan (`:38`, DER).
- **Push mirroring cannot replace publish.** A push mirror has no path or content filter (only protected branches, or a branch regex on Premium), so a directory that must stay off the copy cannot be excluded by it; the projection `publish` builds is what keeps `kb/_querylog/` off the public home (`public/gitlab/repository-mirroring.md:38`, DER; `public/gitlab/protected-branches-tags.md:36`, DOC). Pull mirroring is Premium and does not bring pull requests, so `bridge` does that (`public/gitlab/repository-mirroring.md:13`, `:39`).

## Commands (`_tools/kbgit.py`)

| command | does |
|---|---|
| `python3 _tools/kbgit.py sync [--push] [--dry-run] [--remote R] [--branch B]` | the way to push: fetch, rebase onto the integration remote's `main` (`--remote` overrides), fix, gate, push (exit 0 done, 1 gate red or push rejected, 2 refused, 3 conflict needs `/kb-git-sync` or a human) |
| `python3 _tools/kbgit.py fix [--check] [--base REV] [--upstream REV]` | after any merge or pull, per root in `kb/`: dedupe/merge the union-merged ledgers, renumber colliding legacy ids (the `--upstream` side, already pushed, keeps its ids), rename colliding answer ids to `QK-<slug>`, rebuild the index, and report an entry id that two query-log run files under `kb/_querylog/` share (exit 1 `--check` stale, 2 needs a human); `fmt` only canonicalises the CSV ledgers |
| `python3 _tools/kbgit.py bridge <branch> [--push] [--dry-run] [--remote R]` | a branch of the public home to the integration remote: its commits not on the public `main`, rebased onto the integration `main`, gated and pushed by lane as sync does (exit 0 pushed, 1 refused or gate red, 2 bad arguments, 3 conflict; Public home) |
| `python3 _tools/kbgit.py publish [--dry-run] [--rewrite]` / `check-public [REV]` | push the projection of the integration remote's `main` without `kb/_querylog/` to the public home / exit 1 when `REV`'s history touches it (Public home) |
| `python3 _tools/kbgit.py install-hooks [--uninstall]` | once per clone: `core.hooksPath=.githooks`, so commits get their KB-* trailers and a plain `git push` runs the gate |
| `python3 _tools/kbgit.py trailers [--staged] [REV] [--verified YYYY-MM-DD]` | print the KB-* trailers of the staged change or of a commit; `--amend` rewrites HEAD's message with them |
| `python3 _tools/kbgit.py check-trailers [A..B]` | exit 1 listing kb commits whose trailers are missing or wrong, a malformed `KB-Verified`, `KB-Auto` or `KB-Work` included (default: CI's push range, else `@{upstream}..HEAD`) |
| `python3 _tools/kbgit.py lane [A..B or REV]` | each commit's short hash, its lane and the code paths that decided it (default: CI's push range, else `@{upstream}..HEAD`); `_tools/kblane.py` holds the classifier, see Lanes below |
| `python3 _tools/kbgit.py check-lanes [A..B or REV] [--forge auto\|gitlab\|github\|none]` | exit 1 listing each code-lane commit of the range that no merged merge request or pull request introduced, exit 2 when the forge's API cannot be read (default range as `check-trailers`); see Lanes below |
| `python3 _tools/kbgit.py log <S-id, topic, QK-id or path> [-n N]` | commits that touched it: by trailer, else by diff (`git log -G`) or path history |
| `python3 _tools/kbgit.py blame PATH:LINE` / `asof <YYYY-MM-DD or tag> PATH` / `tag-census YYYY-MM-DD` | the commit that wrote a line plus its sources' urls / a file as of a date or tag / annotated tag `census-YYYY-MM-DD` on HEAD (not pushed) |

History commands exit 0 on success, 1 when check-trailers finds a bad commit or log/blame/asof find nothing, 2 on bad arguments or outside a git clone.

## Workflow

- Two remotes carry `main` (the regime above): the integration remote, the plugin's install url and the default of `sync`, and the public home. `sync --push` pushes to the integration remote; the public home gets `main` only through `kbgit.py publish` (Public home), so it never holds the query log's store. An install gets whatever the integration remote holds.
- Small team, no review step: work on `main` or a short local branch and push with `sync --push`; content goes straight to `main`, code as a `code/<id>` merge request that merges without a pipeline. The local push gate is the gate, and CI is run by hand on the runners: `.gitlab-ci.yml` on GitLab, `.github/workflows/kb.yml` on GitHub (the same tests on Python 3.14, again on the 3.11 floor, the stress suite, trailers, `kb/_self/` docs, doc2query keys, artifacts). On GitLab every job runs on the project's two self-hosted runners (`kb/_self/runners.md`): the Linux jobs name the tag `docker-linux`, the Windows job `docker-windows`, so none waits on GitLab.com's shared-runner quota. Every job is manual (`when: manual`, `allow_failure: true`), on every branch including `code/*`: a push starts no job, and no merge request, auto-merge included, waits on a pipeline (`only_allow_merge_if_pipeline_succeeds` is off, and `allow_merge_on_skipped_pipeline` is on so auto-merge merges the `skipped` head pipeline of a merge request whose jobs are all manual, `public/gitlab/automated-merge-requests.md`; `_tools/test_ci_config.py`, `tests.py -k TestCiAllManual`). A person starts `kb-tests` (the full run with the git scenarios), `kb-trailers`, `kb-tests-floor` or `tool-stress` from the pipeline page when they want the runners' verdict. GitLab also runs the tests on Windows (`kb-tests-windows`: `tests.py`, then `stress_test.py`, and the job fails when either does; on the project's own runner with the `docker-windows` tag: a fresh Windows Server 2025 container per job from `python:3.14-windowsservercore-ltsc2025`, Hyper-V isolation, Windows PowerShell 5.1, MinGit fetched and SHA-256 checked for `git` and `sh`; one job at a time, and a job stays pending while the runner is offline). It is offered in a pipeline whose push changes `_tools/`, `.claude/`, `.claude-plugin/`, `.githooks/`, `.gitlab-ci.yml`, `pyproject.toml` or `uv.lock` and starts on a click; it is the only Windows run, so start it after a change to those paths (`red-pipeline` reads its failed script as red, `kb/_self/backlog.md`); it has `interruptible: false`, so a push to `main` while it runs does not cancel it once started, and `-o faulthandler_timeout=900 --durations=15`, so the log names a test that hangs and the slowest ones. With manual jobs, only the local gate stops a bad push; a job run afterwards detects one.
- One logical change per commit, and every commit passes `python3 _tools/check.py` and `python3 _tools/build_index.py --check`. A source row goes in the same commit as the facts that cite it; a `superseded_by` goes in the same commit as the re-pointed citations; a change to the tools or skills goes with the `kb/_self/` docs that describe it.
- Before pushing: `python3 _tools/kbgit.py sync --push`. It refuses a dirty tree (commit or stash first), fetches, rebases your commits onto `origin/main`, resolves the ledgers and generated files mechanically (`kbgit.py fix`, committed as `chore(kb): kbgit fix after sync`), refreshes stale trailers, runs the gate and pushes only when it is green. The gate runs what the changed paths (from `origin/main`'s merge base, plus the working tree) can break, and lists each skipped check with why: `check.py` for kb content, a root file (`README.md`, `AGENTS.md`) or a tool, `fetch.py --offline` for a pinned artifact or its `_sources.csv`/`_artifacts.csv` row, `doc2query.py stale` for an article or its expansions, `selfdoc.py stale --since origin/main` for a file `kb/_self` describes, `backlog.py check` for backlog items, `querylog.py check` for the query log store, `tests.py --changed origin/main` with `KB_TESTS_FAST=1` (the test files `_tools/testmap.py` maps the paths to, without the `git` scenarios; `kb/_self/tools.md`), and always `check-trailers`. Sync's own `fix` has just rebuilt the generated files, so its gate has no `build_index.py --check`. With no base to compare (a new branch) every check runs and `tests.py` runs its fast subset. `--dry-run` shows what would happen. The push follows the range's lane (Lanes): content-only commits go to `origin/main`; a range with any code-lane commit (its content commits ride along) goes as the branch `code/<id>` (`<id>` the first `KB-Work` id in the range, else `HEAD`'s short hash) with the push options `merge_request.create`, `merge_request.target=main`, `merge_request.auto_merge` and `merge_request.remove_source_branch`, and `main` and local `main` do not move. A remote that answers "the receiving end does not support push options" gets the same push without them, and sync prints that a merge or pull request must be opened from the branch. When `code/<id>` already exists on the remote and is not an ancestor of the rebased work, sync fetches its tip and pushes with `--force-with-lease` against that tip, to `code/*` branches only (never `main`), sending `merge_request.auto_merge` again; a branch that moved meanwhile is refused (exit 1, nothing overwritten). Exit 0 once the branch is pushed. `--dry-run` names the lane and the branch. Lanes route a push to `main` only: `sync --push --branch B` for another branch (a cloud session's working branch, the only one its git proxy takes) pushes to `B` whatever the lane.
- **An autonomous writer reaches `origin`'s `main` only through `kbgit.py sync --push`.** The query log's `querylog.py apply --push` is the one writer that pushes on its own: its commits, and the revert of an automatic push whose pipeline finished red, go through the worktree's `sync --push`; the revert keeps the store's files, marks the findings it undoes `apply-failed` and files one S2 bug item (`kb/_self/querylog.md`, Delivery). Its only other push is a conflict branch `querylog/<run-id>` with a merge request, never `main`. Research (`ql_research.py`, whose model run gets only WebSearch and WebFetch) and ingest (`kbingest.py`) neither commit nor push; a person commits their work and pushes it with `sync --push`. `TestAutonomousWrite` in `_tools/test_sync.py` (`tests.py -k autonomous_write`) holds this: a planted direct `git push` in a fixture writer fails it.
- **The pre-push hook** (`.githooks/pre-push`, installed with the commit hooks) first applies the public-home guard (Public home) to every push, then refuses a push to the integration remote's `main` that carries a code-lane commit (Lanes), then runs the same gate plus `kbgit.py fix --check` and `build_index.py --check` before a plain `git push` of the checked-out branch, and refuses the push when a check fails. The gate skips sync's own push (`KB_GATE_DONE=1`: sync gated already), tags and deletes, and says so for a pushed ref that is not HEAD (the checks read the working tree); the lane refusal applies to sync's push too. `git push --no-verify` skips it; CI then reports what it would have caught. Prefer `sync --push`: it also rebases and fixes the ledgers. The hook scripts start `kbgit.py` through `sh _tools/kbpy`, which finds `python3`, `python` or `py -3`; when it finds none (exit 127) the push goes through with a warning, except to the public home, which it refuses; without Python a code-lane commit for `main` is not refused either.
- Never `git push --force`, never push with a red gate, never rewrite pushed history. The one exception is `kbgit.py publish --rewrite` on the public home (Public home), when a person decides to replace what was pushed there directly.
- Exit 3 means a conflict in an article, tool or doc: the rebase is left in progress with the paths listed. Resolve it with `/kb-git-sync` (by meaning: both sides' facts kept, newer confirmed evidence wins a changed fact, real disagreements go to `_conflicts.md`), or by hand the same way, or back out with `git rebase --abort`. Exit 1 (red gate): `/kb-git-sync` fixes the cause, never the baseline.
- Census tags: `python3 _tools/kbgit.py tag-census YYYY-MM-DD`, then `git push origin census-YYYY-MM-DD`. A census tag says "the kb was confirmed current as of this date" (the tag message counts the sources and the `_fetch_state.csv` checks); create it only after a full verification.

## Lanes (`_tools/kblane.py`)

A commit is in the `content` lane or the `code` lane. A path is content when it is under a kb root (`kb/<name>/**` for a name not starting with `_`), under `kb/_querylog/`, a backlog item (`kb/_self/backlog/*.json`), a process doc directly in `kb/_self/` (`kb/_self/*.md`), `_tools/aliases.csv` or `_tools/lint_baseline.txt`; every other path is code (`_tools/`, `.claude/`, `.githooks/`, the CI file, `AGENTS.md`, `README.md`, `kb/_self/map.csv` and any file in a subdirectory of `kb/_self/`). A commit is code when any path it changes against its first parent is code (a merge commit the same way, a root commit against the empty tree). Every path the query log's writers accept (`ql_deliver.auto_kinds`) and every `kbgit.MECHANICAL` path is content, so a sync that rebases content never becomes code. `kblane.py` imports neither `kbgit.py` nor `backlog.py`; `kbgit.py lane` is its command line (`_tools/test_kblane.py`). `sync --push` routes by it (Workflow); `_tools/test_sync.py` `TestCodeLaneSync` covers both push paths against local bare remotes.

Neither host enforces paths on its free tier, so the hook and `check-lanes` are the enforcement points. **The pre-push refusal:** a push whose remote ref is `refs/heads/main` on the integration remote is refused (exit 1, no API call, sync's own push included) when its new commits hold a code-lane commit: `<remote sha>..<local sha>`, or for a new ref the commits no `refs/remotes/<remote>/*` ref reaches. It names each commit with its code paths and points to `sync --push`, which sends code as `code/<id>`. Pushes to other branches (`code/*`, `querylog/*`, a cloud session's branch) and to other remotes are not judged by it; `git push --no-verify` skips it. **`kbgit.py check-lanes [A..B or REV] [--forge auto|gitlab|github|none]`** takes its range as `check-trailers` does and lists the code-lane commits that no merged request introduced, by the forge's commit association endpoint over urllib: GitLab `GET /projects/:id/repository/commits/:sha/merge_requests?state=merged` (project from `CI_PROJECT_ID` and `CI_API_V4_URL`, header `JOB-TOKEN` from `CI_JOB_TOKEN`; a merge request counts when merged), GitHub `GET /repos/{owner}/{repo}/commits/{sha}/pulls` (`GITHUB_REPOSITORY`, `GITHUB_API_URL`, `GITHUB_TOKEN`; a pull request counts when `merged_at` is set). `auto` picks the forge from `GITLAB_CI` or `GITHUB_ACTIONS`; `none` treats every code-lane commit as unmerged. Only code-lane commits are asked about, and a merge commit is not judged itself: the commits it brings in are (code changed inside a merge commit passes). Exit 0 none unmerged, 1 some listed, 2 the API, its variables or the range cannot be read (it never passes then). No CI job runs it: run it by hand. Limits: GitHub marks a pull request merged when its commits reach `main` by a direct push, so such a commit passes there; a squash commit's association is not documented, so it is listed. `TestCheckLanes` in `_tools/test_kblane.py` covers it against an injected opener and a stub forge on loopback.

## Public home (`_tools/kbpublic.py`)

- **What stays off it:** `kb/_querylog/` (`kbpublic.PRIVATE`), the query log's store, lives on the integration remote only. A clone names its public home with `git config kb.publishRemote <remote>`; a clone without it (a production clone on its own host) has no public home, and nothing below applies to it.
- **`python3 _tools/kbgit.py publish [--remote R] [--source REMOTE/main] [--branch main] [--dry-run] [--rewrite]`** (the source defaults to the integration remote's `main`) fetches both remotes and pushes to the public home a projection of it: every commit rewritten without `kb/_querylog/` (author, committer, dates and message unchanged, a signature dropped), a commit that changed only the store left out, and a commit that never had it kept as it is, with its hash (the history before the query log, and its census tags, are shared by both remotes). The projection is a pure function of the source history, so each publish is a fast-forward of the last. A public branch that is not an ancestor of the projection (a commit pushed there directly) is refused (exit 1) unless `--rewrite`, which pushes with `--force-with-lease` against the tip it fetched. Before it pushes (a `--dry-run` runs the same checks and pushes nothing) it refuses, exit 1 naming every cause, in this order: a root in the projection's tree whose `_root.md` says `visibility: internal`, or any path under a `_private` or `_cache` directory; a file the projection changes against the public tip (every file when there is none) with a leak-scan hit that the tip's version of the same file does not already hold (`kbcommon.leak_hits`, allowing `_tools/tests_allowlist.txt` of the projection; a vendor export or snapshot only for secrets); and an integration CI verdict of the source commit that is not `ok` (`ql_deliver.ci_pipeline`: red, pending, unverified, none, or skip when `glab` or `gh` cannot read it). Content is refused, never filtered (`TestPublishSafety` in `_tools/test_kbpublic.py`). `refs/kb/published` keeps the last projection. Exit 0 published or nothing to do (also without a public remote: a note), 1 refused or the push failed, 2 bad arguments or a git error.
- **The SessionStart hook:** `.claude/settings.json` runs `kbgit.py publish --hook` beside `red-pipeline` (async, `timeout` 60), so the projection reaches the public home at the first session after `main` turns green (no credential in CI). In a clone with a public remote it runs the same publish (the same refusals, the CI verdict included) and prints only a refusal or a failed push, one `kb publish ...` line each; it prints nothing when it published or the public home is current. It exits 0 without a public remote and on every outcome, an unexpected error included (`kbpublic.cmd_publish_hook`, `tests.py -k TestPublishHook`).
- **`python3 _tools/kbgit.py bridge <branch> [--push] [--dry-run] [--remote R]`** brings a branch pushed to the public home (a pull request there) to the integration remote. It fetches the public home's `main` and `<branch>` (the public home is only read, never pushed to), takes the commits `<public>/main..<public>/<branch>` and refuses (exit 1, nothing bridged) when one touches `kb/_querylog/`. It refuses a dirty tree, an operation in progress and a missing public remote or branch (exit 2). It then creates the local branch `bridge/<branch>` (reset when it exists) at the public tip and runs `git rebase --onto <integration>/main <public>/main` on it: the commits are cherry-picked, never merged, because the public `main` is a projection of the integration `main`. Sync's machinery does the rest on that branch: mechanical conflict resolution, `kbgit.py fix`, trailer refresh, the gate, then with `--push` the lane routing (content to the integration `main`, a code-lane commit as `code/<id>` with the merge-request push options). A conflict exits 3 with the rebase left in progress on `bridge/<branch>`; resolve it, then `sync --push` there. Your own branch is never changed: it is checked out again when bridge ends (exit 0, 1 or 2) and the temporary branch is deleted once the push succeeded, kept otherwise. After a push it prints the public branch name and the new integration commits' short hashes; the pull request on the public home is closed by a person once `publish` brings them. `--dry-run` prints the commits and the lane and touches nothing. `TestBridge` in `_tools/test_kbpublic.py`.
- **The guard:** a push to the public home (the remote or its url) of a ref whose history touches `kb/_querylog/` is refused by the pre-push hook for every branch and tag (sync's own push included; without Python the hook refuses any push to the public home), by `sync` before it rebases (exit 2), and by the query log's push when `origin` is the public home (`kb/_self/querylog.md`, Delivery). `python3 _tools/kbgit.py check-public [REV]` is the same check: exit 1 listing the commits of `REV` (default `HEAD`) that touch it.
- **CI on the public home:** the `kb-public` job of `.github/workflows/kb.yml` runs `check-public` on every push, only where the repository variable `KB_PUBLIC_HOME` is `true`, so a fork or a production clone on GitHub without it keeps its store.
- Branches that Claude Code cloud sessions push to GitHub sit on the projected history and carry no store; they reach `origin` by a rebase onto `origin/main`, never by a merge of the two histories.

## Merging (what sync automates)

- `.gitattributes` merges every root's append-only ledgers (`_sources.csv`, `_fetch_state.csv`, `_anchors.csv`, `_answers.md`, `_gaps.md`, `_conflicts.md`) and the generated `_coverage.csv` and `_tools/lint_baseline.txt` with git's built-in union driver: parallel additions merge without conflict markers, but git keeps both sides' lines, so a row both sides touched may appear twice (fix keeps one row per id, and per fact and source in `_anchors.csv`: the latest `verified_utc`). Nothing to configure per clone.
- The append-style tool data (each root's `_retrieval/signals.csv`, `_retrieval/lookup_eval.csv` and `_retrieval/doc2query/expansions.csv`, and `_tools/aliases.csv`) merges with union too, but `fix` does not clean it: keep both sides' rows, one row per signal, alias term or eval id (tests.py fails on a duplicate signal or alias), then `doc2query.py stale` and `rag.py eval` (`/kb-git-sync`, Tool data).
- Writers: append rows and blocks, keep each CSV record on one line, never reorder or rewrap existing lines.
- Merge and rebase with `-c merge.conflictStyle=diff3` (sync does; by hand: `git -c merge.conflictStyle=diff3 pull --rebase`). Without it git keeps lines that two added blocks both end with only once, so two answers ending in `_Agent: kb-research_` interleave and the commit edits the other side's answer. fix restores such a section in the working tree when it knows the sides.
- `sync` runs fix for you. After a merge or pull made by hand: `python3 _tools/kbgit.py fix`, then `python3 _tools/tests.py`. If two branches took the same legacy id, fix asks for `--base $(git merge-base A B)` and renumbers the new rows to hash ids; add `--upstream origin/main` when one side is already pushed, so its ids stay. An answer id both sides took is renamed to `QK-<slug>` on the local side, mentions included. Exit 2 means a human decision (listed); nothing was written.
- Each root's `_coverage.md` merges normally; a conflict inside its coverage table is rebuilt by fix (then `git add` the page). Conflict markers anywhere else in it stop fix.

## Commit trailers

- Run `python3 _tools/kbgit.py install-hooks` once per clone. The commit-msg hook appends trailers computed from the staged diff against the first parent: `KB-Topics` (qualified topics, `public/intune/win32-apps`, whose article or data files changed; a commit from before the roots reads as public's, and `log` matches both forms), `KB-Sources-Added`/`-Changed`/`-Superseded` (`_sources.csv` rows), `KB-Answers` (`_answers.md` ids, `<root>:<id>` outside public). Only non-empty ones, sorted and `, `-joined; more than 40 values become `N ids (see diff)`. Never type them by hand; the hook replaces them on `--amend` and never blocks a commit. Merge commits get none.
- `KB-Verified: YYYY-MM-DD` only when the commit confirms its sources are current (e.g. a `/kb-refresh` that re-read them): `git commit --trailer "KB-Verified: 2026-09-25"` (every shell parses it), or `KB_VERIFIED=2026-09-25` in the hook's environment (a POSIX shell's `KB_VERIFIED=2026-09-25 git commit ...`).
- `git commit --no-verify` skips the hook; the CI job `kb-trailers`, when a person starts it, fails for the push. `sync` checks them before it pushes and rewrites stale ones on the unpushed commits; repair unpushed commits yourself with `python3 _tools/kbgit.py trailers --amend` (HEAD) or `git rebase --exec "python3 _tools/kbgit.py trailers --amend" @{upstream}`. Pushed history is never rewritten; commits up to `e5dadde` (before trailers existed) are exempt.
- `KB-Auto: <values>` marks the query log's automatic commits (`querylog.py apply --push`; values from `querylog`, `eval`, `alias`, `expansion`, `gap`, `research`, `revert`, `kb/_self/querylog.md`, Delivery). Nothing computes it; `check-trailers` flags a second `KB-Auto` line or a value outside the list. `git log --format='%h %(trailers:key=KB-Auto,valueonly)'` is the audit trail.
- `KB-Work: <id>[, <id>]` names the backlog items a commit works on (`kb/_self/backlog.md`). The agent writes it, in the message's last paragraph with `Co-Authored-By` and the other trailers (git reads none in an earlier paragraph); nothing computes it. `check-trailers` flags a second `KB-Work` line, or an id whose item file is in neither the commit nor its parent. On a commit not yet on `origin/main` it also refuses an id whose item is not claimed or is not in a started sprint, except on a backlog-planning commit (only `kb/_self/backlog/*.json` changed) and for the sprint and review items themselves (`kb/_self/backlog.md`, Git); the commit-msg hook warns, the pre-push hook and `sync` refuse. `git log --grep 'KB-Work: <id>'` lists an item's commits, including those of items deleted at sprint close.
- `Self-Reviewed: <doc>, <doc>` is typed by hand: it names kb docs (`kb/_self/`, `AGENTS.md`, `README.md`) that were checked against the commit's change and needed no edit, so `selfdoc.py stale` stops listing them (`/kb-self`).
- Reading them: `kbgit.py log S-k3f7q2zd` / `log auth/kerberos` (bare means public; `public/auth/kerberos` or another root's qualified topic) / `log QK-...`, `kbgit.py blame auth/kerberos.md:42`, `kbgit.py asof 2026-06-30 auth/kerberos.md`, or `git log --format='%h %(trailers:key=KB-Topics,valueonly)'`.
