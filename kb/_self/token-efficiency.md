# Token efficiency: every technique and where it lives

The catalogue of what this kb does to spend fewer tokens, turns and model calls, each with the file that does it and the measurement behind it. The reasoning and the headline numbers (when the kb pays off and when it does not) are in `kb/_self/design.md`; the measurements are in `kb/_self/reports/benchmarks.md` (section names in quotes) and `kb/_self/reports/fact-diff.md`. Change a technique here only together with its code (`/kb-self`).

The cost model all of them follow: a lookup costs the agent's fixed start context times its turns, plus what the tools return. The facts are small (a fact line is under 100 tokens); the context around them is not ("Reading files without the lookup tools"). So each technique does one of five things: skip the model, cut turns, shrink tool output, shrink the always-loaded context, or send the work to a cheaper model.

## 1. Skip the model

- **The `kb:` hook answers without a model call.** A `good` pack with no `check:` line and no `route:` line blocks the prompt and shows the pack as the answer: 0 tokens, about 0.05 s ("Tool speed"). A `weak` pack goes to the model as context, so it does not search again; `kb+:` always does. A `backlog:` prompt is answered the same way from `backlog.py horizon` and `next`. `_tools/kb_hook.py` [CODE _tools/kb_hook.py#answer] ("Lookup tools against reading files").
- **A routed pack costs the differential, not the pack, on `none`.** A pack with a `route:` line (`weak`, a flagged `good`, `none`) goes to the model with one instruction (answer what the kb has, research only what it lacks in the live docs, label it "live docs, not in the kb", never from memory). For `coverage: none` (route `web`) the context adds only the coverage, `route:`, `kb has:` and `kb lacks:` lines, no fact lines, so the model starts from what the kb lacks instead of searching again; `weak` and flagged `good` (route `split`) add the whole pack, cut to stay under 10,000 characters [CODE _tools/kb_hook.py#routed].
- **Structural questions are tools, not reading.** Counts, lists and joins are `rag.py audit`, `facts` and `src --cited` (MCP `kb_audit`, `kb_facts`, `kb_source` with `cited`): 1 call and about 1k tokens, exact, against 8 calls and 102k effective input for an agent reading the files (28 calls and 363k in the first measurement; "Reading files without the lookup tools", T6).
- **`kb_ask.py` answers counts and "who cites" with no model.** It detects them before routing and calls the audit and source tools: $0, 0.5 s [CODE _tools/kb_ask.py#tool_answer] ("Routing by verdict").
- **Source changes are sorted without a model.** `_tools/factdiff.py` checks each source by its provider's cheapest reliable signal (`_tools/providers.csv`: a 304 to the stored ETag, the page's version id, a text hash), resolves each fact of a changed page against its anchor, and dates the unchanged and word-for-word ones in a `KB-Verified` commit; `review` gives a model only the facts whose passage changed, old and new passage each, never a page [CODE _tools/factdiff.py#review_items] ("Dry run on the entra domain" in `kb/_self/reports/fact-diff.md`: 73% of facts with no model, 31 times less text).
- **The model runs at write time, not at lookup time.** doc2query expansions are generated once per fact and indexed; `pack` stays deterministic (`kb/_self/doc2query.md`).

## 2. Fewer turns

- **One call, one verdict, one stop rule.** `pack` returns `coverage: good|weak|none`, the best fact lines by article and one url footer; the verdict tells the agent when to stop: `good` answer, `weak` one reworded pack or one show, `none` state what the kb has and lacks and research only the rest in the live docs [CODE _tools/kbfacts.py#pack] ("Lookup tools against reading files"). The same rule is in `AGENTS.md`, the `/kb-lookup` skill and the MCP server instructions [CODE _tools/kb_mcp.py#INSTRUCTIONS]; the pack's own none sentence carries it too [CODE _tools/kbfacts.py#NONE_SENTENCE].
- **Batch pack.** Up to 6 parts in one call (`questions`, `rag.py pack -q PART -q PART`), a verdict each and one shared footer [CODE _tools/kbfacts.py#pack_many]; a cross-topic question took 2 turns instead of 6 ("Plugin in a host project").
- **`kb_pack` is always loaded.** `_meta` `anthropic/alwaysLoad` on `kb_pack` only, so the first lookup needs no tool-search round trip; the other kb tools stay deferred [CODE _tools/kb_mcp.py#TOOL_LIST] ("Plugin in a host project").
- **`kb_pack` defaults to `detailed`.** The urls come in the same call; making the agent resolve them would cost a turn.
- **Parts are split before routing.** `kb_ask.py` splits numbered parts and several questions, one pack each, so a three-part question stays on the cheap route: $0.013 instead of $0.121 [CODE _tools/kb_ask.py#split_parts] ("Routing by verdict").
- **Change requests are routed by a hook, not by the model's reading.** `.claude/hooks/kb_change_router.py` adds one line naming the skill when a prompt's words name a change skill, once per skill set per session, and nothing otherwise.

## 3. Smaller tool output

- **Fact lines, not pages.** One fact per line with its tag, so a tool returns just the lines that answer, with provenance (`kb/_self/content-rules.md`).
- **A token budget per pack.** `budget` (default 1200 tokens, 200-6000) caps each pack; with 3 or more parts each gets 2 x budget / n, at least 800, which keeps 98% of the expected fact lines and cuts a 6-part pack from 21.4k to 16.4k characters ("Retrieval quality"). A picked `SNIPPET:` bullet prints its code block under it, inside the same budget [CODE _tools/kbfacts.py#snippet_code].
- **Decisions are paid from the budget, not added to it.** A pack prints at most 3 decision lines (`## decisions`, each cut at 300 characters) and they cost at most a third of the budget, charged before the fact lines, so a root with decisions packs within the same `budget` and the facts give way, never the other way round; a kb with no decision row packs byte for byte as before [CODE _tools/kbfacts.py#decisions_for] [CODE _tools/kbfacts.py#MAX_DECISIONS].
- **A tested answer stops at its pinned passages.** `pack --root _self` with a tested match prints the pinned passages, at most three further ones and the tied decisions, not the whole budget; a `weak` pack keeps the budget [CODE _tools/kbfacts.py#TESTED_FURTHER].
- **Observed signals take what the facts leave.** A pack prints at most 2 LOG lines (`observed signal (LOG, not a fact):`, each cut at 200 characters) after the facts, inside the same `budget`: they are dropped first when the facts fill it, and a kb with no active `_logs.csv` row tied to what the pack prints packs byte for byte as before [CODE _tools/kbfacts.py#logs_for] [CODE _tools/kbfacts.py#MAX_LOGS].
- **One deduplicated url footer.** Urls per hit were 25-46% of search output, many repeated ("Reading files without the lookup tools"); pack prints one footer of only the cited ids, and `search` adds urls only with `-u`.
- **`response_format`.** `concise` (fact lines with `path:line` and tag, no urls) is the default for `kb_facts`, `kb_audit` and `kb_search`; `detailed` on request [CODE _tools/rag.py#FORMATS].
- **Capped listings.** `search` returns at most 2 hits per file [CODE _tools/kbfacts.py#SEARCH_PER_FILE]; `kb_show` prints at most 400 lines [CODE _tools/kb_mcp.py#MAX_LINES]; a cut fact keeps its tag and a listing says how many lines were cut and how to get them ("Retrieval quality").
- **Request words are stop words.** "answer", "citation", "please", "explain" do not count as key words, so a covered question is not pushed to the `weak` route [CODE _tools/kbfacts.py#STOP].
- **Retrieval quality is token efficiency.** A false `none` makes the agent give up, a false `good` makes it answer wrongly, a miss makes it search again. So: untagged content ranked at 0.8 [CODE _tools/kbfacts.py#UNTAGGED_WEIGHT], compound identifiers split, a number joined to a unit (`1.5-second`) also held as the number, product aliases (`_tools/aliases.csv`) that never count as key words, doc2query expansions [CODE _tools/kbfacts.py#EXPANSION_WEIGHT], two verdict corrections (common words only: `weak`; another product: `none`) [CODE _tools/kbfacts.py#specific], and the `check:` line for a possible false `good` (`kb/_self/tools.md`, "How the lookup tools decide").
- **`kb/_self/` stays out of the pack.** Its words (hook, skill, plugin) would crowd real answers in `claude/`, `mcp/` and `agents/`; `search --index` reaches it on purpose [CODE _tools/kbfacts.py#index_files].
- **The rules come as passages, not whole docs.** An agent asks for the `kb/_self` rules with `rag.py pack --root _self`: a skill step reads its set (`--set skill:step`), a worker its item's brief (`--item ID`), and any other question a pack of its own. Each answer is the few sentences that hold the rule, with the decisions tied to them, so no doc is read whole [CODE _tools/kbfacts.py#self_units].

## 4. Smaller always-loaded context

- **`AGENTS.md` holds only the lookup rules**, at most 4 KB (tested). It loads in every session and subagent; a 15.8 KB version that also held the maintainer rules cost 6.8k tokens there ("Reading files without the lookup tools"). Maintainer rules sit in `kb/_self/`, one file per job, read by the skills that need them (`kb/_self/README.md`).
- **The plugin ships little.** In a host only the `kb` server's instructions and tool descriptions and the skill and agent names reach every session: about 1.24k tokens, most of it the `kb_pack` schema and the server instructions (`kb/_self/plugin.md`; "Always-on cost"; the figure predates the schema's `include_invalidated` argument and the instructions' sentence on `DECISION` lines, which replaced another).
- **Descriptions stay out of listings.** `/kb-review-workspace` and `/kb-gap` set `disable-model-invocation: true`, so they cost nothing until run; the clone-only writing skills are never in `plugin.json`, while `/sprint`, `/item`, `/backlog` and the `kb-worker` agent are, model-invocable, so a host that installs the plugin lists their four descriptions in every session, as the clone's own `kb-*` entries, links to the same files, do in a clone (`kb/_self/plugin.md`).
- **The plugin is split.** The documentation servers are a second plugin (`.claude-plugin/it-ops-kb-docs/.mcp.json`), so a host that needs only the kb does not carry three more servers' instructions.
- **The hooks cost nothing when not used.** The `kb:` hook returns before loading the kb for a prompt without the prefix, and as the PreToolUse hook on WebFetch it prints nothing on a fetch it lets run, while a fetch the routes table routes elsewhere costs one deny reason instead of the page's summary (`kb/_self/tools.md`); the change router adds nothing to questions, harness messages, prompts that name no change skill or a skill set it already named in the session; `.claude/hooks/session_start.py` runs only in Claude Code on the web and prints a short status; the query log's capture hooks and its `SessionEnd`/`SessionStart` distill launcher print nothing, so they add no context, and its weekly digest hook prints a `systemMessage` for the person once a week, never plain stdout (`kb/_self/querylog.md`, Reporting). The backlog's horizon hook (`_tools/backlog.py horizon --hook`; the plugin's entry runs it with `--opt-in`, which prints nothing in a host project whose `backlog.json` does not name `horizon` in its `hooks` setting) adds a few lines of context per session where it runs: each active sprint's id, title, counts and next item id, and what waits on the operator, without goals or critical paths (`kb/_self/backlog.md`). Its red-pipeline hook (`backlog.py red-pipeline --hook`, a clone only) is async and prints nothing, so it adds no context; the plugin's intake entry (`intake --file --hook --opt-in`) is async, silent and runs only where `hooks` names `intake`. The Python notice (`sh _tools/kbpy --notice`, the clone and the plugin) prints nothing when Python is found, and otherwise a `systemMessage` for the person only.
- **Tool descriptions say what the tools are not.** Every kb tool starts "Documentation facts from it-ops-kb (not live device or directory data)" [CODE _tools/kb_mcp.py#DOCS], so a host with live MECM or AD tools does not call the wrong one and retry.
- **Freshness notes only where they apply, not in the always-on instructions.** A pack about the latest release or a version the kb never names prints one `freshness:` line (the lead article's `retrieved_utc`: check the source live, say the version) [CODE _tools/kbfacts.py#freshness]; a copy behind the branch it follows opens every `kb_pack` with one `kb copy: N commits behind` line and the update command (no path or command on a server limited by `--roots`), read from local refs [CODE _tools/kb_mcp.py#behind_note]. Neither costs a token otherwise ("Partial knowledge, newer versions and stale copies").

## 5. A cheaper model, or none

- **Answer inline, never in a fresh general-purpose subagent.** A subagent pays its start context (10-50k tokens) before reading a line and re-sends it each turn; a one-fact lookup in one cost 44-62k effective input (120-136k in the first measurement) ("Reading files without the lookup tools"). The rule is in `AGENTS.md`, the `/kb-lookup` skill and the server instructions.
- **The lean `kb-lookup` agent**, only for long research whose output would fill the caller's context: kb tools only, Haiku, `effort: low`, `maxTurns: 6`, `omitClaudeMd: true`, the lookup skill preloaded, 4.0k tokens of start context (`.claude/agents/kb-lookup.md`; "`kb-lookup` agent start context", "Models and hand-off patterns"). `effort: low` is on the agent, never on the skill, where it would lower a host session's effort.
- **The review runs in its own context.** `/kb-review-workspace` forks into `kb-reviewer` (Sonnet, `effort: low`, read-only), so reading a host's code stays out of the main session (`.claude/agents/kb-reviewer.md`). On the host scenario's five planted problems it named all five at `low` as at `medium`, at $0.0538 against $0.0927, 21.5 s against 27.8 s and 8 tool calls against 10 (one run each, the same day; "Plugin in a host project").
- **Sprint workers on Sonnet.** Every sprint item, `S1` and `S2` bugs and the breakdown of a story or bug with no tasks included, goes to a headless `claude -p --model sonnet --effort high` session in its own worktree, with `.claude/agents/kb-worker.md` as its role file (the plugin's `agents/worker.md` where the project has none), and the sprint review's reviewer runs the same way; the session model only when the operator asks for it (`kb/_self/backlog.md`, Running a sprint). On the Agent-tool fallback the `kb-worker` agent (the plugin's `agents/worker.md`) takes the item, on the `sonnet` alias at `effort: high`, never a pinned id or `inherit`; it is started without a model override, which would replace the file's `model`. A worker may run the whole suite, which takes the host test lock and waits its turn (`kb/_self/backlog.md`, Working on items), so up to four workers do not load the host. Every `/kb-census` subagent keeps the session model.
- **`kb_ask.py` routes by verdict, not by a model.** `good` goes to Haiku with the packs and no tools; the reader answers `INSUFFICIENT` when the facts are only related, and the question escalates to Sonnet at `--effort low` with the pack as evidence and only the kb server's cached live-docs tools and WebSearch/WebFetch; a pack the kb lacks (`route: web`) goes there directly with the question, the missing words and the nearest article titles, and a partial one (`route: split`) runs the reader on what the kb has and the researcher only on what it lacks, costs summed; both cost less than a bare Sonnet web search, and `web` passed checks the bare search missed ("Routing by verdict against the bare agent"). `--root _self` asks the rule docs with no web: a tested question's pack is the answer with no model, a `weak` pack goes to one Haiku reader given the pack and the full text of its first two sections, and a miss prints what the kb has and lacks [CODE _tools/kb_ask.py#rules]. $0.003-0.022 per covered question against $0.18-0.29 for Opus alone [CODE _tools/kb_ask.py#READER] ("Routing by verdict").
- **A model upgrade under an alias.** The `sonnet` alias the router, the agents and the benchmarks name follows the newest Sonnet; Sonnet 5.5 costs the same per kb question as Sonnet 5 at 19% less input, with a fixed context 12.6k smaller and the Purview false `good` answered from live docs where Sonnet 5 stopped at the pack ("A new model against the one it replaces").
- **The router and the hook on a wide pool.** Over 150 questions the router, its reader Haiku 5.5 (the model the `haiku` alias names from Claude Code 2.1.293) and its researcher Sonnet 5.5, took 17.5k effective input tokens per right answer at $0.024 a run, against 73.3k for Haiku 5.5, 72.0k for Sonnet 5.5 and 56.8k for Opus 5.5 with the kb tools, at a share of runs right (92.0%) whose cell interval overlaps theirs (84.7% to 90.0%); its first rows read on Haiku 4.5 (14.6k, $0.026 a run), a model whose 1-hour cache write costs $2 per million tokens against $0.20 on Haiku 5.5, so their cost does not compare; the hook took none and its pack held the checked text in 85.3% of runs. Neither answers a question that a tool answers by a join (the `decision` and `conflict` kinds), the hook not a count either ("A question pool over the kb, router, hook and web arms").
- **A dearer model is not a more accurate one here.** On the pool Opus 5.5 was right as often as Sonnet 5.5 and Haiku 5.5 within the spread (90.0% against 89.3% and 84.7%), with 15-17k fewer tokens per right answer, at $0.232 a run against $0.150 and $0.009 (same section).
- **Effort `low` on the kb agents.** On that pool `low` took 17% fewer tokens per right answer than `default` on Sonnet 5.5 and was 26% cheaper; on Haiku 5.5 and Opus 5.5 the tokens were within the spread and the run 13% and 6% cheaper; the share right within the spread for all three, and the 32k-token start of a run the same at both levels (same section).
- **A cheaper model is not the older one.** On the pool Haiku 5.5 was right in 84.7% of runs against 48.0% for Haiku 4.5 at $0.009 a run against $0.034; Haiku 4.5 read less per run, so its tokens per right answer were lower (58.7k against 73.3k) while its answers were wrong far more often (same section).
- **Several questions in one session.** In a pool session the first question adds 34.6-38.2k tokens to the prompt and the later ones 3.7-10.1k on average, and a session took 23-34k fewer tokens per right answer than a fresh session for each question, at a share right inside the spread and 30-48% less per question (same section).
- **A lean headless start.** The router's `claude -p` skips user plugins and MCP servers (`--setting-sources project,local --strict-mcp-config`) and runs with hooks off (`--settings '{"disableAllHooks": true}'`, so the query log does not log it twice), and the reader gets no tools: start context 27.2k, then 23.6k, then 8.3k [CODE _tools/kb_ask.py#LEAN] [CODE _tools/kb_ask.py#claude_argv] ("Routing by verdict").

## Speed that keeps turns short

- **A persisted index.** Postings lists in a stdlib `sqlite3` file keyed by a fingerprint of the kb files: a cold `pack` in about 0.04 s instead of 4 s, output unchanged [CODE _tools/kbfacts.py#store] ("Tool speed"). The fingerprint is of the files' content, not their path or times, and a clone's worktrees share the index directory, so a sprint worker's fresh worktree reads the index its clone built instead of rebuilding it (14 s on a Windows host) [CODE _tools/kbfacts.py#content_key]. A rebuild after an edit reuses the weighing of every unchanged unit from a cache beside the index, so it costs well under half a first build (4.7 s against 11 s on that host) [CODE _tools/kbfacts.py#weighed].
- **Live docs are paid once a week.** `docs_search` and `docs_fetch` on the `kb` server keep each remote answer 7 days on disk, keyed by server, tool and arguments, so a repeated search or fetch makes no HTTP call; one answer runs to about 10-26k characters [CODE _tools/kb_mcp.py#docs_cache_read].
- **A warm server.** `kb_mcp.py` builds or loads the index while the client connects, so the first `kb_pack` does not wait [CODE _tools/kb_mcp.py#warm].

## Measured, not assumed

- **The deterministic eval.** `rag.py eval` runs `kb/public/_retrieval/lookup_eval.csv` (recall, verdict, output bytes) in `tests.py`, so a ranking or output change is caught with no agent; it prints only the failing rows and the totals line (`--all` every row), so a session that runs it reads no passing row. Its rows are what ranking work tunes on, so they pass by construction; the answer rate on questions no tuning has seen is the held-out file's (`rag.py eval --file kb/public/_retrieval/lookup_heldout.csv --root public --min 16`, `kb/_self/tools.md`), which refuses a row that rewords a tuned one, so a reworded tuned question cannot lift it.
- **Real usage of every logged lookup.** At session end the query log reads each kb prompt's exact `usage` from the session transcript (`_tools/kbusage.py`, no model) and keeps counts only, per model, subagent group and step, in a usage sidecar beside the run file; the weekly digest reports input per lookup, cache-read and subagent shares, and the context each kb-only step added (`kb/_self/usage.md`).
- **The paid benchmark.** `_tools/agent_bench.py` runs `claude -p` per model and hand-off pattern and records cost, cache tokens, tool calls and checks; `_tools/benchmarks.py` re-runs every measurement, or one by name, into one results file and generates the report's tables from it; every conclusion in `kb/_self/design.md` cites a report section that states its setup.
- **Method rules from the runs.** Compare tokens, not dollars (the run that pays the cache write varies); start each batch from a fresh session; leave the prompt cache lifetime at its default unless lookups repeat more than five minutes apart ("Routing by verdict").
- **Tried and dropped.** RM3 query expansion, case-sensitive names, the verdict rules for a false `good` that demoted true ones, rerankers and embeddings, handing lookups to a model told to route ("Retrieval quality", "Routing by verdict", "Models and hand-off patterns"); a compact brief of a backlog item's packs and referenced facts in the working agent's prompt, which the agent read again on its own, so it added tokens to every request: the brief arm used more tokens in two of three paired runs and 1.1% fewer in the third, and more effective input in all three ("The comparison" in `kb/_self/reports/backlog-briefs.md`).
