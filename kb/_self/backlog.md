# Backlog: planning and shipping changes to this project

How a change to this project is planned, scheduled, worked on, proven done and closed. The work is tracked as epics, stories, tasks, subtasks, bugs and sprints, stored as one JSON file per item in `kb/_self/backlog/`. `_tools/backlog.py` is the only thing that computes state from those files, and three skills run the process: `/kb-backlog` plans, `/kb-sprint` runs a sprint end to end, and `/kb-item` works one item. Read this before any of them. Read the section "Conduct for changes" of `kb/_self/maintaining.md` (`python3 _tools/selfdoc.py section maintaining "Conduct for changes"`), not the whole file, before the change itself.

The backlog is the one queue of open work. `_gaps.md` and `_conflicts.md` stay content ledgers, and query-log findings stay in `kb/_querylog/`. An item may name a ledger entry or a finding in `links`; the ledger entry itself is not the work item.

## Why data, not prose

- An agent keeps its task list as structured data it may only flip from failing to passing after a check. A status written in prose invites a later session to declare the job done too early (`agents/agent-planning-and-done.md`, DOC S2150, DER S2150, S-o3v6ozch).
- Something other than the working agent decides it is done. Here that is `backlog.py done`, which runs the item's checks itself and records their exit codes (DOC S-o3v6ozch).
- One file per item means parallel agents never edit the same file. Random ids mean two writers never pick the same one.

## Levels

GitLab plans with an epic, issue and task hierarchy (`gitlab/work-items-planning.md`, DOC S-v2ztgtdn). Scrum names no epics, stories, subtasks or story points (`agents/agent-planning-and-done.md`, DER S-2wwcyoa4). The levels here are sized by what lands in git:

| kind | id | is | parent | needs |
|---|---|---|---|---|
| epic | `EP-` | an outcome across many pushes | none | title, priority |
| story | `ST-` | one verifiable capability; lands in one `kbgit.py sync --push` | epic or none | goal, checks |
| bug | `BG-` | a defect, sized like a story | epic or none | goal, severity, `repro` |
| task | `TK-` | one commit | story or bug | goal, checks, touches |
| subtask | `SB-` | one agent step inside a task (a `/goal` run, a subagent); no commit of its own | task | touches |
| sprint | `SP-` | a goal and the stories and bugs committed to it | none | goal, the `start` gate |

A story or bug too big for one push is split into two. A task too big for one commit is split into two. There are no estimates. Every id is the kind's prefix and 8 random base32 characters.

## The item file

`python3 _tools/backlog.py new KIND --title ...` creates a file. After `new`, `backlog.py set ID` changes an item's `notes`, `links`, `touches`, `checks`, `depends_on`, `relates_to`, `repos`, `repos_if_needed`, priority, rank and sprint, and replaces its `title`, `goal` and `parent` and a bug's `repro` (a command that must fail now, for the defect, as `new bug`'s), `repro_reason` and `severity` (a list option such as `--touch` replaces the whole list, so a gone path is removed by setting the list again without it; its own append flag (`--add-touch`, `--add-check`, `--add-link`, `--add-depends`, `--add-relates`, `--add-repos`, `--add-repos-if-needed`, `--add-notes` for the notes text) appends what is missing to that field alone (`external` is a map, so `--external TRACKER=ID` replaces the whole map with the given pairs and `--add-external TRACKER=ID` adds ids to a tracker's list), and a call naming both the replace and the append flag of one field is refused (exit 2, naming the field); `--clear FIELD` removes the field; a story needs a `goal` and checks that run real test or tool code, which `check` refuses `python3 -c pass` for) and `backlog.py gate add ID --question Q --option O --option O --recommendation R [--kind blocking|provisional] [--id GATE]` adds a gate. Only a field neither `new` nor `set` writes (`knowledge`, `recurs`, a trigger's text) is changed in the file itself, followed by `python3 _tools/backlog.py fmt` (canonical key order and layout) and `python3 _tools/backlog.py check`; `status`, `claimed_by` and `evidence` are never edited, they come from `claim`, `release`, `done` and the other lifecycle commands. The other commands that write an item, and what `set`, `move` and `reopen` refuse: Item commands, below. Fields, in file order:

| field | holds |
|---|---|
| `id`, `kind`, `title` | identity; the title is a short name that is always printed with the id |
| `status` | `draft`, `todo`, `doing`, `done`, `dropped` (a sprint: `planned`, `active`) |
| `parent`, `sprint` | the hierarchy; only stories and bugs name a sprint, and their tasks and subtasks follow it (`new` refuses `--sprint` on a task or subtask) |
| `review` | true on the sprint's review story |
| `goal_research` | true on the sprint's goal research story |
| `priority`, `rank` | `P1` to `P3`, then an integer order within the priority |
| `severity`, `repro` | bugs: `S1` to `S4`, and the check that fails until the fix lands |
| `goal` | the end state, as a fact about the repository once done |
| `checks` | the commands that prove the goal: `{"run": [argv], "exit": 0, "match": "regex"}`, run without a shell and with an isolated query log home (`CLAUDE_PLUGIN_DATA` a fresh temporary directory, removed afterwards; `kb/_self/querylog.md`, Tests), so no check adds a row to the clone's own spool but the `test.run` row of a `tests.py` run it makes, which `KB_TEST_RUN_HOME` (the clone's real query log directory, kept when a check runs a check) sends to that spool |
| `touches` | path globs the item's commits may change (`*` within a directory, `**` across) |
| `repos`, `repos_if_needed` | the repositories of a multi-repository workspace the item changes, and the ones it may change if the work needs it: lists of names `backlog.json`'s `repositories` map (Project settings) declares, written by `set --repos NAME` and `--repos-if-needed NAME` (repeatable, each with an `--add-` twin) and read by `check`, which refuses a name the map does not declare (every name, in a project with no map), a name listed twice or in both lists, the fields on a sprint, and, while the map is declared, a draft, todo or doing item with `touches` and no `repos`; a done or dropped item is held to the first three only. A project with no `repositories` map is the one repository the root is, and its items carry neither field. While the map is declared an item's `touches` are `<repository>/<glob>` (`workspace/<glob>` for the workspace's own files), and `held --overlaps`, `check`'s unordered-overlap and shared-file warnings and `bl_base.touches_overlap` compare two touches only inside one repository, a glob read against that repository's own tracked files (`bl_plan.touch_files`); a touch whose first segment names no declared repository is compared whole as written, as a project with no map compares them. `claim` compares no touches: `held --overlaps` before the claim is the guard; `dispatch` makes a worktree for each repository of `repos` and none for `repos_if_needed` (Running a sprint) |
| `depends_on`, `relates_to` | hard dependencies (not ready until they are done); soft links |
| `gates` | questions for the operator: `{"id", "kind": "blocking"\|"provisional", "question", "options", "recommendation", "answer", "by"}` |
| `trigger` | an outside event it waits for: `{"when": text, "fired": false}` |
| `knowledge` | the kb facts the work rests on: `{"ask": [questions], "refs": [...]}`, each ref a topic (`<domain>/<slug>` or `<root>/<domain>/<slug>`), a QK answer id (`QK-...`, `<root>:QK-...` outside `public`), a source id, or a fact (`<root>/<path>#<fact key>`, the 12-hex key `_anchors.csv` uses); `check` fails on a ref the clone's kb does not hold at HEAD (an uncommitted edit counts for nothing until it is committed) and reports a fact key no longer in its file as `stale knowledge` without failing, for an item that is todo or doing in an active sprint only (a draft, done or dropped item, one in a planned sprint and an epic outside any sprint keep theirs unchecked, so a kb refresh that renames a cited article does not turn the gate red), while the field's form (`ask` and `refs`, lists of non-empty texts) is checked on every item |
| `links`, `notes` | ledger entries, answers and docs it relates to; present-state notes |
| `external` | the item's ids in outside trackers: a map of tracker name to a list of ids (`{"jira": ["PROJ-123"], "gitlab": ["12"]}`), written by `new --external TRACKER=ID` (repeatable) and `set --external` or `--add-external`, never by hand. `check` refuses a tracker `backlog.json`'s `trackers` key (Project settings) does not name, an id that tracker's pattern does not match whole, an id listed twice and a sprint's `external`; a project with no `trackers` key (or an empty one) accepts none, so the kb's own items carry none. `show` prints one `external TRACKER REF URL` line per id (`bl_base.external_lines`, the one helper the worker's brief calls), `find` matches an id as it matches a word of the title, the `claim` and `done` commits carry a `KB-Ref` trailer per id (Git, below) and `land` writes them into the merge request description |
| `recurs` | optional, a process item's mark: the ids of the sprints (`SP-...`) in which the work came back, each once; `check` refuses a value that is not a list of sprint ids, and does not require the sprints to exist, since `close` deletes them. An open P1 item with two or more is one `start` warns of when the sprint leaves it out (Sprints, Start) |
| `claimed_by`, `evidence` | written by `claim` and `done` only |

Items describe the present, never a history: no dated logs, no "tried X on Monday". What happened is in the commits. The git history keeps an item's earlier versions and the design choices of finished work, including items deleted at sprint close:
- `git log --grep "KB-Work: <id>"` lists the commits that worked on an item;
- `git log --all -- kb/_self/backlog/<id>.json` lists the versions of its file;
- `git show <commit>^:kb/_self/backlog/<id>.json` prints its last text before deletion.

## Item commands

Before filing, `backlog.py similar "<title>" [--goal G]` ranks the open items (draft, todo or doing) by word overlap: the share of the query's words (lowercased letters and digits, stop words and single characters left out) found in an item's title and goal, highest first, the first ten with the shared count, `near` marking a near-duplicate (a share of 0.60 or more and two words or more); it exits 0. `new` runs the same comparison on its title and goal and prints one `warning: near-duplicate of open <id> “<title>”` line per near-duplicate; it still writes the item and exits as it would without the warning, so dropping the new item (or the old one) is a reader's call. `backlog.py find WORD...` lists the open items whose title, goal or external ids (`external`, the item file) hold every word (case-insensitive), each followed by its parent chain, and exits 1 with one line when none match; `backlog.py tree --open` leaves out done and dropped items.

`set` and `gate add` each write the item only when the result raises no error `check` would not have raised before; they refuse `status`, `claimed_by`, `evidence`, the identity fields (`id`, `kind`), a done item's `goal`, `repro`, `checks` and `touches`, a `repro` or `severity` on an item that is not a bug, and every field it does not name, exit 2 (a `--repro` that passes now or fails for its own error exits 1, as `new bug` refuses it, except that a bug reopened after its fix landed takes one that passes now, as `reopen` below says) with the rule and the file unchanged, and the same command run again changes nothing.

Two more commands write `status`: `backlog.py move ID --sprint SP|none` sets a story's or bug's sprint and writes the status that sprint's state gives (`todo` in an active sprint, `draft` in a planned one or in none), and its draft and todo tasks and subtasks follow; `backlog.py reopen ID --why TEXT` takes a done item back to work (evidence and `claimed_by` cleared, `todo`, or `draft` while its sprint is planned). `move` refuses, exit 2 and the files unchanged, a task, subtask or review story (a task follows its story), a `doing`, `done` or `dropped` item or one with a `doing` task (release or reopen it first), a sprint that does not exist, an item without `touches` into an active sprint (as `start` requires), and any result `check` would flag; a second run changes nothing. `reopen` refuses every status but `done` (a draft, todo or doing item is open already, a dropped one is not reopened: file a new item), a blank `--why` and any result `check` would flag but one: a touch of the item's own that names a path git history has and the tree lacks, which `check` does not flag while the item is done, so reopening reveals it rather than adds it. `reopen` prints each such touch; keep one the item's own work commits changed (`done` refuses those commits as outside touches without it) and repoint only the checks with `set ID --check`, dropping with `set ID --touch` only a touch no work commit of the item changed, before `done` runs again (a gone path in a repro or check is a warning, which refuses nothing). `reopen` keeps the done file under `refs/kb-reopened/ID` (sprint close and `drop` outside a sprint delete each such ref whose item file no longer exists, so the clone keeps none of a removed item), and a bug that was done (that ref, or a commit of its file with an `evidence` key) takes `set ID --repro` with a repro that passes now, since its fix has landed and `done` reruns the repro and needs it to pass; a bug never done still refuses one. The reason is printed and never written to the item, since an item describes the present; the commit message carries it.

## Status and readiness

Only `draft`, `todo`, `doing`, `done` and `dropped` are stored. Whether an item is ready or waiting is computed on every call, never stored, so it cannot go stale. `backlog.py show ID` prints what an item waits on. An item is ready when all of these hold:
- it is `todo` (or `doing`, claimed by you);
- its sprint is active (`/kb-item` may take an item outside any sprint: `next --any`, but its work lands only once it is in a started sprint, Git below);
- every `depends_on` item of it or an ancestor is `done`;
- no blocking gate on it or an ancestor is unanswered;
- every trigger on it or an ancestor has fired;
- it has no open children;
- if it is the review story, every other item of its sprint is done or dropped.

GitLab's status categories match these states: Triage for `draft`, To do, In progress for `doing`, Done, and Canceled for `dropped`. Only Done and Canceled close an item (`gitlab/work-items-planning.md`, DOC S-il7kjbdz).

`python3 _tools/backlog.py next` prints the first ready item. The order is:
1. `S1` bugs;
2. then the `priority` and `rank` of the story or bug on top;
3. then the item's own `rank`.

**Knowledge state.** `show`, `next` and `horizon` run `pack` in process (no network, no model) on each `ask` and each `ref` of an item's `knowledge` (The item file) and print one state for each:
- `sufficient`: coverage `good` with no `check:` line (a `good` with one is `partial`);
- `partial`: coverage `weak`;
- `unknown`: coverage `none`, or a ref the kb does not hold;
- `stale`: a fact key no longer found in its file, or a source the pack cites has `superseded_by` set in `_sources.csv`;
- `conflicting`: the lead article (for a source ref, that source) has an open `_conflicts.md` entry: one that no `Resolved <date>`, `Superseded <date>` or `Reviewed <date>, not a source disagreement` note closes (`Reviewed <date>, still open` leaves it open).

`stale` wins over `conflicting`, which wins over coverage. There is no other state. The state is computed on every call, never stored, and never changes readiness; `horizon --hook` runs no pack, and an item without `knowledge` costs nothing.

## Priority and severity

Priority says when an item is scheduled; severity says how much a bug hurts. They are separate axes, as in GitLab's triage (`gitlab/work-items-planning.md`, DOC S-25zwwcdx).

| priority | means |
|---|---|
| `P1` | next: it goes into the running sprint or the next one |
| `P2` | planned: the next few sprints |
| `P3` | wanted, no date |

| severity | in this project | example |
|---|---|---|
| `S1` | a wrong answer served as `good`, private data in a public root or the query-log store, a broken gate or CI for everyone, lost kb content | the leak scan misses a tenant id |
| `S2` | a tool, hook or skill fails, with a workaround or on one OS | `kb_ask.py` crashes on Windows paths |
| `S3` | wrong or stale output that misleads nobody for long: a doc that disagrees with its code, a weak verdict that should be good | `tools.md` names a removed flag |
| `S4` | cosmetic | a typo in a docstring |

An `S1` bug joins the active sprint when it is filed and goes to the front of `next`. It never waits for the next sprint.

## Dependencies, gates and triggers

- **`depends_on`**: the item is not ready until each named item is `done`. Dependencies are inherited, as gates and triggers are: a task or subtask also waits on each undone `depends_on` item of every story, bug or task above it (`show` names the ancestor it comes through), so `next`, `ready` and `horizon` never offer work under a story that is not free to start, and `horizon` places it after that dependency on the critical path. `claim ID --by X` accepts an item whose only undone dependencies are `doing` and claimed by X, so a `depends_on` that orders two items sharing a file does not stop the one session working both in order (another session's claim still waits). `check` rejects a cycle and a dependency on a dropped item. `drop` refuses an item that an item not dropped depends on, and removes the dropped item's id from the `depends_on` of dropped items, so a chain dropped dependants first leaves none. GitLab's equivalent is **is blocked by** (`gitlab/work-items-planning.md`, DOC S-evjlv5hf).
- **`relates_to`**: information only.
- **Gates** are questions only the operator can settle. Each gate records its question, its options and a recommendation.
  - `blocking`: the item, and every item under or after it, waits until the operator answers: `backlog.py answer ID GATE --answer TEXT --by operator`. These are always blocking:
    - a push anywhere but the integration `main`, a `code/<id>` branch or a publish;
    - deleting kb content or history;
    - secrets and credentials;
    - the query log's mode, redaction or what it sends to the API;
    - a rule in `AGENTS.md`;
    - a sprint's start, which only the operator answers (`answer SP start --answer approve --by operator`).
  - Every gate has a class, which says who may answer it; a gate of class `secrets`, `push` or `agents-rule` is always blocking and only the operator answers it: Gate classes, below.
  - Rule-guarding work: a choice the goal leaves open on an item touching an `agents-rule` path is a blocking operator gate, added and asked before any code is written, never settled by the worker and held after the work; a provisional answer about a shared map or naming rule is put to the operator when it is recorded (`/kb-item`). `/kb-sprint plan` lists each committed item whose touches are rule-guarding before the start gate is asked, and asks each choice its goal leaves open as a blocking gate then, not after the code.
  - `provisional`: the agent goes on with the recommendation (`answer ID GATE --provisional`, recorded as `by: agent`). The sprint's review story cannot finish until the operator confirms each such answer (`--confirm --by operator`; `--confirm` with no `--by` or with `--by agent` exits 2, the gate unchanged) or changes it; a changed answer becomes a task or a bug. A delegate confirms one only under the operator's grant: the operator writes `set SP --delegate NAME --by operator` on the sprint (a grant `set` refuses without `--by operator`, recorded as `{name, by: operator}`), and then `answer ID GATE --confirm --by delegate:NAME` is accepted for that sprint's items and recorded as `by: delegate:NAME`; with no such grant (none, another name, or one an agent wrote), for a blocking gate, or for a gate of a class only the operator answers (`secrets`, `push`, `agents-rule`), it is refused as before, and a delegate never answers a gate itself.
- **Triggers** hold an item until something outside the repository happens, such as a Claude Code release or a spec change. A session that sees it happen runs `backlog.py fire ID`.
- **Escalation.** An agent escalates a decision it cannot make itself: it records a gate with its recommendation (`backlog.py gate add ID --question Q --option O --option O --recommendation R`; `--do OPTION=CMD|ID` gives an option its `do` field, the argv that carries it out or the id of the item whose work adds that command, and `check` warns, once for each option, of an option of an unanswered blocking gate with none, so one option's `do` silences no other and an operator's answer never waits on a command nobody planned; a gate about a capped file, `AGENTS.md` or `README.md`, is refused unless each option states the file's measured size after it, `N bytes` from `wc -c`, so the operator is asked once) and moves on to the next ready item. In an interactive session it also asks the operator at once (AskUserQuestion) with the same options. A choice an item's goal leaves open is a `provisional` gate (`gate add ID --kind provisional ...`) that the agent answers at once (`answer ID GATE --provisional`) and commits with the work, never only a line in its report: a sprint lands an item only once each of its gates is answered or provisional, and the review has the operator confirm each provisional answer (Running a sprint, below). It answers SP-ufr3qnff, where a choice a worker named only in its report landed unasked and came back as a bug.

## Gate classes

Every gate has a class, one of `secrets`, `push`, `start`, `querylog`, `agents-rule`, `delete` or `design`, from the most restricted to the least: `_tools/bl_authority.py` derives it from the item's `touches` (`_tools/kbgit.py`, `_tools/kbpublic.py`, `_tools/kg_*`, `_tools/kblane.py`, `.gitlab-ci.yml`, `.github/`, `.githooks/` give `push`; `kb/_querylog/` `querylog`; `AGENTS.md`, `CLAUDE.md`, `.claude/agents/`, `.claude/skills/`, `.claude/hooks/`, `.claude/settings.json`, `.claude/settings.local.json`, `.claude-plugin/` and the code that guards the gate classes, the `bl_` modules (`_tools/bl_`, every `_tools/bl_*.py`), `kb_hook.py`, `kbdecide.py`, `backlog.py`, `kbpy`, and the test runner the tests run through, `_tools/tests.py` and `_tools/conftest.py`, `agents-rule`, so a sprint never approves a change to its own guards or to the code its checks execute; a path naming a secret, credential, password, token or key `secrets`, the word token anywhere but in the file name of a Markdown doc (`api.token`, `tokens.json` and `tokens/` are secrets, `kb/_self/token-efficiency.md` is not); a glob that matches one of these paths counts, `_tools/bl_*.py` included) and from the gate's id and question (`start`, query log, redaction, a rule, deleting, pushing, publishing, uploading, deploying, a merge request or GitLab, secrets, a PAT, ssh, a passphrase or a bearer token), the strictest of them, `design` when none. A touch is read lower-case with a leading `./` and a trailing `/` dropped, and a directory touch (`_tools/`, `.claude`, `.`) names every path under it; `_tools/kbpublic.py` gives `push` and `.claude/hooks/` `agents-rule`; the words origin, mirror, release (word-bounded, with their endings), public repository give `push` and `.env`, rotate keys `secrets`; the words of a gate's `do` and `host_check` commands count as its text; a sprint's start gate is classed over the touches of its items that are not dropped (`bl_authority.sprint_scope`). `gate add` stores the class, derived over the whole gate (its `do` and `host_check` words too), and prints it with what set it, each touch path and word of the gate's text that names that class (`class agents-rule (matched 'rule')`; `bl_authority.class_reasons`, which `derived_class` reads, so the two never diverge), so a misclass shows and is filed as a bug: a gate is never reworded to change its class; the class in force is the stricter of the stored one and the derived one, so a lower class written into an item file changes nothing and `check` reports it (an unknown class too). A gate is answered by the operator (`--by operator`) or by an agent (`--by agent`, `--provisional`); `answer --record --by operator` keeps the operator's answer as an active decision of kb/_self. The operator reads the decisions with `kbdecide.py list --root _self --status active`; the autopilot decisions kept from before its retirement are ratified or reverted with `kbdecide.py ratify` and `revert` (`kb/_self/code.md`). `set --touch` or `--add-touch` (and `--clear touches`) re-derives the class of every gate of the item and stores the stricter one, an unanswered provisional gate that becomes one of the classes below turning blocking, so widened touches re-class a gate already written. A gate whose derived class is `secrets`, `push` or `agents-rule` (`bl_authority.OPERATOR_CLASSES`) is always blocking: `gate add` makes it blocking whatever `--kind` says and prints that it did, `answer --provisional`, `answer --confirm` and an agent's `--answer` on it are refused naming the class (the item unchanged) unless `--by operator` is given, and `check` reports such a gate that is provisional or that an agent answered as an error on an open item, and as a warning (`answered by ... in a refused class: the operator re-confirms`) when the item is done or dropped and an agent answered it, since `answer` stays strict. `check` also reports a gate whose stored class is lower than the derived one (an agent edited it down), unless the operator answered the gate, since the class guarded nothing after that; the derivation's planted failures are the tests of `_tools/test_authority.py`.

`--record`, added to `answer ID GATE --answer TEXT --by operator`, also keeps the operator's answer as an active decision of `kb/_self/_decisions.csv` (`kbdecide.py record`; `kb/_self/content-rules.md`, Decisions): its maker is the `operator` role of the central register, its source names the item and the gate, its context is `item:<ID>` and its id also takes the gate (`kbdecide.py record --gate`), so two gates answered with the same text are two decisions, and sprint close (which deletes the item) leaves it active, since a done item does not invalidate it. An answer of the agent is never a decision: with `--provisional`, `--confirm` or a `--by` other than `operator` it exits 2 and writes nothing (`--by` takes `operator` or `agent`, and `--record` only `operator`).

## The horizon

`python3 _tools/backlog.py horizon` shows how far each active sprint can go without the operator:
- how many items are done, and how many are still reachable;
- which items wait on which gate or trigger (with its question and recommendation);
- the next item;
- the critical path, with the number of items that can run in parallel at each step.

For a planned sprint (`horizon --sprint SP`), an unanswered start gate, or one answered with anything but an approval (`approve`, `approved`, `yes`), is the operator's question, and every item waits on it. Once the operator approved it, the sprint is reported as approved, not started, with `backlog.py start SP` as the step that remains, and its items are counted as waiting on that start, not on the operator or a trigger. `horizon` and its hook also name each approved planned sprint while other sprints are active, on a line of its own before theirs (approved, not started, with `python3 _tools/backlog.py start SP` as its next step), so no approval waits unseen behind a running sprint. Several approved sprints have no order between them: `start SP` refuses none for another's being approved or active, so the next to start is the one whose `backlog.py start SP` is run.
An item whose `depends_on` (its own or an ancestor's) points to an undone item outside the sprint waits on it: `horizon --sprint SP` names each such dependency with where it stands (in no sprint, or in a sprint, `, not started` when that sprint is not active), and `start SP` warns, exit 0, of each one in no sprint or in a sprint not started, so the operator sees it before approving.
A `SessionStart` hook (`horizon --hook`) prints a short form of it, each active sprint's id, title, counts and next item id without its goal or critical path, plus what waits on a gate, a trigger or a start (with no active sprint, the planned ones, each approved one marked approved, not started with its `backlog.py start` command; beside active sprints, each approved planned one on the first line), at the start of every session in a clone except one `/clear` starts (matcher `startup|resume|compact|fork`). Its whole output stays under 1000 characters however many sprints are active: a title and a waiting cause are shortened on its lines, and the last lines give way to one naming how many were left out and `horizon`, which prints them all.

## Definition of done

Every item meets the shared minimum, the same bar for every item (`agents/agent-planning-and-done.md`, DOC S-2wwcyoa4):
- the gate in `kb/_self/maintaining.md` passes (it runs the suite);
- a new gate has one planted failure in the suite, within the ceiling in `_tools/tests_ceiling.json`, and nothing else needs a test;
- no new dependency; the tools stay standard library only;
- portability: files are read and written with `encoding="utf-8"` (and `newline="\n"` when writing), paths go through `pathlib`, and subprocesses take argument lists;
- `/kb-self` has run when `_tools/`, `.claude/`, `.claude-plugin/` or `.gitlab-ci.yml` changed;
- the commits carry their KB-* trailers and `KB-Work`, and went through `kbgit.py sync --push`.

Each item adds three parts of its own: the end state (`goal`), the commands that prove it (`checks`), and what must not change (`touches`). Scrum has no acceptance criteria (DER S-2wwcyoa4), so the checks are the item's part of the bar.

`python3 _tools/backlog.py done ID` is the only way to `done`. In short (each rule in full: What done refuses, below), it refuses while:
- the item waits on anything, or a file in scope has uncommitted changes;
- a work item has no `touches` of its own or under it;
- no commit with a `KB-Work` trailer naming the item (or a descendant) changes a file other than item files;
- a code-lane commit of the item is not on the integration `main` as last fetched: merge its `code/<id>` request, fetch, run `done` again;
- a commit of the item left a file outside its scope changed at `HEAD`;
- a check fails, or passed while doing nothing in this clone;
- a review story still has an agent's provisional answer.

When it succeeds it records the commit and each check's exit code and output digest in `evidence`. A bug is done when its `repro` passes as well: a command that fails before the fix and passes after it, a tool run on a planted input or a command with a match, and a test only when no log and no gate output can show the defect again. What let the bug through goes into the sprint's retrospective. `backlog.py goal ID` prints a `/goal` condition naming the same end state, checks and scope, so a transcript-only judge sees the proof (`agents/agent-planning-and-done.md`, DOC S-vp5onm7b), and under it each answered gate of the item's parent chain with its answer and who gave it, which a worker's brief must not contradict.

## What done refuses

`python3 _tools/backlog.py done ID` refuses when any of these hold:
- the item waits on anything;
- a review story: a check or bug repro of a done item of its sprint fails when run once more on the sprint's tip (`bl_land.rerun_done_checks`), named with its item, so an item whose check fails on main does not close with the sprint; one whose test run selects no test (`tests.py`'s exit 2 with its `collects no test` line, or pytest's own exit 5: a later change deleted the test it names) is printed as `gone` and not counted, since a done item's check or repro cannot be repointed to a run that passes; a gone check is found once per sprint: the rerun records it in its item's `evidence` (`gone`, committed with the review's done, or before its refusal), close's summary names it on the item's line, and the sprint's next landing prints it as found gone earlier and does not run it again;
- a file in scope has uncommitted changes (the checks run on `HEAD`);
- a work item (not an epic or a review story) has no `touches` of its own or under it: `start` requires a scope of every work item, and a story or bug filed with `--sprint` into an active sprint is `todo` at once without one, so `done` holds the same rule (`backlog.py set ID --touch GLOB`);
- the item has `touches` of its own and no commit reachable from `HEAD` carries a `KB-Work` trailer, as git reads trailers, naming the item or one of its descendants and changing a file other than item files (a claim or planning commit, which changes only `kb/_self/backlog/*.json`, is not the work; a story or bug whose tasks carried the work needs no commit of its own; a story flagged `goal_research` whose notes hold `No outside facts: <reason>`, at their start, on a line of their own or after a sentence's end, with a reason after the colon, needs none either, since there was nothing to write, while any other kind, or a story without the flag, is refused as before);
- a code-lane commit whose `KB-Work` trailer names the item or one of its descendants (lanes: `_tools/kblane.py`; a rename counts both its old and its new path, so moving a code path into a content path is a code-lane commit, as for `sync`; a commit that changes `.gitattributes` only between its `# pinned:start` and `# pinned:end` lines, which `kbgit.py fix` regenerates, is content, as `kblane.commit_paths` counts it) is not an ancestor of `refs/remotes/<integration>/main` as last fetched, or that ref does not exist: it names the commits and the merge requests `sync` opened for them (branch `code/<id>`, the one `kg_lane.lane_plan` names for the range `sync` pushes, as `land` does: the first `KB-Work` id of that range, which may be another item's); merge them, fetch, run `done` again. `done` does not fetch, and a content-lane commit never needs to be on the integration `main`;
- a commit whose `KB-Work` trailer names the item or one of its descendants left a file outside the scope (the item's `touches` with its descendants') changed at `HEAD` (a later revert clears that);
- a `kb/_self` doc (or `AGENTS.md`, `README.md`) that `kb/_self/map.csv` maps to a file those commits changed is older than that change, by `selfdoc.py stale --since <the merge base of HEAD and refs/remotes/<integration>/main>`, the range `land`'s step `stale` reads after its rebase (with no such ref or no common history, the parent of the item's oldest such commit): it names each doc and the item's files that moved past it (reason class `stale-docs`), before any check runs, so a worker's `done --dry-run` finds it rather than the landing. A doc edited in the range or named in a `Self-Reviewed:` trailer of a commit in it is up to date, as at the sync gate; another change's stale doc in the range is not the item's; a landed code item's commits are below the merge base at land's second pass, so they are not judged again;
- one of its checks fails;
- a check or a bug's repro passed while doing nothing in this clone, and no other passing check runs tests (`tests.py` or pytest) that did their work, unless the operator answered the item's `host-bound` gate `accept` (or an approval): its output carries a no-op marker (`bl_check.NOOP_MARKERS`: `no public remote`, `nothing published`, `no test can be affected` and the like) or a pytest summary where every selected test was skipped. BG-uqmjlqfl's repro, `kbgit.py publish --dry-run`, printed `no public remote; nothing published` and passed in a clone without a publish remote (SP-v5xagbyv). `done` warns of each such check, and of one that runs no test or tool code, which it does not refuse;
- a review story still has an agent's provisional answer.

Each refusal first appends an ops row `done.refused` with the item, the closed classes of what refused it and the names of the failed checks, never their text (`kb/_self/querylog.md`, Surfaces), so the rework a refusal costs can be split by its cause.

## Checks that prove an item

A check is a command that does its work in the clone: a tool run on a planted input, a command with a match, or `tests.py` or a `-k` selection of an existing test. A check need not be a test. The suite runs the lookup eval and `check.py` over the live kb. A check that runs a Python tool names `python3`; `done`, a bug's repro and `red-pipeline` run it with the interpreter that runs `backlog.py`, so a check proves the item on any host where the tool itself runs, a Windows Store `python3` alias or none on `PATH` included.

## Sprints

A sprint is a goal and the stories and bugs committed to it. It ends when its goal is met, not on a date. That departs from Scrum's fixed length but keeps the Sprint Goal as the one commitment (`agents/agent-planning-and-done.md`, DER S-2wwcyoa4).

3. **Run** (`/kb-sprint run`): work ready items in `next` order until the horizon shows nothing reachable. Then report what waits on whom.
4. **Review**: the review story depends on every other item of the sprint. Its work:
   - the operator confirms or changes each provisional answer;
   - `backlog.py cost --rework` runs for the sprint and for each of its stories and bugs, and its output goes to the reviewer and to the operator as retrospective input (what the work cost; the items with rework, the tokens from an item's first refused `done` on; where shared tokens stand out): it reports tokens only, no prices and no blame, and a figure with an unresolved id is incomplete (Cost of work, below); a cost read while the sessions that did the work are still open is provisional (the output says `open session figures` or `no figure yet`; the zeros beside them mean the open sessions are not distilled into sidecar lines yet, not no work: their usage rows are in the spool and the `open session figures` block prints them apart, and only `no figure yet` says the spool holds no usage row to read): the review says the figures are provisional, never reports those zeros as the sprint's cost, and close reruns `backlog.py cost --rework SP` once those sessions have closed, writing that rerun's figures into the retrospective, or says they are still provisional;
   - a sprint that changed what the query log writes runs distill once on a copy of the real spool in mode `local` (nothing pushed) and shows its run file, sidecars and `querylog.py check` on that store, so a sidecar no work ever delivered shows before the close (SP-fvztfmtm; `/kb-sprint review`, step 3);
   - a fresh-context reviewer (a headless Sonnet session by default, as Running a sprint says) reads the sprint's diff against each item's goal and reports only gaps that affect correctness or a goal (DOC S-o3v6ozch); its brief names each goal clause a check does not read; it runs in a git worktree of its own under `.claude/worktrees/`, never in the orchestrator's checkout, where the SessionStart intake hook files drafts that make a landing refuse a dirty tree (SP-vayhvwfy), and its launch names `--max-turns`, its working directory (that worktree) and its scratch directory `_cache/scratch/<id>/`, and says it is read-only; the whole `tests.py` runs only after the reviewer has returned, since a run beside its session took 21 s against the 20 s darwin ceiling (SP-rvslem3h);
   - a gap that is `S1` becomes a bug in this sprint; every other gap is parked: filed as a draft in no sprint, under its epic or none, with a link naming the review that found it (`backlog.py set ID --add-link 'parked: SP-... review'`), and it joins a sprint only as Plan says for a parked draft;
   - `backlog.py check` and `tests.py` pass, run as the story's checks.
5. **Retrospective**: from the sprint's evidence, list the process failures: refused `done`s, checks that passed on broken work, late gates, briefs that missed something, rules that got in the way, work that cost more than its size suggested (close's rerun of `backlog.py cost --rework SP` once the sprint's sessions have closed, never the review's provisional read; still `open session figures`: say the figures are provisional). The operator picks which to act on. Each accepted change is parked: a draft story in no sprint naming its failure (Changing this process, below), under its epic or none, with a `parked: SP-... close` link naming the close that found it; it joins a sprint only as Plan says for a parked draft. The findings go in the close commit's body, never into the docs.
6. **Close**: `backlog.py close SP` refuses while anything is open. Otherwise it deletes the sprint, its items and the epics they finished, drops their ids from every remaining item's `relates_to` and `depends_on` (a done dependency is satisfied; one on a dropped item stays for `check` to report) and the `do` entries of its gates that name them by id (an argv stays), removes its workers' leftovers in the clone it runs in (the sprint's clean `agent-*` worktrees, its `work/<id>` branches and the empty `worktree-agent-*` branches; never `--force`, a locked, dirty or process-holding worktree, a branch with a commit `origin/main` lacks or a `worktree-agent-<x>` branch whose `agent-<x>` worktree is another sprint's live worker is kept and printed as `close: kept ...: reason`; none of it with `--summary`), and the commit carries `KB-Work: SP-...`. `close SP --summary` only prints, after its item lines, for a sprint goal of more than one clause (split at `; ` and `, and `) or one list of statements joined by `, ` and ` and `, a `goal clauses:` block naming each clause with the done item whose title and goal hold at least half its words (a clause no single item carries is split at `, ` and ` and ` into its parts, each named with its own item), or `unmet` and the open item that carries it now (one moved out mid-sprint) or none, and one line per item close would delete (tasks, subtasks, the review, dropped items and the finished epics included): its id, title, kind, status and the commit `done` recorded in `evidence`, or `no evidence commit` for a dropped one; it changes nothing, so the retrospective is written before the close (with `--commit` it is refused). That list is the close commit's body (`close SP --commit` writes it there); only the retrospective's findings are written by hand. The git history keeps all of it (The item file, above). Leftovers close did not reach (another sprint's merged `work/ID` branches, a clone's old `orch/` branches, clean agent worktrees) go with `backlog.py tidy`, which lists them with why each other one stays and with `--apply` removes them the same way (`kb/_self/tools.md`).

Several sprints may be active at once. Each has its own horizon.

## Working on items

- **One item** (`/kb-item ID`, or `/kb-item` for `next --any`; one session works one item, and the next item starts in a fresh session):
  1. claim it, from the session's own worktree (each session works in its own git worktree from its first command (`git worktree add`), never a checkout another session works in: `claim` records the claims made in a working tree in its own git dir and refuses (exit 1, naming the other session) a claim by a second session while one of them is still doing there (a session is `CLAUDE_CODE_SESSION_ID`, which Claude Code sets in every Bash subprocess, else the claimer's `--by`; so one session, an orchestrator, claims for several subagent names in its own checkout)): `backlog.py claim ID --by <session> --commit --trailer 'Co-Authored-By: ...'`, which commits the item file on its own with `KB-Work: ID` (a backlog-planning commit; Git, below) before any work commit, since `check-trailers` reads the item as each commit has it;
  2. print its `/goal` condition;
  3. do the work within `touches`, and commit with `KB-Work: ID`; run `/kb-verify`; the rules for the work come from the sets and questions of `python3 _tools/rag.py pack --root _self` (`--set kb-item:STEP` for a step's tested questions, a question in quotes for any other rule), and the item's brief from `python3 _tools/rag.py pack --root _self --item ID --budget 600`, not from reading sections;
  4. land it with `backlog.py land ID [--branch B] --trailer '...'` (the branch defaults to `work/ID`), one command for the steps of Landing, below, which stops at the first failing one and names it (`land stopped at step <step>`, exit 1). A landing is a long command: start it in the background with the Bash tool's longest `timeout` (7200000 ms), since a foreground command is lost at the 10-minute limit. Fix the cause and run it again:
     - a content-only item, or one whose code-lane commits (`_tools/kblane.py`) are on the integration `main` already: `backlog.py done ID --commit` with the `--trailer` lines, which commits the item file; the stale check, the lookup eval and the lint once when the landing changes `_tools/`, else the lint on the changed articles' paths when it changes a kb root's `.md` files; `kbgit.py sync --push`, straight to `main`;
     - an item with a code-lane commit not yet on the integration `main` (`done` would refuse it): step `checks`, which runs the item's checks and a bug's repro as `done` does and stops there when one fails, so no `code/<id>` request that would auto-merge is pushed for an item whose proof fails (a check whose test run selects nothing is named as malformed), then those three when `_tools/` changed, then `kbgit.py sync --push`, which sends a `code/<id>` merge request; `main` does not move and the item is not done. Once the request has merged, the same `land` rebases onto the merged `main`, where the code commits are, and finishes as a content item does; its range is the item file alone, so those checks do not run twice.
- **A subagent's item** (a worker that `/kb-sprint run` starts in a worktree; the orchestrator's side: Running a sprint, below):
  - **One suite**, stated here once (`kb-worker.md`, `kb-sprint` and `kb-item` refer to it): a worker may run `python3 _tools/tests.py`, which takes the host test lock and waits its turn, or a selection (`tests.py -k NAME`), and its item's own `checks`. A sprint worker running `/kb-verify` skips its `tests.py --changed` step (step 5, which names the exception, as `.claude/agents/kb-worker.md` rule 3 does): parallel runs of it load the host into false timeouts (SP-flkl5gom, where two workers ran it through `/kb-verify` against their brief). The sync gate runs `tests.py --changed origin/main` at each landing; `backlog.py land` runs the item's checks, the stale check and, for a landing that changes `_tools/`, the lookup eval and the lint around it. The review story's checks are `backlog.py check` and `tests.py`.
  - A subagent in a worktree cannot run the lookup eval as a Bash command. Claude Code's worktree isolation check, not a repo or plugin hook and not a permission rule, refuses any Bash command with the word `eval` in it, even `grep eval`, as one that runs a string through `eval`. The subagent runs its pytest wrapper instead: `python3 _tools/tests.py -k "test_lookup_ and passes"` (which passes when the eval exits 0). A command inside a script file the subagent runs passes the check, and so does an item check that `backlog.py done` runs as a subprocess.
  - A subagent that finds a defect outside its item files a bug and does not fix it. A doc that needs an edit outside its `touches` stops its work with a report; its `Self-Reviewed:` trailer names only docs read and found still correct (SP-jtfo4ael, where two workers named docs that still needed an edit to clear the gate).
  - A worker whose item changes how a `bench_*` module or `agent_bench.py` counts or prices a run runs the item's real probe (Sprints, Plan, above) before its last commit, with the cap and command the goal names, and keeps the stream under `_cache/`. Its notes get the stream's path and the billed and list costs (`backlog.py set ID --add-notes`), and the report names them. A probe whose list cost is more than 20% from the billed cost is a defect of the change, fixed before the commit, not a figure to report; a probe the goal does not name, or one that would pass its cap, stops the work with a blocking gate, and fake-stream tests alone never land such a change.
  - A stacked item, whose base holds another item's commits not yet landed, names in its own commit's `Self-Reviewed` trailer every doc `selfdoc.py stale --since <the item's base>` lists for its change, not only the stack's: the item below lands first, and its trailer then stops covering the ones above (SP-x2pvljz6, where two stacked commits were amended at landing for `kb/_self/code.md`).
- **A bug a worker files** with `backlog.py new bug` is handed back by committing its new item file alone, in a commit of its own on `work/<id>` whose `KB-Work` names the new bug, and by naming the bug in the report, so no untracked item file makes `land` refuse the worktree; `done`'s scope allows it, since `kb/_self/backlog/**` is always in scope and a commit of item files only is no work commit.
- **A bug filed while landing** (by the gate, a review or a refused `done`) is filed with `--sprint SP`, an active sprint's id (`backlog.py new bug` sets no sprint without it; a bug filed without one is draft, and `backlog.py move ID --sprint SP` makes it `todo` there, since `set --sprint` refuses a draft item into an active sprint), and committed on its own first, a backlog-planning commit with only its item file, then claimed and committed as in step 1 above, before the commit that fixes it: `check-trailers` refuses a `KB-Work` id whose item file is in neither the commit nor its parent, one that is not claimed, and one not in a started sprint.
- **An item whose touches are item files only** (a fix of planning data, such as an epic's text) can never pass `done`, which needs a `KB-Work` commit that changes a file other than item files: land the fix as a backlog-planning commit, then close the item with `backlog.py drop ID --why` naming the fixing commit. `backlog.py new` and `check` warn of an open story, task, subtask or bug whose scope is item files only and name this route, so no worker claims an item it cannot finish (BG-plvwei5i's fix of an epic's text was refused by `done`).
- **Finding a defect**: `backlog.py new bug --title T --severity S --repro "CMD" --goal G`. The repro command must fail now, and because of the defect. `new` refuses one that passes. It also refuses one that fails for its own error, naming the cause but not dumping the output:
  - it cannot start: not found, exit 127 or 9009, or a shell's or `python -m`'s lone not-found message, unless that message names a tool inside a wrapper the repro started (a shell script or hook that ran and could not find `jq`), which may be the defect; every command word of the repro's own `-c` string, split at `&&`, `||`, `;` and `|`, is its own, so `sh -c 'cd /tmp && jq .'` missing `jq` cannot start;
  - Python cannot compile its own code: a `SyntaxError` in the `-c` string or in a script it names that git does not track (python's options such as `-u` and `-X dev`, and a shell's `-c` string, are read for the script they run; a `SyntaxError` in a repository tool the repro runs, such as a 3.12-only construct on 3.11, is a genuine reproduction), such as a Windows path like `kb\public\x.md` inside a Python string, or statements whose newlines `--repro`'s split lost (use `/` and `;`, or a script);
  - its own code is wrong: the traceback's last exception, raised in the `-c` string or an untracked script, is a `ModuleNotFoundError`, an `ImportError`, a module's missing attribute, a `TypeError` (but not one of subscripting, `len()` or iterating a `None` the code under test returned), `NameError` or `UnboundLocalError`, or `No module named 'pytest'` from a test module it imports (select it with -k); raised inside the code under test, they are a genuine reproduction;
  - the tool it runs rejects its arguments: argparse's exit 2 with `usage:` and `error:`;
  - a test run selected no tests: `tests.py`'s exit 2 with its `collects no test` line, pytest's `no tests ran`, or exit 5 with everything deselected, such as a `-k` that matches nothing.

  A repro runs the behaviour it names when it can: a test that plants the defect, or the tool run on a planted input. One that only matches text in a file proves the text, not the behaviour: BG-qtphqxt2's rejected the literal `>&2`, which the fix met by writing `>& 2`; BG-g6qpxe5x's was a regex over a test's text; BG-rrht7uts's grepped `_tools/` for `worktrees` and passed on a fix that did not work. `new` refuses such a repro (a `grep`, `git grep`, `rg`, `findstr` or `Select-String`, `awk` or `sed` run over a file, a shell `-c` of nothing but greps, or of text filters such as `cat` or `head` feeding a grep, `awk` or `sed` or testing the output of one (`test -z "$(grep ...)"`), or a `python -c` that reads a file and imports only text modules such as `re`, `json` and `pathlib`; exit 2, nothing written) unless `--repro-reason TEXT` states why the behaviour cannot run, such as a defect that is a doc's wording, kept as the item's `repro_reason`. `check` warns, counted as `warnings=` without failing, of an open bug whose repro is such a one with no `repro_reason`, naming any `_tools/` source file it reads for a string. A script repro (`python3 repro.py`) is not judged.

  A failed assertion, a traceback from the code under test, or a tool that prints a finding and exits 1 counts as a reproduction. `new` warns, and still files the item, of a repro or check that runs no test or tool code (`true`, `echo`, a `python -c` that only passes, prints or exits 0), of a `python -c` repro or check that runs a tool with `subprocess` and reads its stdout but never its `returncode` (nor `check=True`), which a crash printing nothing passes, of a failing repro whose output says it did nothing in this clone (below), and of a bug whose repro runs a tool against this clone's state with no `--check` that runs tests: such a repro can pass at `done` without the fix, so name a test selection that plants the defect. The repro that `red-pipeline` builds is its own command and does not go through this check.

## Git

- Work lands through `python3 _tools/kbgit.py sync --push`, as for every change, by lane (`kb/_self/git.md`, The regime by role): content-only work (backlog items, `kb/_self/*.md`, kb roots) goes to the integration `main`; work with a code-lane commit goes as a `code/<id>` merge request, and the item is done once that request has merged and the commits are on the fetched integration `main`.
- Every commit that works on an item ends with `KB-Work: <id>[, <id>]`, one line, in the message's last paragraph together with the other trailers (`Co-Authored-By` and the KB-* trailers the hook adds after them). Git reads trailers only in that paragraph: a `KB-Work` line in an earlier one, or with a blank line before `Co-Authored-By`, is no trailer, and `done` finds no commit for the item. An item with `external` ids also has one `KB-Ref: <ref>` trailer per id on its `claim` and `done` commits (`--commit`), after `KB-Work` and before the session's own trailers: the ref is the tracker's `ref` template filled in (by default the id, `PROJ-123`; `#12` for a tracker whose template is `#{id}`), so a Jira key anywhere in the message links the commit to the issue and a trailer line with no `#command` triggers no smart commit action (`public/gitlab/jira-issue-keys-in-commits.md`). A `KB-Ref` trailer never closes a GitLab issue: a closing pattern needs a keyword before the reference (`public/gitlab/issue-closing-patterns.md`). `python3 _tools/kbgit.py check-trailers` flags a second line, or an id whose item file is in neither the commit nor its parent, and, on a commit not yet on `origin/main`, a `KB-Work` line git does not read as a trailer (the commit-msg hook warns of it when the commit is made).
- Work lands only for a claimed item of a started sprint. On a commit not yet on `origin/main`, `check-trailers` refuses a `KB-Work` id whose item, as the commit has it, is not `doing` or `done` (not claimed), or whose sprint is not active (not in a started sprint). The pre-push hook and `sync`'s gate run it, so such work is not pushed; the commit-msg hook warns when the commit is made. Exempt: a backlog-planning commit (it changes only item files: new items, claims, gates, a sprint's plan, start or close), and the sprint and review items themselves. A claimed research item of a planned sprint (Sprints, above; its own `touches` read at the commit) passes on a commit that changes only kb content (paths inside named kb roots) and item files, and is refused on one that changes anything else, such as `_tools/`, `.claude/`, `.githooks/`, CI or `kb/_self/` docs. An item outside any sprint joins a started sprint before its work lands. Commits already on `origin/main` are history and stay as they are.
- Changing an item's JSON (claim, set, gate add, gate answers, done) goes in the same commit as the work, or in its own commit with the same trailer.
- `--commit` on `claim`, `done`, `new`, `start` and `close` makes that commit: only the item files the command wrote or deleted (`git commit --only`: changes staged before it stay staged and out of it), the subject `chore(backlog): claim|done|file|start|close ID "title"`, and a last paragraph of `KB-Work: <ids>` (the item; a new sprint and its review story) followed by the session's own trailers, each passed as `--trailer 'KEY: VALUE'` (a `KB-*` key is refused: the command writes `KB-Work` and `KB-Ref` and the hook the others). `check-trailers` passes on it; it flags a `KB-Ref` value of more than one word, or a `KB-Ref` line git does not read as a trailer, as it does a `KB-Work` one.

## Landing

`backlog.py land` (Working on items, step 4) runs these steps: `clean tree` (it refuses uncommitted changes; but when the tree's only change is untracked `kb/_self/backlog/*.json` intake drafts that no commit of `HEAD` names and whose links carry a `fingerprint` and a `detector`, as the checkout's own SessionStart hook files them, `land` first moves them to `_cache/intake-drafts/<name of the checkout>/` of the clone `land` runs in and says so, `bl_land.own_checkout_drafts`, and they stay there when it stops at a later step; any other untracked or modified file, or an untracked item that is no filed draft, refuses the tree and nothing is moved), `branch` (missing, or checked out in another worktree; a finished worker's worktree under the `.claude/worktrees/` of the clone `land` runs in (`git rev-parse --show-toplevel` there, so a linked worktree's workers sit under its own directory, not the main checkout's) on the item's own `work/<id>` branch (or detached at its tip: a worker that detached to free the branch) with no uncommitted changes (but untracked `kb/_self/backlog/*.json` intake drafts that no commit of the branch names, which `land` moves to `_cache/intake-drafts/<worktree name>/` of the clone it runs in, the gitignored scratch area, and says so, `bl_land.intake_drafts`; any other untracked or modified file still refuses the worktree and nothing is moved), that Claude Code left locked (its lock reason starting `claude agent`) or that is unlocked and named `agent-*` or by the item id, never the worktree `land` runs in, is unlocked if locked and removed instead, never with `--force`, and `land` says so; once the item has landed, `land` deletes its `work/<id>` branch and the removed worktree's `worktree-agent-*` branch when `git cherry` shows every commit on the integration `main`, since agents' shells may not run `git branch -D`; while a process still runs in it, its working directory there, `land` refuses instead and names each pid and command: `bl_land.live_processes` reads `/proc/<pid>/cwd` on Linux and `lsof -d cwd` on other POSIX hosts, and where neither is there, or on Windows, which exposes no process's working directory to the standard library, `bl_land.held_by_process` renames the worktree to a sibling name and back first: Windows locks a running process's current directory against a rename, so a refused rename refuses the landing, naming the error, with the worktree still registered and every file in place (BG-nlp5aat5, where the orchestrator's own working directory in the worktree left it half deleted and unregistered); a rename that succeeds says it could not check and removes the worktree as before), `fetch`, `rebase` (it fetches the integration remote's `main` and rebases the branch on it, `origin/main` as fetched, never local `main`: an orchestrator in its own clone or worktree cannot move a `main` another worktree has checked out, and it falls behind; a conflict aborts the rebase, leaving nothing changed, and the branch is rebased by hand on `origin/main` after `git fetch`; a claim commit of the item or its descendants that the starting checkout has and the branch lacks, made after the branch was cut or never pushed, is cherry-picked under the branch's own commits first, so `main` gets claim, then work, and `check-trailers` finds the claim; a claim that does not apply stops the step), `done` (the done commit is also kept as `refs/land/<id>` until the landing is verified: a run that finds the branch without it, as after a failed push, puts it back instead of running the checks again), `scope` (a code-lane item only: done's scope rule over the item's commits, before the merge request is pushed, so a file outside its touches stops it here, not after the merge), `checks` (a code-lane item only: its checks and a bug's repro run before the merge request is pushed), `stale` (for a landing that changes `_tools/`: `selfdoc.py stale --since` the integration main over the rebased range, before the lookup eval, so a missing `Self-Reviewed` trailer fails in seconds; a stacked item whose lower item has landed is caught the same way), `rag.py eval`, `lint` (`.claude/skills/kb-verify/lint.py`; with the eval for a landing that changes `_tools/`, else alone on the qualified paths of the `.md` files the landing changes under a kb root, `bl_land.changed_articles`, so a pointerless CODE tag a content commit adds stops that landing at `lint`, not the next code landing), `kbgit.py sync --push` and, for an item that lands on `main`, `verify` (it fetches `main` again and requires the item's done commit to be an ancestor of it and the item's file there to read done; a sync that exits 0 without pushing stops here, and `land` never prints `landed` without it). For an item whose scope holds external ids, a code item's `land` then sets the description of its open merge request on the integration remote's forge project (`bl_forge.set_description`: a `glab api` PUT, the gh arm refuses and is said; after `sync --push` has opened it by push options, and again on a later pass that finds it waiting, each pass reading the request once with `bl_land.read_code_request` and the description and the stuck line below using that one read) to what it holds with a block headed `Tracker references (KB-Ref):` and one `- TRACKER REF: URL` line per id of the item and its descendants, in place of a block of its own from an earlier run; the block holds no closing or trigger keyword, so merging the request closes no issue, and a request it cannot change is said and never fails the landing, while one it cannot read, a remote that names no forge project or a CLI not signed in adds nothing (`bl_land.describe_merge_request`). Each step and each end is an ops row (`land.step`, `land.end`; `kb/_self/tools.md`), and a landing whose item or descendants have no line in the committed work sidecars (a line names no session) says which of three it is (`bl_land.ops_work_rows`, read only, exit unchanged): `warning: <id> landed with no work rows on <remote>/main (undelivered): ...` when a work sidecar naming the item sits in the local store beside the spool of this host or of the main worktree of the clone's git common dir (`_cache/querylog/store`, written by distill, delivered by `querylog.py apply --push`) and neither the checkout nor the integration main holds it, naming the store a session end left unpushed; else, when a spool holds a worker's row of the item (a `branch` row, which opens a headless worker's window, or an `agent-start` or `agent-stop` row, which a worker started with the Agent tool writes inside the orchestrator's session; the orchestrator's own `claim`, `done` and `release` rows do not count, since it claims every item it delegates), no warning, only `land: <id>'s work rows are late: session ... still open | closed and not distilled in <spool>` (its figures reach `backlog.py cost` once the session has ended and distill has run); else `warning: <id> landed with no work rows (missing): ... (a worker started without the capture hooks?)`. The rebase switches the checkout to the branch; every run and every stop after it switches back to the branch `land` started on (or its commit, from a detached `HEAD`), so the orchestrator's next `claim --commit` lands on its own branch and not in the landed item's merge request. After a run that pushed (a landing, or a code item's merge request) and switched back, `land` fast-forwards that checkout with `git merge --ff-only` to the `main` it fetched, when it is on a branch whose `@{upstream}` is the integration `main` and has no uncommitted changes, and says so (`land: fast-forwarded <branch> N commit(s) to <remote>/main`), so the orchestrator's next claim starts from the pushed `main` and needs no manual fast-forward; a detached `HEAD`, a branch with another upstream or none, a dirty tree or a diverged branch is left alone, a dirty or diverged one said with its reason (`land: left <branch> N commit(s) behind ...`), and a refusal never changes `land`'s exit status. With `--wait-merge SECONDS` a code item's first pass is followed in the same run by a bounded wait for its merge request, read from git (a fetch of the integration `main` every 60 s until the item's code commits are on it, not the forge CLI), then the second pass; a wait that runs out stops at step `wait-merge` naming the `code/<id>` branch, so no session writes a poll loop of its own. A resolved conflict in a `_tools/*.py` file is checked to parse and to keep every definition either side added (a top-level function, class or assigned name, a class's method or attribute), by `python3 _tools/kbgit.py lost-definitions FILE` before `git add`, before `land` runs again (`/kb-git-sync`, `kb/_self/git.md`).

For an item whose `repos` name repositories of a multi-repository workspace (a `repositories` map in `backlog.json`, Project settings), `land` has two steps of its own after `clean tree` and `branch`'s check that the local `work/<id>` exists, before the workspace's own worker worktree is released (`bl_land.land_repositories`): `requests` reads the merge request whose title starts `<id>:` of each repository of `repos`, once for the pass, through `bl_forge` run in that repository's checkout (its own `origin` names its project, so `forge_project` stays empty in such a workspace: it names one project for every read), and stops, naming every repository and its state (`opened`, `closed`, `none` for no request, or why the read failed), when one is not `merged`, with nothing changed; `repositories` then fetches each repository's `origin`, reads its default branch from the remote (`git ls-remote --symref origin HEAD`), and refuses by repository name a worktree `dispatch` made at `<worktree_dir>/<id>/<repository>` that has uncommitted changes, is locked (by anything, a Claude Code agent's lock included), is not on `work/<id>` or has a process running in it (the rules of the worker's worktree above, `release_worker_worktree` with the repository's checkout), removing none; with every one clear it removes each, never with `--force`. The `done` of that landing writes `evidence.repositories`: for each repository the request's url (`!<iid>` when it has none) and its merge commit, the first merge commit between the branch's tip and the default branch, the tip itself for a fast-forward, else the newest first-parent commit whose message says `See merge request <project>!<iid>` (`""` and said when none is found); it requires no commit of the workspace carrying the item's `KB-Work` trailer (the work is merged in its repositories), and its scope rule reads the workspace's own commits against the item's `workspace/<glob>` touches (`bl_land.own_globs`). Once the item has landed, `land` deletes each repository's `work/<id>` when `git cherry` shows every commit on its default branch; one with a commit the default branch lacks is kept and said. `close` removes what a landing left of such an item's repositories (`bl_land.clean_repository_leftovers`): each of those worktrees that is clean, unlocked, free of processes and merged into the default branch as the checkout last fetched it, its `<id>` directory once empty, and the branch when merged there; the rest is kept, and `close: kept ...: why` says why. A project with no `repositories` map lands as above.

For an item with a code-lane commit not yet on the integration `main`: `land` names that branch with `kg_lane.lane_plan`, given the root it works in (no module global swapped), the helper sync names it with, so the two agree when the range begins with another item's commit (a bug filed with `new --commit`). A re-run before the merge, with a `code/<id>` branch on the remote holding the same tree, pushes nothing and says it waits. On GitLab, with `glab` signed in, that re-run also reads the request through `bl_forge` (once for the pass: the read the description step above uses too, read only): an open one that is mergeable, set to auto-merge and whose head pipeline was skipped never merges by itself, since auto-merge waits for a pipeline to succeed, so `land` names it and the command that merges it (`backlog.py merge` with the item's id); a remote on disk, the gh arm (`forge` `github`, whose merge refuses, so no line names a command), a CLI not signed in or a failed call adds nothing. After the `land` that sent the request, the session that ran it (`/kb-sprint run` step 4, `/kb-item` step 7) reads the request itself, `glab mr view code/<id> -F json -R <project url>`: `state` `opened` with a `merge_error` is an auto-merge that failed, so it retries once with `python3 _tools/backlog.py merge <id>` and names the error in its report; a retry that fails too is reported with its error and left to the operator, never tried a third time. `opened` with no `merge_error` waits for the re-run above, and `merged` goes on to it (SP-rhgeod5g, where the auto-merge of a request failed with a pre-receive hook error and a plain merge went through; it is `backlog.py merge <id>` now, which merges only the item's own `code/<id>` on the integration project).

## Running a sprint

**A sprint** (`/kb-sprint run SP`): one session is the orchestrator.

- Each orchestrator runs from its own clone or git worktree, never the checkout another session works in: two sessions in one checkout land each other's uncommitted files. Before it lands a branch, `git status --short` shows only its own changes, and `land` refuses a tree with untracked files too: a landing moves the untracked intake drafts (`kb/_self/backlog/*.json` from the SessionStart hooks) of the checkout it runs in aside itself, before its `clean tree` step, and says so (Landing, above); so are the drafts in a finished worker's worktree, when `land` removes that worktree.
- Ready items whose `touches` do not overlap run in parallel. A `kb/_self/<name>.md` doc is no overlap: items that share only such docs run at once, since a landing's rebase merges their doc hunks and the stale check still runs at each landing; shared code and any other shared file still order them (SP-qzip6qar, where nearly every item named `backlog.md`, `tools.md` or `code.md` and 14 items ran one at a time). `claim --commit` commits only the item it claims, so a new sprint's own file and its review and research stories are committed first (`new sprint --commit`), before the claim sync. The paths other sessions hold come from the backlog, never from messages between sessions: after `git fetch`, `backlog.py held --ref origin/main` lists each claimed item's `touches` with its claimer and sprint, and `held --overlaps ID --ref origin/main` the claimed items an item would meet (exit 1 when there is one; SP-bno4xpft, where sessions negotiated path holds by message and one expired unread); two ready items that share a file are ordered with `set ID --add-depends OTHER`, which `claim --by` accepts for the one session working both). Each goes to a worker in its own git worktree (the one the orchestrator makes for a headless session, or `isolation: "worktree"` on the Agent-tool fallback) on a local branch `work/<id>`, never pushed.
- Shared-file move: a task that moves code out of a file other items edit (a split of `backlog.py` or `kbgit.py`) is announced first to the manager session; in-flight items on that file drain: no new claims on it, and `python3 _tools/backlog.py held --overlaps ID --ref origin/main` shows none of the mover's claimed touches overlapping before the move starts; the move is one atomic commit per file moved: new modules git-added, mapped in `kb/_self/map.csv` and the tools map, docs in the same commit, patch targets repointed, and a `bl_` or `kg_` module never importing `backlog` or `kbgit` at any depth; once the move is on main, the sessions are told to rebase onto it before their next commit on the file.
- A worker starts on the orchestrator's branch tip: the orchestrator's `git worktree add` for a headless worker branches from its `HEAD`, and `.claude/settings.json` sets `worktree.baseRef` to `"head"`, which branches a fallback isolation worktree from that `HEAD` too, instead of `origin/main`. That `HEAD` must include the pushed claim commits, so the orchestrator dispatches only after its claim sync (`kbgit.py sync --push` of the claims). The `HEAD` is that of the session's own working directory, so the orchestrator's session starts in its own clone or worktree: one started in another checkout branches its workers from that checkout's `HEAD`, and only the worker's fetch-and-rebase brings them to `origin/main`. The worker checks its base against `origin/main` and rebases only if behind, with no checkout by hand, so its work lands without a cherry-pick after the orchestrator rebased onto a merged request (SP-4fbfzobr, where every worker began on a stale base).
- A sprint in a second clone, because another sprint holds the session's own clone, makes each headless worker's worktree in that clone (`git -C <clone> worktree add <clone>/.claude/worktrees/agent-<id> -b work/<id> origin/main`). On the Agent-tool fallback it is orchestrated from a fresh Claude session started in that clone: the Agent tool gives a subagent no working directory of its own (it starts in the session's), so `isolation: "worktree"` from a session in the other clone branches from the wrong clone. A session that cannot start there makes each worker's worktree by hand after the claim sync, `git -C <clone> worktree add <clone>/.claude/worktrees/<id> -b work/<id> origin/main` after a `git -C <clone> fetch origin`, starts the subagent without `isolation` and names that path in the brief; the worker runs every command by absolute path into it, since its working directory stays the session's (SP-xourq2gj, where the orchestrator made the worktrees by hand with no rule to follow).
- Every item, whatever its kind (a task or subtask, an `S1` or `S2` bug with its tasks and subtasks, a story or bug with no tasks yet for its breakdown), goes to a headless session, `claude -p --model sonnet --effort high --output-format json`, whose brief makes `.claude/agents/kb-worker.md` its role file; it takes the session model only when the operator asks for it (SP-s5fdczv7, where headless Sonnet sessions did an `S2` investigation bug and an untasked story). On the Agent-tool fallback, for a session that cannot start `claude -p`, an item goes to the `kb-worker` agent (the newest Sonnet at high effort), started with no `model`, which would replace the agent's. The sprint review's fresh-context reviewer follows the same default, headless Sonnet, the session model only on request; it and every `/kb-census` subagent never use `kb-worker`, and a census subagent keeps the session model.
- A headless worker's brief has three fixed parts (SP-s5fdczv7, where the first headless worker had no scratch directory, so its proof script went to `/tmp` and its cleanup was refused, the goal research worker stopped at its 100-turn cap, and the orchestrator's foreground `cd` into a worker's worktree moved its own session's working directory there): a scratch directory `_cache/scratch/<id>/` outside the worktree, which the orchestrator makes, passes with `--add-dir` and names in the brief for the worker's throwaway files (the staging copies below sit in it too); the brief goes to the session on stdin (`claude -p ... --add-dir <scratch> < brief.md`), never as a trailing prompt argument, which `--add-dir` swallows (it takes several paths) and the session exits 1 with `Input must be provided either through stdin or as a prompt argument when using --print` (SP-d3hybrlv); `--max-turns` by item kind, 60 for a task or subtask that is not research, 100 for a bug or a story with no tasks, 200 for a research task or subtask (its scope kb content only, as a research story's), a research story or an investigation bug (`kb/public/claude/ci-and-headless.md`: print mode only, the session exits with an error at the limit, no default); and the orchestrator runs a command in a worker's worktree only in a subshell, `( cd <path> && ... )`, or with `git -C <path>`, never a bare `cd`, since its working directory persists between Bash calls.
- `python3 _tools/backlog.py brief ID` prints that brief and `python3 _tools/backlog.py dispatch ID` starts the worker from it (`_tools/bl_dispatch.py`, `kb/_self/tools.md`): the brief holds the item's JSON and goal text, its external tracker ids with their urls, the role file, the worker's worktree and scratch directory, the in-flight items and the files their touches change, the known failing tests the orchestrator names (`--known TEST=BUG`, and `--probe TEXT` for a bug of unproven cause), the fixed worker rules and the rules of the project's own docs (`rules_section`: when `backlog.json`'s `kb_root` names a kb root, its cited fact lines with `path:line` and tag, `rag.py pack --root _self --item ID` for the kb's own `_self` and `rag.py pack --root ROOT` on the item's title and goal for another root, `--item` serving `_self` only; else the docs its `docs_map` maps the item's touches to, each by path and `##` headings; a project with neither gets one line saying no docs map is set, so a worker reads the rules of its files and never the project's whole rulebook; a project becomes a root through `/kb-add-root` and `/kb-ingest`); `dispatch` makes the worktree and the scratch directory when absent (in a workspace whose `backlog.json` declares `repositories`, also one worktree for each repository of the item's `repos` at `<worktree_dir>/<id>/<repo>`, on `work/<id>` from that repository's own `origin` default branch, read from the remote after a `git fetch origin` in its checkout, with no upstream set: a repository whose fetch fails refuses the dispatch naming it before any worktree is made, a repository of `repos_if_needed` gets none, the worker asks for it in its report, and the brief names each worktree), writes the brief there and runs the session in the foreground with the brief on stdin and `--max-turns` by kind, so the orchestrator starts it as a background command and is told when the session exits; it records the session's pid when it starts and its `session_id` when it exits in the claims ledger of the clone's git dir (`worker_pid`, `worker_session`; the id is read from the JSON result, no flag fixes it up front, and a session id is no part of a committed item file), and `--dry-run` prints the worktree, the brief path and the argv and starts nothing. A brief for a worker is not written by hand.
- A headless worker is started with the project settings: a session started with `--setting-sources local` loads no capture hooks and its work never reaches `backlog.py cost`, while a worker started with the project settings is counted through the `branch` row of its `work/<id>` worktree, since a work window opens from a `claim` or from the session's `work/<id>` branch (`kb/_self/usage.md`, In the query log). Those settings run the SessionStart hook `backlog.py intake --file --hook`, which in a linked worktree under `.claude/worktrees/` files nothing and prints one line on stderr naming the worktree (so a worker leaves no untracked drafts under `kb/_self/backlog/` for `release_worker_worktree` to refuse, `kb/_self/usage.md`, In the query log; a worktree made elsewhere still gets them, and `land` run from another checkout does not move them: `release_worker_worktree` refuses a worktree not under `.claude/worktrees/`, so `land` stops at its `branch` step naming that worktree, the drafts still in it, and they are moved aside by hand or `land` is run from that worktree, where they are the checkout's own drafts, Landing, above). The orchestrator makes its worktree after the claim sync, `.claude/worktrees/agent-<id>` on `work/<id>`, so `land` removes it. Such a session cannot write under `.claude/` in permission mode `default` or `acceptEdits`, which prompt for protected paths with no one to answer (`bypassPermissions` allows it; `kb/public/claude/settings-and-scopes.md`): it then edits staging copies the orchestrator copies back, and the orchestrator makes every edit under `.claude/`. After the orchestrator copies the staging copies back into the worktree it runs `python3 _tools/selfdoc.py check` and the item's own `checks` there, before the commit and `land`: the worker's checks read the worktree's unchanged `.claude/` files, not the copies it edited, so its `problems=0` says nothing about them (SP-pbekfhaz, where ST-zzsbdbi7's worker reported `problems=0` while its staged kb-sprint text held a dead heading reference). The staging copies sit outside the worker's worktree, in the worker's scratch directory `_cache/scratch/<id>/`, which the session gets with `--add-dir`: copies left in the worktree are untracked, and `release_worker_worktree` refuses a worktree with untracked files, the intake drafts (`kb/_self/backlog/*.json` that no commit of the item's branch names) apart: `land` moves those to `_cache/intake-drafts/<worktree name>/` of its clone, says so, and the orchestrator copies back to `kb/_self/backlog/` the ones triage keeps (SP-mlemdqbn, where the orchestrator moved about six drafts out of every worker's worktree by hand before each landing).
- When the Agent tool does not list `kb-worker` (agent files load at session start, so a session that added or changed it cannot use it), the fallback item goes to `general-purpose` with `model: sonnet`, the one `model` the orchestrator passes on the Agent tool, and a brief that points the worker at `.claude/agents/kb-worker.md`.
- The orchestrator lands them one at a time with `backlog.py land ID` (Working on items, step 4), after `git status --short` shows only its own changes and the worker's worktree is removed, by `land`, since `git worktree remove` is denied to agents (`land` refuses a branch checked out in another worktree, except that it unlocks and removes a clean worker's worktree Claude Code left locked, as Landing says: an agent whose background work outlived its report leaves its worktree locked with the reason `claude agent agent-<id> (pid ...)`, the pid that of the orchestrator's own session, and the repository cannot stop Claude Code taking that lock; a worker ends every background command and monitor it started before it returns, `.claude/agents/kb-worker.md` rule 8, and `land` refuses while one still runs in the worktree, SP-3brmvlnh, where a worker left a ten-minute intake run with `tests.py` under it and another left monitors that woke the orchestrator a dozen times): code goes as a `code/<id>` merge request, and a second `land` on a later pass, once it has merged, runs `done` and pushes the item file. Content-only items land in one run, straight to `main`, and `backlog.py land ID --wait-merge 1800` lands a code item in one run too; a commit that changes code, `kb/_self/_decisions.csv` or an item file beside code is the code lane (`_tools/kblane.py`).
- Before it lands an item, the orchestrator reads the item's gates on its branch (`git show work/<id>:kb/_self/backlog/<id>.json`) and lands it only after each gate is answered or provisional: a worker records each choice its goal leaves open as a provisional gate answered `--provisional`, committed with its work (`.claude/agents/kb-worker.md`), so an unanswered one, or a choice its report names without a gate, goes back to that worker; an open blocking gate keeps the item waiting. A default, a width, an opt-in, a limit or a price a worker picks is such a choice, and a choice on an item whose touches are rule-guarding is a blocking gate: a worker whose `gate add` prints `made blocking` commits the gate and stops with a report, which the dispatch brief's fixed rule and `kb-worker.md` rule 6 both say. A worker that changes what a function returns or takes runs `backlog.py referrers` on it first and covers every consumer in the same item (the same two places), so a consumer missed there is not left to a bug filed after the landing. The review confirms each provisional answer (Sprints, Review).
- An answer the operator gives in the orchestrator's session to a gate that exists only on a worker's `work/<id>` branch is recorded by the orchestrator with `python3 _tools/backlog.py --root <worktree> answer ID GATE --answer TEXT --by operator` run against that worker's worktree (`<worktree>` is `.claude/worktrees/agent-<id>`, which `dispatch` made; the gate is one the worker committed and stopped on), then a commit there of the item file alone (`git -C <worktree> add kb/_self/backlog/<id>.json`, a message whose `KB-Work` names the item), so `land` reads the answer on the branch. The worker does not sign by `operator` an answer the orchestrator relays: `--by operator` is the operator's own record, so the worker leaves the gate open and hands it back in its report (`.claude/agents/kb-worker.md` rule 6; SP-gkbtjjce, where BG-qqdfqx2d's worker refused to sign a relayed operator answer and the orchestrator recorded it in the worker's worktree with no rule naming that route).
- Items that share a file run one after another.
- A sprint planned off its host, whose goal or items can only run on one host (a host precondition, a trigger on a host session), has its stories' premises run on that host: the first run pass there runs each committed story's `Premise:` command before any claim or dispatch, records each result in the story's notes (`backlog.py set ID --add-notes`), and, for a premise that does not reproduce, the orchestrator asks the operator (reshape the story to a test-only item, or move it out of the sprint) before any worker is dispatched. The plan step's premise run (Sprints, Plan) assumes the planner can run the premise where it plans, which a host-bound sprint planned elsewhere cannot. A host the orchestrator cannot reach runs the premise through the project's route for that host, which the sprint's orchestrator brief names (SP-eahtellz, where a premise planned on macOS failed only mid-sprint on Windows).
- A worker's brief names the `kb-worker` set (`python3 _tools/rag.py pack --root _self --set kb-worker`) and the item brief command (`python3 _tools/rag.py pack --root _self --item ID --budget 600`) instead of a section to read. It also names the in-flight sibling items and the files they change, and the known failing tests: each test the orchestrator already knows fails on the host, with the bug filed for it (id and title) and its cause, so a worker neither files it again nor guesses a cause; a failure the brief does not name is the worker's to file (SP-rhgeod5g, where two workers each filed a duplicate bug with a wrong cause for a failure the orchestrator had already diagnosed and filed). A figure the orchestrator adds to a brief, or puts in a gate's question, for a worker or the operator to rely on (a length, a limit, a count, the shape of a name) is measured, with the command that measured it beside it, never lifted from an example (SP-vayhvwfy, where a worker modelled a worktree name's length on the brief's example `agent-ST-xxxxxxxx` and a gate's limit was confirmed on it, while an Agent-tool worktree here is `agent-` and 17 hex characters, 6 characters longer).
- A bug whose cause is unproven (its goal names a symptom, or a cause nobody has shown) gets one probe from the orchestrator before it is dispatched, and the brief names the probe's result. The probe is one short run that reproduces or isolates the suspected cause, such as a single `claude -p` session or a planted repro, far smaller than a worker pass (`backlog.py cost` reports it in tokens like any run); a bug whose probe shows its cause goes to the worker with that cause, and one the probe cannot settle goes with the probe's output and what it ruled out, never a second probe in the orchestrator. It answers SP-owbgisoj, where BG-ay4w32jc spent two worker passes on a symptom, and one `claude -p` probe by the orchestrator (that SessionEnd fires and a detached child survives) redirected it to its cause.

## Bug intake

Bugs come from:
- an agent at any time;
- the operator;
- a sprint review;
- a red pipeline: `python3 _tools/backlog.py red-pipeline` reads, among the last 100 finished pipelines of the integration remote's `main` (on GitLab one job-list call for each, so it stops after `bl_intake.IDLE_PIPELINES` in a row in which no job ran, and then answers "not checked", never a verdict: a job that ran behind more pipelines nobody started, red or not, is out of reach; `--status` exits 1, and the intake `ci` detector files nothing), the newest one in which a job ran (`ql_deliver.job_ran`: a start time, success, running, or a failure of its own, and not canceled: a job someone started and canceled holds no verdict), or the newest finished one when no job ran in any of the pipelines listed and the read did not stop early (through `bl_forge`: `glab api`, `gh` on GitHub, where it reads the newest completed run, and its jobs only under `--job` or once a run is red; a note and no filing when neither is signed in; on GitLab one waiting on manual jobs counts as finished). Every job in `.gitlab-ci.yml` is manual, so most pipelines of `main` are ones nobody started, and a newer one of those hides nothing. On GitLab it reads the pipeline by its jobs, not by its status, since every job is manual with `allow_failure: true`, so the status says success whatever they did, and a job nobody started holds nothing (`ql_deliver.job_verdict`):
  - **red**: the pipeline failed, or a job someone started failed on its own account (`failure_reason` `script_failure`, `job_execution_timeout` or `stuck_or_timeout_failure`), whichever job;
  - **unverified**: the job list is unreadable, or a job named in `ql_deliver.GATE_JOBS` did not succeed (none is named while every job is manual, so a pipeline nobody ran is green);
  - **green**: neither.

  When it is red and no automatic revert (`KB-Auto: revert`) covers it, it files one bug for it: `S1` when the `kb-tests` job failed (the gate itself is red on `main`), else `S2`. An unverified pipeline files nothing. With every job manual, `red` means a job someone started failed its script; a pipeline no one started is green. The bug's `links` name `pipeline <id>` and `fingerprint <12 hex>`: a hash of the first failed job's name (by name, among the jobs whose script ran when there are any; a job counts by its newest attempt, so one that failed and was retried to success is no failed job) and its first failure (the first failing test id, else its first error line with colours, hex ids and numbers taken out; GitLab.com's per-line timestamp and stream marker, such as `01O` or `01E`, come off every line before either is matched), read from the job's log. An item that already names `pipeline <id>` stops a second bug, and a pipeline whose fingerprint an open bug already carries is added to that bug's `links` instead of filing another. The bug's repro is `red-pipeline --status --job <that first failed job>` when that job's script ran and failed: `--job` reads the newest pipeline of `main` in which that job succeeded or failed on its own account (`ql_deliver.job_decided`), so the repro exits 1 until the job runs again and passes, not when a later push starts nothing, another job passes, or someone starts the job and cancels it or leaves it manual or skipped (BG-sim2fdaa). Plain `--status`, when no failed job whose script ran was read (a pipeline red by its status whose failed job never ran, such as `ci_quota_exceeded` or `runner_system_failure`, which a `--job` repro would skip for an older pass: BG-vsqfchgz), exits 1 while the pipeline it reads is red or unverified, naming each gate job that did not pass when `GATE_JOBS` names any). An async `SessionStart` hook runs it silently in every clone (`red-pipeline --hook`), and the bug it files is an uncommitted item file until someone commits it. It answers the failure of a red `main` that nobody filed. Intake runs as its own hook beside it (below), offline, so the pipeline read stays this hook's. The same check is intake's `ci` detector (below);
- a query-log revert: the revert commit of a red automatic push adds one `S2` bug item of its own (the same repro, `red-pipeline --status --job <its first failed job>`), naming the failed pipeline and the reverted findings, with the same `pipeline` and `fingerprint` links, or joins the open bug that already carries its fingerprint (`kb/_self/querylog.md`, Delivery), so `red-pipeline` files no second one.
- intake: `python3 _tools/backlog.py intake` runs the detectors registered in `_tools/bl_intake.py` (`DETECTORS`, each added with the `@detector(name)` decorator and a function of the repository's files: no model, no network except the `ci` detector, which runs only under `intake --network`, and no clock except the `drift` detector's time budget for running checks, below) and prints one block per candidate item: detector, kind, fingerprint, title, goal, the repro of a bug and its links. The `ci` detector is `red-pipeline`'s main-pipeline check, with the same fingerprint and links (but for the `detector ci` link intake adds), so whichever of `intake --network` and `red-pipeline` runs first files the bug and the other skips it; plain `intake` and `intake --status` never use the network. A fingerprint is 12 hex characters hashed from the detector's name and the finding's key, so a finding keeps its fingerprint between runs. The `drift` and `trailers` detectors each report their whole finding set as one candidate whose key is the constant `WHOLE_KEY`, so each keeps one fingerprint, and one open item, whatever commits enter or leave the window, which items drift or which checks the budget reached; that item's notes list what was found when it was filed, and its `intake --status` exits 1 while the detector reports anything and 0 once it reports nothing. A candidate whose fingerprint an open item's links (`fingerprint <12 hex>`) already carry is marked skipped, as `red-pipeline` does for a failure. Plain `intake` writes nothing; `--file` files each new candidate (`bl_intake.file_found`) as a `draft` item outside any sprint, for the operator or the planner to triage, so a second run files nothing: a candidate `backlog.py similar` calls a near-duplicate of an open item of another detector or a hand-filed one is merged into that item's notes once (`Found again by the intake: ... (fingerprint HEX)`) and files no draft, and at `bl_intake.OPEN_DRAFTS_MAX` (60) open drafts, of any origin, the rest are refused with the cap message on stderr and exit 1. A bug's repro is `intake --status <fingerprint>`, which exits 1 while a detector still reports that fingerprint (or one cannot run) and 0 once none does. `intake` exits 1 when a detector failed, and 2 for a bad fingerprint or `--status` with `--file`. An item it files carries the detector's name as its last link, `detector <name>` (the bug `red-pipeline` files has none), which the query log digest counts by (`kb/_self/querylog.md`, Reporting).
  - **The detectors**, each a candidate with a fingerprint of its own, which `intake --status` takes as the repro or check of what it files:
    - `drift`: one story naming the items that disagree with their commits (fingerprint: the detector's own, `WHOLE_KEY`): a `doing` item whose newest work commit on the integration `main` is more than `DRIFT_HOURS` older than the tip, with no `done` after it, and a `draft` or `todo` item with `touches` whose touched files changed since its file did and whose checks all pass on `HEAD`. The age counts from the tip's commit time, not the clock. The detector runs those checks without a shell, each for at most `CHECK_TIMEOUT_S` and all within `DRIFT_BUDGET_S` (a monotonic clock, the only time intake reads), so an intake stays short enough for the hook. Each check runs with an isolated query log home as the checks of `done` and `land` do (`bl_base.check_env` and a fresh temporary directory as `CLAUDE_PLUGIN_DATA`, removed after the check), so no drift check adds a row to the clone's spool, except the `test.run` row of a `tests.py` run it makes (`KB_TEST_RUN_HOME`). It takes the eligible items in id order starting after the last item the previous run reached (kept in a file in the git directory, never tracked; the first run starts at a hash of the number of commits on the tip of the integration `main`, `HEAD` without one): a budget that covers only some of them reaches every one within as many runs as there are eligible items, whatever number of commits lands between runs, not the same first few every run. Each check leads a process group of its own (POSIX `start_new_session`, Windows `CREATE_NEW_PROCESS_GROUP`), and a timeout, or the process exiting while the check still runs (the hook stops waiting and exits), ends the whole group (`os.killpg`, Windows `taskkill /T /F`): `tests.py`, `uv`, pytest and its xdist workers, not only the check's own process. Nor does any check but the read-only forms drift allows (`bl_intake.DRIFT_SCRIPTS`: `tests.py`, `rag.py`, `check.py`, `selfdoc.py` and the kb-verify `lint.py`, run by exactly `python3` or `python`), so `python3 -c`, `kbgit.py sync` or `publish` and the backlog writers never run there (`bl_intake.check_program_refusal`): drift runs every item's committed checks in every session with that session's credentials, so a planted `git push` or publish check never runs there; the item is counted unchecked in a note of its own (`Drift.refused`). `done` and `land` still run the read-only `sh` and `git` repros items carry (`bl_land.run_check`), while an open item's repro and checks keep to the forms `check_program_refusal` admits, `python3 -c` included, so they run without a shell on every host; `backlog.py check`, and so the push gate, fails on an open item whose repro or check takes another form or runs no test or tool code (`bl_check.trivial_command`), so an item file that would turn those live-backlog tests red fails its own push. A check that runs the whole suite never runs: a whole-suite wrapper (`perfcheck.py`), or `tests.py` or pytest with no `-k` or a `-k` with no term outside `not` (pytest also runs when it names a test file), read through a shell string (`sh -c '...'`, `bash -lc`, `cmd /c`, `pwsh -Command`) as well. An item left unchecked (a check timed out, a whole-suite check, the budget spent) is counted in the story's notes and never reported as passing;
    - `trailers`: one `S3` bug listing the commits of the integration `main` no more than `TRAILER_WINDOW_DAYS` older than its tip (merges left out) whose `KB-Work` line git does not read as a trailer, or that change `_tools/`, `.claude/`, `.githooks/` or `.gitlab-ci.yml` with neither a `KB-Work` nor a `KB-Auto` trailer, its notes naming their short hashes (fingerprint: the detector's own, `WHOLE_KEY`);
    - `stranded`: one candidate per query-log finding of the committed store, read at `HEAD`, whose newest record is a `candidate-gap`, an open source finding with the `stage` signal (a `route` one is report-only, listed by `querylog.py status`, and no stage moves it), `no-fix` (but a no-fix eval finding closed `--tried`, until its note is `QUEUE_TRIED_DAYS` old) or `apply-failed` and is more than `STRANDED_DAYS` older than `HEAD`'s commit day (`kb/_self/querylog.md`, Store and Learn): a story to probe the host's provider (`/kb-probe`) for a source finding with the `stage` signal, an `S3` bug for any other (fingerprint: the finding id and its state, so a finding that moves on is a new one);
    - `repeats`: one story per command class or tool group (a `call.tool` row's `class`, else its `tool`) that the sessions of the committed ops sidecars called more than `REPEAT_THRESHOLD` (300) times in the latest closed ISO week (the week before the one today's UTC date is in, never the running week, whose count only grows), at most `REPEAT_MAX` (5) a scan, most calls first, naming the section-sized command to use instead when `bl_intake.INSTEAD` has one (`rag.py show` for `cat`, `head` or `sed`, `rag.py search` for `grep`, `selfdoc.py section` for `tools.selfdoc`); it reads the rows at `HEAD` by `git grep`, never a spool, within a count budget (`REPEAT_ROWS_MAX` rows, the rest counted in the notes), and its fingerprint is the class alone, the week staying in the title and notes, so each class is filed once and its `intake --status` check passes once a later closed week is at or under the threshold;
    - `ci`: above.
  - **The hook:** a second async `SessionStart` hook in `.claude/settings.json`, beside `red-pipeline --hook` which keeps reading `main`'s pipeline, runs `intake --file --hook` (`timeout` 60), offline: no `--network`, so the `ci` detector does not run. `--hook` is silent (no output, exit 0 whatever happens, as `horizon --hook` and `red-pipeline --hook` are; the one exception: with `--file` in a worker's linked worktree under `.claude/worktrees/` it files nothing and prints one line on stderr naming the worktree, `bl_ci.in_worker_worktree`), runs the detectors one after another, the fast offline ones first, then `drift` (`INTAKE_HOOK_SLOW`, on what is left of the budget), then the network ones (with `--network`), stops waiting for them after `INTAKE_HOOK_BUDGET_S` (50 s, under the hook's timeout; the drift detector takes about half a minute) and files what the detectors that finished by then found, so a drift scan that outlasts the budget costs only its own findings. With `--file` it writes the drafts as other `--file` runs do (`bl_intake.file_hook`), except that it files none for a fingerprint that an open item of its checkout (an untracked draft or a committed item) or a draft set aside under `_cache/intake-drafts/` of the clone's main worktree (`bl_intake.INTAKE_ASIDE`, where `land` moves a worker's drafts and those of the checkout it runs in) already holds, none while open drafts are at `bl_intake.OPEN_DRAFTS_MAX`, and merges no near-duplicate, so a second session, in whichever checkout, files nothing; it never commits and never pushes. The drafts stay uncommitted item files until `/kb-backlog` triage lists them first (the new files in `git status --porcelain -uall kb/_self/backlog/` whose links carry `fingerprint` and `detector`) and commits those it keeps, with `KB-Work` naming them.
- ops rows: a sprint close, a red-pipeline read and an intake run leave one row each in the query log's ops spool (`kb/_self/querylog.md`, Surfaces), counts and names only: `close` writes `sprint.close` before it deletes the items, `red-pipeline` and the delivery CI check write `ci.pipeline` only when a pipeline's state changed (with the job-list calls the read made), and `intake` writes `intake.detect` for a detector that found something or ran out of its budget (the drift detector's coverage included). A row never makes the command fail or wait.

## Processes left running

**Processes left running** (`python3 _tools/backlog.py procs`, `_tools/bl_procs.py`; SP-4i5quwba, where workers left locked worktrees and stray sleep shells): `procs` lists, read only, every process whose working directory lies in the clone's main checkout or a worktree of it, and, in a workspace whose `backlog.json` declares `repositories`, in a repository's checkout or one of its worktrees (what `live_processes` finds, with its parent, age and command name; never a command line or an environment), as `orphan` (its parent is gone: a background run a session left behind), `hook` (an orphan younger than `bl_procs.HOOK_GRACE_S`, 60 seconds, whose standard output is the clone's `_cache/querylog/distill.log`: the run a session's end hook starts, detached, which delivers for seconds with its parent gone and ends on its own; told by that file, never by a command line; ST-iltxwoty, where `land` stopped on the end hook of a worker that had just exited and `selfcheck` failed `orphans` on three 12-second-old runs of an operator's `/clear`) or `foreign` (a live session's own work). Nothing is ever signaled: an orphan is named for the operator, who ends it when it is theirs, and `selfcheck` fails while one runs; a hook older than the 60 seconds is an orphan. The commands that recorded the autopilot's own processes and ended them went with the autopilot (BG-xwolxdi6). A host that cannot list working directories (Windows) says so. `land` names each pid and command of a process that keeps it from removing a worker's worktree (Landing), after waiting up to `HOOK_GRACE_S` for the processes of the worktree whose parent has exited (`bl_land.wait_for_hooks`: one look each second, no wait for a process whose parent lives, which is a session's own work), and says which of them is a session-end hook; a worktree whose only process was a hook that ended in time is removed, and `land` says how long it waited.

## Self-check

**Self-check** (`python3 _tools/backlog.py selfcheck`, `_tools/bl_selfcheck.py`; `/kb-sprint run` opens every pass with it): read only, its one network call the read of each claimed item's `code/<id>` request that `claims` makes through `bl_forge` (a read that fails is `unknown:forge`, no failure), it prints one line when its seven checks hold and else one line for each check that failed or could not be read, with the remedy the kb-sprint skill, Self-check, names, capped (`LINE_MAX`, `MAX_CHARS`, `SHOW`; what it drops is counted in its last line; `--full` lifts the cap) and exiting 1 on a failure. `allow-rules` reads `.claude/settings.json` (never writes it) against the commands the skills run, kept as `SKILL_COMMANDS` in the module (a rule `Bash(PATTERN)` covers a command PATTERN matches whole, `*` any text, a trailing ` *` also no arguments; the commands `.claude/settings.json` denies to agents, `git worktree remove` and `git branch -D`, are not on that list, since `land` runs them as a process of its own); `checkout` fails a clone that is a linked worktree of another checkout (its `git rev-parse --git-common-dir` is not its own `--git-dir`), naming that checkout and saying to use a standalone `git clone`; `hooks` reads `core.hooksPath`, the `.githooks` scripts and the plugin manifest; `host` the load against `LOAD_PER_CORE` per core and the two host locks against `HOST_LOCK_WAIT_S`; `claims` and `main` read the signals `stalled` computes (`bl_stall.collect`), the claim signals `claim-no-commit`, `returned-no-commit`, `returned-staged` and `mr-dead` and the newest `ci.pipeline` row (`main` makes no forge call of its own); `orphans` the orphans of `procs` (any process in a checkout of the clone whose parent is gone, a `hook` in flight apart: it passes and is named, with its age, in the check's detail (`--json`)). The orchestrator acts on a failure before it dispatches work, or records why it cannot (a gate).
## Stalled work

**Stalled work** (`python3 _tools/backlog.py stalled`, `_tools/bl_stall.py`; a run where a worker with staged files, no commit and no live test process waited for a background-run completion notice that never came and stalled a chain until the orchestrator finished the item): `stalled` lists, read only and with exit 0, each claimed (`doing`, with a claimer) or ready item that shows a signal, its id and title together, with the signals (`--json` prints the same as one object). It reads the claims (the item files), git (the commits on any ref whose last paragraph carries the item's `KB-Work` line, the newest `chore(backlog): claim` commit as the claim's time, the worktrees and the branches `work/<id>` and `code/<id>`), the ops rows of the query log (this host's spool and the committed ops sidecars, through the `ql_store` readers, each row id once and only a row of a closed event with its closed keys) and the host test lock file, and, for a claimed item, its `code/<id>` request through `bl_forge` (`forge_project` and the `forge` setting, one read for each claimed item in a run, none for a ready one): that read is its only network call; it never reads a process's command line or environment (the scan of working directories is `procs`'s) and writes nothing. An input it cannot read is listed as `unknown:<what>` (`claim-time`, `git`, `worktrees`, `procs`, `lock`, `forge`: a request read that fails, a forge CLI not signed in or a remote that names no forge project, which also ends the run's reads), never guessed; with no `ci.pipeline` row the main is `unknown`. The signals, with the limits as named constants in `bl_stall.py`: `claim-no-commit` (a claim with no work commit, a commit that is no planning commit, for longer than `CLAIM_NO_COMMIT_S`); `returned-no-commit` and `returned-staged` (a worktree of the item with no live process, no work commit and a claim older than `RETURNED_GRACE_S`, the second with staged or modified tracked files left: the worker waited for a notice that never came); `done-refused` (`DONE_REFUSED_N` `done.refused` rows of the item); `check-timeout` (`CHECK_TIMEOUT_N` of those rows that name `check-failed` and took as long as `CHECK_TIMEOUT_S`, the time a check is given); `land-same-step` (`LAND_SAME_STEP_N` failed `land.step` rows of one step); `mr-dead` (the item's `code/<id>` request is not merged and does not merge by waiting: its head pipeline `failed`, `canceled`, `skipped` or `manual` (`MR_DEAD_PIPELINE`), or its detailed merge status is one that needs a push, a rebase, an approval, a resolved thread or another request's merge (`MR_DEAD_MERGE`, the values `kb/public/gitlab/automated-merge-requests.md` lists as not cleared by waiting; a status it does not list, `checking`, `unchecked`, `ci_still_running` or `conflict` among them, is no signal, and neither is a merged request or none; shown for claimed items); `red-main` (the newest `ci.pipeline` row is red; shown for claimed items); `lock-wait` (a live process has held the host test lock for longer than `HOST_LOCK_WAIT_S`; shown for claimed items). What to do about a signal is the orchestrator's call; the kb-sprint skill, Stalled work, lists the usual steps.
## Cost of work

`python3 _tools/backlog.py cost ID [--runs] [--rework] [--format text|json]` prints what an item and its descendants cost in tokens, from the work sidecars the query log's distill writes (`kb/_querylog/work/<yyyy-mm>/<run-id>.jsonl`; `kb/_self/querylog.md`, Distill, and `kb/_self/usage.md`). It works for an item of any kind and reads no command text, session or prompt id: the sidecar holds none. `_tools/bl_cost.py` owns the report, its parser and its registration with `bl_cli`, and `backlog.py` defines none of it: `bl_cost` never imports `backlog` and registers `cost` itself.
- **What it sums:** the item lines (`item: <id>`) of every sidecar for the item and each descendant in the item files at `HEAD` and those restored from git history (below); for a sprint, its own line (the multi-window prompts of its orchestrator) and the items in it. A shared line (`items`: the ids its session claimed) is its session's, not an item's: it is in the shared figure (below), never in an item's direct or attributed.
- **Per model:** requests, `in`, `cr` and `out`, with `cw` (cache writes) after them as a figure of its own, never added to another count. Four groups, printed apart: direct, the item lines' `main` (the main agent's prompts inside the item's windows); attributed, their `sub` (the subagents routed to the item) summed over agent groups; shared, the counts of the prompts of the sessions that worked the item (or one of its descendants) outside any of their windows, the `main` and `sub` of the shared lines together; and the session total, direct + attributed + shared, each count and each `cw` summed on its own, so a `cw` is never in an `in`. A model row ends with `all models`, the sum of the rows, zeros when there are none.
- **Which shared lines, and each once:** a shared line belongs to a report when any id in its `items` is in the report's scope (the item, its descendants, a sprint's items), and is counted once in that report, however many of its items are in the scope and in however many items the report rolls up: an epic or a sprint adds a session's shared counts once, not once per item the session worked. The sidecar holds no session or prompt id, so a line is the unit: one line per session per run, and a session's prompts are counted in one run only (Querylog, Distill). The same line is in the report of each item it names (the task and the bug one session worked each show the session's shared counts, which are the session's, not split), so the shared figures of two items that were worked by one session are not to be added: roll them up in the report of their common ancestor or sprint. A report's `by item` and `run_lines` hold item lines only, with no shared figure; `--runs` lists the shared lines apart. The ids of a shared line count as named in the history lookup below, so a deleted task found only through a shared line still reaches its epic.
- **`--runs`** lists each run's line apart, one per run and item, and before them each shared line (its run, the items it names, its prompts and counts); `--format json` gives the same numbers (`direct`, `attributed`, `shared`, `session_total`, `shared_prompts`, `by_item`, and with `--runs` `run_lines` and `shared_lines`). A sidecar that breaks the store's work gates (`ql_store.work_line_problems`) is skipped whole and named on stderr, so a bad file never skews a sum.
- **`--rework`** adds, after the report above and changing none of it, what the item work cost before its items' first refused `done` and what it cost from there on. Rework is the `rework` block of an item line (`kb/_self/usage.md`, Work sidecar; `kb/_self/querylog.md`, Distill): the counts of the prompts from the prompt that ran the item's first refused `done` (a `done` that exited 1) to its `done` or `release`, and of the subagents routed to it from those prompts, a part of the line's counts. The report sums them over the same lines as the item-work figures (a sprint's research items stay out, as they do there; a sprint's own line has none, since a prompt in several windows is never split), and work is those figures less rework, so the two always add to the report's direct and attributed.
  - *Per item:* an item with no refused `done` in its window has no rework figure, and is not listed; one with a refusal is listed with its prompts and tokens (`in` + `cw` + `cr` + `out`) of work and of rework. A refusal of one session does not carry into another's rows, and the unit is the prompt, so work and rework are an estimate by prompt, not by minute.
  - *Open sessions:* a session still open has no sidecar line yet, so `--rework` reads its spool (`bl_cost.open_lines`, `kb/_self/querylog.md`, Distill) and prints its figures apart as `open session figures`, provisional until it closes. Its windows are the ones distill gives once it closes (`ql_distill.item_finder` over the root's backlog directory): a `claim` or `branch` row of an item with no item file, or a `branch` row of a stale `work/<id>` checkout of an item already done or dropped, opens no window unless a later `done` or `release` row of the item closes it, and a session left with no window adds no open figure.
  - *Output:* text, a `work and rework` block after the report (and its research and overhead) with `work` and `rework` each as direct and attributed per model, then one row per item with rework; with `--format json` the report's keys plus `rework_split`: `items` (the ids with rework), `work` and `rework` (`prompts`, `direct`, `attributed`, `tokens`), `by_item` (for those ids, `work` and `rework` the same way) and `token_keys`. Without `--rework` no key and no line differs (`--runs` lines carry no `rework`). `--rework` takes an ID, never `--research`. It reports tokens only, no prices, and says nothing of who or what caused a refusal.
- **Items deleted at sprint close** (`close` deletes a sprint, its items and the epics they finished, which stay in git history) are read from their last version in git history, so an epic's total and a closed sprint's include their lines, and `cost` takes the id of a closed sprint or item itself. The ids with a work line and no item file are asked of `git log --all --diff-filter=D` on the item files (one call for up to 100 ids, each id asked once per run, an id with a file never), whose removed lines are the item's JSON as it was when deleted; a restored item's parent that has no file is asked in turn, so a subtask reaches its story through a task that has no line of its own. Its `parent` and `sprint` (or those of the story or bug above it) place its lines. The report names these items (`from git history`, `restored` in json). An id with no deletion in the history this clone holds (never committed, or a shallow clone cut it, or no `git`) stays out of every sum and is named on stderr (`no item file and no git history for ...`; `unresolved` in json), never an error; an id with neither a file nor a history exits 2. The sidecar format is unchanged.
- **A sprint's research and system overhead** are printed apart from the item work, for a sprint id only (any other id prints as above):
  - *Research:* the lines of a research item (Sprints, above: a story, task or subtask whose `touches`, its descendants' included, are all kb content) leave the item-work figures (direct, attributed, the session total, `by item`, the run and item counts) and print as a total of their own: its items, runs and prompts, direct and attributed per model and their sum. No figure is counted twice. The sprint's own line and the items that are not research stay in the item work, and the shared figure is as above: it and the session total still count the shared counts of the sessions that worked research items, whose own item lines are left out of direct, attributed and the item parts of the session total; the research total holds item lines only, so no count is in both.
  - *System overhead:* the `overhead` lines of the sidecars of the runs inside the sprint's window (`kb/_self/usage.md`), per kind (calls and the main agent's counts per model) and in all kinds. Overhead is in no item's or sprint's figure and is never added into one. The window runs from the oldest commit that adds `"status": "active"` to the sprint's item file (the start) to the newest commit that deletes the file (the close); while the file exists the window is open, with no upper bound. A run is inside it when the time in its run id, read as UTC, is at or after the start and at or before the close. Git decides, as for the restored items: in a shallow clone, with `git` missing or failing, or when no commit ever set the sprint active (or the file is gone and no commit deletes it), the overhead is reported unresolved with that reason and no figure, never guessed.
  - *json:* the keys `research` and `overhead` are in the report of a sprint id only. `overhead` holds `resolved`, `reason`, `start` and `end` (UTC, `end` null while the window is open), and, resolved, `runs`, `calls`, `kinds` and `total`; `run_lines` with `--runs` keeps every item line, research included.
- **`cost --research`** (no ID, no `--runs`; `--format text|json`) lists the items that did research against the query log's gap findings, each with its tokens, the gap findings its commits closed, and tokens per closed gap. It reads the same sidecars and the same restored items as `cost ID`, and changes nothing of `cost ID`'s output.
  - *Which items:* every item (the restored ones with a work line included) whose `research` field is true (a field a later item adds to the item file: until it exists, none is selected by it), or whose `links` name a gap finding, an `F-<12 hex>` id that the committed store's findings (`kb/_querylog/findings`) record with kind `gap`. A link naming an eval, alias, expansion or source finding, or an id the store does not hold, selects nothing. An item with neither is left out however much it cost. An item may be selected by both (`selected_by`).
  - *Tokens:* the item's own lines only (no descendant: a descendant that qualifies has its row, so no line is in two rows, and no shared line, which belongs to a session), direct + attributed, as the sum of `in`, `cw`, `cr` and `out` over the models. `requests` is a count of calls and `cw1h` a part of `cw`, so neither is added. Direct and attributed are also given apart. An item with no work line has 0 tokens.
  - *A closed gap:* a gap finding is closed by a commit when a `_gaps.md` of any root (`kb/*/_gaps.md`) has, in that commit, a Resolved or Superseded dated note under the entry whose bullet names the finding id (the notes that settle an entry for `querylog.py queue`, `kb/_self/querylog.md`, The research queue) and has none in the commit's first parent (or has no entry or no file there). The item's closed gaps are those of the non-merge commits, on any branch (`git log --all`), whose `KB-Work` trailer names its id (a trailer may name several items, each gets the gap); a commit with no such trailer, another item's, a Tried or Partly resolved note, an id only a note's text names, or a note the parent already had, closes nothing for it. The query log's own record that a gap is closed (`querylog.py close`) is a commit of its own with no `KB-Work` trailer, so it is not the join. One `git log` lists the commits and one read per commit and ledger follows.
  - *Tokens per closed gap:* the item's tokens divided by the count of its closed gaps, integer division (floor), so 249 tokens over 2 gaps is 124; `n/a` (null in json, `gap_status` `none`) when it closed none, and 0 when it spent no token and closed one. Two sessions' work on one gap, or a gap closed by one item and refined by another, are not split: each item's commits count for it.
  - *Unresolved:* git decides, as for the overhead above: in a shallow clone, with `git` missing or failing, the closed gaps and the ratio are not guessed: the tokens print, `closed gaps: unresolved (<reason>)` and `tokens per closed gap: unresolved` in the text, `closed_gaps` and `tokens_per_gap` null with `gap_status` `unresolved` and `git.resolved` false in json. Git is not asked when no item is selected.
  - *Output:* text, one row per item after a header: its id and title (no other item text), tokens, direct and attributed, the closed gaps, the ratio; ordered by tokens, highest first, then id. Json, `--format json`: `research_items` (per item: `id`, `title`, `selected_by`, `runs`, `prompts`, `direct` and `attributed` as per-model counts, `tokens`, `direct_tokens`, `attributed_tokens`, `closed_gaps`, `gap_status`, `tokens_per_gap`), `git` (`resolved`, `reason`), `token_keys`, `skipped` and `unresolved` (as for `cost ID`); no key is a sprint report's `research` total. A `/kb-research` session that claims no item has no `KB-Work` trailer and no item line, so it is in no row.
- **An item with no item line** (none for it or any descendant, whether or not `--rework` finds an open session with work in the scope) reads 0 prompts and says why in one line, after the header, and adds no figure to the item: the figures stay its own item lines' (a shared line, the sprint's line or another item's line never moves into them). Except for `shared`, whose figures are the session's and print as above, the text then ends, exit 0, with no direct, attributed, shared or session-total table of zeros (a sprint's system overhead with runs, or unresolved, still prints after the line; its research block of zeros does not; with `--rework`, the line is followed by the open session block of an open session with work in the scope, never by the work and rework split of zeros, so `cost --rework ID` prints the line plain `cost ID` prints), so a review that sees the line quotes it and never records zeros as a cost (SP-fvztfmtm closed with zeros because no work sidecar had been delivered). `--format json` keeps every key. `no_line` in json has `kind`, `reason` and, for `shared`, `runs`, for every other kind `spool` (`paths`, the spool directories read, the clone's and the main worktree's when it is another, and `usage_rows`, the `usage` rows in them):
  - *`no-capture`:* the spool holds no `usage` row at all, or capture writes none (mode off, the `DISABLED` marker). The line is `no capture: <spool path> holds no usage rows on this clone` (the paths, when the main worktree's spool is another directory). A delivered spool's rows are deleted (`kb/_self/querylog.md`, Spool), so on a clone whose spool is emptied by delivery an item no sidecar names reads this too: the line says what the spool holds, not that capture never ran. It is checked before the two time kinds below, which need a spool that holds rows.
  - *`shared`:* a shared line names it. The reason gives each such run, its shared prompts and, when the item has a sprint, the prompts of that sprint's line in the same run, and says they are the session's, outside any window or on the sprint's line where windows overlapped (a prompt in several windows of one sprint is counted there, never split per item; a shared line also holds prompts in windows of different sprints), not the item's own. A session that held several claims at once, such as an orchestrator's, leaves its items here.
  - *`before-first-sidecar`, `after-newest-run`:* no sidecar names it and the spool holds usage rows (the reason ends by saying that none is in a window of the item, or that rows of one wait for their session's distill). Git is asked once (`git log` with the patches, for the newest commit whose patch adds a line with `"status": "done"` to the item's file: its last transition to done, so a reopened item is dated by its last done, and the reopen commit, which removes the status, does not count; a shallow clone, git missing or no such commit gives no time). The item was done before the oldest work sidecar's run id (UTC) or after the newest one. The reason says which and names the likely cause, not a fact, since a host with capture off reads the same: before, likely no session had the capture hooks yet; after, likely its rows are not distilled or delivered yet.
  - *`unnamed`:* no sidecar names it, the spool holds usage rows and the time says neither: its session's rows were not delivered or it ran without the capture hooks, which the store does not tell apart; the reason ends as the two kinds above do. A sprint line names no item, so an item whose every prompt was counted there alone is also here.
- **Not covered:** the prompts outside a window that did not use the kb (they have no usage row, so no sidecar holds them: the shared figure is a lower bound of what a session spent outside its windows) and, for any id but a sprint, the background runs' overhead. With no sidecar and no spool row it prints the `no capture` line and exits 0.

## Project settings

What differs from one project to the next is one file, `backlog.json` at the repository root (`KB_BACKLOG_CONFIG` in the environment names another path, which replaces it); nothing of it lives under `.claude/`, which a headless session cannot write in `default` or `acceptEdits` mode. `bl_base.SETTINGS` is the one place that lists its keys, their types and the kb's own values: `item_dir`, `id_prefixes` (the six kinds' two-letter prefixes), `always_in_scope`, `review_checks`, `research_checks`, `land_stale`, `land_eval` and `land_lint` (a step's command; `[]` for a project with no such step), `lane_module`, `worktree_dir`, `scratch_dir` (a path relative to the clone's top, never absolute and with no `..`, which `config` and `check` refuse: where a worker's scratch directory `<scratch_dir>/<id>/` sits), `forge` (`"gitlab"`, read and merged through glab, or `"github"`, read through gh: the integration remote's forge, which `bl_forge` reads merge requests, pipelines, jobs and job logs from), `forge_project` (`""`: read from the integration remote's URL), `trackers` (`{}`: an item's `external` accepts none), `docs_map` (a repository path to a `doc,pattern` CSV that says which docs describe which paths, as `kb/_self/map.csv` does; `""`: none) and `kb_root` (the name of the kb root, the project's own or an installed plugin's, whose rules `rag.py pack --root` serves; `""`: the project is no root) and `repositories` (`{}`: the project is the one repository the root is, as the kb is; else an object of repository name, lower case letters, digits, hyphens and underscores and never `workspace`, which names the workspace's own files, to the repository's checkout path under the workspace, forward slashes, relative, no `..` and one name for each path: the names an item's `repos` and `repos_if_needed` take, `bl_base.repositories()`). The worker's brief reads them (Running a sprint): `kb_root` set gives the rules as cited fact lines of that root, else `docs_map` set the docs and `##` headings its patterns map the item's touches to. `trackers` maps a tracker's name (lower case) to `{"pattern": a regex the whole id matches, "url": a template with `{id}`, "ref": an optional template with `{id}` and no space, `{id}` by default}`: `{"jira": {"pattern": "[A-Z][A-Z0-9]+-[0-9]+", "url": "https://jira.corp.example.com/browse/{id}"}}`. A key the file leaves out takes the kb's value, so the kb's committed file holds the kb's current values and removing it changes nothing. `backlog.main` loads the file once per process, for the root the command runs on (`--root`, else the tool's own checkout when that is a git working tree, else, for a tool installed as a plugin, the working directory's git root), before it builds the parser, so `new`, `set`, `check`, `land`, `brief` and `dispatch` of a project use that project's item directory, id prefixes, trackers and worktree directory; `bl_base.setting(NAME)` reads one effective value of it at call time, and the accessors of `bl_base` (`rel_dir()`, `kinds()`, `id_re()`, `always_in_scope()`, `review_checks()`, `research_checks()`, `worker_dir()`, `scratch_dir()`) are made from it, never copied into a constant at import. A new setting is one row of `SETTINGS`. The modules read them through `bl_base`: `bl_land` the land steps (an empty command is a step `land` skips), `lane_module` (the module `unlanded_code` asks which lane a path belongs to), `worktree_dir` (also `bl_ci.in_worker_worktree`, `dispatch`'s worktree path), `scratch_dir` (`dispatch`'s and `brief`'s scratch path) `forge_project` (the one project every `bl_forge` call names: `land`'s request read and description PUT, `merge`, and the pipeline, job-list and job-log reads of `red-pipeline`, the intake `ci` detector and the query log's delivery CI check, which run no glab or gh themselves; `""` keeps the project the remote's URL names) and `forge` (`bl_forge`'s arm, glab or gh; the gh arm reads state and its merge and description verbs refuse; a url-read caller with no setting takes the arm of the url's forge, github.com being GitHub), and `bl_cli.id_shape()` the id prefixes.

`backlog.py config` (the handler is `bl_base.cmd_config`, which `backlog.py` registers, since `bl_base` imports no `bl_cli`) prints each setting with its value and its source (`file` or `default`) and exits 0. A file that is not a JSON object, an unknown key or a value of the wrong type is refused naming the key (`config` exits 2, `check` reports it); the key keeps its default meanwhile.

## Writing about items

Every message, report, commit body or note that names an item gives its id and its title together: `ST-pbonxqx4 “Direct push on the real origin”`, never a bare id. The tool's own output does the same. A list of ids alone tells the reader nothing.

An item is published with the repository, so it never holds this host's computer name or its user's name: placeholders only (`PL-LT-00123`, `jan.kowalski`). `backlog.py check`, and so the push gate, refuses an item whose JSON holds a piece of either, naming the item's id and the field (`gates[0].question`) and withholding its title, the one exception to the rule above; its output never prints the name or the piece. It answers BG-477tasb3, where checks written to keep the names out of a report spelled pieces of them, and the leak scan (addresses, tokens, GUIDs) does not look for names. Checks that guard against host or user names read them from the environment at run time, never spell them: `COMPUTERNAME` and `HOSTNAME`, the socket host name's first label, `USERNAME`, `USER` and `LOGNAME` (getpass when none is set), and the profile folder's name (`USERPROFILE`, `HOME`). A name of more than 8 letters and digits also has its Windows 8.3 short form as a piece (`jankow~`, as a TEMP path's `JANKOW~1` profile folder), unless a generic name starts with its first six. No command prints a piece either: every line `backlog.py` writes (a title in `list`, `tree`, `show` or `done`, a repro's output, a refusal, the session hook's message) has it replaced by `<name withheld>`, so a name never reaches a line an agent copies into a commit message. A piece is the whole name, it without separators, each part between non-alphanumerics and each CamelCase part of those (`JanKowalskiCorp`: `jankowalskicorp`, `kowalski`; `XYZ-PC01`: `xyz-pc01`, `xyzpc01`, `pc01`), kept when it has a letter, 5 characters or 4 with a digit, and is not a name every CI runner, container or fresh install shares (`runner`, `container`, `desktop`, `project`: `bl_base.GENERIC_NAMES`), so an ordinary short word never matches; a name made only of such parts (`gitlab-runner`, a shell executor's account; `ContainerAdministrator` and `ContainerUser`, a Windows container's) gives no piece at all, and a Kubernetes pod's random five-character suffix (`bl_base.POD_SUFFIX`) is no piece of its own, so `check` and the push gate never refuse kb text on a CI machine for naming it; it matches case-insensitively anywhere in a string value or key. The project's own repository paths, read from the git remotes' URLs (`namespace/project` and `namespace%2Fproject`; a URL or git's scp-like `[user@]host:path`, the user optional, git's output read as UTF-8 with replacement so a non-ASCII remote never crashes `check`), are left out of the match, since a namespace can equal a user's name; the name anywhere else is still refused. `check` also refuses an item whose text (every string of its JSON: title, goal, repro, `repro_reason`, notes, gate questions, options, recommendations and answers) has a leak-scan hit (`kbcommon.leak_hits`, urls stripped as the scan of tracked files strips them, with the allowlist of `_tools/tests_allowlist.txt`, read by `kbpublic.parse_allowlist`), naming the item's id, the field and the kind (secret, home, ip, email, guid), never the value, so a bug filed with a quoted address or id is refused before it is committed.

## Changing this process

A new field, state, command or rule is added only for a failure that happened, and its commit names that failure. A mechanism that no longer catches anything is removed the same way. The project settings and the constants made from them, the refusals, the `Backlog` class, `git` and `run`, the scope helpers, the name guard `say` prints through and the commit helpers live in `_tools/bl_base.py`, which `backlog.py` and `bl_intake.py` import and which never imports `backlog`. A subcommand registers itself: its module calls `bl_cli.register(name, handler, add_arguments)` (`_tools/bl_cli.py`) with `handler(bl, args)` and a function that adds its arguments to the parser, in the order the usage text lists it, and `main` in `backlog.py`, which builds the parser from that registry and dispatches, is not edited: `main` holds no `add_parser` call, and a name registered twice is refused. A new refusal has one planted failure in the suite, within the ceiling (`_tools/tests_ceiling.json`). `backlog.py check` runs in the gate, so a broken item file fails it.

`_tools/bl_check.py` owns the checks: `validate` (the rules above), the knowledge an item names and its state, the host and user name findings, the repro and no-op warnings, and the `check` and `selectors` commands, which it registers with `bl_cli` itself when imported, `backlog.USAGE` putting them in the usage order; `backlog.py` defines none of it and `bl_check` never imports `backlog`.

`_tools/bl_plan.py` owns the plan side: the rules about code and its docs (`stale_touches`, `docs_after_code`, `docs_warnings`, with `touch_paths`, `dependencies` and `dependents`, which they share), the host-check gates, where a dependency outside a sprint stands (`outside_deps`) and the `start` command, which it registers with `bl_cli` itself when imported, `backlog.USAGE` putting them in the usage order; `bl_check` imports `bl_plan` for the rules `check` runs and `bl_plan` never imports `bl_check`, so the two form no cycle; `backlog.py` defines none of it, `bl_plan` never imports `backlog`, and no `bl_` module imports another in a cycle.

`_tools/bl_land.py` owns the landing side: `done` (the checks and the evidence), `land` (the rebase and the steps to the integration main, naming the `code/<id>` branch through `kg_lane`, with the worker's worktree release and the stuck merge request line), `close`, and what they share (`item_commits`, `unlanded_code`, `out_of_scope`; `run_check`, which `backlog.py`'s `host-check` and a bug's repro run through too, and which gives each run an isolated query log home, is `bl_base`'s, so `bl_ci` runs a repro without `bl_land`); it registers `done`, `land`, `merge` and `close` with `bl_cli` itself, `backlog.USAGE` putting each in its own usage position; the readiness rules `done` reads (`waits`, `open_gates`) sit in `bl_base`, below it; `bl_land` imports `bl_base`, `bl_check`, `bl_intake` and `kg_lane`, never `backlog`; `backlog.py` defines none of it, `bl_land` closes no import cycle, and `land` names the branch through `kg_lane` and never sets `kbgit.KB`.

`_tools/bl_ci.py` owns the CI side: the pipeline readers through its own `run` (`latest_pipeline`, `covered_by_revert`), the failure fingerprint helpers (`normalise_error_line`, `first_failure`), the red-main bug (`red_bug`, `bug_with_fingerprint`, `add_pipeline`) and the `red-pipeline` and `intake` commands with `hook_intake`, which it registers with `bl_cli` itself (`backlog.USAGE` orders them) and which `backlog.py` re-exports under their old names for `ql_deliver`; it imports `bl_base` (the runner of a check) and `bl_intake`, never `bl_land` or `backlog`, and `backlog.py` and `ql_deliver` (the red-main bug of a reverted push) import it; `backlog.py` defines none of it and `bl_ci` closes no import cycle.

`_tools/bl_view.py` owns the read-only views: what is ready (`ready`), the near-duplicates (`words`, `similar`, `is_near`), `horizon` and its SessionStart hook form (`hook_json`, `clip`), and the `similar`, `list`, `tree`, `find`, `show`, `next`, `held` and `horizon` commands, which it registers with `bl_cli` itself when imported, `backlog.USAGE` putting them in the usage order; `backlog.py` re-imports `similar` and `is_near` for `new` and `cmd_horizon` for its hook dispatch; it imports `bl_base`, `bl_check` (the knowledge lines) and `bl_plan`, never `backlog`, and only `backlog.py` imports it; `backlog.py` defines none of it and `bl_view` closes no import cycle.

`backlog.py` is the facade: its usage text, the usage order of the subcommands (`USAGE`, which `bl_cli` registers them in) and `main`'s dispatch, nothing else. The item writers live in `bl_items.py`: `new`, `fmt`, `claim`, `release`, `answer` (with `run_decide`, `record_decision` and `commit_answer`), `set` (with `changed_item`, `changed_items`, the `SET_` refusals, `appended` and `reclass_gate`), `move`, `reopen`, `gate` (with its size-cap rules), `host-check`, `fire`, `drop`, `referrers` and `goal`, with `parse_cmd` and their argument builders, kept together because each writes item files through `changed_items` and the shared refusals (`changed_items` refuses every error `check` counts that the edit adds, a refused repro or check and a doc-only task that waits for another item's code included; `reopen` alone lets through the reopened item's own gone touches and refused repro or check, which it only reveals); importing `bl_items` registers their commands. `backlog.py` defines no name other than `USAGE` and `main`, and none that a `bl_` module also defines; no writer is in `backlog.py` and `bl_items` never imports `backlog`.
