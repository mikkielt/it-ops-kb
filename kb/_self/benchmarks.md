## Scenarios: `run`

`benchmarks.py` holds the command line and the `SCENARIOS` registry, the scenarios sit in `bench_lookup.py`, `bench_retrieval.py`, `bench_querylog.py`, `bench_load.py` and `bench_install.py`, the harness in `bench_core.py`, the report tables in `bench_report.py`, the question pool in `bench_pool.py` and the isolated instances of `repro` in `bench_repro.py`, the sandbox, inputs and plan of `multi` in `bench_multi.py`: `run` re-runs all scenarios or the named ones (paid `claude -p` runs through `agent_bench.py` and its own, from a throwaway clone with the query log off and a local bare `origin`; the query-log scenarios in mode `local` under a scratch directory) and writes their rows to `kb/_self/reports/benchmarks.csv` (a same-day re-run of a scenario replaces its rows; a `p95_ms` row is the nearest rank, `ceil(0.95 * n)`, of its n timings [CODE _tools/bench_core.py#stat_rows] [CODE _tools/bench_retrieval.py#s_verdict]) or to FILE

`run new-model` pits a new model against the one it replaces on a curated subset, pinned by id in one batch (`NEW_MODEL` in `_tools/bench_install.py`)

`run route-by-verdict` pits `router-pinned` against the bare web arm `web-sonnet-5-5` and the kb arm `sonnet-5-5` on six questions and records per case the route the pack took, each arm's cost, time and checks, and whether the router stays within the operator's cost bar ("Routing by verdict against the bare agent" in `kb/_self/reports/benchmarks.md`) [CODE _tools/bench_lookup.py#s_route_by_verdict]

`run navigation` puts three questions (a query-log delivery rule, a `kbgit.py` trailer or sync rule, a benchmark scenario) to fresh Sonnet sessions in a throwaway clone with read-only tools, scores each answer by the function and test names it gives, never by a path, and records per case turns, tool calls, files read, input tokens and checks under the arm `--arm` names (default `current`; a run replaces only its own arm's rows of the day) ("Finding the code" in `kb/_self/reports/benchmarks.md`) [CODE _tools/bench_lookup.py#s_navigation]

`run freshness` (no model, no paid run) looks up each answerable row of the question pool (route `good`; `--sample N` keeps N rows of each kind, drawn with `--seed`) with the cited sources revalidated live (`kbfacts.pack_many` with `revalidate=True`, within each provider's pacing and the revalidation's time budget), and records for all lines and per host (of the source whose outcome a line prints, the worst of those it cites) the printed `DOC` lines by outcome (`current`, `moved`, `not_found`, `source_dated_only` and `not_checked`) with the shares of the first three, the requests made (counted at `provider.request`; a request the time budget refused was not made) and the median and p95 (nearest rank) wall time of the lookups that cite the host, and for all also the questions, the slowest lookup (`max_s`), the lookups the time budget cut (`budget_spent`) and the sources by how they were answered

`--dry-run` prints per host the sources a run would ask, the lines and questions that cite them and one request per source per question as the least, asks nothing and writes no row ("Freshness of the cited sources" in `kb/_self/reports/benchmarks.md`) [CODE _tools/bench_retrieval.py#s_freshness]

`run session-load` (no model, no paid run; a host with no `os.wait4`, Windows, or no `sh` skips it) replays the hook events of one Claude Code session through the hook commands of the throwaway clone's own `.claude/settings.json`, each started as Claude Code starts one (`sh -c`, the event as JSON on stdin, `CLAUDE_PROJECT_DIR` set) with the query log home planted under the scratch directory (`CLAUDE_PLUGIN_DATA` and `CLAUDE_PLUGIN_ROOT` both set), a `claude` that fails at once first on PATH and a coord store of its own: the synchronous hooks of an event one after another in file order, the async ones at once and not waited for until the last event, after which the replay waits for them to exit and for any process left running in the clone [CODE _tools/bench_load.py#Replay]. The arms are `A` (every hook), `B` (arm `A` and the kbmon pane's commands, below), `C` (a command naming `coord_hook.py` or `querylog.py` left out) and `D` (no hook) [CODE _tools/bench_load.py#arm_hooks], named by `--arms` (default `A`, `C` and `D`; `B` runs only when named, as it adds a window to each phase; `pool`'s arms go in the same flag, each scenario taking its own, and `--arms` with `pool` and `session-load` both named needs a pool arm too); each runs in the phase `idle` (SessionStart, SessionEnd) and `working` (three prompts between them, each with two tool calls and a Stop, `WORKING`) [CODE _tools/bench_load.py#events]. Arm `B` stands for an interactive session, the only one in which the kbmon-pane mod works (it returns at `session.start` when `isInteractive` is false, `kb/public/claude/mods.md`): over a `--window` of seconds per phase (default `WINDOW_S`, 150, which holds three runs at the mod's schedule) it runs, as `.claude/skills/kbmon-pane/hooks/register.tsx` does, `python3 _tools/kbmon.py --once` and then `--status all` (a pane run), the first after the mod's `FIRST_MS` and then every `--pane-every` seconds (default the mod's `REFRESH_MS`, both read from the file in the replay clone); a tick that falls while a run is going does nothing, as the mod starts no second refresh, and a run that started inside the window is waited for [CODE _tools/bench_load.py#Replay]. Each pane run asks both commands, whereas the mod asks `--status all` only when its needs-you row changed and `--receipt` only when the alert rows change, so a pane run here is the heavier refresh. The pane's CPU, memory and starts are in the class `kbmon` (`kbmon.py`) and the classes of the processes it starts, over the window and not over `NOMINAL_S`: arm `B`'s `spawns_per_min` is the hooks' starts per minute of the session plus the pane's per minute of the window. Per phase arm `B` also writes `pane_runs` (case `<phase> all`) and `pane_failures` (case `<phase> replay`, a pane command that exited with 2 or more; `kbmon.py` exits 1 while an alert is on). One unmeasured replay of arm `A` warms the caches, and one unmeasured run of the pane commands when arm `B` runs; each rep then replays every arm and phase once, and a row is the median of the reps. A run of some arms keeps the rows of the arms it did not run in the same record, so `--arms B` adds to a record of `A`, `C` and `D` [CODE _tools/benchmarks.py#main]. Every hook command is measured by `os.wait4` (CPU seconds, utime plus stime of the command and the children it waited for; peak memory, `ru_maxrss` converted to MiB by platform, bytes on macOS and KiB on Linux) [CODE _tools/bench_load.py#maxrss_mb], a sampler of `ps` follows the processes under it for their memory [CODE _tools/bench_load.py#Sampler], and a `sitecustomize` on `PYTHONPATH` logs, through an audit hook, each process a Python program of the tree starts, so the starts of a program that is not Python are not counted [CODE _tools/bench_load.py#SITE]. The classes are the host panel's (`mon_host.kind_of`: `kbmon`, `fseventsd`, `tests`, `kb-tools`, `claude`, `other`) and `git` and `lsof` [CODE _tools/bench_load.py#process_class]; the CPU of a hook command goes to the class of its own command line, its children's starts and memory to their own classes. The rows are, per case `<phase> <class>` (each class that started a process, and `all` for their sum) and arm, `cpu_s` (its note names the host's cores, the 1-minute load at the start of each rep and `warm`), `rss_peak_mb`, `rss_mean_mb` (the mean of the samples) and `spawns_per_min` (the starts of a session of `NOMINAL_S` seconds, so the arms compare); per phase `<phase> replay` the `wall_s` and the `hook_failures` (commands that exited non-zero); per hook command, case `EVENT script arguments (tool)`, `sync_ms`, or `async_ms` for an async hook, the median of its runs, and, case `<phase> hook <script arguments>`, `spawns`: the command and the processes its tree started per replay, so the starts of each hook show and the starts of arm `A` less those of arm `C` are those of the hooks `C` leaves out [CODE _tools/bench_load.py#s_session_load]. Every hook that both arms run starts the same processes in every replay: each replay has a fresh query log home, coord store (`KB_COORD_STORE`) and working tree, the intake hook's drift cursor is removed, and one commit in the replay clone that changes the mode of each backlog item file leaves no item eligible for the drift scan, whose checks otherwise run within a wall-clock budget and start as many processes as fit it, which moves with the host's speed and load; the cost of the intake hook in a clone where those checks run is therefore not measured [CODE _tools/bench_load.py#pin_drift]. `--fs-usage FILE` (with `session-load` named alone, else exit 2; a missing file or one with no wide `fs_usage` line also exits 2) reads a capture the operator makes by hand and starts no replay and no model: `sudo fs_usage -w -f filesys > fs_usage.txt` beside the session, which this tool never runs (a run without `--fs-usage` prints that command, and no check or run of the tool calls `sudo`), and per process class and for `all` writes, case `capture <class>`, arm `capture` (so a same-day run of the replay arms keeps these rows and the reverse), `file_reads` (an `open` whose mode string starts with `R`, a `read`, `readv`, `pread`, `preadv` or `RdData` line; writes and `WrData` left out) and `distinct_paths` (the paths of those lines; a descriptor read prints none, and `fs_usage` keeps only a path's last 28 bytes, so two long paths may count as one). The class is the process name before the thread id each line ends with (the number after the dot is a thread id, `kb/public/python/macos-fs-usage-output.md`): any `python` is `kb-tools`, `git`, `lsof`, `claude` and `fseventsd` are their own and every other name is `other`; a class with no line is written as 0, and an open that failed counts as a read when its mode string starts with `R` [CODE _tools/bench_load.py#read_capture] ("What one session costs the host" in `kb/_self/reports/benchmarks.md`)

`run pool` runs every row of the question pool (the public file and, when this host has it, the query-log file) as a fresh session per question on the arms `haiku-5-5`, `haiku-4-5` and `sonnet-5-5` (the kb's tools, models pinned by id; `opus-5-5` too, when `--arms` names it, as a run with no `--arms` leaves it out, and then on its sanity subset of four kinds, `bench_pool.SUBSET_KINDS`, unless `--kinds` or `--arm-kinds` name others; `--arm-kinds opus-5-5=all` runs every row, as a model change needs), `router` (`kb_ask.py`'s routing with the routed models pinned), `hook` (the `kb:` hook through `_tools/kbpy`, no model, its wall time recorded) and, on the kinds of `WEB_KINDS` only, `web-haiku-5-5` and `web-sonnet-5-5`

`--arms`, `--kinds` and `--reps` select the set, `--arm-reps ARM=N` and `--arm-kinds ARM=K+K` (comma separated pairs, or the flag repeated) give one arm its own reps and kinds, an arm they do not name taking `--reps` and `--kinds` (a web arm still takes only the kinds of `WEB_KINDS`; the value `all` is every kind), and an arm they name that the run does not run (`opus-5-5` without `--arms`, say) is an error that exits 2 [CODE _tools/bench_pool.py#parse_arm_map], `--sample N` keeps N rows of each kind of the pool, drawn per kind by a generator seeded from `--seed` before any kind filter, so one kind's rows and the other arms' stay as they were [CODE _tools/bench_pool.py#sample_rows], `--effort` the levels (`low` passes `--effort low`, `default` passes none; Haiku 4.5, which Claude Code gives no effort level, runs once), `--dry-run` prints the plan per arm label (rows or groups, reps) and starts no model, and exits 2 for any other scenario, or none named, as only the scenarios of `PLANNED` in `benchmarks.py` have a plan and the others would start their paid runs [CODE _tools/benchmarks.py#PLANNED]

`--shape fresh,session` runs both shapes in one run, the fresh runs first, under one `--max-usd`, one set of spend rows and one record date, the `ARM/session` key of `--arm-reps` and `--arm-kinds` giving an arm its own value in the session shape only (the `ARM` key applies to both, and each session arm's groups are built from its own kinds) [CODE _tools/bench_pool.py#plan_legs]

`--shape session` runs the pool in groups of six rows (mixed kinds, never two rows of one `source`, ordered by a generator seeded from `--seed`) each in one `claude -p` session on the kb arms `haiku-5-5` and `sonnet-5-5` (the first question starts it with `--session-id`, each later one resumes it with `--resume`), under arm labels ending in `/session`, and records per position in the session `marginal_input` (the question's last prompt less the last prompt of the question before it) and `cache_read_share` (cache reads over input) with the checks, beside the per-kind rows [CODE _tools/bench_pool.py#run_sessions]

`--jobs N` (default 1) runs up to N of the pool's `claude -p` runs at once, on threads around the subprocesses: the unit is one run (shape `fresh`) or one session (shape `session`, its six questions in order inside it), the rows and their order are those of `--jobs 1` whatever order the runs finish in, `bench_core.SPEND` is updated under a lock, and the date `Bench` reads once at the start stamps every row, so a run that crosses midnight is one record [CODE _tools/bench_pool.py#run_tasks]; a kb, session or web run whose `claude -p` outlives its timeout is one error run, as a router or hook run is, and the chunk's other runs and rows are written [CODE _tools/bench_pool.py#execute_run]; a session question's cost, `out`, model usage and web searches are its share of the running totals a resumed run's result event reports (the total less the question before it's, per model), and each pool run's `spend_usd`, `spend_input_tokens` and `spend_output_tokens` rows carry the arm `paid: <its arm labels>`, so a same-day run of other arms keeps them and the records and spend tables sum a record's rows, and a same-day run of arm labels that an earlier spend row of the record also names takes them out of that row, which keeps its remaining labels with its spend, tokens and runs totalled from the record's own rows (`settle_spend`, run after the rows are merged), so `pool verify` holds after any partial rerun [CODE _tools/bench_pool.py#settle_spend] [CODE _tools/bench_pool.py#live_session_runner]

`--max-usd X` starts no new run of a shape once the finished runs of the scenario, the runs in flight and the run to start would pass that shape's part of X (what is left of X shared out by the shapes' estimated spend, the last shape taking all that is left [CODE _tools/bench_pool.py#leg_cap]), each run in flight counted at the mean cost of its kind on its arm label, a session at its questions' together less what its answered questions have cost [CODE _tools/bench_pool.py#run_tasks], the runs of a shape starting one of each arm label in turn so that a run the cap stops leaves every arm label some runs, not the last labels none [CODE _tools/bench_pool.py#interleaved] (the first run of a shape starts whatever it is priced at while the shape's part is above 0, and the runs in flight finish, so the spend passes X only by the runs that cost more than the mean of their kind), writes one `spend_stopped` row per arm label (case `not started`, the value the units not started, the note their `id#rep` or `group N#rep` names in the order they would have run) and exits 1 [CODE _tools/bench_pool.py#s_pool]

`--dry-run` also prints an estimate of the spend per arm label: each run priced at the mean `cost` of its kind's cell of the label in the newest earlier pool record of the results file that holds one, else of the label's `all` cell in its newest (what the runs were billed, web searches included), so that a label's kinds are priced each at its own cost, else, for a kb arm with no record of its label, on the mean per-run counts (uncached, cache write, cache read, output) of the same cell of the same effort and shape label of another kb arm, the newest record first and Sonnet 5.5 before the others, priced at `PRICE` (the arm's own model, its lowest price tier, cache writes at the rate of the run's billing surface, `bench_core.write_rate`), else the stated default `DEFAULT_RUN` (a Sonnet 5.5 lookup with the kb tools; none for the hook arm), web searches left out of the last two; a label whose kinds are priced differently also prints a line per kind [CODE _tools/bench_pool.py#assumed_run]; over `--max-usd` it says so and still exits 0 [CODE _tools/bench_pool.py#estimate_lines]; a run records per kind and arm label (`model:level`) and for all kinds the means of `input`, `cache_read`, `cache_write`, `effective_input`, `out`, `start_ctx`, `pack_tokens` (the size of the kb tool results in the stream), `tool_calls`, `turns`, `wall_s` and `cost`, the checks passed, the runs fully right, `fixed_share` (`start_ctx` over `input`) and `tokens_per_right` (the effective input of the runs over those fully right) with the 95% bootstrap interval of `tokens_per_right` and of the right share over the cell's pool rows (`tokens_per_right_lo`/`_hi`, `right_share_lo`/`_hi`, a fixed seed, a row's reps kept together) [CODE _tools/bench_pool.py#interval], each run's record going to the scratch runs file; a same-day run replaces only the rows of the arm labels it ran ("A question pool over the kb, router, hook and web arms" in `kb/_self/reports/benchmarks.md`) [CODE _tools/bench_pool.py#s_pool]; a scenario the host cannot run prints `<name>: skipped: <reason>` and writes no rows (`querylog-hooks` and `kbpy` without `sh` on PATH, as from PowerShell or cmd) [CODE _tools/bench_core.py#need_sh]; the `claude` shims that scenarios put first on PATH get a `claude.cmd` beside them on Windows, which resolves commands only by a PATHEXT extension [CODE _tools/bench_core.py#shim_dir]; a run is priced at the pinned model its transcript reports, from one table, `PRICE` in `bench_core.py` (input, output, 5-minute cache write, cache read and 1-hour cache write per MTok of `claude-haiku-4-5`, `claude-haiku-5-5`, `claude-sonnet-5`, `claude-sonnet-5-5` and `claude-opus-5-5`, from the pricing page, source S2131, a run's Sonnet 5.5 cache reads at the rate the cost figure of its Claude Code version counted, $0.20 up to 2.1.295 and the page's $0.10 from 2.1.296 (`READ_BEFORE`, `read_price`; a version that is empty or unknown takes the earlier rate; the conflict in `kb/public/_conflicts.md` is resolved); Haiku 5.5 has one price up to 100,000 prompt tokens and a higher one over, applied per request, and a run records its highest tier in the row's note; `usage_sum` prices each request's cache writes at the TTL they were written for, by the `cache_creation` split of the request's `usage` that a `claude -p` stream carries when it has one, else at the rate of the run's billing surface, `BILLING_SURFACE`: one hour on a subscription, five minutes on an API key, and `est_cost`, the effective input, the dry-run estimate and the pool's list cost all read that one rule), the alias arms (`haiku`, `sonnet`, `opus`) resolve to the model the run reports, else to the one the alias names on the run's Claude Code version (`ALIAS`; the alias's first model when the version is empty or `?`), and a model with no row in the table stops the scenario instead of being priced by guess [CODE _tools/bench_core.py#usage_sum]

## `report`

`report` generates the report's tables from that file (the `bench:` markers `table`, `records`, `spend`, `matrix` (one metric by case and arm), `effort` (the `low` and `default` levels per model), `session` (`marginal_input` and `cache_read_share` by position in the session and arm label) and `multi` (the tables of the scenario `multi`, one per case, with the arms `concurrent`, `sequential` and `delta` side by side, then per kb arm and bare twin of each record and knob set tokens and USD in all and per correct answer, verified fact and passing item with a `kb minus bare` column (kb lower, kb higher or equal), `no data` where no row is behind a figure, a research case's `facts_verified` (kb) beside the twins' own `facts_matched`, and `not comparable` for a twin's per-verified-fact figures, whose count is the kb agent's [CODE _tools/bench_report.py#multi_tables])), and `--check` exits 1 when a table or a number in `README.md` disagrees with it, or when a marker other than `spend` and `multi` names a scenario with no rows in the file (the `multi` marker then says so itself) [CODE _tools/bench_report.py#empty_markers]

## `pool`

`pool build` writes the question pool `kb/public/_retrieval/bench_pool.csv` (columns `id`, `kind`, `domain`, `phrasing`, `source`, `question`, `checks`, `expected_route`; `checks` is a JSON list of regexes, each row has at least one; the kinds are `fact`, `csv_fact`, `multi` and `synthesis` (40 rows of `lookup_eval.csv`, stratified by domain, their regexes written by Sonnet in one `claude -p` call from the eval question and the line of its expected article or data file that best matches it, never a heading, a front-matter line, a csv header, a table header row, a line of a code block, a line that wraps the one before it (a paragraph with no list marker opens a line of its own at each sentence, so the line that states a Summary's limit is not lost to the paragraph's first line, while the rarity below counts only the lines that do not) or a line that does nothing but point to another article or data file (a fact that ends in a pointer clause is a line, and its pointer clause is not read): a csv file's data row is a line like an article's body line, and a row over several lines is one; words count by their first five letters (`replaced` meets `replacement`) and an identifier with underscores is one word (`win_dsc`), each shared word by how rare it is among the file's lines, so the file's own subject on nearly every line counts for little, and half as much when the line has the stem only in another form of the word, a line that holds four or more of the question's words in a row, in the question's order, scores more for each word from the fourth on, terms of one stem counting once (the question's own phrase, over a line with the same words scattered), a `SNIPPET:` line scores a tenth less than a prose line of the same words, a line needs two shared words, and a tie goes to the line sharing more whole words, then to the first line [CODE _tools/bench_pool.py#fact_for], an unusable regex replaced by a check for that article's path), `heldout` (20 rows that name `lookup_heldout.csv` cases by id, drawn from the cases that name an expected article and that no earlier pool held [CODE _tools/bench_pool.py#EARLIER_HELDOUT], and hold no question text: `bench_pool.question_of` reads it at run time, the held-out rule of "Conduct for changes" in `maintaining`), `offkb` (15 of the off-kb list, route `none`), `false_good` and `near_miss` (verdict design misses, with two eval questions typed with a lowercase brand), `gap` (open entries of `_gaps.md`), `count`, `cites`, `decision` and `conflict` (route `tool`: articles per domain, who cites a source id, an active decision, two sources of a `_conflicts.md` entry), `snippet` (SNIPPET lines, checked by their code tokens), the five scenario kinds, six rows each, read from `kb/public/_retrieval/bench_scenarios.csv` (columns `kind`, `domain`, `question`, `answer`, `route`, `note`; the file's rows join the pool as they stand and the build asks no model for them: `sc_present`, a question whose answer the kb states, expected route `good` and a check of the regex of the kb line that answers it; `sc_partial`, the kb has part of it, route `split`, that regex and a kb-lacks phrase (`LACKS_CHECK`); `sc_absent`, the kb lacks it, route `web` (a `none` verdict, or a false good the row's note marks), the pool's `GAP_CHECK`;
