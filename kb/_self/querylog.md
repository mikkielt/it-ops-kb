# Query log: a self-improving lookup pipeline

Every kb lookup leaves a redacted, judged record in the repository, in `kb/_querylog/`. `learn` turns the records into findings, and `apply` turns accepted findings into eval rows, aliases, expansions and `_gaps.md` entries, pushed straight to `main` once the local gate passes. The aim is better knowledge handling by agents, not an approval workflow for people: no merge requests unless a conflict needs one.

- **Stages,** in the order the data flows and in the order of the sections below: capture (hooks and tools, a local spool) -> distill (stdlib rules, then Haiku in batches) -> the store -> learn (deterministic findings) -> apply (the local gate) -> delivery (a direct push) -> reporting.
- **Code:** one entry point, `_tools/querylog.py`, which every hook and person runs (its commands are in `kb/_self/tools.md`), and one module per stage (the table below); `_tools/ql_base.py` holds what the stages share: where the files are, the per-user config, the lock, atomic writes, the commands they run and the `claude -p` call. Standard library only, plus the `claude` CLI for Haiku; macOS, Linux and Windows.
- **Why it can be built from hooks:** `UserPromptSubmit` gives the prompt with `session_id` and `prompt_id`, and `Stop` gives `last_assistant_message` for the same session (`claude/hooks.md`, DER S743; the answer `QK-self-improving-lookup-pipeline-query-logging` in `kb/public/_answers.md`).

| stage | module | commands |
|---|---|---|
| capture | `_tools/ql_capture.py` (`record`, which `kb_hook.py`, `kb_ask.py`, `fetch.py` and `census.py` call) | `capture`, `where` |
| distill | `_tools/ql_distill.py`, with `_tools/redact.py` and `_tools/kbusage.py` (a prompt's token counts from its transcript, `kb/_self/usage.md`; its `tree` command is a report outside the stages) | `launch`, `distill` |
| store | `_tools/ql_store.py` (the run and findings files, their readers and writers, the gates) | `check` |
| learn | `_tools/ql_learn.py` | `learn` |
| apply | `_tools/ql_apply.py` (eval rows with their fixes, the gap step), `_tools/ql_research.py` (research, the quote check, the research queue) | `apply`, `gap-replay`, `quotecheck`, `queue`, `close` |
| delivery | `_tools/ql_deliver.py` (plugin hosts and cloud sessions too) | `apply` with its push |
| reporting | `_tools/ql_report.py` | `digest`, `status`, `show` |

## Rules

- **One owner per truth.** The store owns logged lookups; findings, the digest and every change `apply` makes derive from the store and the kb.
- **Run metadata once per run file**, in its header line, never per entry.
- **Derived state converges.** A second run on unchanged inputs changes nothing.
- **Stages stay separate.** Miss, candidate gap, gap, candidate fact and claim are distinct states, and each promotion is recorded on the finding.
- **`learn` writes findings; `apply` turns accepted findings into changes.** Nothing else writes kb files.
- **Deterministic code first.** An entry's question and citations come from the kb's own rows. Haiku only judges: whether the reply answered, the best among candidate articles code listed, and whether the question identifies someone. Nothing it writes is stored; it never picks an article code did not offer, never writes a fact, and never decides a gate.
- **Every gate has one planted failure in the suite:** the input the gate must refuse.

## Surfaces

Every row has `id` (a fresh UUID), `ts` (UTC, milliseconds), `surface` and `v`, its row format (Spool); a hook row also has `session_id` and `prompt_id`. Fields that would be empty are left out.

- **Rows join on `prompt_id`**, a common hook input field (`claude/hooks.md`, DOC S743). A tool that writes from inside (`kb_ask.py`, `fetch.py`, `census.py`) sees no `prompt_id`: its row goes to the tools file, and distill attaches it to the prompt of the same clone whose `UserPromptSubmit`-to-`Stop` window holds the row's time; a row in no window is an entry of its own (a run outside Claude Code).
- **Fetches and answers count only beside the kb**, checked at capture: a `fetch` or `stop` row is written only when the prompt already used the kb (a `kb_hook` or `mcp` row, a prompt with a `kb_intent`, or a tool row since the prompt began). A fetch made before the prompt's first kb call is not logged, and an async kb row that lands after the `Stop` hook ran loses that answer.
- **Failures count.** `PostToolUse` fires only after a successful call, so the same hook runs on `PostToolUseFailure`, which gives the `error` text (`claude/hooks.md`, DOC S743). A failed shell command is read for a fetch (the error's status) and for a refused `backlog.py done` (below).
- **Shell commands are parsed only for `curl`, `wget` and `backlog.py`**, in `Bash` and in `PowerShell` (which takes shell commands on Windows, `claude/hooks.md`, DOC S743): the first http(s) url after the command word gives host and path. Command-text parsing undercounts (a script, an alias, a variable), which is why `fetch.py` and `census.py` log from inside; other commands are not counted.
- **A `work` row is one successful `backlog.py claim`, `done`, `release`, `land` or `merge`, or one refused `done` (not one refused only for the code-lane order, `unlanded-code`: the `code/<id>` request still to merge is the orchestrator's landing, no rework; `ql_capture.only_unlanded` reads the error text for it and stores none).** The parser (`ql_capture.work_action`) reads the command in pieces split at unquoted `;`, `&`, `|` and newlines, and takes the first piece that has the script's name after nothing but an interpreter or launcher (`python3`, `py -3`, `sh .../kbpy`, a PowerShell `&` call, a path), its flags and environment assignments, then an optional `--root`, the action and an item id; the options after it (`--by`, `--commit`, `--trailer`, `--branch`, `--wait-merge`) are skipped and never kept. A successful `land` or `merge` is stored as `action: done` (`work_action` reads both as `done`; `work_call` gives the command as typed): `land` runs `done` as a process of its own, which no hook sees, so the `land` or `merge` the session ran is the row that closes the session's window of the item, as a `done` does, the first pass of a code item's `land` included (it exits 0 while the merge request is still to merge). **A `done`, `land` or `merge` launched in the background writes no `done` row at its launch:** its `PostToolUse` fires when the call returns at launch, with a `backgroundTaskId` and none of the command's output or exit status (`claude/hooks.md`; `run_in_background` in its input, or a `backgroundTaskId` in its result for a command that reached its timeout, `ql_capture.launched_in_background`), so capture stores `action: done-pending` instead, which opens and closes no window. The row that closes the session's window of the item is then a `done` row that `ql_capture.settle_pending` writes, on the prompt of the first later `UserPromptSubmit`, `PostToolUse`, `PostToolUseFailure` or `Stop` event of the session, once the item file `kb/_self/backlog/<id>.json` at the root of the checkout the event's directory is in says `"status": "done"` (the landing's done commit; a file read, no process), unless a `done` or `release` row of the item already followed the pending one (a foreground `land` run after it). A background landing that stops at a step or is refused leaves the file open and so the window open, and its rework prompts stay on the item. The `done` row of a session that never claimed or branched the item opens and closes nothing, and a `land` of another item closes none of this item's windows. A `done --dry-run`, an action piped into another command, any other `backlog.py` command, a command that only mentions the script (`echo`, `git commit -m`, a search, a quoted text) and a command with no valid id write no row. A call that exits non-zero fires `PostToolUseFailure`, not `PostToolUse` (`claude/hooks.md`, DOC S743), and its `error` begins `Exit code N`, so the success path writes no row for it. The failure path (`ql_capture.refused_done`, the same hook command on `PostToolUseFailure` in `.claude/settings.json` and the plugin) writes `action: refused`, with the item id, the subagent's `agent_id` and nothing of the command or the `error`, when the command is a `backlog.py done ID` by the same parser and the first line of `error` is exactly `Exit code 1`, the code `backlog.py` exits with when it refuses (`WORK_REFUSED_EXIT`). No row is written for: an interrupt (`is_interrupt` true); an `error` with no such first line (a shell that could not start, a timeout: `Command timed out after ...`); another exit code (2 is bad usage, 127 and 9009 a missing interpreter); a failed `claim`, `release`, `land`, `merge` or other `backlog.py` command; a `done --dry-run`; a command that only mentions the script. A `refused` row opens and closes no work window (`ql_capture.usage_targets`, `ql_distill.work_windows` open one from `claim` or `branch` and close it with `done` (a `land` or `merge` is stored as one) or `release` only), since the item is not done. The row says the command exited 1, not why `done` did, and a command that joins `done` with another that fails (`done ID && make`, `cd x && done ID`) writes it as well; a pipeline's exit code is its last command's, so a `claim`, `done`, `release`, `land` or `merge` followed by `|` (`done ID | tail`, `done ID 2>&1 | tee`, `done ID || echo`; an `&` of a redirect such as `2>&1` is no separator) is none, for the success event and the failure event alike, since neither says what the action did. A claim or release that fails leaves nothing: the row says the command ran. One command that runs several `backlog.py` actions writes the first only.
- **A session on a `work/<id>` branch writes a `branch` `work` row** (`ql_capture.branch_row`, from the `UserPromptSubmit` capture hook): `action` `branch`, `item` the id of the `work/<id>` branch checked out at the event's directory (read from the repository's HEAD file with no process, as `agent_row` does; only the id and the action are written, never the branch text or a path) and the prompt's `prompt_id`. It is written only when all three hold: the prompt is the session's first (no earlier `prompt` row of the session in its spool file), the item file `kb/_self/backlog/<id>.json` at the root of the checkout the event's directory is in exists with `"status": "doing"` (a file read, no process), and the session's rows hold no `claim`, `done` or `release` of the item. So a worker session started in the worktree of a branch whose item the orchestrator claimed opens that item's work window with no `claim` of its own, while a checkout left on a stale `work/<id>` branch with no item file, an orchestrator whose directory followed a `cd` into a worker's worktree, and a session back in a worktree after the item was done open none: such a session runs no `land` of the item (`land` runs `done` as a process of its own that no hook sees), so no row of it would close the window, and a window `done`, `land`, `merge` or `release` closed is not reopened by the session's later prompts. `ql_capture.usage_targets`, `ql_distill.work_windows` and `ql_distill.rework_windows` treat it as a `claim`: the window stays open until a `done` or `release` row of the same item, and the item is one the session worked (`backlog.py cost` counts it, `bl_cost.open_lines`). A session on no such branch writes none.
- **A subagent's start and stop are `work` rows** (`ql_capture.agent_row`, from the `SubagentStart` and `SubagentStop` hooks): `action` `agent-start` or `agent-stop`, `agent` (a salted short hash of the event's `agent_id`; the salt is `agent.salt` in the querylog directory, made on first use and never committed, so the id itself is never written), `group` (`kbusage.agent_group` of the agent type, lower case, a closed class: `kb-worker`, `general-purpose`, ..., `other`) and `item` when the event's directory is on a `work/<id>` branch (read from the repository's HEAD file with no process; only the id, never the branch text or a path). They carry no `prompt_id`, open no work window and join no prompt. `SubagentStart` can fire more than once for one agent, so a start row is not a dispatch count. Distill turns each pair into an `agent.run` line (the ops sidecar, below).
- **An `ops` row is a closed event** (`ql_capture.OPS_EVENTS`; `ql_capture.ops_problems` is the one function that reads a row's shape, at capture and in the store). Each event has required and optional keys, and a key holds one of the closed shapes of `OPS_KINDS`: `item` and `sprint` (an item id; a sprint's), `token` (a lower-case name of at most 40 characters, a letter first, then letters, digits, `_`, `.` and `-`: a step, lane, check, state or detector, never a sentence), `sha` (7 to 12 hex), `agent` (a salted short hash, never an agent id), `test_file` (a bare test file name, `test_*.py` or `conftest.py`: never a node id or a path), `reason` (a class of `OPS_REFUSED`) and `mode` (`OPS_TEST_MODES`), `ms` and `count` (non-negative whole numbers, capped), `exit` (a whole number, a Windows status code included) and `flag` (true or false); a key may also be a bounded list of one shape or a bounded table of objects whose keys are of these shapes. The events: `land.step` (`item`, `step`, `exit`, `ms`), `land.end` (`item`, `exit`, `ms`, `lane`), `sync.gate` (`ms`; `checks` as a table of `name`, `ran`, `why`, `exit`, `ms`; `scope`, `files`, `push`, `exit`), `done.refused` (`item`, `reasons`, `ms`; `checks`), `sprint.close` (`sprint`, `landed`, `dropped`, `bugs`, `confirmed`, `refused`, `ms`), `ci.pipeline` (`state`, `calls`; `sha`), `intake.detect` (`detector`; `found`, `budget`, `coverage`), `test.run` (`mode`, `ms`, `exit`; `selected`, `total`, `workers`, `passed`, `failed`, `skipped`, `slow` and `files` as tables of `file` and `ms`, `failed_files`), `agent.run` (`group`, `ms`; `agent`, `item`) and `stall.remedy` (`item`, `signal`, `remedy`, `count`: a remedy the retired autopilot took for stalled work; a past event, `ql_capture.PAST_EVENTS`: `record` writes none, and the rows the committed sidecars hold stay readable) and `call.tool` (`tool`, `group`, `outcome`, `size`; `class`, `purpose`, `ms`): one row beside every `PostToolUse` or `PostToolUseFailure` event of a kb tool, a documentation server's tool or a Bash or PowerShell command (the operator's scope; `ql_capture.call_row`), with the tool group (`kbusage.call_group`), the agent group (`main` outside a subagent), the outcome (`ok`, `error` or `interrupt`), the result's size class (`empty`, `lt1k`, `lt10k`, `lt100k`, `ge100k`), the shell command's closed class (`kbusage.command_class`: `tools.<stem>` for a `_tools/` script, `python-c`, `python-m`, `python-script`, `<tool>.<subcommand>` only for a subcommand `kbusage.CLASS_SUBCOMMANDS` lists, else the tool alone, a known command's name or `other`; never the command, a path or another free word) `duration_ms` when the event has one, and for `python-c` or a script on stdin its closed purpose (`ql_capture.python_purpose`: `test-run`, `backlog-edit`, `kb-read`, `parse` or `other`, the first rule of `PYTHON_PURPOSES` the code matches; the code is never kept; ), so the census outlives the transcripts; an ops row in the tools file is no kb use for a fetch (`used_kb`); and the hook events of permissions, compactions and API-error turn ends (`ql_capture.hook_ops_row`): `permission.request` (`tool`, `group`), `permission.denied` (`tool`, `group`; `rule`, the classifier rule the reason names in `[...]` as a token when it is one of the built-in labels `claude auto-mode defaults` prints (`ql_capture.DENIED_RULES`, `ql_capture.denied_rule`; a custom rule's or any other bracketed text gives no rule), or `classifier-unavailable`), `compact.pre` (`trigger`, `group`), `compact.post` (`trigger`, `group`; `size`, the summary's size class) and `turn.error` (`error`, `StopFailure`'s documented class or `unknown`; `group`), never the reason text, a command or tool input, custom instructions, the summary or error details. A new event or key is a change to this registry and to this paragraph, never a free-form field; the event's writer is the tool that did the work, which owns when it writes (its own item).
- **Four events have their writers** (`ql_deliver.ops_row` is the one call, which is `ql_capture.record` with no write inside a test run and no error out: a tool never fails or waits for its log; a test that writes ops rows into a spool of its own sets `KB_OPS_TEST_SPOOL=1` and points `CLAUDE_PLUGIN_DATA` at a directory outside the clone, and only both lift the guard (`ql_deliver.own_test_spool`)): `sprint.close` is written by `backlog.py close` before it deletes the sprint's items (`sprint`; `landed` and `dropped`, the items of the sprint done and dropped; `bugs`, the items of kind bug among them; `confirmed`, the provisional gates of the sprint and its items answered by the operator; `refused`, the `done.refused` rows of the local spool and the committed ops sidecars that name one of the items, each row once; `ms`, from the commit that added the sprint's file to the close; no row when git has no such commit, and none for `close --summary`); `ci.pipeline` by `backlog.py red-pipeline` and by the CI check of the delivery (`ql_deliver.ci_pipeline`), only when the pipeline's state (`red`, `pending`, `green`, `unverified`) differs from the one last recorded for its id (`ci-state.json` beside the spool, the last few dozen pipelines, never committed), with `calls`, the job-list calls the read made, and `sha` (a `red-pipeline --job J` read writes none); `done.refused` by `backlog.py done` before it refuses an item (`item`; `reasons`, the closed classes of each refusal it found, sorted: `children-open`, `not-ready` (a wait, or no touches of its own or under it), `status`, `provisional-answer`, `uncommitted`, `no-work-commit`, `unlanded-code`, `outside-touches`, `check-failed`, `no-op-proof`; `checks`, the names of the failed or no-op checks as tokens, the `-k` selector of a test run, else the script or the program, never the command; `ms`, from the start of `done`); `intake.detect` by `backlog.py intake` (not `--status`) and its hook, one row for each detector that found a candidate or ran out of its budget (`found`, the candidates kept; `budget` and `coverage`, the items its checks reached, only for `drift`, the one detector with a budget). A row holds counts, durations, item ids, short shas and a state or detector name, never a title, a name or a host.
- **A rules lookup is a `kb_ask` row with `root` `_self`** (a `pack --root _self` call or a `kb_ask.py --root _self` run): `question` (one part as text, several as a list), `verdict`, `tested` (the matched tested-question ids), `pinned`, `set` (a `--set` run, which has no question) or `item`, `budget`, `chars` and `lines` of the printed text, `parts`, `docs` and `key_missing` (the key words no printed passage holds). It joins no public count: distill keeps it as an entry with `root` and learn, apply and the digest read it apart from the public lookups.
- **The MCP server does not log**, except a `_self` pack (Capture): it never sees `session_id` or `prompt_id`, so its rows could not join.
- **Logging hooks are async.** An async hook cannot block or add context, which a logging hook never needs, and it does not delay the prompt (`claude/hooks.md`, DOC S743). A headless `claude -p` run exits right after its answer, before an async `Stop` hook finishes, so its entries have no `stop` row; `usage` rows are read after the prompt, never at its `Stop` (`kb/_self/usage.md`). The `kb:` hook stays synchronous because it answers; its row is one local append after the answer is printed.
- **Fetch outcomes classify facts only:** `http-<status>` (a status the tool or the error text gives), `empty`, `redirect-cross-host` (WebFetch returns such a redirect as text instead of following it, `claude/hooks.md`, DOC S-3yod3u7q; `fetch.py` and `census.py` compare the final url's host), `truncated` (`census.py`'s read limit reached), `error`; everything else is `unknown`: "a bot page", "the summary lacked it", and a shell fetch's exit code 0. Source signals (a host that needs staging, a route misused) are report-only findings.
- **`lines`** are the kb lines a result returned, never their text: `{line, tag, verdict}` per pack line (`- root/path:line ...`) or search hit (`[score] root/path:line`), in order, each once, at most `LINES_MAX`; `tag` is the line's `[TAG ids]` and `verdict` the `coverage:` line above it, each left out when there is none (`ql_capture.pack_lines`).
- **`sources`** on a `kb_ask` row are the ids of the kb sources whose urls the researcher's answer names, sorted, at most `SOURCES_MAX`, never the urls or the text (`kb_ask.note_sources`, `ql_learn.answer_sources`). `kb_ask.py`'s `claude -p` runs with hooks off, so its fetches are never logged and the answer's urls are the only trace of the pages it read. The urls are read from the researcher's result text alone (a `web` run's answer, a `split` run's live part or an escalated run's answer, not the reader's kb part and not an error result's errors), each compared to the `_sources.csv` urls of every root as a fetched page is (Learn, the False none bullet), and only the ids of the matches stay: a url no source row holds leaves nothing. The field is left out when no id matches. It is an optional field of format 1, like `escalated`: the row format does not change.
- **A tool response is read, never kept:** `tool_response` for an MCP call is undocumented (a gap entry under `claude/hooks.md`), so its text is taken from a string, a content-block list or an object holding one.

## Capture (`querylog.py capture`)

- **One command for every hook event.** `sh "<root>/_tools/kbpy" _tools/querylog.py capture`, async, on `UserPromptSubmit`, `PostToolUse`, `PostToolUseFailure`, `Stop`, `SubagentStart`, `SubagentStop`, `PermissionRequest`, `PermissionDenied`, `PreCompact`, `PostCompact` and `StopFailure` in `.claude/settings.json` and the plugin. It reads the event on stdin, appends at most one row (and a `call.tool` ops row beside a kb, docs or shell call's own), prints nothing and exits 0 on any input; a `PermissionRequest` hook that prints nothing leaves the permission prompt as it was.
- **Tools** call `ql_capture.record(surface, session_id, **fields)`, or `record_request(url, outcome)` per HTTP request; `record` never raises. `kb_hook.py` loads `ql_capture` only for a `kb:` prompt. `rag.py pack --root _self` (a question, `-q` parts, `--set`, `--item`) and `kb_pack` with `root` `_self` (`kbfacts.record_self`) write a `kb_ask` row with `root: "_self"`, the mark of a rules lookup, `question` (a list for several parts; none for `--set`), `verdict` (none for `--set`), `tested` (the matched tested-question ids), `pinned` (the passages printed for them), `set` or `item`, `budget`, `chars` (printed), `lines`, `parts`, `docs` (the docs printed) and `key_missing` (key words no printed passage holds, at most 12); the row joins the tools file like any tool's.
- **Size:** a row longer than `SPOOL_ROW_MAX_CHARS` has its longest text field cut, ending ` [...]`; a row that still does not fit keeps only `id`, `ts`, `surface`, `v`, `session_id` and `prompt_id`, with `cut: true`.
- **Pruning:** every `UserPromptSubmit` capture deletes spool files untouched for `SPOOL_MAX_AGE_DAYS`, so rows never distilled do not outlive the horizon.
- **Usage of the earlier prompts:** every `UserPromptSubmit` capture then writes a `usage` row for each earlier prompt of its session that used the kb or lies inside a work window and has none, read from the transcript the event names (`ql_capture.add_usage`, `kb/_self/usage.md`).
- **`querylog.py where`** prints the mode, the config file, the directory and whether capture writes.

## Spool

- **Where:** `_cache/querylog/spool/<session_id>.jsonl` in a clone on every OS (short UUID names keep Windows paths short; a copy that runs from a linked git worktree of the clone, such as `../it-ops-kb-worker2`, spools in the main worktree's `_cache/querylog`, where `backlog.py cost` and distill read, `ql_base.places`), and `${CLAUDE_PLUGIN_DATA}/querylog/spool/` in a plugin host: the hook runs the plugin's copy, so `CLAUDE_PLUGIN_ROOT` names this code and `CLAUDE_PLUGIN_DATA` is set (`claude/hooks.md`, `claude/plugins.md`, DOC). Rows without a session, or with a session id that is not a safe file name, go to `tools-<yyyy-mm-dd>.jsonl` (UTC) beside them. The `DISABLED` marker is `_cache/querylog/DISABLED` in a clone and `${CLAUDE_PLUGIN_DATA}/querylog/DISABLED` in a host.
- **Never committed** (`_cache/` is ignored). A spool file is deleted once its distilled entries are delivered or dropped (a file with waiting or undelivered entries keeps only their rows): in mode `local` an entry is delivered when its run file is in the local store, in mode `auto` when its run file is on `origin/main` (Delivery), so a failed push deletes nothing; rows never distilled are deleted after `SPOOL_MAX_AGE_DAYS`, the same horizon as Claude Code's own local transcripts (`claude/data-retention.md`, DOC S747).
- **Row formats.** A row capture writes carries `v`, its row format (`ROW_FORMAT`), which goes up when what a row holds changes; distill reads each format in a branch of its own, and a row without `v` is format 0:
  - **format 0:** every row written before `v`. Its fields depend on the commit that wrote it: a `kb_hook` or `mcp` row may lack `lines`, an `mcp` row `verdicts`, a `prompt` row `kb_intent`, a `fetch` or `tool_fetch` row `chars`, and a `fetch` row its `fetcher`, host and path (a docs-server call without a url never had them); a row cut to its ids has only those and `cut`. A field a row lacks is left out of the entry. A kb row with `lines` gives its own. A `kb_hook` or `mcp` row without `lines` that names `articles` gets the lines of `pack` on the kb at `HEAD` for each question it recorded (its `question`, each part of its `questions`, or its `query`), only those of the articles it recorded, and its entry is `cited: pack`; a row with no question, or whose pack has no line in those articles, gives none.
  - **format 1:** the rows of Surfaces. A kb row without `lines` returned no kb line, and pack does not run for it.
  - **Skipped:** a line that is not a JSON object, a row without a string `id` or `ts`, a surface capture never writes, and a `v` other than 1 to `ROW_FORMAT` (a newer capture's, or a `v` of 0 written out) are not read. Distill counts those of the closed sessions and the finished days in the run header's `counts` (`skipped`), and they go from the spool in the same pass; those of an open session or of today's tools file are neither read nor counted yet.
- **Raw text stays here.** The spool holds prompts and answers as typed, which is why it is local and short-lived; nothing raw leaves it except rule-redacted text sent to Haiku to judge, and no prompt or answer text reaches the store.
- **The pipeline never logs itself:** every `claude -p` it starts (`kb_ask.py`'s reader and researcher, the Haiku stage in `redact.names_argv`, research in `ql_research.research_argv`) runs with `--settings '{"disableAllHooks": true}'` (`kbcommon.NO_HOOKS`), which turns hooks off for that run over project and local settings (`claude/hooks.md`, DOC S743). The benchmarks never log either: every `claude -p` of `_tools/agent_bench.py` carries it too, and `_tools/benchmarks.py` runs from a throwaway clone whose query log is `off` and whose `origin` is a local bare repository; its query-log scenarios run the hooks in mode `local` under a scratch directory (`kb/_self/reports/benchmarks.md`).

## Distill

- **Trigger.** The `SessionEnd` hook only starts a detached distill and returns. `SessionEnd` hooks share a 1.5-second budget, and a plugin hook's `timeout` does not raise it, so a batch job with a network push fits only as a launcher (`claude/hooks.md`, DOC and DER S743; the answer `QK-kb-need-know-build-query-log`). `SessionStart` also starts one, for sessions that closed without it. Both run `querylog.py launch` (synchronous on `SessionEnd`, async on `SessionStart`, in `.claude/settings.json` and the plugin): `SessionEnd` writes the marker `spool/<session_id>.end` first, before the launcher lists the spool or reads another session's transcript, so a kill inside the hook's budget never leaves the ending session unmarked, and a detached `querylog.py distill --settle LAUNCH_SETTLE_S` starts only when something is ready and no distill holds a fresh lock. A `SessionEnd` whose session has a spool file and whose input names `transcript_path` always starts one, with `--session` and `--transcript`, right after the marker and before the catch-up below: it waits up to `USAGE_LOCK_WAIT_S` for the lock and writes that session's `usage` rows before it distills (`kb/_self/usage.md`), reading the `transcript_path` the hook was given, not a search by session id. Either event also starts such a distill, one each, for up to `MISSED_ENDS_MAX` other sessions of the spool that have no marker yet whose transcript shows they exited (the last record is Claude Code's `cost-state`, `kbusage.transcript_ended`; the transcript is the most recently modified file `<session id>.jsonl` under the project directories of the Claude config directory, `kbusage.find_transcript`, because `/cd` and a worktree entry or exit move a session's transcript to another project directory and can leave a stale copy in the first): a `SessionEnd` that never ran, as none did for a headless worker the orchestrator started in the background (`kb/_self/usage.md`). That distill writes the session's `usage` rows and only then writes its marker (`ql_distill.close_ended`), so no other pass consumes the session before its rows exist; the distill's log starts with a line `launch: session <id> exited without a SessionEnd`. The launcher prints nothing and always exits 0; the child's output goes to `distill.log` beside the spool.
- **Closed sessions only.** A spool file is ready when its session ended (its `.end` marker), or when it has been idle for `SESSION_IDLE_CLOSED_S` (a crash or a kill fires no `SessionEnd`, and writes no exit record the launcher could read); a session closed by idleness gets the marker when distill rewrites its file, so it stays closed. A tools file (`tools-<day>.jsonl`) row joins the prompt whose window holds its time: from the prompt row to its `Stop` row, else to the next prompt, the last one to the session's end (the latest-starting window when several do). A row in the window of an open session waits with it; a row in no window becomes an entry of its own once its UTC day is over. `consumed.json` beside the spool lists the tools rows already distilled, and a finished day's tools file goes once all its rows are.
- **One distill per machine**, under the lock (Portability); a second one exits at once with exit code 3.
- **The local store:** distill writes the run file to `store/` beside the spool (`_cache/querylog/store/` in a clone, `${CLAUDE_PLUGIN_DATA}/querylog/store/` in a host), laid out as `kb/_querylog/`. An entry a run file of the local store already holds is not distilled again, so its Haiku output is never regenerated. A prompt that never used the kb is not an entry, and its rows go with its session's file.
- **Mode `local`** deletes the spool rows of every entry it wrote or dropped, and never commits or pushes.
- **Mode `auto`** deletes the rows of dropped entries only, then runs the push of `apply --push` (Delivery) under the same lock, from the clone, or in a plugin host from its managed clone (Delivery, Plugin hosts); the rows of written entries stay until their run file is on `origin/main`, and a closed session keeping them is picked up by the next `SessionEnd` or `SessionStart` launch, which retries the push.
- **Its own worktree.** Automatic commits are made in a git worktree beside the spool (`_cache/querylog/worktree` in a clone, `${CLAUDE_PLUGIN_DATA}/querylog/worktree` of the managed clone in a host), checked out detached at `origin/main` and reset there at the start of every run, never in the person's checkout, so a background commit never meets their uncommitted work (`apply --push`, and through it mode `auto`'s distill).
- **Steps:** join the rows on `prompt_id`; keep the prompts that used the kb (and their fetches; a window prompt that did not use the kb has a `usage` row and no entry); take each entry's question and citations from its kb rows (below); redact (below); Haiku judges; write one run file to the local store, and beside it the usage sidecar of the written entries whose prompt has a `usage` row of this `kbusage.READER_VERSION` (a row of another version is left out; Store) the work sidecar of the closed sessions that worked an item and of the run's own Haiku calls (below), and the ops sidecar of the tools files' `ops` rows (below); in mode `auto`, copy it into the worktree, run `learn` and `apply` there, and make one commit of the store files and what they changed, with the `KB-Auto` values of its paths (`querylog` among them), pushed once (Delivery).
- **The work sidecar** (`ql_distill.plan_work`) is written from the `work` rows and the `usage` rows of each closed session only, so a session still open has no line yet; `backlog.py cost --rework` reads such a session's spool itself, the clone's and the main worktree's when it is another directory (`bl_cost.open_lines`, the same `ql_distill.plan_work` code, read-only, writing no sidecar) and prints its figures after the sidecar figures, apart from them and marked `open session figures` (provisional until the session closes), or says the open session has no usage rows to read yet instead of an unexplained zero:
  - **item lines:** a prompt inside a work window (`kb/_self/usage.md`; the windows of `ql_capture.usage_targets`, walked per item by `ql_distill.work_windows`) that has a `usage` row of this `kbusage.READER_VERSION`, in the closed shape the store keeps, adds that record's `main` and `sub` counts to the tally of the item whose window holds it. A `claim` or `branch` row opens a window only for an item that has a file in the item files of the clone distill runs in (`ql_distill.item_finder`, the files `sprint_finder` reads), unless a later `done` or `release` row of the session closes it (`ql_distill.kept_rows`): a `branch` row of a stale `work/<id>` checkout, written before the capture hook read the item file, has no closing row and opens none, so it cannot hold every later prompt of a long session in a window and force the shared line. Nor does a `branch` row written at or after the commit that set its item done or dropped (`ql_distill.stale_branch`: the item file in the distilling clone says `done` or `dropped`, and the latest commit that changed that file's `"status"` text dates it), the row of a helper session started in a worker worktree whose `work/<id>` branch predates the item's done commit and whose own copy of the item file still says `doing`; a row with no time, or an item whose status no commit dates (a status not yet committed), counts as written after it. A worker's own `branch` row, written before the done commit, keeps its window when distill runs after the landing (a lock wait, a missed session end), and a `claim` row is never held stale, since `backlog.py claim` refuses an item that is not open. Meanwhile the `claim` an orchestrator's own `land` closed keeps its window although a sprint close deleted the file before the session was distilled. `ql_distill.rework_windows` follows the same rule. A prompt in one window counts on that item's line, and a prompt inside several windows counts once, on the line of the sprint the items share (`ql_distill.work_lines_of`, `sprint_finder`: the sprint read from the item files of the clone, stored as the id of the line), or on its session's shared tally when they share none or a sprint is unknown; the subagents the record routes to items (`routed`, `kbusage.work_item`: by the `work/<id>` branch their records name, else by the one `.claude/worktrees/<id>` directory their shell commands name, for a worker of a hand-made worktree) add their `sub` counts to those items' tallies with no prompt; the tallies of every session of the run merge into one line per item;
  - **rework** (`ql_distill.rework_windows`): an item line has a `rework` block, in the shape of its counts (`prompts`, `main`, `sub`), when the item has a `refused` row inside its window (a `backlog.py done` that exited 1, Surfaces). The block holds the counts from the prompt of the item's first `refused` row to the end of its window (its `done` or `release`), the subagents routed to the item from those prompts included: a prompt is the finest unit, so the prompt that ran the first refused done is rework, and the prompts before it are work. The block is a part of the line's own counts and is never added to them: the line keeps the window's total, work is the line less `rework`, and the two sum to it. An item with no refused row has no block, so no rework figure. A `refused` row with no open window (a `claim` or `branch` row) in the session's rows opens nothing, a `release` ends the rework and a later `claim` of the item starts a window with none, and a refusal never carries from one session to another. A prompt inside several windows counts on its sprint's line, which is never split. Counts only: no id, time or text joins the block, and a sidecar written before it reads as before;
  - **interrupts** (ST-enx4hrlr): a tool call the user interrupted (`PostToolUseFailure` with `is_interrupt` true) leaves a `work` row of action `interrupt` in its prompt, with no item and no text, beside its `call.tool` row's outcome `interrupt`; an item line counts as `interrupts` (a positive whole number, the gates refusing any other value) the interrupt rows of the prompts of that item's window alone, while a prompt in several windows or outside any counts on no line, so the wasted calls of two items compare.
  - **shared lines:** a prompt outside every window with such a `usage` row (a kb prompt: other prompts outside a window have no row), or inside windows that share no sprint, adds to its session's shared tally, which becomes one line naming the items whose window the session opened (a `claim` or its `work/<id>` branch); a session with no such prompt writes none;
  - **unrecorded:** a session that opened no item's window (no `claim` row and no `branch` row, or only ones of items with no file that no row closes, above), a `done` or `release` with no `claim` or `branch` row of the item earlier in the session's spool file included, and a session still open. Window prompts without a usable `usage` row are counted in the header's `missing`, never in a line;
  - **no entry needed:** a run with no entry, nothing dropped and nothing skipped but with work lines or an overhead line still writes its run file (no entry), so the sidecar has the run file beside it;
  - **the overhead line** (`ql_distill.Spend`) is not read from any session: it is the run's own Haiku calls' token counts (below, Haiku's batch), added up into one line, `overhead: distill`, `calls` (the calls that reported counts) and `main` (per model), written after the item and shared lines; a run whose calls reported none (a replayed or stubbed Haiku, an older CLI, no call made) writes none, and a run with no work line but an overhead line writes a sidecar of it alone. The digest, `rag.py eval` and `census.py` start no model, so they write none (`kb/_self/usage.md`);
  - **never twice:** `worked.json` beside the spool lists, per session, the prompts a sidecar already counted (`{session id: [prompt ids]}`, local and never committed), so a session whose rows stay in the spool (mode `auto`, until delivery) is not counted again by the next run; a session that has left the spool leaves the file; the delivery step (`spool_delivered`) settles no pass's counting, so it keeps a closed session whose work-window prompts the file does not list, for the next distill pass to count and settle; `backlog.py cost --rework` leaves the prompts the file lists out of its open session figures (`bl_cost.open_lines`), so a session distilled after an idle close that then reopened adds only its later prompts to them, never the ones the sidecar figures above already hold;
- **The ops sidecar** (`ql_distill.plan_ops`) is read from the `ops` rows of the tools files, which are not part of any prompt's window (`ql_distill._plan` leaves them out of the join): each unconsumed row becomes one line, in time order, if it is the closed shape the store keeps (`ql_store.ops_line`: its `id`, `ts`, `event` and the event's keys, with no `surface` or `v`) and the leak scan finds nothing in its values (`ql_store.ops_line_leaks`). A row that fails either is dropped, counted in the run header's `skipped`, and never read again. The `agent-start` and `agent-stop` rows of a closed session (`ql_distill.plan_agents`) add one `agent.run` line per agent hash: `group`, `agent`, `item` when a row has one, and `ms` from the earliest start to the latest stop, the line's id derived from the pair's two row ids so the same rows write it once; a hash with a start and no stop, a stop and no start or a stop before every start is skipped and counted in `skipped`, not written, and so is a pair whose line is not the closed shape or that the leak scan flags. A row is read once: `consumed.json` lists it, and the run file's `ops` sidecar holds it; a row whose id a sidecar of the local store already holds (the run that wrote it ended before it recorded the row) writes no second line. Today's tools file stays until its day is over, as for every tools row, and goes when all its rows are consumed. A run with ops rows and nothing else writes a run file of no entry, so the sidecar has the run file beside it.
  - no session id, prompt id, transcript path, branch, cwd or command text is read into a line: only the item ids, the prompt counts and the summed token counts.
- **Caps.** At most `HAIKU_BATCH_ENTRIES` entries per `claude -p` call, `HAIKU_BATCHES_PER_RUN` calls per run and `HAIKU_DAILY_CALLS` calls per machine per day (counted in `haiku-calls.json` beside the spool). Over a cap, entries wait in the spool for the next run; so do the entries of a call that fails (no CLI, a timeout, an exit code), while a reply that is not the expected JSON drops its batch. Entries with no question (a `fetch.py` request, a `kb_show` call, a kb prompt that made no kb call) need no Haiku and are always written.
- **The question** is the one the kb was asked, taken by code from the lookup's kb rows in time order, the first that names one: the `kb:` hook's or `kb_ask.py`'s `question`, or a kb MCP call's `question`, the first part of its `questions`, or its `query` (`ql_distill.kb_question`). With several kb calls it is the first call's, the one the pack answered first, so a miss that a reworded call then fixed is the question learn re-runs. The prompt as typed is never the question, and neither is any rewrite of it. A prompt with a `kb_intent` that made no kb call is an entry with no question (its fetches still count for source findings), in which learn finds no lookup. The question goes through the rules and the leak scan; a hit drops the entry.
- **A rules lookup** (a `kb_ask` row with `root` `_self`, and no public kb row in its prompt: `ql_distill.rules_fields`) is an entry with `root` and, each only in its closed shape (Store), `tested`, `set`, `item`, `route`, `model`, `answer_lines`, `key_missing` (its words go through the leak scan: a hit leaves the field out), `verdict`, `chars` and `question` (through the rules and the leak scan like any question). It keeps no `articles`, `citations` or `cited`: those are the public kb's lines. Haiku does not judge it: its entry has no `judged` and no `best`, since a judgement is of an answer from public articles, the reply a rules lookup has no text of, and the pack's verdict and the reader's `answer_lines` already say whether the rule docs answered. A row without `root` is distilled as before.
- **The citations** are the kb lines the lookup's kb rows returned (`lines`, Surfaces), each once: those whose `path:line` the reply's text names (with or without `kb/`, or without the root), `cited: reply`, else the first ones, `cited: pack`; at most `CITATIONS_MAX` (`ql_distill.citations`). They are the kb's public lines, never the reply. A format 0 row without `lines` gets them from `pack` on `HEAD` (Spool, Row formats), and those entries are `cited: pack`. An entry with no citation keeps no `articles`, since an article is stored only with the lines that back it; its recorded articles are still Haiku's candidates.
- **Haiku's batch** is, per entry with a question, that question, the rule-redacted prompt and reply (each cut to `HAIKU_TEXT_MAX_CHARS`) and its candidate articles, the ones its kb calls returned; Haiku returns only a judgement (`answered`, `partly`, `missed`), the best candidate or null, and whether the question identifies a person or an organisation. Any other field of the reply, free text included, is left out, and a best article that is not a candidate becomes null. The call is `redact.names_argv` with `--output-format json`, run in an empty temporary directory: the result's `result` is the reply, and its `modelUsage` (token counts per model, never its text, session id or cost) becomes the run's overhead line (`ql_distill.haiku_result`; an error result fails the call like any other, and a stdout that is not a result is the reply itself with no counts); `--replay FILE` answers from a recorded reply file instead, which is what the tests use.

## Redaction (`_tools/redact.py`)

1. **Rules** (stdlib `re`, `redact()`): key and token shapes (`kbcommon.SECRETS`), JWTs, UNC paths, home and drive paths, UPNs and emails, down-level `DOMAIN\name`, domain SIDs, GUIDs (hyphenated and bare), IPv6, IPv4, FQDNs, computer-name patterns, high-entropy strings, in that order. Each becomes the placeholder for its kind (table below).
2. **The leak scan** on the stored question after the rules (`finish()`): the scan is `kbcommon.leak_hits`, the same shapes the tracked-file leak test  flags, so nothing the scan would catch reaches the store; a hit drops the entry.
3. **Haiku** on the rule-redacted text only, to judge: it flags a question that names a person or an organisation, and that entry is dropped. Names rest on Haiku's flag, with no NER layer and no rewrite; the test corpus includes names. `redact.names_argv` is the Haiku call's argument list; `ql_distill.py` supplies the model, the caps, the timeout, the prompt and the reply's parsing.

| kind | placeholder |
|---|---|
| hyphenated / bare GUID | `00000000-0000-0000-0000-000000000000` / 32 zeros |
| IPv4 / IPv6 | `192.0.2.10` / `2001:db8::10` (the documentation ranges) |
| domain SID | `S-1-5-21-0-0-0-<RID>`: the domain identifier goes, the RID stays |
| UPN or email / down-level logon | `jan.kowalski@corp.example.com` / `CORP\jan.kowalski` |
| FQDN | `corp.example.com` |
| computer name | `PL-SRV-0042` when it reads as a server (SRV, SQL, DC1, ...), else `PL-LT-00123` |
| UNC host / home-directory user / other path segment | `\\PL-SRV-0042` / `jan.kowalski` / `PL-PATH` |
| key, token, JWT, high-entropy string | `<secret>` (angle brackets: the secret shapes never match a placeholder) |

- **What stays:** well-known SIDs (`S-1-5-18`, `S-1-5-32-*` built-in groups, capability `S-1-15-3-*` and the other constant ones) identify no one, while an `S-1-5-21-*` domain SID names the organisation's domain; a user is matched both as a UPN and as `DOMAIN\name`, with no suffix allowlist, since an explicit UPN's suffix need not be the DNS domain (`reuse/pseudonymization-tokenization.md`, DOC and DER S-h2cmbqvf, S-dcjdn73r). Windows authorities (`NT AUTHORITY\`, `BUILTIN\`) and registry roots (`HKLM\`) are not logons. Loopback, multicast, netmasks, the documentation ranges and names (`example.com`, `.test`) stay.
- **The allowlist is the public root, read at run time.** `known()` runs the same shapes over every text file of `kb/public` (never an internal root, which names real tenants) once per process, and any GUID, public IP, host, email, logon, computer name or token found there stays: Graph app ids, CSP and ASR GUIDs, vendor hosts. So the vendor allowlist is the hosts the root names, matched exactly (a tenant's `name.sharepoint.com` is not kept because `sharepoint.com` is). One owner, nothing generated to go stale: an id an article adds is kept from the next run. A private address the kb shows is an example there, so private IPs are never kept this way.
- **Paths:** a segment made only of words the public root uses stays (`C:\Windows\CCM\Logs`), any other becomes `PL-PATH`; the user of `C:\Users\<name>`, `/Users/<name>` and `/home/<name>` always becomes `jan.kowalski` (`Public`, `Default` stay).
- **High entropy:** a token of `ENTROPY_MIN_LEN` or more letters, digits, `+` and `_` (trailing `=` allowed), with a letter and a digit, at `ENTROPY_MIN_BITS` or more. Per-character entropy alone does not separate identifiers from keys (`DeviceManagementConfiguration` scores 3.8 bits), so a token made only of words the public root uses, split at case and digit changes with each word 3 letters or more (`Win32LobAppPowerShellScript`), stays.
- **Doubt drops.** An entry Haiku flags as still identifying, or one the second leak scan catches, is dropped; only its counts go to the run header. A reply that is not the expected JSON drops its batch.
- **Haiku runs batched at distill:** `claude -p --model haiku --tools "" --settings '{"disableAllHooks": true}'` with no user plugins or MCP servers (`--setting-sources project,local --strict-mcp-config`), the batch on stdin. Its judgement is stored once per entry id and never regenerated, so a second distill cannot change a committed entry.
- **Idempotent:** `redact(redact(x)) == redact(x)`, and the placeholders pass through unchanged.
- **What the API sees:** rule-redacted text (the kb's question, the prompt and the reply) goes to the Claude API, under the organisation's retention (30 days standard for commercial use, `claude/data-retention.md`, DOC S747); `/kb-setup` says so.

## Store (`kb/_querylog/`)

- **Files:** `kb/_querylog/<yyyy-mm>/<run-id>.jsonl` (a header line, then entries), `kb/_querylog/findings/<yyyy-mm>/<run-id>.jsonl`, `kb/_querylog/usage/<yyyy-mm>/<run-id>.jsonl`, the usage sidecar, `kb/_querylog/work/<yyyy-mm>/<run-id>.jsonl`, the work sidecar, and `kb/_querylog/ops/<yyyy-mm>/<run-id>.jsonl`, the ops sidecar, each of the run file of the same run. One file per run, so parallel pushes from different machines never touch the same file and no `merge=union` driver is needed; a finding's state is its last record across findings files, so no file is edited after its run.
- **Header:** `run` (the run id, `<yyyymmdd>T<hhmmss>Z-<8 hex>`, which names the file and its month directory), `pipeline` (`PIPELINE_VERSION`), `retrieval` (the pack index version, `kbfacts.INDEX_VERSION`), `kb_commit` (`HEAD` of the clone that distilled) and `counts` (`entries`, `dropped`, `waiting`, and `skipped` when distill skipped spool rows, Spool). Entries carry none of these. A run with no entry, nothing dropped, nothing skipped and no work line writes no file.
- **Entry:** one compact JSON line, fields left out when empty: `id` (the spool row id of the lookup's prompt, so the same lookup distilled twice shows as a duplicate), `surface` (`prompt` for a session's lookup, else the tools row's surface), `day` (UTC), `intent`, `tools` (the kb tools used), `route`, `question` (the kb's own, Distill), `verdict` (the worst pack verdict), `articles` (cited), `citations` (each `line`, `root/path:line`, with the `tag` and `verdict` the kb printed beside it), `cited` (`reply` or `pack`), `judged`, `best`, `sources` (the kb source ids a `kb_ask.py` row carried, Surfaces: each once, sorted, at most `SOURCES_MAX`, from the lookup's `kb_ask` rows only) and `fetches` (`tool`, `fetcher`, `host`, `path`, `outcome`, `n` per distinct fetch, and `chars`, the sum of the result characters its rows recorded). A standalone `fetch.py` or `census.py` request is an entry with `tool`, `host`, `path`, `outcome` and `chars` at the top. A fetch keeps its host and path only when the host is a DNS name outside the private and example names that the rules leave unchanged (the public root names it); otherwise only its tool and outcome stay. An entry with `root` `_self` (Distill) also keeps `tested` (tested-question ids, at most `TESTED_MAX`), `set` (a set name), `item` (a backlog item id), `model` (a tool name), `answer_lines` (`kb/_self/<doc>.md:<line>`, at most `ANSWER_LINES_MAX`), `key_missing` (words, at most `KEY_MISSING_MAX`) and `chars`, the printed characters of its lookup; these fields are an entry's only with `root`.
- **Usage sidecar:** a header of exactly `run`, `reader` (the `kbusage.READER_VERSION` distill reads) and `counts` (`entries`, the lines; `missing`, the run's written entries without usage), then one line per written entry whose prompt has a `usage` row of that reader: `id` (the entry's) and the record's `main`, `sub`, `start`, `steps` and `cut` (`kb/_self/usage.md`). A run whose entries have no usage writes no sidecar. Usage is kept apart from the entries, which hold what the kb was asked and returned, and joins them on `id`.
- **Work sidecar:** a header of exactly `run`, `reader` (the `kbusage.READER_VERSION` distill reads) and `counts` (`items` and `shared`, the lines of each kind; `missing`, the window prompts without usable usage; and `overhead`, the overhead lines, only in a file that has one, so an earlier sidecar reads as before), then one line per item worked in the run's sessions, in id order: `item` (the id of an item, or of a sprint: below), `prompts` (the window prompts counted) and `main` and `sub`, the usage record's counts summed per model (`requests`, `in`, `cw`, `cw1h`, `cr`, `out`) and, for `sub`, per agent group (`kb/_self/usage.md`), with no `start`, `steps` or `cut`; an item line has no prompt of its own (`prompts` 0, an empty `main`) when only subagents routed to it were counted, and then has a `sub`; an item line may also have `rework` (`prompts`, `main` and `sub` in the same shapes, with the same no-prompt form), the part of its counts from its first refused done on (Distill), absent when the item has no refused done in its window, never on a sprint's line; then one shared line per session that worked an item and has prompts outside its windows or in windows with no common sprint: `items` (the ids whose window it opened, by a `claim` or its `work/<id>` branch, sorted), `prompts`, `main` and `sub` of those prompts. An item has one line in a file and may have one in the sidecar of every run its sessions fall in; a shared line carries no session, so two sessions with the same items write two like lines. A prompt inside two windows counts once, on the line of the items' common sprint, so the lines never sum above the sessions' total. No session or prompt id and no text: the sidecar joins nothing, and a report resolves an item's place in the backlog itself and counts a shared line once for a subtree holding any of its items. Last, an overhead line for each kind of the kb's own background runs that spent tokens (`OVERHEAD_KINDS`: `distill`, `digest`, `eval`, `census`; only `distill` is written, Distill): `overhead` (the kind), `calls` (the `claude -p` calls counted) and `main`, their counts per model in the usage record's shape, with no `item`, `items`, session, prompt, `sub` or text; the tokens are the system's, not an item's, so no item's totals take them (`kb/_self/usage.md`). A kind has one line in a file, and the line has no date: the run id of its file, read as UTC, dates it, which is how a sprint's cost report finds the overhead inside the sprint's window (`kb/_self/backlog.md`, Cost of work). A run with no work line and no overhead line writes no sidecar.
- **Ops sidecar:** a header of exactly `run` and `counts` (`rows`, the lines), then one line per `ops` row of the run's tools files, in time order, ids breaking ties: `id` (the spool row's UUID, which joins nothing and keeps a row from being written twice), `ts` (the row's UTC time), `event` and the event's keys (Surfaces), in the event's order. It is a sidecar of `kb/_querylog/` like the usage and work sidecars, so it has the store's redaction class and gates and goes only to the integration remote: it is part of the path `kbpublic.PRIVATE` cuts from the public projection, of the paths `kbgit.py`'s gate runs `querylog.py check` for, and of what `apply --push` copies (Delivery). It holds names, exit codes, counts, milliseconds, item ids, short shas, test file names and closed reason classes, never free text. A run with no `ops` row writes no sidecar. `kblog.py propose` reads the sidecar through `ql_store`'s readers and `ops_line_problems` (`kb/_self/content-rules.md`, Logs) and writes aggregates of it, never a line, as proposed log rows.
- **Findings file:** the same header (`counts`: `findings`, `open`, `fixed-since`), then one record per finding whose state this run changed: `id` (`F-` and 12 hex of a hash of its kind and subject, so the same finding has the same id in every run and clone), `kind`, `state`, and per kind: `stage`, `promotions` (each `from`, `to` and `by`: `learn`, `apply`, `research` or `kb-research`), `entry` (the store entry it came from; the question stays in the store), `expect`, `article` (for a gap finding from stage `gap` on, the article its entry sits under), `terms`, `tried` (a gap finding's day of its newest tried note, The research queue), or for a source finding `signal`, `host`, `level`, `needs`, `triggers`, `tool`, `route`; a `rules` finding has `stage` `miss` only and its `observed` holds the `question`, the `verdict`, `route` `miss` when the reader found no answer, and `answer_lines` and `key_missing` when the entry has them; `observed` holds what the run saw (the pack's verdict and articles on HEAD, counts) and never decides whether a record is written.
- **Never committed:** the prompt or answer, raw or redacted, or any summary or rewrite of them; `session_id`, `prompt_id`, `transcript_path`, the user, the host name.
- **Not a root:** `pack` and `search` skip it (a directory under `kb/` starting with `_`), and the leak scan in `_tools/tests.py` covers its tracked files.
- **Gates** (`ql_store.py`),: a duplicate id across run files (`kbgit.py fix --check`, exit 2, through `ql_store.duplicate_ids`); a missing header or provenance field, a count other than `entries`, `dropped`, `waiting` and a positive `skipped`, run metadata or a raw spool field in an entry; free text in an entry (a `summary`, an unknown field, or anything but its closed value in `day`, `intent`, `tools`, `route`, `verdict`, `articles`, `judged`, `best` or `sources`, which holds source ids only: no url, no text, none twice, at most `SOURCES_MAX`); citations that are not 1 to `CITATIONS_MAX` `path:line` items with a known tag and verdict, an entry with `articles` and no citations, or `cited` missing beside them or other than `reply` or `pack`, an entry with a rules field (`tested`, `set`, `item`, `model`, `answer_lines`, `key_missing`) and no `root`, or one whose `root` is not `_self` or whose rules field is not its closed shape; an identifier in a run file (a question the leak scan flags or the rules would change); a fetch with a query string or fragment, a non-public host or command text, or an `n` or `chars` that is not a count; in a findings file, a header that does not name its file, a record with a bad id, an unknown field, kind, state, stage or signal, a `rules` finding at a stage other than `miss`, a promotion without its stages or by another than `learn`, `apply`, `research` or `kb-research`, a `tried` that is not a day or not on a gap finding, a gap finding closed at `claim` that a later record puts at another stage (a closed gap reappears), promotions that do not follow each other or end elsewhere than the record's stage, a gap finding from stage `gap` on with no article, an entry no run file holds, a source finding's non-public host, a source finding in a state `apply` sets, or an eval finding `applied` whose alias or expansion finding is not; in a usage sidecar, a header other than `run`, `reader` and `counts`, a run id that does not name its file, no run file of that run beside it, a count that does not match, a line whose entry that run file lacks, an id twice across sidecars, an unknown field, a model id, agent group or tool group outside its than `run`, `reader` and `counts` (`counts` is `items`, `shared`, `missing`, and `overhead` only in a file with an overhead line), a run id that does not name its file or month, no run file of that run beside it, a count that does not match its lines, a line that is both an item and a shared line or neither, an unknown field (a session or prompt id, a command, a usage record's `start` or `steps`), an item that is not an item id, `items` that are not item ids sorted and each once, a `prompts` that is not a positive count (an item line alone may have 0, with an empty `main` and a `sub`), a model id, agent group or count outside the usage shapes, `cw1h` above `cw`, a `rework` that is not a block of `prompts`, `main` and `sub` alone, has counts outside those shapes or above its - **Why commit machine-written data at all:** the store is the one input `learn` and the digest read, so every clone computes the same findings and numbers from git alone (`agents/docs-maintenance-agents.md`).

## Learn

- **`learn`** (`querylog.py learn [--store DIR]`) reads the store and the kb at `HEAD` and writes findings only: no eval row, alias, expansion or gap entry. Mode `local`: it reads the local store beside the spool and writes `findings/` there (`logging is off` in mode `off`), unless `--store` names one.
  - **Re-run first.** A judged miss (Haiku judged it `missed` or `partly`, or its verdict was `weak` or `none`, except that a `weak` verdict Haiku judged `answered` is no miss, while a `none` verdict stays one whatever Haiku judged) is re-run with `pack` on `HEAD`. It passes when the verdict is `good` with its `best` article among the pack's (the eval rule of `rag.py eval`), or, with no `best`, `good` with no `check:` line. One that passes is `fixed-since`, and gets no fix finding.
  - **Kinds and stages.** A miss with a `best` article (the kb has the answer, the pack missed it) is an `eval` finding at stage `miss`, with its fix: `alias` when the question uses words the kb never holds (`terms`), else `expansion` of that article (a paraphrase). A miss with no `best` is a `gap` finding, unless it is a false none or its lead holds the answer (below), promoted by learn from `miss` to `candidate-gap` (recorded in `promotions`); `apply` and research make the later promotions (`gap`, `candidate-fact`, `claim`), each recorded the same way.
  - **False none.** A `none` entry whose stored fetches (a fetch with outcome `http-4xx`, `http-5xx`, `empty` or `error` aside, since no page was read) name a page a root's `_sources.csv` holds is a false none: the kb cites the page the answer came from. Pages compare by host and path, without scheme, `www`, query, fragment, trailing slash or `.md`, and without the locale segment on `learn.microsoft.com`. Learn writes an `eval` finding at stage `miss` in place of the `gap` finding: its `expect` is the article with the most lines citing the matched sources (ties by path), and `observed` holds their ids as `sources`. Only article lines count, so a source that only a ledger cites gives no false none. The entry's `sources` (the ids a `kb_ask.py` researcher's answer named, Surfaces) count as fetched pages that read: `kb_ask.py` runs with hooks off, so its fetches are never in the store, and a source an article cites is the same evidence, with no page comparison left to do. The `alias` or `expansion` fix follows when the re-run fails, as for any eval miss.
  - **A lead that holds the answer** (`ql_learn.held_article`). A miss whose re-run on `HEAD` is `none`, with no false none by its pages, is an `eval` finding at stage `miss` for the pack's lead article when that lead lies in the question's domain (below, the gap step) and one of its tagged facts holds, as written (case aside, not inside a longer word or number), every word the pack lists under `kb lacks`: the pack's words missed a fact that is there (a number with a unit suffix), a retrieval miss and no knowledge gap. A gap candidate learn wrote earlier for the same entry is then no longer derived and becomes `fixed-since`.
  - **Rules findings** (`ql_learn.rules_miss`, `rules_finding`): an entry with `root` `_self`, a question, no `set` and a `weak` or `none` verdict or route `miss` (the reader found no answer) is a `rules` finding at stage `miss`, in no way a public gap or eval finding (`is_miss` is false for it, so no public pack re-run, article or Haiku judgement applies). It carries in `observed` the question, the verdict, `route` `miss` when that was the route, and `answer_lines` and `key_missing` when the entry has them, and a `pair` (`rules_pair`, below under Apply) when a key word has a counterpart in a quoted line. A `good` lookup and a `--set` run make none. Its re-run is `pack --root _self` on the working tree, as learn's other re-runs: `fixed-since` when the verdict was weak or none and the pack is now `good`, or when `kb/_self/_retrieval/lookup_eval.csv` already holds the question as a row; else `open`. It never gets a stage after `miss`.
  - **Source findings** (report-only, never applied) cover the hosts the store's fetches name. `stage`: a Share trigger (a root's `_sources.csv` at `HEAD`) or a Failures trigger (failed fetches in the store plus errors in the roots' `_fetch_state.csv`) of `kb/_self/web-sources.md` holds, and the host is below `STAGE_NEEDED_LEVEL`. `route`: WebFetch read a host whose routes-table row avoids WebFetch. A host's staging level comes from its provider-registry row (`_tools/providers.csv`, or a root's `_providers.csv`, read through `provider.py`: level 3) when it has one, else from the routes table in `web-sources.md` (level 1), else 0; both are read at run time. A test keeps them in agreement: every row of `_tools/providers.csv` names a host the routes table has. Another test holds the trigger numbers in `querylog.py` equal to `web-sources.md`.
  - **State converges.** A record is written only when it changes a finding's state or subject (its `observed` part aside), in states `open` and `fixed-since`; an open finding learn no longer derives becomes `fixed-since`, and so does a `no-fix` eval finding whose question now passes on `HEAD` (one that still misses stays `no-fix`; its `fixed-since` record drops the `tried` day `close --tried` gave it, which the store takes on a gap finding or a `no-fix` eval finding only), any other in a state `apply` set is left to `apply`, and one whose last record is at a later stage than learn derives (a gap the research queue recorded `fixed-since`) is left as it is. The file's run id is the time of the newest run file (or one second after the newest findings file, so the files sort in the order they were written) and a hash of its records: a second run on the same store and `HEAD` writes nothing, and another clone writes the same file.

## Apply

- **`apply`** (`querylog.py apply [--store DIR]`) turns accepted findings into changes. Mode `local`: it reads the local store beside the spool (`logging is off` in mode `off`), unless `--store` names one, and writes the kb changes to this clone's working tree, uncommitted and never pushed.
  - **An eval row only with its fix.** For each open eval finding, in id order, with its open alias or expansion finding: the eval row (`kbid.py eval` id, the `best` article, `good`) goes into the article's root's `lookup_eval.csv` together with a candidate fix, and stays only when every `rag.py eval` question passes, the mean pack of the eval questions measured before the run does not grow, and off-kb `good` does not rise (`kb/_self/doc2query.md`); otherwise the files are put back and the next candidate is tried. A question that already passes gets nothing (learn records it), and a red `rag.py eval` before any change stops the run (exit 1).
  - **Alias candidates:** the words of the article's file name, then of its title, up to `ALIAS_CANDIDATES`; a word that is a term of an alias group stands for that group, else it starts a new one (`word,word`). Each finding term becomes a `term,canonical` row in `_tools/aliases.csv` (a root other than public: the `aliases.csv` in its own retrieval data). A term already in an alias file, a term the kb holds, or a canonical word another group owns is refused.
  - **Expansion candidates:** the article's tagged facts sharing the most words with the question, up to `EXPANSION_CANDIDATES`; the row is the fact's key and the stored question, in the root's `doc2query/expansions.csv`. The gates above stand in for the Doc2Query-- filter, which would drop a question the pack misses by definition.
  - **Outcomes, as new records** in one findings file (named as learn names its files): the eval finding and its fix `applied`; with no accepted fix, the eval finding `no-fix`, promoted from `miss` to `candidate-gap` (by `apply`), and its fix `rejected`, each with the failed gates in `observed`. Source findings are never applied. An eval finding `no-fix` stays a candidate gap: the kb holds its best article, so it is no knowledge gap. A second apply on unchanged inputs writes nothing, since no finding it acts on is still `open`.
  - **The gap step**, after the eval findings: each open gap finding at `candidate-gap` is re-run with `pack` on the working tree. It reproduces when it still fails (the rule of `learn`'s re-run, with no best article), and it lies in a kb domain when its lead path belongs to an article (the article itself, a same-stem data file or a file its `files:` lists), for a `none` verdict only when that lead matches more than half of the question's key words the kb knows (`ql_learn.domain_article`; a `none` lead with fewer is a stray word match), and for a `weak` verdict only when that lead holds the question's subject (`ql_apply.weak_off_topic`): one line of the lead's topic (a fact, an untagged line or a data row, each with its file name and title, as the pack's index holds them; a product alias counts where the product's other names are, `Gate.unit_words`) holds more than half of the question's key words the kb knows, and either five of them or three with two specific to the kb (`ql_apply.specific_words`: in at most one article in fifteen), and the pack names no key word the lead never mentions (`unmatched`, the pack's `check:` line) unless the lead is about another one (ten of its lines hold it). The subject is words that stand together in one line: words spread over the article, a qualifier of its title (format, status) or a stem of its file name (`deletion`) is no subject. "cargo metadata --no-deps invokes rustc ..." is agents/codebase-mapping's gap, since a Rust fact of its body holds cargo, metadata and no-dep, 3 of 5; "What is the maximum email attachment size?", led by mecm/collect-client-logs, is not, since its best line holds size, 1 of 4. A short generic question ("laptop battery replacement": battery and laptop share a line of logs/azure-monitor-agent, 2 of 3) is rejected: a pair of words in one line is chance, and so are three common ones ("how big should the page file size be": file and size). The rule stays lexical: a generic question whose line holds five of its words, or three with two specific ones, still passes it, and the off-kb list's `weak` questions with a lead are all rejected. Then a `_gaps.md` entry in that article's root, at the end of the section headed with its topic (`## <domain>/<slug>`, a new section at the end when there is none): the question the kb was asked, in bold, the day of the lookup, the finding id, "Looked in the kb <date>" with the pack's verdict, and `(topic: <domain>/<slug>)`. The finding is promoted from `candidate-gap` to `gap` (by `apply`), `applied`, with its `article`. An entry whose finding id is already in the file is not written again. Off the kb's domains (no lead, a lead no article holds, a stray `none` lead, a `weak` lead without the subject) it is `rejected` at `candidate-gap`, with `off the kb's domains` in `observed`: no topic can take its entry. Passing now, or a `none` pack whose lead holds the words it lacks (learn's rule above), it is left to `learn`, which records it `fixed-since` or as an eval finding. So no gap candidate but those left alone (below) stays open after an apply: the digest's open gaps are none but what the queue reaches.
  - **Rules findings:** each open `rules` finding (`ql_apply.rules_one`), in id order, whose entry has a question. When its `answer_lines` name a `kb/_self/<doc>.md:<line>`, the first line that gives an anchor yields a row of `kb/_self/_retrieval/lookup_eval.csv`: the id `SQ-` and the question's slug (the `EV-` slug of `kbid.py eval`), the question as asked, the doc, `good`, `yes`, the anchor phrase and empty `sets`. The phrase is 4 to 6 consecutive words of that line as written, with no `;` and no punctuation at either end, chosen for rarity (`ql_apply.anchor_phrases`): the fewest occurrences per word across the `kb/_self` docs, the longer then the earlier first, a window holding a token with no letter or digit left out, and the first of the five rarest that the row's anchor check finds in a passage of its doc. The row goes through the gates of an eval row (`try_fix`: the whole `rag.py eval`, which includes `--root _self`, passes, the mean pack does not grow, off-kb `good` does not rise) and stays only then, the finding `applied` with the row's id and the line in `observed`; else the files are put back and the finding is `no-fix` with the failed gates (an id taken by another question or no anchor phrase included), still at stage `miss`. When learn recorded a `pair` on the finding (a key word of the question no passage holds, and the word of the quoted line that shares the most characters with it at the start and end together, at least four, with no other word as close: `unsaved`, `uncommitted`), the rows `term,canonical` (and the canonical word to itself when no alias file holds it) go into `kb/_self/_retrieval/aliases.csv` with the eval row and stay only when the same gates hold and no alias file holds the term yet, else the eval row alone is tried; `observed` then names the pair. A finding with no answer line, or none with a pair, gets no alias: with no answer line it is left open and the apply prints how many need a person; a question the file already holds gets nothing (learn records it `fixed-since`). The row is written to this clone's working tree like every apply change.
  - **Replaying the gap step:** `querylog.py gap-replay [--store DIR]` re-runs the gap step's decision (`ql_apply.gap_decision`: the rules above, `domain_article`, `weak_off_topic` and `held_article`) on the working tree over every gap finding of the committed store `kb/_querylog` (or DIR), whatever its state, in id order, and prints one tab-separated line per finding: its id, the question, the pack's lead path, the verdict and the decision (`keep`: an entry under the lead's topic; `reject`: off the kb's domains; `passes`; `held`: an eval finding; `no-entry` when its entry has no question). It is read-only: it writes no record, ledger or file, so its output before and after a change to a gap-step rule shows which real findings the change flips (`kb/_self/backlog.md`, Sprints). Exit 0.
  - **Left alone:** findings named by `--hold` (those pending on a conflict branch, Delivery), and a finding recorded `apply-failed` more than `FAILED_RETRIES` times, even when a later record opens it again.
- **Research is opt-in per user**, capped by the user's own daily count, and runs inside `apply`, after the gap step, on gap findings at stage `gap` (in id order, one `claude -p` run each, while runs are left today, at most `RESEARCH_RUNS_PER_APPLY` in one apply):
  - **Off unless the user's config file turns it on:** `research` true and `research_daily` a whole number of 0 or more (else `DEFAULT_RESEARCH_DAILY`); no file, an unreadable file, another value, mode `off` or the `DISABLED` marker leave it off. `research-runs.json` beside the spool (`{"day", "runs"}`, UTC day) counts the runs started today, a failed call included. `apply --push` passes its clone (`--clone`), or in a plugin host its querylog directory (`--plugin-data`), so the worktree's apply reads the person's own config file and count.
  - **The run:** `ql_research.research_argv` (`RESEARCH_MODEL`, hooks off, no user plugins or MCP servers but this copy's `kb` stdio server, given as `--mcp-config` JSON with `--strict-mcp-config`, whose `docs_search` and `docs_fetch` are its only tools allowed: they reach the three documentation servers through its 7-day live-docs cache, so a search the queue repeats within the week calls no docs server; `WebSearch` and `WebFetch` the only built-in tools, `--permission-mode dontAsk` with those tools allowed) in an empty temporary directory, the prompt on stdin: the question, the topic and the article's fact lines with their line numbers. The reply is JSON: at most `RESEARCH_FACTS_MAX` candidate facts, each with its text, tag (`DOC` or `COMMUNITY`), url, title, publisher, licence, reuse class, a quote from the page, and `conflicts_with` (the line of an existing fact the page contradicts, or null). `apply --replay-research FILE` answers the runs and the page fetches from a recorded file instead, which is what the tests use.
  - **The candidate gates**, deterministic: the text is one sentence with no tag, no topic marker and nothing the leak scan flags, and not already a fact; the url is http(s) on a DNS name outside the private names; the reuse class is one of `kbcommon.REUSE`; title, publisher and licence are given; `conflicts_with` names a fact line; then `quotecheck` on the url. The finding is promoted from `gap` to `candidate-fact` (by `research`).
  - **Add-only:** an accepted fact becomes a bullet at the end of the article's Facts section, `- <text> [<tag> <id>]`, its id added to the `sources:` header; a new url gets a source row (`kbid.source_id` with the root's prefix, `retrieved_utc` today), put in id order as `kbgit.py fix` keeps the file, and an existing one keeps its id; a candidate with `conflicts_with` becomes a `_conflicts.md` entry under the topic, naming the existing fact's line, the page and both sides' ids, "not settled", and writes no fact. A fact written also closes the finding's `_gaps.md` entry with a `  - Resolved <day>:` note naming the count of facts, their source ids and the finding (content rules, Ledgers), so the queue finds the `claim` record's entry resolved. Then the gates: no existing fact line, ledger line or source row (but its generated `used_in`) removed or edited, `build_index.py` then `check.py` with `errors=0`, no `rag.py eval` question newly failing and off-kb `good` not rising. A failed gate puts every file back.
  - **Outcomes:** a fact written promotes the finding from `candidate-fact` to `claim` (by `research`), `applied`; conflicts only leave it `applied` at `candidate-fact`; nothing accepted or a failed gate is `rejected` at `candidate-fact`, and a reply that is not the expected JSON `rejected` at `gap`, each with its reasons in `observed`. A call that fails (no CLI, a timeout, an exit code) writes no record, so a later run tries again. A finding at `claim` or `rejected` is not researched again.
- **`querylog.py quotecheck URL QUOTE`** accepts a quote only when it has `QUOTE_MIN_WORDS` to `QUOTE_MAX_WORDS` words and is on the page: fetched with `fetch.py`'s `fetch` (the kb's user agent and per-host pause, one query log request row), reduced by its `to_text` (HTML to the text of `<main>` without page chrome), then both sides normalized (entities decoded, Markdown links and emphasis dropped, NFKC, straight quotes and dashes, lower case, single spaces). `--page FILE` reads a recorded page. Exit 0 on the page, 1 not, with the reason. The quote is checked, never stored: a `paraphrase` source allows none in the kb. The gates and the quote check are research's review.

## The research queue

- **`querylog.py queue [N] [--store DIR]`** lists the open gap findings for `/kb-research --queue [N]` (`.claude/skills/kb-research/SKILL.md`), from the committed store `kb/_querylog` unless `--store` names another. An open gap finding is kind `gap` at stage `gap` or `candidate-fact` with its article, not `fixed-since` or `apply-failed` and never closed at `claim`, whose `_gaps.md` entry (the top-level bullet in its article's root naming the finding id, as the gap step writes it) exists.
  - **Re-run first:** each one's question is re-run with `pack` on `HEAD`; one that passes now (learn's rule, with no best article) gets a `fixed-since` record at its stage, in one findings file named as learn names its files, and leaves the queue.
  - **Dated notes under the entry** (indented bullets, `kb/_self/content-rules.md`, Ledgers): `Resolved <date>:` or `Superseded <date>:` closes the entry; `Tried <date>:` and `Partly resolved <date>:` leave it open. An entry whose newest open note is younger than `QUEUE_TRIED_DAYS` waits, counted to the UTC day of `HEAD`'s commit; an entry resolved in the ledger whose finding has no `claim` record is named with the `close` command to run, and not queued.
  - **Ranking:** one item per question (every gap finding that asked it, each with its entry), by the number of logged lookups (store entries) that asked the same question (case and spacing aside), then by the oldest lookup's day, then by finding id; the top N (all without N) are printed grouped by topic, in rank order of each topic's first item. Only the store and `HEAD` go in, so the same store and `HEAD` print the same lines in any clone.
  - **Output:** `queue: gaps= queued= listed= waiting= fixed-since= day=`, then per topic `topic <domain>/<slug>` and its items (`<n>. asked=<lookups> since=<day>`, `question: ...`, and one `<finding id> <_gaps.md path>:<line>` line per finding), then the waiting, fixed-since and resolved-but-unrecorded findings, and `problem:` lines. Exit 0; 1 when a closed gap reappears: a later record after its `claim` (also a `check` gate), or its entry without a `Resolved` note.
- **`querylog.py close F-ID [F-ID ...] (--claim | --tried NOTE | --reject) [--store DIR] [--commit [--trailer 'KEY: VALUE']]`** records what `/kb-research` did with one queue item, one findings file per finding; no older file is edited:
  - `--claim`: once the entry carries a `Resolved <date>:` note (the skill writes it by the content rules), the finding is promoted from its stage to `claim` by `kb-research`, `applied`;
  - `--tried NOTE`: writes `  - Tried <date>: NOTE (topic: <domain>/<slug>)` under the entry (UTC today) and records `tried` with that day; the gap waits `QUEUE_TRIED_DAYS`; an eval finding whose newest record is `no-fix` (apply found no fix for the miss) takes `--tried` too: its record keeps `no-fix` and carries `tried` and the note, with no `_gaps.md` line, and the stranded detector leaves it alone until the note is `QUEUE_TRIED_DAYS` old;
  - `--reject`: for an open gap finding whose entry was removed from the ledger as off the kb's domains (no topic can take it). The queue skips a finding without an entry, so without this record it would stay open for good. The finding is moved back from its stage to `candidate-gap` (recorded in `promotions`, by `kb-research`) and marked `rejected`, with `off the kb's domains` in `observed`. That is the record the gap step writes for such a candidate, so apply, research, learn and the queue leave it alone after that. It refuses while an entry still names the finding: use `--claim` or `--tried`, or remove the entry first.

  - `--commit [--trailer 'KEY: VALUE' ...]`: commits the findings files it wrote, alone (`git commit --only`: what was staged before stays staged and out of it), subject `chore(querylog): close <ids> (claim|tried|rejected)`, the `--trailer` lines its last paragraph and never a `KB-Work` trailer. The record is the query log's, not the work item's that answered the gap: a research task's touches are kb content only and never name `kb/_querylog/`, so the record under its trailer makes `backlog.py done` refuse the story over a path outside its touches. A `KB-*` key, a line that is no trailer, or `--trailer` without `--commit` is refused before anything is written. The `--tried` note in `_gaps.md` stays for the research commit.

  Exit 0; 1 refused: no open gap finding, no entry naming it (`--claim`, `--tried`), `--claim` without a `Resolved` note, `--tried` on a resolved entry or with an empty note, `--reject` while an entry still names it, a refused `--trailer`, or a failed commit (the records stay written).
- **Convergence:** a second `queue` after a closing run lists nothing it closed and writes nothing.

## Delivery

- **Straight to `main` on `origin`**, the repository the clone came from: run files, findings, eval rows, aliases, expansions, gap entries and opt-in research, once the local gate passes and a rebase on `origin/main` is clean. `kbgit.py sync --push` is the only path by which they reach it, the revert of a red push included (CI before any new push, below); the one other push is a conflict branch, never `main` (`kb/_self/git.md`, Workflow).
- **Never to the public home.** When `origin` is the clone's public home (`git config kb.publishRemote`, `kb/_self/git.md`, Public home), `apply --push` refuses (exit 2) and the run files stay in the local store and the spool; a clone without a public home (a production clone) pushes as below.
- **`querylog.py apply --push`** runs from a clone, by hand in every mode but `off` and from mode `auto`'s distill, under the distill lock (exit 3 when it is held):
  1. fetches `origin`'s `main` and its `querylog/` branches and resets the worktree (Distill) to `origin/main`;
  2. deletes the spool rows of the entries whose local run file `origin/main` already holds (a push whose deletion did not run, a conflict branch merged since);
  3. checks CI (below);
  4. copies into the worktree's `kb/_querylog/`, at the same paths, the local store's run files and usage, work and ops sidecars `origin/main` lacks, and its findings files `origin/main` lacks whose records are all in a state `learn` writes (`open`, `fixed-since`) for findings `origin/main` records none of; a local findings file holding `apply`'s outcomes describes changes to the clone's own working tree and stays local;
  5. gates the copied files with the worktree's `querylog.py check` over its store and the leak scan (`redact.scan` over every value but the run, entry and finding ids); a problem commits and pushes nothing (exit 1);
  6. runs the worktree's own `learn`, then its `apply`, on that store, and makes one commit of the copied files and what they changed, with the `KB-Auto` values of all its paths (`querylog` among them; `chore(kb): query log apply <run-id>`, or `chore(kb): query log store, ...` when they changed nothing);
  7. pushes that commit once with the worktree's `kbgit.py sync --push` (fetch, rebase, fix, the gate, `git push origin HEAD:main`);
  8. once that push reached `origin/main`, deletes the spool rows of the entries of the run files it copied. A failed push or a conflict branch deletes nothing; the next run copies the same files again.

  Nothing new and no change from `learn` and `apply` pushes nothing. Exit 0 when it pushed, had nothing to push, waited on CI or pushed a conflict branch; 1 when a step failed (a red gate pushes nothing); 2 refused (no `origin`, `origin` the public home, a plugin host with no recorded install source, a cloud session on a detached `HEAD`, `--store` with `--push`).
- **Trailers:** each commit carries `KB-Auto:` with its values from `querylog`, `eval`, `alias`, `expansion`, `gap`, `research`, `revert`, taken from the paths it changes (`gap` for a root's `_gaps.md`; `research` for its articles, `_sources.csv`, `_conflicts.md` and the coverage files build_index regenerates; a path `apply` never writes is refused and nothing is committed, and so is a change that removes or edits an existing fact line, ledger line or source row against `HEAD`), then its KB-* trailers (`kbgit.py trailers --amend`), and `Self-Reviewed:` for the docs `kb/_self/map.csv` gives those data files, since appended rows change no doc. `kbgit.py check-trailers` flags a second `KB-Auto` line or an unknown value.
- **The integration remote only** (`git config kb.integrationRemote`, default `origin`; the text here says `origin`). Mirroring to other remotes (`claude` on GitHub) stays a person's job.
- **No hard-coded host.** The forge and host come from `origin`'s url (https, ssh or `user@host:path`): `github.com` is GitHub, any other host GitLab, and a url with no host (a local path) GitLab.com (`FALLBACK_GITLAB_HOST`).
- **A conflict `kbgit.py sync` cannot resolve** (exit 3) aborts the rebase and pushes the commit as it was to `querylog/<run-id>` (the run id of its findings file) with `-o merge_request.create -o merge_request.target=main`; `main` gets nothing and the findings stay pending on `main`, for a person or `/kb-git-sync`. Later runs pass the finding ids of every `querylog/` branch that `origin/main` does not contain yet to `apply --hold`, so no second branch is opened for them. They read the findings files the branch adds with `git cat-file blob`, never `git show REV:PATH`, which checks its argument as a file name and fails as too long a name on Windows in a deep worktree; a file they cannot read, or a failed `git for-each-ref`, `merge-base` (an `--is-ancestor` exit other than 0 or 1, or no base) or `diff --name-only`, stops the run with nothing pushed, so a held finding is never applied for want of reading it. The push options open the MR without a token (`gitlab/automated-merge-requests.md`, DOC S-2d2dlaeq). No auto-merge: a failed pipeline does not end auto-merge, so a retried job would merge a red MR (the answer `QK-kb-need-know-build-query-log`).
- **CI before any new push.** The last commit on `origin/main` with a `KB-Auto` trailer (not a revert) is checked at the tip of its push (with the `kbgit fix after sync` commits sync added after it): `glab auth status --hostname <host>`, then `glab api --hostname <host> projects/<path>/pipelines?sha=<sha>&per_page=20` on GitLab, of which it reads the newest that failed, is unfinished or in which a job ran (`ql_deliver.job_ran`; a canceled job did not), else the newest (every job is manual, so a newer pipeline of the commit that no one started hides nothing); `gh auth status --hostname <host>`, then `gh run list --commit <sha> -R <host>/<path> --json status,conclusion,databaseId,url` on GitHub; skipped with a note when the CLI is not signed in or the call fails. Only a finished failure is red: `failed`, or a completed run concluded `failure`, `timed_out` or `startup_failure`; `manual`, `skipped`, `canceled` and `success` are not, and optional manual jobs never make a pipeline `failed` (`gitlab/automated-merge-requests.md`, DOC and DER S-kdfwn4eo, S-4darq3cp, S-4hzaehlu). Unfinished (`created`, `pending`, `running`, ... or a run not `completed`): nothing is pushed this run. On GitLab a pipeline that is neither is read by its jobs (`glab api --hostname <host> projects/<path>/pipelines/<id>/jobs?per_page=100`, `ql_deliver.job_verdict`), since every job in `.gitlab-ci.yml` is manual with `allow_failure` and the status says success whatever they did: a job someone started that failed on its own account (`failure_reason` `script_failure`, `job_execution_timeout` or `stuck_or_timeout_failure`) makes it red, whichever job; else a job named in `ql_deliver.GATE_JOBS` still running holds the push as unfinished; else such a job that did not succeed, or a job list that cannot be read, makes it **unverified**, and nothing is pushed this run either, with a line naming each such job. `GATE_JOBS` is empty while every job is manual: a pipeline in which nobody started a job is not held, so the push goes on. Red on a push that changed only `kb/_querylog`: a revert would keep every file, so the run notes it and goes on. Red otherwise: a revert commit (`KB-Auto: revert`) of that push, keeping the store's files, with one findings file recording `apply-failed` for every finding the push applied, and one bug item in `kb/_self/backlog/` (severity S2; titled and noted with the failed pipeline's id and url and the reverted findings; its repro is `backlog.py red-pipeline --status --job <the first failed job>` when that job's script ran and failed (`ql_deliver.job_decided`), which fails until that job runs on main again and passes, a run of it canceled, manual or skipped being no verdict (plain `--status` when no such job was read, as for a pipeline red by its status whose failed job never ran, such as `ci_quota_exceeded`); its links name `pipeline <id>` and `fingerprint <12 hex>`, computed from the failed pipeline's first failed job (by each job's newest attempt, read from the pipeline's whole job list) and its log the way `backlog.py red-pipeline` computes it; skipped when the backlog already names that pipeline, and when an open bug already carries the fingerprint the revert adds `pipeline <id>` to that bug instead and its commit changes that item file, so `backlog.py red-pipeline` files no second one), goes through `kbgit.py sync --push`, and the run ends there; a revert that does not apply cleanly pushes nothing (exit 1). An `apply-failed` finding is never applied again (`FAILED_RETRIES`).
- **No CI job writes to the repository.** The project leaves job-token pushes off, and `.gitlab-ci.yml` runs branch and tag pipelines only.
- **Plugin hosts** (`ql_deliver.host_push`) push from a managed clone, `${CLAUDE_PLUGIN_DATA}/querylog/clone`, never from `${CLAUDE_PLUGIN_ROOT}`, the read-only cache copy that changes with every version (`claude/plugins.md`, DOC S-toe7z3kj):
  - **the clone url** is the plugin's install source: the entry of its marketplace (the `<marketplace>` of `CLAUDE_PLUGIN_ROOT`, `cache/<marketplace>/<plugin>/<version>`) in `known_marketplaces.json` beside `cache/`, a `git` source's `url` or a `github` source's repository over https, else the `origin` url of the marketplace's git clone or directory (its `installLocation`, `marketplaces/<name>`) (`claude/plugins.md`, DOC and DER S-toe7z3kj, S-gxuoqjzy). None recorded: exit 2, nothing pushed;
  - the clone is made on first use without a checkout, pointed at the install source again when it moved, and serves the worktree beside the spool; the push is `apply --push`'s, with research read from the host's `config.json` and counted beside its spool (`apply --plugin-data`). A failed `git clone` pushes nothing (exit 1);
  - **a push refused for want of rights** writes `DISABLED` beside the spool (why and when) and deletes the spool, which turns logging off for good on that host. It is recognised by the remote's own words in the push output (`ql_deliver.push_refusal`): GitLab's `You are not allowed to push code to this project.`, `... to protected branches on this project.`, `You are not allowed to force push code ...` or `... upload code ...`, GitHub's `Permission to <repo> denied to <user>` or `GH006: Protected branch update failed`, or `The requested URL returned error: 403` on a push whose fetch just succeeded (`gitlab/automated-merge-requests.md`, CODE and DOC S-ag7ica4f, S-qcamxpw6, S-vtgbttzo, S-fuytyyvw, S-sraelr2g);
  - no refusal: a generic `(pre-receive hook declined)` (push rules, custom hooks and timeouts give it too), a DNS or connection error, a `remote failure`, another HTTP status, an SSH key refused, or a red gate; the spool stays and the next run retries (S-naq3uqba, S-l6s4hfqp).
- **Cloud sessions** (`CLAUDE_CODE_REMOTE=true` in the session's environment) distill in the container, in the clone the session checked out, and push to its `origin`: the GitHub repository the session cloned, whose git proxy takes `git push` to the session's current working branch only (`agents/headless-agent-runtimes.md`, DOC S-gu5aqnrl, S-mkqjh4ac). So the push goes to the branch the clone has checked out:
  - on `main`, the flow above;
  - on another branch, the worktree starts from `origin/<branch>` (from `origin/main` while the branch is not on `origin` yet), `kbgit.py sync --push --branch <branch>` pushes there, and the automatic commits reach `main` with that branch's pull request; the spool rows go once the run files are on `origin/<branch>`. A conflict pushes nothing (the proxy takes no `querylog/` branch) and the findings stay pending. The session's own later push to that branch needs a rebase on `origin/<branch>` first;
  - a detached `HEAD`: exit 2, nothing pushed;
  - no `DISABLED`: a refusal there leaves the spool, and the container goes with the session.
- **A clone** reports a refusal for want of rights in its output (`kbgit.py sync exit 1: nothing pushed to main (refused for want of rights: ...)`) and writes no `DISABLED`.

## Reporting

- **Digest:** `querylog.py digest [--store DIR] [--week YYYY-Www]` prints one ISO week's numbers from the committed store, `kb/_querylog`:
  - lookups (entries by surface), verdicts, Haiku's judgements, misses and how many are fixed, each miss by the finding that stands for it (its eval finding when it has one, else its gap finding): fixed when that finding is `fixed-since`, an eval finding `applied` or a gap finding `applied` at `claim`, so a gap candidate learn superseded with an eval finding that apply recorded `no-fix` is not fixed; each miss once, and not while that finding is `open`, fetches with their failures and result characters, usage from the sidecars (the week's lookups with a usage line; input tokens per lookup, uncached + cache write + cache read over `main` and `sub`, median and p90 by nearest rank; output median; the share of that input read from the cache and spent in subagents; the steps made only of kb tools, with their median `grow` and median result characters), run files written and entries dropped by redaction, finding records written, and every finding's kind and state at the week's end;
  - rules lookups apart from the public ones, after the fetches line and only when the week has a rules entry or a rules finding is open at its end: `rules lookups: N (good n, weak n, none n, no verdict n)`, `rules printed characters: SUM, mean MEAN` (over the lookups that kept `chars`), and `rules sets run: N, open rules findings: N`. A rules entry is in none of the public counts above (lookups, verdicts, judged, misses, usage);
  - after the usage lines, the work lines (`ql_report.work_lines`), from the work sidecars of the week's runs (by their run id's date, like run files): `work: 6 items, tokens 3460 (main 80%, subagents 20%); top 5 by tokens`, then one line per listed item, `  TK-xxxxxxxx: 1200 tokens, main 67%, subagents 33%`, the most tokens first and the id first among equals, at most `WORK_TOP` (5) of them. An item's tokens are its lines' counts of the week's runs summed, uncached input, cache writes, cache reads and output, `main` (its own prompts) and `sub` (the subagents routed to it) together, the shares being each one's part of that. Only item lines count: a sprint's line (`SP-...`, the prompts inside several of its items' windows) is listed like an item, a shared line is a session's and an overhead line the system's, so neither is any item's tokens. A line holds the id alone, never a title, session or prompt, and an item deleted at sprint close is listed by its id like any other. A sidecar that breaks the work gates (Store) is left out whole, as `backlog.py cost` leaves it out. The work sidecar holds no kb-tool counts, so there is no kb-tool share to show; a week with no item line prints no work line;
  - after the work lines, the ops block (`ql_report.ops_lines`), from the rows of the ops sidecars counted in the ISO week of each row's own `ts` (else its run's day), so a Monday distill does not move the last week's rows, a sidecar that breaks the ops gates left out whole: `ops: N rows (event n, ...)`, then `land.end`, `sync.gate` and `test.run` each with its count, failures and median milliseconds (a `test.run` with pytest's exit 5, no test selected, is no failure but `selected nothing N`), `done.refused`, `agent.run` by agent group, `call.tool` with its errors, interrupts and its top five command classes, and one line per hook event (`permission.request`, `permission.denied`, `compact.pre`, `compact.post`, `turn.error`) present; only event names, classes and counts, and nothing when the week has no ops row; a second digest on the same store prints the same lines.
  - on the default store the digest ends with one `intake:` line, the open items (not done or dropped) that `backlog.py intake --file` filed, counted by the `detector <name>` link they carry: `intake: 3 open (drift 1, trailers 2)`, or `intake: none open`. It reads the item files of `kb/_self/backlog/` as they are in the working tree, the uncommitted drafts the SessionStart hook wrote included, and runs no detector (the drift detector spends a time budget on its checks), so it is the one line that differs between clones at one commit; with `--store` it is left out (`kb/_self/backlog.md`, Bug intake);
  - entries count by their `day`, run and findings files by their run id's date, and a finding's state at the week's end is its last record in the findings files dated up to that Sunday, so a past week's digest stays the same as the store grows;
  - the week is the `--week` argument, else the ISO week of the store's newest entry: nothing else goes in (no clock, no machine, no path in the output), so every clone at one commit prints the same lines but for the `intake:` line, which is checked on two copies of one fixture store.
- **Shown once a week:** a synchronous `SessionStart` hook, `querylog.py digest --hook` with `timeout` `DIGEST_HOOK_TIMEOUT_S` (`.claude/settings.json` and the plugin), prints last week's digest (the ISO week before the one the machine's UTC date is in) as `{"systemMessage": ...}` at the first `SessionStart` of an ISO week:
  - a synchronous hook's `systemMessage` is shown to the person, while plain stdout goes to Claude's context and an async hook's `systemMessage` reaches only Claude, on the next turn (`claude/hooks.md`, DOC and DER S743), so this hook is synchronous and the distill launcher stays async;
  - the marker `digest-week` beside the spool (`_cache/querylog/` in a clone, `${CLAUDE_PLUGIN_DATA}/querylog/` in a host) names the week it last showed; it is written before the store is read, so a slow or failed digest is not tried again that week;
  - nothing shows in mode `off` or with the `DISABLED` marker, for a week with no entry, run file or finding record, or when reading the store took over `DIGEST_BUDGET_S`; the hook always exits 0 and never blocks.
- **Status:** `querylog.py status [--store DIR]` prints three lists:
  - open source findings of the committed store, most result characters first: the `chars` the store's fetches of the host recorded, so the host whose pages cost the most context comes first;
  - open merge requests from a `querylog/` branch to `main` on `origin`'s forge (host from `origin`'s url, as in Delivery): `glab auth status --hostname <host>`, then `glab api --hostname <host> projects/<path>/merge_requests?state=opened&target_branch=main&per_page=100` on GitLab; `gh auth status --hostname <host>`, then `gh pr list -R <host>/<path> --base main --state open --json number,title,headRefName,url -L 100` on GitHub; the branch prefix is matched on the answer, since both filters take one whole branch name (`gitlab/automated-merge-requests.md`, DOC and DER S-4abgkvor, S-dn5ck62j); not signed in, a failed call or no `origin` prints a note instead;
  - reverted automatic commits: the commits at `HEAD` whose `KB-Auto` trailer holds `revert`.
- **Show:** `querylog.py show` answers a point question about the store without a script over the JSONL files. It takes exactly one of five things to show, and prints only what the store holds:
  - `--run ID`: a run file's header (pipeline and retrieval versions, the first 12 characters of `kb_commit`), its counts, whether it has a usage sidecar, and one line per entry (id, surface, day, verdict, judged, how many cited lines, the question's first characters);
  - `--entry ID`: every field of the entry in its fixed order, each citation (line, tag, verdict) and fetch, the findings that name it (each as `--findings` prints it, without the entry) and whether the entry has usage in its run's sidecar;
  - `--findings`: each finding's last record across the findings files, in kind order (`eval`, `alias`, `expansion`, `gap`, `source`) and then by id, one line each (id, kind, state, stage, entry, and the fields it has among `expect`, `article`, `terms`, `tried`, `signal`, `host`, `level`, `needs`, `triggers`, `tool` and `route`), under a count line that names the filters; three filters narrow it and combine:
    - `--kind K`: one of the finding kinds above;
    - `--state S`: one of the states learn and apply give a finding (`open`, `fixed-since`, `applied`, `rejected`, `no-fix`, `apply-failed`);
    - `--article A`: a path or its tail, such as `public/windows/laps.md` or `laps.md`, matched against the finding's `article` or `expect`, whole or after a `/`;
  - `--usage RUN`: the run's usage sidecar, a header (reader, entries, missing) and one line per entry with input tokens (uncached, cache write, cache read), output, requests, subagent input and steps; a run with no sidecar prints one line saying so, exit 0;
  - `--spool`: the local spool, never a row's text, id or session: a count of files and rows, one line per file (a session file by its number and whether its session ended, a tools file by its day; rows by surface, the days they fall on, rows distill cannot read), and the number of rows whose id the committed store holds; `spool: empty` when there is none.
- **Show, reading and limits:** it reads the committed store, `kb/_querylog`, or the layout `--store DIR` names (`--spool` reads the local spool and refuses `--store`). It writes nothing and runs no model, no git and no network. An id for `--run`, `--entry` or `--usage` may be its start when exactly one id of the store starts with it, and an exact id wins over a longer one it begins; a list stops after `SHOW_LIMIT` lines (`--limit N` to change it, `0` for all) with one line saying how many were left out. A list under a filter that matches nothing prints a count of `0` and exits 0.
- **Show, refusals:** exit 0 for an answer, an empty one included. Exit 2, the rule on stderr as `show: refused: ...`, for an id that is not letters, digits and hyphens (up to 40 characters), an unknown or ambiguous id (it names the first ids that match), a `--kind` or `--state` that is no known value, an `--article` that is no path, a negative `--limit`, `--kind`, `--article` or `--state` without `--findings`, `--store` that names no directory or comes with `--spool`, and a store file that does not read (it names the file and points at `querylog.py check`). Naming none of the five, or two, is argparse's own refusal, also exit 2.
- **Export:** `querylog.py export --format jsonl [--since DAY] [--event E] [--with-question] [--store DIR]` (`_tools/ql_export.py`) prints the store's entries, findings, usage, work and ops rows as JSON Lines for a tool that reads logs; it builds no endpoint and sends nothing:
  - each line is one record under the OTLP-JSON log record field names: `timeUnixNano` (a decimal string), `severityNumber` and `severityText`, `eventName`, `body` (always the empty AnyValue `{}`, the null one), `attributes` (a list of `{"key", "value"}` pairs) and `resource` (`{"attributes": [...]}` with `service.name` `it-ops-kb` and `kb.run`, the run id); a value is `stringValue`, `boolValue`, `intValue` (a decimal string, as OTLP-JSON writes an int64), `doubleValue`, `arrayValue` (`values`) or `kvlistValue` (`values`), and a null is `{}`; the lines come in the order of time, event name and record id, so one store prints the same bytes in every clone;
  - the event names are one flat namespace with no dot: the family and the row's surface, kind or ops event joined by underscores, `entry_<surface>`, `finding_<kind>`, `usage`, `work_item`, `work_shared`, `work_overhead` and `ops_<event>` (an `OPS_EVENTS` name, its dot an underscore, `ops_land_step`); each record also carries the attributes `kb.record` (`entry`, `finding`, `usage`, `work` or `ops`), `kb.type` (the original surface, kind or ops event, such as `land.step`; none for usage) and `kb.id` (the record's id), then the row's closed fields; the time is the ops row's `ts`, an entry's `day` at 00:00:00, and for the other rows the time their run id names; a record's id is the row's own id (a finding's is its id and its run, a work row's its run and line);
  - the severity is `WARN` for a refused `done`, an ops row with an exit code other than 0 and a finding recorded `apply-failed`, else `INFO`;
  - it reads the committed store or `--store DIR` and writes nothing: no file of the store changes, and no model, git or network runs; `--since` keeps the records from that day on and `--event` one event name;
  - redaction happens at read time, row by row, with the store's own gates (`ql_store`: `entry_problems`, `record_problems`, `usage_line_problems`, `work_line_problems`, `ops_line_problems`, which reads an ops row through `ql_capture.ops_problems`): a key the row's format does not have is dropped, a value outside its closed shape (free text in a name included) or a hit of the leak scan (`redact.scan`) leaves the whole row out, and an entry's `question` is left out unless `--with-question` is given, which still runs the scan over it;
  - a row it cannot read or that fails a gate is left out and counted on stderr by file and line with the kind of failure, never by a value, and the exit is 0; exit 2 refuses a format other than `jsonl`, a `--since` that is no day, an `--event` outside the event names above and a store that is no directory.
- **Audit trail:** `git log --format='%h %(trailers:key=KB-Auto,valueonly)'`.

## Configuration

- **No environment variables.** Program defaults are the constants in the table below.
- **Per-user choices** live in one uncommitted file, written by `/kb-setup`: `_private/querylog.json` in a clone, `${CLAUDE_PLUGIN_DATA}/querylog/config.json` in a host. Keys: `mode` (`auto`, `local`, `off`), `research` (true or false), `research_daily` (runs per day). Research's daily count is `research-runs.json` beside the spool.
- **Modes:** `auto` distills to the local store, then commits and pushes the run file, findings and fixes (Delivery); `local` distills to the local store only, and `learn` and `apply` work on it, `apply` writing to the clone's working tree without committing; `apply --push` is run by hand in either; `off` writes nothing, not even the spool. A config file that cannot be read, or names no known mode, counts as `off` (fail closed); no file means `DEFAULT_MODE`.
- **What `/kb-setup` says:** by default logging, fixes, gap entries and pushes are automatic and research is off; the redacted questions the kb was asked, with the `path:line` of the kb lines it returned, are recorded in the repository (never the prompt as typed or the reply); rule-redacted text is sent to the Claude API for Haiku to judge, kept under the organisation's retention (30 days standard for commercial use, `claude/data-retention.md`, DOC S747). It asks whether to keep the default and writes the answer to the config file.

## Portability

- **One Python entry point.** Every hook calls `sh _tools/kbpy <script>`, which finds `python3`, `python` or `py -3` and checks that the one it found runs. Hooks without `args` run in `sh -c` on macOS and Linux and in Git Bash on Windows, and on Windows `python3` is only an alias (`claude/hooks.md`, DOC S743; `python/stdlib-windows-portability.md`, DOC S-sjuwcuhk). Without Git Bash, Windows hooks run in PowerShell, the launcher cannot start, and nothing is logged there.
- **The lock uses no `fcntl`**, which is Unix only: an `O_EXCL` file, `distill.lock` beside the spool, holding the owner's PID and start time, stale after `LOCK_STALE_S`, never checked by signalling the PID (`python/stdlib-windows-portability.md`, DOC S-oavxfpsn, S-ew7mucsg). A stale lock is renamed away before a new one is created, so of two takers one wins.
- **The `SessionEnd` launcher detaches** with `start_new_session=True` on POSIX and `creationflags=DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` on Windows, with stdin redirected from `DEVNULL` and stdout and stderr to `distill.log` (`python/stdlib-windows-portability.md`, DOC S-dabwnzz5). On Windows it adds `CREATE_BREAKAWAY_FROM_JOB`, and starts the child without it when the job the hook runs in refuses breakaway. Whether Claude Code's hook process on Windows sits in a job object that ends the child is undocumented (a gap entry under `python/stdlib-windows-portability.md`).
- **Files and processes:** every file is opened with `encoding="utf-8"` (and `newline="\n"` when writing), paths go through `pathlib`, and subprocesses take argument lists, never `shell=True`.
- **Tested on Linux, Windows and macOS**; CI runs the tests on Linux and Windows (`kb/_self/git.md`).

## Tests

- **Where:** `_tools/test_redact.py` holds the query log's privacy guards: the redactor, what distill stores from a captured prompt and answer, the closed shape of an ops row and the store check on a planted leak (the fixture spool, the recorded Haiku reply, the golden run file, the fixture store and the recorded page are in `_tools/fixtures/querylog/`). The pipeline's errors are read from the ops rows and `querylog.py digest`.
- **Shared setup:** the git scenarios clone one seed per run (`conftest.kb_seed`: a kb copy committed once, its bare repository packed, shared by the xdist workers).
- **Tests never write the clone's spool and never deliver:** a test sets `CLAUDE_PLUGIN_ROOT` and `CLAUDE_PLUGIN_DATA` to a temporary directory, and a run inside a test writes no ops row.
- **Checks and repros never write the clone's spool either:** `bl_base.run_check`, which `done`, `land`, `precheck`, a bug's repro and `host-check` run every check through, sets `CLAUDE_PLUGIN_DATA` to a fresh temporary directory holding `querylog/config.json` `{"mode": "local"}` and `CLAUDE_PLUGIN_ROOT` to the clone (`ql_base.plugin_data` takes a copy whose root is `CLAUDE_PLUGIN_ROOT` for the plugin), so a check or repro that imports `ql_capture` (or runs a tool that does) still records, into that directory, and the directory is removed afterwards. One that sets its own `CLAUDE_PLUGIN_DATA` in its own code keeps it. `KB_INDEX` and `KB_DOCS_CACHE` are set to where the inherited environment keeps the pack index and the live-docs cache, so the isolated directory costs no index rebuild: unset, the index is the clone's shared one (the main worktree's `_cache/`, from a linked worktree too, as `kbfacts.index_dir` finds it) and the live-docs cache the checkout's own `_cache/live-docs`. The one capture that leaves it is the `test.run` row of a `tests.py` run the check makes: `check_env` names the query log directory the calling process would write to (`ql_base.places`, unless capture is off there) in `KB_TEST_RUN_HOME`, a value the environment already holds staying (a check that runs a check still names the clone's), and `tests.py` writes that row into its spool, so the digest's ops block counts the runs checks make beside the direct runs and the sync gate's.

## When a mechanism can go

Each mechanism below works around a limit; it can be removed once that limit is gone.

- **The `SessionStart` launch and the idle close (`SESSION_IDLE_CLOSED_S`)** exist because a crash or a kill fires no `SessionEnd`, and a headless worker started in the background had none either. The launcher's close of a session whose transcript shows it exited (`MISSED_ENDS_MAX`) stands in for that `SessionEnd`; it relies on Claude Code's `cost-state` record, a transcript record no document of Claude Code names, so a version that stops writing it leaves only the idle close. They can go when Claude Code runs `SessionEnd` for every way a session ends.
- **The detached distill behind `launch`** exists because `SessionEnd` hooks share a 1.5-second budget that a plugin hook cannot raise. It can go when a plugin's `SessionEnd` hook can run for as long as a distill and a push take.
- **The time-window join of tools rows** exists because a tool run from inside a session sees no `prompt_id`. It can go when Claude Code passes `prompt_id` to the processes a session starts.
- **Parsing `curl` and `wget` out of shell commands** exists because shell fetches are no tool calls of their own. It can go when `fetch.py` and `census.py` (which log from inside) are the only shell fetches beside kb lookups, which the store's `fetcher` field shows.
- **The age-only lock (`LOCK_STALE_S`)** exists because `os.kill(pid, 0)` ends the holder on Windows. It can go when the standard library checks a PID without signalling it on every OS.
- **The CI check, the revert and `apply-failed` (`FAILED_RETRIES`)** exist because an automatic commit reaches `main` before its pipeline runs. They can go when automatic commits land on `main` only after a green pipeline, which `.gitlab-ci.yml`'s branch pipelines and direct pushes do not give.
- **Conflict branches, their merge requests, `--hold` and the merge-request list of `status`** exist because `kbgit.py sync` cannot resolve every rebase conflict by rule. They can go when `status` lists no open conflict merge request and `git log` shows no `querylog/` branch merged over a year of automatic commits.
- **Source findings and their ranking by result characters** exist because hosts are staged by hand (`kb/_self/web-sources.md`). They can go when every host the store's fetches name has the staging level it needs, so `status` lists no open source finding for a year.
- **Fetch `chars`** exists for that ranking only, and goes with the source findings.
- **The `usage` rows read from the transcript at session end** exist because no hook input carries a prompt's token usage and the transcript lacks the answer's request when `Stop` runs. They can go when Claude Code passes the prompt's `usage` to the `Stop` hook, and capture then writes the same record from it.
- **A cloud session's push to its working branch** exists because the session's git proxy takes pushes to that branch only. It can go when the proxy takes a push to `main`.
- **The weekly digest hook** exists because no other place shows the store's numbers to people. It can go when the numbers are read from another place built on the same `digest`, such as a CI job's report, and the hook shows nothing new.
- **The Haiku stage** exists because code cannot tell whether a reply answered its question, or find a person's or organisation's name in a question. It can go when learn picks its misses from the pack's verdict alone and a rule-only check flags the names of the name corpus.
