# Code: the rules for the tooling in `_tools/`

The Python under `_tools/` follows these rules; a change to it keeps them. They describe what the code does now. Each rule lives here once: the gate and the definition of done (`kb/_self/maintaining.md`, Conduct for changes; `kb/_self/backlog.md`, Definition of done) point here for the code, and `kb/_self/tools.md` lists the tools and their commands.

## Runtime

- **Standard library only.** A tool runs with the interpreter alone, on Python 3.11 or newer, with no install step. `pyproject.toml` names dependencies for development only (pytest, pytest-xdist, ruff); no tool imports them outside a test.
- **One entry point.** A hook reaches a script through `_tools/kbpy`, never by naming an interpreter (`kb/_self/querylog.md`, Portability).

## Portability

The same code runs on Linux, macOS and Windows.

- **Text is UTF-8.** Every `open`, `read_text` and `write_text` names `encoding="utf-8"`; a write adds `newline="\n"`, so a file has the same bytes on every host. A script that reads or prints text through a pipe (a hook, the MCP server) reconfigures its streams to UTF-8.
- **Paths go through `pathlib`** in new and changed code (older modules still use `os.path`): no string joins with `/` or `\`, no shell syntax in a path. A path written into a doc or a ledger uses `/`.
- **Subprocesses take an argument list**, never a string and never `shell=True`. A tool starts Python with `sys.executable`, not `python3`, which on Windows can be a Store alias.
- **A file at a revision is read with `git cat-file blob REV:PATH`**, never `git show REV:PATH`: `show` also checks its argument as a file name, which fails as "Filename too long" in a deep Windows checkout.
- **No Unix-only calls** (`fcntl`, signalling a PID to probe it, `os.fork`). A lock is an `O_EXCL` file; a detached child sets the creation flags of each OS.
- **Windows names no process's working directory.** Before removing or moving a directory a process may hold there, a tool renames it to a sibling and back (`bl_land.held_by_process`, with `os.rename`): Windows refuses while a process runs with it as its current directory or holds a file open in it, so a refused rename is a reason to leave the directory as it is.
- **A test skips what a host lacks** (no `sh`, no `git`, no PowerShell) with a marker that names the missing part; it never passes without running.

## Git in tests

- **A test never acts on the real repository.** `_tools/conftest.py` removes the variables that name a repository (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and the others) from the environment before any test, because a git hook sets them and a run it starts would inherit them. It clears `KB_NO_PUBLISH_HOOK` the same way (at import, so in every xdist worker), because a session may export it and a test that needs it sets it itself with `monkeypatch`.
- **A test over the repository's live data holds at any size of it.** A test that reads the live kb or backlog asserts named content or a shape (a verdict, a header, an exit code), never a count or a length another session's growth can break, or it runs over a fixture.
- **A scenario builds its own repository** in a temporary directory, with `git_env()` for its environment: no global or system git config (its own entries only: no automatic maintenance, and `core.longpaths`, since a worktree of a seeded clone under a Windows pytest temp directory passes 260 characters and no host setting reaches the scenario's git, BG-6sdkqlsu), a fixed author and committer, and none of the variables that leak a CI run or a verification date. The `Repo` helper runs git in such a directory, `kb_seed` seeds it with the tool files and kb content a run needs (repacked into one pack, so a scenario's two clones link one file, not one per object), and `scenario` is the fixture that hands a test such a repository. A test that needs git carries the `git` marker, so `tests.py -m "not git"` leaves it out. `tests.py` hands a worker a whole file or class (pytest-xdist `loadscope`): two long scenarios of one file run one after the other, and each in a class of its own run on a worker of its own, as in `test_land_e2e.py`.
- **A sync or pre-push run inside a scenario sets `KB_SYNC_NO_TESTS=1`**, so the scenario's own gate does not start the suite again.

## Output

- **Output is deterministic.** The same inputs give the same bytes: sorted iteration where order is not data, `\n` line endings, no BOM, and a clock or an environment value only where recording it is the tool's purpose.
- **Threads leave the output as one worker's would.** A tool that runs subprocesses in parallel uses `concurrent.futures` threads and no extra dependency, writes what the runs return in the order of its input on the calling thread (never in the order they finish), and guards a counter the threads share with a lock (`bench_pool.run_tasks`, `bench_core.SPEND_LOCK`).
- **Derived state converges.** A second run on unchanged inputs writes nothing and changes nothing (`build_index.py` twice, `querylog.py learn` and `apply` twice, `kbid.py add` with the same row, `benchmarks.py pool build` and `pool build --querylog` over their own files, which keep the sample they hold (the public one its checks too) and ask no model, unless `pool build --redo ID` names eval rows to ask for again). A `--check` form writes nothing and exits 1 when a run would change a file.
- **A derived cache's key holds the form of its rule.** A cache of results one of our rules computed (a projection, a leak scan's verdicts or values) puts a form constant of that rule in its key or file name (`kbpublic.PROJECTION_FORM`, `SCAN_FORM`), bumped whenever the rule changes what it yields, so no result cached under an older rule is read; a cache of verbatim fetched text needs none.
- **A file another process reads while a run writes it** (the query log's) is written whole or not at all: to a temporary name, then replaced.

## Exit codes

- **Each tool documents its own codes** in its docstring and in `kb/_self/tools.md`; a change to them changes both. A code is never renumbered.
- **The pattern the tools share:** 0 done or nothing to do; 1 the tool found what it looks for (a failed check, stale docs, a change `--check` would make, a failed step); 2 it could not do what was asked (bad arguments, not a git clone, an unreadable input, a refusal); 3 a human or another process must act first (a conflict, a held lock). A tool states where it differs.
- **A hook that only logs or informs exits 0 whatever happens**, so it never blocks a prompt or a tool call by failing; only a gate blocks, with exit 1. A hook that answers by running another tool (`backlog:` runs `backlog.py`) lets the prompt through with a note when that tool fails or times out.
- **A usage error is not a finding.** An argument error exits 2, so a caller cannot mistake it for exit 1.

## Checks and their tests

- **The suite is small and has a ceiling.** `python3 _tools/tests.py` runs the whole suite (pytest and pytest-xdist through uv). `_tools/tests_ceiling.json` holds the most test ids (`max_ids`) and test files (`max_files`) the suite may have and the longest a full run may take per platform (`max_seconds`), with `decision`, the id of the decision that records them. `tests.py` checks the file count and that `decision` names an active decision of `kb/_self/_decisions.csv`, made by the operator, whose text holds the file's own numbers; a full run also fails when it ran more ids than `max_ids` or took longer than `max_seconds`; `tests.py --ceiling` checks ids and files without running a test. On a CI runner `KB_TEST_TIMEOUT_FACTOR` multiplies the seconds. A number of the ceiling changes only with the operator's recorded answer (`python3 _tools/backlog.py answer ID GATE --answer "tests-ceiling ids=N files=N seconds=..." --by operator --record`, then that decision's id in the file); an agent never raises it. A new test id needs room under `max_ids`; at the ceiling it replaces one.
- **A test is written only for** one command's main path, end to end; one planted failure per gate, the input the gate must refuse (a check that no planted input can fail proves nothing, `kb/_self/backlog.md`, Definition of done); a machine-read format another tool parses; a secret, leak or untrusted-code guard.
- **A test is never** a matrix (at most two `parametrize` cases); a test that reads a doc, a skill or an agent file to assert its wording; a test of a helper when the command's behaviour shows the same; a regression test for a defect a log shows.
- **A bug gets a retrospective, not a test.** Operational errors are detected from logs (the ops rows `test.run`, `sync.gate`, `land.step`, `done.refused`, `ci.pipeline` and `python3 _tools/querylog.py digest`) and from a gate's own output. A bug is fixed and proven by its `repro` (a tool run on a planted input, or a command with a match); what let it through goes into the sprint's retrospective as a process finding, a backlog story when a change is accepted. A regression test is written only when no log and no gate output can show the defect again, and then within the ceiling and the kinds above. When something breaks later, file a bug and a retrospective finding; the suite does not grow.
- **A compile warning is an error.** Before pytest, every `tests.py` run (a selection and a `--changed` run too, not `--ceiling` or `--write-lint-baseline`) compiles each `_tools/*.py` from its source text, writing no `.pyc`, and exits 1 naming each file and line whose compile warns, such as an invalid escape sequence (a `SyntaxWarning`; a `DeprecationWarning` before Python 3.12): a regex or Windows path in a plain string literal needs a raw string or a doubled backslash. pytest only prints such a warning, a cached `.pyc` does not repeat it, and a file no test imports is never compiled by a test.
- **A file format is named in `kbcommon` and checked in `check.py`.** The decision files (`kbcommon.DECISION_COLS`, `MAKER_COLS`, `POLICY_ROW`, `DECISION_ID`, `context_refs`) are checked by `check.py`'s `check_decisions`, which reports each broken rule by file and line.
- **A path limit is a named constant of `check.py`.** `WINDOWS_MAX_PATH` less the length of a typical Windows worker worktree prefix (`WORKTREE_PREFIX`) gives `TRACKED_PATH_MAX`, the longest path `git ls-files` may list; `check.py` without `--root` refuses a longer one. A tool that writes a tracked file under a new directory depth keeps within it.

## Layout

- **Flat modules in `_tools/`.** No packages: the directory is on `sys.path` for every script, and a package named like a script would shadow it.
- **A subsystem is a prefix.** The query log's stages are `ql_*.py` modules (`ql_base.py` holds the shared ground, `ql_store.py` the entry and finding formats with their gates (the entry keys and the finding kinds), the others one stage each); `kbgit.py`'s are `kg_*.py` (`kg_base.py` the shared ground, `kg_merge.py` merge and ledger repair, `kg_lane.py` the lane plan, the `code/<id>` branch name and the lane commands, `kg_sync.py` the sync run, its gate and its push, `kg_lock.py` the host's main lock `sync --push` and `land`'s rebase hold, and the bounded wait their git fetches and pushes run under (it reuses the helpers of `tests.py`'s test lock and imports no `kbgit`), `kg_trailers.py` the trailer computation, the audit of a range and the work state, `kg_hooks.py` the git hooks and the hook install, `kg_history.py` the history commands, `kg_bridge.py` the public-bridge command); `benchmarks.py`'s are `bench_*.py` (`bench_core.py` the harness, `bench_report.py` the report tables, `bench_lookup.py`, `bench_retrieval.py`, `bench_querylog.py` and `bench_install.py` the scenario families, `bench_pool.py` the question pool the pool command builds, the `pool` scenario that runs it and the `pool verify` and `pool respend` commands that check and repair its record); `backlog.py`'s are `bl_*.py` (`bl_base.py` the shared ground: the project settings read from `backlog.json` for the root the command runs on (`load_settings`) and the accessors that give them at call time (`setting`, `rel_dir`, `kinds`, `id_re`, `always_in_scope`, `worker_dir` ...: no module copies one into a constant at import), the refusals, the `Backlog` class, `git` and `run`, the scope helpers (with the touches overlap rule), the external tracker id helpers (`external_*`: the one place an item's `external` ids become refs, urls, `KB-Ref` trailers and a merge request description block, which `show`, `land` and the commit helpers call), the name guard, the commit helpers and the readiness rules (`waits`), which `backlog.py` and the other `bl_` modules import and which imports no `bl_` module at load nor `backlog`; `bl_cli.py` the subcommand registry, where each module that owns a command registers its parser and handler when imported, `backlog.py`'s `USAGE` puts them in the usage order and `backlog.main` builds the parser from it, importing `bl_base` only; `bl_cost.py` the `cost` command's report, a command group that registers its own parser and imports `bl_base` and `bl_cli` only; `bl_dispatch.py` the `brief` and `dispatch` commands: the worker's brief, its turn cap, and the headless session's start (it writes the brief and the session's output outside the worktree, in the scratch directory, never into a committed file), registering its own parser and importing `bl_base`, `bl_cli`, `bl_items` (the `goal` text) and `bl_land` (the worker's branch and worktree names); `bl_ci.py` the CI readers, the red-main bug and the `red-pipeline` and `intake` commands, importing `bl_base`, `bl_cli` and `bl_intake`, never `bl_land` or `backlog`; `bl_forge.py` the one read of a merge request (by branch or title prefix: merged, opened with its pipeline status and detailed merge status, closed) and of a ref's newest pipeline, and the merge of the item's own `code/<id>` request, through a glab arm and a gh arm chosen by the `forge` setting, aimed at `forge_project` else the integration remote's URL; the gh arm reads and its merge verb refuses; it imports `bl_base` at load and `ql_deliver`, `kbpublic` and `kg_lane` where it reads them, never `bl_land` or `backlog`; `bl_view.py` the read-only views (ready, similar, horizon and its hook form, and the `similar`, `list`, `tree`, `find`, `show`, `next`, `held` and `horizon` commands), importing `bl_base`, `bl_check`, `bl_cli` and `bl_plan`; `bl_items.py` the item writers (`new`, `fmt`, `claim`, `release`, `answer` with its decision recording, `set`, `move`, `reopen`, `gate`, `host-check`, `fire`, `drop`, `referrers` and `goal`, with `parse_cmd` and the shared write path `changed_items`), registering their commands itself and importing `bl_authority`, `bl_base`, `bl_check`, `bl_cli`, `bl_land`, `bl_plan` and `bl_view` (`similar` for `new`'s near-duplicate warning), never `backlog`; `bl_check.py` the item rules (`validate`), the knowledge checks, the repro and no-op warnings and the `check` and `selectors` commands, importing `bl_base`, `bl_authority`, `bl_cli`, `bl_intake` and `bl_plan`; `bl_authority.py` the gate classes and the classes only the operator answers, importing `bl_base` only; `bl_plan.py` the code-and-docs rules, the overlap that orders two items (`shared_doc`, the `kb/_self` docs that `held --overlaps`, through `touches_meet`, and `check`'s shared-file and unordered-overlap warnings leave out of the base overlap rule), the host-check gates and the `start` command, importing `bl_base` and `bl_cli` only, never `bl_check` (the two form no import cycle); `bl_land.py` the `done`, `researched` (the goal research story's check, by `done`'s rules), `land` and `close` commands with the evidence and the worker's worktree release they share, importing `bl_base`, `bl_check`, `bl_cli` and `bl_intake`, never `backlog` (and no `bl_` module imports it); `bl_intake.py` the intake's detector registry, candidates, fingerprints and draft items, and the filing of `intake --file` (`file_found`: the near-duplicate merge and the open-drafts cap) and of its hook form (`file_hook`: the cap and the fingerprints of open items and of the drafts set aside under `INTAKE_ASIDE`, which `bl_land` imports, with no merge), which writes the backlog's files only through the `Backlog` it is given; `bl_procs.py` the process inventory behind `backlog.py procs` (registers itself, imports `bl_base` and `bl_cli` only); `bl_stall.py` the stall signals behind the read-only `backlog.py stalled` (registers itself, imports `bl_base` and `bl_cli` at load and the query log, `tests`, `bl_procs` and `bl_forge`, which reads a claimed item's `code/<id>` request for `mr-dead`, where it reads them); `bl_selfcheck.py` the six checks behind `backlog.py selfcheck` and its capped output (registers itself, imports `bl_base`, `bl_cli`, `bl_procs` and `bl_stall` at load, and `tests` and `kg_hooks` where it reads them); `backlog.py` itself holds the usage text and the dispatch, and the item writers and readers of one item (`new`, `fmt`, `claim`, `release`, `answer`, `set`, `move`, `reopen`, `gate`, `fire`, `drop`, `host-check`, `goal`, `referrers`) are in `bl_items.py`, which registers them (`kb/_self/backlog.md`, Changing this process); each `bl_` module has its own row in `kb/_self/tools.md`). A module's first lines say what it holds and which doc describes it.
- **A CLI facade keeps the command.** `_tools/querylog.py`, `_tools/kbgit.py`, `_tools/benchmarks.py` and `_tools/backlog.py` are the scripts hooks and people run; each holds the command line, the usage text and the dispatch (`benchmarks.py` also the `SCENARIOS` registry), and the stages live in the prefixed modules beside it. A split moves code behind a facade and leaves the commands, their output and their exit codes as they were.
- **Tests sit beside the tools** as `_tools/test_<subject>.py`, shared setup in `_tools/conftest.py`, which also holds the tracked-file scans (`tracked`, `text`) that the tests over kb content share.

## Imports

- **A module imports the modules below it.** The facade imports its helpers; a helper never imports its facade. Inside a prefix, the shared ground (`ql_base.py`, `kg_base.py`, `bench_core.py`) imports no sibling, and a stage imports the stages it builds on, never one that builds on it.
- **No cycles at the top level.** A reach back up the order is an import inside the function that needs it.
- **A leading underscore means the module's own.** Another module does not import or call a name that starts with `_`; a name two modules need is public, without the underscore.
- **A reader of a file format that a writing tool also reads is below it.** `kbdecide.py` imports `kbfacts.py` (to find facts), so the lookup side reads `_decisions.csv` itself, tolerantly and by its columns (`kbfacts.decision_rows`), never through `kbdecide.py`; `check.py` stays the one place that judges the format.
## Writing a checked file

- **A tool that writes a file `check.py` checks asks `check.py` whether the write is clean.** `kbdecide.py` writes a root's `_decisions.csv` (or kb/_self's), then runs `check.check_decisions` over the files as they are and undoes the write, with exit 2 and the errors, when it added one the file did not have before; it never hand-copies a rule of the format, so a row it writes cannot fail the check, and a later rule applies to it at once. The module takes the check as a library, which is the one place a tool imports `check.py`.
- **A refusal exits 2 and leaves every decision file as it was.** The message names the rule. `ratify` and `revert` of an autopilot decision refuse any `--by` but `operator`, a decision that is not an active autopilot one and an empty `--why`, and a revert files its story through `backlog.py`. The commands an agent may not run are `supersede` and `restore` without `--by operator`, and `invalidate` of a `proposed` row, which names no maker. `sweep` is open to agents and applies a rule for each of these: a dropped item, an item deleted at close whose last version in git history is dropped, an item deleted by `drop` outside a sprint whose last version is not done, a superseded source, a gone article or domain, a passed `review_by`; it leaves alone a done item, an item deleted as done, an item still present and a missing fact. The relink flag for a missing fact and `relink`, which is open to agents too, draw on the likeliest fact's sources (git history, anchors, doc2query questions, the decision's words) and offer none below a cut. The tool reuses `kbfacts.fact_key` for a fact's key and `kbfacts.units` for the facts, so it never hashes a fact itself.
