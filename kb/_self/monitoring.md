# Monitoring: kbmon, one snapshot of the kb and its surroundings

`python3 _tools/kbmon.py` names nine panels (the kb, coord, running sessions, the query log, the host, the sprint, the cleanup, a paid benchmark run's bench and the log) and shows each whose module exists, as one JSON snapshot (`--json`), as metric points (`--metrics`), as event and span records (`--events`), as the agent's one-line receipt (`--receipt`), as a plain-words answer to one question (`--status`), as plain text (`--once`), live (without any of them) or live in a pane beside the session (`--split`), laid out as the Layout section gives it. The facade `_tools/kbmon.py` holds the command line, the usage text and the exit codes; `_tools/mon_base.py` the panels, the run of a panel and the snapshot; `_tools/mon_view.py` the redaction, the layout of the text view and the console's escape support; `_tools/mon_export.py` the metric points; `_tools/mon_events.py` the event and span records; `_tools/mon_receipt.py` the receipt; `_tools/mon_status.py` the status answer; `_tools/mon_needs.py` the `needs you` line; `_tools/mon_split.py` the pane split; each panel is the module `_tools/mon_<name>.py` (`mon_kb.py` for the kb panel, `mon_clean.py` for the cleanup panel). A command's flags and exit codes are in `python3 _tools/kbmon.py --help` and `kb/_self/tools.md`.

## The snapshot

- **Schema 1.** `--json` prints one object: `schema` (1), `taken` (UTC time), `panels` and `alerts` (a list of `{kind, id, message, since}`, the alerts the `ok` panels judge from their data; empty while none does: the kb panel's failed lookup eval `kb.eval`, the sessions panel's orphan process, the host panel's low disk and the querylog panel's refused delivery, below). `panels` holds one entry for each of `kb`, `coord`, `sessions`, `querylog`, `host`, `sprint`, `cleanup`, `bench` and `log`, or only those `--panel NAME` (repeatable) names, in that order.
- **A panel has a state and seconds.** `state` is `ok`, `timeout`, `error`, `absent` or `unsupported`; `seconds` is how long the panel took (the timeout itself for `timeout`, 0 for `absent`); `data` holds the panel's object for `ok`, `{"error": ...}` for `error` and `{"reason": ...}` for `unsupported`, and for `absent` or `timeout` where the panel's own `collect` ended in it (see below); it is left out for a `timeout` that `--timeout` cut and for an `absent` panel with no module.
- **A panel is a module.** `mon_<name>.py` has `collect(ctx)`, which returns the panel's data (a dict of JSON values) and reads without writing, and may have `lines(data)` or `lines(data, width)`, the panel's body rows (`width` is the columns the view may use), which the view prints under the panel's title behind the gutter, and `REFRESH_S`, the seconds the live view serves the panel's last `ok` result before it runs the panel again (see The live view). `collect` raises `mon_base.Unsupported` when this host or setting cannot give the panel (state `unsupported`), `mon_base.Absent` when it has nothing to show (state `absent`), `mon_base.Timeout` when its source gave no answer in time (state `timeout`); each of the three gives `{"reason": ...}`, the exception's text, as the panel's data (`Absent`: the bench panel with no run; `Timeout`: the coord panel's server, see The coord panel); any other exception is state `error`; a panel with no module is `absent`. `ctx` holds the clone `root`, the coord `store`, `url` and `key_file` (`--root`, `--store`, `--url`, `--key-file`). All flags are defined by the facade, so a panel's module changes none of them.
- **Each panel runs in a daemon thread, all at once, bounded by `--timeout` seconds** (default 10). A panel still running then is `timeout` and its thread is left behind: a daemon thread never holds the process at exit, so the snapshot returns when the slowest bound passes, not when the slow source answers. The panels that read the ops rows (`bl_stall.ops_rows`: kb, sessions, host, sprint and log) share one read of them within a snapshot.
- **Exit codes.** 0 a snapshot was shown (`--receipt` too, with or without an alert); 1 it was shown and its `alerts` are not empty; 2 a bad argument, or a `--from-snapshot` file that is unreadable or is no snapshot of schema 1.

## Read only and redacted

- **A run writes nothing and starts nothing.** It builds no pack index, runs no lookup eval, makes no network request (but for the coord panel's, to the `--url` server) and writes no file in the clone, the query log home or `_cache/`. The kb panel sets `KB_INDEX=0` for the rest of the process, so even the fingerprint memo the lookup tools keep in the index directory is not written.
- **Every printed string passes `redact.redact`**, in `--json` and in `--once`: each string and each key of the snapshot, and each line of the text view once more after a panel's own `lines` made it. A snapshot saved with `--json` and shown with `--from-snapshot FILE` passes the same rules, so a saved file that holds a token, a path or a host name prints with the query log's placeholders. The public root's content, which `redact` allows, is read only when a string matches an identifier shape (`mon_view.LazyKnown`), and for the GUID shape, which the session ids of coord events have, only the GUIDs of it are scanned for; the scan is kept for the life of the process. A session id is no such object id: the coord panel, the log panel and the coord status answer show it, before any redaction, as `s-` and the first six hex characters of its SHA-256 (`mon_view.session_label`: a claim's `session/` key, a holder, an event's `holder`, `operator` and `session` fields and the digest's `session/`, `session=` and `holder=` words), so the raw id is never printed and one session has one label in every panel; any other GUID still gets the placeholder, and every other string, a holder that is no GUID too, still passes `redact.redact`.
- **The text view prints no control character** of a panel's text; an escape byte appears only in a frame that is coloured and redrawn in place (see The live view).

## The metric points

`--metrics` prints one JSON object: `schema` (1), `taken` and `points`, from the same snapshot as `--json` (so `--panel` and `--from-snapshot` work, and the strings have passed `redact.redact`). `mon_export.py` turns it into points, each with `name`, `unit`, `kind`, `value` and `attributes`.

- **Names.** `kbmon.<panel>.<measure>`: `kbmon.kb.facts` (unit `{fact}`, attributes `root` and `tag`, the counts of `rag.py audit`), `kbmon.kb.articles`, `kbmon.kb.gaps`, `kbmon.kb.conflicts`, `kbmon.kb.index_age`, `kbmon.kb.eval_passed`; `kbmon.coord.claims` (attribute `state`: `live` or `over_budget`), `kbmon.coord.claim.left`, `.budget` and `.spend` (attribute `item`), `kbmon.coord.event_seq`, `kbmon.coord.runs` (unit `{run}`, attribute `state`: one point for each of coord's run states, 0 for a state no item is in), `kbmon.coord.run.blocked_wait` (the seconds the oldest blocked run has waited since its newest progress event, 0 with none) and `kbmon.coord.run.working_silent` (the most seconds a working run has gone since its newest progress event, 0 with none); `kbmon.sessions.procs` (attribute `class`), `.worktrees` and `.stalled`; `kbmon.cleanup.leftovers` (unit `{leftover}`, attributes `class` and `verdict`), `.removable_bytes` and `.free`; for every panel `kbmon.panel.up` (1 for `ok`) and `kbmon.panel.seconds` (attribute `panel`); and `kbmon.alerts`. A panel with no exporter gives its `up` and `seconds` points only.
- **Kinds.** `gauge` for a value that goes up and down, `sum` for the coord event sequence number, which only grows.
- **Attributes are numbers, flags or identifiers.** A string value is kept only when it is letters, digits and `_ . : / # @ -` (120 characters at most) and `redact.redact` returns it as it is; a point with any other attribute value is left out whole. No free text of a panel (an error, an event field, a digest line, a path) is exported.
- **No holder.** Claims are counted by state; a claim's key is the `item` attribute only when it is a backlog item id (two letters, a dash and eight characters), and a claim's holder is never an attribute.

## The receipt

`--receipt` prints one JSON object, `line` and `fingerprint`, from `mon_receipt.py`, for an agent that wants the monitor's state in a few tokens. It takes the snapshot of the querylog, sessions, host and sprint panels, or of the panels `--panel` names (so `--timeout` and `--from-snapshot` work, and the strings have passed `redact.redact`), and uses its `alerts` and, for the count of what waits on the operator, the entries of `mon_needs.py` (the sprint panel has no alert of its own). It writes no file and exits 0 with or without an alert, so a caller reads the object, not the code.

- **The line.** With alerts: `ALERT`, the messages of the first two alerts, `(+N more)` when there are more, and `state on ask: python3 _tools/kbmon.py --once --panel NAME`, with NAME the panel of the first alert. It ends with `; needs you: N — python3 _tools/kbmon.py --status all`, N being the number of entries of the `needs you` line (`(not read: PANELS)` after it when a panel that count reads was not read), the command printing that line first. It is at most 200 characters (the messages are cut with an ellipsis to fit, the ending never) and `redact.redact` leaves it as it is. With no alert: `kbmon: no alert on` and the alert panels read, then the same ending; a panel that timed out or errored judges nothing, so it is no alert.
- **The fingerprint.** Twelve hex characters of a hash of the sorted kinds and ids of the alerts. It moves when an alert appears, goes or changes kind or id, and stays when only an alert's message or `since` changes, or what waits on the operator; kbmon keeps no earlier fingerprint, the caller compares.

## The status answer

`--status [TOPIC]` prints a short answer in plain words to one question about the monitored work, for an agent or a person who would otherwise read the whole text view. TOPIC is `sessions`, `cost`, `querylog`, `coord`, `sprints`, `load` or `all` (the default). `mon_status.py` takes one snapshot of the panels the topic needs (sessions: sessions; cost and querylog: querylog; coord: coord; sprints: sprint and host; load: host and sessions; all: those five, and its first line is the `needs you` line of the Layout section) and answers from it, so `--timeout` and `--from-snapshot` work and a panel that is not `ok` gives one line that says so. `--panel`, `--once`, `--metrics`, `--receipt`, `--events` and `--split` beside it exit 2; `--json` makes the answer an object.

- **What each topic says.** `sessions`: each orphan process by pid, age and checkout, each stalled item by title and id with its signals, each live Claude Code session as one line (6 at most, then `+N more sessions`; the line is `mon_sessions.session_line`, the same text the sessions panel shows), this clone's operator id, one line for the live session intents in coord (their count and the titles of the items they announce, 6 at most then `+N more`; no session label, which only the session lines carry), the overlaps between live sessions, one line each with both labels and items, the shared files and the strategy (`--json` fact `overlaps`, their count), and a pointer to `python3 _tools/kbask.py summary` for a model summary, which runs only when asked and stays capped by its budget and turns. `cost`: today's dollars, usage rows and tokens from the querylog panel's `usage_today`, each model with no price, and the day's dollars by model, by session (its `s-` label) and by sprint (the sprint's title; `none` for usage outside a work window), the top three of each with `+N more`; `--json` gives all of each as the facts `by_model`, `by_session` and `by_sprint` ({name: dollars}). `querylog`: the last delivery outcome (a refused one with its first error line), the undelivered entries and runs, and the spool. `coord`: each live claim's key (the session claims first, a session by its label), time left and budget beside spend, never its holder; then the count and ids of the open asks to the operator (the ids are where the operator acts) and one line of the coordination settings a file sets, each key with its value and the file that set it (`strategy.working = after (set by settings.json)`), or `all default`; `--json` facts `asks_to_operator` and `settings`. `sprints`: where the items were read from (the local `origin/main`, with the commits the checkout is behind it, and, when it is behind and cannot fast-forward, a line saying so with the cause from the panel's `fast_forward`; `--json` facts `fast_forward`), and one row for each sprint, the active one first, then the approved, then the planned: its short name (its title cut after a whole word to at most 40 characters, `mon_status.short_name`, ending in an ellipsis where cut), its state, items done of all (done and dropped count as done), the percentage and the ETA (`not started` for an approved sprint, `waits for start gate` for a planned one), at most 100 characters (`mon_status.sprint_row`, the function the sprint panel's rows use too); `--detail` (with `sprints` only, and not with `--backtest`, else exit 2) prints the full lines instead: for each sprint its title, items done of all with the percentage, the items in progress and to do, its next item, the items left, each by its short title, and the ETA; under both forms the gates that wait for an answer, each landing in progress (by its item's title, its last step and how long ago that was; never by id) and the host load. The ETA is an estimate from `mon_eta.estimate` (see Estimate under the sprint panel): `ETA about 33-69 min, high confidence; basis: 3 code from 12, 1 review from 12, tail from 12.` on one line of the detail lines (from 180 minutes in hours, `about 3.5-5.0 h`; a row has `ETA 33-69 min`), taken at the snapshot's time; with no duration history it says there is no ETA yet, and where the panel read the checkout's files because `origin/main` was not readable, that `origin/main` was not readable. An id is written only on a line where the operator acts (a waiting gate). `load`: the load average against the cores, the holders of the suite and main locks, the processes in the clone, the disk, and the CPU consumers grouped by kind (and clone, for the kb's own scripts) in CPU order, each with its percent, process count, a fixed cause and a fixed remedy, and which kind of percent ps gives on this host; `--json` adds `groups` of `kind`, `clone`, `cpu`, `procs`, `cause` and `remedy`.
- **Plain words.** An item is named by its title, from the clone's backlog, and by its id only on a line where the operator acts (a stalled item to release, a gate to answer); an item the backlog does not hold is named by its id.
- **Short, redacted, clean of paths.** An answer is at most 25 lines (in `all` each topic gives four and ends in a pointer to `--status TOPIC` when it holds more); every line passes `redact.redact` and every absolute path is replaced by `<path>`, so a line names no path outside the clone.
- **`--json`.** One object: `schema` (1), `topic`, `taken`, `lines` and `facts` (numbers, flags and names of the topic, or, for `all`, an object of them for each topic).
- **Exit codes.** 0 shown, also when the snapshot has an alert; 2 a bad argument or an unreadable snapshot. It calls no model, starts no session and writes no file.
- **Plain questions reach it first.** `mon_status.topic_of(question)` maps a plain question to a topic by fixed cue words, each a word that names the monitored thing beside a word that asks its state (sprints and progress or percentage, sessions and running or stuck, `my computer` and load, cost and today, or `so far` in a question about what I or we spent, the query log and delivered, `coord` and claims), `all` when the question names several, and None otherwise, so a docs question that holds only one of the words (how Claude Code sessions resume, what a licence costs, a ConfigMgr deployment's status) or opens with how to do something or what a thing does (`how do I`, `how to`, `how does`, `what does`) stays a lookup. The `kb` MCP server's `kb_monitor_status` tool (`topic` as `--status`, the team's own server only) returns the lines of `kbmon.py --status TOPIC --json` as text to any agent, with no model call and each panel bound by `--timeout`, and `kb-observer` starts from `kbmon.py --status`, which `kbask.py` lets its session run. `kb_ask.py` answers a question it maps with `kbmon.py --status TOPIC` before any pack or model (`--route` prints `kind=status`), the `status:` prompt of the kb hook blocks with the same lines as the reason and `status+:` passes them to the model as context (`mon_status.run` starts `kbmon.py`; a failure lets the prompt through with a note), and one `AGENTS.md` line sends a status question there first. None of them writes a query log row.

## The OpenTelemetry adapter

`otel/kbmon_otel.py` sends the metric points, the event records and the spans over OTLP/HTTP with the OpenTelemetry Python SDK. It is a project of its own: `otel/pyproject.toml` names the SDK, the OTLP/HTTP exporter and the Prometheus exporter, `otel/uv.lock` pins them, and `uv run --frozen --project otel python otel/kbmon_otel.py` installs them into `otel/.venv` and runs it. No file in `_tools/` imports an OpenTelemetry package; the adapter runs `kbmon.py --metrics` and `kbmon.py --events` as child processes and exports what they print.

- **Off until an endpoint is set.** The SDK's own variables name where to send: `OTEL_EXPORTER_OTLP_ENDPOINT` (a base URL; the exporter appends `v1/metrics`) or `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`. `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` does the same for logs (`v1/logs` appended) and `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` for spans (`v1/traces` appended), and each signal falls back to the general variable. A signal with none of its variables is not sent; with none at all the adapter sends nothing, prints `export is off` and exits 0.
- **Credentials from the environment only.** Headers come from `OTEL_EXPORTER_OTLP_HEADERS` (or the `_METRICS_`, `_LOGS_` and `_TRACES_` variant of a signal) and no flag or file names them. No header value is printed or logged: a filter on the log handler replaces each value with `***`, the endpoint is shown as scheme, host and port only, and the child kbmon run gets the environment without any `OTEL_` variable.
- **Encoding.** The SDK exporter's own (protobuf over HTTP); nothing is encoded by hand.
- **What is sent.** The points of one snapshot as observable gauges, and `sum` points as observable counters, with the point's unit and attributes under the resource `service.name` `kbmon` (`OTEL_SERVICE_NAME` overrides it). The attribute rules of The metric points apply, since the points are kbmon's own.
- **The resource names the operator by id.** Every signal carries one resource, which `kbwho.otel_attributes()` builds (`kbwho.py --otel-attributes` prints it, and the adapter runs that for both of its resources): `service.name`, `kb.operator.id` with the operator id (left out when there is none) and each entry of `OTEL_RESOURCE_ATTRIBUTES` except `user.email` and one whose value holds an email address. The adapter makes the resource from it alone, with no `Resource.create`, so the SDK's own read of `OTEL_RESOURCE_ATTRIBUTES` adds nothing; when `kbwho.py` gives no attributes the resource is `service.name` alone.
- **Claude Code's own `user.email`.** The attribute `user.email` belongs to the telemetry Claude Code itself exports (`kb/public/claude/otel-monitoring.md`) and reaches only the exporter the operator configures for the session; `kbotel.py` keeps no identity attribute (its `EVENT_KEYS` allowlist has none), and the adapter's resource never carries one.
- **Event records.** Each round runs `kbmon.py --events` and sends every object of its `events` as one log record to `/v1/logs`, under the same resource: `name` is the record's event name, `time` its timestamp, `attributes` its attributes (already limited to numbers, flags and identifiers by The event and span records), with severity text and number `WARN` for an event whose `severity` is `warn` and `INFO` for any other, and no body. Each signal keeps its own cursor in memory: the first round has none, so it sends what a call without `--since` reads, and each round after it gives the cursor of the last round that sent this signal. A round whose log send failed keeps the log cursor and exits 1, so its events are sent again by the next round (a receiver may see one twice); a restart has no cursor and sends the first round's events again. The events do not depend on `--panel`, which is refused by `--events`, and `--from-snapshot` sends none; `--store`, `--url` and `--key-file` go to both child runs. The `spans` of the same object are not sent as log records.
- **Spans.** The `spans` of the same `--events` object are sent to `/v1/traces` (`otel/otel_spans.py`), under the same resource: each is one SDK span with the `id` and `trace` kbmon gave it (so a span sent twice has the same id), its `start` and `end` as the span's times, its `attributes`, and the status `ERROR` when kbmon's `status` is `error`, else `OK`. A landing is one trace: `kb.land` runs from its first `land.step` to its `land.end`, and each `kb.land.step` is a child span of it in the same trace. A `kb.agent.run`, a `kb.test.run` and a `kb.delivery` are a span each. A finished run of an item is one trace: `kb.item` with a `kb.worker` and a `kb.landing` child for each stretch (The event and span records). The worker's own Claude Code telemetry joins it: `backlog.py dispatch` starts the session with `TRACEPARENT` naming the `kb.worker` span and `OTEL_RESOURCE_ATTRIBUTES` naming the item and sprint, so what a worker exports, when its operator turned that telemetry on, carries the trace and the item and sits under the `kb.worker` span; `kb.item.id` and `kb.sprint.id` are added to the entries the dispatching environment had, and `user.email` and an email-valued entry are dropped, as for the adapter's resource above. Spans have a cursor of their own, apart from the log records': a round whose span send failed sends the spans again and not the log records that were sent, and the reverse. Signals at the same cursor share one `kbmon.py --events` run, so a run is made per distinct cursor.
- **`/metrics` on loopback.** `--prometheus-port N` also serves the same points at `/metrics` through the SDK's Prometheus reader (`otel/otel_prom.py`) and prints the URL, `http://127.0.0.1:N/metrics`; port 0 takes a free port. Without the flag nothing is served and there is no default port. The listener binds `127.0.0.1` only: the server's own default is every interface, so the adapter passes the address itself, and `--prometheus-bind` takes only a loopback address (`127.0.0.1`, `::1` or `localhost`), any other host exits 2 naming loopback. It serves kbmon's points only: the reader has a registry of its own, not prometheus_client's global one, so the Python process and GC metrics are not there, and any path but `/metrics` answers 404. The reader answers each scrape from the latest snapshot, so a scrape before the first snapshot is empty. With no OTLP endpoint set and the flag given, the adapter serves `/metrics` and sends nothing over OTLP.
- **Flags.** `--once` sends one snapshot and exits (`--count N` sends N); without either the adapter sends every `--interval` seconds (default 60) until Ctrl-C. `--panel` and `--from-snapshot` are kbmon's, and `--timeout` bounds the child run. Exit codes: 0 sent or export off; 1 a send failed; 2 kbmon gave no points or events, or an argument was bad (a round's code is the worst of its metrics and its events).

## A local Prometheus

`otel/prometheus.yml` scrapes the adapter's `/metrics` on `127.0.0.1:9464` every 60 seconds and loads `otel/kbmon.rules.yml`, so a Prometheus on the operator's machine shows kbmon's points and fires six alert rules, which it sends to the Alertmanager on `127.0.0.1:9093` that `otel/alertmanager.yml` configures. The repository holds the three files and no service file for a host (no launchd plist, systemd unit or timer): the operator installs Prometheus and Alertmanager outside the clone.

- **Start the adapter** from the clone's root with `uv run --frozen --project otel python otel/kbmon_otel.py --prometheus-port 9464`. With no OTLP endpoint set it serves `/metrics` and sends nothing over OTLP (The OpenTelemetry adapter). It takes a snapshot every `--interval` seconds, so a scrape sees the latest one.
- **Start Prometheus** with `--config.file` set to `otel/prometheus.yml` (a Prometheus the operator installs, for example from a package manager). It reads `kbmon.rules.yml` from the config file's own directory, so run it with the file where it stands or copy both files together.
- **The rules.** `KbmonLookupEvalFailed` fires while `kbmon_kb_eval_passed == 0` (the lookup eval failed), `KbmonAlertHeld` while `kbmon_alerts > 0` (kbmon holds any alert) and `KbmonOrphanProcess` while `kbmon_sessions_procs{class="orphan"} > 0` (an orphan process is listed); `KbmonGateWaiting` while `kbmon_coord_run_blocked_wait_seconds > 900` (a run has waited on a gate over 15 minutes), `KbmonRunStalled` while `kbmon_coord_run_working_silent_seconds > 3600` (a working run has posted no progress event for over an hour) and `KbmonRunFailed` while `kbmon_coord_runs{state="failed"} > 0` (a run is in the failed state); each waits 5 minutes (`for: 5m`).
- **Alertmanager.** Prometheus only evaluates the rules; the Alertmanager notifies (`kb/public/logs/prometheus-retention-exposition.md`). Start the Alertmanager the operator installs with `--config.file` set to `otel/alertmanager.yml` and `--web.listen-address=127.0.0.1:9093`. The file groups alerts by name and routes every one to one receiver, a webhook at `http://127.0.0.1:9095/alert`, resolved alerts included; it holds no credential and no address outside the machine. The webhook url points at a receiver that does not exist yet: the repository ships no program that listens there (a parked story adds one that posts each alert as a coord ask to `operator`, which the needs-you line shows). Until a receiver runs on that port, a firing alert is attempted and fails, and Alertmanager's own page at `127.0.0.1:9093` still lists it.
- **Names come from the reader.** A point's name gains its unit as a suffix (`kbmon.kb.index_age` in seconds is `kbmon_kb_index_age_seconds`) and a sum gains `_total`, so a name in a rule is proven, not derived by hand.
- **`--check-rules FILE`** reads one kbmon snapshot through the SDK's Prometheus reader in the process, with no listener and no OTLP send (an endpoint variable in the environment is not used), and compares the `kbmon_` names that the `expr:` values of FILE use with the names the reader serves. It exits 0 when every name is served and prints how many it checked, 1 when some are not and prints each missing name on its own line, and 2 when FILE cannot be read, holds no `expr:` that uses a `kbmon_` name or kbmon gave no points. `--panel` and `--from-snapshot` choose the points as for a send. A label value in quotes is not a name.

## The event and span records

`--events [--since CURSOR]` prints one JSON object from `mon_events.py`: `schema` (1), `cursor`, `events`, `spans` and `problems`. It reads the log panel's sources again (the coord store or `--url` server, the ops rows of `bl_stall.ops_rows` and the query log's last apply outcome) and not the panels, so `--panel` and `--from-snapshot` are refused (exit 2), and like every mode it writes nothing.

- **Events.** `{name, time, attributes}`: every coord event as `coord.<kind>` with its `seq` and fields, every `done.refused` row as `kb.done.refused` and the last apply outcome as `kb.delivery.apply` (attribute `outcome`). `severity` is `warn` on a `done.refused` event and on a delivery that is `refused` or `fetch-failed`.
- **Spans.** `{name, id, trace, parent, start, end, status, attributes}`: a landing is `kb.land` (attributes of its `land.end` row: `item`, `exit`, `ms`, `lane`) with a child `kb.land.step` for each `land.step` row of its item in the landing's span (a second of slack before its start); `kb.agent.run` (its `exit` is 1 when the subagent's closing text was an API error) and `kb.test.run` are one span for each row; a delivery is `kb.delivery`, as long as the log gives its time (the same time as the event, start equal to end). A row's time is when it was written, so a span starts `ms` before it; rows of one millisecond are read in their write order (the committed sidecars' in their files' order, the spool's in the order of its file), so a `land.step` row that shares its `land.end` row's millisecond keeps its child span. A landing becomes a span only once its `land.end` row is in the log, and a `land.step` row with no `land.end` is not exported. The run of an item is a span from its coord progress events (the `run/ITEM` moves): `kb.item` from the run's first move to the move that ends it (`landed`, `refused` or `released`; a run that goes on after `refused` starts a new `kb.item` at its next move), with attributes `item`, `sprint` (the sprint of the item in the backlog, as `origin/main` holds it, else the checkout; left out where the item has none), `state` (the ending state) and the `exit` and `gates` of the ending event; a child `kb.worker` for each `working` to `returned`, `failed` or `blocked` stretch and a child `kb.landing` for each `landing` to `landed` or `refused`, in the item's trace with the same attributes (`state` the stretch's ending state). `status` is `error` when the ending state is `failed` or `refused`. The `id` is a hash of the first move's sequence and the span's name, so it is the same on every call; `trace` is 32 hex characters (the width of a W3C trace id) of a hash of the run's first move's sequence, the same for every span of the run, and a child's `parent` is the `kb.item`'s `id`. `--events` keeps the `trace` as it is, which redaction would read as a GUID. The `kb.worker` of a run that is working has the ids `mon_events.worker_ids` gives, which dispatch hands the worker as `TRACEPARENT` (`00-<trace>-<id>-01`). A span is exported once the move that ends it is above the cursor's coord sequence, so a child may be sent before the `kb.item` that is its parent; a run still under way has no `kb.item`. `status` is `error` when the row's `exit` is not 0 and for a delivery that is `refused` or `fetch-failed`, else `ok`; a delivery has no `ms` attribute. `id` is 16 hex characters of a hash of the row's id, the same on every call, and `trace` is the id of the landing's root (a span of its own for any other).
- **Times and attributes.** Times are Unix nanoseconds. An attribute is kept when its value is a number, a flag or an identifier of the rules of The metric points that `redact.redact` leaves as it is (a list of them as `name_n` for its length and `name_1`.. for the first four; a coord field of comma-separated parts, such as an intent's `item`, is that list); any other attribute is left out and its record stays, and an attribute named `holder` is never set. Every string of the object passes `redact.redact` once more.
- **Cursor.** `cursor` is one opaque text that holds the newest time of the ops rows read with a short key of each row of that millisecond, the newest coord sequence and the time of the delivery exported; the caller keeps it and gives it back with `--since`. Records are those with a time or sequence above it, and the ops rows of the cursor's millisecond whose key it lacks, so the second call with the first call's cursor repeats none of them and a row written in the cursor's millisecond is not lost. Without `--since` the newest 4000 ops rows and 1000 coord events are read. A source that fails adds a `problems` line (`coord unavailable: ...`) and leaves its part of the cursor where it was, so the next call tries it again; a cursor this tool did not print exits 2. An ops row that reaches the spool or the committed sidecars later with a time below the cursor's is not exported, and a delivery is exported only while the apply outcome stands last in the log, with at most its own run's `apply --push: deleted the spool rows` line after it (`standing` in `ql_report.last_outcomes`; its time is the log's last write), so any other line written after it makes no delivery of its own and the outcome is exported once.

## Adding an OpenTelemetry signal

Four places hold OpenTelemetry code, and each takes one kind of work. Put a change in the place whose job it is.

- **The SDK adapter, `otel/`.** The only code that imports an OpenTelemetry package. `otel/kbmon_otel.py` is the runner (the command line, the endpoints, the child `kbmon.py` runs, the cursor and the loop) and each signal that goes over OTLP/HTTP has a module beside it: `otel/otel_logs.py` (`Logs`, the log records), `otel/otel_spans.py` (`Spans`, the traces) and `otel/otel_prom.py` (the Prometheus reader and the `/metrics` server on loopback); the metric points are sent by the runner's own `Sender`. A signal is one module and one row of `SIGNALS`, the registry `main` builds its exporters from (the endpoint variable's name, the class to build, how its records are counted and its progress and failure lines): `main` and `send_events` name no signal, so a new one edits neither. A new SDK package goes in `otel/pyproject.toml` and `otel/uv.lock`, never in `_tools/`.
- **The stdlib exports, `_tools/`.** What the adapter sends is printed by `kbmon.py` first, in the standard library: `_tools/mon_export.py` turns a panel's data into metric points (a new measure is a function in it and a row of its `EXPORTERS` table, keyed by the panel's name) and `_tools/mon_events.py` turns the log panel's sources into event and span records (a new event or span is a reader beside `coord_records`, `ops_records` and `delivery_records` that `collect` calls, with a cursor part if it needs one). The rules of The metric points and The event and span records hold there: attributes are numbers, flags and identifiers that `redact.redact` leaves as they are, and no holder or free text is exported. A new panel gets its points by `mon_<name>.py` and a row in `EXPORTERS`; a panel without one gives `kbmon.panel.up` and `kbmon.panel.seconds` only.
- **The query log's export, `_tools/ql_export.py`.** `querylog.py export --format jsonl` prints the committed store as OTLP-JSON log records for a tool that reads logs (`kb/_self/querylog.md`, Reporting). It builds no endpoint and sends nothing, has its own flat event names and its own gates, and does not go through kbmon. A new family of query log rows is added there, with the store's gates.
- **The receiver, `_tools/kbotel.py`.** `kbotel.py serve` takes Claude Code's own OpenTelemetry events on loopback (`kb/_self/usage.md`, OpenTelemetry events) and keeps the attributes of its `EVENT_KEYS` allowlist, each in a closed shape. A new event or attribute of Claude Code is a row of `EVENT_KEYS`; the receiver stays stdlib and keeps no text or identity attribute.

**What kbmon exports against what a tool records itself.** kbmon holds no store of its own: each run reads the state of the clone, the coord store, the ops rows and the last delivery outcome as they are, and exports them as points and as records after a cursor the caller keeps. What must outlive the run is recorded by the tool that does the work, as a row of its own log: an ops row of `ql_capture` for a landing step, a test run or an agent run, an entry of the query log for a lookup, an event of the coord store for a claim. Add the measure or event to kbmon when it can be read from such a source on every run; add the row to the tool when it is lost unless written when it happens, and let `mon_events.py` or `ql_export.py` export it from there. The query log's export carries the committed history of the store with its own redaction at read time; kbmon's carries the live state and the recent records with `redact.redact` on every string. A fact that Claude Code itself measures (a request's cost and tokens, a tool's duration) is exported by Claude Code and taken by `kbotel.py`, never recomputed in kbmon.

## Layout

`mon_view.render_text` lays out every frame. `W` is the terminal's columns less one (`COLUMNS`, else the terminal's size, else 80): the last column is never written, and no line is longer than `W`.

- **Rows, top to bottom.** The alert line while an alert is shown; the header; the `needs you` line; a blank row; the panels `kb`, `coord`, `sessions`, `querylog`, `host`, `sprint`, `cleanup` and `bench` with a blank row between; the log tail last, which fills the rest of the screen (three rows at least; when the log has more rows than fit, the oldest are dropped and the newest, the bottom ones, stay; the alert rows are counted out first, so an alert never pushes them off). Only the panels `--panel` names are shown, in that order.
- **Header.** `kbmon · YYYY-MM-DD HH:MM:SSZ · refresh Ns · frame n · root`, with a space, U+00B7, a space between the parts, the time in UTC and the root `.` for the clone the script is in. `kbmon` is bold.
- **Needs you line.** One row under the header, `needs you: ` and what waits on the operator, `nothing` when it is empty (`mon_needs.line`, built from the sprint, querylog, sessions and host panels of the snapshot, and the coord panel's open asks, so a saved snapshot gives the same line). In this order, each `; ` apart: each open blocking gate of an active, approved or planned sprint or of one of its open items (`SP-xxxxxxxx gate NAME`, a planned sprint's start gate too); each ask addressed to `operator` that no `answer` of the state `completed`, `failed` or `rejected` has ended (`ask ID since 2026-10-24 14:02: the first 60 characters of the question`, redacted; an Alertmanager alert, a cleanup verdict or a session's question posted as an ask shows here, from the moment it is open: `announce.needs_you_after_min` is not applied); each overlap of two live sessions that no `coordinate` event decided and that is `announce.needs_you_after_min` minutes old (`overlap ST-… (s-…) with ST-… (s-…), undecided for 12m`; the sessions panel's `overlaps`); each active sprint with items left, none ready and none in progress (`SP-xxxxxxxx blocked: N items left, none ready`); a refused query-log delivery with the failed gate or the line that stopped it (`query-log delivery refused: …`); each process of class `orphan`, the oldest first (`orphan pid N (age, in CHECKOUT)`); a disk with under 10 percent free (`disk 5% free`, the host alert's threshold); and a checkout that is behind `origin/main` and cannot fast-forward, with the sprint panel's `fast_forward` cause (`checkout cannot fast-forward to origin/main: …`). A kind names three entries at most and counts the rest (`+2 more gates`); a cause is cut after a whole word at 100 characters. A panel of the four that the snapshot lacks or holds not `ok` adds `; not read: PANELS` (the coord panel too, when the snapshot holds it in state `timeout` or `error`; a snapshot without it, or with no coord store, has no asks to read), so `nothing` is never said of a source that was not read. The row is yellow when it names something and dim when it says `nothing`; `kbmon.py --status all` starts with the same line, and its `--json` facts hold the entries as `needs` (`kind`, `text` and the kind's own fields).
- **Alert line.** `!! ALERT message — since HH:MM`, white bold on red when coloured; without colour a row of `W` `=` follows it. A second alert adds ` (+N more)`. The snapshot's `alerts` make kbmon exit 1.
- **Panel title**, at column 0: `name  state  S.Ss`. A state other than `ok` adds `  — reason` (the error text, or the `reason` a panel gave for `unsupported`, `absent` or `timeout`; where it gave none, `no answer in time` for a timeout and `no mon_<name>.py` for an absent panel) and has no body. The name is bold, the state coloured, and the rest dim when the state is not `ok`.
- **Body rows** sit behind a two-column gutter: two spaces, `! ` for a warning (the row in yellow) or `!!` for an error (red). A panel's own row that starts `! ` or `!!` keeps that gutter; any other row gets two spaces. The label starts at column 2 padded to 10 and the value at column 12; lists are joined by ` · `; a table has a lowercase header row, two-space gaps and its flags in the gutter.
- **Colour** is the 16 ANSI colours and bold, every coloured run ends in SGR 0: green (32) for `ok`, passed and bars under 80%; yellow (33) for a warning, `timeout`, `! ` rows and bars of 80 to 99%; red (31) for an error, `!!` rows and bars of 100% and more; white bold on red (1;97;41) for the alert line only; dim (90) for `absent`, `unsupported` and reasons; bold for names. Colour never carries meaning alone: the state is always written.
- **A narrow terminal**, in this order: under 100 columns the side blocks stack (coord events under the claims, the host's ceiling as 3 rows); lists wrap at an item and continue at column 12; tables shrink their gaps from 2 to 1, cut paths from the left as `…/`, then drop the lowest column; free text is cut at `W` with `…`; ids, counts and states are never cut. The view cuts any line that still passes `W` with `…`.
- **Glyphs** are ASCII and `·`, `—`, `–`, `…`.

## The live view

Without `--json` and `--once`, kbmon shows a frame every `--interval` seconds (1 to 300, default 5) until Ctrl-C or `--count` frames (1 or more; an `--interval` or `--count` out of bounds exits 2) and exits 0, or 1 when the last snapshot had an alert.

- **On a terminal, or with `--ansi`, the frame is redrawn in place:** each frame starts with the cursor-home and screen-erase sequences (`ESC[H`, `ESC[2J`) and is cut to the terminal's lines less one.
- **A resize redraws at once.** On a terminal, with a frame redrawn in place, the live view draws the last snapshot again at the terminal's new columns and lines as soon as the window is resized, without reading the panels, and the redraw starts with the same erase sequences, so a shrink leaves no stale text. Where the platform has `SIGWINCH` the signal triggers it (the view blocks between frames until the signal or the next frame is due, so it uses no CPU meanwhile); on Windows, which has none, the view reads the size 4 times a second between frames. A pipe, a file, `NO_COLOR`, `--once` and `--json` have no redraw.
- **The view idles between frames.** The next snapshot is read one `--interval` after the last frame was drawn, and nothing runs in the wait. What the live view does not read again at once keeps its cost low: a panel with a `REFRESH_S` is served from its last `ok` result inside it (kb 10 s, log 10 s, sessions, sprint and querylog 30 s; the title still shows the seconds of the run that made it), the kb panel's counts are read again only when a file of a root changed (its name, time or size), the ops rows are read again only when a spool or sidecar file changed and 30 seconds have passed since the last read, and a panel that outlasted `--timeout` is waited for again at the next frame instead of started a second time. `--once` and `--json` print what they printed before.
- **A pipe, a file, or `NO_COLOR` set, gives plain frames:** no escape byte, one frame after another with a blank row between, unless `--ansi` asks for the escapes. `--once` is always one plain frame, with escapes only for `--ansi`.
- **Beside the session.** `kbmon.py --split` runs the live view as `kbmon.py --interval 60` in a new pane of the terminal the session is in, found from the environment in this order: tmux where `TMUX` is set (`tmux split-window -d -h -l 40%`, aimed at `TMUX_PANE`), WezTerm where `WEZTERM_PANE` is set (`wezterm cli split-pane --right --percent 40`, which aims at that pane), Windows Terminal where `WT_SESSION` is set (`wt -w 0 split-pane -V -s 0.4`); each starts in the clone's directory. Elsewhere, or when the splitting command is not found or fails, it prints the command to run in a second terminal and names `install_wezterm.py` for the optional WezTerm; Apple Terminal has no split command. `--dry-run` prints the command it would run and runs nothing. `--root`, `--panel`, `--store`, `--url` and `--key-file` are passed on to the pane's view. The exit code is 0 in every case, and the printed command is not passed through `redact.redact`, since it must run as printed. The 60-second interval is what keeps the pane's CPU low: the view idles between frames, so the first frame's reads are nearly all of its cost.
- **Windows.** `mon_view.enable_vt()` switches on the console's virtual terminal processing for standard output (`ctypes`, `SetConsoleMode`). It returns True off Windows and False where the console cannot take escapes (no console, a redirected output, an old console host); kbmon then writes plain frames one after another, with or without `--ansi`.

## The kbmon-pane mod

`.claude/skills/kbmon-pane` is a Claude Code mod (a plugin of function hooks, an early-access API): it loads in every session of the clone with no install and no settings change, once the workspace is trusted. It shows kbmon in a pane beside the chat and gives the agent only the receipt. It runs `python3 _tools/kbmon.py` from the session's working directory, so a session started in the clone's root is the one it serves.

- **Only an interactive session.** At `session.start` the mod reads `isInteractive`; false (a `-p` run, the SDK) and it registers and opens nothing and appends nothing.
- **The pane.** An interactive session registers `/kbmon` and opens the pane `kbmon`; `/kbmon` opens it again and refreshes it. Every 60 seconds a timer runs `kbmon.py --once` with `COLUMNS` set to the pane's `bodyColumns` and draws the text, each line cut at the edge. Python is found as `python3`, `python` or `py -3`, whichever gives output first, and the one that worked is tried first the next time; a run that gives none shows the reason in the pane.
- **No overlap.** The timer starts no run while the last is still going; it marks the pane stale instead, and a run that ended at another width than the pane now has is followed by one at the new width.
- **A resize** clips the drawn text at once; a second after the resize settles the mod runs kbmon again at the new width, or the next timer run does, whichever is first.
- **The receipt.** After a run whose alert rows differ from the last run's, the mod runs `kbmon.py --receipt`. When the fingerprint differs from the one the session holds, it appends the `line` as one user-role row (`$.session.append`), and shows it as a toast unless it is the first of the session. The first one comes at session start; a later one only when the alert set changes, and a reload of the mod appends none while the fingerprint stays. The pane's text is never given to the agent.
- **The notification.** After each run the mod reads the `needs you` row of the text. When that row changed since the last reading, or ends in an ellipsis (kbmon cuts a row at the pane's width), it runs `kbmon.py --status all` and takes its first line, the whole `needs you` line, and calls `$.ui.notify` with it. The session's first reading is the baseline and tells nothing; an unchanged line and `nothing` are never told. A person sees it only where `preferredNotifChannel` names a terminal channel. A call that rejects (another mod's hook denied it, the terminal write failed) or answers `isSent: false` is no error: the pane, the receipt and the next notification go on, and a change is told once whatever the call answered. A run of `--status all` that fails leaves the reading for the next refresh.

## The coord panel

`data` of `mon_coord.py`:

| key | holds |
|---|---|
| `source` | `local` (the store) or `url` (a `coord.py serve` server) |
| `claims` | per live claim, in key order: `key`, `holder`, `left_s` (whole seconds left of the lease), `budget_usd`, `spend_usd` (null for a claim with no budget) and `over_budget` |
| `events` | the newest 10 events, newest first: `seq`, `kind` and `fields` |
| `digest` | the lines of `coord.py digest`: the live intents and claims, with the progress state of an intent's items and its age |
| `asks` | the asks addressed to `operator` that no closing answer has ended, oldest first, 20 at most: `id`, `since` (UTC time of the ask) and `text` (the question after `redact.redact`, cut to 60 characters; read for the first three only, else empty); `asks_open` counts all of them |
| `settings` | the effective coordination settings (`kbsettings.explain` of the clone at `--root`, with the one `kb/NAME/settings.json` when exactly one root has one): per key such as `strategy.working`, `value` and `source` (`default`, or the settings file relative to the clone: `settings.json`, `kb/NAME/settings.json`); a settings file that cannot be read gives `settings_error` and an empty `settings` |
| `runs` | per item with a `run/<item>` value, in key order: `item`, `state` (a run state of `coord.RUN_STATES`) and `age_s` (whole seconds since the item's newest progress event, null with none), from `coord.py list` and every event `wait --since 0` returns |

- **Read through coord.py.** The panel runs `coord.py list`, `wait --since 0 --timeout 0` and `digest --key '*'` as three child processes at once, then `coord.py get` of the question of each of the first three open asks to the operator, so it opens no SQLite file and no key file itself. The lease tokens `list` and `digest` leave out are never in the data, and the key file's content is never read or printed by kbmon.
- **Where it reads.** With `--url` (and `--key-file`, which coord.py reads) from the server, else from the store `--store` names, else `KB_COORD_STORE`, else the store of the clone at `--root` (a workspace that installs the plugin has one of its own, so `--root WORKSPACE` shows that workspace's coord, sessions and sprint panels), found with `git rev-parse --git-common-dir` and, where git cannot run, from `ROOT/.git` (a directory, or a `gitdir:` file and that directory's `commondir`); a store that is not there is `absent` with the path it looked at.
- **Absent.** A local store file that is not there makes the panel `absent` with `{"reason": ...}` naming the store path, and is not created (coord.py's own commands would create it).
- **Timeout.** A server that cannot be reached, or whose three commands take over 30 seconds, makes the panel `timeout` with `{"reason": ...}`; one that is reached and gives no answer is `timeout` when `--timeout` passes, whichever is sooner. The children are killed when kbmon exits. Any other failure of a command (a key file others can read, a refused token) is `error` with coord.py's last line.
- **View.** A table of key, holder, seconds left, budget and spend, a row over budget starting `! `; at 100 columns or more the newest 5 events sit beside it from column 52 under `events` (`#410  claim     topic/winget  w2`), below 100 under it; then up to two intent lines of the digest under `intents`, `asks` with the count of open asks to the operator where there are any, and `settings` with one row of the keys a file sets (`strategy.working=after (settings.json)`), `all default` where none does.

## The sessions panel

`data` of `mon_sessions.py`:

| key | holds |
|---|---|
| `procs` | per process with a working directory in a checkout of the clone, in pid order (`backlog.py procs`' inventory): `pid`, `age_s`, `class` (`orphan`, `hook`, `detached` or `foreign`), `checkout`, `session` and `item` |
| `procs_unreadable` | the reason `backlog.py procs` gives when the host cannot list processes (on Windows, that PowerShell did not answer); left out otherwise |
| `procs_limit` | on Windows only, what the host cannot show (see Windows processes below); left out elsewhere |
| `sessions` | per live Claude Code session, oldest first, 30 at most: `label` (`s-` and six hex characters of the session id's SHA-256 like the coord panel's, never the raw id; null when nothing names the id), `role`, `item` and `item_title` (null unless the session works on exactly one item), `sprint` and `sprint_title`, `step`, `started` (UTC time of the process's start; null when the process table does not list it), `last_activity` (UTC time of the newest row of the session's own spool file; null without one), `spend_usd` (the spool file's usage rows priced as `backlog.py cost` prices them; null when no usage row names the session), `pid` and `checkout` |
| `worktrees` | per worktree of `git worktree list`: `path` and `branch` (null for a detached head) |
| `dispatch` | per dispatch run of this clone, from the claims ledger of its git dir (`bl_dispatch.record_worker`: a record with a `worker_pid` or a `worker_session`), live workers first, then by item, 20 at most: `item`, `pid`, `session` (the label `s-` and six hex characters, never the raw id; null before the session ended) and `alive` (the pid still runs; null where the host cannot tell or the record has no pid); an empty list where the ledger is not there or does not read |
| `stalled` | per claimed or ready item with a signal of `backlog.py stalled`: `item` and `signals`; left out where the root has no backlog items |
| `operator` | this clone's operator, from `kbwho.operator()`: `id` (null when no source gives one) and `role` |
| `intents` | per live session intent of the coord store (`coord.py digest`, newest first, 20 at most): `session`, `item` and `operator` (null for an intent posted without one), a session id as `s-` and six hex characters of its SHA-256 like the coord panel's, never the raw id; left out when the store is not there or does not answer |
| `overlaps` | per pair of live sessions (the intents of `intents`, a dispatching session's `backlog-claim` intent left out, each session's intents merged) whose items or touch paths meet (`coord.overlaps`: equal, a directory-style prefix or a glob), longest first, 20 at most: `a` and `b` (each `session` as its label, `operator` and `item`, the session's first), `files` (the paths of either that meet a path of the other, sorted), `strategy` (`undecided`, else the strategy of the newest `coordinate` event between an item of each, in either order) and `age_s` (seconds since the later of the two sessions' first intent event); left out with `intents` |
| `needs_you_after_min` | `announce.needs_you_after_min` of the clone at `--root` (`kbsettings.effective`, the workspace file then the kb root's, the default when the settings do not read), present with `overlaps` |

- **Checkout, never an absolute path.** `checkout` and a worktree's `path` are relative to the clone: `.` is the clone itself, a worktree under it is its path under it (`.claude/worktrees/agent-ST-xxxxxxxx`), one outside it is its directory name, with the parent directories that tell it from another outside worktree of the same name (`a/wt`, `b/wt`), and a process in a subdirectory adds it (`./_tools`).
- **Session.** A process whose command name is `claude` is a Claude Code session: `headless`, with `item` set to the id in the branch, when its checkout is a worktree on a `work/<id>` branch, else `interactive`. Any other process has null `session` and `item`. Worktrees are told apart by their path, not their directory name, so two that share a name keep separate rows, and a process in either keeps its own branch (the process's working directory places it when its checkout name is shared). The command line of a process is never read, but on Windows, where it places the process (Windows processes below), and is then matched and dropped.
- **Sessions.** One entry for each process whose command name is `claude` in a checkout of the clone, and for each dispatch record whose pid still runs but that the process table does not list (a worktree on its `work/<id>` branch places it; `started` is then null), never one for a command line or an environment: neither is read (on Windows the command line is matched against the checkout paths and dropped). A process gets its session id from, in this order, the dispatch record that names its pid (`worker_session`), the one session that made the claims of its checkout's ledger (`session` of a record that is a session id), the one coord intent of its item that is not a claim's (topic `backlog-claim`, a dispatching session's) and is not another process's, and the one session the coord hook left a state file for in its checkout (`_cache/coord_hook/<id>.json`, only the file name read) whose lease is live; an id binds to one process, the oldest of a checkout first, and a process nothing binds has a null `label` and no spend. The `item` of a worker is its dispatch record's, else its `work/<id>` branch's; of any other session the open (`todo` or `doing`) items of its ledger claims, else of its intents, the field null when they are not exactly one, and `sprint` the sprint they share.
- **Role.** The first row that fits, from the checkout's path and branch, the ledgers, the item files and the coord leases: `bare twin` (the checkout is `bare/agentN`), `benchmark agent` (`multi-<hash>/agentN`), `observer` (nothing names the session and a `remediate/` coord claim is live), `reviewer` (its item is a review story), `worker` (a dispatch record names the process, or its checkout is on a `work/<id>` branch), `sprint runner` (the ledger of its checkout holds a dispatch record), `planner` (its items are all epics or sprints), `interactive` (its checkout is a worktree of the clone) and else `unknown`. No documented field names a session's role; the table is this repository's own.
- **Step.** The step of a landing in progress (the newest `land.step` row of the ops rows without a later `land.end`) while one of the session's items, or for a sprint runner an item it dispatched, is in one; else `review` for a reviewer; `waiting` while an item has an open blocking gate or a sprint runner has a worker whose pid still runs; else `claim` while an item is `todo`, `work` while it is `doing`; null with no item. A host that cannot list processes still lists a dispatched worker whose pid runs. On Windows no pid is probed (`os.kill(pid, 0)` ends the process there), so a sprint runner's step reads without its workers and no unlisted worker is added.
- **Operator.** `operator` and each intent's `operator` are operator ids, never an email address: `kbwho.py` maps the login's email to an alias, and the coord hook posts that alias as the intent's `operator` field (a `coord.py serve` server replaces it with the name of the caller's key file). The panel reads the intents with one `coord.py digest` run on the same store or `--url` as the coord panel.
- **Dispatch.** The records are the ones `dispatch` writes when it starts a worker (`worker_pid`) and when the session exits (`worker_session`), so a run whose session has not ended has a pid and no session, and a worker that died shows `alive` false beside the live ones. Liveness is the pid's existence, not the process's name; a pid the host has reused reads as alive. The ledger is a file of this working tree's git dir that git never commits, so the list is this checkout's and never another clone's.
- **Stalled.** The signals are those of `backlog.py stalled`, read without the forge: the panel starts no network request, so `mr-dead` is never in `signals` and an item with only an unknown signal is left out.
- **Overlaps.** `overlaps` is built from the digest's live intents and the coord store's events (one `coord.py wait --since 0 --timeout 0`), no session id leaves the module but as its label. An overlap with `strategy` `undecided` whose `age_s` is at least `needs_you_after_min` minutes is an entry of the `needs you` line (`overlap ST-… (s-…) with ST-… (s-…), undecided for 12m`); a younger one, or one a `coordinate` event decided, is none, so it shows in the panel only.
- **Alert.** While `procs` lists a process of class `orphan`, the snapshot's `alerts` hold `{kind: "orphan", id: "sessions.orphan", message, since}`: the message counts the orphans and names the oldest one's pid and age, `since` is empty. A `detached` process (its parent gone, its own process group, a live child) raises none. The alert goes when no orphan is listed; the alert line (Layout) and the exit code 1 follow as for the delivery alert.
- **Unreadable processes.** A host that cannot list working directories (no `/proc` and no `lsof`) gives `procs` empty and `procs_unreadable`, the reason of `backlog.py procs`; the panel stays `ok`, so the operator, the intents, the worktrees and the stalled items still show, and the view's first process row reads `processes unreadable: REASON`.
- **Windows processes.** Windows exposes no working directory, so `bl_procs.windows_snapshot` reads the host's process table through PowerShell (`Get-CimInstance Win32_Process`: pid, parent, start, command name and command line as JSON; `powershell`, else `pwsh`) and lists a process when a checkout path of the clone appears in its command line (the longest path wins, case and slash direction ignored), its `checkout` that checkout and its command name without `.exe`. The command line is only matched against the checkout paths, never printed or kept. A process whose command line names no checkout is not listed, so an orphan that `backlog.py procs` tells by its working directory is not told here; `procs_limit` says so, with the count of processes that show no command line at all (another account's, unless run elevated), and the view's `limit` row prints it in place of `processes unreadable`. Without a PowerShell that answers, `procs_unreadable` and that row apply. `backlog.py procs` and `backlog.py selfcheck` still say the host cannot list processes by working directory.
- **View.** A table of pid, age, class, session, item and checkout, an orphan's row starting `! ` and orphans first (12 rows at most, then `+N more`); `worktrees` with `path  branch` joined by ` · `, those on a `work/` branch first (12 at most); then `dispatch` with `item  pid  session  alive|ended|unknown` joined by ` · ` (live runs first, 6 at most, then `+N more`); then a `! ` row for each stalled item with its id and signals. Above the table, a row with this clone's operator id and role, the live session intents as `session  item  operator` joined by ` · ` (6 at most, then `+N more`) and the `sessions` rows (8 at most, then `+N more`), each the `session_line` of its entry: `label  role  sprint  item title  step  up 1h00m  last 20m ago  $1.25`, at most 120 characters (fewer in a narrow view), the sprint's title cut to 20 characters and the item's to 40 or to the room the other fields leave, a field the entry does not know left out; the elapsed time and the last activity are taken at the snapshot's `taken` time, so a saved snapshot shows the same line; under the sessions, the `overlaps` rows, `s-… ST-… with s-… ST-… sharing PATHS, STRATEGY` (4 at most, then `+N more`).

## The sprint panel

`data` of `mon_sprint.py`:

| key | holds |
|---|---|
| `sprints` | per sprint of the backlog that is active or planned, active first, then approved, then planned, ids in order within a state: `id`, `state` (`active`; `approved`, a planned sprint whose start gate the operator approved and `backlog.py start` is left; `planned`), `title`, `items` (the count of its items for each status), `next` and `next_title`, `open` (up to 20 items not done or dropped, in the order `backlog.py next` offers them: `id`, `title`, `status`, `kind` (see History), `claimed` (the UTC time of the item's last claim commit on `origin/main`, or null) and `after` (the ids of the sprint's open items it depends on, directly or through another, or that come before it in that order with touches that meet its own, `bl_plan.touches_meet`, in that order)), `review_done` (the UTC time of the done commit of its review story, or null) and `waiting` |
| `source` | `origin/main`, or `checkout` where that ref cannot be read |
| `behind` | the commits `HEAD` is behind `origin/main`; null for `checkout` |
| `fast_forward` | `{can, why}` for the checkout the panel reads, null for `checkout`: `can` is false when `HEAD` holds commits `origin/main` lacks, or when tracked files with local changes (staged or not) are also changed by the commits `HEAD` is behind; `why` names each cause with the count of commits or files and up to three paths relative to the clone (`up to date` or `nothing in the way` where `can` is true) |
| `history` | how long items and sprint tails took, in minutes (see History): `kinds`, `all`, `tail` and `outliers` |
| `landings` | per landing in progress, newest first: `item`, `title`, `step` (the newest `land.step` row's step), `since` (the time of the landing's first `land.step` row) and `last` (the time of the newest) |

- **Read through backlog.py, from `origin/main`.** The item files are those of the local `origin/main` ref (`bl_view.items_at`; the panel fetches nothing, so the checkout may lag it by many commits, which `behind` counts), and where the ref cannot be read the checkout's own files, `source` `checkout`. The sprints and their items are `bl_base.Backlog`'s over them, `next` is the item `bl_view.ready` puts first (an active sprint only, else null) and `waiting` holds `{item, gate}` for each open blocking gate of the sprint (its start gate until it is answered) and of its items that are not done or dropped. A root with no backlog has an empty `sprints`. `review_done` is the time of the newest first-parent commit of `origin/main` whose subject starts `chore(backlog): done ID` for the sprint's review story, read by `mon_eta.lifecycle` at the first sprint with a finished review story.
- **History.** `mon_eta.py` reads the first-parent commits of `origin/main` whose subject starts `chore(backlog): claim ID`, `done ID`, `close SP-ID` or `start SP-ID` (the last only for the backtest) with one `git log` and the item files at the claim commits with one `git cat-file --batch`, and keeps the result in memory for the same `origin/main` commit (no file; `source` `checkout` has an empty history). An item's duration is the minutes from its last claim commit before its newest done commit to that done commit, and its kind comes from its item file at that claim commit: `review` (`review` true), `research` (`goal_research` true), `bug` (kind `bug`), `bench` (a touch names `kb/_self/reports/benchmarks.csv` and its goal says paid), `content` (no touch under `_tools/`, `.claude/`, `.claude-plugin/`, `.githooks/` or `otel/`), else `code`; an open item's `kind` is read the same way from its current file. The `tail` of a closed sprint is the minutes from the done commit of its review story to its close commit. Each kind keeps its last 30 durations; a kind of at least four drops each one above its p75 plus three times its p25-p75 spread and `outliers` counts them. `kinds` (a key for each kind with durations), `all` (the kinds pooled after that) and `tail` (its last 30) each hold `n`, `p25`, `median` and `p75`, one decimal, the inclusive quantiles of Python's `statistics` (a single duration is all three; none gives `n` 0 and null).
- **Estimate.** `mon_eta.estimate(row, history, now)` gives an active sprint's time left from its row, the `history` and the time the snapshot was taken (so a saved snapshot gives the same answer and a later refresh a new one): `low_min`, `high_min`, `confidence` and `basis`, or nothing where the history lacks a figure it needs. Each open item counts its kind's p25 toward the low end and its p75 toward the high end; a kind of fewer than four durations takes the pooled `all` figures and makes the confidence `low`. An item in progress counts each figure less the minutes since its claim, never below 5 (`FLOOR_MIN`), so a long item neither freezes nor inflates the estimate. The review story is added in full after the other items, which form chains along their `after` lists that run side by side on `WORKERS` of 4: the work takes the larger of the longest chain and the chains' sum divided by 4, for each end. The `tail` is added, less the minutes since `review_done` once the review is done (never below 5). The confidence is `high` when the fewest durations behind any figure used is at least 10, `medium` at least 4, else `low`; the basis names the items counted by kind with the durations behind each, and the tail's. `--status sprints --json` gives each sprint's `name` (its short name) and, for each active sprint, `eta_low_min`, `eta_high_min`, `confidence` and `basis` under `progress`, null where there is no estimate.
- **Backtest.** `kbmon.py --status sprints --backtest N` (`mon_eta.backtest`) replays `estimate` over the last N sprints closed on `origin/main` at 25, 50 and 75 percent of the time from each one's start commit to its close commit; a sprint is replayed only when another closed before its start, and one that none preceded is left out of the N. At a point the `history` holds the items done and the sprints closed at or before it, and the sprint's items, those whose item file at their claim commit names the sprint, are done (a done commit at or before the point), in progress (claimed at or before it, counted from that claim commit) or to do; an open item follows the open items it depends on and the earlier-claimed ones whose touches meet its own. A point's error is the distance from the middle of the range to the actual minutes left (to the close commit), and its relative error that distance over those minutes; a point inside the range is one whose actual minutes lie between `low_min` and `high_min`. It prints a line for each replayed sprint (`median absolute error`, `median relative error`, points inside the range of all) and `backtest: sprints=S points=P median absolute error=E min median relative error=R% inside the range=C%`, with `--json` an object of `schema`, `topic`, `sprints` and `summary`. It needs `--status sprints` and N of 1 or more, else it exits 2 naming `--status sprints`; it reads only the commits and item files of the ref and writes nothing.
- **Landings.** The ops rows are `bl_stall.ops_rows`' (this host's spool and the committed sidecars). An item is in progress while it is still open in the backlog (an item file of `origin/main` not `done` or `dropped`) and its newest `land.step` row has no later `land.end` row; rows of one millisecond keep their write order, the committed sidecars' in their files' order and the spool's in the order of its file. A landing that stopped without a `land.end` row (a killed process, or a row from before landing wrote one) stays listed while its item is open, and the status answer gives its age (`last step 5.2 days ago`); one of a done, dropped or unknown item is not listed.
- **View.** A row for each sprint, the one `mon_status.sprint_row` writes for `--status sprints` (one implementation, so the view and the status answer show the same row): its short name (`mon_status.short_name`: the title cut after a whole word to at most 40 characters, padded to 40), its state, items done of all (done and dropped count as done), the percentage and, for an active sprint, the ETA (the range `mon_eta.estimate` gives at the snapshot's taken time, from 180 minutes in hours; `no ETA yet` where there is no estimate, `no ETA: origin/main not readable` where the panel read the checkout's files; `mon_view` hands the panel the taken time, so a saved snapshot shows the same range and a later refresh a new one), `not started` for an approved sprint and `waits for start gate` for a planned one, at most 100 characters, with no id; under it up to two `waiting  ITEM/GATE` rows of its other open gates (12 sprints at most); then up to six `landing  ITEM  STEP  since TIME` rows, each state written, not coloured.

## The host panel

`data` of `mon_host.py`:

| key | holds |
|---|---|
| `load` | the 1, 5 and 15 minute load as three numbers, or `"unsupported"` on a host with no `os.getloadavg` (Windows) |
| `cores` | `os.cpu_count()`, or null |
| `suite_lock` | the whole-suite lock's live holder: `pid`, `clone` (`this` or `other`) and `started` (UTC time); null when none holds it |
| `main_lock` | the main lock's live holder: `pid`, `clone`, `started` and `step`; null when none holds it |
| `ceiling` | `max_ids`, `max_files` and `max_seconds` (this platform's, times the CI factor and the clone's profile factor: `busy` is 15) of `_tools/tests_ceiling.json`, with the clone's `profile` (`usual` or `busy`, `tests.read_profile`), against `ids` and `last_run_s` (the newest passing full `test.run` row that ran pytest, null before any) and `files` (the clone's `test_*.py`); `{"error": ...}` where `tests.read_ceiling` refuses the file |
| `disk` | the file system that holds the clone, from `shutil.disk_usage`: `free_bytes`, `total_bytes` and `free_pct` (one decimal); `{"error": ...}` where the call refuses the path |
| `groups` | the CPU consumers of one `ps -A -o pid=,pcpu=,args=` listing as `{kind, clone, cpu, procs}` in CPU order (`kind`: `kbmon`, `fseventsd`, `kb-tools`, `claude`, `tests` or `other`; `clone`: `this` or `other` for a script of a `_tools` directory given by an absolute path, else null, a relative path (`python3 _tools/kbmon.py`) included, which the listing cannot place without the process's working directory), or `"unsupported"` where the host has no `ps` (Windows); `cpu_basis` says what ps's percent is: `recent` (a decaying average, macOS) or `lifetime` (CPU time over the process's life, Linux) |

- **Read through the lockers' readers.** The two locks are the files `tests.py` (`kb-tests.lock`) and `kg_lock.py` (`kb-main.lock`) keep in the host lock directory (`KB_HOST_LOCK_DIR`, else `/tmp`); the panel reads them with `tests.read_lock`, `tests.parse_holder`, `tests.pid_alive` and `kg_lock.holder_step`, and the ceiling with `tests.read_ceiling`. It takes, clears and writes no lock, and the ceiling file is only read. A lock file whose pid no longer runs, or whose record cannot be read, is no holder.
- **`this` or `other`, never a path.** A holder's `clone` is `this` when it is the clone the panel reads (`--root`), else `other`; the path in the lock record is not printed.
- **Alert.** While `disk.free_pct` is under 10, the snapshot's `alerts` hold `{kind: "disk", id: "host.disk", message, since}`: the message gives the percentage and the free and total gigabytes, `since` is empty. The alert goes at 10 or more free; the alert line (Layout) and the exit code 1 follow as for the delivery alert.
- **Command lines stay in memory.** The panel matches each command line of the listing against fixed patterns (`kbmon.py`, `fseventsd`, pytest or `tests.py`, any other script in a `_tools` directory, `claude`) and keeps only the kind, the clone, the summed CPU and the count; no command line, argument or path is printed or kept in the snapshot. The sessions panel still never reads one.
- **Unsupported load.** A host with no `os.getloadavg` shows `load` as `unsupported`; the locks and the ceiling are shown as on any host.
- **View.** `load` (`1.00 · 2.00 · 3.00 · 8 cores`), `suite` and `main` (`pid · this clone · since YYYY-MM-DD HH:MMZ`, the main lock also `step`, or `none`), then the ceiling: `ids`, `files` and `last run`, each as `{used}/{limit} [|||||||...] {pct}%` with 10 cells (the percentage floored to a cell); `last run` is named `last run (busy)` on a clone with the busy profile. The three share one row where the joined row fits the width (about 108 columns for typical numbers), else three aligned rows. A bar of 80 to 99% starts its row with `! ` (yellow) and one of 100% or more with `!!` (red), the shared row by its worst bar; a row under 80% has no colour, since the view colours whole rows.

## The querylog panel

`data` of `mon_querylog.py`:

| key | holds |
|---|---|
| `mode`, `disabled` | the query log's mode in the config file (`auto`, `local` or `off`) and whether the `DISABLED` marker is there |
| `spool` | the rows waiting in the local spool: `files`, `rows`, `by_kind` (rows per surface, the surfaces that have a row) and `unreadable` (rows distill cannot read) |
| `undelivered`, `undelivered_runs`, `undelivered_since`, `delivery_ref` | the entries in the local store's run files that `origin/main` does not hold yet (0 in mode `local`, where an entry is delivered once distill wrote it), the run files holding them, the time of the oldest such run id or null, and false when the delivery ref cannot be read (then every run file of the store counts) |
| `last_distill` | the outcome of the last `distill:` line of `distill.log` (`written` with `entries`, `dropped` and `waiting`, `nothing`, `off`, `locked` or `failed`), or null |
| `last_delivery` | `{outcome, why, when}` of the last terminal `apply --push:` line (`pushed`, `nothing`, `conflict`, `waiting`, `locked`, `refused`, `fetch-failed`), or null; `why` is the failed gate and its first error line that `backlog.py land` reads for a push that delivered nothing, else empty |
| `last_pushed` | `{commit, when}` of the newest query log commit on `origin/main` (a first-parent commit with a `KB-Auto` trailer holding `querylog`), or null |
| `usage_today` | `{rows, tokens, usd, unpriced, by_model, by_session, by_sprint}`: the UTC day's usage rows (Usage, In the query log), their tokens (uncached input, cache writes, cache reads and output) and their cost at `backlog.py cost`'s prices; `unpriced` names a model the price table lacks. The three `by_` maps are {name: USD}, largest first, each group priced as the day is: the model, the spool session that wrote the prompt (its `s-` label; `distilled` for usage only a distilled sidecar line stands for, whose spool session is gone) and the sprint of the item the prompt's work window names (`ql_distill.work_windows`; `none` outside a window or when its windows span several sprints) |

- **Read through the query log's readers.** The counts come from the structured readers beside the text ones in `ql_report.py` (`spool_state`, `undelivered`, `last_outcomes`, `standing_apply`, `last_pushed`, `usage_today`), which `querylog.py show --spool` shares (`spool_scan`); the panel parses none of the lines `show` and `status` print. It reads the query log home of this copy of the tools (`ql_base.places`: the clone's `_cache/querylog`, or the plugin's data directory), whatever `--root` names, and writes nothing; the delivery ref is read with `git ls-tree` and `git log` on the local ref, with no fetch.
- **Counts and kinds only.** The spool keeps prompts and answers as typed; the panel carries no question, prompt or reply text, no session id and no row id: rows are counted by surface, runs by their id's time, commits by hash.
- **When.** `distill.log` carries no time per line, so `when` of an outcome is the log's last write, set only on the outcome that stands last in the log and null on the other.
- **Alert.** While the last `apply --push:` outcome that tried a push is `refused`, whatever lines follow it of runs that tried none (another run held the lock, or the last automatic commit's CI was awaited; `ql_report.standing_apply`) or of the distill (a failed gate, a rejected push, a conflict or a worktree left behind; the `DISABLED` marker a push refused for want of rights writes is the same outcome), the snapshot's `alerts` hold `{kind: "delivery", id: "querylog.delivery", message, since}`: the message names the failed gate and its first error line, or the line that stopped the run (a push refused for want of rights has no gate), `since` is the time (UTC, `YYYY-MM-DD HH:MM`) of the oldest run file the delivery ref lacks, which a refusal keeps undelivered and so does not move while it stands, else the log's last write. A fetch or connection failure (`fetch-failed`) is the `! ` row only, no alert. A later push that delivered, or nothing to push, makes the outcome `pushed` or `nothing` and the alert goes. The alert line (Layout) and the exit code 1 follow from it on `--once`, every live frame and `--json`; a snapshot saved with `--json` shown with `--from-snapshot` is judged again from its panels.
- **View.** Four rows: `spool` (rows in files, then the four surfaces with most rows and `+N more`), `delivery` (the undelivered count, the last pushed commit and time, the last apply outcome), `distill` (the outcome with its counts, the mode, `DISABLED` when the marker is there) and `today` (rows, tokens and dollars, with the model that has no price). A refused push replaces the delivery row with `!!delivery  REFUSED <gate and first error line> · since <oldest undelivered run> · undelivered N`; a push whose fetch failed, or an undelivered entry with no readable delivery ref, makes it a `! ` row.

| `rows` | each leftover `backlog.py tidy` lists, as tidy's `--json` rows: `class` (`worktree`, `branch`, `sandbox` or `scratch`), `verdict` (`remove` or `keep`), `reason`, `bytes`, the `path` or the `branch`, the `item` when a record names one and `approximate` where the walk that measured the bytes was cut |

The first line starts `! ` while the disk is under pressure.

## The log panel

`data` of `mon_log.py`:

| key | holds |
|---|---|
| `events` | the newest rows of the three sources, oldest first: `ts` (UTC time, empty when unknown), `source` (`coord`, `ops` or `delivery`), `event`, `subject`, `fields` (key to text) and `warn` |
| `problems` | one line for each source that could not be read, `coord unavailable: ...` |

- **Sources.** `coord` is every event `coord.py wait --since 0 --timeout 0` gives, from the local store or the `--url` server as the coord panel connects (a local store that is not there gives no coord row); `ops` is the `land.step`, `land.end`, `done.refused` and `test.run` rows of `bl_stall.ops_rows`, rows of one millisecond in the spool's order; `delivery` is the query log's last apply outcome (`ql_report.last_outcomes`), timed by the distill log's last write when it stands last in the log and untimed (`--:--:--`, sorted first) when it does not. A source that fails adds a `problems` row and the others still show; the panel writes nothing.
- **Subject and fields.** The subject is the first of `key`, `item`, `topic`, `touch`, `path`, `fact` and `session` (an ops row: `item`, `sprint` or `mode`; a delivery row: the outcome), else `-`. A field is kept only when its value is a number or a word of letters, digits and `. _ / : @ -` (a list of them joined by `,`) that `redact.redact` leaves as it is: no free text of an event reaches the view. The coord fields start with `holder`, `operator` and `session`; an ops row's follow the order of its event's keys. A session id in a coord field or key shows as its label. A `coordinate` event (the strategy a session chose about another item, posted by `kbask.py coordinate`) is one row, `coordinate` with the chooser's item as its subject and the fields `item`, `other`, `strategy`, `touch`, `session` (as its label) and `operator`; `--events` names it `coord.coordinate`.
- **View.** Under the title `log  ok  S.Ss`, one row for each event at column 2: `HH:MM:SS source event subject key=value ...`, the time in UTC, the source padded to 8. A `done.refused` row, a delivery whose apply outcome is `refused` or `fetch-failed`, and a `problems` row start with `! ` (yellow). The log is the last panel and takes the rows the terminal has left (three at least); the layout keeps its newest rows, the bottom ones, and drops the oldest from the top, a `problems` row first.

## Coord, asks and remediation

- **The coord.py store:** its commands, claims, events, `serve`, the coord hook and the `coord_` MCP tools are in `kb/_self/coordination.md`; this doc has the coord panel and the log panel that read them.
- **Asks and remediation:** `kbask.py` (`ask`, `answer`, `remediate`, `summary`, `cleanup`) and the `kb-observer` sessions are in `kb/_self/coordination.md`; kbmon only reads asks and answers, and the log panel shows them as coord events.

## The kbmon.py command

Commands: `python3 _tools/kbmon.py [--json | --once | --metrics | --receipt | --events | --status [TOPIC] [--detail] [--backtest N] | --split [--dry-run]] [--since CURSOR] [--panel NAME] [--timeout S] [--root DIR] [--ansi] [--interval S] [--count N] [--store PATH] [--url URL] [--key-file PATH] [--from-snapshot FILE]`

- One snapshot of the kb, coord, sessions, query log, host, sprint, cleanup, bench and log as panels (`kb/_self/monitoring.md`): `--json` prints one JSON object of schema 1 with each panel's state (`ok`, `timeout`, `error`, `absent`, `unsupported`), seconds and data, `--once` the same panels as plain text with no escape byte, `--metrics` the snapshot as one JSON object of metric points (`kbmon.<panel>.<measure>`, a unit, kind `gauge` or `sum`, a number, attributes of numbers, flags and identifiers `redact.redact` leaves as they are, never a claim's holder), `--receipt` one JSON object of `line` and `fingerprint` for an agent, from the alerts of the querylog, sessions and host panels (or of the panels `--panel` names): the line is at most 200 characters, unchanged by `redact.redact`, names up to two alert messages, how many more there are and `python3 _tools/kbmon.py --once --panel NAME` for the state on ask, and the fingerprint moves only when the set of alert kinds and ids does; it exits 0 with or without an alert, `--status [TOPIC]` a short plain-words answer (at most 25 lines, every line through `redact.redact` and with no absolute path) for TOPIC (`sessions`, `cost`, `querylog`, `coord`, `sprints`, `load` or `all`, the default) from one snapshot of the panels the topic needs (`mon_status.py`; `all` starts with the `needs you` line the text view prints under its header; `sprints` reads the sprint and host panels: one row for each sprint, the active one first (a short name of at most 40 characters, its state, done of all, the percentage and the ETA, at most 100 characters; `--detail` prints the full lines instead, the items left each by its short title), the host load, how many commits the checkout is behind `origin/main`, why it cannot fast-forward when it cannot (`fast_forward` of the sprint panel) and an ETA range with its confidence word and basis from `mon_eta.estimate` (per-kind p25 to p75 of the claim-to-done history, chains side by side, the review and the tail added; `--json` facts `eta_low_min`, `eta_high_min`, `confidence` and `basis`); `--json` makes it an object of `schema`, `topic`, `taken`, `lines` and `facts` (the `load` topic also `groups` of `kind`, `clone`, `cpu`, `procs`, `cause` and `remedy`, the CPU consumers in CPU order); a claim's holder is never named; it takes no `--panel`, calls no model, writes no file and exits 0 also with an alert; `--status sprints --backtest N` (N of 1 or more; any other use of `--backtest` exits 2) replays `mon_eta.estimate` over the last N sprints closed on `origin/main` and prints a line for each and `backtest: sprints=S points=P median absolute error=E min median relative error=R% inside the range=C%`, see `kb/_self/monitoring.md`), `--events` one JSON object of a cursor, events (coord events, `done.refused` rows and the query log's apply outcome) and spans (each landing with a child span per `land.step`, each `agent.run`, each `test.run` and each delivery whose time the log gives) newer than the cursor `--since` was given (the cursor is the caller's to keep; times in Unix nanoseconds, attributes of numbers, flags and identifiers `redact.redact` leaves as they are), none of them with `--panel` or `--from-snapshot`, neither a live text view every `--interval` seconds (1 to 300, default 5; `--count` frames, 1 or more, default until interrupted) that is redrawn in place with ANSI escapes on a terminal or with `--ansi` and written as plain frames on a pipe, under `NO_COLOR` or where a Windows console cannot take escapes, and on a terminal redrawn again from the last snapshot, without reading the panels, as soon as the window is resized (`SIGWINCH`, on Windows the size read 4 times a second), the view idling between frames and serving a slow panel's last result for its `REFRESH_S` seconds.
- `--split` opens the live view `kbmon.py --interval 60` in a pane beside the session (`tmux split-window` where `TMUX` is set, `wezterm cli split-pane` where `WEZTERM_PANE` is set, Windows Terminal `wt split-pane` where `WT_SESSION` is set) and elsewhere prints the command to run in a second terminal and names `install_wezterm.py`, `--dry-run` printing the command it would run, exit 0 in every case; each panel is `mon_<name>.py` and runs in a daemon thread bounded by `--timeout` seconds (default 10), so a slow source is shown as `timeout` while the snapshot returns, and a panel with no module is `absent`; the coord panel gives each live claim with its holder (a session id as `s-` and six hex characters of its SHA-256), seconds left and budget beside spend, the newest events with their sequence numbers and the live intent digest, read through `coord.py list`, `wait` and `digest` from the local store (`--store`, `KB_COORD_STORE` or the default of the clone at `--root`; a store that is not there is `absent` and is not created) or from a `coord.py serve` URL with `--url` and `--key-file` (never printed; an unreachable or silent server is `timeout`); the sessions panel gives the processes working in a checkout of the clone (pid, age, class and checkout relative to it, from `backlog.py procs`), each Claude Code process as headless with its item in a worker worktree on a `work/<id>` branch and else interactive, each live Claude Code session as a `sessions` entry (label, role, item and sprint with their titles, step, start, last activity and spend, never a command line or an environment), the worktrees with their branches, the dispatch runs of the clone's claims ledger (item, worker pid, worker session label and whether the pid still runs) and the items `backlog.py stalled` flags, read without the forge, this clone's operator id and role (`kbwho.operator()`) and the operator id of each live session intent of the coord store (never an email address), `procs_unreadable` with the reason where the host cannot list working directories, `procs_limit` on Windows, which places a process by the checkout path in its command line (matched, never printed or kept), and the alert `sessions.orphan` (kind `orphan`) while an orphan process is listed; the host panel gives the 1, 5 and 15 minute load with the core count (`unsupported` where the host has no `os.getloadavg`), the live holders of the whole-suite lock and of the main lock (pid, `this` or `other` clone, start, and the main lock's step; never a path), read through the readers of `tests.py` and `kg_lock.py`, and the suite's ids, files and last full-run seconds against the numbers of `_tools/tests_ceiling.json`, the CPU of one `ps -A -o pid=,pcpu=,args=` listing grouped by kind (`kbmon`, `fseventsd`, `kb-tools`, `claude`, `tests`, `other`) and clone (`this` or `other` for a script under an absolute path, else none) with the command lines matched in memory and never printed or kept (`unsupported` where there is no `ps`), and the free and total bytes and the free percentage of the clone's file system, the alert `host.disk` (kind `disk`) while under 10% is free.
- The sprint panel gives every active, approved or planned sprint with its items' counts by status, its next item, its open items (each with its kind, the time of its last claim commit and the open items it follows) and its waiting gates, read through `bl_base.Backlog` and `bl_view.ready` from the item files of the local `origin/main` ref (`bl_view.items_at`, no fetch; the commits the checkout is behind it and the time of its review story's done commit ride along, with the per-kind claim-to-done history and the review-to-close tail of `mon_eta.py`; the text view writes an active sprint's `ETA LOW-HIGH min` from `mon_eta.estimate` at the snapshot's taken time), and each landing in progress (an item still open in the backlog whose newest `land.step` ops row has no later `land.end`) with its last step; the kb panel gives the roots' articles and facts by tag as `rag.py audit` counts them, the open gaps and conflicts, the newest refresh and census dates, the last eval outcome recorded at a landing (the alert `kb.eval`, kind `eval`, while it failed) and the pack index age; the querylog panel gives the spool's waiting rows by kind, the local store's entries `origin/main` does not hold yet, the last distill and apply outcome (a refused push as a `!!` row and as the alert `querylog.delivery`, which makes kbmon exit 1 until a later push delivers) and the day's usage rows with their tokens and cost in USD, read through the structured readers of `ql_report.py` and carrying no question, prompt or reply text; the cleanup panel gives every leftover `backlog.py tidy` lists (`bl_selfcheck.leftovers`, read through `bl_clean.safe_to_remove`) with its class, verdict, reason and bytes and a count of each class, the bytes of all the `remove` rows walked within one shared budget so the panel stays inside its timeout, read from the local coord store (`--store` or `KB_COORD_STORE`; `--url` is `unsupported`) and removing nothing; the bench panel gives a paid benchmark run's progress, spend against its cap and sandbox disk (below, "The bench panel"); the log panel gives the newest coord events, `land.step`, `land.end`, `done.refused` and `test.run` ops rows and the last apply outcome of the query log, oldest first, one per line as time, source, event, subject and the fields whose values are numbers or ids `redact.redact` leaves as they are (a `done.refused` row or a failed delivery behind `! `); a run builds no index, runs no eval and writes no file; every printed string passes `redact.redact`, a snapshot saved with `--json` and shown with `--from-snapshot` too; exit 0 shown (`--receipt` also with an alert), 1 shown with an alert, 2 a bad argument or an unreadable snapshot [CODE _tools/kbmon.py#main]
