# Plugin: layout rules, installing it elsewhere, a team's own roots

The repository root is a Claude Code plugin marketplace (`.claude-plugin/marketplace.json`) with two plugins that read the kb and write nothing to it (the writes are `kb_feedback`'s append to the local query log spool and the opt-in `coord_*` tools' claims and events in the coord store, which is no kb file). Sections 1-2 are the rules for changing them; sections 3-7 are the runbook an agent follows to set the kb up in another project (a person only asks for it).

## 1. What each plugin ships

**`it-ops-kb`** (the repository root, `.claude-plugin/plugin.json`):
- **the `kb` MCP server** (`_tools/kb_mcp.py`, stdlib Python over stdio). Every lookup tool's description starts "Documentation facts from it-ops-kb (not live device or directory data)", so a project that also has live MECM/AD tools keeps them apart. Tools:
  - `kb_pack`: the evidence pack (coverage verdict, fact lines with `path:line`, source urls, and a last line `pack: P-<8 hex>`, its handle); `questions` batches up to 6 parts in one call; the operator's decisions of the served roots come beside the facts (labelled `decided` or `proposed (not confirmed)`; `include_invalidated: true` adds the invalidated, with why; `root="_self"` serves the clone's rule docs, and a server limited to named roots refuses it), and `kb_show` lists those tied to the lines it shows; the active LOG rows (observed signal, never coverage) of the matched articles follow under `observed signal (LOG, not a fact):`, in `kb_show` and `kb_audit` too, and so does a `flagged (feedback, not a fact)` line for each printed fact line that a committed feedback report calls wrong or stale (`kb_audit` counts them in a `flags` column). `revalidate: true` (the team's own server only) asks the cited sources of the printed lines now, within a time budget, and marks each line current, moved (with the new passage), not found or source-dated only; a source it could not ask keeps its offline stamp, and the pack says so. Left out, it asks only the cited sources past their freshness lifetime (the days a source's facts count as fresh after a check, estimated from its own change history; `kb/_self/tools.md`, "Freshness lifetime"), whose footer line carries a `[stale: ...]` stamp; `revalidate: false` or `KB_NO_REVALIDATE=1` in the server's environment asks none. It is always loaded (`anthropic/alwaysLoad`), so the first lookup needs no tool-search round trip.
  - `kb_facts`, `kb_audit`, `kb_search`, `kb_show`, `kb_source`, `kb_status` (the copy's commit and date, the latest census, and how many commits it is behind the marketplace clone or upstream branch it follows, as of the last fetch). When the copy is behind, every `kb_pack` opens with a `kb copy: N commits behind ...` line naming the update command, so a model tells the user without calling `kb_status`.
  - `kb_feedback` (the team's own server only; absent under `--roots` and from `kb_http.py`): an agent's report on one lookup, `pack` (the `pack:` handle) or `question`, `outcome` (answered, partly, missed, misled), up to 10 `lines`, `best`, `source_url`, `claim` and `tool_issue`, in closed fields. It is the one tool of the kb with `readOnlyHint` false (the `coord_*` tools below write to the coord store): it appends one `feedback` row to the local query log spool (`kb/_self/querylog.md`, Surfaces) and writes nothing else, and the same report again records nothing. A weak or none `kb_pack` prints the call ready on a `feedback:` line where the tool is served, a good one none, and a server without the tool prints none; the server's instructions carry one clause for it.
  - `coord_claim`, `coord_renew`, `coord_release`, `coord_post`, `coord_get`, `coord_put`, `coord_digest`, `coord_wait`, `coord_dedup` (the team's own server only, unless it is started with the environment variable `KB_COORD_TOOLS` set to `0`, since they write to the coord store: with it `0` `tools/list` names none and a `tools/call` of one is an unknown tool; absent under `--roots` and from `kb_http.py`): the `coord.py` commands of those names on the local coord store, or on the `coord.py serve` address `KB_COORD_URL` names with the key file `KB_COORD_KEY_FILE` (`kb/_self/coordination.md` describes the store, the commands and these tools; `kb/_self/tools.md`). Where served they come after `kb_docs` (the last of the read-only command tools `kb_monitor_status`, `kb_settings`, `kb_backlog`, `kb_querylog` and `kb_docs`, which follow `kb_feedback`) and before `kb_backlog_write` and the live-docs tools, in a fixed order, so the tool list does not change between sessions, and none is always loaded, so a client defers them behind its tool search. A renew or release needs the token `coord_claim` returned. `coord_get` (`readOnlyHint` true) reads the text an ask's or answer's `ref` names, and `coord_put` (`readOnlyHint` false, `destructiveHint` false) writes it, only under `ask/ID` or `answer/ID`, redacted and at most 8000 characters.
  - `kb_settings` (the team's own server only; absent under `--roots` and from `kb_http.py`): how coordination is set up in the host project (`CLAUDE_PROJECT_DIR`, else the working directory), the text of `kbsettings.py explain`: `key` (one setting such as `strategy.working`; all when left out) and `kb_root` (a plain directory name), answered with each setting's value, its source (the settings file that set it as a path relative to the workspace root, or `default`), its meaning and the `kb/_self/coordination.md` section and the key's bullet that state it, with no line number (`kb/_self/coordination.md`, Settings, key by key). `readOnlyHint` true; it reads the settings files and the table of `kbsettings.py` and takes no model call; a plugin workspace gets its own `settings.json` read. It is deferred like every kb tool but `kb_pack`, and listed right after `kb_monitor_status`.
  - `kb_monitor_status` (the team's own server only; absent under `--roots` and from `kb_http.py`): the status of this clone's monitored work for any agent, `topic` `sessions`, `cost`, `querylog`, `coord`, `sprints`, `load` or `all` (the default), as the lines of `kbmon.py --status TOPIC --json` (at most 25, `kb/_self/monitoring.md`, The status answer), or, with `panel` (one of kbmon's panel names, else refused naming them), the JSON `kbmon.py --json --panel NAME` prints, through `redact.redact` and with no 25-line limit (an alert in it does not make the call fail). `readOnlyHint` true; it reads local files and the coord store, takes no model call, and each panel is bound by kbmon's `--timeout`. It is deferred like every kb tool but `kb_pack`.
  - `kb_backlog` (the team's own server only; absent under `--roots` and from `kb_http.py`): the backlog's read-only commands as one tool, `command` one of `show`, `list`, `next`, `horizon`, `stalled`, `cost`, `ops`, `selectors`, `held`, `referrers`, `find`, `similar`, `tree`, `config`, `landings`, `runs`, `procs`, `check`, `report` or `usage` and `args` the list of that command's own arguments (`['ST-xxxxxxxx']`, `['--kind', 'sprint']`), answering the text `backlog.py` prints for it, run through the redaction rules pass. `usage` with no `args` answers every `backlog.py` command with a line each; with a command (and its sub-command: `['gate', 'add']`) it answers the argument list `--help` prints for it, for a command the tool refuses too, so a session reads a verb's arguments without a shell run; the parser renders it, no handler runs and nothing is written. Any other command, `precheck`, `host-check`, `claim` and `done` among them, and `runs --reconcile` (also by an abbreviation of the option), is refused as a tool error, which is what keeps the tool `readOnlyHint` true; the command line stays the way to those. Any command ends the text with `(exit 1)` when it exits 1 with output (a stray found, no hit, a `runs` drift, a `next` with nothing ready, an `ops` or `landings` that cannot read the log, a refusal that names what is missing), as `kb_docs` does, so a session reads it whole; an exit 2 (a usage error) and an exit 1 with no output come back as a tool error cut to its last 2000 characters.
  - `kb_querylog` and `kb_docs` (the team's own server only, as `kb_backlog`): the same kind of tool for the query log and the kb's own docs. `kb_querylog` takes `digest`, `status` or `show` and answers what `querylog.py` prints; `kb_docs` takes `stale`, `section`, `map`, `check` (`check.py`) or `eval` (`rag.py eval`) and answers what `selfdoc.py`, `check.py` or `rag.py` print, with `(exit 1)` last when the command found something (stale docs, a failed check or eval row); any other exit is a tool error. Each command has a closed list of options (`digest --week`, `show --run`/`--entry`/`--findings`/`--usage`/`--spool` with their filters, `stale --since`/`--work`, `check --root`, `eval --root`/`--file`/`--min`/`--all`/`--free`): another option, an abbreviation of one, a value that starts with `-` and any command outside the list, `querylog.py close` and `eval --write-shares` among them, is refused as a tool error, which keeps both tools `readOnlyHint` true. Output past 60,000 characters is cut with a note that says so.
  - `kb_tools` (the team's own server only, as `kb_backlog`): which of the kb's tools, skills, agents and MCP tools answers a need, the lines `kbtools.py [NEED]` prints: `need` (optional; in plain words, the whole catalog when left out), answered through the redaction with one line for each entry, its command and what it answers; no model is called. `readOnlyHint` true, an argument other than `need` refused as a tool error; listed right after `kb_docs` [CODE _tools/kb_mcp.py#kb_tools].
  - `kb_topics_for`: the kb topics that code touches (MSAL classes, AdminService routes, Negotiate/SPN, LDAP libraries, Graph scopes, ...), from `kb/public/_retrieval/signals.csv`.
  - `kb_backlog_write` (the team's own server only, and only when it is started with the environment variable `KB_BACKLOG_WRITE_TOOLS` set to `1`: with it unset `tools/list` names none and a `tools/call` of it is an unknown tool; absent under `--roots` and from `kb_http.py`; `readOnlyHint` false, `destructiveHint` false): `command` one of `claim`, `release` or `answer` and `args` that command's own arguments (`['ST-xxxxxxxx', '--by', 'NAME']`, `['ST-xxxxxxxx', 'GATE', '--answer', 'TEXT', '--provisional']`), run as a `backlog.py` child with `CLAUDECODE=1` set whatever the server's own environment holds, so the command sees an agent session and every gate and authority rule of the command line holds, a ceiling-class gate's terminal-only rule included (`answer --by operator` on one exits 2 and writes nothing). Any other command is a tool error. A call whose command line, written `python3 _tools/backlog.py COMMAND ARGS`, a `Bash(...)` deny rule of the clone's `.claude/settings.json` or `.claude/settings.local.json` matches (`*` for any text; a trailing ` *` also matches the bare command) is refused before the command runs, as is every call while one of those files is there and cannot be read; a deny rule in another spelling is not matched. A refusal of the command comes back as a tool error holding its message. Where served it comes after the `coord_*` tools and before the live-docs tools, and none of it is always loaded. The setting only lists the tool: it changes no gate class and no deny rule (`kb/_self/backlog.md`, Item commands).
  - `docs_search`, `docs_fetch`: the live docs servers of `it-ops-kb-docs` called over HTTP by the server itself, each answer kept 7 days in `${CLAUDE_PLUGIN_DATA}/live-docs`, so a repeated search costs no call and no output; they reach the network (`openWorldHint`), are labelled "live docs, not in the kb", and are absent under `--roots` and with `KB_LIVE_DOCS=0` (`kb/_self/tools.md`).
  - `response_format`: `kb_facts`, `kb_audit` and `kb_search` answer `concise` by default (no url footer), `kb_pack` `detailed`.
- **`/it-ops-kb:kb-lookup`**, which Claude may also invoke on its own. A single fact is one `kb_pack` call in the session that asked.
- **the `it-ops-kb:kb-lookup` agent**, for long research whose output would fill the caller's context: kb tools only, Haiku, low effort, no `CLAUDE.md`, the lookup procedure preloaded (4.0k tokens of startup context, measured).
- **`/it-ops-kb:kb-review-workspace [paths or focus]`**, started by hand. It runs in the `it-ops-kb:kb-reviewer` agent (Sonnet at `effort: low`, `Read`, `Grep`, `Glob`, `LSP` and the kb tools, the project's `CLAUDE.md` loaded; it uses `LSP` for definitions and references when a code intelligence plugin makes it active, else `Grep`), maps the project's code to kb topics with `kb_topics_for`, and reports findings in chat, each with the project's `path:line` and the kb's `path:line`, tag and source url. It writes nothing. At `low` it named all five planted problems of the `host-lookups` scenario, as at `medium` (one run each, 2026-10-09; `kb/_self/reports/benchmarks.md`, "Plugin in a host project").
- **`/it-ops-kb:kb-gap <question>`**, started by hand when the kb did not answer (`none`, `weak`, or facts that missed the point). It runs `kb_status`, `kb_pack` and `kb_audit` and prints an issue text to paste into the kb's tracker: the question, the kb version, the verdict, the nearest articles with `path:line`, what was missing and whether a gap is already logged. It replaces the organisation's names and ids with the kb's placeholders, and writes, sends and posts nothing.
- **`/it-ops-kb:sprint`, `/it-ops-kb:item` and `/it-ops-kb:backlog`, and the `it-ops-kb:kb-worker` agent** (`skills/sprint`, `skills/item`, `skills/backlog` and `agents/worker.md` at the plugin root, listed in `plugin.json`): the kb's own sprint, item and backlog skills and worker role file, for a project with a `backlog.json` at its root. Every `backlog.py` command in their text is `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py`, run against the host project's backlog and item directory, and their text names no path of the kb's own tree: a step only the kb has (the rule packs of `kb_root`, the docs `docs_map` maps, the landing's `land_stale`, `land_eval` and `land_lint`, the code lane of `lane_module`) runs when the project's `backlog.json` names it and is skipped, said so, when it does not; the landing's push is the project's own, the argv of `land_push` (`git push origin HEAD:main` in a host project with no gate script; the kb's `backlog.json` names `kbgit.py sync --push`, and a project that names none stops `land` at the push step), and an empty `lane_module`, the default, lands every commit as content. A skill's name is its directory's (their frontmatter has no `name`), so a link under another name serves the same file; the agent's name is `kb-worker`, whatever its file's. The kb's own `.claude/skills/kb-sprint/SKILL.md`, `.claude/skills/kb-item/SKILL.md`, `.claude/skills/kb-backlog/SKILL.md` and `.claude/agents/kb-worker.md` are such links, relative symlinks to those four files, so one set of the text exists and a clone, a worker's worktree or a session without the plugin installed runs its sprint under the `kb-*` names; a change to the text goes to the plugin's file, never the link. `${CLAUDE_PLUGIN_ROOT}` is substituted in a plugin skill's or agent's Markdown body, not in the environment of a Bash command, so a headless worker reads the role file by the plugin's full path that its brief names (the project's own `.claude/agents/kb-worker.md` when it has one) and writes the directory where the file shows the variable (`kb/_self/backlog.md`, Running a sprint). They are model-invocable, so their descriptions are listed in every session of a host that installs the plugin (`kb/_self/token-efficiency.md`).
- **the backlog's SessionStart hooks, opt-in** (`backlog.py horizon --hook --opt-in`, synchronous with `matcher` `startup|resume|compact|fork` and a short `timeout`, and `backlog.py intake --file --hook --opt-in`, async with `timeout` 60; the same launcher): each does nothing (prints nothing, files nothing, exit 0) unless the host project's `backlog.json` names it in its `hooks` setting, a list of `horizon` and `intake` that is `[]` by default; any other value is refused naming `hooks` (`backlog.py config`, exit 2), and the hook keeps its default meanwhile. `plugin.json`'s description names the key. The kb's own `.claude/settings.json` runs both commands without `--opt-in`, so its `backlog.json` leaves `hooks` out and a clone that also installs the plugin runs each once (`kb/_self/tools.md`, the `horizon --hook` and `intake` rows).
- **the coordination hook, opt-in** (`.claude/hooks/coord_hook.py --opt-in`, through the same launcher, `timeout` 10, on `SessionStart`, `SessionEnd`, `PermissionRequest`, `Notification` for the types that wait on the person, `UserPromptExpansion` for `kb-research` and `PreToolUse` for Bash, Skill and Edit or Write): it does nothing unless the host project's `backlog.json` names `coord` in `hooks`, which then also accepts `coord`, and which the plugin's sprint skill adds at the first run, with the operator's coordination settings, by `kbsettings.py init`; the project's sessions then take their presence lease and announce their items in a coord store of the project's own (its common git directory, found from `CLAUDE_PROJECT_DIR`), and nothing is written into the plugin's copy (`kb/_self/coordination.md`, The coord hook).
- **the `kb:` prompt hook** (UserPromptSubmit, `_tools/kb_hook.py`): `backlog:` is answered by it from `backlog.py` without the model (`backlog+:` hands the output to Claude), and `status:` the same from `kbmon.py --status` (`status+:` hands the lines to Claude; `kb/_self/monitoring.md`, The status answer); `kb!: <report>` records a person's report on the session's last kb answer as a `feedback` row and blocks the prompt with a receipt, with no model turn (`kb/_self/tools.md`, `kb_hook.py`); `kb: <question>` is answered without the model when the kb covers it or a tool holds its answer by the question's kind (a count, a decision id, a conflict, a gap entry, a citation: `kb/_self/tools.md`, How the lookup tools decide); a routed pack (`weak`, `none`, or a `good` one with a word held nowhere in the kb or a `check:` line that sets a route) goes to Claude with the differential: answer what the kb has from the pack, research only what it lacks in the live docs and label that part, never fill it from memory (`kb/_self/tools.md`, How the lookup tools decide). The same script is the plugin's synchronous PreToolUse hook on `WebFetch`: a url whose host the routes table of `kb/_self/web-sources.md` routes away from WebFetch is denied, the reason naming the row's find and read routes; any other fetch runs unchanged (`kb/_self/tools.md`, `kb_hook.py`). It runs in shell form through `sh "${CLAUDE_PLUGIN_ROOT}/_tools/kbpy"`, which finds `python3`, `python` or `py -3`: exec form would need a real `.exe` named in `plugin.json` on Windows, where `python3` is only an alias (`kb/public/claude/hooks.md`).
- **the query log's capture hooks** (`_tools/querylog.py capture`, async, the same launcher; `querylog.py` is the entry point of the query log's stage modules, `_tools/ql_*.py` ship with it): on `UserPromptSubmit`, on `PostToolUse` and `PostToolUseFailure` for the kb server's tools, `WebFetch`, the docs plugin's servers and `curl`/`wget` shell commands, on `Stop`, on `SubagentStart` and `SubagentStop`, and on `PermissionRequest`, `PermissionDenied`, `PreCompact`, `PostCompact` and `StopFailure` (ops rows of classes only; a `PermissionRequest` hook that prints nothing decides nothing). They add nothing to context and write only to `${CLAUDE_PLUGIN_DATA}/querylog/` (`kb/_self/querylog.md`).
- **the query log's distill launcher** (`_tools/querylog.py launch`, the same launcher): on `SessionEnd` (synchronous, it returns at once) and on `SessionStart` (async). It prints nothing and starts a detached distill only when a closed session waits in `${CLAUDE_PLUGIN_DATA}/querylog/spool/`, and on `SessionEnd` for a session with spool rows always, with the session's transcript path as an argument so the distill first writes that session's token usage rows (`kb/_self/usage.md`), and on either event for each session of the spool whose transcript shows it exited with no `SessionEnd` of its own (found by its session id under the Claude config directory's `projects/`); the run file goes to `${CLAUDE_PLUGIN_DATA}/querylog/store/` (`kb/_self/querylog.md`, Distill). In mode `auto` the push runs from a managed clone of the plugin's install source (its marketplace's entry in `known_marketplaces.json`) under `${CLAUDE_PLUGIN_DATA}/querylog/clone`, never from the plugin copy; a push the remote refuses for want of rights writes `${CLAUDE_PLUGIN_DATA}/querylog/DISABLED` and deletes the spool, so that host logs nothing again (`kb/_self/querylog.md`, Delivery).
- **the roots' fetch hook** (`kbroot.py fetch --hook`, async with `timeout` 60; the same launcher): at a session start it fetches into `${CLAUDE_PLUGIN_DATA}/roots/` each fetch root for which any one of these holds: it has no clone, its last fetch is older than 24 hours, or its pointer's `url`, `ref` or `pin` changed since the last fetch (any one of them), each within a time bound, prints one line for each root that failed and nothing else, and always exits 0; it does nothing where no pointer names a fetch root (`kb/_self/tools.md`, `kbroot.py`).
- **the query log's weekly digest** (`_tools/querylog.py digest --hook`, the same launcher): on `SessionStart`, synchronous with a short `timeout`. At the first `SessionStart` of an ISO week it prints last week's digest of the plugin copy's committed store as a `systemMessage`, which is shown to the person, never as plain stdout, which would go to Claude's context; otherwise it prints nothing. Its week marker is `${CLAUDE_PLUGIN_DATA}/querylog/digest-week` (`kb/_self/querylog.md`, Reporting).
- **the Python notice** (`sh _tools/kbpy --notice`): the first `SessionStart` hook, synchronous with a short `timeout`. It prints nothing when the launcher finds Python 3.11+; without one it prints a `systemMessage` saying the kb's hooks and tools do not run and how to install Python (on Windows `install-python.ps1` by its full path beside `kbpy`, the plugin copy's own under `${CLAUDE_PLUGIN_ROOT}`), since every other hook then exits 127 in silence.

**`it-ops-kb-docs`** (`.claude-plugin/it-ops-kb-docs/`): the three documentation servers (Microsoft Learn, Claude Code docs, MCP spec), with every `submit_feedback` call blocked by the plugin's PreToolUse hook (a plugin cannot ship permission rules), a shell command that prints why and exits 2, so it needs no interpreter. It is one command that sh and PowerShell both parse (sh runs its first half and exits; PowerShell reads that half as a string and runs the second), with no `shell` field, so it blocks in whichever shell the host gives a hook: sh, Git Bash, or PowerShell on Windows without Git Bash (`kb/public/claude/hooks.md`). Install it only for servers the project does not have already: each adds its name and instructions to every session.

The writing skills (`/kb-research`, `/kb-refresh`, `/kb-add-topic`, `/kb-ingest`, `/kb-census`, `/kb-git-sync`, `/kb-self`, `/kb-upstream-report`) and the gate stay in a clone of this repository (the backlog skills are the plugin's, above): the plugin copy is replaced on every update. A sprint runs one suite, stated in `kb/_self/backlog.md` (Working on items).

## 2. Rules for changing the plugin

- **What reaches a host project:** only the `kb` server's instructions and tool descriptions, the skill and agent names and descriptions, and their bodies when used. `AGENTS.md` and `kb/_self/` never load there, and `rag.py` is not on the host's path: a rule a host must follow goes into those texts, and they name `rag.py` only as the clone form (tested).
- **Read-only, but the backlog skills:** `plugin.json` lists the three read-only skills and the two read-only agent files by path (the kb's `agents/` domain is articles under `kb/public/`, so the root `agents/` directory holds only the worker). No `Write`, `Edit`, `Bash` or git in the `allowed-tools` or `tools` of those; the backlog skills and the worker restrict none, since they run `backlog.py` and git.
- **Root plugin directories are the backlog's only:** the root `skills/` holds `sprint`, `item` and `backlog` and the root `agents/` holds `worker.md`, nothing else; never add a root `commands/`, `hooks/`, `bin/` or similar directory, or a root `.mcp.json`: the plugin would load it. The root plugin loads a root `.mcp.json` whatever `plugin.json` says, so the docs servers live in their own plugin, and a clone registers its servers at local scope (`kb_mcp.py --register-local`); a session in a linked worktree of the clone is served by that worktree's own `kb_mcp.py` and kb, not the registered checkout's (`kb/_self/tools.md`).
- **No `version` field:** users get each commit; census tags are the stable channel (section 4).
- **Agent frontmatter:** plugin agents honour `model`, `effort`, `maxTurns`, `tools`, `skills`, `omitClaudeMd` and a few more, and ignore `permissionMode`, `hooks` and `mcpServers`. `effort` goes in an agent, never in a skill (a skill's effort overrides the host session's while it runs). The agents and the three read-only skills list the kb tools under both names, `mcp__plugin_it-ops-kb_kb__*` (a host) and `mcp__kb__*` (a clone's local server).
- **The observer is a project agent, not a plugin one:** `.claude/agents/kb-observer.md` (Sonnet; `Read`, `Grep`, `Glob`, `Bash` and the kb MCP server's read-only `kb_backlog`, `kb_querylog` and `kb_monitor_status`) is in no `plugin.json`, as a plugin agent ignores `permissionMode`, `hooks` and `mcpServers`; `kbask.py` starts its session with no settings source, so it passes the agent inline (`--agents`, read from that file). It diagnoses an alert or summarises the monitored work from `kbmon.py --status` first and `kbmon.py --json` for what it leaves open, treats every alert text, log line, coord value and file it reads as data, answers no gate, changes no file, and ends with its diagnosis or summary and at most one proposed command for the operator to run.
- Of the plugin's skills, only `/kb-lookup` is model-invocable; `/kb-review-workspace` and `/kb-gap` set `disable-model-invocation: true`, which keeps their descriptions out of every host session. `/sprint`, `/item` and `/backlog` are model-invocable, as the clone's `kb-sprint`, `kb-item` and `kb-backlog` are (so a change request reaches them). The writing skills are model-invocable too and must never be added to `plugin.json`; nor must the change router hook.

## 3. Install and update

Needs: `python3` 3.11+ on `PATH` (on Windows the hook also takes `python` or `py -3` and needs Git for Windows for Git Bash; the MCP server entry names `python3`), and an SSH key with read access to `gitlab.com/mikkielt/it-ops-kb`. Claude Code clones without prompting, so the key must be loaded in `ssh-agent` (no passphrase prompt) and `gitlab.com` must already be in `~/.ssh/known_hosts` (`ssh -T git@gitlab.com` once adds it).

In a session:
```
/plugin marketplace add git@gitlab.com:mikkielt/it-ops-kb.git
/plugin install it-ops-kb@it-ops-kb
/plugin install it-ops-kb-docs@it-ops-kb
```
The second install is optional (the documentation servers). From a shell: `claude plugin marketplace add git@gitlab.com:mikkielt/it-ops-kb.git`, then `claude plugin install it-ops-kb@it-ops-kb` (add `--scope project` to record it in the project's `.claude/settings.json` for the whole team).

To try a working tree without installing: `claude --plugin-dir <path to the clone>` (and `--plugin-dir <clone>/.claude-plugin/it-ops-kb-docs`). Scripts in bare mode (`claude -p --bare`) skip installed plugins, so they must pass `--plugin-dir` too.

Check it: `/mcp` lists `plugin:it-ops-kb:kb` as connected. Then call `kb_status` (start there whenever freshness matters): it answers with the kb commit, its date, the latest census tag and `behind_upstream` (commits the marketplace has that this copy lacks, as of the last marketplace update). Then ask a question in the kb's domains (for example "what does the kb say about Kerberos constrained delegation versus on-behalf-of?"); the answer should cite `path:line`, the fact's tag and the source url.

Update: the plugin sets no `version`, so every new commit on `main` is a new version. `/plugin marketplace update it-ops-kb` in a session (or `claude plugin update it-ops-kb@it-ops-kb` from a shell), then `/reload-plugins` or a new session. Or turn on background updates once: `/plugin`, then **Marketplaces**, `it-ops-kb`, **Enable auto-update**.

## 4. Pin a confirmed copy

For teams that should not follow every commit: the releases are the census tags, `census-YYYY-MM-DD`, each a commit whose sources were all confirmed current on that date (`git ls-remote --tags git@gitlab.com:mikkielt/it-ops-kb.git 'census-*'` lists them). ## 5. What it costs and what to watch

- **Context:** about 1.24k tokens in every session once the `kb` server connects (`kb/_self/reports/benchmarks.md`, "Always-on cost"): the `kb_pack` schema (the figure predates its `include_invalidated` argument and the instructions' sentence on `DECISION` lines, which replaced another), the server's instructions, the `kb-lookup` skill and both agent descriptions, the deferred tool names. `claude plugin details it-ops-kb` shows less: it misses path-listed agents and the inline server; `/kb-review-workspace` and `/kb-gap` are never listed, so they cost nothing until run. The docs plugin adds each server's instructions. The server's whole `tools/list`, which a client loads only as tools are searched for, is measured in `kb/_self/token-efficiency.md`, "MCP tools for commands".
- **Disk and time:** one clone of the repository per installed copy; Python 3.11+ standard library only. After each update the first lookup builds the index (3-5 s measured), then a cold lookup takes about 0.1 s.
- **Known limit, a false `good`:** the verdict counts the question's key words in the best article, not meaning, so a `good` pack can be about something related. Common words that no single fact holds together are `weak`, and a rare product name that no printed line holds is `none`; beyond that the pack prints a `check:` line when a name the question uses appears nowhere in the lead article, or when no single fact holds half the key words; the kb tools' instructions say to answer only if a cited line answers the question itself. Without that line the risk is lower, not gone: check that the cited fact answers what was asked, and report a miss with `/it-ops-kb:kb-gap`.
- **Keep the host's code context small:** the kb is an on-demand tool, not loaded text (`kb/public/agents/coding-agent-codebase-context.md`, "How it fits"), so it pairs with two settings that do the same for the host's own code (`kb/public/claude/large-codebases.md`):
  - **a code intelligence plugin** for the project's languages, one language server per plugin (`/plugin install pyright-lsp@claude-plugins-official`; the server binary is installed separately, `kb/public/claude/plugins.md`), so Claude finds definitions and callers through the server, not by reading and grepping files;
  - **`Read` deny rules** in the project's `.claude/settings.json` (not inherited from parent directories) for checked-in generated and vendored code, such as `Read(./**/vendor/**/*)` under `permissions.deny`; `.gitignore` already keeps ignored paths out of searches. The rules cover the built-in file tools and the Bash file commands Claude Code recognizes, not a `grep -r` over the directory.

  `/it-ops-kb:kb-review-workspace` names either one that the workspace lacks; it changes no settings.
- **Headless answers:** `_tools/kb_ask.py` needs a clone and the `claude` CLI; in a session with the plugin the path is `kb_pack` or `/it-ops-kb:kb-lookup`.

## 6. A team's own knowledge: roots beside `kb/public`

A team keeps its own knowledge (its systems, repositories, runbooks; real hostnames and tenants allowed) in roots beside `kb/public`, and one `kb` server answers across all of them: a question that spans a vendor product and the team's own service gets both roots' facts in one pack, each line under its qualified path (`public/intune/...`, `mdm/enrol/...`).
- **Where:** in the team's own fork or clone of it-ops-kb, as `kb/<name>/` created with `/kb-add-root` (`python3 _tools/kbroot.py add`), with its own id prefix, `_sources.csv`, ledgers, coverage page and `_retrieval/` data (`kb/_self/content-rules.md`, "Roots"). The fork pulls tools and `kb/public` from upstream without conflicts inside its own roots, and serves as the team's plugin marketplace (section 3 with the fork's url), so an installed plugin carries every root. Internal roots never go to the upstream remotes.
- **Outside the repository:** `KB_ROOTS=DIR[:DIR]` adds roots kept elsewhere (each with its own `_root.md`) to the read tools and checks, e.g. `claude mcp add --scope user kb -e KB_ROOTS=$HOME/src/team-kb -- python3 ~/src/it-ops-kb/_tools/kb_mcp.py`. Set it on the server only (`-e`); git, census and fetch work on the repository's roots only. A directory with no `_root.md` is reported as a missing root (`kb/_self/tools.md`) and the others answer. The index file then gets its own name (`kbindex-r<hash>-...`) beside the default one.
- **In another repository:** `/kb-add-root` asks where the new root is kept (a directory here, a fetch root or a submodule root in the team's own repository) and for a remote one runs `kbroot.py add-remote --access fetch|submodule` and, for a fetch root, `kbroot.py fetch`; the repository holds the root (`_root.md`) before the pointer names it. A pointer file `kb/_roots/<name>.md` names a root kept in its own repository (`url`, `ref`, `pin`, `access`: `submodule` or `fetch`; `kb/_self/content-rules.md`, "Roots"); `kbroot.py add-remote` writes the pointer (with `--access submodule` it also runs `git submodule add` at `kb/<name>/`); the read tools serve the root once its checkout is on disk (`kb/<name>/` for a submodule; for a fetch, a clone that `kbroot.py fetch` makes in `_cache/roots/<name>/` of a clone and in `${CLAUDE_PLUGIN_DATA}/roots/<name>/` of a plugin host, so each user of a host gets the roots their credentials reach) and `kbroot.py list` shows one that is not as `missing` (a root that names a `team` shows `team=NAME`, as in `kb_status`), with the reason, a failed fetch's among them (a failed git command gives its reason line: the `! [rejected]` line of a refused push, else the last line that is no `hint:` line, the url left out). `kbroot.py push NAME` writes back a submodule root: it pushes the root's commits to its own remote, then commits the gitlink in the superproject; a fetch root is read-only. In a plugin host, where the plugin copy is read-only, `add`, `add-remote`, `push` and `fetch --pin` are refused with exit 2 before any git call or write: run them in a clone of the team's repository.
- **Filter:** `python3 _tools/kb_mcp.py --roots NAME[,NAME]` starts a server that serves only those roots (its index file is named after that root set); `root` on `kb_pack`, `kb_search`, `kb_facts` and `kb_audit` (`--root NAME` on the command line) keeps one root, and the name of a root that is missing (a pointer not fetched) is no error: `kb_pack`, `kb_search`, `kb_facts` and `kb_audit` answer with no match and the `roots missing:` line with its reason, as `rag.py pack --root` does [CODE _tools/kb_mcp.py#root_of]; `kb_status` lists every root with its prefix, visibility and counts. A bare `domain` covers that domain in every root and is matched without regard to case; one no path is under is an error that lists the domains.
- **Embedded in a host MCP server:** another team's server that runs `_tools/kb_mcp.py` as its stdio child and re-exposes its tools follows `kb/_self/embedding.md`.
- **Over HTTP, for a client that cannot start a process:** `python3 _tools/kb_http.py` serves the same tools on a Streamable HTTP endpoint, for a remote MCP client that connects by url, such as a Copilot Studio agent (`kb/public/agents/copilot-studio-mcp-client.md` for the client side). It listens on loopback, so it reaches such a client only through a TLS proxy or platform in front of it that authenticates the caller; the server has none of its own. It serves `kb/public` only unless its `--roots` names more. Everything that can start a child process uses the stdio server instead: the plugin, a local agent, a host MCP server (`kb/_self/embedding.md`). Neither plugin starts `_tools/kb_http.py`; whoever hosts it runs it from a clone. Flags and exit codes: `kb/_self/tools.md`; its limits: `kb/_self/design.md`; deploying it: `kb/_self/hosting.md`.
- **Checked in a host:** a fork with a team root, installed as a plugin in a host project (a local-scope directory marketplace), loaded with `--plugin-dir`, and served through `KB_ROOTS`, answered a question spanning both roots with lines and citations from each (`kb/_self/reports/host-plugin-roots.md`). A fork runs the upstream tests unchanged whatever it names its roots.
- **A team's repositories into its root:** `/kb-ingest` turns a repository at a pushed commit into `CODE` and `DOC` facts of a root, each source row written with `kbid.py add`, leaving out secret, generated and vendored files (`python3 _tools/kbingest.py survey`, with `--pins` for the toolchain versions the repository declares), and can map its packages, imports, entry points and symbols (definitions and their references) first with the installed toolchains' read-only commands (`kbingest.py map`, opt-in, output under `_cache/ingest/`). From a clone, "source `<repo>` and put it here" writes to `kb/<root>/`. From a host project the plugin copy stays read-only: the facts land in a writable clone of the team's fork (the default: the gate, trailers and `kbgit.py sync` apply, and every installed copy gets them at its next update) or in a `KB_ROOTS` directory committed by its own repository's git; never in the plugin cache or `${CLAUDE_PLUGIN_DATA}`, which no git history holds. The host session opens the clone with `claude --add-dir <clone>`, which loads the clone's skills, and runs its tools by path (they find the kb from their own location, not the working directory). Where the team's root is a submodule root of that clone, `/kb-ingest` writes the facts into its checkout `kb/<root>/`, commits them there and runs `kbroot.py push <root>` before the clone's `kbgit.py sync`.
- **Who commits as whom:** a person commits as themselves, with a signing key whose public half is in their forge profile; a headless runner commits as a bot user (a project or group access token's user, a service account, or a GitHub App); a fetch root reads with a read-only deploy key, which holds no write access to the team's repository (`public/gitlab/commit-signing-and-provenance.md`, `public/gitlab/multi-repository-layouts.md`). Each commit that changes a root with a `team` also carries the computed `KB-Teams: <team>[, <team>]` trailer beside `KB-Work` (`kb/_self/git.md`, "Commit trailers"); a commit that changes no such root carries none.
- **Size:** a word counts as a key word only when under a fifth of the lines of all roots together hold it, so a small team root reaches `good` for words the public root rarely uses.
- **Decisions:** a root may keep `_decisions.csv` and `decision-makers.csv`, which `check.py` validates; a decision maker's name stays out of a root that is not `internal` and out of the published `kb/_self/`, and a root's `by_ref` may name a maker of the central register `kb/_self/decision-makers.csv`; a root saves its makers by a policy (role only, role and name, or the central register) that the operator sets with `kbdecide.py makers`, and its first decision waits for it (`kb/_self/content-rules.md`, "Decisions"). `D`, like `L` (a log row's id), cannot be a root's id prefix: `kbroot.py add` refuses both (`kbcommon.RESERVED_PREFIXES`). The leak scan refuses ids with an internal root's prefix, and the url host and path of its pointer, in public roots, the tools and the docs (`kbcommon.private_hits`); when the registry does not load (two roots share an id prefix), it reads each root's `_root.md` directly, so no internal name passes.

Without `--roots`, and unless the environment variable `KB_COORD_TOOLS` is `0` (they write to the coord store; with it `0` `tools/list` names none and a `tools/call` of one is an unknown tool), it also serves nine coordination tools, `coord_claim`, `coord_renew`, `coord_release`, `coord_post`, `coord_get`, `coord_put`, `coord_digest`, `coord_wait` and `coord_dedup`, listed in that order after `kb_docs` (before `kb_backlog_write` and the live-docs tools) and never under `--roots` or in `kb_http.py`, so the list is the same in every session and a client's prompt cache holds [CODE _tools/kb_mcp.py#coord_enabled]; none sets `anthropic/alwaysLoad`, so a client defers them behind its tool search. Each is the `coord.py` command of its name, run as a `coord.py` child process: against the local store (`KB_COORD_STORE`, else the one `coord.py` and the coord hook default to) or, when `KB_COORD_URL` and `KB_COORD_KEY_FILE` both name a `coord.py serve` address and its operator's key file (one without the other is a tool error), through `--url`/`--key-file`. A tool takes the command's arguments and returns what the command prints: `coord_claim(key, ttl, holder?, budget?)`, `coord_renew(key, token, ttl?)`, `coord_release(key, token)`, `coord_post(kind, fields?)` (`fields`: an object of NAME to id values, up to eight), `coord_get(key)` (`readOnlyHint` true: the value, revision and holder of any key, through `redact.redact`, so the text an ask or answer event's `ref` names can be read), `coord_put(key, value, revision?, token?)` (`readOnlyHint` false, `destructiveHint` false, `idempotentHint` true: writes the text of an ask or answer, so `key` must be `ask/ID` or `answer/ID` and any other key is a tool error before `coord.py` runs; `value` goes through `redact.redact` and is at most 8000 characters, `revision` is the revision the key must be at and defaults to 0, a new key, and `coord.py`'s own refusals of a stale revision, of a key a live lease holds without the holder's `token` and of another team's key stay), `coord_digest(key[], lines)` (plain text, as the command prints it) `coord_wait(since, timeout, kind?, item?)` (`kind` and `item` as `wait --kind` and `--item`: only the events of that kind whose `item` field is one of the comma-separated ids, `last` the newest sequence scanned) and `coord_dedup(question, holder?, topic?, token?, ttl?, code?)` (`coord.py dedup` with its id-only fields, `code` an array of REPO:PATH[#SYMBOL] targets claimed the same way, listed right after `coord_wait`: it claims the lack terms of the question's pack that no overlapping live claim covers and returns `topic`, `terms`, `uncovered`, `overlaps`, `held`, `claimed` and `token`, with `code` also `code_uncovered`).
- A command that exits non-zero is a tool error holding the command's refusal (an unknown or expired token, a held key, a value that is no id). `coord_renew` and `coord_release` refuse a call without the holder's `token`, and `coord.py` refuses any other value, so a handle one agent knows does not let another renew or release it. `timeout` of `coord_wait` is a number of seconds from 0 to 60, since the server answers one request at a time and a wait holds every other call; a value that is no such number (a string such as `"100"`, a boolean, a negative or a larger number) is a tool error before `coord.py` runs, whatever the client's schema check did [CODE _tools/kb_mcp.py#coord_run]. Without `--roots` it also serves two live-docs tools, `docs_search(server, query)` and `docs_fetch(server, target)` (`server`: `microsoft-learn`, `claude-code-docs` or `mcp-docs`, urls from `.claude-plugin/it-ops-kb-docs/.mcp.json`; `target`: a page url for Microsoft Learn, a read-only filesystem command for the other two), which call the remote server over Streamable HTTP and keep each answer 7 days in `_cache/live-docs/` (`$KB_DOCS_CACHE`, else `$CLAUDE_PLUGIN_DATA/live-docs`), keyed by server, tool and arguments; a repeat within 7 days makes no HTTP call, an older, corrupt or failed entry is fetched again and an error is never stored. Each answer opens `live docs, not in the kb: <server> <tool> (fetched YYYY-MM-DD; kept 7 days)`. `KB_LIVE_DOCS=0` turns them off; under `--roots` and in `kb_http.py` they are absent [CODE _tools/kb_mcp.py#docs_call]. The clone's `.claude/settings.json` sets `MAX_MCP_OUTPUT_TOKENS` to 10000, the fixed warning threshold, below Claude Code's default of 25,000 (`kb/public/claude/tool-output-limits.md`): a larger MCP result from any server is saved to a file in the session's `tool-results` directory and replaced by its path, so one oversized answer does not ride every later turn.
