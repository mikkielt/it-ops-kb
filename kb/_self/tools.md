# Tools

Every tool is stdlib-only Python in `_tools/`, run as `python3 _tools/<tool>`. Each tool's docstring (`--help`) is its full reference; this file is the one table of what exists and how the lookup tools decide. The read tools span every root (`kb/public` and any root a team adds; `_tools/kbcommon.py`, "Roots") and name files and topics by qualified path, `<root>/<path in root>` (`public/intune/win32-apps.md:12`); `--root NAME` (MCP: `root`) keeps one root. Lookup rules for agents are in `AGENTS.md`. Skills and subagents read the part of a doc they need with `python3 _tools/selfdoc.py section DOC HEADING` (the `selfdoc.py` row below), not the whole file; skills read Conduct that way, and the other rules are asked for with `python3 _tools/rag.py pack --root _self` (the `rag.py pack` row below). Before reading a tool's source, run `python3 _tools/selfdoc.py map-tools FILE` (or grep the full map for a name): it gives each function, class, method and test with `path:line` and its first docstring line, so only the lines of the symbol found need reading (`rag.py show PATH:LINE -n N` or `sed -n`).

## How the lookup tools decide

- **One parser.** `pack`, `facts`, `audit` and `src --cited` read the kb through `_tools/kbfacts.py`, which parses fact units (bullets, table rows, data rows), tags (grammar in its docstring), validity windows (`windows_in`, `window_ended`; `kb/_self/content-rules.md`, Facts and tags) and ledger entries one way for every tool; each row `kbfacts.audit` returns holds `ended`, the count of the article's facts whose window has ended.
- **One tokenizer.** The index and the query split words the same way (`terms`, `key_terms`, `camel_parts` in `_tools/kbfacts.py`): text and question are NFC (a decomposed `Könige` is one word), words are casefolded (`Straße` meets `strasse`), and an identifier splits at a capital of any script (`PobierzŁącze` -> `pobierz`, `łącze`; `GetEntityÜbersicht` -> `get`, `entity`, `übersicht`). Only prose words and identifier parts are folded; a path, a code symbol or an id is compared as written. ASCII text tokenizes as it did before, and there is no setting. [CODE _tools/kbfacts.py#terms]
- **The verdict.** `pack` ranks fact lines (BM25 with light stemming) and prints `coverage: none` when the question's named terms are not in the kb or most key words are missing, `weak` when the best article matches under 60% of the key words, else `good`. A word counts as a key word only when under a fifth of the lines of all roots together hold it, or when a single line holds it, so a small root served alone keeps its key words [CODE _tools/kf_index.py#informative_words]. A line holds the words of its file name, article title, section and text; its directory name ranks it but is not held, so a growing domain does not turn its own name (`agents`) into a common word. It also holds the parts of its compounds (hyphen and dot parts, identifier parts), and a number joined to a unit by a hyphen as the number itself, so a question's `1.5 seconds` matches a fact's `1.5-second`, and a version a model id spells with a hyphen as the dotted one, so `Opus 5.5` matches the `claude-opus-5-5` row of `claude/models.csv` [CODE _tools/kbfacts.py#terms]. A number keeps its digits whole: the stemmer drops a doubled final letter of a word, never a doubled final digit, so a build number `26100` is indexed as `26100` and the RID `544` of `S-1-5-32-544` as `544` [CODE _tools/kbfacts.py#stem]. A dotted version is one word with or without its `v` prefix, in the question and in the kb, so a question naming `2.1.294` finds the facts that spell `v2.1.294`, and the other way round [CODE _tools/kbfacts.py#stem]. The article whose one printable line holds the most of those key words leads the pack, and the other articles keep their order by score, so a data row that holds a question's model, columns and price words comes before prose facts that each hold a rare word or two; within a data file the rows print by score, not in file order, so the budget cuts the weakest row first, where an article's facts print in article order [CODE _tools/kf_index.py#pack]. Untagged lines (printed `(no tag)`) can lift `none` to `weak`, never to `good`. `rag.py eval` checks this against `kb/public/_retrieval/lookup_eval.csv`; `tests.py` runs it. When a row's verdict turns only on a key word's share crossing that fifth, eval re-judges it on the committed `word_shares.csv` (Commands), and the verdict a pack prints is unchanged. [CODE _tools/kf_index.py#pack]
- **The rules route (`--root _self`).** `pack` and `search` read the top-level `kb/_self/*.md` docs as sentence passages instead of fact lines. A line longer than a passage is split at its sentences, and a sentence that is still too long at its list separators. A passage after the first of a line carries the line's lead (the bold lead of a bullet, else its first clause) in front of its text, and a nested list item carries the end of its parent's last sentence. A table row's passages each start with its first cell. The first cell of a table row and the bold lead of a bullet weigh like a title. The verdict is `good` only when the question matches a tested question of the eval file (at least three quarters of the question's key words are in it and at least half of its own key words in the question, a word of fewer than three letters never counting), and the passage that tested question is anchored to is printed first, marked `tested`; otherwise it is `weak` or `none`. A pack with a tested match prints its pinned passages and at most three further passages, whatever the budget leaves, so a tested answer is short; a `weak` pack keeps the whole budget, since the reader must find the line itself [CODE _tools/kf_index.py#pick_passages]. A passage longer than the print width is cut at it, unless the words that answer lie beyond the cut: it then prints as the window around the tested question's anchor phrase (else around the densest cluster of the question's key words), with `...` at each cut end [CODE _tools/kbfacts.py#clip_around]. A tested question is an expansion of its anchored passage: it weighs like a doc2query expansion and never adds a key word. The informative words of each anchored tested question are computed once per store view [CODE _tools/kf_index.py#tested_matches]. The active decisions of `kb/_self/_decisions.csv` come after the passages, each tied to the docs or sections whose passages are printed by an `article:_self/<doc>[#<Heading>]` context reference; for a question, such a tied decision prints only when its text or its source holds a key word of the question or of the tested question pinned, so a section's decisions do not follow every question that touches the section [CODE _tools/kf_index.py#pack]. `--item ID` builds the question from the item's title and goal, takes as candidate docs those `kb/_self/map.csv` names for the item's `touches` (every rule doc when none), and adds the decisions whose context is `item:ID`. `--set NAME` prints, with no ranking and no verdict, the anchored passage of each row whose `sets` cell names `NAME` (`skill`, or `skill:step`, a bare skill name taking all its steps), then the decisions tied to those passages. `rag.py eval --root _self` checks the route against `kb/_self/_retrieval/lookup_eval.csv`; `tests.py` runs it. [CODE _tools/kbfacts.py#self_units]
- **Two corrections to the verdict.** Both are lexical and cheap, and neither demotes a true `good` of the eval set ("Retrieval quality" in `kb/_self/reports/benchmarks.md`). [CODE _tools/kf_index.py#specific]
  - *Common words only:* a `good` becomes `weak` when no single tagged fact holds every key word and the question names nothing specific: no name (a capital or a digit), identifier (`list/get`, `python_files`, `--frozen`, `gitlab-runner`), one-word product alias (`dsc`), word an article is about (in its title or file name, with 60% of the word's lines: `ruff`, `krbtgt`) or word the kb itself mostly spells as a brand (`cmpivot` -> CMPivot). "email attachment size" and "mailbox size limit" are `weak`; "battery health report" stays `good` (one fact holds all three).
  - *Another product:* the verdict becomes `none` when a name the question uses is held by under 1% of all lines and by none of the lines the pack could print (VMware Horizon, SAP GUI, Zscaler); a line holds a name as a word of its own, not as the part of a hyphenated word (`Horizon` in "long-horizon tasks"), whatever the order of the top articles, unless another part of that hyphenated word is a word of the question that is no stop word, a one-letter part too (`Hyper V` finds `hyper-v`, `Invoke WebRequest` finds `Invoke-WebRequest`, `Break Glass` finds `break-glass`). An unknown name of 4 or more letters among well-matched words (NinjaOne) is also `none`; the exemption stays for abbreviations (AV, PC).
- **The `check:` line (a possible false `good`).** The verdict counts words, not meaning. Under a `good` verdict the pack prints `check:` when a name the question uses (a product, an id) appears nowhere in the lead article, or when no single fact holds half of 4+ key words. The `kb:` hook then passes the pack to the model instead of answering alone. A third note, the scatter check, is a query performance prediction signal fitted to this kb's labelled questions and never a generic predictor (predictors vary most with the collection: `kb/public/agents/hybrid-retrieval.md`): it prints `check:` under a `good` the decisions did not lift when the pack's three best articles lie in two or more domains and its best BM25 score is under `kbfacts.SCATTER_SCORE`, the words having matched a little in each of several topics and fully in none. No single feature tried (the spread of the top scores, the rarest key word's idf, the key-word count) separated the off-kb goods from the eval goods; the pair flags most of the former and few of the latter, so it is a note: the verdict and the route do not change, the `kb:` hook answers such a pack alone with the line in the answer, and `rag.py eval` counts an eval `good` row that carries it in `noted=` [CODE _tools/kf_index.py#SCATTER_SCORE]. The threshold is the whole score that flags most off-kb goods net of eval goods over the public root's `lookup_eval.csv` `good` rows and its off-kb list, the lower score on a tie; the held-out file is never read [CODE _tools/rag.py#scatter_calibration].
  - `python3 _tools/benchmarks.py run verdict` prints the fitted threshold, the one in force and, at each, the off-kb goods and the eval goods flagged (case `scatter check`) [CODE _tools/bench_retrieval.py#scatter_rows]; a threshold that is no longer the fitted one after eval rows or off-kb lines are added shows there, the constant kept by hand; its counts are those of the notes the packs carry, and no held-out row is read [CODE _tools/rag.py#scatter_calibration]. Three more notes read the lead article's printed facts and are not fitted: `passing`, when a plain word of the question (alphabetic, not an identifier or a brand spelling) is held by at most `kbfacts.PASSING_UNITS` units of the kb, is no word of the lead article's title or `applies_to`, and those facts miss another key word and, the rare word counted, at least `kbfacts.PASSING_MISSING` of the key words (a count of tempdb data files meets one line on encryption at rest that names tempdb; the one word of eight or ten that a paraphrase leaves out is no sign); `priced`, when the question asks for a price (price, pricing, cost, but not a cost asked in a unit of measure, `in resource units` or `how many resource units ... cost`; `how much` beside a licence, subscription or seat, or `per user`, `per device`, `per month`, `per year` unless the question asks for a quantity of memory, data, storage or bandwidth: `how much memory per device`, a quantity word right after `how much`, or one anywhere on the line when no `is` or `are` follows `how much`; `how much is OneDrive storage per user per month` names a product and is priced, and a cost asked on a later line of the question counts) and no printed fact of the lead article holds an amount, a currency sign or code beside a number [CODE _tools/kf_index.py#PASSING_UNITS]; and `parted`, when the question holds a name of two or more capitalised words in a row after its first word (`Exchange Online`), each a key word the kb holds, and no printed fact of the lead article holds the whole name beside any lower-case key word of the question (`retention`, `policies`): the name sits in some facts and what is asked about it in others, and the pair is named under `kb lacks:` [CODE _tools/kf_index.py#name_apart].
  - Each prints `check:` and, unlike the scatter note, sets `route: split` with `kb has:` and `kb lacks:`, so the `kb:` hook passes the pack on instead of answering alone; the verdict does not change and `rag.py eval` counts an eval `good` row that carries one in `noted=`: the eval's `noted` is the count of eval `good` rows whose pack prints a `check:` or `route:` line, and `rag.py eval` fails when it is above `NOTED_BASELINE` [CODE _tools/rag.py#NOTED_BASELINE]. A question whose key words all sit in one article about another thing meets `parted` when it names that thing in capitals (Exchange Online retention policies, whose words one Purview audit-retention article holds, with `Exchange Online` in other facts of it than `retention` and `policies`). What still passes the corrections and the notes, all on the off-kb list (`kb/public/_retrieval/doc2query/offkb_questions.txt`): common words that unrelated facts hold together ("password reset link" in the KRBTGT article, "How many members can a Microsoft Teams shared channel have?" in an article on a chatbot's channels), without a `check:` line. A lexical rule would need to know which word is the subject; the rules tried and what they cost are in "Verdict corrections" in `kb/_self/reports/benchmarks.md`.
- **The `freshness:` line.** A question about the latest release (latest, newest, current version) or naming a version the kb never mentions (`2.2.365`) gets `freshness: these facts are as of <lead article's retrieved_utc>`, and "check the cited source live and say which version your answer is for". Without it, models reported the kb's newest release as the latest ("Partial knowledge, newer versions and stale copies" in `kb/_self/reports/benchmarks.md`). [CODE _tools/kf_index.py#freshness]
- **The source stamp and the fact marks.** Every pack's source footer ends each cited source's line with `[confirmed <date>, <signal>]`, read from files with no network: the date is the newest of the source's anchors' `verified_utc`, its `_fetch_state.csv` `checked_utc` and the census's `confirmed <date>` in its `version_or_date` (`unconfirmed` when none dates it); the signal is the first of its provider's signals (`_tools/providers.csv`) that its state row holds: `pinned` (a url whose text cannot change), `git`, `etag`, `lastmod`, `version` or `hash`, else `no baseline` [CODE _tools/kf_fresh.py#source_stamp]. They are notes: the verdict, the route and the choice of lines never depend on them, the `kb:` hook and `kb_pack` print them as `pack` does, the `concise` format keeps the marks and drops the footer, and the `_self` pack has neither (its facts cite no source). - **Freshness lifetime.** Each source has a lifetime, the days its facts count as fresh after a check, computed with no request as a tenth (`provider.FRACTION`, RFC 9111's typical heuristic fraction) of its estimated mean time between changes, from the first evidence it has [CODE _tools/provider.py#lifetime]: its recorded changes, the `changed_utc` values across the git history of its root's `_fetch_state.csv` (the file keeps only the latest, so the history is the record; none outside a git repository), when it has two or more, by Cho and Garcia-Molina's modified estimator over its checks, the mean check interval over `-ln((n - X + 0.5) / (n + 0.5))` for `n` check intervals and `X` changes seen, which stays finite where every check saw a change and the plain rate is infinite [CODE _tools/provider.py#modified_interval]; else the commits of its Learn page's source file (`census.LEARN_MAP`) in the census's clone cache over the last `provider.WINDOW_DAYS` when it has two or more, one git walk per repository, never a fetch, so a page whose repository is not cloned has none [CODE _tools/provider.py#learn_commits]; else the time since its page date, a date of its `version_or_date` or a stable `Last-Modified`, which is RFC 9111's heuristic; else its provider's `lifetime_days` (`_tools/providers.csv`, then the `*` row). A pinned url has none and is never stale. The state file's history is read once per revision and kept under `_cache/lifetime/`. A source's age is the time since the newer of its last check and its facts' verified date, unknown when neither dates it, and a source whose age is unknown or past its lifetime is stale unless its url is pinned [CODE _tools/kf_fresh.py#root_freshness]; `fetch.py --status` reads the same function [CODE _tools/fetch.py#status]. The estimate counts the changes the state file recorded: `fetch.py --diff` writes `changed_utc` when a page's hash differs, and `factdiff.py detect` records its check time as `changed_utc` for a source whose verdict is `changed`, `replaced` or `moved` and leaves the one of any other verdict, beside `detected_utc` and the document's hash [CODE _tools/factdiff.py#cmd_detect], so a source has two recorded changes only once two runs saw it change, and until then the file commits and page dates carry most.

The `kb_hook` and `mcp` capture rows keep the handle as `pack` (`kb/_self/querylog.md`, Surfaces). A revalidation's marks and summary line come after it. The line under the coverage, `as of DATE: N matching facts left out as not yet valid or no longer valid then`, counts the facts the date left out among the 40 best-ranked matching ones (those scoring at least 0.4 of the best), also when N is 0. - **Revalidation at question time.** `rag.py pack --revalidate` and `kb_pack`'s `revalidate: true` ask every source the printed fact lines cite now and say per line what the page shows; `kb_pack` with `revalidate` left out and `kb_ask.py` ask only a cited source past its freshness lifetime (above): its footer line first carries `[stale: AGE old, lifetime DAYS]`, then what the page showed, and a live result younger than the lifetime is reused with no request, so a source stays quiet for its lifetime; a pack in which no cited source is past it asks nothing and says so in its last line. `revalidate: false`, `KB_NO_REVALIDATE=1` (both tools) and `kb_ask.py --route` make no request; `rag.py pack` without the flag and the `kb:` hook never go to the network.   - Results go only under `_cache/` (`_cache/revalidate/<root>/<source id>.json`, beside the detection cache: no anchor, state row, source row or log is written), and a source asked within its provider's pacing (`provider.pacing`: the hour over the row's documented requests an hour, never under the per-host delay) is answered from that result with no request. A lookup that asks only some of a source's lines keeps the lines of its stored result still younger than that window, of the same verdict, beside the new ones with the earlier check time (`factdiff.lookup_store`; an older result or another verdict is replaced), so another printed fact of a source asked moments ago needs no request and no line is reused past the window of its own check. The census and refresh read those stored results as hints (`factdiff.lookup_hints`: fact key, source id, outcome and date, read within that same pacing): `factdiff.py detect` and `census.py check` ask no request for a source whose stored result found its page unchanged with every checked line `current` or `source-dated only` (a source a lookup found changed, moved or gone, a pinned url and a source no lookup asked are checked as before), `detect` logs it with verdict `hinted`, signal `lookup` and no fact rows and writes no state row, `check` makes it a `NEEDS-READING` row with the note `lookup hint` that phase 2 does not read (`census.UNREAD`, as `blocked`) and clones no repository for it, and neither `factdiff.py apply` nor `confirm` dates it: only a request of the run itself confirms a source, so a hinted source keeps its date until the next run asks it; the `detect` line counts `hinted=N`, and `census.py summary` prints `spared by a lookup hint` with the count of rows noted so. The requests of one revalidation share one time budget (`factdiff.REVALIDATE_BUDGET_S`, under the MCP client's idle timeout; `provider.budget`): a network error, the budget, GitHub's unauthenticated limit (a 403 or 429 with no requests left, or the run's REST count used up for the repository of a pinned url), a page that does not answer, or an HTTP error of the search for a passage that left its page or of a candidate page it found (any status but 200, a candidate page's 404 and 410 excepted: that is an absent page), no HTTP answer of either, or a 200 answer of the search that is not in the shape of the provider's search (`provider.search_shape`, which `provider.py search` reads too: Learn's results, GitHub's items, arXiv's Atom feed, PyPI's project; a sign-in page, an error object, a JSON list; a list of the shape with no hits stays an answer), each held against every source that leans on the answer the run kept, leaves that source's lines with the offline stamp, and the pack says so on the source's footer line and in a last `revalidate DATE:` line (DATE is the UTC day, the one every `checked_utc` stamp of the run names, whatever the host's time zone) that names each source it could not check and why.
  - A host that did not accept a connection (a `URLError` from the request: a timeout of the connect, a refusal, a name that did not resolve) is left alone for a window (`provider.host_seen`, `provider.host_down`): `provider.DOWN_BASE_S` seconds, doubled with each failure in a row after the earlier window ended, up to `provider.DOWN_CAP_S` (a record whose end lies more than that after its start, or after now, is read as ending at that bound); the host's other sources of the same pack and every lookup of this process, or of another process on the clone, within the window make no request to it and are offline with the reason `host did not accept a connection N s ago (ERROR); not asked again for M s`, so a firewalled host that drops packets costs one connect timeout, not the time budget of every pack. Every request of the revalidation reads and records the window of the host it goes to (`provider.gated_request`, under `provider.down_window`): a source's page, the search (`api.github.com`, `export.arxiv.org`, the Learn search), a candidate page, the made-up sibling page and a pinned url's repository request, so two searches against a host that does not accept a connection make one request, not two (a search_api row whose host and path have no shape in `provider.SEARCH_SHAPES` is asked nothing, and an answer is kept by its request, so two providers' searches of one query are two answers); a request not made is a network error for the source or passage that leant on it, as one made and answered with none. A redirect is followed through its hosts: each that answered ends its own window, and a connection that was not made starts the window of the host it was made to (the last redirect target), not of the source's own host that answered the redirect; a redirect hop into a host already in its window is not requested (the request ends with the reason above, `provider.request`'s `refuse`), so two sources whose hosts redirect to one firewalled host connect to it once, and the refused hop starts no new window and leaves the earlier one as it was.
  - The record is the process's and a file per host under `_cache/provider-down/` (never committed); an answer of any status, or any other error than a connection that was not made, ends the window, and the time budget used up shows nothing of the host: a request it refused, and a connect that timed out at the timeout it had shortened to the time left (`provider.request` marks it `cut`), start no window and leave the host's earlier one as it was. `detect` and `census.py check` do not read it. A server limited to named roots (`--roots`, `kb_http.py`) answers `revalidate` with an error. The revalidation resolves only the printed lines [CODE _tools/kf_fresh.py#revalidate_pack].
- **The route lines.** A `weak` or `none` pack, and a `good` pack with a word held nowhere in the kb or with a `check:` line that sets a route (the unmatched name, the spread, `passing`, `priced` and `parted` lines; the scatter note is the one `check:` line that sets none), prints `route: split|web`, `kb has:` and `kb lacks:` after the coverage, `check:`, `freshness:` and none-sentence lines and before the first article (the none sentence says the kb does not cover the question and tells the agent to state what the kb has and lacks and to research the rest in the live docs, never from memory [CODE _tools/kbfacts.py#NONE_SENTENCE]); a clean `good` pack prints none of them, so its text is unchanged. `none` routes `web`, the rest `split`, except a near miss: a `none` whose words held nowhere in the kb are all language or format names (T-SQL, PowerShell, Python, Bash, KQL, JSON, YAML, XML, CSV) routes `split`, since the kb may hold the subject and lack only the syntax (the `sp_getapplock` question, `not in the kb: t-sql`), and prints no none sentence but the fact lines and source footer a `weak` pack would, so the reader can answer the part the kb has; a best article's share of key words does not decide the route [CODE _tools/kf_index.py#LANGUAGE_NAMES]. `kb has:` lists the question's own words, in its order, that the best article matches, `kb lacks:` the informative ones it does not (`-` when empty). A decision is printed when it *answers* the question, or is *tied* to what the pack prints and holds one of the question's informative words. Tied is: a printed fact cites it (`[DECISION id]`) or it names the fact (`fact:`; both print with no word needed), or its `article:` is a printed article, its `domain:` holds one, or its `source:` is cited by a printed fact. An invalidated decision tied to a printed article needs no word. An active one that answers makes the pack `good` whatever the facts say (its words no longer count as missing, no `check:` line follows from the facts, no route line when nothing else is missing, and the line reads `coverage: good (an active decision answers it ...)`); a proposed or an invalidated one never changes the verdict, so a question only a proposal answers stays `weak` or `none` and prints the proposal for what it is. - **The index.** `pack`, `search`, the `kb:` hook and the MCP server read one persisted index: postings lists in a stdlib `sqlite3` file named after a fingerprint of the kb files' content. It lives in `_cache/` in a clone, the main worktree's for every linked worktree of the clone (`${CLAUDE_PLUGIN_DATA}` for an installed plugin, a temp directory if neither is writable; `KB_INDEX=DIR` elsewhere, `KB_INDEX=0` in memory only), is never committed, and is rebuilt the first time after any kb file changes; a cold `pack` then takes about 0.1 s. A rebuild weighs again only the units whose inputs changed: `weighed()` keeps each unit's words and weights in a unit cache beside the index, one file per root set named as the index files are (`kbunits.sqlite` for this repository's roots alone, else `kbunits-r<hash>.sqlite`), so a build over fewer roots never prunes the rows of another set's, with a row keyed by `INDEX_VERSION`, the doc2query mode, the weighing code (the title, Summary and expansion weights, both `STOP` sets, the word patterns, and a digest of the compiled code of `_weigh`, `terms`, `stem` and `bare`, which ignores comments and line numbers) and everything it reads for the unit (path, title or lead, section, text, its article's Summary, its expansions, its tested questions), so an edit to the weighing re-weighs every unit with no `INDEX_VERSION` bump, and drops the rows no unit used once they pass twice the units weighed, then runs `VACUUM` so the file gives the freed pages back (a `DELETE` alone leaves its size; the prune is rare, since the rows must double first) (the docs state no size or count of the cache or the index: both grow with the kb, `ls -l _cache` shows them); the postings are written in term order. The fingerprint is git's blob ids of the files (a modified or untracked file, and one marked assume-unchanged or skip-worktree, which git never reports modified, hashed as git would), so it depends on neither the checkout's path nor the files' times: a fresh worktree of a clone finds the index its clone built for the same content (first `pack` under 1 s instead of 14 s on that host), a file touched without a change keeps it, and an edit of any indexed file gives a new one [CODE _tools/kbfacts.py#content_key]. Those two git calls run only when the files' times and sizes, taken from the directory listings rather than one `stat` per file (about 0.7 ms a file in a Hyper-V container), changed since the checkout last asked: a memo file per checkout (`kbkey-<hash>.txt` beside the index) maps them to the key, which is kept 2 s after it was computed [CODE _tools/kbfacts.py#fingerprint]. The index files and the unit cache of any other root set go once unused for 14 days (`PRUNE_OTHER_ROOTS`; opening a unit cache marks it used too), however many there are, so `_cache` holds at most the 4 plus the current file of this root set and one file set per root set in use [CODE _tools/kf_index.py#prune_indexes].

- **The `kb:` hook.** `kb: <question>` of a kind a tool decides ("Questions a tool decides") is answered by that tool as a `good` pack is, the prompt blocked and the answer shown (`kb+:` hands it to the model as context, with the live-docs instruction when the kb lacks it); any other `kb:` question is answered from the pack without calling the model when coverage is `good` with no `route:` line (the name and spread `check:` lines come with one, the scatter note does not); otherwise the prompt goes to the model with context. A pack with a `route:` line (the route lines above) gets the differential: one instruction to answer what the kb has from the pack with `path:line` and urls, to research only what it lacks in the live docs, to label that part "live docs, not in the kb" with its url and never to fill it from memory, then the pack for `split` or, for `web`, only its coverage, `check:`, `freshness:`, `route:`, `kb has:` and `kb lacks:` lines, then its `feedback:` and `pack:` lines, with no fact lines. The pack is cut at a line boundary so the context stays under the 10,000 characters Claude Code keeps (`kb/public/claude/hooks.md`); the hook stays free of the model and the network. `kb+: <question>` always goes to the model: a clean `good` pack with a short instruction, a routed pack as for `kb:` [CODE _tools/kb_hook.py#routed]. `kb!: <report>` is a person's report on the session's last kb answer: the hook writes one `feedback` row of the session joined to that entry (its `prompt_id` and pack handle, `kb/_self/querylog.md`, Surfaces), reads by rule alone a `path:line` at fault (when the text says wrong, stale or outdated), those words and `missing` as the outcome, and a public url as the source, keeps the rest as a rule-redacted `comment` of class `unclassified` in the local spool, blocks the prompt with a one-line receipt naming the `FB-` id, and calls neither the model nor the network; a session with no earlier kb entry gets a line that says so and records nothing [CODE _tools/kb_hook.py#feedback_answer]. `backlog:` is answered by the same hook without the model, with the output of `backlog.py horizon` and `backlog.py next --all --any` as the reason; `backlog+:` passes that output to the model as context, cut to the same limit: each command keeps an equal share of it (a short output leaves the rest to the other), cut at line boundaries and ending in a note of how many lines were left out and the command that prints them all, so a long `horizon` never drops the `next` list [CODE _tools/kb_hook.py#fit_blocks]. A failing or timed-out command never blocks the prompt: the model gets a note naming it. Neither prefix writes a query log row or loads the facts. `AGENTS.md` routes a plain-words question about open work and its order to those two commands, or to the `backlog:` prefix, so no search of the codebase is needed. `status: [text]` runs `kbmon.py --status TOPIC` (`mon_status.run`, TOPIC what `mon_status.topic_of` reads from the text, else `all`) and blocks the prompt with its lines as the reason, so no model turn runs; `status+:` lets the prompt through with the same lines as context, told to answer in plain words and name no backlog id; a kbmon that fails or times out lets the prompt through with a note naming it, and neither prefix writes a query log row. A `kb:` prompt is never read for a topic: it stays the docs lookup [CODE _tools/kb_hook.py#status_answer]. `AGENTS.md` sends a plain status question (sprints, sessions, load, cost) to `kbmon.py --status` the same way.
- **Questions a tool decides.** Some kinds of question have an answer a tool already holds, which ranking fact lines only approximates, so `pack_many` (`rag.py pack`, `kb_pack`, `kb_ask.py`) and the `kb:` hook ask `kbfacts.routed` first [CODE _tools/kf_route.py#pack_routed]; `pack` itself, which `rag.py eval` runs, is unchanged, and a question no expert answers ranks as it always did. Each kind has a deterministic cue and an expert [CODE _tools/kf_route.py#routed]: a count or list of articles (`how many articles ... in the intune domain`, a domain or `kb`, no other topic word) prints `rag.py audit`'s totals; a decision id (`D-...`) prints the row of the decisions ledger as `kbdecide list` reads it, with its `path:line`; `which sources disagree on <topic>` prints the whole `_conflicts.md` entry (a `###` heading with its bullets is one entry) with its source ids and their urls, which `search` cuts at a line; `what does the kb say about <topic>` that an open `_gaps.md` entry names prints `coverage: none`, `route: web`, `kb lacks:` and that entry; a source id with a citation word prints the files and lines that cite it (`src --cited`): a `cite` form (`cites`, `cited`, `citing`, `citation`) anywhere, or `mention`, `refer` or `name` right before the id (a `to`, `the`, `source`, `sources` or `id` may stand between, so `mention the source S123` and `refer to source id S123` route too), or `used by`, `mentioned in` right after it, so `Which articles mention S123?` routes there and `Which flag name does S123 give?` stays a lookup [CODE _tools/kf_route.py#CITE_CUE]. A ledger entry answers only when every topic word of the question (cue words left out, at least 3) is in the entry's title, and a gap entry must be open (tagged `UNK`, with no `Resolved`, `Superseded`, `Closed`, `Partly resolved`, `Mostly resolved` or `Narrowed` note line under it [CODE _tools/kf_route.py#OPEN_GAP]; the entry stays in the ledger, `audit --entries` lists it, and the research queue reads `Closed` as `Resolved` and `Partly resolved` as an open lead) and its title's words the question holds must weigh at least a third of the title's weight, a word weighing its inverse document frequency over the kb's units [CODE _tools/kf_route.py#_title_share]: a broad question whose words only fit inside a narrower entry's title (`what does the kb say about python.org Windows installers`) is a lookup the pack answers, one that names the entry's own missing fact (`the Authenticode signature of python.org Windows installers`) gets the entry. When more than one expert answers, their ranked lists are fused by reciprocal rank fusion with k = 60 [CODE _tools/kf_route.py#rrf]: only ranks are read, a key adds 1/(k + rank) for each list that holds it and nothing for a list that lacks it, and equal scores go to the best single rank, then to the `path:line` key. A routed answer prints at most 6 items, each ledger entry whole up to 1800 characters, then the sources' urls. `rag.py eval` fails a row whose question is routed (`failed=routed`), so every eval row stays a ranking row. No test asks `routed` a broad lookup the kb answers (a `what does the kb say about <article title>?` per article, the held-out and off-kb questions), nor each kind's own phrasings built from what the kb holds, since the live-kb tests were deleted: the only guard of a cue or ledger rule is `rag.py eval`, which refuses a row whose question is routed and runs at the landing of a change to `_tools/` or to any file under a kb root, so a cue looser or narrower than the eval rows show is found by a lookup that comes back routed or unrouted, not by a test.
- **`kb_ask.py` routing.** A question `mon_status.topic_of` maps to a topic by fixed cue words (a word that names the monitored thing beside a word that asks its state: sprints and progress, a session and running or stuck, `my computer` and load, cost and today, the query log and delivered, `coord` and claims; one question that names several gets `all`; a docs question that holds only one of the words, or opens with `how do I`, `how to`, `how does` or `what does`, gets none) is answered first by `kbmon.py --status TOPIC`, before any pack or model, and `--route` prints `kind=status topic=TOPIC`; no query log row is written for it [CODE _tools/mon_status.py#topic_of]. A question that asks which tool, command or script answers a need, by fixed cue words as well (`tool`, `command` or `script` beside `which`, `what` or `how do I find`; `what does` is none), is answered next by the lines of `kbtools.py` for the question, `--route` printing `kind=tools`, no model or query log row. An entry answers it by the question's content words (`kbtools.answering`): the cue words (`tool`, `command`, `script`, `line`, `find`, `show`, `list`, `print` and the like) never count, a tool is read by its name, summary and `Answers:` lines, a skill, an agent or a kb MCP tool by its name alone (their descriptions hold the names of the products the kb covers). The catalog answers alone when it holds three quarters of the question's content words (`HELD`); holding fewer, it answers only when the question's offline pack is not `good`, so a docs question that shares a word or two with a tool keeps its pack route; where no entry answers it, the steps below take it [CODE _tools/kb_ask.py#tools]. A question of a kind a tool decides (above) is answered by that tool, no model; a question of several parts is split first and each part routed in its pack. Numbered parts or several questions are split, one pack each (up to 6). `good` goes to Haiku with the packs and no tools (`claude -p` without user plugins and MCP servers), which replies `INSUFFICIENT: ...` when the facts are only related, escalating. A pack with a `route:` line plans by it (`--route` prints `kind=web` or `kind=split` with the route, `kb has:` and `kb lacks:` lines): `web` goes to one Sonnet researcher at low effort with the kb server alone (its cached `docs_search` and `docs_fetch`, so a repeated live-docs search within 7 days calls no docs server) and WebSearch/WebFetch, given the question, the `kb lacks:` line and up to three nearest article titles as leads to verify; its JSON result is printed, and an error result's errors go to stderr with exit 1. `split` runs two: the Haiku reader (no tools, JSON result) answers the `kb has:` part from the pack, and the researcher answers only the `kb lacks:` part without the pack; one answer is printed, the kb part and then the live part under "Live docs, not in the kb", and `-v` prints each run's cost and their sum. A reader's `INSUFFICIENT` sends the whole question to the researcher and sets `escalated`; the row's route stays `split`. A split pack without its `kb has:` or `kb lacks:` line is read whole and escalates as `good` does. In a several-part split each part goes where its own route sends it: a part with no `route:` line to the reader whole, a `web` part to the researcher whole (its `kb has:` words never reach the reader), a `split` part's `kb has:` words to the reader and its `kb lacks:` words to the researcher; `--route` lists each part's entries [CODE _tools/kb_ask.py#part_routes].
- **fact diff.** `factdiff.py detect` trusts a provider's signal only as far as `_tools/providers.csv` says it works (a 304 is always trusted, and a Learn page whose source file has no commit since the baseline day is `unchanged` by git with no request (a change that reaches the page through another file, as in `census.py check`, moves no commit of the page's own file and this signal does not see it); a 200 falls through to the version id, then the text hash; a wiki page or a repository home has its blob ids in the census's clone cache as version id and an issue or a discussion its latest timeline timestamp, and a baseline of the text alone is dated against that signal: nothing after its `detected_utc` is `unchanged`). `apply` dates a source only when the text it was compared with is no newer than the source's last confirmation, by the detection baseline or the page's own content date (`updated_at` on Learn), and a fact found word for word only when its anchor was placed no later than that; the rest waits for `review` or the census's own checks. A source held back because its baseline postdates its last confirmation starts its dating chain at its next confirmation (a `/kb-refresh` or the regular census); no separate run is needed. A confirmed source with no baseline gets one at `census.py confirm` from the cached document of that census, so a live page with no date is decided by its hash at the next one; `census.py baselines` lists the sources that have none. The cut-offs live in `_tools/factdiff.toml`, each with its measurement in `kb/_self/reports/fact-diff.md`.
- **fetch.** `--diff` exits 0 when nothing changed, 1 when a source changed and 2 when a fetch or the selection failed, as `diff` does. `--max-lines N` caps each diff, `--no-save` compares without moving the baseline, `--delay` sets the per-host pause (default 1.1 s). HTML is reduced to its main text first, so page chrome does not count as a change. Only pinned urls carry `artifact_sha256` (raw files at a commit or tag, release downloads); for live pages the hash taken at retrieval sits in `version_or_date`.
