# Maintaining the kb

Before any edit, research, refresh, census, commit or push, read the section "Conduct for changes" (`python3 _tools/selfdoc.py section maintaining "Conduct for changes"`), not this whole file, and the section "Skills that change the kb" only to pick a skill; `AGENTS.md` and the change router hook (`.claude/hooks/kb_change_router.py`) point there. A lookup needs only `AGENTS.md`, which every session and subagent loads; this file is read on demand, so it never costs a lookup anything. The other rules are split by job (see `kb/_self/README.md`): `kb/_self/content-rules.md` for what you write, `kb/_self/tools.md` for the commands, `kb/_self/git.md` for commits and pushes, `kb/_self/plugin.md` for the plugin.

Read the sections you need, not whole docs: `python3 _tools/selfdoc.py section DOC HEADING` prints one section of a `kb/_self` doc (`DOC` a name such as `maintaining` or `maintaining.md`, `HEADING` its text, case-insensitive). A skill names the git doc `git.md`, never a bare `git`: Claude Code's worktree isolation check reads a second `git` word in one Bash command as a second git call and refuses the command. Each skill names the sections it uses by heading, so renaming a heading means updating the skills that name it (`selfdoc.py section` exits 1 and lists the doc's headings when none matches). The gate and the commit rules are the section "Conduct for changes" below. The skills read only that section this way; every other rule comes from `python3 _tools/rag.py pack --root _self --set SKILL:STEP`, which prints a step's tested rule questions with the doc line that answers each, or `python3 _tools/rag.py pack --root _self "<question>"` for any other rule, and when its coverage is weak or none, `python3 _tools/kb_ask.py --root _self "<question>"` has a reader quote the answering lines from the sections. The same holds for code: before reading a tool's source, `python3 _tools/selfdoc.py map-tools FILE` lists its functions, classes and tests with `path:line`, so you read only the symbol you need (`kb/_self/tools.md`).

## Setup (first session in a fresh clone)

Run `/kb-setup` (Claude Code), or do the same by hand. In Claude Code on the web, `.claude/hooks/session_start.py` (a SessionStart hook in `.claude/settings.json`) already installs the commit hooks, registers the MCP servers, runs `check.py` and points the new session to the backlog, on every start, resume and `/clear`; in every clone a `SessionStart` hook prints the backlog's horizon, except after `/clear` (`kb/_self/backlog.md`). An async `SessionStart` hook, `backlog.py red-pipeline --hook`, files a bug for a red `main` pipeline and a second, `backlog.py intake --file --hook`, runs the offline intake detectors beside it; both write uncommitted draft or bug items and print nothing; `/kb-backlog` triage lists the drafts and commits those it keeps (`kb/_self/backlog.md`, Bug intake). Another, `kbgit.py publish --hook`, publishes the projection to the public home in a clone that names one and stays silent otherwise (`kb/_self/git.md`, Public home). The query log's `SessionStart` hooks start its distill and show its weekly digest once per ISO week, and its `SessionEnd` hook starts the distill (`kb/_self/querylog.md`, Distill and Reporting).

1. **Python 3.11+** as `python3` (the floor in `pyproject.toml`); on Windows `python` or `py -3`, plus Git for Windows, whose Git Bash runs the hooks. On Windows without Python, `_tools/install-python.ps1` installs the version pinned in it from python.org, and the uv pinned in it from uv's GitHub release (SHA-256 checked, into `%USERPROFILE%\.local\bin` on the user PATH; not pip), per user: it checks the host for conflicts first and stops without changing anything when it finds one (exit 3, `CONFLICT:` lines the agent quotes to the user), verifies the installer's SHA-256 and signature, and adds `python3.exe`, which the python.org installer lacks and the skills and permission rules call. Every hook (`.claude/settings.json`, the plugin, `.githooks/`) starts its script through `sh _tools/kbpy`, which finds the interpreter on each OS; the one exception is the raw-read hint on PowerShell calls, which runs with `shell: powershell` so it fires without Git Bash too (`kb/_self/tools.md`). Without Git Bash the other Claude Code hooks fail to start, since `sh` is missing. Nothing to install for the tools: they use the standard library only. The tests use pytest through uv (`pyproject.toml`, `uv.lock`) on the newest stable CPython, pinned in `.python-version` (3.14); `tests.py` installs both on first run. CI also runs them on 3.11 (`UV_PYTHON=3.11`) and on Windows (`kb/_self/git.md`). Moving the pin: edit `.python-version`, `uv lock`, the CI images, the version and SHA-256 values in `_tools/install-python.ps1` (its uv pin from the uv release's `.sha256` assets, `kb/public/python/uv-windows-install.md`; the Python pin from python.org's release API, named in the script), then the full gate.
2. **Checks pass on a clean tree:**
   - `python3 _tools/check.py` -> `errors=0`
   - `python3 _tools/fetch.py --offline` -> `mismatch=0 unknown=0`
   - `python3 _tools/tests.py` -> the suite passes, within its platform's `max_seconds` (`_tools/tests_ceiling.json`); the last run on the project's Windows host is in `kb/_self/reports/windows-run.md`
3. **MCP servers are in place.** `python3 _tools/kb_mcp.py --register-local` registers, at local scope (this machine and this clone only), the `kb` server and the three documentation servers of `.claude-plugin/it-ops-kb-docs/.mcp.json` (listed in `AGENTS.md`), and replaces a `kb` server that runs another clone's `kb_mcp.py`; `python3 _tools/kb_mcp.py --status` names the one the `kb` server runs on its `registered:` line. The root has no `.mcp.json` on purpose (`kb/_self/plugin.md`).
   - `claude mcp list` must show `kb` and the three docs servers `Connected`. Their tools keep the names `.claude/settings.json` allows (`mcp__kb`, `mcp__microsoft-learn__...`). The read-only kb commands it allows (`python3 _tools/rag.py *`, `backlog.py`, `check.py`, `kbid.py` (its reading forms, not `add`), `kbusage.py tree` and `errors`, `querylog.py show` and `export`, ...) are allowed for both shell tools, `Bash(...)` and `PowerShell(...)`: on Windows Claude Code runs commands through the PowerShell tool, and a `Bash(...)` rule never covers it (`public/claude/powershell-tool.md`). It also allows, for both shells, what the sprint skills run, in the narrow forms they use: `kbgit.py` `sync`, `check-trailers`, `fix --check`, `trailers` and the history commands (never `publish`), `selfdoc.py stale`, the git subcommands that read (`status`, `log`, `show`, `diff`, `add`, `merge-base`), `git commit` with `-m`, `-F` or `--amend`, `git rebase origin/main`, `--continue` and `--abort` (never `git rebase *` nor `git commit *`: the deny list also names `git rebase` with `--exec` or `-x`, which run any command, and `git commit` with `--no-verify` or `-n`, which skip the hooks), a plain `git fetch`, `worktree list` and `add` (no `git checkout` of a branch: workers start in worktrees, and the deny list still names `git checkout work/* *`, `orch/* *` and `-b * *`, so no checkout restores an older revision's settings), `git -C <path>` with `status`, `log`, `fetch` and `worktree add`, `glab mr view` (a merge goes through `backlog.py merge ID`, the item's own `code/<id>` only; no `glab mr merge` is allowed), the tools `Agent`, `Edit`, `Write` and `SendMessage`. No `kbdecide.py` form, `PushNotification` or `ToolSearch` is allowed: nothing that runs now needs them. It denies to every session's shells `kbgit.py publish`, `git push` (with or without `-C`), `git branch -D`, `git worktree remove`, `git checkout --` and a checkout of paths from another revision (`git checkout * -- *`): a deny is never prompted, so those run through the tools that do them as processes of their own (`land` removes a finished worker's worktree and deletes its landed branches, `sync --push` pushes) or by hand outside Claude Code. The lists hold no `kbgit.py`, `kbdecide.py`, git or glab rule, whole shell or tool rule beyond these.
   - `Failed`: check network or proxy access to the url; the servers need no credentials.
   - Do not load the plugin in a clone (`--plugin-dir .`): the project skills and agents and the local servers would load a second time under plugin names.
   - Other agents (not Claude Code): register the same three urls as streamable-HTTP MCP servers in your client.
   - Optional, per user: GitHub's read-only repository server needs a personal token. Add it at user scope, never in a repo file:
     `claude mcp add --scope user --transport http github-repos-ro https://api.githubcopilot.com/mcp/x/repos/readonly --header "Authorization: Bearer $GITHUB_PAT"`
4. **Git hooks:** `python3 _tools/kbgit.py install-hooks`, once per clone: KB-* trailers on commits, and the gate on a plain `git push` (`kb/_self/git.md`). In a clone that also has a public remote (a public GitHub copy), name it once: `git config kb.publishRemote <remote>`; its `main` then moves only through `python3 _tools/kbgit.py publish`, which leaves out `kb/_querylog/` and any `_logs.csv`, refuses a `_private` or `_cache` path, and a push carrying the store or a `_logs.csv` there is refused. The integration remote is `origin` unless `git config kb.integrationRemote <remote>` names another; it and the publish remote are set the same way, in the clone only. On the public GitHub repository set the Actions variable `KB_PUBLIC_HOME` to `true` (`kb/_self/git.md`, Public home). A production clone with no public remote skips both.
5. **Query log:** logging, fixes, gap entries and pushes are automatic by default (mode `auto`), and research is off. `/kb-setup` says what that records in the repository and sends to the API, asks whether to keep it, and writes the answer to `_private/querylog.json` (`kb/_self/querylog.md`, Configuration).
6. **Do not** run `python3 _tools/fetch.py --diff` over the whole kb as part of setup: it is a long network job that writes `_fetch_state.csv`. A whole-kb baseline is the maintainer's decision; a targeted `--diff` from `/kb-refresh` is committed with that refresh.
7. **The sprint orchestrator checks all of this at every pass.** The first step of each pass of `/kb-sprint run` is `python3 _tools/backlog.py selfcheck` (read only, capped): whether the allow rules in `.claude/settings.json` cover the commands the skills run, the commit hooks of step 4 and the plugin are installed, the host is within its load and lock limits, no claim is stale, no orphan runs in a checkout of the clone and `main` is not red, each failure with the remedy the kb-sprint skill names (Self-check); the orchestrator acts on a failure before it dispatches work, or records why it cannot (`kb/_self/backlog.md`, Self-check).

## Skills that change the kb

**A request to change the kb goes through one of these skills (`.claude/skills/`), never freehand edits.** Claude invokes them on its own: they are model-invocable, with descriptions that start with their trigger ("Use when ..."), and all but three stay out of the plugin, so their descriptions cost nothing in host projects. A person can still type them. Each names the `kb/_self/` files it relies on. The three that are in the plugin, `/kb-sprint`, `/kb-item` and `/kb-backlog`, and the `kb-worker` agent exist once, as the plugin's `skills/sprint/SKILL.md`, `skills/item/SKILL.md`, `skills/backlog/SKILL.md` and `agents/worker.md`: `.claude/skills/kb-sprint/SKILL.md`, `.claude/skills/kb-item/SKILL.md`, `.claude/skills/kb-backlog/SKILL.md` and `.claude/agents/kb-worker.md` are relative symlinks to them, so the `kb-*` names serve a clone, a worker's worktree and a session without the plugin installed; edit the plugin's file, never the link (`kb/_self/plugin.md`, section 1).

The routing is also deterministic: `.claude/hooks/kb_change_router.py`, a UserPromptSubmit hook in `.claude/settings.json` (never in the plugin), adds one line of context to a prompt that asks for a change (add, update, fix, refresh, research, commit, push, ...), naming the likely skill from its words plus the rule below the table. A prompt whose words name no change skill gets nothing, and a skill set it has already named in the session (a marker per `session_id` under `_cache/change_router/`) is not named again, so a follow-up such as "commit it" adds no repeat context. A `SessionStart` hook with matcher `compact|clear` (`kb_change_router.py --reset`, in `.claude/settings.json` too) removes that session's marker, since a compaction or clear drops the earlier routing line from the conversation: the next change request is routed again. It prints nothing and exits 0 whatever it reads, and a missing marker or directory is a no-op. Questions, `kb:` prompts, slash commands and harness messages (a subagent's report, a task notification) pass unchanged, and so does a malformed event (a prompt that is not a string, a field that is missing or of another type, JSON that is not an object): the hook stays silent and exits 0, never blocking a prompt. `python3 .claude/hooks/kb_change_router.py --test "<prompt>"` shows what it adds. A new change skill needs a route there.

| skill | does | docs its sets and questions draw on |
|---|---|---|
| `/kb-setup` | the setup above, with a pass/fail report | this file |
| `/kb-research <question>` / `--queue [N]` | research a question in the context of the topics the kb has, then extend them; `--queue` works the top N gaps of `querylog.py queue` the same way and closes each `_gaps.md` entry (`querylog.py close`) | content rules, tools, git, query log |

Work is planned and tracked in the backlog (`kb/_self/backlog.md`); a commit that works on an item carries `KB-Work: <id>`. Any change ends with `/kb-verify`, then `python3 _tools/kbgit.py sync --push` (`/kb-git-sync` when it stops; content reaches `main`, code goes as a `code/<id>` merge request, `kb/_self/git.md`); a change to tools, skills, hooks, the plugin or a rule also runs `/kb-self`. The read-only skills (`/kb-lookup`, `/kb-review-workspace`, `/kb-gap`) follow `AGENTS.md` and the plugin rules.

## Conduct for changes

- Do not edit files listed in `_artifacts.csv` by hand; they are pinned by sha256 (`fetch.py --refresh` rewrites them).
- **Real misses feed the eval set, every time.** A failed real-world lookup (a `/it-ops-kb:kb-gap` report, a wrong or `weak`/`none` `kb:` answer, a pack a session had to redo) is re-run with `python3 _tools/rag.py pack "<question>"`, worded as asked (placeholders for private names):
  - the kb has the answer but the pack misses its article or gives a false verdict: a `kb/public/_retrieval/lookup_eval.csv` row (`kb/_self/content-rules.md`, Ledgers); when the miss is paraphrase, expand only that article (`kb/_self/doc2query.md`);
  - the kb lacks the fact: a `_gaps.md` entry, then `/kb-research`;
  - a row that fails only through the false `good` no verdict rule separates (`kb/_self/tools.md`, the `check:` line) stays out of the file, which has no expected-failure column; name it in the commit instead;
  - the exception: a failing row of the held-out file `kb/public/_retrieval/lookup_heldout.csv` (`kb/_self/tools.md`, the answer-rate fitness test) stays in that file and is never moved into `lookup_eval.csv`, added there reworded, or expanded on with doc2query, so the file keeps measuring what tuning has not seen; a missing fact it shows may still go to `_gaps.md` and `/kb-research`, since its questions were researched before.
- **Open ledger entries are state, not work items.** Real disagreements stay in `_conflicts.md` until a source settles them, and an entry that needs a lab, a login or unpublished information carries a dated note of what was tried and what it still needs; `python3 _tools/rag.py audit --entries` lists them per article.
- **`AGENTS.md` has a 4 KB cap** (4096 bytes, tested) and fills nearly all of it: an addition needs a cut elsewhere (`wc -c AGENTS.md`). Maintainer detail goes in `kb/_self/`, never there.
- **Python in `_tools/` follows `kb/_self/code.md`:** standard library only, portability, git isolation in tests, deterministic and converging output, exit codes, one planted failure per gate within the test ceiling, flat prefixed modules behind a CLI facade, import direction. Read it before adding or splitting a tool or a test.
- A change to `_tools/`, `.claude/`, `.claude-plugin/`, `.githooks/` or a rule changes what `kb/_self/` says: run `python3 _tools/selfdoc.py stale --since @{upstream}` and update the docs it lists in the same commit (`/kb-self`). `Self-Reviewed:` names only docs read and found still correct, never a way past the gate; a doc that needs an edit outside a backlog item's `touches` stops the item's work with a report.
- **The gate is `python3 _tools/kbgit.py sync --push`** (`kb/_self/git.md`): it runs only what the changed paths can break, the checks each path needs and `tests.py --changed origin/main` (no tests for backlog items or the query log store, the suite without the git scenarios for kb content, the whole suite for any other path), so a content-only change gates in seconds. Do not run the suite before it as a habit:
  - `/kb-verify` reports on a change (contract lint, the docs check, the checks the paths need) before a commit;
  - `python3 _tools/tests.py` runs the whole suite while you work; `tests.py -k NAME` or `tests.py _tools/test_x.py` runs a selection, and one that collects no test exits 2 naming it, before any worker starts (`kb/_self/tools.md`); every run first fails on a compile warning (an invalid escape) in any `_tools/*.py` (`kb/_self/code.md`); the same suite runs at a landing's `done` checks, in a sprint review story and in CI;
  - tests are few and under the ceiling in `_tools/tests_ceiling.json`, and a bug gets a retrospective finding, not a test (`kb/_self/code.md`, Checks and their tests);
  - after reworded or removed facts, `python3 _tools/doc2query.py stale` (the gate runs it for article changes).
- `tests.py` scans tracked files only: stage new files (`git add`) before running it, or they pass unchecked. A passing run is recorded by the tree of the index and the tracked files' changes, so the sync gate reuses it for the same selection on the same tree instead of running pytest again (`tests.py --no-reuse` forces a run); an untracked `.py` file under `_tools/` leaves a run unrecorded and unreused, and any other untracked non-ignored file is keyed by its name and content, so an edit to it makes the next run a new one (`kb/_self/tools.md`).
- Every `tests.py` run records an ops row `test.run` (`kb/_self/tools.md`) in the query log's spool: the suite's times are read from those rows. A run a backlog check or repro makes records it in the clone's real spool too (`bl_base.check_env` names the clone's query log directory in `KB_TEST_RUN_HOME`, which `tests.py` writes the row to), so the digest counts it; every other capture of the check goes to its temporary query log home, which is removed after the run (`kb/_self/backlog.md`).
- A whole-suite `tests.py` run takes a host-wide lock and waits for another such run on the same host, naming its pid and clone (`kb/_self/tools.md`): sessions sharing a host, a sprint worker too, need no message to avoid overlapping runs. A selection takes no lock.
- Commit messages: conventional prefix (`docs(kb):`, `fix(kb):`, `feat(kb):`, `chore:`), imperative, body explaining why; your own trailers (e.g. `Co-Authored-By`) in the last paragraph, and the hook appends the KB-* ones after them. Commit only when asked. Push with `python3 _tools/kbgit.py sync --push` (`kb/_self/git.md`).
