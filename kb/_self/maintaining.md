# Maintaining the kb

Before any edit, research, refresh, census, commit or push, read the section "Conduct for changes" (`python3 _tools/selfdoc.py section maintaining "Conduct for changes"`), not this whole file, and the section "Skills that change the kb" only to pick a skill; `AGENTS.md` and the change router hook (`.claude/hooks/kb_change_router.py`) point there. A lookup needs only `AGENTS.md`, which every session and subagent loads; this file is read on demand, so it never costs a lookup anything. The other rules are split by job (see `kb/_self/README.md`): `kb/_self/content-rules.md` for what you write, `kb/_self/tools.md` for the commands, `kb/_self/git.md` for commits and pushes, `kb/_self/plugin.md` for the plugin.

Read the sections you need, not whole docs: `python3 _tools/selfdoc.py section DOC HEADING` prints one section of a `kb/_self` doc (`DOC` a name such as `maintaining` or `maintaining.md`, `HEADING` its text, case-insensitive). A skill names the git doc `git.md`, never a bare `git`: Claude Code's worktree isolation check reads a second `git` word in one Bash command as a second git call and refuses the command. Each skill names the sections it uses by heading, so renaming a heading means updating the skills that name it (`selfdoc.py section` exits 1 and lists the doc's headings when none matches). The gate and the commit rules are the section "Conduct for changes" below. The skills read only that section this way; every other rule comes from `python3 _tools/rag.py pack --root _self --set SKILL:STEP`, which prints a step's tested rule questions with the doc line that answers each, or `python3 _tools/rag.py pack --root _self "<question>"` for any other rule, and when its coverage is weak or none, `python3 _tools/kb_ask.py --root _self "<question>"` has a reader quote the answering lines from the sections. The same holds for code: before reading a tool's source, `python3 _tools/selfdoc.py map-tools FILE` lists its functions, classes and tests with `path:line`, so you read only the symbol you need (`kb/_self/tools.md`).

## Setup (first session in a fresh clone)

Run `/kb-setup` (Claude Code), or do the same by hand. In Claude Code on the web, `.claude/hooks/session_start.py` (a SessionStart hook in `.claude/settings.json`) already installs the commit hooks, registers the MCP servers, runs `check.py` and points the new session to the backlog, on every start, resume and `/clear` (in any other clone it prints only one line, `backlog.py tidy --report`: how many recorded worktrees, branches, bench sandboxes and scratch directories `tidy` would remove, and the bytes, with nothing removed); in every clone a `SessionStart` hook prints the backlog's horizon, except after `/clear` (`kb/_self/backlog.md`). An async `SessionStart` hook, `backlog.py red-pipeline --hook`, files a bug for a red `main` pipeline and a second, `backlog.py intake --file --hook`, runs the offline intake detectors beside it; both write uncommitted draft or bug items and print nothing; `/kb-backlog` triage lists the drafts and commits those it keeps (`kb/_self/backlog.md`, Bug intake). Another, `kbgit.py publish --hook`, publishes the projection to the public home in a clone that names one and stays silent otherwise (`kb/_self/git.md`, Public home). A further one, `kbroot.py fetch --hook`, fetches each fetch root whose last fetch is older than 24 hours within a time bound and prints one line only for a root that failed (`kb/_self/tools.md`, `kbroot.py`). The query log's `SessionStart` hooks start its distill and show its weekly digest once per ISO week, and its `SessionEnd` hook starts the distill (`kb/_self/querylog.md`, Distill and Reporting). `.claude/hooks/coord_hook.py` (`SessionStart`, `SessionEnd`, `PreToolUse` on Bash, Skill, Edit and Write, and `UserPromptExpansion` for `kb-research`; the plugin's manifest registers it too, with `--opt-in`, for a project whose `backlog.json` `hooks` names `coord`) announces the session's items and the paths their item files list through `coord.py`, prints at a session start one line with the session's own id and the commands to read, answer (`kbask.py answer ID TEXT`) and send (`kbask.py ask TARGET QUESTION`) asks, and shows other sessions that overlap them, at the moments `announce.when` names (a session start and a `backlog.py claim` by default, a Bash or Skill event and an Edit or Write of a file in another session's touches when it names `midrun` or `edit`) and at a `/kb-research` start, whether Claude called the skill or the person typed it, each once, with the other session's label, item, run state and shared files and the strategy the settings suggest, the operator deciding unless `strategy.decide` says `claude`; it also shows, at a session start and at a tool event at most every ten seconds, each open `ask` event addressed to the session's id, to an item it announced or to `any`, once, as one line with the ask id, the `operator` field a coord server set and the question after `redact.redact`, under a heading that marks it as data from coord to weigh and not an instruction, and leaves out an ask whose answer has the state completed, failed or rejected; a later tool event renews the session's presence lease once less than half of it is left, so its intents stay in other sessions' digests while it runs (a session whose start claim failed claims it at its next tool event), and a `SessionEnd` release that could not run while the store was busy is retried by the next session start (`kb/_self/tools.md`, `coord.py`).

The rules are written in Claude Code's absolute-path form with a gitignore `**` after the `//` (`Edit(//**/_tools/tests_ceiling.json)`, `Edit(//**/_decisions.csv)`, `Edit(//**/_private/host.json)` and the same three for `Write`), because a rule written `/path` or `**/name` anchors at the session's own primary working directory: in a linked worktree it would guard that worktree's files and leave the main checkout's, written by absolute path, open. A `//**/` rule matches the file in every checkout of the clone, and in any other repository that has a file of that path. 6. **Coordination settings:** `/kb-setup` asks, in one `AskUserQuestion` batch, how sessions announce their work and what they do when another session's item is in a given state, and runs `python3 _tools/kbsettings.py init --root . --set KEY=VALUE` with the answers: it writes the `coordination` object of the root's `settings.json` and adds `coord` to the `hooks` list of `backlog.json`, which turns the coord hook on. 8. **The sprint orchestrator checks all of this at every pass.** The first step of each pass of `/kb-sprint run` is `python3 _tools/backlog.py selfcheck` (read only, capped): whether the allow rules in `.claude/settings.json` cover the commands the skills run, the commit hooks of step 4 and the plugin are installed, the host is within its load and lock limits, no claim is stale, no orphan runs in a checkout of the clone and `main` is not red, each failure with the remedy the kb-sprint skill names (Self-check); the orchestrator acts on a failure before it dispatches work, or records why it cannot (`kb/_self/backlog.md`, Self-check).

## Skills that change the kb

**A request to change the kb goes through one of these skills (`.claude/skills/`), never freehand edits.** Claude invokes them on its own: they are model-invocable, with descriptions that start with their trigger ("Use when ..."), and all but three stay out of the plugin, so their descriptions cost nothing in host projects. A person can still type them. Each names the `kb/_self/` files it relies on. The three that are in the plugin, `/kb-sprint`, `/kb-item` and `/kb-backlog`, and the `kb-worker` agent exist once, as the plugin's `skills/sprint/SKILL.md`, `skills/item/SKILL.md`, `skills/backlog/SKILL.md` and `agents/worker.md`: `.claude/skills/kb-sprint/SKILL.md`, `.claude/skills/kb-item/SKILL.md`, `.claude/skills/kb-backlog/SKILL.md` and `.claude/agents/kb-worker.md` are relative symlinks to them, so the `kb-*` names serve a clone, a worker's worktree and a session without the plugin installed; edit the plugin's file, never the link (`kb/_self/plugin.md`, section 1).

The routing is also deterministic: `.claude/hooks/kb_change_router.py`, a UserPromptSubmit hook in `.claude/settings.json` (never in the plugin), adds one line of context to a prompt that asks for a change (add, update, fix, refresh, research, commit, push, ...), naming the likely skill from its words plus the rule below the table. A prompt whose words name no change skill gets nothing, and a skill set it has already named in the session (a marker per `session_id` under `_cache/change_router/`) is not named again, so a follow-up such as "commit it" adds no repeat context. A `SessionStart` hook with matcher `compact|clear` (`kb_change_router.py --reset`, in `.claude/settings.json` too) removes that session's marker, since a compaction or clear drops the earlier routing line from the conversation: the next change request is routed again. It prints nothing and exits 0 whatever it reads, and a missing marker or directory is a no-op. Questions, `kb:` prompts, slash commands and harness messages (a subagent's report, a task notification) pass unchanged, and so does a malformed event (a prompt that is not a string, a field that is missing or of another type, JSON that is not an object): the hook stays silent and exits 0, never blocking a prompt. `python3 .claude/hooks/kb_change_router.py --test "<prompt>"` shows what it adds. A new change skill needs a route there.

## Conduct for changes

- Do not edit files listed in `_artifacts.csv` by hand; they are pinned by sha256 (`fetch.py --refresh` rewrites them).
- **Real misses feed the eval set, every time.** A failed real-world lookup (a `/it-ops-kb:kb-gap` report, a wrong or `weak`/`none` `kb:` answer, a pack a session had to redo) is re-run with `python3 _tools/rag.py pack "<question>"`, worded as asked (placeholders for private names):
  - the kb has the answer but the pack misses its article or gives a false verdict: a `kb/public/_retrieval/lookup_eval.csv` row (`kb/_self/content-rules.md`, Ledgers); when the miss is paraphrase, expand only that article (`kb/_self/doc2query.md`);
  - the kb lacks the fact: a `_gaps.md` entry, then `/kb-research`;
  - a row that fails only through the false `good` no verdict rule separates (`kb/_self/tools.md`, the `check:` line) stays out of the file, which has no expected-failure column; name it in the commit instead;
  - the exception: a failing row of the held-out file `kb/public/_retrieval/lookup_heldout.csv` (`kb/_self/tools.md`, the answer-rate fitness test) or of the repro benchmark's frozen questions `kb/public/_retrieval/repro_bench.csv` stays in that file and is never moved into `lookup_eval.csv`, added there reworded, or expanded on with doc2query, so the file keeps measuring what tuning has not seen; a missing fact it shows may still go to `_gaps.md` and `/kb-research`, since its questions were researched before.
- **Open ledger entries are state, not work items.** Real disagreements stay in `_conflicts.md` until a source settles them, and an entry that needs a lab, a login or unpublished information carries a dated note of what was tried and what it still needs; `python3 _tools/rag.py audit --entries` lists them per article.
- **`AGENTS.md` has a 4 KB cap** (4096 bytes, tested) and fills nearly all of it: an addition needs a cut elsewhere (`wc -c AGENTS.md`). Maintainer detail goes in `kb/_self/`, never there (what `audit` prints per article and the hook that points raw article reads at the lookup tools are in `kb/_self/tools.md`).
- **Python in `_tools/` follows `kb/_self/code.md`:** standard library only, portability, git isolation in tests, deterministic and converging output, exit codes, a test only for a critical component and one planted failure per such gate within the test ceiling, flat prefixed modules behind a CLI facade, import direction. Read it before adding or splitting a tool or a test.
- A change to `_tools/`, `.claude/`, `.claude-plugin/`, `.githooks/` or a rule changes what `kb/_self/` says: run `python3 _tools/selfdoc.py stale --since @{upstream}` and update the docs it lists in the same commit (`/kb-self`). `Self-Reviewed:` names only docs read and found still correct, never a way past the gate; a doc that needs an edit outside a backlog item's `touches` stops the item's work with a report.
- **The gate is `python3 _tools/kbgit.py sync --push`** (`kb/_self/git.md`): it runs only what the changed paths can break, the checks each path needs and `tests.py --changed origin/main` (no tests for backlog items or the query log store, the suite without the git scenarios for kb content, the whole suite for any other path), so a content-only change gates in seconds. Do not run the suite before it as a habit:
  - `/kb-verify` reports on a change (contract lint, the docs check, the checks the paths need) before a commit;
  - `python3 _tools/tests.py` runs the whole suite while you work; `tests.py -k NAME` or `tests.py _tools/test_x.py` runs a selection, and one that collects no test exits 2 naming it, before any worker starts (`kb/_self/tools.md`); every run first fails on a compile warning (an invalid escape) in any `_tools/*.py` (`kb/_self/code.md`); the same suite runs at a landing's `done` checks, in a sprint review story and in CI;
  - a change gets no test by default and a test exists only for a critical component (leak and untrusted-code guards, the push and publish gates, operator-only authority, formats another tool parses); the tests are few and under the ceiling in `_tools/tests_ceiling.json`, and a bug gets its repro, user feedback and a retrospective finding, not a test (`kb/_self/code.md`, Checks and their tests);
  - after reworded or removed facts, `python3 _tools/doc2query.py stale` (the gate runs it for article changes).
- `tests.py` scans tracked files only: stage new files (`git add`) before running it, or they pass unchecked. A passing run is recorded by the tree of the index and the tracked files' changes, so the sync gate reuses it for the same selection on the same tree instead of running pytest again (`tests.py --no-reuse` forces a run); an untracked `.py` file under `_tools/` leaves a run unrecorded and unreused, and any other untracked non-ignored file is keyed by its name and content, so an edit to it makes the next run a new one (`kb/_self/tools.md`).
- Every `tests.py` run records an ops row `test.run` (`kb/_self/tools.md`) in the query log's spool: the suite's times are read from those rows. A run a backlog check or repro makes records it in the clone's real spool too (`bl_base.check_env` names the clone's query log directory in `KB_TEST_RUN_HOME`, which `tests.py` writes the row to), so the digest counts it; every other capture of the check goes to its temporary query log home, which is removed after the run (`kb/_self/backlog.md`).
- A whole-suite `tests.py` run takes a host-wide lock and waits for another such run on the same host, naming its pid and clone (`kb/_self/tools.md`): sessions sharing a host, a sprint worker too, need no message to avoid overlapping runs. A selection takes no lock.
- Commit messages: conventional prefix (`docs(kb):`, `fix(kb):`, `feat(kb):`, `chore:`), imperative, body explaining why; your own trailers (e.g. `Co-Authored-By`) in the last paragraph, and the hook appends the KB-* ones after them. Commit only when asked. Push with `python3 _tools/kbgit.py sync --push` (`kb/_self/git.md`).

## The test runner

Commands: `python3 _tools/tests.py [-k NAME] [PATH ...] [--changed [REV]] [--ceiling] [--no-reuse] [--write-lint-baseline]`

- What CI (`.gitlab-ci.yml`) runs: every `_tools/test_*.py` file, in parallel, with pytest and pytest-xdist through `uv run --frozen`; `-k NAME` runs the tests whose name matches and `PATH` only those test files (or `::` nodes); a run with arguments (a `-k`, named files, a `--changed` run given more) first collects its selection in one pytest with no workers (`tests.selected_ids`), and one that collects no test exits 2 before any worker starts, with one line naming the selection as given and the files it looked in (`tests.empty_selection_line`, `collects no test`), and records its `test.run` row with exit 2, selected 0 and workers 0: pytest's exit 5 is never returned, a run that still ends with it being said the same way with exit 2; before pytest, every run but `--ceiling` and `--write-lint-baseline` (a selection and any `--changed` run, the one that needs no tests too) compiles each `_tools/*.py` in-process from its source text, writing no `.pyc`, and exits 1 naming each file, line and category whose compile warns or fails, such as an invalid escape sequence (a `SyntaxWarning`, a `DeprecationWarning` before Python 3.12; `tests.compile_warnings`, which records the warnings rather than raising them, since a raised `SyntaxWarning` becomes a `SyntaxError`), so a file no test imports, or one a cached `.pyc` hides, cannot pass.
- `--changed [REV]` runs what a change from REV's merge base (default `HEAD`: the working tree) needs: nothing when only backlog items (`kb/_self/backlog/`) or the query log store (`kb/_querylog/`) changed, the suite without the `git` scenarios when only kb content changed, the whole suite for any other path (the sync gate runs `--changed` against the integration `main`); `KB_TESTS_FAST=1` leaves out the `git` scenarios (`-m "not git"`); each pytest run is keyed (`tests.run_key`) by its selection (the pytest arguments that choose its tests, paths relative to the clone, without the worker and report options: with the tree they decide the collected ids, so no collection is run for the key), the tree of the index plus the tracked files' working-tree changes (`tests.work_tree`: `git add -u` and `git write-tree` with `GIT_INDEX_FILE` naming a temporary copy of the index, never the person's own; `kb/public/gitlab/git-test-repositories.md`) and the version of the Python that runs pytest (`.venv/pyvenv.cfg` under uv, else this interpreter's); an untracked `.py` file under `_tools/` leaves a run without a key, so nothing is reused or recorded for it, and the name and content hash of every other untracked non-ignored file a git scenario copies (`conftest.seed_files`' set: `tests.untracked_digest`) are in the key, so an edit to one, or its removal, gives a new key; a run that exits 0 records its key and UTC time in `_cache/tests/results.json` (the newest 200 kept), a failing one records none and drops its key; a run with `KB_TESTS_FAST=1` (the sync gate's) whose key the file holds as passed prints `reused: <key> from <UTC time>`, records its `test.run` row with `reused` true and exits 0 without starting pytest, and `--no-reuse` forces the run.
- `--ceiling` collects the test ids without running them and compares ids and files with the ceiling; `--write-lint-baseline` accepts current lint errors as known debt; leak-scan exceptions in `_tools/tests_allowlist.txt`; the ceiling is `_tools/tests_ceiling.json` (`max_ids`, `max_files`, `max_seconds` per platform, and `decision`, the id of the active operator decision in `kb/_self/_decisions.csv` whose text holds the file's own numbers): every run checks the file count and the decision, a full run also fails when it ran more ids than `max_ids` or took longer than `max_seconds`, and on a CI runner `KB_TEST_TIMEOUT_FACTOR` (at least 1) multiplies the seconds, as the clone's profile does (`usual`, or `busy`: 15 times each platform's `max_seconds` in that clone only; `profile` in `_private/host.json`, which `tests.py --set-profile usual|busy` writes from the operator's own terminal and refuses in an agent session or an IDE's integrated terminal, naming the standalone-terminal route (`bl_authority.IDE_ROUTE`), `tests.py --show-profile` prints; `/kb-setup` asks for it before it runs the suite, and a refused run names the profile); a number changes only with the operator's recorded answer, and a new test id needs room under `max_ids`; each run appends one ops row `test.run` to the query log's spool (`tests.run_fields`, `record_run`): mode, selected and total test files, workers, milliseconds, exit, passed, failed and skipped counts, the slowest files, every file's time for a full run, the names of the test files that failed and `reused` for a reused run, never test ids; best effort (nothing when capture is off, nothing from a run inside a test, no exception out of `tests.py`); a run that a backlog check or repro makes (`bl_base.run_check`) writes its row into the clone's real spool, the query log directory `KB_TEST_RUN_HOME` names (`bl_base.check_env`, set unless capture is off), every other capture of that check staying in its isolated home; a full run and a `--changed` run first take the host lock (`host_lock`: an `O_EXCL` file `kb-tests.lock` in `KB_HOST_LOCK_DIR`, default `/tmp` or the Public profile on Windows, holding pid, clone and start time; a holder whose pid no longer runs is cleared, by one waiter only, a live one is named and waited for, and an empty or unreadable file is left alone for `KB_HOST_LOCK_GRACE` seconds (default 10), its holder having not written the record yet; none for `-k`, a run of named test files, `-n 1` or a run inside a test); with no `-n` the workers are `KB_TEST_WORKERS` when set, else the CPUs divided among this run and the other live `tests.py` runs (each holds a `kb-tests-run.PID` file beside the lock; `tests.default_workers`), at most `DEFAULT_WORKER_CAP` and at least 1, and an explicit `-n` wins.
- `tests.py` scans tracked files only, so stage new files before a run.
