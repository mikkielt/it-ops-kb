# Runtimes that run an agent unattended, on a schedule

## Summary
Claude Code offers three unattended shapes: `claude -p` (headless CLI, runs wherever you invoke it),
CI integrations (GitHub Actions, GitLab CI/CD) that run inside the platform's own runners on an event
or `schedule:` trigger, and "routines" (Anthropic-hosted cloud cron/API/GitHub-event agents, research
preview since April 2026). GitHub's Copilot coding agent and GitLab's Duo Agent Platform are the
non-Anthropic equivalents: both push only to prefixed branches and return a pull/merge request rather
than writing to the target branch directly. None of these give a scheduled agent write access to a
protected branch without a review step.

## Facts
- `claude -p "<prompt>"` runs Claude Code non-interactively; exit code 0 on success, non-zero on failure; `--output-format text|json|stream-json` controls how the result returns, with `json` including `total_cost_usd` and a per-model cost breakdown. [DOC S1800]
- `--allowedTools` auto-approves named tools (permission-rule syntax, e.g. `Bash(git diff *)`); `--max-turns` (via `claude_args` in CI, or directly on the CLI) caps iterations; permission modes for `-p` include `auto` (classifier reviews actions), `dontAsk` (denies everything that would otherwise prompt, "useful for locked-down CI runs"), and `acceptEdits` (auto-approves file writes and common filesystem commands). The default starting mode for `-p` is Manual on every plan, so an unattended run must pass a mode or `--permission-prompts none` explicitly. [DOC S1800]
- `--permission-prompts none` denies (rather than blocks waiting on) anything that would need a human answer — used "for scheduled jobs" with nobody to answer a permission prompt; `AskUserQuestion` becomes uncallable and any un-answered MCP elicitation is cancelled. [DOC S1800]
- `--bare` skips hooks, skills, custom commands, subagents, plugins, MCP servers, auto memory and CLAUDE.md for a reproducible run; Anthropic calls it "the recommended mode for scripted and SDK calls" and says it "will become the default for `-p` in a future release." In bare mode Claude Code never reads OAuth/keychain credentials — it needs `ANTHROPIC_API_KEY` (or Bedrock/Vertex/Foundry provider credentials) set explicitly. [DOC S1800]
- Piped stdin is capped at 10 MB in `-p` mode; larger input must go to a file referenced by path. [DOC S1800]
- Claude Code GitHub Actions (`anthropics/claude-code-action@v1`) authenticates with `ANTHROPIC_API_KEY`, a `CLAUDE_CODE_OAUTH_TOKEN` (subscription token from `claude setup-token`), or workload-identity federation (`anthropic_federation_rule_id` + `anthropic_organization_id` exchanging the workflow's GitHub OIDC token for Claude API access, no static secret stored). It can also route through Amazon Bedrock, Google Cloud's Agent Platform, or Microsoft Foundry via OIDC, again without a static cloud credential. [DOC S1801]
- The GitHub Action has two modes: interactive (`@claude` mention in a PR/issue comment or review, or issue title/body — no `prompt` input) and automation (a `prompt` input, runs on any GitHub event including `schedule:`, subject only to the actor checks). Automation-mode results default to the workflow run log; the action posts to the PR/issue only when the prompt directs it and grants a posting tool, e.g. `--comment` with the inline-comment MCP tool. [DOC S1801]
- Before starting, the GitHub Action checks (a) the triggering user has write access to the repo (skipped for actor-less events like `schedule`) and (b) the actor is human, not a bot, unless listed in `allowed_bots` — this second check also applies to scheduled runs, which GitHub attributes to whichever user last edited the workflow's cron line. [DOC S1801]
- GitHub scheduled workflows run only from the default branch, and GitHub auto-disables a schedule after 60 days of no repository activity on public repos. [DOC S1801]
- Cost control knobs named by the vendor: `--max-turns` in `claude_args`, workflow-level job timeouts, GitHub's concurrency controls to cap parallel runs, and keeping `CLAUDE.md` concise since it is read on every run. Two cost axes: GitHub Actions minutes (GitHub-billed) and API tokens (Anthropic-billed, or subscription usage under an OAuth token). [DOC S1801]
- Claude Code GitLab CI/CD is GitLab-maintained and in beta; setup is one `.gitlab-ci.yml` job plus a masked `ANTHROPIC_API_KEY` CI/CD variable, or OIDC-based role assumption for Amazon Bedrock/Google Cloud's Agent Platform (no static cloud keys). Example job invokes `claude -p "$AI_FLOW_INPUT" --permission-mode acceptEdits --allowedTools "Bash Read Edit Write mcp__gitlab"`. [DOC S1802]
- GitLab's own docs describe the flow as: an event (e.g. an `@claude` mention) triggers a pipeline job that runs Claude Code sandboxed in a container with workspace-scoped write permissions; every change "flows through an MR so reviewers see the diff and approvals still apply." [DOC S1802]
- Claude Code "routines" (research preview, shipped April 2026, Pro/Max/Team/Enterprise) are a saved prompt + repositories + connectors, run on Anthropic-managed cloud infrastructure (or a self-hosted environment) on a **schedule** (hourly/nightly/weekly presets, or a custom cron edited via `/schedule update`; minimum interval one hour), an **API** trigger (POST to a per-routine URL with a bearer token, `experimental-cc-routine-2026-04-01` beta header), or a **GitHub event** trigger (`pull_request.*`, `release.*`, with field filters). [DOC S1803]
- A routine run is a full cloud session with **no permission-mode picker** — "the session runs shell commands, uses skills..., and calls any connectors you include, all without stopping for approval" apart from some artifact-publish actions. Everything it does through the user's linked GitHub/connector identity appears as that user (commits, PRs, Slack messages). [DOC S1803]
- Routine output returns as a new Claude Code cloud session per firing (GitHub triggers never reuse a session across events); a human opens the session to review the diff and "create a pull request." Claude pushes only to `claude/`-prefixed branches by default; pushing elsewhere is rejected if the branch is protected, has someone else's open PR, or carries a commit from another author. [DOC S1803]
- Fired text (API `text` field, or **Run now** text) arrives wrapped in a `<routine-fire-payload>` block labelled untrusted; the routine's saved prompt must explicitly opt in to acting on it, "or the routine treats the text as inert context." [DOC S1803]
- Routines draw on the normal subscription usage limit plus a **daily cap on routine runs per account**; one-off (single-fire) schedules don't count against that daily cap. If usage credits are off, extra runs are rejected once the cap is hit. [DOC S1803]
- If a routine's GitHub connection lapses, it skips runs for up to 72 hours before auto-disabling. [DOC S1803]
- GitHub's Copilot cloud agent (earlier called the coding agent) works from assigned issues in its own ephemeral development environment, with a firewall on by default that blocks outbound connections to unauthorized hosts to prevent exfiltration; it responds only to users with repository write access, and Actions workflows triggered by its pull requests need approval from a write-access user before they run. [DOC S1804]
- The responsible-use page (S1804, re-read 2026-09-26) no longer states that the sandbox is GitHub Actions-powered or that a blocked request is recorded as a warning on the PR; the firewall how-to (S1805) is the likely home of those details. [UNK: not re-confirmed 2026-09-26]
- The cloud agent can push to a single branch only: the pull request's branch when triggered by mentioning `@copilot` on an existing PR, otherwise a new `copilot/` branch created for it; it is also subject to the repository's branch protections and required checks, and can perform only simple push operations. [DOC S-szgomxsz]
- GitLab Duo Agent Platform reached GA on 2026-01-15 for Premium and Ultimate customers on GitLab.com and GitLab Self-Managed, with GitLab Dedicated planned during the GitLab 18.8 release cycle; usage is paid in GitLab Credits, with $12 (Premium) and $24 (Ultimate) of included credits per user. [DOC S1807]
- GitLab-managed external agents include a Claude Code agent, a Codex (OpenAI) agent, an Amazon Q Developer agent, and a "Develop with Gemini" agent; self-managed instances can add custom external agents via the AI Catalog. [DOC S1806]
- GitLab agent triggers include MR creation/approval, "MR ready" status, MR conflicts, and work-item creation/status changes; agents authenticate via GitLab-injected `AI_FLOW_AI_GATEWAY_TOKEN`/`AI_FLOW_AI_GATEWAY_HEADERS`, a `AI_FLOW_GITLAB_TOKEN` scoped to `ai_workflows` endpoints, OIDC ID tokens, or project CI/CD variables for third-party providers; results return as "a ready-to-merge change or an inline comment." [DOC S1806]
- `claude -p` has a hard cost cap: `--max-budget-usd` (print mode only) stops spending at a dollar amount; subagent spend counts toward it, and once reached, spawning another subagent fails with `Budget limit reached` (enforcement needs Claude Code v2.1.217+). `--max-turns` caps agentic turns and exits with an error when reached (no limit by default). GitHub Actions / GitLab CI/CD add job-level `timeout`. [DOC S1824]
- `-p` (headless) sessions default to Manual permission mode on every plan and load the full interactive context (hooks, skills, MCP servers, CLAUDE.md) unless `--bare` is passed; Anthropic states `-p` "shows no workspace trust dialog and no per-server approval prompt," so a project's `.claude/settings.json` hooks and `.mcp.json` servers run even in an untrusted directory unless `--bare` is used. This is a permission-surface fact for any headless job for a tiered-confirmation system that loads a working directory it does not fully control. [DOC S1800]
- `--permission-prompts none` (Claude Code v2.1.259+) is the documented flag for genuinely unattended jobs "for example, in a scheduled job": it removes `AskUserQuestion`, cancels unanswered MCP elicitations, and denies (rather than blocks on) anything that needs human input — this is the concrete mechanism behind a "tier ≥ 2 always confirmed" requirement failing safe (denied, not silently approved) when nobody can answer in a headless run. [DOC S1800]
- GitHub Agentic Workflows (`gh-aw`, GitHub Next + Microsoft Research per its docs site, MIT-licensed code; the repository moved from `githubnext/gh-aw` to `github/gh-aw`) is a separate, GitHub-native runtime: workflows are Markdown files with YAML frontmatter compiled into ordinary GitHub Actions workflows; a `schedule` frontmatter trigger (e.g. `on: schedule: daily`) runs an agent job unattended, same as any GitHub Actions cron. [DOC S1818, S-qso27noq]
- gh-aw's "safe-outputs" mechanism is its named guardrail for unattended write access: the agent job itself runs read-only/sandboxed by default, any writes it wants to make (PR, comment, issue, file) are buffered as "configured write requests," a separate scoped-permission job validates and applies them — i.e. the agent process never holds direct write credentials. [DOC S1818, S-qso27noq]
- gh-aw's docs site also describes a dedicated scanning job that "blocks suspicious changes" before they land; the current repository README does not mention such a job. [DOC S1818]
- gh-aw's own gallery includes a "Documentation Maintenance" sample workflow described as automatically detecting "drift between code and documentation and propos[ing] reviewable updates" — the clearest scheduled/GitHub-native counterpart to Claude Code routines' "Docs drift" example (`agents/docs-maintenance-agents.md`), and it ships from the same GitHub org as Copilot coding agent. [DOC S1818, S-qso27noq]
- A team that keeps "one job per runner and trigger, all logic stays in one script" as a rule: gh-aw's trigger (a `schedule:`/event block inside a Markdown workflow file compiled to a normal Actions YAML) is the one shape among the scheduled-agent runtimes surveyed that stays fully inside a reviewable repository file, closer to that rule than a routine's or Duo Agent Platform's server-side trigger config — but it still represents the repository's own CI defining a recurring job that runs itself with no human present, which is exactly the shape "a session never schedules its own future" cautions against. [DER S1818, S-qso27noq]
- A "one job per runner and trigger, all logic stays in one script" rule and a "a session never schedules its own future" rule bear directly on routines/scheduled GitHub Actions/GitLab Duo agents as a class: all three products default to letting the *agent's own platform* own the cron, separate from the repository's own CI definition. [DER S1801,S1803,S1806: none of the three runtimes' scheduling lives in the repository the way a single CI script would — a routine or Duo Agent Platform schedule is configured server-side, outside the pipeline file such a rule would review]

## Reference

| Runtime | Trigger kinds | Unattended auth | Output | Cost basis |
|---|---|---|---|---|
| `claude -p` (local/any host) | invoked by the caller's own scheduler (cron, task runner) | `ANTHROPIC_API_KEY` (bare mode) or provider creds | stdout / JSON / stream-json | API tokens (or subscription) [DOC S1800] |
| Claude Code GitHub Action | `@claude` mention, or any GitHub event incl. `schedule:` | repo/org secret (`ANTHROPIC_API_KEY`/`CLAUDE_CODE_OAUTH_TOKEN`) or OIDC federation | PR comment, workflow log, or a PR/commit when granted write | GitHub Actions minutes + API tokens [DOC S1801] |
| Claude Code GitLab CI/CD | manual, MR event, or webhook-fed pipeline trigger | masked `ANTHROPIC_API_KEY` var, or OIDC to Bedrock/Vertex | MR, or job log | Runner minutes + API tokens [DOC S1802] |
| Claude Code routines | schedule (≥1 h), API POST, GitHub event | user's claude.ai account + linked GitHub/connector identities | new cloud session per fire, reviewed and turned into a PR by a human | subscription usage + daily run cap [DOC S1803] |
| GitHub Copilot cloud (coding) agent | issue assignment | ephemeral environment, firewalled by default | `copilot/`-prefixed branch → PR | Copilot billing (not itemized here) [DOC S1804,S1805,S-szgomxsz] |
| GitLab Duo Agent Platform (external agents) | MR/work-item events | `AI_FLOW_*` tokens / OIDC / CI/CD vars | MR or inline comment | Premium/Ultimate seat plus GitLab Credits ($12/$24 included per user) [DOC S1806,S1807] |
| GitHub Agentic Workflows (`gh-aw`) | `schedule:`/GitHub-event frontmatter, compiled to Actions YAML | GitHub Actions job token + the agent's own API key/OAuth secret (same as the underlying CLI it wraps) | validated "safe-outputs" (PR, comment, issue) applied by a separate scoped-permission job | GitHub Actions minutes + the wrapped agent's own API/subscription cost (not itemized) [DOC S1818, S-qso27noq] |

**Cost figures actually published (2026-09-25):** none of the runtimes surveyed publish a fixed price-per-run; Claude Code's own figure is the client-side `total_cost_usd` estimate returned by `--output-format json` after a run, explicitly caveated as able to "differ from your actual bill" — no vendor here (Claude Code, GitHub Copilot coding agent, GitLab Duo Agent Platform, `gh-aw`) states a published unattended-run cost figure beyond "GitHub Actions minutes," "runner minutes," "API tokens," or an unspecified seat/credit charge. [DOC S1800,S1801,S1802,S1804,S1806,S1818]
