# Prior art for self-updating documentation

## Summary
No product surveyed here runs a fully unattended "docs agent that commits straight to the docs branch."
The common pattern is: read the code/repo (not a separate spec), regenerate on a trigger (deploy, PR
merge, or on-demand query), and either serve the result live (DeepWiki, Mintlify's generated `llms.txt`)
or open a change for a human to merge (Swimm's Auto-sync commit, a Mintlify agent-authored PR). None of
the vendor docs found this session state a fully-autonomous merge-with-no-review path for prose docs.

## Facts
- DeepWiki (Cognition AI, the company behind Devin) turns a public GitHub repository into a generated wiki by replacing `github.com` with `deepwiki.com` in the repo URL; it combines an LLM with code analysis to extract architecture, module relationships and implementation detail, and represents the codebase as a graph (files as nodes, relationships as edges). [DOC S1808]
- DeepWiki indexes "code and metadata (pull requests, git history, team discussions)" alongside the codebase itself — its trigger for staying current is tied to repository activity, not a fixed calendar schedule, though the exact update cadence/mechanism is not stated in the fetched pages. [DOC S1808] Cadence: [UNK]
- Cognition frames DeepWiki as accelerating "the cycle of implementing code from documentation and refining documentation from code," i.e. docs and code are meant to converge through repeated regeneration rather than a one-time write. [DOC S1808]
- Devin's own docs describe "DeepWiki repository wikis" as a feature Devin consults/produces for a repo it works in. [DOC S1809]
- GitHub's `CognitionAI/deepwiki` repository exists on GitHub (found via search; page content and licence not independently fetched this session). [DOC S1810] Licence: [UNK]
- Mintlify auto-generates `/llms.txt`, `/llms-full.txt`, and a Markdown version of every page, "generated from your docs on every deploy" — i.e. the trigger is a documentation deploy, not a code-repository event, and no human review gate is described for this generation step because it is a mechanical export of already-published prose. [DOC S1811,S1812]
- Mintlify's own blog states a separate "Mintlify agent API" pattern for auto-updating documentation when *code* changes, via GitHub Actions or an n8n workflow — i.e. code-diff-triggered doc updates are a distinct, opt-in pipeline from the always-on `llms.txt` export. [COMMUNITY S1810: search-engine synopsis of the blog index cites this API but the specific how-to page was not independently fetched and verified this session] Mechanism/review step: [UNK]
- Mintlify supports auto-merging Mintlify-bot-authored documentation PRs by adding the Mintlify bot to a repository ruleset bypass list — implying the default path is a PR a human (or bypass rule) merges, not a direct commit. [COMMUNITY S1810: same caveat as above]
- The `llms.txt` file format (root or subpath `llms.txt`, Markdown, one mandatory H1 + blockquote summary, optional H2 file-list sections with links) was proposed by Jeremy Howard, v1 published 2024-09-03, v2 updated 2026-08-10; the spec explicitly states "agents are best served by concise, expert-level information gathered in a single, accessible location," i.e. its trigger for use is agent navigation, not compliance. [DOC S1813]
- The `llms.txt` spec's own currency mechanism is a public GitHub repo, a community Discord, and an issue tracker — there is no vendor-run scheduled regeneration described in the spec itself; individual sites (like Mintlify above) choose their own trigger (deploy-time) for producing a conforming file. [DOC S1813]
- Swimm's "Auto-sync" and "Verify" features run "at any relevant pull, merge, or CI test": Verify checks code snippets/"smart tokens"/"smart paths" embedded in docs against the current code and fails the check when documentation is out of date; Auto-sync determines whether a change is simple enough to update automatically and, when so, "can automatically compile an auto-synced version of documentation and commit it." [DOC S1814,S1815]
- Swimm's drift trigger is therefore a code change reaching CI (pull, merge, or test run), not a calendar schedule; more complex/impactful changes fail Verify instead of auto-syncing, forcing human review. [DOC S1815]
- GitHub Copilot Spaces (GA 2025-09-24) let a user centralize context — repos, code, PRs, issues, free-text notes, uploaded files — that grounds Copilot's chat answers for a task; it is a curated-context store for querying, not a scheduled or merge-triggered documentation generator. [DOC S1816,S1817]
- Copilot Spaces access: any Copilot-licensed user (including Copilot Free) can create a space; organization-owned spaces can be shared at varying access levels, personal spaces can be shared publicly, with specific users, or kept private. [DOC S1816]
- DeepWiki wikis are steered by a `.devin/wiki.json` file committed to the repository root: it can list exactly which pages to generate (overriding DeepWiki's automatic clustering) and carry a `repo_notes` field that points the generator at important folders, e.g. "prioritize the cui/ folder." Committing a change to `.devin/wiki.json` and asking DeepWiki/Devin to "regenerate your wiki" is the one explicit, human-triggered refresh path documented; a continuous/automatic refresh cadence beyond that is not documented in the pages fetched. [DOC S1809] Automatic refresh cadence: still [UNK] after a second attempt this session.
- **Google Code Wiki** (announced 2025-11-13): generates and maintains structured repository documentation with diagrams and a Gemini chat; it "regenerates the documentation after each change" (trigger: code change, not a schedule). Public preview for open-source repositories only; a Gemini CLI extension for private repositories was announced as coming, behind a waitlist. No MR/review gate is described. [DOC S1825]
- GitHub Agentic Workflows (`gh-aw`, MIT-licensed, GitHub Next + Microsoft Research) ships a sample "Documentation Maintenance" workflow in its gallery that is described as automatically detecting "drift between code and documentation and propos[ing] reviewable updates" — a schedule- or event-triggered, GitHub-native counterpart to DeepWiki/Swimm, and it uses the same "safe-outputs" review gate (buffered writes validated and applied by a separate scoped job) as gh-aw's other workflows, rather than direct commits. [DOC S1818,S1819] (Full runtime mechanics recorded in `agents/headless-agent-runtimes.md`, not repeated here.)
- The **AGENTS.md standard** (agents.md, stewarded by the Agentic AI Foundation under the Linux Foundation, originated by OpenAI Codex/Amp/Google Jules/Cursor/Factory) is a single predictable file read by an AI coding agent for build/test/convention instructions, distinct from a human-facing README; nested `AGENTS.md` files in subdirectories override the parent (closest wins); the standard claims 20+ supporting tools and over 60,000 adopting open-source projects as of the page fetched. It is a grounding-file convention, not a self-updating-docs mechanism in itself — nothing in the standard triggers or reviews its own regeneration. [DOC S1820]
- GitHub Copilot recognizes `.github/copilot-instructions.md` (repo-wide) and glob-scoped `.github/instructions/**/*.instructions.md` files for build/test/convention guidance, applied across Copilot Chat, code review, and cloud agent (coding agent) tasks; Copilot's own docs additionally list `**/AGENTS.md`, `/CLAUDE.md`, and `/GEMINI.md` as custom-instruction files it also reads — i.e. GitHub Copilot treats a repository's own Claude Code `CLAUDE.md` as a native input format without any conversion step, if a Copilot coding-agent task ever runs against that repository. [DOC S1821] The fetched page names no scheduled or issue-triggered documentation-update workflow specific to Copilot coding agent beyond this instruction-reading behaviour — recorded as absent rather than researched further, since this was the only official page fetched for this sub-question this session. [UNK: scheduled/issue-triggered Copilot docs-update workflow]
- Deterministic guardrail tools usable in front of (or instead of) a docs-generating agent: **Vale** (MIT, errata-ai) is a markup-aware prose linter — style rules (Microsoft/Google/Red Hat style packages, or custom YAML rules) checked via a `.vale.ini` config, runnable in GitHub Actions or a pre-commit hook, enforcing terminology/voice/"state the present"-style rules mechanically rather than by asking a model. [DOC S1822] **markdownlint** (MIT, DavidAnson) is a Node.js Markdown/CommonMark style checker with 60+ built-in rules (MD001–MD060: headings, lists, whitespace, links, code blocks, tables), runnable in CI/pre-commit/ESLint pipelines, with inline HTML-comment exceptions per file. [DOC S1823] Neither tool detects doc-vs-code drift by itself; both are the kind of "strict build" check a docs-quality gate would require, applied to style/structure rather than content currency. `lychee` (a Rust link checker named in the deepening-pass brief) could not be fetched this session (`lychee.cc` did not resolve; the correct current URL was not independently verified) — recorded as a gap. [UNK: lychee's current URL/license, not independently confirmed this session]
- `doc-detective` and `Swimm`'s content-currency features are asymmetric in what's documented here: Swimm's Verify/Auto-sync (already covered above) is vendor-documented as a code-diff drift check with a CI-fail gate; no page for `doc-detective` was fetched this session (not in the URL list provided and no budget spent hunting for it), so it remains untested prior art rather than a confirmed gap-closer. [UNK: doc-detective]
- A team that keeps "no session schedules its own future" as a rule: none of these products' default trigger is a self-scheduled recurrence in that sense — DeepWiki and the `llms.txt` export regenerate from a push/deploy event already outside the agent's control, and Swimm's Auto-sync/Verify runs inside CI a human already triggers. Only a Mintlify-agent-API cron or a Claude Code routine (see `agents/headless-agent-runtimes.md`) introduces the kind of self-scheduled recurrence such a rule would flag. [DER S1811,S1812,S1814,S1815: compares each product's stated trigger against "a session never schedules its own future"]

## Examples
For a repository whose docs live under a strict-build docs home, a Swimm-style trigger ("run a check when a docs-relevant directory changes in a merge request") stays closer to a "no repository holds anything but code, data, generated reference and docs" regime than a DeepWiki- or routine-style calendar job, since it rides the existing merge-request pipeline rather than adding a new scheduled trigger against example fixtures such as `corp.example.com`.
