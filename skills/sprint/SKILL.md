# Run a sprint

`${CLAUDE_PLUGIN_ROOT}` is the directory that holds the tool scripts: the plugin's, or, where this text runs from a clone's own copy and still shows the variable, that clone's top directory, and there write each command in the relative form `python3 _tools/SCRIPT.py` from that directory, which its `.claude/settings.json` allow rules match (an absolute path matches none). The Bash tool does not set it: write the path where a command below shows it.

Read the backlog with the `kb_backlog` kb MCP tool first when your tools list it (`command` one of `show`, `list`, `next`, `horizon`, `stalled`, `cost`, `ops`, `selectors`, `held`, `referrers`, `find`, `similar`, `tree`, `config`, `landings`, `runs`, `procs`, `check`, `report` or `usage`, `args` its arguments; `usage` lists the verbs and runs none); the `backlog.py` command a step below shows is the fallback, and the way to every command the tool refuses (`claim`, `brief`, `land`, `done` and the rest, which write).

The project's `backlog.json`, at its repository root, names the steps only some projects have. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py config` prints each setting and whether it came from the file or is a default. A step below that names a setting runs when that setting is set (a non-empty value, a non-empty argument list) and is skipped, said so in one line, when it is not; no step asks for a file the project does not have:
- `kb_root`: the kb root whose rule docs the project keeps; empty means the project has none, and every rule-pack command below is skipped.
- `docs_map`: the CSV that maps an item's touches to the docs it must keep right; empty means no docs warning.
- `land_stale`, `land_eval`, `land_lint`: the argument lists of the landing's stale-doc check, lookup eval and lint, run from the project's root before the push; `[]` means no such step.
- `lane_module`: the module that says which lane a path belongs to: a project with a code lane sends code through a merge request, and `done` waits for it; `""` (the default) means no code lane, and every commit lands as content (`done --commit`, then the push).
- `land_push`: the argument list of the push, run from the project's root (a first element ending in `.py` runs under python3, any other is the program, e.g. `["git", "push", "origin", "HEAD:main"]`): the landing's last step and the route for the claim commits. It has no default: a project that names none stops `land` at the push step, which names this key, so a host names it.
- `item_dir`, `worktree_dir`, `scratch_dir`: where item files, worker worktrees and scratch directories sit; the brief and `dispatch` print the real paths, so never assume one.

Run each command on its own (no `;`, `&&`, pipes into other tools or loops): permission rules match single commands, so a chained command asks for approval or is refused in a headless run.

Whenever you name an item (in chat, a question, a subagent brief, a commit), give its id and its title together, never a bare id.

When `kb_root` is set, rules are asked for, not read up front: `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/rag.py pack --root KB_ROOT --set <name>` prints a step's tested rule questions and the line that answers each. The sets of this skill: `kb-sprint:plan`, `kb-sprint:start`, `kb-sprint:run`, `kb-sprint:review`, `kb-sprint:close` and `kb-commit` (before a commit or push of the orchestrator's own). Once an item is claimed, `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/rag.py pack --root KB_ROOT --item ID --budget 600` prints the rules of the docs its touches map to. Any other rule: `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/rag.py pack --root KB_ROOT "<question>"`. A rule you needed and no set gave you is a miss: say so in your report, with the question as you asked it.

## plan "<goal>"
1. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py new sprint --title T --goal G` creates the sprint, its blocking `start` gate, its review story and its goal research story (a research item: claim and work it first, then `done`; one finished with tested rows in the `_self` root's eval file `lookup_eval.csv`, a code-lane path (`${CLAUDE_PLUGIN_ROOT}/_tools/kblane.py`), lands with `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py land ID --wait-merge 1800`, since `done --commit` refuses its commits as not on `origin/main`). `claim --commit` commits only the item it claims, so the sprint's own file and its review and research stories get a planning commit first (`new sprint --commit`).
2. See what covers the goal: `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py find WORDS`, `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py tree --open` and `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py list --kind bug`: every `S1` and `P1`, then by priority and rank, as far as the goal needs. Put them in the sprint with one call, `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py set ID ID... --sprint SP --commit` (every option but those naming one item applies to each id; one id refused leaves all unchanged); every item edit goes through `set` or the other commands, never a hand edit of its JSON. A story or bug moves between sprints, or out of one, with `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py move ID --sprint SP|none`, and a done item goes back to work with `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py reopen ID --why TEXT`. A parked draft (a `parked: SP-...` link) is committed only when its `notes` name the fitness test it blocks or a real user's report. Break stories into tasks with `touches` and `checks` (`new task --parent ID --touch G --check CMD`): the files its change edits, each moved or renamed path or symbol's referrers (`python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py referrers PATH|SYMBOL... --item ID`) and, when `docs_map` is set, the docs it maps them to, never a glob wider than those files. Take an item's `touches` from the `kind=ref` lines of `referrers` (files that use the term in code, from the code map) and read its `kind=text` lines for docs. Every symbol or constant a goal changes is run through `referrers` by name, and so is a new subcommand's facade registration, before the claim: each file it lists goes into `touches`, so a worker neither stops on a reader outside them nor widens them itself. A removed or renamed flag is run through `referrers` as a term after a `--` (`python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py referrers -- --flag`, since a bare `--flag` is read as an option of `referrers` and exits 2), and each file that prints or documents it goes in too. A task that adds a new tool module names the docs map's csv, and one that adds a flag names its command facade and the readers it calls. An item that moves the figures of the benchmarks results file (`benchmarks.csv`) or the report code has `README.md` in its touches, since `report --check` reads its numbers. A research or gap story's goal states where its findings go: into dated ledger notes only (gap notes, no article fact and no source row, so its touches name no article and no `_sources.csv`) or also into article facts with source rows (its touches name the articles and their `_sources.csv`, as below); a goal that leaves it open sends the worker to a provisional gate, so the planner settles it before the start gate. A research or refresh item whose touches name a kb root's articles has that root's `_sources.csv` in them too: no always-in-scope path covers it, so a source row the worker adds there is refused at `done` otherwise. It has that root's `_retrieval/doc2query/expansions.csv` as well, when the work may reword a fact: the rows keyed to the old text go stale, and the root's doc2query `stale` check fails until they are pruned, so the worker prunes them in the item instead of stopping to have its touches widened. The same item has that root's `_anchors.csv` beside `_retrieval/doc2query/expansions.csv` in its touches when its work may reword or add a `DOC` fact: a reworded fact's key is new, so its anchor row is missing until the worker runs `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/factdiff.py anchor --file` for the file, and the review finds the fact unanchored and the old rows orphaned. A change gets no test by default and a test exists only for a critical component, so an item's touches name a test file only when its goal changes a critical component's test (`set ID --add-touch TEST_FILE`, before the start gate): `done` refuses a commit that changes a file outside them, and `check` warns of a test file the notes or goal name that no touch covers.
   Other sessions' plans and files: run `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py peers --sprint SP` first (the other live sessions by label and topic, the planned sprints and held claims on `origin/main`, and each file this sprint shares with them; `held --ref origin/main` lists the held paths alone). On an `overlap`, ask that session: `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/kbask.py ask TARGET QUESTION` (TARGET its item id, or `any`), then record the order you agreed as `set ID --add-depends OTHER` or in the item's `--add-notes`, before the start gate. A `doc` line orders nothing: the landing's rebase merges its sections.
3. Map the goal's clauses to items. A clause no item carries is either already met in the tree (drop it and name the earlier item that delivered it: `git log --grep 'KB-Work: ID'`; a goal changes only by the operator, `set SP --goal G --by operator`, which `set` refuses without; an item moved out of the sprint with `move` prints the clause it leaves behind and this remedy) or work still to plan: add an item for it. A goal that rejects a query-log finding as off the kb's domains first runs its question once with `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/rag.py pack "<question>"` and once with `--root _self`, and names the finding off-domain only when neither pack leads with a line that answers it; one the `_self` docs answer is a rules miss, planned as a tested `_self` question (a row of `lookup_eval.csv`, landed as step 1 says), not as off-target.
4. Check each committed item's goal for its step order: for an item with a code-lane commit (`lane_module`), `done` and a push to the integration branch come after its merge request merges. A goal that puts them before is rewritten (`set ID --goal G`) or gets a gate (`gate add`) before `start`.
5. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py fmt` and `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py check` (no warning about a committed item's docs; a file in the touches of more than half of the sprint's items means they run one after another: split them), then `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py selectors` (a check selector that collects `NONE` names no test), `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py precheck SP` (it runs each committed item's checks once on the base: a check that already passes proves nothing yet, and one that fails prints the last 20 lines of its output under its line: read them, since a check that fails on a traceback, or on a part other than its premise, proves nothing and is fixed before the start gate; it also lists each item's goal clauses with the check that reads each, step 6) and `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py horizon --sprint SP`.
6. When a conflict predictor writes its predictions as JSON lines, `precheck SP --conflicts FILE|-` prints them beside the sprint's own file overlaps, those that name an item outside the sprint apart (`kb/_self/backlog.md`, Sprints): order or split the items it names before the start gate. Read the goal clauses `precheck SP` printed for each committed item (the goal split at `; ` and `, and `, as `close --summary` splits a sprint goal) against the check or repro it names for each, from the item's `clauses` mapping, which the planner records with `set ID --add-clause CLAUSE=N` (N the index of the check, then the repro, that reads the clause; `check` refuses an index out of range and a clause the goal does not hold): a clause it warns of, one no check reads, is a missing check, recorded before the start gate is asked (`set ID --add-check CMD`, then its `--add-clause`), and so is a goal of several clauses it warns has no mapping. A check that reads one clause of a several-clause goal proves that clause only. A goal clause is worded no stronger than its check, and a check asks no more than its clause says: a clause that says "resolved or narrowed" is not read by a check that requires the literal `Resolved`, and a check a sibling item's facts already satisfy is tightened or its clause reworded before the start gate. For the outputs or figures a goal names, review each against the checks. A goal clause that names a constant in the code (such as `LAUNCH_BUDGET_S`) is read against what the constant bounds there (`python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py referrers CONSTANT` lists where it is read): a clause that asks it to bound something else is rewritten before the start gate, since the check would prove the constant's bound and not the clause. A goal's time or share figure names the run it was measured on (profiled or not, which host, warm or cold) and the story's premise measures that run, not another. Each run figure a goal names (row counts, subsets, arms, reps, effort levels) maps to a flag of the command that runs it, or the clause is rewritten or a flag task added before the start gate, not found as a gate mid-work. Stories that change the same function get checks on its behaviour, not its internal shape (the argv it plants, the url it asserts, the helper it calls): a done story's check does not change until a reopen, so a later story's landing that changes the shape breaks it. A check that orders or bounds measured figures (timings, starts, memory) is written after the planner has measured the figures' run-to-run spread on the base or a prototype (the repeated runs of the measuring command, on the planning host), and states its margin against that spread, or asserts an exact difference the code makes by construction: a margin guessed from one run fails on the host's noise, not on the work. A committed item whose touches name code has at least one check that runs the changed behaviour (the tool run on a planted input, or the test selection of a critical component), not only a read of source text (`check` warns when every check only reads files). A check that reads clone or host state a hand run can satisfy (refs, files outside the tree, a spool) is paired with one that runs the code path the goal names. A planted check that reads query-log, spool or workspace state is run once through `bl_base.run_check`, the runner of the landing (an isolated `CLAUDE_PLUGIN_DATA` home, a colourless env), against a prototype of the fix before the start gate, since the landing sees an empty home where a shell sees the clone's own: make a worktree of the base, apply the prototype of the fix there, and run `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py --root PROTOTYPE precheck SP` (`precheck` runs each committed item's checks through `run_check`; a check that passes from a shell and fails there is fixed before the start gate: SP-hja7yu5k, whose span story's check 1 passed from a shell and failed twice at the landing, where `kbmon --events` printed the cursor `1.0.N.0` and the redaction rewrote it to `192.0.2.10`). A check that bounds a tool's git calls counts every git process (each `subprocess.Popen` of `git`), not one helper's calls. An item that adds or widens a cache carries a check that changing each input, the computing code included, gives a fresh value. A check that asserts a phrase's absence reads only the line or section the goal names, not the whole file. An item whose goal adds a rule that tells an agent to run a command (a subcommand of the backlog tool with a term or flag) carries one check that runs the command form the rule text gives, on a planted input or this clone, beside its doc-text check: a check that reads only the phrase passes while the rule's own command fails (SP-4jfepy6u close: ST-pogg4knc's check read the phrase `removed or renamed flag` while the rule's command, `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py referrers --add-touch`, exits 2: BG-sq2qycqc). The same step names the other checks that read a phrase and not the behaviour: each condition of a clause gets its own planted case (BG-4flop3jv); a wording bug's check reads its claim by the items it names, not one phrasing (BG-ab3tndhy); an item that changes how `researched` reads a goal gets a check that runs `researched` on the sprint's own goal research story (SP-sqgyoiaz); a lock or concurrency story gets a planted check for each recovery path (BG-h6aqngbp); a skill-text check reads the step its goal names, not a line found by its prefix (BG-adgc5qf2); a rule that calls a path in scope gets a check that runs `in_scope` on that path (BG-6bb4zzdy); a committed item that sends new text through `redact` (a new field, comment or prompt path into the spool, the query log store or a Haiku call) gets a check that runs that path on a planted input holding one fake secret of each kind `redact` handles (one for each shape in `kbcommon.SECRETS`) and one `key=value` assignment, built at run time so no secret-shaped literal sits in the check, and asserts none of them survives in the output. A gap-research story's check counts a Resolved, Partly resolved, Narrowed or Closed note as closing only when the note cites a tagged article fact by path:line, read in the article, or a source id its article cites: a check that counts the closing word alone passes a closing on a code read or a local run with nothing behind it (SP-5cyrnkw7 and SP-z6wolmvm, whose fresh reviews found 37 such closings). A check over the rows of a pool or table (the benchmark question pool, the eval's rows) calls the code's own predicate (`bench_pool.path_only`, `bench_pool.too_broad`, or the function that judges that kind of row), not a new regex: a hand regex fails on a row the predicate passes, or passes one it rejects (a hand regex that failed one of six path-only rows passed with four still path-only after the work). A goal that attributes rows or windows around a landing gets one check that drives the land sequence (a rebase, `done --commit`, a failing step) on a fixture, not a hand-set item file. An item whose work replays, rebases or rewrites commits (`repro replay`, a cherry-pick of another clone's history) carries the check `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/kbgit.py check-trailers origin/main..HEAD`, so a trailer the sync gate refuses (a second `KB-Work` line on a replayed commit) fails the item's `done` in the worker's worktree, not the landing (SP-bhzxxhub close: ST-apmeih5l's `done` passed all seven checks, then `kbgit.py sync --push` stopped at `check-trailers` with 7 bad commits). Run each committed story's premise once and record the result in its notes (`set ID --add-notes TEXT`); a story whose premise does not reproduce is not committed. A committed item whose goal adds a refusal or a detector condition (a push, `done` or `check` that refuses, a finding key, a window) runs it once against today's main, on a fixture or the tool's own dry run, and a gate is asked before the start when it would fire now (on every push, or on a state main already holds), not found after it. A committed item whose goal names a paid run with a spend cap has its `--dry-run` estimate in its notes, and a cap below the estimate is a gate asked before the start. A choice the goal leaves open on an item whose touches guard a rule is a blocking gate, added before any code. Before asking, run `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py host-check SP`: on exit 1 show the operator the failing gate and its output and do not ask yet. Ask the operator to approve the goal and the committed items (AskUserQuestion: approve / change / cancel), showing each goal clause with its item's id and title, any clause dropped as met, and the gates the items will meet.

## start SP
Only on the operator's approval in this conversation:
1. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py answer SP start --answer approve --by operator`.
2. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py start SP`. It prints `warning:` lines for a sprint item whose mapped docs sit outside its `touches`: before any claim, ask the operator to move each named doc into that item's touches (`set ID --add-touch G`), and rerun `check`. It refuses while an answered gate's host check fails.

Never answer the start gate yourself.

## run [SP]
At the first run in a workspace with no `coordination` object in the project root's `settings.json` (`python3 ${CLAUDE_PLUGIN_ROOT}/_tools/kbsettings.py explain announce.when --root .` prints `source: default`), before step 1, ask the operator for the coordination settings in one AskUserQuestion batch of four questions, the default first in each (`kb/_self/coordination.md`, Coordination settings): `announce.when`, when a session announces its work (`start,claim` offered first, as `kbsettings.py` has it built in, `start,claim,midrun`, `start,claim,midrun,edit`); `strategy.decide`, who picks the strategy when no key settles it (`operator` first, `claude`); `strategy.landing`, what a session suggests when another item that touches the same files is being landed (`wait` first, `ask`, `after`, `proceed`); `strategy.working`, the same when that item is being worked (`ask` first, `wait`, `after`, `proceed`). Then run `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/kbsettings.py init --root . --set KEY=VALUE` with one `--set` for each answer: it writes the whole `coordination` object of `settings.json` (the other keys take their defaults) and adds `coord` to the `hooks` list of `backlog.json`, which turns the plugin's coord hook on for the workspace. A workspace that already has the object is asked nothing (`kbsettings.py show --root .` prints it); a session that cannot ask (headless) runs nothing and says the defaults apply.

You are the orchestrator. Run from your own clone or git worktree, never a checkout another session works in: `claim` refuses a claim by a second session while one of them is still doing there. A linked worktree you run from is recorded as a leftover of this clone when you make it: `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py own <worktree path> --class worktree --sprint SP` (`--drop` clears the record once it is removed); `dispatch` records each worker's worktree, scratch directory and pid itself. Loop:
1. Run `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py selfcheck` first and act on each failure before anything is claimed, then `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py horizon --sprint SP`, `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py next --sprint SP --all` and `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py stalled`.
2. From the ready list take up to four items whose `touches` do not overlap each other or any item in flight, and start them with one call: `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py begin ID... --by <name> --trailer 'Co-Authored-By: ...'` (`--dry-run` first prints, for each id, the claim and dispatch it would make or the refusal, and writes nothing). It runs the chain below, steps 2 and 3 in one: `git fetch`, the overlap check against the items of the call and the claims of every session, a refusal for an item with a local `work/<id>` branch or for a story `next` marks `no worker` (step 3 lands it), the claims with `--commit` and your `--trailer`, one push of the claim commits with the `land_push` argument list and `dispatch --detach` of each, printing its id, pid and `dispatch.log`; an item it refuses is named with the reason and the others go on (exit 1 when any was refused), and it takes no more than four ids. To choose the ids, `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py next --sprint SP --batch` prints them in `next` order (a `kb/_self` doc is no overlap; it reads the claims of your checkout, so after `git fetch` and a fast-forward it holds the other sessions' too). The commands `begin` chains, for one item or when it cannot run: after `git fetch`, `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py held --overlaps ID --ref origin/main` lists the claimed items, of every session, whose touches an item would meet (exit 1 when there is one). Right before the claim run `git fetch origin` and check that no local `work/<id>` branch exists. Claim each: `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py claim ID --by <name> --commit --trailer 'Co-Authored-By: ...'`, then push the claim commits once with the argument list `land_push` names (`config` prints it), run from the project's root.
3. Start one worker per item, whatever its kind, except a story `next` marks `no worker` (every task of it is done and its checks pass in your clone, which `fetch` and a fast-forward keep level with `origin/main`): it needs no session, which would only run those checks again. Claim and push it as step 2 does, make its branch with `git branch work/<id>` at your `HEAD`, which holds the claim commit, and land it as step 4.4 does. `brief ID` names such a story the same way. Any other item gets its worker from `begin` (step 2), or from two commands:
   - `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py brief ID [--known TEST=BUG]... [--probe TEXT]` prints the worker's brief: the item's JSON and goal text, its external tracker ids with their urls, the role file, the worktree and scratch directory, the in-flight sibling items and the files their `touches` change, the known failing tests, the fixed worker rules and the rules of the docs its touches map to. Name each test you already know fails on the host with `--known TEST=BUG`; a figure you add to a brief is measured, with the command beside it, never lifted from an example.
   - `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py dispatch ID` (the same `--known` and `--probe`) makes the worker's worktree on `work/<id>` from your `HEAD` (a repository's, on the branch the `naming` setting gives) and its scratch directory, writes the brief there and runs `claude -p --model sonnet --effort high --output-format json --add-dir <scratch> --max-turns N` in the worktree with the brief on stdin, and without `--detach` returns only when the session exits: a long command, as a landing is (step 4.4). Never run it in the foreground: the Bash tool moves a foreground command to the background at its 10-minute limit, and the worker is killed with it and resumed (SP-uwkr7iyl). Start it with `--detach`: `dispatch ID --detach` (the same `--known` and `--probe`) runs the dispatch in a new session with stdin closed and what it prints in `dispatch.log` of the worker's scratch directory, prints that process's pid and the log path and returns at once, so a worker that outlasts a background command's timeout is not killed with it (SP-uwkr7iyl). Wait for it with the one wait command of the paragraph "Waiting and the run states" below (the dispatch moves the item's run state to `working` and, when the session exits, to `returned` or `failed`, which ends that wait; the command it prints already holds the worker's `--pid` and starts after the events posted so far), then read the log: its last lines say how the worker exited, with its `session_id`, and end with the first line of the worker's report and its warnings; `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py report ID` prints the rest in one call (the session's result text, the branch's commits with the diffstat and the item's gates there), so no `result.json` or `git log work/<id>` is read by hand. Where a background writes its log: `dispatch.log` for `dispatch --detach`, and for a `land` you start in the background a redirect into the item's scratch directory (`land ID > <scratch>/land.log 2>&1`), which exists once `dispatch` has run, never into `_cache` of a worktree that may not have it yet (SP-uwkr7iyl). Write no launcher script of your own: one left in a shared scratch directory was removed mid-run and the next dispatch failed (SP-75hdeqld). Send a stopped or returned worker back (a landing that stopped at its checks, a narrower request) with `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py dispatch --resume ID --message FILE [--detach]`, never a hand-built `claude -p --resume`: it resumes the session of the item's last dispatch in the worker's worktree with the worker's environment and caps, the message file on stdin, and moves the run state to `working`, then `returned` or `failed`, as a dispatch does (it refuses while the worker's pid still runs). `N` is 100 for a task, subtask or bug that is not research, 150 for a story with no tasks, 200 for a research item; `--max-turns N` names another cap. `--dry-run` prints the worktree, the brief path and the argv and starts nothing.
   The brief goes to the session on stdin, never as a trailing prompt argument, which `--add-dir` swallows. You run a command in a worker's worktree only in a subshell, `( cd <path> && ... )`, or with `git -C <path>`, never a bare `cd`.
   The Agent tool is the fallback, for a session that cannot start `claude -p`: one subagent per item with `isolation: "worktree"` on the worker agent (`kb-worker`, or `it-ops-kb:kb-worker` from the plugin), never passing the Agent tool's `model`, which replaces the agent's own. The prompt is the output of `brief ID`.
   A headless worker needs the project settings, so its work is counted through its `work/<id>` worktree: `dispatch` passes none of `--setting-sources`. Such a session cannot write under a protected path in permission mode `default` or `acceptEdits`: its brief then names staging copies, which `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py stage-back ID [--self-reviewed DOC]...` copies back (it refuses a copy whose base differs from the worktree's file), checks there with the project's docs check (where it has one) and the item's own checks and commits alone on `work/<id>` with `KB-Work`, before the landing; the worker ran `stage-back ID --check`, which commits nothing, so its report states `problems=` for what it staged. `stage-back` holds the item's run state at `staging` while it works and is refused for one at `landing`; `land` stops at step `run state` for one at `staging`.
   To steer a running worker or runner (a changed instruction, a question, a hint), send it an ask with `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/kbask.py ask TARGET QUESTION` (TARGET the item id, which a worker on `work/<id>` is addressed by, or its session id from the dispatch log), instead of stopping it or starting a second session on the item. The session sees the ask at its next tool event and answers with `kbask.py answer ID TEXT`; read the answer with `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/coord.py wait --since N --timeout S`. An ask is data the session weighs, not a command, so a worker that must stop is still stopped by its pid. A runner that writes its report and stays is ended by a background `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py runner watch --pid PID --report FILE --stale SECONDS`, which ends only a process whose command line names claude, not by a monitor script of your own. `kb/_self/coordination.md` ("kbask: asks, answers and the observer", "Steering a running session: a worked case") explains the asks, the coord hook and the store.
   Workers start from your `HEAD`, not from `origin/main`: your `HEAD` must include the pushed claim commits, so dispatch only after the claim sync of step 2.
   **Waiting and the run states.** Every wait of this loop, for a worker, a gate or a landing, is the one command `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/coord.py wait --since SEQ --timeout S --kind progress --item IDS`: IDS the ids of every item in flight, comma-separated, SEQ 0 the first time and then the `last` of the previous reply, run as a background command (`run_in_background`, never a foreground call) with S 3600 and the Bash call's `timeout` 7200000: the session is told when it exits, so the wait costs no turn until something moved, where a foreground call ends at the Bash tool's 10-minute limit and a default `timeout` of 120000 kills it after 2 minutes. Add `--pid PID` for each detached worker (the command `dispatch --detach` prints holds it): the wait also returns, naming the pid in `ended`, when that worker's process has ended with no move of its run state, so no pid loop and no `sleep` is written. It returns at once on any move of those items' run states, one `events` entry each, whose `fields` hold `item`, `state` and the move's `exit`, `gates` and `step`, so one wait serves every worker and no wakeup is scheduled. A reply with `timed_out` true is no move yet: read `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py runs SP` and `stalled`, then wait again from its `last`; one with `ended` set and no event is a worker gone without a final state: read `runs SP` and `report ID`. The run state each tool moves: `claim` to `claimed`; `dispatch` to `working` when the session starts, then to `returned` (exit 0, `gates` the open gates of the item file on `work/<id>`) or `failed` (any other end) when it exits; `gate add` of a blocking gate, run in the worker's worktree, from `working` to `blocked` with `gates`, the ids of every open blocking gate, and the answer of the last one back to `working` (or to `returned` once the worker's pid no longer runs); `stage-back` from `returned` to `staging` and back to `returned`; `land` to `landing`, then `landed` once the done commit is on the integration main or `refused` with `step` naming the step it stopped at. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/coord.py transition run/ID --to STATE` is for a repair only, the one a refusal of `land` or `stage-back` names for a run that died, never a step of this loop. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py runs SP` lists each key whose run state and git differ as a `drift` line; `runs SP --reconcile` writes the state git shows to each key it lists, and nothing else writes it back (step 6).
4. When the wait shows an item `returned`, land its branch yourself, one at a time:
   1. Land an item only after its gates are answered or provisional. A worker's open blocking gates are read from the `gates` of its `blocked` event as the worker posts them, never from its branch after it returns: ask the operator for them at once (step 5), the worker's session still running. A provisional gate does not move the run state, so read the gates on its branch before the landing (`python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py show <id> --ref work/<id> --field gates`): an unanswered provisional gate, or a choice the report names that no gate records, goes back to the same worker (`claude -p --resume <session_id>`) to record and answer on its branch; an open blocking gate keeps the item waiting. An answer the operator gives you for a gate that exists only on the worker's branch is recorded by you in the worker's worktree: `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py --root <worktree> answer ID GATE --answer TEXT --by operator --commit` (`--confirm --by operator --commit` for a provisional answer), which commits the item file alone on the worker's branch with `KB-Work` naming the item, so no hand `git commit` is made there; a reword of the item on its branch is `backlog.py --root <worktree> set ID ... --commit`, which commits the item file alone the same way. Each provisional answer is the review's to confirm.
   2. `land` works in a landing worktree of its own, so the checkout you run it in may hold changes of your own, untracked files included, and no step asks for it to be clean. A checkout another session works in is never one to claim or land in: make a worktree of your own before your first claim (`git worktree add <path> -b <branch> origin/main` from that checkout) and run the loop from there. `land` of one item's branch accepts a worker's worktree under either checkout's `worktree_dir` (`close` reads only your own), removes the worker's clean worktree itself and deletes its `work/<id>` branch once the item has landed.
   3. Where the project has a verification skill, run it on the changed files.
   4. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py land ID --trailer 'Co-Authored-By: ...'`, never the steps by hand: in a landing worktree of its own, so the checkout it is run in may hold its own changes, it fetches, rebases `work/<id>` on `origin/main`, then runs each landing step the project's settings name (`land_stale`, `land_eval`, `land_lint`; a step set to `[]` is skipped), then `done --commit` and the push of `land_push`. With a code lane (`lane_module`) the same `land` lands a code item in one run: it waits up to 1800 seconds (`--wait-merge SECONDS`; `--wait-merge 0` pushes and stops) for the item's merge request, read from git, then runs the second pass. A landing is a long command: start it in the background with `timeout` 7200000 ms and the log in the item's scratch directory, and wait for its `landed` or `refused` with the wait command above.
   It stops at the first failing step, moves the run state to `refused` with that step and names it (`land stopped at step <step>`): `landing lock`, `clean tree`, `branch`, `requests`, `repositories`, `fetch`, `rebase`, `done`, `checks`, `stale`, `eval`, `lint` or the push. Fix the cause and run it again.
   If `done` refuses, send the reasons back to the same worker or release the item (`python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py release ID`) and file what blocks it.
   Once the goal research story has landed, run `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py precheck SP` again before the next claim, since the research story's facts may already satisfy a sibling's check, and tighten each sibling check it now warns passes (`set ID --check CMD`, with its `--add-clause` mapping) so it fails until that item's own work, before that item is claimed: a check that passes before the work proves nothing (SP-5x5ut5ko, SP-6ukmjucf).
5. A provisional gate: take the recommendation (`answer ID GATE --provisional`) and go on, except a choice on an item whose touches guard a rule, which is a blocking operator gate, never settled by the worker. A blocking gate: its items wait; in an interactive session ask the operator now, as soon as its item's `blocked` event shows it, in one batch with the recommendations. An answer the operator gives by an option's place or by taking the recommendation is `answer ID GATE --option N --by operator` or `--recommended --by operator`, never the option's text retyped.
6. Before the review, run `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py runs SP --reconcile`: a crash, a killed landing or an unreachable store leave a run state apart from git, and only this writes it back; the plain `runs SP` that follows shows no `drift` line (exit 0).
7. Stop when `next` prints nothing ready. Report the horizon: what landed, and what waits on which gate or trigger.

## review SP
The review story is ready once every other item is done or dropped. Its checks are the project's `review_checks`. Its work:
1. Run `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py selectors`, which lists each check's `-k` selector with the tests it collects, and re-point or drop each open item whose check names one that is gone. Start a fresh-context reviewer, by default a headless session as run step 3 starts a worker, on the sprint's diff (`git log --grep "KB-Work"`). It runs in a worktree of its own, never in your checkout, with a brief in a scratch directory outside the worktree, both recorded when you make them (`python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py own <path> --class worktree|scratch --sprint SP`, and the session's pid with `--class process`), read-only: it edits no file, commits nothing, files no item and reports only gaps that affect correctness or a goal. Its brief names the paid commands as not allowed: `pool build` with `--ask` or `--redo ID`, and a bench run without `--dry-run`; it makes no paid model call. Its brief names a report file in the reviewer's scratch directory (`_cache/scratch/<review id>/gaps-report`) and tells it to write its final gap list to that report file before its last message; read the report file, not only the session's result, since `claude -p`'s result holds only the last turn, which can be a short follow-up. Its brief gives it each provisional answer of the sprint (the gate, its question and the recommendation taken) with the diff of the commits that carry it, so it reads the work each answer allowed.
2. Print what the work cost, one command per id: `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py cost --rework SP`, then the same for each story and each bug of the sprint. A cost read while the sessions that did the work are still open is provisional (the output says so); say it as a measure of the work, never as blame. Then `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py ops SP` prints the sprint's own operational rows (each item's `land.step` and `land.end`, each `done.refused` with its reasons, each worker's `agent.run`): show its output to the operator beside the cost.
3. Confirm or change each provisional answer with the operator only after the reviewer's report is in, with that report beside each answer (`answer ID GATE --confirm --by operator`, or a new answer plus a task or bug for the change): a confirmation given before the reviewer has read the work it allowed can be overturned by the reviewer's gap, which then becomes a later draft instead of a changed answer.
4. File an `S1` gap as a bug in this sprint. Park every other gap: a draft in no sprint (`new bug|story` without `--sprint`) with a link naming this review (`set ID --add-link 'parked: SP-... review'`). File a parked story with `--check CMD` (a command that proves its end state; `new` only says "to fill in: checks missing" and writes it, but `check` counts a story with no check an error) and a parked bug with `--repro CMD`, so the review's own checks stay green. `new bug` needs a `--repro` that fails now, and refuses one that only matches text in a file unless `--repro-reason TEXT` says why the behaviour cannot run (nine review gaps of SP-uwkr7iyl were refused as bugs and filed as stories): a non-`S1` gap with no repro command yet is parked as a draft story with its `--check`, or as a bug with its best failing command and `--repro-reason`. A commit you make yourself for this step or step 3 (the gate confirmations, the parked drafts) changes only item files, so it is a planning commit and carries no KB-Work line: `check-trailers` asks for none on it, and refuses one that names an id whose item file the commit does not change (the rule: each named id's file is changed, on one line; other changed item files may stay unnamed).
5. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py done <review id> --commit --trailer 'Co-Authored-By: ...'`, then push through the project's route. The review's `done` re-runs the checks of every done item of the sprint once on the tip and refuses, naming each, when one fails there.

## Stalled work
`python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py stalled` lists claimed or ready work that makes no progress (read only): each item's id and title with its signals `claim-no-commit`, `returned-no-commit`, `returned-staged`, `done-refused`, `check-timeout`, `land-same-step`, `mr-dead`, `red-main`, `lock-wait` and `finished-alive` (a worker whose result is written and whose own process still runs past the grace period: `dispatch`'s wait ends it with SIGTERM to that pid only when `backlog.json` sets `stop_finished` true, else stop it by hand). A signal whose input cannot be read shows as `unknown:<what>`: read that input by hand. What to do is the orchestrator's call, one step at a time, while a ready item with no signal remains to be taken: finish a `returned-staged` item in the orchestrator, run in the foreground; send the work back once (`dispatch --resume ID --message FILE`) with a narrower request; `release ID` and dispatch again with the failure named in the brief; file what blocks the item and take the next; or ask the operator with a gate.
