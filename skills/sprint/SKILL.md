# Run a sprint

`${CLAUDE_PLUGIN_ROOT}` is the directory that holds the tool scripts: the plugin's, or, where this text runs from a clone's own copy and still shows the variable, that clone's top directory. The Bash tool does not set it: write the path where a command below shows it.

The project's `backlog.json`, at its repository root, names the steps only some projects have. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py config` prints each setting and whether it came from the file or is a default. A step below that names a setting runs when that setting is set (a non-empty value, a non-empty argument list) and is skipped, said so in one line, when it is not; no step asks for a file the project does not have:
- `kb_root`: the kb root whose rule docs the project keeps; empty means the project has none, and every rule-pack command below is skipped.
- `docs_map`: the CSV that maps an item's touches to the docs it must keep right; empty means no docs warning.
- `land_stale`, `land_eval`, `land_lint`: the argument lists of the landing's stale-doc check, lookup eval and lint, run from the project's root before the push; `[]` means no such step.
- `lane_module`: the module that says which lane a path belongs to: a project with a code lane sends code through a merge request, and `done` waits for it; `""` means no code lane, and every commit lands as content (`done --commit`, then the push).
- `land_push`: the argument list of the push, run from the project's root (a first element ending in `.py` runs under python3, any other is the program, e.g. `["git", "push", "origin", "HEAD:main"]`): the landing's last step and the route for the claim commits. Its default is the kb's own gate script, which a host project has not, so a host names it.
- `item_dir`, `worktree_dir`, `scratch_dir`: where item files, worker worktrees and scratch directories sit; the brief and `dispatch` print the real paths, so never assume one.

Run each command on its own (no `;`, `&&`, pipes into other tools or loops): permission rules match single commands, so a chained command asks for approval or is refused in a headless run.

Whenever you name an item (in chat, a question, a subagent brief, a commit), give its id and its title together, never a bare id.

When `kb_root` is set, rules are asked for, not read up front: `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/rag.py pack --root KB_ROOT --set <name>` prints a step's tested rule questions and the line that answers each. The sets of this skill: `kb-sprint:plan`, `kb-sprint:start`, `kb-sprint:run`, `kb-sprint:review`, `kb-sprint:close` and `kb-commit` (before a commit or push of the orchestrator's own). Once an item is claimed, `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/rag.py pack --root KB_ROOT --item ID --budget 600` prints the rules of the docs its touches map to. Any other rule: `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/rag.py pack --root KB_ROOT "<question>"`. A rule you needed and no set gave you is a miss: say so in your report, with the question as you asked it.

## plan "<goal>"
1. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py new sprint --title T --goal G` creates the sprint, its blocking `start` gate, its review story and its goal research story (a research item: claim and work it first, then `done`). `claim --commit` commits only the item it claims, so the sprint's own file and its review and research stories get a planning commit first (`new sprint --commit`).
2. See what covers the goal: `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py find WORDS`, `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py tree --open` and `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py list --kind bug`: every `S1` and `P1`, then by priority and rank, as far as the goal needs. Put each in the sprint with `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py set ID --sprint SP`; every item edit goes through `set` or the other commands, never a hand edit of its JSON. A story or bug moves between sprints, or out of one, with `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py move ID --sprint SP|none`, and a done item goes back to work with `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py reopen ID --why TEXT`. A parked draft (a `parked: SP-...` link) is committed only when its `notes` name the fitness test it blocks or a real user's report. Break stories into tasks with `touches` and `checks` (`new task --parent ID --touch G --check CMD`): the files its change edits, each moved or renamed path or symbol's referrers (`python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py referrers PATH|SYMBOL... --item ID`) and, when `docs_map` is set, the docs it maps them to, never a glob wider than those files. Every symbol or constant a goal changes is run through `referrers` by name, and so is a new subcommand's facade registration, before the claim: each file it lists goes into `touches`, so a worker neither stops on a reader outside them nor widens them itself. A removed or renamed flag is run through `referrers` as a term, and each file that prints or documents it goes in too. A task that adds a new tool module names the docs map's csv, and one that adds a flag names its command facade and the readers it calls. An item that moves the figures of the benchmarks results file (`benchmarks.csv`) or the report code has `README.md` in its touches, since `report --check` reads its numbers. An item whose touches name code has the test file it extends in its touches now (`set ID --add-touch TEST_FILE`), before the start gate: `done` refuses a commit that changes a file outside them, and `check` warns of a test file the notes or goal name that no touch covers.
   Paths other sessions hold: after `git fetch`, `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py held --ref origin/main`, never messages to those sessions.
3. Map the goal's clauses to items. A clause no item carries is either already met in the tree (drop it and name the earlier item that delivered it: `git log --grep 'KB-Work: ID'`) or work still to plan: add an item for it.
4. Check each committed item's goal for its step order: for an item with a code-lane commit (`lane_module`), `done` and a push to the integration branch come after its merge request merges. A goal that puts them before is rewritten (`set ID --goal G`) or gets a gate (`gate add`) before `start`.
5. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py fmt` and `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py check` (no warning about a committed item's docs; a file in the touches of more than half of the sprint's items means they run one after another: split them), then `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py selectors` (a check selector that collects `NONE` names no test), `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py precheck SP` (it runs each committed item's checks once on the base: a check that already passes proves nothing yet) and `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py horizon --sprint SP`.
6. Review each committed story's goal for the outputs or figures it names against the checks: a clause no check reads is a missing check, recorded before the start gate is asked (`set ID --add-check CMD`). A goal clause that names a constant in the code (such as `LAUNCH_BUDGET_S`) is read against what the constant bounds there (`python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py referrers CONSTANT` lists where it is read): a clause that asks it to bound something else is rewritten before the start gate, since the check would prove the constant's bound and not the clause. A goal's time or share figure names the run it was measured on (profiled or not, which host, warm or cold) and the story's premise measures that run, not another. Each run figure a goal names (row counts, subsets, arms, reps, effort levels) maps to a flag of the command that runs it, or the clause is rewritten or a flag task added before the start gate, not found as a gate mid-work. A committed item whose touches name code has at least one check that runs the changed behaviour (a test selection it extends, or the tool run on a planted input), not only a read of source text (`check` warns when every check only reads files). A check that reads clone or host state a hand run can satisfy (refs, files outside the tree, a spool) is paired with one that runs the code path the goal names. A check that bounds a tool's git calls counts every git process (each `subprocess.Popen` of `git`), not one helper's calls. An item that adds or widens a cache carries a check that changing each input, the computing code included, gives a fresh value. A check that asserts a phrase's absence reads only the line or section the goal names, not the whole file. A goal that attributes rows or windows around a landing gets one check that drives the land sequence (a rebase, `done --commit`, a failing step) on a fixture, not a hand-set item file. Run each committed story's premise once and record the result in its notes (`set ID --add-notes TEXT`); a story whose premise does not reproduce is not committed. A committed item whose goal adds a refusal or a detector condition (a push, `done` or `check` that refuses, a finding key, a window) runs it once against today's main, on a fixture or the tool's own dry run, and a gate is asked before the start when it would fire now (on every push, or on a state main already holds), not found after it. A committed item whose goal names a paid run with a spend cap has its `--dry-run` estimate in its notes, and a cap below the estimate is a gate asked before the start. A choice the goal leaves open on an item whose touches guard a rule is a blocking gate, added before any code. Before asking, run `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py host-check SP`: on exit 1 show the operator the failing gate and its output and do not ask yet. Ask the operator to approve the goal and the committed items (AskUserQuestion: approve / change / cancel), showing each goal clause with its item's id and title, any clause dropped as met, and the gates the items will meet.

## start SP
Only on the operator's approval in this conversation:
1. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py answer SP start --answer approve --by operator`.
2. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py start SP`. It prints `warning:` lines for a sprint item whose mapped docs sit outside its `touches`: before any claim, ask the operator to move each named doc into that item's touches (`set ID --add-touch G`), and rerun `check`. It refuses while an answered gate's host check fails.

Never answer the start gate yourself.

## run [SP]
You are the orchestrator. Run from your own clone or git worktree, never a checkout another session works in: `claim` refuses a claim by a second session while one of them is still doing there. Loop:
1. Run `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py selfcheck` first and act on each failure before anything is claimed, then `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py horizon --sprint SP`, `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py next --sprint SP --all` and `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py stalled`.
2. From the ready list take up to four items whose `touches` do not overlap each other or any item in flight: after `git fetch`, `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py held --overlaps ID --ref origin/main` lists the claimed items, of every session, whose touches an item would meet (exit 1 when there is one). Right before the claim run `git fetch origin` and check that no local `work/<id>` branch exists. Claim each: `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py claim ID --by <name> --commit --trailer 'Co-Authored-By: ...'`, then push the claim commits once with the argument list `land_push` names (`config` prints it), run from the project's root.
3. Start one worker per item, whatever its kind, with two commands:
   - `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py brief ID [--known TEST=BUG]... [--probe TEXT]` prints the worker's brief: the item's JSON and goal text, its external tracker ids with their urls, the role file, the worktree and scratch directory, the in-flight sibling items and the files their `touches` change, the known failing tests, the fixed worker rules and the rules of the docs its touches map to. Name each test you already know fails on the host with `--known TEST=BUG`; a figure you add to a brief is measured, with the command beside it, never lifted from an example.
   - `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py dispatch ID` (the same `--known` and `--probe`) makes the worker's worktree on `work/<id>` from your `HEAD` and its scratch directory, writes the brief there and runs `claude -p --model sonnet --effort high --output-format json --add-dir <scratch> --max-turns N` in the worktree with the brief on stdin, until the session exits. Start it as a background command (the Bash tool's `run_in_background`, `timeout` 7200000 ms) so you are told when the worker returns, and never wait for it by polling. `N` is 60 for a task or subtask that is not research, 100 for a bug or a story with no tasks, 200 for a research item; `--max-turns N` names another cap. `--dry-run` prints the worktree, the brief path and the argv and starts nothing.
   The brief goes to the session on stdin, never as a trailing prompt argument, which `--add-dir` swallows. You run a command in a worker's worktree only in a subshell, `( cd <path> && ... )`, or with `git -C <path>`, never a bare `cd`.
   The Agent tool is the fallback, for a session that cannot start `claude -p`: one subagent per item with `isolation: "worktree"` on the worker agent (`kb-worker`, or `it-ops-kb:kb-worker` from the plugin), never passing the Agent tool's `model`, which replaces the agent's own. The prompt is the output of `brief ID`.
   A headless worker needs the project settings, so its work is counted through its `work/<id>` worktree: `dispatch` passes none of `--setting-sources`. Such a session cannot write under a protected path in permission mode `default` or `acceptEdits`: its brief then names staging copies, which you copy back and commit yourself, running the item's own checks there before the landing.
   Workers start from your `HEAD`, not from `origin/main`: your `HEAD` must include the pushed claim commits, so dispatch only after the claim sync of step 2.
4. When a worker returns, land its branch yourself, one at a time:
   1. Land an item only after its gates are answered or provisional. Read them on its branch (`git show work/<id>:<item_dir>/<id>.json`, its `gates`): an unanswered provisional gate, or a choice the report names that no gate records, goes back to the same worker (`claude -p --resume <session_id>`) to record and answer on its branch; an open blocking gate keeps the item waiting. An answer the operator gives you for a gate that exists only on the worker's branch is recorded by you in the worker's worktree: `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py --root <worktree> answer ID GATE --answer TEXT --by operator`, then a commit there of the item file alone. Each provisional answer is the review's to confirm.
   2. `git status --short` shows only your own changes; `land` removes the worker's clean worktree itself and deletes its `work/<id>` branch once the item has landed.
   3. Where the project has a verification skill, run it on the changed files.
   4. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py land ID --trailer 'Co-Authored-By: ...'`, never the steps by hand: it fetches, rebases `work/<id>` on `origin/main`, then runs each landing step the project's settings name (`land_stale`, `land_eval`, `land_lint`; a step set to `[]` is skipped), then `done --commit` and the push of `land_push`. With a code lane (`lane_module`) `land ID --wait-merge 1800 --trailer ...` lands a code item in one run: it waits up to that many seconds for the item's merge request, read from git, then runs the second pass. A landing is a long command: start it in the background with `timeout` 7200000 ms.
   It stops at the first failing step and names it (`land stopped at step <step>`): `clean tree`, `branch`, `requests`, `repositories`, `fetch`, `rebase`, `done`, `checks`, `stale`, `eval`, `lint` or the push. Fix the cause and run it again.
   If `done` refuses, send the reasons back to the same worker or release the item (`python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py release ID`) and file what blocks it.
5. A provisional gate: take the recommendation (`answer ID GATE --provisional`) and go on, except a choice on an item whose touches guard a rule, which is a blocking operator gate, never settled by the worker. A blocking gate: its items wait; in an interactive session ask the operator now, in one batch with the recommendations.
6. Stop when `next` prints nothing ready. Report the horizon: what landed, and what waits on which gate or trigger.

## review SP
The review story is ready once every other item is done or dropped. Its checks are the project's `review_checks`. Its work:
1. Confirm or change each provisional answer with the operator (`answer ID GATE --confirm --by operator`, or a new answer plus a task or bug for the change).
2. Print what the work cost, one command per id: `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py cost --rework SP`, then the same for each story and each bug of the sprint. A cost read while the sessions that did the work are still open is provisional (the output says so); say it as a measure of the work, never as blame.
3. Run `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py selectors`, which lists each check's `-k` selector with the tests it collects, and re-point or drop each open item whose check names one that is gone. Start a fresh-context reviewer, by default a headless session as run step 3 starts a worker, on the sprint's diff (`git log --grep "KB-Work"`). It runs in a worktree of its own, never in your checkout, with a brief in a scratch directory outside the worktree, read-only: it edits no file, commits nothing, files no item and reports only gaps that affect correctness or a goal.
4. File an `S1` gap as a bug in this sprint. Park every other gap: a draft in no sprint (`new bug|story` without `--sprint`) with a link naming this review (`set ID --add-link 'parked: SP-... review'`).
5. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py done <review id> --commit --trailer 'Co-Authored-By: ...'`, then push through the project's route. The review's `done` re-runs the checks of every done item of the sprint once on the tip and refuses, naming each, when one fails there.

## close SP
1. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py close SP --summary` prints one line per item close will delete, then each goal clause with the item that carried it or `unmet`, and changes nothing. Keep its `delivered by` list for the commit body.
2. **Retrospective.** From this sprint's evidence, list what went wrong in the process, not in the product: a `done` that refused, a check that passed although the item did not work, each bug fixed with what let it through, a gate that should have been asked earlier, a brief that missed something, and what cost more than its size suggested (`cost --rework SP` rerun now). Show the list to the operator. Each change they accept is parked: a draft story in no sprint with a link naming this close. Write nothing into the docs directly.
3. `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py close SP --commit --trailer 'Co-Authored-By: ...'` deletes the sprint, its items and the epics they finished, and commits that with `KB-Work: SP-...` in the last trailer paragraph and a body that lists the `delivered by` list and the retrospective's findings.
4. Push through the project's route.
5. **Clean up:** `close` removes, as a process of its own, the sprint's clean worker worktrees and `work/<id>` branches whose commits are on the integration main, and prints each `removed`, `deleted` and `close: kept <path or branch>: <reason>` line. Report them; a kept item stays until its reason is gone, never removed by hand or with `--force`.

## Self-check
`python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py selfcheck` (read only) opens every pass of `run`: one line when its checks hold, else a line for each that failed (`FAIL`, exit 1) or could not be read (`UNKNOWN`), with its remedy. Act on a failure before dispatching, or record why you cannot (a gate). The checks: `allow-rules` (a command the skills run has no allow rule in the project's settings: ask the operator, a run never edits settings), `checkout` (use a standalone clone as the orchestrator's clone), `hooks`, `host` (dispatch fewer workers), `claims`, `orphans` and `main` (the newest pipeline row is red: file it with `python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py red-pipeline`).

## Stalled work
`python3 ${CLAUDE_PLUGIN_ROOT}/_tools/backlog.py stalled` lists claimed or ready work that makes no progress (read only): each item's id and title with its signals `claim-no-commit`, `returned-no-commit`, `returned-staged`, `done-refused`, `check-timeout`, `land-same-step`, `mr-dead`, `red-main` and `lock-wait`. A signal whose input cannot be read shows as `unknown:<what>`: read that input by hand. What to do is the orchestrator's call, one step at a time, while a ready item with no signal remains to be taken: finish a `returned-staged` item in the orchestrator, run in the foreground; send the work back once (`claude -p --resume <session_id>`) with a narrower request; `release ID` and dispatch again with the failure named in the brief; file what blocks the item and take the next; or ask the operator with a gate.
