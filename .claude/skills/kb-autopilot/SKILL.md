# The autopilot manager: one tick

Started once as `/loop 15m /kb-autopilot` in the manager's own clone (never a checkout another session works in): each firing is one tick, and the repository, not the conversation, holds the state. A tick plans and judges through subagents and runs the sprints through headless runners (`python3 _tools/autopilot.py runner start`); `/kb-sprint` says what a runner and a review do (`## run`, Headless; `## review SP`; `## close SP`), and this skill orchestrates those and repeats none. Read these sections of the `kb/_self/` docs once, in one command:

```
python3 _tools/selfdoc.py section backlog "Dependencies, gates and triggers" backlog "Sprints" maintaining "Conduct for changes"
```

**Limited tick.** `--only SP[,SP]` limits the tick to the named sprints; without it the tick is as described below. Read `python3 _tools/autopilot.py status` first: a named sprint that is not an active (started) sprint is named in the digest and ignored, and no new sprint is planned in its place. A limited tick starts a runner only on a named sprint, never on another started sprint, and plans, researches and starts no new sprint (step 5); the review, retrospective and close of step 3 run only for the named sprints; the digest says the tick was limited and to which sprints (step 7); step 9 records it. Intake (step 2), open gates (step 4), orphans (step 6) and notify (step 8) are not narrowed: they run as in any tick, so notifications fire as usual.

Run each command on its own (no `;`, `&&`, pipes into other tools or loops): the shared permission rules match single commands. Name an item by id and title together, never a bare id. Never write auto-memory: no memory file, no `MEMORY.md`; what a tick keeps is `_cache/autopilot/state.json` (step 9) and what the commands print.

## The tick
1. **Orient.** `python3 _tools/autopilot.py status` prints the state: runners (`SP pid N alive`, or `SP ended CAUSE`), active sprints, open gates, unratified decisions and the last tick's number and actions. This tick is that number plus one (1 when none). Then `python3 _tools/kbgit.py sync` (the clone to `origin/main`), and `python3 _tools/backlog.py selfcheck`: act on each failure before anything else, as `/kb-sprint` Self-check says, or record in step 9 why you cannot.
2. **Intake.** `python3 _tools/backlog.py intake --file --network` writes the new candidates as drafts. When it filed any, or `git status --porcelain -uall kb/_self/backlog/` shows uncommitted drafts, start the **triage** subagent.
3. **Exited runners.** For each `SP ended CAUSE` line of status (a limited tick: only for a named sprint), `python3 _tools/autopilot.py runner-status SP` names what the run landed, the gates it left and the bugs it filed. Then by cause:
   - `sprint-done`: only the review story is left. The **review** subagent judges the sprint; then the sprint's review, the **retrospective** subagent and the close follow `/kb-sprint review SP` and `/kb-sprint close SP`, with these changes: the manager does what the operator would, `answer ITEM GATE --confirm --by autopilot` for each answer the reviewer lists under `confirm`, and for each under `change` the new answer, `answer ITEM GATE --answer TEXT --by autopilot --record`, with a bug that names it, filed `python3 _tools/backlog.py bounds file --origin review --kind bug --sprint SP --title T --severity S --repro CMD --goal G --evidence commit:SHA`; `python3 _tools/backlog.py done REVIEW-ID` once every provisional answer is confirmed; each retro story is filed as a draft with `python3 _tools/backlog.py bounds file --origin retro --sprint SP --title T --goal G --evidence commit:SHA` (only a `filed` result is given a gate; `merged` and `kept` go in the close commit body), given a gate (`gate add ID --question "Take this retro change: T?" --option take --option leave --recommendation take`) and picked: `answer ID GATE --answer take --by autopilot --record`. A pick that exits 2 is a kept gate (step 8).
   - `landed-limit`, `compaction`: work remains; the sprint takes a runner again in step 5, unless it is making no progress (step 5 reads that from the run history, which the tool keeps).
   - `blocked`: what waits is a gate (step 4), a trigger, a refused command or an unmerged `code/<id>` request; name it in the digest.
   - `error`, `timeout` (the runner ended the child at its deadline; a child that hits `--max-turns` ends as cause `error`): read the newest `_cache/autopilot/SP/*.stderr`; a second `error` or `timeout` in a row for one sprint (the last ticks' actions say) is not started again: name it in the digest.
4. **Open gates.** `python3 _tools/backlog.py horizon` names what waits on which gate. For each open blocking gate, answer it with its recommendation: `python3 _tools/backlog.py answer ITEM GATE --answer TEXT --by autopilot --record`. A gate of class `secrets` or `push` exits 2 and is left open: it is a kept gate (step 8). Never `--by operator`, never an answer for a kept class by another route.
5. **Refill to two runners.** Count the live runners in status. A limited tick refills only the named active sprints: a started sprint outside the list is not given a runner, and 5.1's plan, 5.2's research and start of a new sprint do not run (say in the digest that none was planned because the tick was limited). Before each refill, for the sprint it would run, `python3 _tools/backlog.py bounds stop --sprint SP --budget K --landed N` (`--budget` and `--landed` only with a run's `--landed K`; never `--runs-landed`: stop reads the sprint's run history, `_cache/autopilot/SP/runs.jsonl`, which `runner start` appends to when each run ends, not state.json, which a model writes), so a sprint whose last two runs landed nothing (no progress, an `error` or `blocked` run included) is not restarted forever: exit 1 and a first line `bounds: stop CAUSE: DETAIL` means start no runner for it and name that line as the reason in the digest; for `no-progress` it also names the sprint and its causes in a notification (step 8), once. A `no-progress` stop lasts until the operator, or the manager on the operator's word, has fixed the cause and runs `python3 _tools/backlog.py bounds reset-runs --sprint SP`, which clears that sprint's run history. For each missing runner:
   1. a started sprint with ready work and no live runner is taken first (`python3 _tools/backlog.py next --sprint SP --all`); else the **plan** subagent plans one, and when it names a `stop` reason (nothing ready, the sprint's budget spent, an inflow guard tripped) no sprint is planned: say it in the digest;
   2. the **research** subagent works the sprint's goal research story; the sprint is started only when it reports `done`: `answer SP start --answer approve --by autopilot --record` (which commits the item file and the decision row itself, as two commits), then `python3 _tools/backlog.py start SP --commit`, then `python3 _tools/kbgit.py sync --push` (a runner's worktree starts from `origin/main`, so the start must be pushed first);
   3. start the runner in the background, never in the foreground (it blocks while it supervises its child): `python3 _tools/autopilot.py runner start SP`, with the Bash tool's `run_in_background`, and `--landed K` only to bound a run. A start refused with exit 1 and `operator-present only` (an item touches files a headless run may not edit) is not retried: report the sprint in the digest as operator-present only, once, not every tick. A start it refuses (exit 2: two runners live, a sprint another runner holds, touches that overlap) is left for a later tick, except a refusal that names a dirty or diverged worktree: `python3 _tools/autopilot.py runner reset SP` names the cause, keeps the uncommitted files in a git stash and a diverged branch as `stale/SP-STAMP`, and frees the worktree (it refuses while a live runner holds SP); then start the runner once more in this tick, and put the cause and what was kept in the digest, so the refusal does not come back every tick. A runner that was killed leaves status `SP ended error` (a SIGTERM or SIGHUP, or a gone process, ends it in `error`): step 3 treats it as any other `error`;
   4. run `python3 _tools/autopilot.py status` again, read the runner's pid from its `SP pid N alive` line (once more after a moment when it is not there yet) and record it: `python3 _tools/backlog.py procs --record N`.
6. **Orphans.** `python3 _tools/backlog.py procs` lists what runs on in the clone; `backlog.py procs --end` ends the owned orphans only, after its grace.
7. **Digest.** `python3 _tools/kbdecide.py digest --commit` writes `kb/_self/reports/autopilot-digest.md` and commits that file alone (`kbgit.py sync` refuses a tracked change left uncommitted), the autopilot's unratified decisions for the operator to ratify or revert (`python3 _tools/kbdecide.py list --root _self --status active` lists them), with the tick's own lines (a limited tick says so, and to which sprints, with each ignored sprint id): what each step did, and why no work was started when none was. `python3 _tools/kbgit.py sync --push` then pushes what the tick committed (the digest, the item files and each `--record` answer's decision row); a tick leaves no tracked change uncommitted.
8. **Notify.** Only for a kept gate: an open blocking gate of a class the autopilot may not answer (`secrets`, `push`; `kb/_self/backlog.md`, Dependencies, gates and triggers), not named in the last tick's actions. Load PushNotification with ToolSearch (`select:PushNotification`) and call it once per such gate: the item's id and title, the gate's question, one line. Also once for a sprint stopped for no progress (`bounds: stop no-progress`), not named in the last tick's actions: its title and causes, one line. Never for an error, a finished sprint, a refused command or the digest: they wait in the committed digest.
9. **Record the tick.** Write `_cache/autopilot/state.json` (never committed): `{"tick": N, "actions": ["short line per step that did something"]}` (a limited tick starts its first line with `limited to SP[,SP]`), with each kept gate it notified, which the next tick reads from status.

## The subagents
Each judgment step runs in a fresh subagent on the session model (`subagent_type: "general-purpose"`, no `model`). Its brief names the item or sprint, the step's rule (below), that it runs each command on its own, asks no question and answers no gate, and ends: "Reply with one JSON object and nothing else". The tick reads only that object; a reply that is not one JSON object with those keys is asked once to resend it, then the step is skipped and said in the digest.
- **triage** (`/kb-backlog triage` over intake's drafts; it commits the kept item files with `KB-Work` and deletes the dropped uncommitted ones): a draft is kept only when it names a failure that happened, with its evidence (a commit, a test id or an ops row), and `python3 _tools/backlog.py similar` finds no near-duplicate. Keys: `keep` (ids), `drop` (ids), `merge` (a list of `{"id", "into"}`), `why` (one line).
- **review** (the sprint's diff, as `/kb-sprint review SP` step 3, with each item's goal and `backlog.py cost --rework SP`): reports only gaps that affect correctness or a goal, and files each with `bounds file --origin review --kind bug` (no evidence or a near-duplicate is not filed). Keys: `verdict` (`pass` or `gaps`), `confirm` (a list of `{"item", "gate"}`), `change` (a list of `{"item", "gate", "answer", "why"}`), `gaps` (ids of the bugs it filed).
- **retrospective** (`/kb-sprint close SP` step 2: what went wrong in the process, from the sprint's evidence; no product findings). Keys: `stories` (a list of `{"title", "failure", "evidence", "goal"}`, each naming a failure that happened), `no_change` (one line each).
- **plan** (`/kb-sprint plan` steps 1 to 5, not the operator's approval): Keys: `sprint` (the id, or an empty string), `goal`, `items` (a count), `stop` (an empty string, or `no-ready`, `budget` or `guard`).
- **research** (the sprint's goal research story: claim it, work it with the kb tools and the live docs, `done`): Keys: `sprint`, `done` (true or false), `gaps` (one line each).

## Compact Instructions
A compaction keeps, in this order: the tick number; the runners (sprint, pid, alive or cause); the kept gates not yet notified and those notified (item id and title, gate); the sprints in review, retro or close and the step each is at; the last tick's actions. Everything else is read again: `python3 _tools/autopilot.py status` prints it, and its `SessionStart` hook after a compaction does too. Never keep a subagent's reply beyond its JSON keys.
