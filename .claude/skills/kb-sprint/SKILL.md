# Run a sprint

Read the conduct rules first (`selfdoc.py section` prints one section with its line numbers):

```
python3 _tools/selfdoc.py section maintaining "Conduct for changes"
```

Every other rule of `kb/_self/` is asked for, not read up front. When a step below is reached, run its set: `python3 _tools/rag.py pack --root _self --set <name>` prints that step's tested rule questions, the line that answers each (`path:line`) and the decisions tied to them. The sets of this skill:
- `kb-sprint:plan`: before `plan "<goal>"`
- `kb-sprint:start`: before `start SP`
- `kb-sprint:run`: before `run [SP]`
- `kb-sprint:review`: before `review SP`
- `kb-sprint:close`: before `close SP`
- `kb-commit`: before a commit or a push of the orchestrator's own
Once an item is claimed, for each item you brief: `python3 _tools/rag.py pack --root _self --item ID --budget 600` prints the rules of the docs its touches map to and the decisions that apply to it.

Any other rule: `python3 _tools/rag.py pack --root _self "<question>"` (`-q` for several parts, `--budget 400`). `coverage: good` names a tested question: follow its line. `weak` or `none`: `python3 _tools/kb_ask.py --root _self "<question>"` has a reader quote the answering lines from the sections, or read the section it names with `python3 _tools/selfdoc.py section DOC HEADING`. A rule you needed and no set or question gave you is a miss: say so in your report, with the question as you asked it.

Run each command on its own (no `;`, `&&`, pipes into other tools or loops): the shared permission rules match single commands, so a chained command asks for approval or is refused in a headless run.

Whenever you name an item (in chat, a question, a subagent brief, a commit), give its id and its title together, never a bare id.

## plan "<goal>"
Rules of this step: `python3 _tools/rag.py pack --root _self --set kb-sprint:plan`.

1. Run `python3 _tools/backlog.py new sprint --title T --goal G`. It creates the sprint, its blocking `start` gate, its review story and its goal research story (a research item: claim and work it first, with the kb tools and the live docs for gaps, writing kb facts and gap entries through the kb skills, then `done`). Before the research story is claimed, run the goal's questions through `python3 _tools/rag.py pack -q Q -q Q` (one `-q` per question) and narrow the research story's goal with `python3 _tools/backlog.py set ID --goal G` to the questions whose coverage is weak or none, naming them; a goal whose every question is `good` gets a research story whose done needs no outside facts, finished with a `No outside facts: <reason>` note (the pack's answers stand as its findings). `claim --commit` commits only the item it claims, so the sprint's own file and its review and research stories get a planning commit first (`new sprint --commit`), before any claim sync.
2. Check what covers the goal with `python3 _tools/backlog.py find WORDS`, then pick the stories and bugs with `python3 _tools/backlog.py tree --open` and `python3 _tools/backlog.py list --kind bug`: every `S1` and `P1`, then by priority and rank, as far as the goal needs. A parked draft (a `parked: SP-...` link, from an earlier review or close) is committed only when its `notes` carry a line naming the fitness test it blocks (the held-out answer rate, a content sprint) or a real user's report; one that names neither stays a draft in no sprint, listed in the plan, never promoted (`kb/_self/backlog.md`, Sprints). Put each in the sprint with `python3 _tools/backlog.py set ID --sprint SP` (every item edit goes through `set` or the commands below, never a hand edit of its JSON; a story or bug moves between sprints, or out of one, with `python3 _tools/backlog.py move ID --sprint SP|none`, which writes the status that sprint gives it, and a done item goes back to work with `python3 _tools/backlog.py reopen ID --why TEXT`; the planning commit names in `KB-Work` only the items whose files it changes). Break stories into tasks as `/kb-backlog` does, with `touches` and `checks` (an item's `touches` are planned, not guessed, when it is filed or scheduled: the files its change edits, each moved or renamed path or symbol's referrers (`python3 _tools/backlog.py referrers PATH|SYMBOL... --item ID`) and the `kb/_self/` docs `kb/_self/map.csv` maps its code to (`python3 _tools/selfdoc.py map <file>`), never a glob wider than those files (a `_tools/bl_*.py` glob meets every other worker's item, BG-ncpteupy); a docs warning `backlog.py check` gives for the item is acted on then, by adding the docs it names (`set ID --add-touch DOC`), so the warnings stay few enough to act on) (`new task --parent ID --touch G --check CMD`, later `set ID --add-touch G`); a task that changes code carries the `kb/_self/` docs `kb/_self/map.csv` maps to it in its own `touches`, not a later docs task. A change to how agents read docs or call a tool puts every consumer of that route (skills, `.claude/agents/` definitions, `AGENTS.md`, headless runs such as `_tools/ql_research.py`) in some item's `touches`.
   Paths other sessions hold: after `git fetch`, `python3 _tools/backlog.py held --ref origin/main` (each claimed item's touches, claimer and sprint), never messages to those sessions.
3. Map the goal's clauses to items. Split the goal into its clauses and name, for each, the committed item that carries it (its `goal` or `touches`). A clause no item carries is either already met in the tree, so drop it from the goal and name the earlier item that delivered it (`git log --grep 'KB-Work: ID'`), or work still to plan: add an item for it. Never leave a clause with no item: `close --summary` could not name one for it.
4. Check each committed item's goal for its step order against the lane rules. Read the order the goal gives for done, `sync --push` and a push to `main`: for an item with a code-lane commit (`_tools/kblane.py`), `done` and a push to `main` come after its `code/<id>` merge request merges, and `sync --push` before then only opens that merge request. A goal that puts `done` or a push to `main` before the merge is rewritten to the lane's order (`python3 _tools/backlog.py set ID --goal G`), or, when the right order is a choice, gets a gate (`gate add`) naming the options and a recommendation; do it before `start`, since only the worker's brief would catch it (SP-bwlxievv, where a goal put `done` before `sync --push` for code items). A bug or story whose goal names a fix mechanism has it run through `python3 _tools/rag.py pack --root _self` too: a rule it meets is named in the goal, or the mechanism is left open (SP-owbgisoj).
5. `fmt` and `check` (no warning about a committed item's docs: add the docs it names to that item's `touches`; a warning that a file is in the touches of more than half of the sprint's items means they will run one after another: split those edits by section into separate items, or order them up front; a warning that an item's repro or check names a file that is gone: point it at the file's new place or drop the item), then `python3 _tools/backlog.py selectors` (a selector of the sprint's items that collects `NONE` names no test: fix it before the start), then `python3 _tools/backlog.py precheck SP` (it runs each committed item's checks once on the base; a check that already passes proves nothing yet: make it fail until the work is done, or say in the item's notes that it passes before the work and why), then `python3 _tools/backlog.py horizon --sprint SP` (it shows the start gate as the one thing everything waits on).
6. Review each committed story's goal for the outputs or figures it names (such as four totals, a session total or a shared figure) against the checks of the story and its tasks: a named figure no check reads is a missing check, recorded before the start gate is asked (`set ID --add-check CMD`, or a task that adds it). Every clause of the goal maps to a check assertion, not only the figures it names: a clause a check does not read is recorded the same way (SP-sz5fbvqn: a check proved an alias row, not the goal's clause that the pair is in no alias file yet). A committed item whose goal adds or widens a rule that attributes rows, windows or cost to an item (a capture row, a work window, a cost line) carries, beside its positive check, one check that a session outside the rule is not attributed (SP-mlemdqbn: a worker's prompts were proved to count, an orchestrator's were not proved to stay out, and BG-lbazs72w was found after landing). A goal about attributing work (windows, cost lines) lists, before the start gate is asked, every row kind and every session that writes one (the `ql_capture` constants `WORK_ACTIONS`, `OPEN_ACTIONS` and `AGENT_ACTIONS`, the orchestrator's sessions and the workers'), each with the item that covers it; a row kind or session no item covers is a story added or a clause dropped (SP-owbgisoj: planning looked only at branch rows, missed the orchestrator's own claim rows, and BG-m6fknqr5 was left to S2). Run each committed story's premise once, before the start gate is asked: the command in its `notes` or on a `Premise:` line there; record the result in its notes (`set ID --add-notes TEXT`), and a story whose premise does not reproduce is not committed: reshape it to a test-only item that pins the behaviour, or move it out (`move ID --sprint none`). A committed story whose goal names a quality of answers (an answer rate, a verdict's accuracy, a ranking) has as its premise a probe of that quality on held-out inputs (such as `rag.py eval --file` on questions the work will not tune on), so a gate the probe raises is asked before the start, not mid-work. A committed item whose goal names a paid run with a spend cap (a smoke record, a probe, a benchmark record) has that command's `--dry-run` run on the planning host with the command's real flags, before the start gate is asked, and its notes record (`set ID --add-notes TEXT`) the command, the run count, the sequential runtime (the run count times the mean wall seconds of a run in the last record) and the spend at each pinned model's prices (`kb/public/claude/models.csv`). A spend cap below the estimate is a spend cap gate asked before the start, not mid-run (`gate add`, the estimate named in the question); a run too long sequentially gets its parallel-run story before the start. A paid command with no `--dry-run` that estimates it (every `benchmarks.py` scenario but pool, BG-wapzksub) is never run to look: its notes say `no estimate`, and the operator is asked for the spend cap in a gate before the start (SP-2vhfsn4o: a goal said `--max-usd 5` for a command whose dry run estimated 23.37 USD, the gate came after the code and the first smoke spent 26.62; SP-hm4qgf3t: a record was sized only during the run, 3,150 runs and 20-30 h, so a story was filed mid-sprint). List each committed item whose `touches` are rule-guarding (the `agents-rule` paths of `_tools/bl_authority.py`) and ask each choice its goal leaves open as a blocking gate then (`gate add`), not after the code. A figure a gate's question or options rest on (a limit, a width, a count) is measured or read from the tree before the gate is asked, and the question names the command that gave it (run step 3, the brief's figures). Before asking, run `python3 _tools/backlog.py host-check SP`: it runs the `--host-check` command of each answered gate that names a host setup, on this host, and records the result; on exit 1 show the operator the failing gate and its output (the setup is not in place: enable it, or change the gate) and do not ask yet. Ask the operator to approve the goal and the committed items (AskUserQuestion: approve / change / cancel). A goal figure that a gate's answer turns into a maximum (an answer of at most N) is rewritten with `set ID --goal G` before the start gate is asked. Show each goal clause with the id and title of its item, any clause dropped as met with the earlier item that delivered it, and the gates the items will meet.

## start SP
Rules of this step: `python3 _tools/rag.py pack --root _self --set kb-sprint:start`.

Only on the operator's approval in this conversation:
1. `python3 _tools/backlog.py answer SP start --answer approve --by operator`.
2. `python3 _tools/backlog.py start SP`. It prints `warning:` lines for a sprint item whose mapped docs sit outside its `touches` (an item planned before `check` warned of it): before any claim, ask the operator to move each named doc into that item's `touches` (`set ID --add-touch G`), and rerun `backlog.py check`. It runs each answered gate's host check on this host and refuses while one fails (`backlog.py host-check SP` shows the output), and warns of a gate that names a host setup with neither a host check nor a `host_unchecked` reason.

Never answer the start gate yourself.

## run [SP]
Rules of this step: `python3 _tools/rag.py pack --root _self --set kb-sprint:run`.

One suite, `python3 _tools/tests.py` (`kb/_self/backlog.md`, Working on items): a worker of step 3 runs the item's own checks and may run it, never `--changed` (its `/kb-verify` skips that step: `kb-verify` step 5), the gate per landing runs the `tests.py --changed origin/main` of `sync --push` in step 4, and the review story's checks run `backlog.py check` and `tests.py` once at sprint end, after the reviewer has returned (the review step below).

You are the orchestrator. Run from your own clone or git worktree, never a checkout another session works in (each session works in its own git worktree from its first command (`git worktree add`), never a checkout another session works in: `claim` records the claims made in a working tree in its own git dir and refuses (exit 1, naming the other session) a claim by a second session while one of them is still doing there): a second orchestrator starts its own (`kb/_self/backlog.md`, Running a sprint). Loop:
1. Run `python3 _tools/backlog.py selfcheck` first (Self-check) and act on each failure before anything is claimed, then `python3 _tools/backlog.py horizon --sprint SP` and `python3 _tools/backlog.py next --sprint SP --all`. A sprint whose goal or items can only run on one host and was planned elsewhere runs, as the first step of its first pass on that host, each committed story's `Premise:` command there, records each result with `python3 _tools/backlog.py set ID --add-notes`, and asks the operator about any premise that does not reproduce (reshape the story to a test-only item, or move it out) before step 2's claims; a host you cannot reach runs the premise through the project's route for that host, which the sprint's orchestrator brief names.
2. From the ready list, take up to four items whose `touches` do not overlap each other or any item in flight: after `git fetch`, `python3 _tools/backlog.py held --overlaps ID --ref origin/main` lists the claimed items, of every session, whose touches an item would meet (exit 1 when there is one). Before a claim, `grep -rn` the existing tests and run `python3 _tools/selfdoc.py stale` for the behaviour the fix changes, and list what they name in the item's `touches`, with any skill the work edits, up front: `done` refuses a file outside the touches. Right before the claim run `git fetch origin` and check that no local `work/<id>` branch exists: two sessions can pass `held` together and the second push conflicts. Claim each: `python3 _tools/backlog.py claim ID --by <subagent name> --commit --trailer 'Co-Authored-By: ...'`, then push the claims once, the claim sync: `python3 _tools/kbgit.py sync --push`.
   - Shared-file move: a task that moves code out of a file other items edit (a split of `backlog.py` or `kbgit.py`) is announced first to the manager session; in-flight items on that file drain: no new claims on it, and `python3 _tools/backlog.py held --overlaps ID --ref origin/main` shows none of the mover's claimed touches overlapping before the move starts; the move is one atomic commit per file moved: new modules git-added, mapped in `kb/_self/map.csv`, the tools map, docs in the same commit, tests keeping their names, patch targets repointed, and a `bl_` or `kg_` module never importing `backlog` or `kbgit` at any depth; once the move is on main, the sessions are told to rebase onto it before their next commit on the file.
3. Start one worker per item, whatever its kind (a task or subtask, an `S1` or `S2` bug and its tasks and subtasks, a story or bug with no tasks yet for its breakdown), with two commands (SP-s5fdczv7, where headless Sonnet sessions did an `S2` investigation bug and an untasked story, and the brief was written by hand):
   - `python3 _tools/backlog.py brief ID [--known TEST=BUG]... [--probe TEXT]` prints the worker's brief: the item's JSON and goal text, its external tracker ids with their urls, the role file `.claude/agents/kb-worker.md`, the worktree and scratch directory, the in-flight sibling items and the files their `touches` change, the known failing tests, the fixed worker rules and the rules of the docs its touches map to. Name each test you already know fails on the host with `--known TEST=BUG` (the bug filed for it, so the worker neither files it again nor guesses a cause), and for a bug whose cause is unproven give the result of the one probe you ran first (one short run, far smaller than a worker pass) with `--probe TEXT`, so the worker starts from the cause (`kb/_self/backlog.md`, Running a sprint).
   - A figure you add to a brief (in `--probe TEXT`, a `--known` note or a sibling's briefing) for the worker to rely on, a length, a limit, a count or the shape of a name, is measured, with the command that measured it beside it; one lifted from an example or from memory is never given as a figure (SP-vayhvwfy, where a worker modelled a worktree name's length on the brief's example `agent-ST-xxxxxxxx` and a gate's limit was confirmed on it, while an Agent-tool worktree here is `agent-` and 17 hex characters, 6 characters longer).
   - `python3 _tools/backlog.py dispatch ID` (the same `--known` and `--probe`) makes the worker's worktree `.claude/worktrees/agent-<id>` on `work/<id>` from your `HEAD` and its scratch directory `_cache/scratch/<id>/`, writes the brief there and runs `claude -p --model sonnet --effort high --output-format json --add-dir <scratch> --max-turns N` in the worktree with the brief on stdin, started with the project settings, until the session exits. Start it as a background command (the Bash tool's `run_in_background`, `timeout` 7200000 ms) so you are told when the worker returns, never in the foreground of your own session, and never wait for it by polling. `N` is 60 for a task or subtask that is not research, 100 for a bug or a story with no tasks, 200 for a research task or subtask (its scope kb content only, as a research story's), a research story or an investigation bug; `--max-turns N` names another cap. It takes the session model only when the operator asks for it (`--model` naming that model instead of `sonnet`). It records the session's pid when it starts and its `session_id` when it exits in the claims ledger of the git dir (`worker_pid`, `worker_session`), writes the session's JSON output to `<scratch>/result.json` and exits 0 only when the session exited 0 without `is_error`. `--dry-run` prints the worktree, the brief path and the argv and starts nothing.
   The brief goes to the session on stdin, never as a trailing prompt argument, which `--add-dir` swallows (it takes several paths; SP-d3hybrlv, where the session exited 1 with `Input must be provided either through stdin or as a prompt argument when using --print`); the scratch directory sits outside the worktree for the worker's throwaway files and its `.claude/` staging copies, one directory for both (SP-s5fdczv7, where the first headless worker had no scratch directory and its proof script went to `/tmp`). You run a command in a worker's worktree only in a subshell, `( cd <path> && ... )`, or with `git -C <path>`, never a bare `cd`, since your working directory persists between Bash calls.
   The Agent tool is the fallback, for a session that cannot start `claude -p`: one subagent per item with `isolation: "worktree"` on `subagent_type: "kb-worker"` (the newest Sonnet at high effort), never passing the Agent tool's `model`, which replaces the agent's own; when the Agent tool does not list `kb-worker` (agent files load at session start, so a session that added or changed it cannot use it), `subagent_type: "general-purpose"` with `model: "sonnet"` (kb-worker's model; general-purpose would take the session's). The prompt is the output of `python3 _tools/backlog.py brief ID`, which points the subagent at the role file.
   A headless worker needs the project settings (a session started with `--setting-sources local` loads no capture hooks, so its work never reaches `backlog.py cost`; a worker started with the project settings is counted through the `branch` row of its `work/<id>` worktree, since a work window opens from a `claim` or from the session's `work/<id>` branch: `kb/_self/usage.md`, In the query log): `dispatch` passes none of `--setting-sources`. Such a session cannot write under `.claude/` in permission mode `default` or `acceptEdits`, which prompt for protected paths with no one to answer (`bypassPermissions` allows it; `kb/public/claude/settings-and-scopes.md`): its brief then names staging copies of the `.claude/` files its item touches, which `dispatch` copies to `<scratch>/staging/<repository path>` and the worker edits instead; they sit outside its worktree, since copies left in the worktree are untracked and `release_worker_worktree` refuses it. You copy them back and make every edit under `.claude/` yourself. After copying them back into the worktree run `python3 _tools/selfdoc.py check` and the item's own `checks` there, before the commit and the landing: the worker's checks read the worktree's unchanged `.claude/` files, not the copies it edited (SP-pbekfhaz, where a worker reported `problems=0` while its staged text held a dead heading reference).
   Workers start from your `HEAD`, not from `origin/main`: `dispatch` makes the worktree from the `HEAD` of the checkout or worktree it runs in, and `.claude/settings.json` sets `worktree.baseRef` to `"head"`, which branches each fallback isolation worktree the same way. Your `HEAD` must include the pushed claim commits, so dispatch only after the claim sync of step 2. That is the session's own working directory: a session started in another checkout (a shared clone on an old `main`) while it orchestrates from its own clone branches its workers from that other checkout's `HEAD`, and only the worker's fetch-and-rebase brings them to `origin/main`; start the orchestrator's session in its own clone or worktree. The brief names no base to check out by hand: the worker checks its base against `origin/main` and rebases only if behind (`.claude/agents/kb-worker.md`, rule 2).
   A sprint in a second clone (another sprint holds the session's own clone): run the commands against that clone (`python3 _tools/backlog.py --root <clone> dispatch ID`) after `git -C <clone> fetch origin` and a fast-forward of its `main` to `origin/main`, so its `HEAD` holds the claim sync; the worktree is then made in that clone. On the fallback, the Agent tool gives a subagent no working directory of its own (it starts in the session's), so `isolation: "worktree"` would branch from the wrong clone. Start a fresh Claude session in that clone and orchestrate from there. A session that cannot start there makes each worker's worktree by hand, after the claim sync: `git -C <clone> fetch origin`, then `git -C <clone> worktree add <clone>/.claude/worktrees/<id> -b work/<id> origin/main`; it starts the subagent without `isolation` and names that path in the brief, where the worker runs every command by absolute path into it (`python3 <path>/_tools/...`, `git -C <path> ...`), since its working directory stays the session's. Close step 5 cleans these worktrees up with its commands run against that clone (`git -C <clone>`).
   The brief's fixed rules are the tool's, in `_tools/bl_dispatch.py`; the rules of the project's own docs come from `rag.py pack --root _self --item ID` (`kb/_self/backlog.md`, Running a sprint). An item with a single commit and a narrow `touches` may be done in this session instead; a code-lane item done there lands with `python3 _tools/backlog.py land ID --branch BRANCH --wait-merge 1800` (`BRANCH`: its commits on a `work/<id>` branch or on your own branch), which waits for its `code/<id>` merge request and runs `done` and the push, so no hand poll of `origin/main` is needed (SP-ktup3cha, where an item committed here was polled by hand before `done`).
4. When a worker returns (its headless session exits, or its fallback subagent returns), land its branch yourself, one at a time:
   1. Land an item only after its gates are answered or provisional. Read them on its branch (`git show work/<id>:kb/_self/backlog/<id>.json`, its `gates`): an unanswered provisional gate, or a choice the report names that no gate records, goes back to the same worker (`claude -p --resume <session_id>`, the `session_id` of its JSON output; SendMessage for a subagent) to record and answer on its branch; an open blocking gate keeps the item waiting (step 5). An answer the operator gives you for a gate that exists only on the worker's branch is recorded by you in the worker's worktree, not by the worker: `python3 _tools/backlog.py --root <worktree> answer ID GATE --answer TEXT --by operator`, then a commit there of the item file alone (`git -C <worktree> add kb/_self/backlog/<id>.json`, `KB-Work: <id>` in the last trailer paragraph), so `land` reads it on `work/<id>` (`kb/_self/backlog.md`, Running a sprint). Each provisional answer is the review's to confirm (review step 1).
   2. `git status --short` shows only your own changes (another session's files in your checkout: stop and move to your own clone or worktree); `land` refuses a tree with untracked files too, but moves the untracked intake drafts (`kb/_self/backlog/*.json` that the SessionStart hooks file, with a `fingerprint` and a `detector` link) of the checkout it runs in to `_cache/intake-drafts/<checkout name>/` itself, when they are the tree's only change, and says so before its `clean tree` step: they stay there when it stops at a later step, so copy back the ones triage keeps (the drafts in a finished worker's worktree go to `_cache/intake-drafts/<worktree name>/` the same way when `land` removes that worktree; any other untracked or modified file still refuses the tree or the worktree and nothing is moved); `land` refuses a branch checked out in another worktree, except a finished worker's, which it removes itself: `git worktree remove` and `git branch -D` are denied to agents (`.claude/settings.json`), and `land`, a process of its own, removes the worker's clean worktree under `.claude/worktrees/` (locked by Claude Code, or unlocked and named `agent-*`) and, once the item has landed, deletes its `work/<id>` branch. While a process still runs in the worktree it refuses too, naming each pid: ask the worker to end it (`claude -p --resume <session_id>` for a headless worker, whose session has exited; SendMessage for a fallback subagent), or end it yourself, then land again;
   3. `/kb-verify` on the changed files;
   4. `python3 _tools/backlog.py land ID --trailer 'Co-Authored-By: ...'`, never the steps by hand. It runs `git fetch` and rebases `work/<id>` on `origin/main` (the integration remote's `main` as fetched, never local `main`, which your own clone or worktree cannot move while another worktree has it checked out), then: `land ID --wait-merge 1800 --trailer ...` lands a code item in one run: after the first pass it waits up to that many seconds for the item's merge request, read from git, then runs the second pass, so no session polls the forge itself. After a run that pushed, `land` fast-forwards your checkout to `origin/main` when it is clean and on a branch whose upstream is `origin/main`, so the next claim starts from the pushed `main` (it says so; a dirty or diverged checkout it leaves alone and names why, which you fix before the claim).
      - a content-only item (its commits touch only kb roots, `kb/_self/*.md` and item files): `done --commit`, then `sync --push` straight to `main`;
      - an item with a code-lane commit (`_tools/kblane.py`: any commit that changes code, `kb/_self/_decisions.csv` or an item file beside code is one) not yet on the integration `main`: `sync --push` sends the range as a `code/<id>` merge request; `main` does not move and the item is not done. On the next pass, once the request has merged, run the same `land` again: it rebases onto the merged `main` (the merged commits keep their hashes), runs `done --commit` and pushes the item file;
      - it runs `python3 _tools/selfdoc.py stale --since origin/main` first, then, when the landing changed `_tools/`, the lookup eval and the contract lint, before `sync --push` (workers never run the eval or the lint; the full `tests.py` runs at the review story). A landing is a long command: start it in the background with the Bash tool's `timeout` 7200000 ms, never the default.
   After a `land` that sent a `code/<id>` merge request, read the request: `glab mr view code/<id> -F json -R <project url>`. `state` `opened` with a `merge_error` is an auto-merge that failed: retry once with `python3 _tools/backlog.py merge <id>` (it merges only the item's own `code/<id>` on the integration project, and a headless run only its own sprint's; `glab mr merge` itself is not allowed) and name the error in your report; a retry that fails too is reported with its error and left to the operator, never tried a third time. `opened` with no `merge_error` waits for the next pass's `land`.
   It stops at the first failing step and names it (`land stopped at step <step>`): `clean tree`, `branch`, `fetch`, `rebase` (aborted, nothing changed: after `git fetch`, rebase the branch on `origin/main` by hand as `/kb-git-sync` does), `done`, `checks` (a code item's own check or repro failed: nothing was pushed; fix it), `stale` (a doc the range leaves stale: read it and name it in the `Self-Reviewed` trailer, or edit it), `rag.py eval`, `lint` or `kbgit.py sync --push` (`/kb-git-sync`). Fix the cause and run it again.
   If `done` refuses, send the reasons back to the same worker (as in step 4.1) or release the item (`python3 _tools/backlog.py release ID`) and file what blocks it; for an unmerged `code/<id>` request it names the request to merge.
   A bug filed while landing is filed with `--sprint SP` (an active sprint; or `backlog.py move ID --sprint SP`, which makes a draft bug `todo` there), committed on its own, then claimed, before the commit that fixes it: `check-trailers` refuses a `KB-Work` id not in a started sprint (`kb/_self/backlog.md`, Working on items).
5. A provisional gate: take the recommendation (`answer ID GATE --provisional`) and go on, except where a choice the goal leaves open on an item whose `touches` name a rule-guarding path (the `agents-rule` paths of `_tools/bl_authority.py`: `_tools/bl_*`, `_tools/backlog.py`, `.claude/skills/`, `.claude/settings.json`, `AGENTS.md` and the others) is a blocking operator gate, added and asked before any code is written, never settled by the worker and held after the work; and a provisional answer about a shared map or naming rule (a map such as `kb/_self/map.csv`, an id or name scheme other items follow) is put to the operator when it is recorded, not left for the review. A blocking gate: its items wait. In an interactive session ask the operator now, in one batch with the recommendations.
6. Stop when `next` prints nothing ready. Report the horizon: what landed, and what waits on which gate or trigger (each with its question).

## review SP
Rules of this step: `python3 _tools/rag.py pack --root _self --set kb-sprint:review`.

The review story is ready once every other item is done or dropped. Its checks are `python3 _tools/backlog.py check` and `python3 _tools/tests.py`. Its work:
1. Confirm or change each provisional answer with the operator (`answer ID GATE --confirm --by operator`, or a new answer plus a task or bug for the change), the ones workers recorded for choices their goals left open (run step 4.1) among them.
2. Print what the work cost, one command per id, each on its own: `python3 _tools/backlog.py cost --rework SP`, then the same for each story and each bug of the sprint (`python3 _tools/backlog.py tree --sprint SP` lists them). Keep each output for step 4 and the close retrospective; a cost read while the sessions that did the work are still open is provisional (the output says `open session figures` or `no figure yet`; the zeros beside them mean the open sessions are not distilled into sidecar lines yet, not no work: their usage rows are in the spool and the `open session figures` block prints them apart, and only `no figure yet` says the spool holds no usage row to read): the review says the figures are provisional, never reports those zeros as the sprint's cost; an id whose output is the header and one `no capture: ...` or `no item line: ...` line, with no table, has no figure: the review quotes that line for it and records no zero (SP-fvztfmtm closed with zeros because no work sidecar had been delivered); and close reruns `backlog.py cost --rework SP` once those sessions have closed, writing that rerun's figures into the retrospective, or says they are still provisional; and show the operator what the sprint's work cost, which items had rework, and where shared tokens stand out. Rework is the tokens an item spent from the prompt that ran its first refused `backlog.py done` (a `done` that exited 1) to its `done`; the output lists each item that has it with its work and rework tokens, and an item with none is not listed. Say it as a measure of the work, never as blame: it names no one and no cause. It reports tokens only, no prices, and a figure whose output names an unresolved id (`no item file and no git history for ...` on stderr) is incomplete: say so with the figure.
3. A sprint that changed what the query log writes (an item whose `touches` name `_tools/querylog.py`, `_tools/ql_*.py` or a capture hook) runs the pipeline once on a copy of the real spool, never on the spool itself: copy `_cache/querylog/spool/` to `<scratch>/querylog/spool/`, write `{"mode": "local"}` to `<scratch>/querylog/config.json` (mode `local`: the delivery goes to the copy's own store, nothing is pushed), run `python3 _tools/querylog.py distill` with `CLAUDE_PLUGIN_ROOT` set to this clone and `CLAUDE_PLUGIN_DATA` to `<scratch>`, then `python3 _tools/querylog.py check <scratch>/querylog/store`. Show the operator both outputs and the run file with its usage, work and ops sidecars: an empty sidecar where the sprint's work should have written rows, or a check problem, is a gap for step 5 (SP-fvztfmtm closed with `backlog.py cost` printing zeros because no work sidecar had ever been delivered).
4. A sprint that deleted or renamed tests or tool flags runs `python3 _tools/backlog.py selectors`, which lists each check's `-k` selector with the tests it collects, and re-points or drops (`set ID --check CMD`, `drop`) each open item whose check names one that is gone. Start a fresh-context reviewer, by default a headless session as run step 3 starts a worker, on the sprint's diff (`git log --grep "KB-Work"` over the sprint's items). It runs in a worktree of its own, never in your checkout: the project settings run the SessionStart intake hook, which files drafts in the working tree it starts in, and a landing refuses a dirty tree (SP-vayhvwfy, where the reviewer started in the orchestrator's checkout and one landing was refused). Its launch:
   - worktree: `git worktree add --detach .claude/worktrees/agent-<review id> HEAD` from your clone, a detached worktree under `.claude/worktrees/` named as a worker's: `close` step 5 removes a clean one whose commit names a sprint item and says `kept` for any other, which is then the operator's to remove, never yours by hand;
   - scratch directory: `_cache/scratch/<review id>/` of your clone, outside the worktree, for its throwaway files and the brief;
   - brief: the review story's id and title, each item's goal, the cost outputs of step 2 and each goal clause a check does not read, which it reads against the diff itself, written to `<scratch>/brief.md` and sent on stdin as `dispatch` sends a worker's (a trailing prompt argument is swallowed by `--add-dir`);
   - command: `claude -p --model sonnet --effort high --output-format json --add-dir <scratch> --max-turns N` (the project settings, so no `--setting-sources`; the session model only when the operator asks for it; `N` the cap run step 3 gives a story with no tasks, never an uncapped run), started in a subshell `( cd <worktree> && ... )` as a background command with `timeout` 7200000 ms, its output to `<scratch>/result.json`; its working directory is the worktree, never your clone. On the fallback it is a subagent on `subagent_type: "general-purpose"` with `model: "sonnet"`, which has no working directory of its own: its brief names the worktree and it runs `git -C <worktree>` commands;
   - read-only: its brief says it edits no file, commits nothing, files no item and writes only under its scratch directory, and runs no whole `python3 _tools/tests.py` (a `-k` selection takes no host lock). It reports only gaps that affect correctness or a goal; the cost is context for them, not a gap to report, and you file them in step 5.
   Run the whole `python3 _tools/tests.py` only after the reviewer has returned: a run beside the reviewer's session took 21 s against the 20 s darwin ceiling (SP-rvslem3h), so the review story's check and the `done` of step 6 come after it, never while its session runs.
5. File an `S1` gap as a bug in this sprint (`/kb-backlog bug`). Park every other gap: file it as a draft in no sprint, under its epic or none (`backlog.py new bug|story` without `--sprint`), and add a link naming this review (`python3 _tools/backlog.py set ID --add-link 'parked: SP-... review'`); it joins a sprint only as plan step 2 says.
6. `python3 _tools/backlog.py done <review id> --commit --trailer 'Co-Authored-By: ...'`, then `python3 _tools/kbgit.py sync --push`. The review's done also re-runs the checks of every done item of the sprint once on the tip and refuses, naming each, when one fails there: reopen that item (`backlog.py reopen ID --why ...`) and fix it, or fix its check, before the review is done. A check or repro whose test run selects no test, because a later change deleted the test it names, prints as `gone` and does not refuse.

## close SP
Rules of this step: `python3 _tools/rag.py pack --root _self --set kb-sprint:close`.

1. `python3 _tools/backlog.py close SP --summary` prints one line per item close will delete, then each goal clause with the item that carried it or `unmet` and where it went (an unmet clause goes into the retrospective) (id, title, kind, status and the commit `done` recorded, or `no evidence commit`) and changes nothing. It refuses while anything is open. Keep its `delivered by` list for the commit body.
2. **Retrospective.** From this sprint's evidence, list what went wrong in the process, not in the product:
   - a `done` that refused;
   - a check that passed although the item did not work;
   - each bug fixed in the sprint, with what let it through;
   - a gate that should have been asked earlier;
   - a subagent brief that missed something;
   - a rule in `kb/_self/backlog.md` or a skill that got in the way;
   - what cost more than its size suggested, and the items with rework, from `backlog.py cost --rework SP` rerun now, once the sprint's sessions have closed (tokens only; still `open session figures`: say the figures are provisional).
   Show the list to the operator. Each change they accept is parked: a draft story in no sprint (`/kb-backlog`) naming the failure it answers, under its epic or none, with a link naming this close (`python3 _tools/backlog.py set ID --add-link 'parked: SP-... close'`); it joins a sprint only as plan step 2 says. Write nothing into the docs directly.
3. `python3 _tools/backlog.py close SP --commit --trailer 'Co-Authored-By: ...'` deletes the sprint, its items and the epics they finished, and commits that with `KB-Work: SP-...` in the last trailer paragraph and a body that lists:
   - the `delivered by` list `close --summary` printed, as it is;
   - the retrospective's findings, each with the story it became or "no change", added above the trailers with `git commit --amend`.
4. `python3 _tools/kbgit.py sync --push`.
5. **Clean up** once the close commit is pushed: nothing to remove by hand, `close` already did it as a python process of its own, because `git worktree remove` and `git branch -D` are denied to agents in `.claude/settings.json`. After `close` deleted the sprint it removes, in the clone it ran in and never with `--force`: the sprint's clean detached or `work/<id>` `agent-*` worktrees, the sprint's `work/<id>` branches and the `worktree-agent-*` branches whose tip is on the integration main: the harness makes one for each subagent worktree and it stays at its base commit while the subagent works on `work/<id>`, so it has no commits and no `KB-Work` trailer, and `close` counts it a leftover when it has no commits beyond `origin/main`, no worktree has it checked out and its `agent-<x>` worktree, read before any removal, is not another sprint's worker (that one is kept, naming the worktree) (a branch goes only with `git branch -d` semantics: every commit on `origin/main`). `close --summary` removes nothing, and a failing cleanup never undoes the close.
   1. Report what `close` printed: each `removed` and `deleted` line, and each `close: kept <path or branch>: <reason>` line (a commit `origin/main` lacks, uncommitted files, a lock, a live process, the worktree `close` ran in, another sprint's leftover).
   2. A kept item stays until its reason is gone: do not remove it by hand, never with `--force`, and name it in the report for the operator. Never touch another sprint's worker worktrees or branches, or `_cache/querylog/worktree`.
   3. `close` cleans only the clone it ran in: when a worker ran in another clone or a container, name that clone in the report for the operator (its `git worktree list` shows what is left).

## Self-check
`python3 _tools/backlog.py selfcheck` (read only, capped; its one network call is the read of each claimed item's `code/<id>` request, `unknown:forge` when it fails) opens every pass of `run`, before `stalled`: one line when all of seven checks hold, else a line for each that failed (`FAIL`, exit 1) or could not be read (`UNKNOWN`, never a failure: read that input by hand), with its remedy. Act on a failure before dispatching, or record why you cannot (a gate). The checks and what each does on failure:
- `allow-rules`: a command the skills run, or a tool the loop calls, has no allow rule in `.claude/settings.json`: ask the operator; the settings are the operator's, a run never edits them, and the item that needs the refused command is released and the command named.
- `checkout`: the orchestrator's clone is a linked worktree of another checkout, so its workers' worktrees land there: use a standalone `git clone` as the orchestrator's clone.
- `hooks`: the commit hooks or the plugin are not installed: run `/kb-setup` (`python3 _tools/kbgit.py install-hooks`) before any commit.
- `host`: the load is over its per-core limit, or a host lock has been held past `HOST_LOCK_WAIT_S` by a live process: dispatch fewer workers; a worker waits its turn for the host test lock, and a `tests.py -k NAME` selection takes none; end a lock's holder only when it is yours and stuck.
- `claims`: a claimed item shows `claim-no-commit`, `returned-no-commit`, `returned-staged` or `mr-dead`: act on it as Stalled work says.
- `orphans`: a process in a checkout of the clone runs on after its parent is gone (`procs` lists each with its pid and checkout): end it if it is yours, or ask the session that left it; nothing ends it for you.
- `main`: the newest `ci.pipeline` row is red: file it as a bug (`python3 _tools/backlog.py red-pipeline`) and take the next ready item; with no row the check is `UNKNOWN`: `python3 _tools/backlog.py red-pipeline --status` reads the forge.

## Stalled work
Stalled work is claimed or ready work that makes no progress, or is hampered. `python3 _tools/backlog.py stalled` lists it (read only, exit 0, `--json` for one object; its one network call is the read of each claimed item's `code/<id>` request): each claimed or ready item, its id and title together, with its signals. Run it at step 1 of every pass of `run`, before claiming. Its named limits (`CLAIM_NO_COMMIT_S`, `RETURNED_GRACE_S`, `DONE_REFUSED_N`, `CHECK_TIMEOUT_N`, `LAND_SAME_STEP_N`, `HOST_LOCK_WAIT_S`) are in `_tools/bl_stall.py` and `kb/_self/backlog.md`. A signal whose input cannot be read shows as `unknown:<what>`: read that input by hand, never assume it is fine.

The signals:
- `claim-no-commit`: a claim with no work commit past the limit.
- `returned-no-commit`: a worker's worktree with no live process and no commit.
- `returned-staged`: the same with staged or modified files left: the worker waited for a background-run completion notice that never came.
- `done-refused`: `done` refused repeatedly.
- `check-timeout`: a check ran out of its time twice.
- `land-same-step`: `land` stopped at the same step twice.
- `mr-dead`: a claimed item's `code/<id>` merge request is not merged and will not merge by waiting: its pipeline failed, was canceled, skipped or is manual, or its merge status needs a push, a rebase, an approval or a resolved thread. Its work is pushed: read the request and what holds it before any release. A read that fails shows as `unknown:forge`, never as this signal.
- `red-main`: the newest pipeline row is red.
- `lock-wait`: the host test lock held past the limit.

What to do is the orchestrator's call, one step at a time, while a ready item with no signal remains to be taken meanwhile:
- finish a `returned-staged` item in the orchestrator (stage, commit with `KB-Work: <id>` in the last trailer paragraph), then run its checks in the foreground, never as a background command whose completion notice a session must wait for;
- send the work back once (`claude -p --resume <session_id>` for a headless worker, the `session_id` of its JSON output; SendMessage for a fallback subagent) with a narrower request: one file, one test selector, a foreground run; for `lock-wait` a `-k` selection, which takes no host lock;
- `python3 _tools/backlog.py release ID`, then dispatch it again (`run` step 3) with the failure named in the brief;
- file what blocks the item as a story or a bug (`/kb-backlog`), release the item and take the next ready item;
- ask the operator, with a gate (`gate add ID ...`) when the answer decides the item's work.
