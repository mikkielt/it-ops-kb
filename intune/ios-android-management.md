# Intune iOS/iPadOS and Android device management

## Summary
iOS/iPadOS enrollment splits into supervised **Automated Device Enrollment (ADE)** for corporate-owned devices (Apple Business Manager/Apple School Manager tokens; setup shared with macOS, see `intune/macos-management.md`), **Apple Configurator** direct enrollment for existing/unregistered devices, and unsupervised **BYOD** options — **Device enrollment with Company Portal**, **web-based device enrollment**, and **Account driven user enrollment** (Apple User Enrollment, a separate managed-Apple-ID-backed volume that keeps work data apart from personal data; the older "User enrollment with Company Portal" is deprecated for new enrollments). Android splits into **Android Enterprise** (managed Google Play-based: personally owned work profile / BYOD, corporate-owned fully managed (COBO), dedicated (COSU) kiosk, corporate-owned work profile (COPE)), **Android (AOSP)** for devices without Google Mobile Services, and the deprecated **Android device administrator (DA)**. Both platforms enroll through a Microsoft-specific token/binding step (Apple ADE token + MDM push certificate; managed Google Play binding) that is separate from the per-device enrollment method (QR code, zero-touch, NFC, token, Company Portal). This article does not repeat the ABM/ASM token or Apple MDM push-certificate setup steps already documented in `intune/macos-management.md`; it focuses on iOS/iPadOS- and Android-specific enrollment types, ownership models and their constraints. See `intune/mobile-enrollment-types.csv` for a platform/ownership/method matrix.

## Facts

### iOS/iPadOS: ADE (supervised) enrollment paths
- ADE devices support Enrollment **with user affinity** (single assigned user) or **without user affinity** (userless/shared/kiosk, including Apple Shared iPad — Setup Assistant panes are automatically skipped for Shared iPad). [DOC S-wdoafrjc]
- For user-affinity ADE, admins choose the authentication method before creating the enrollment policy: **Setup Assistant with modern authentication** (recommended: user enters Entra credentials directly in Setup Assistant, device is fully Entra-registered when Company Portal is installed via VPP) or the **Company Portal app** (choose this when you need MFA, expired-password reset prompts, wipe capability, or automatic Company Portal install via VPP without requiring an Apple ID sign-in). **Setup Assistant (legacy)** is not recommended; user affinity is not supported at all on tvOS/visionOS. [DOC S-wdoafrjc]
- Company Portal install method for ADE devices matters: **VPP token + Install Company Portal with VPP** (recommended) is a one-time install with automatic updates and doesn't require the user's personal Apple ID; without a VPP token, the user must sign in to the App Store with an Apple ID (a personal iCloud or Gmail-based Apple ID) to get Company Portal, which slows enrollment and, if skipped, leaves the device unregistered in Entra ID (noncompliant, Conditional Access resources unavailable). [DOC S-wdoafrjc]
- Already-enrolled ADE devices get Company Portal pushed via an **app configuration policy** that marks it a required, device-licensed app assigned to the same group as the enrollment policy — this avoids re-enrollment and keeps the app current through the existing policy. [DOC S-wdoafrjc]
- **Supervised** mode (Yes/No on the enrollment policy) unlocks more management options and disables Activation Lock by default; devices show "This iPhone is supervised and managed by `<organization>`" in Settings. ADE is the recommended way to get supervised mode at scale — a device enrolled unsupervised can only become supervised via Apple Configurator (USB, factory reset required). Apple Shared iPad for Business **must** be supervised. [DOC S-w2fd3dgm]
- **Locked enrollment** (Yes/No) hides the "Remove Management Profile" button in Settings so users can't unenroll; required (Yes) for Microsoft Entra shared device mode. On devices added to ADE after original purchase (not bought through Apple Business/School originally), the remove-management button stays visible for the first 30 days after activation regardless of this setting. Company Portal's Remove Device/Factory Reset self-service actions are unavailable on ADE-enrolled devices regardless of Locked enrollment. [DOC S-w2fd3dgm]
- ADE supports Entra shared device mode for frontline scenarios and Apple Shared iPad on iPadOS (both listed as supported scenarios alongside supervised mode, zero-touch, bulk enrollment, and single-user or userless devices); BYOD/personal devices, DEM accounts, and side-by-side management with another MDM are not supported. [DOC S-yiwjr2wo]
- ACME certificate issuance for the ADE management profile requires **iOS 16.0+ / iPadOS 16.1+**; devices already enrolled don't get an ACME cert unless re-enrolled (shared fact with macOS ADE — see `intune/macos-management.md`). [DOC S-yiwjr2wo]

### iOS/iPadOS: BYOD enrollment (device enrollment vs. Apple User Enrollment)
- **Device enrollment with Company Portal**: full device management (not just an app/feature), can deploy device-wide certificates, requires a user affinity (can be a DEM account); only ADE-enrolled devices can receive OS updates via MDM policy — plain device-enrolled BYOD devices cannot be forced to update via MDM. **Web based device enrollment** (iOS 15+) is the same flow via the Company Portal website instead of the app, letting users without a managed Apple ID enroll and access VPP apps. [DOC S-wdoafrjc]
- **Account driven user enrollment** (Apple User Enrollment, iOS/iPadOS 13+ — full feature set from iOS/iPadOS 15+) creates a separate managed **APFS volume** on the device for work data/apps, keeping it apart from personal data; supervision is never available with this method. Devices on iOS/iPadOS 14.9 or earlier that are assigned an account-driven profile fall back to the deprecated Company-Portal-based flow automatically. [DOC S-7synnxi2]
- Apple User Enrollment (either method) needs **Managed Apple IDs** for users, or **federated authentication** (Apple Business linked to Entra ID) so users sign in with their normal work credentials instead of a separate Apple ID. [DOC S-wdoafrjc]
- Apple User Enrollment limitations: no app inventory or certificate/provisioning-profile inventory outside the managed APFS volume; no UDID or other persistent device identifiers (serial number, IMEI, phone number) collected; no SCEP user profiles with Subject Name Format = Serial Number; can't install App Store apps as managed, and can't take over management of apps outside the managed volume (app protection policies still apply to them) unless the user deletes and reinstalls; each enrollment gets a unique ID that does not persist after unenrollment. [DOC S-7synnxi2]
- Account-driven user enrollment requires publishing an unauthenticated **service-discovery file** at `https://<your domain>/.well-known/com.apple.remotemanagement` (no file extension, `application/json` content type) on the same domain users sign in with, pointing Apple at the Intune enrollment endpoint (`https://manage.microsoft.com/EnrollmentServer/PostReportDeviceInfoForUEV2?aadTenantId=<tenant-id>`, `manage.microsoft.us` for GCC/US Gov, a separate endpoint for the China 21Vianet cloud). [DOC S-fdtw5sil]
- Devices running iOS 15.5 can't complete Apple User Enrollment if MFA needs a text or call during enrollment; iOS 15.7–16.3 can't enroll while using text-based MFA (phone-call MFA works). [DOC S-7synnxi2]
- Comparison: account-driven user enrollment supports just-in-time registration and needs only Microsoft Authenticator; the deprecated Company-Portal-based user enrollment additionally needs the Intune Company Portal app for iOS and routes the user through Company Portal, Safari, and Settings across several screens. Neither supports supervision. [DOC S-7synnxi2]

### iOS/iPadOS: DDM (declarative device management)
- On iOS/iPadOS 15+ devices enrolled via **User Enrollment**, settings-catalog configuration automatically uses **DDM**; if DDM isn't available, the device falls back to Apple's standard MDM protocol. All other iOS/iPadOS devices continue on standard MDM unless a feature (e.g. software updates) is explicitly DDM-based. [DOC S-27rerlcs]
- Apple has deprecated MDM-based software update workloads; Intune is moving iOS/iPadOS **17.0+** and macOS **14.0+** software updates to DDM (Settings catalog > Declarative Device Management > Software Update), which lets the device manage the full update lifecycle (prompt, download, prepare, install) instead of Intune scheduling a fixed install. Supervised-device MDM-based update policies (iOS/iPadOS 10.3–18, supervised) remain documented but are being phased out. [DOC S-27rerlcs, S-4hhozw7m]
- Line-of-business iOS/iPadOS apps and Apple VPP tokens can set **Management type: MDM** (default) or **DDM**; DDM app management (iOS/iPadOS 18+) gives efficient delivery and real-time status but is unavailable for Intune-App-SDK/MAM-integrated apps (management type is then forced to MDM), doesn't work with app configuration policies (MDM-only), and — for VPP-token DDM apps — doesn't yet support "Available" assignments (Required/Uninstall only). [DOC S-27rerlcs]

### Android Enterprise: ownership models and managed Google Play
- Every Android Enterprise enrollment scenario requires the Intune tenant to be connected to a **Managed Google Play** account first (Devices > Enrollment > Android tab > Prerequisites > Managed Google Play); this binds an Entra account as the Google Admin owner and lets Intune auto-provision Company Portal, Microsoft Authenticator, Managed Home Screen and Microsoft Launcher to devices during enrollment. [DOC S-3v22wodo, S-jq73dzml]
- **Personally owned work profile (BYOD)**: personal device, mark as corporate or personal, supports DEM accounts; not for organization-owned or userless/kiosk devices. Enrolls via **web-based enrollment** (enrollment URL or redirect from Company Portal/a productivity app, Chrome-based) — the method Intune is transitioning to — or **app-based enrollment** (Company Portal from Google Play). [DOC S-3v22wodo]
- **Fully managed (COBO)**: organization-owned, single user, work-only (no personal use); requires a factory reset before enrollment; Microsoft Intune app auto-installs during enrollment. [DOC S-3v22wodo]
- **Dedicated (COSU)**: organization-owned, kiosk-style, no assigned user, DEM not supported; requires factory reset; used for scanning/ticketing/inventory devices; Managed Home Screen should be assigned for multi-app kiosk scenarios. [DOC S-3v22wodo]
- **Corporate-owned work profile (COPE)**: organization-owned, single user, allows personal use in a separate work profile; requires factory reset; DEM not supported; can be repurposed as a dedicated (userless) device post-enrollment by assigning it a "dedicated device" (Device experience) profile. [DOC S-3v22wodo]
- **AOSP (Android Open Source Project)**: organization-owned devices without Google Mobile Services (limited OEM support); can be userless or single-user but enrolls **one device at a time** (no bulk enrollment); requires factory reset (new devices may not); the Microsoft Intune app and Microsoft Authenticator app auto-install and the device stays locked in the enrollment process until it completes. [DOC S-3v22wodo]
- Enrollment methods for Android Enterprise corporate scenarios (dedicated, fully managed, COPE): **QR code** (recommended for most scenarios; tap the first screen repeatedly after a factory reset to launch the QR reader — Android 9+ has one preinstalled), **enrollment token** (type `12345`-style string; doesn't expire; not supported on COPE running Android 11.0), **Google Zero Touch** (devices purchased from an authorized zero-touch reseller; provisioning starts out of the box; linking the zero-touch account to Intune creates a default configuration that overrules the zero-touch portal's own default — for COPE/dedicated configurations, don't link the account, use the zero-touch portal directly), **Samsung Knox Mobile Enrollment (KME)**, and **NFC** (custom NFC tag; not supported on COPE running Android 11.0). Devices must not be restarted mid-enrollment or they may appear enrolled but be unmanaged. [DOC S-zdoohqe4]
- The **`afw#setup`** value entered at the Google sign-in screen (instead of a Gmail account) is the DPC identifier for provisioning Microsoft Intune as the device policy controller; it works only for full device management (fully managed), not COPE on Android 11. [DOC S-zdoohqe4]
- Factory reset protection (FRP) behavior differs by ownership after an Intune wipe: COPE keeps FRP active on both a Settings-app factory reset and recovery/bootloader reset (but not after an Intune wipe); fully managed (COBO) and dedicated (COSU) only keep FRP on a recovery/bootloader reset — none of the three retain FRP after an Intune wipe. Corporate-owned devices with a work profile on Android 15 require re-entering the associated Google account after any reset (Settings-app or Intune wipe). [DOC S-zdoohqe4]
- **Managed Google Play** offers three app types Intune can push silently without user-visible permission prompts (admin must approve permissions on users' behalf in the Managed Google Play console): **store app** (public Play Store apps, browsed/approved/synced from the Intune admin center), **private (LOB) app** (published to Managed Google Play by Intune admins or via the Google Play Developer Console — a private app can never be made public once published this way), and **web link** (a URL with an admin-defined icon and display mode; only "Custom" store-layout Collections require manual placement, "Basic" mode shows all approved apps automatically). When an app's permissions change on update, the update isn't delivered to devices until an admin re-approves the new permissions. [DOC S-jq73dzml, S-3v22wodo]

### Android device administrator (deprecated)
- Google deprecated Android device administrator (DA) management in 2020; Microsoft ended support for DA devices with access to **Google Mobile Services (GMS)** in **August 2024** (some sources also cite "end of 2024"); DA management remains supported only for Android 15-and-earlier devices **without** GMS (e.g. countries/regions where GMS isn't available), documented at `intune/app-management/manage-without-gms`. [DOC S-pcr6rjdl]
- Microsoft's recommended migration path: stop enrolling new devices with DA, use another Android Enterprise method or app protection policies instead, migrate existing DA devices (a dedicated streamlined migration flow exists for moving DA devices to personally owned work profile management), and create a device enrollment restriction blocking DA — Android devices otherwise attempt DA enrollment before other methods. [DOC S-pcr6rjdl]

## Examples
Account-driven Apple User Enrollment service-discovery file, published at `https://corp.example.com/.well-known/com.apple.remotemanagement` (no file extension, `Content-Type: application/json`) for tenant `00000000-0000-0000-0000-000000000000`:
```json
{"Servers":[{"Version":"mdm-byod","BaseURL":"https://manage.microsoft.com/EnrollmentServer/PostReportDeviceInfoForUEV2?aadTenantId=00000000-0000-0000-0000-000000000000"}]}
```

Android Enterprise fully managed provisioning: at the Google sign-in screen during out-of-box setup, enter the Microsoft Intune DPC identifier instead of a Gmail account:
```
afw#setup
```

Device enrollment restriction to block Android device administrator enrollment (create under Devices > Enrollment > Restrictions, targeting a group that includes device `PL-LT-00123`): set **Personally owned devices** and **Corporate-owned devices** platform restriction for **Android device administrator** to **Block**, leaving Android Enterprise methods **Allow**.
